# P2 组织器插件与 Codex Brainstorming 对照测试指南

**文档性质：** 长期测试指南  
**适用范围：** P2 需求分析系统、组织器插件、Codex `brainstorming` skill 对照验证  
**首次整理日期：** 2026-05-08

## 1. 指南定位

本文用于统一沉淀 P2 组织器插件验证、真实 Codex `brainstorming` skill 对照测试、长轮次决策模式分析和整改建议归纳的方法。

本文不是某一次测试报告，也不是某个组织器的设计说明。单次执行数据、运行截图、日志摘要和统计结论仍应归档到 `DOC/CODEX_DOC/06_测试文档/03_机测记录/`；本文只规定后续反复执行同类测试时应遵守的测试口径、隔离方法、数据格式和分析方法。

本文应作为以下工作的共同入口：

1. 新增一种 P2 组织器插件后的效果验证。
2. 对比 `xg-heuristic-orchestrator`、`brainstorm-v1`、Dify workflow 型组织器或远端服务型组织器的决策行为。
3. 将 P2 组织器插件与真实 Codex `brainstorming` skill 做对照测试。
4. 分析“为什么 P2 输出不如 brainstorming 直观、深入或稳定”。
5. 把测试结论反推到组织器设计、Prompt 资产、插件合同和前端观测页面。

## 4. 核心测试问题

这类测试不应只比较“写了多少字”。必须回答以下问题：

1. 组织器是否先识别关键产品决策，而不是直接填需求规格章节。
2. 组织器是否能在长轮次中维护稳定的决策链。
3. 每轮是否只提出一个最关键的下一步问题，且用户能理解为什么要问。
4. 对用户输入的组合意图、偏离选项、补充事实、反驳和改题是否能正确处理。
5. 是否存在模板章节、完成度树或硬编码规则过度牵引的问题。
6. 是否能在轮次上限或信息足够时主动收束并输出成稿。
7. 调用日志是否能复现每一阶段的模型输入、输出、输出格式要求和后处理。
8. 测试结论能否明确映射到插件 Prompt、schema、adoption、runtime 或前端观测设计。

## 5. 测试对象分类

### 5.1 P2 本地策略解释型组织器

典型对象：

```text
orchestrators/xg/xg-heuristic-orchestrator/
orchestrators/xg/brainstorm-v1/
```

测试重点：

1. 插件 manifest 是否可发现。
2. adapter 是否只通过统一运行时端口与宿主交互。
3. Prompt、schema、adoption、spec_strategy 是否承担主要业务判断。
4. Python 代码是否只做合同校验、字段映射、状态归并和错误处理，不做章节匹配、业务拒绝、下一问选择等智能判断。

### 5.2 Dify workflow 型组织器

典型对象：

```text
orchestrators/xg/brainstorm-v1-dify-workflow/
```

测试重点：

1. Dify 输入字段是否与 P2 插件输入合同一致。
2. Dify 输出字段是否能归一化为 P2 `OrchestratorRunResult`。
3. Dify 内部节点能否表达 intent、decision state、write projection、next planning 等阶段。
4. P2 调用日志是否能看到 workflow 请求、原始输出和归一化结果。

### 5.3 远端服务型组织器

远端服务型组织器后续接入时，应按同一合同测试。区别只在于 transport 和认证方式，不改变 P2 侧对组织器的判断口径。

### 5.4 Codex Brainstorming Skill

真实 Codex `brainstorming` 不是 P2 插件，也不是需求规格正文 patch 系统。它是 Codex 本地 skill，通过 `SKILL.md` 约束模型行为。

因此，对照测试不能把 P2 的正文写入量作为唯一指标；应重点比较它的决策推进方式：

1. 是否先判断项目范围和关键风险。
2. 是否一轮一个主问题。
3. 是否给出选项、推荐和理由。
4. 是否在信息足够后进入方案比选。
5. 是否在用户要求或轮次上限时主动成稿。

## 6. 标准测试场景

### 6.1 基准起始输入

后续默认使用以下起始输入作为基准场景：

```text
我希望创建一个态势分析系统。这个态势分析系统里面要有态势的展示，要有一系列态势分析工具，比如地理信息分析工具、通视量算、坡度分析，还有部署分析系统。但是当前用户、使用模式我都没有想清楚，希望你来一块帮我想清楚。
```

### 6.2 标准 20 回合输入链路

当需要比较长轮次决策模式时，使用以下输入链路：

| 回合 | 输入摘要 |
| ---: | --- |
| 1 | 起始模糊需求：建设态势分析系统，含态势展示、GIS 分析、通视量算、坡度分析、部署分析，用户与使用模式未明确。 |
| 2 | 主用户：参谋分析员；下游查看者：指挥员。 |
| 3 | 主场景：实时态势，兼顾事前研判；给出典型流程。 |
| 4 | 数据模式：混合模式；实时接入态势与告警，导入底图、任务区、DEM、部署点位和标注。 |
| 5 | 部署影响分析边界：覆盖与冲突分析，不做自动最优推荐。 |
| 6 | 协同模式：中协同，支持结果共享与接力编辑，不做强实时共编。 |
| 7 | 指挥员消费方式：系统内指挥视图 + 导出报告和图件。 |
| 8 | 刷新方式：准实时刷新，普通态势 10-30 秒，关键告警尽快推送。 |
| 9 | 角色权限：管理员、参谋分析员、指挥员、情报分析员、值班操作员。 |
| 10 | 非功能与部署：2 秒地图查询、10 秒分析、30 并发、权限分级、审计、离线底图、内网/专网。 |
| 11 | 精度口径：辅助研判级，不承诺测绘工程级精度。 |
| 12 | 导出形式：专题图件 + 简化研判报告。 |
| 13 | 明确不做范围。 |
| 14 | 异常与补偿机制。 |
| 15 | 验收任务链。 |
| 16 | 主要界面列表。 |
| 17 | 安全要求。 |
| 18 | 回看：哪些关键决策已闭合、哪些未闭合。 |
| 19 | 补充剩余未闭合项：GIS 数据接入优先方式、模板先固定。 |
| 20 | 强制停止追问，输出完整需求规格说明草案。 |

### 6.3 变体测试场景

后续至少应补充以下变体：

1. 用户只回答选项，不补充事实。
2. 用户选择选项并补充关键事实。
3. 用户完全忽略选项，提出新方向。
4. 用户反驳组织器建议。
5. 用户要求回到前面章节或前面决策点。
6. 用户给出互相冲突的信息。
7. 用户要求提前成稿。
8. 用户要求停止追问但保留未闭合问题。

## 7. P2 组织器测试方法

### 7.1 测试入口

优先使用真实后端 API，而不是直接调用内部函数：

```text
POST /api/requirement-analysis/sessions
POST /api/requirement-analysis/sessions/{session_id}/turns
```

可使用 `FastAPI TestClient(create_app())` 在本地进程内执行，避免浏览器操作不稳定影响测试。

### 7.2 必备配置

每次报告必须记录：

| 字段 | 说明 |
| --- | --- |
| 组织器 ID | 例如 `xg-heuristic-orchestrator`、`brainstorm-v1` |
| Provider | 例如 DeepSeek、Mock Provider、Dify workflow |
| 模型 | 真实模型名称或 mock 标识 |
| 模板实例 | 本次使用的需求规格说明模板实例 |
| 启动参数 | 会话 topic、写入策略、知识包、模板等 |
| 代码提交 | 当前 git commit hash |
| 测试方式 | API、页面、人测、脚本或混合 |

### 7.3 必采数据

每轮至少保存：

1. 用户输入。
2. 助手可见回复。
3. 临时正文或结构化承载页快照。
4. 决策链状态快照。
5. 下一步交互规划。
6. Provider 调用日志数量。
7. 每次 Provider 调用的阶段 ID、Prompt ID、输入摘要、输出摘要和后处理结果。
8. 错误、重试、降级或空输出情况。

如果页面已经提供调用详情，应优先导出页面展示字段；如果页面无法导出，应从后端响应和数据库快照中补齐。

## 8. Codex Brainstorming 对照测试方法

### 8.1 必须隔离运行

真实 Codex `brainstorming` 测试必须在独立临时 git 仓库或临时目录中运行，不能直接在 CodeFactoryV2 工作树中运行。

原因是 Codex 会读取当前项目上下文。如果在 CodeFactoryV2 仓库中测试，它可能读到 P2 设计文档、代码和已有测试报告，导致测试污染。

推荐目录形态：

```text
/tmp/codex-brainstorm-compare.<random>/
```

目录内至少执行：

```bash
git init
```

### 8.2 执行方式

首次启动可使用：

```bash
codex exec --json --dangerously-bypass-approvals-and-sandbox \
  --output-last-message "$OUT" \
  "请使用真实 brainstorming skill 和我进行需求探索，不要写代码。不需要浏览器。我的初始想法是：..." \
  > "$JSONL" </dev/null
```

续接可使用：

```bash
codex exec resume --json --dangerously-bypass-approvals-and-sandbox \
  --output-last-message "$OUT" \
  "$THREAD_ID" \
  "用户下一轮输入..." \
  > "$JSONL" </dev/null
```

### 8.3 必采数据

每轮至少保存：

1. thread ID。
2. 用户输入。
3. Codex 最后一条回复。
4. jsonl 原始事件。
5. 输出长度。
6. 是否提问。
7. 是否给选项。
8. 是否给推荐。
9. 是否进入方案比选。
10. 是否主动成稿。

### 8.4 污染样本处理

如果发现某轮 Codex 回复引用了 CodeFactoryV2 当前项目、P2 文件、既有测试结论或本不应知道的上下文，该样本必须标记为污染样本，不得纳入统计结论。

污染样本可以在报告中说明，但不能用于支持能力判断。

## 9. 对比指标

### 9.1 量化指标

| 指标 | 含义 |
| --- | --- |
| 总轮次 | 每组会话执行轮次 |
| 平均助手回复长度 | 判断用户可见层是否过短 |
| 中位数助手回复长度 | 排除极端长回复干扰 |
| 长回复轮次 | 例如超过 300 字的轮次 |
| 最终正文长度 | 判断成稿规模，但不能单独代表质量 |
| 正文长度回落次数 | 判断补丁应用是否覆盖或丢失 |
| Provider 调用次数 | 判断阶段链路是否按设计执行 |
| 决策项增长数 | 判断决策链是否推进 |
| 未闭合问题数量变化 | 判断是否收束 |
| 成稿轮次 | 判断系统何时进入落稿 |

### 9.2 行为指标

| 指标 | 观察点 |
| --- | --- |
| 首轮行为 | 是直接写章节，还是先识别关键决策 |
| 下一问质量 | 是否一轮一个主问题，是否有理由 |
| 组合意图处理 | 是否同时吸收选项选择和补充事实 |
| 偏离输入处理 | 是否能识别用户正在换题或新增方向 |
| 反驳处理 | 是否能修正前一轮判断 |
| 决策链连续性 | 是否重复问已经闭合的问题 |
| 方案比选能力 | 是否能提出 2-3 个路径并推荐 |
| 收束能力 | 是否能在信息足够或上限到达时主动成稿 |
| 可观测性 | 是否能从日志解释为什么这么问、为什么这么写 |

```text

## 6. Codex Brainstorming 测试过程与数据
## 7. 量化统计
## 8. 代表轮次摘录
## 9. 决策模式对比
## 10. 根因分析
```

报告正文必须包含足够的测试数据，不能只给结论。至少应包括每组每轮的输入摘要、输出摘要、输出长度、阶段判断和关键异常。

## 11. 判断规则

### 11.1 不能接受的测试结论

以下结论不充分：

1. “输出少，所以效果差。”
2. “调用了多次模型，所以链路合理。”
3. “正文有内容，所以本轮成功。”
4. “Brainstorming 更像人，所以应该照抄。”
5. “Mock Provider 通过，所以真实模型也会通过。”

### 11.2 可接受的测试结论

可接受结论应满足：

1. 有原始输入输出证据。
2. 有至少一组完整长轮次链路。
3. 有 P2 与对照对象的同题比较。
4. 能指出差异发生在哪个阶段或哪个合同字段。
5. 能区分模型能力问题、Prompt 资产问题、状态设计问题、后处理问题和前端展示问题。
6. 能提出可验证的整改方向。

## 12. 测试到设计的回写规则

测试报告形成后，应按以下顺序处理：

1. 先判断问题是否只是实现缺陷。
2. 如果是实现缺陷，进入研发计划或 issue。
3. 如果涉及概念、边界、状态机、Prompt 阶段、插件合同或页面观测模型，应形成设计补充稿。
4. 设计补充稿经审阅后，归并到 `P2-需求分析系统设计.md`。
5. 主设计文档归并后，再进行代码实现或测试脚本固化。
6. 实现完成后，再用本指南规定的同类测试验证设计是否兑现。

## 13. 经验结论

截至 2026-05-08，已有测试形成以下稳定经验：

1. 真实 Codex `brainstorming` 的优势主要来自连续决策过程，而不是单轮输出更长。
2. P2 不能直接照搬 `brainstorming`，因为 P2 还要承担模板适配、结构化状态、正文投影、调用日志和组织器插件合同。
3. P2 要接近 `brainstorming` 的体验，关键不在于增加固定规则，而在于让组织器插件用模型阶段维护决策链，并把下一步问题生成交给模型判断。
4. `write` 在探索收束阶段不应被理解为“补齐需求规格正文”，而应被理解为把当前结构化决策状态可视化、可审阅地投影出来。
5. 单次短链路测试不足以评价 `brainstorming` 类能力；长轮次测试应至少覆盖 10 轮，完整对比建议使用最多 20 轮。
6. Codex skill 对照测试必须隔离工作树，否则会被项目上下文污染。
7. 组织器插件测试必须同时看用户可见回复和 Provider 调用日志；只看正文长度会误判问题。

## 14. 后续维护要求

后续每次完成新的组织器插件、Dify workflow、远端组织器接入或 Prompt 策略升级后，应至少执行一次本指南下的对照测试。

如果测试过程中出现新的稳定经验，应更新本文；如果只是某次样本现象，应只写入对应机测记录，不直接改本文。
