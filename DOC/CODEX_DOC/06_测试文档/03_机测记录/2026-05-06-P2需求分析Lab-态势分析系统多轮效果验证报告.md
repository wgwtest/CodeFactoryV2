| 4 | 数据、功能范围与排除项 | 数据主要来自地图底图、目标位置、任务区域、地形高程、部署点位和人工录入信息。第一阶段先做态势展示、地图交互、测距测面、通视分析、坡度分析、部署影响分析、结果保存和报告导出，不做历史推演、AI自动决策和跨部门流程编排。 |
| 5 | 非功能与验收 | 非功能方面，希望普通地图浏览和查询在2秒内响应，常用分析工具在10秒内返回结果；支持至少30个并发用户；要有权限分级、操作审计、离线底图部署能力。验收时要能完成一条从态势查看到分析工具使用再到结果导出的完整任务链。 |

## 8. P2 与真实 brainstorming skill 的差异

### 8.1 对照口径差异

| 维度 | P2 当前 Lab | Codex 真实 brainstorming skill |
| --- | --- | --- |
| 主要目标 | 把用户输入转成需求规格临时正文和 patch。 | 通过自然对话收束用户意图、方案和设计。 |
| 每轮产物 | 临时正文、修订片段、下一问。 | 一个澄清问题或阶段性整理，不急于写正文。 |
| 对话形态 | “本轮写入了哪些章节 + 下一步确认”。 | “为什么先问这个 + 选项 + 推荐或风险提示”。 |
| 状态推进方式 | 依赖组织器阶段和文档 patch。 | 依赖逐问澄清和显式决策点。 |
| 是否可比正文增量 | 可统计。 | 不适用。 |

### 8.2 交互组织差异

真实 `brainstorming` skill 的前三个高频决策点非常稳定：

1. 先确认主用户。
2. 再确认核心使用场景或工作流。
3. 再确认数据来源、协同深度、能力边界等影响架构和范围的关键变量。

P2 当前 Lab 的组织方式不同：

1. 第一轮就尝试把内容写入多个需求规格章节。
2. 用户可见回复主要是章节写入清单。
3. 下一问有时没有明显吸收上一轮已回答内容。
4. Review 和规划阶段即使存在，也没有充分变成用户可见的解释。

### 8.3 用户感知差异

真实 skill 让用户觉得“被带着思考”的原因不是单纯字数更长，而是它在每轮里做了三件事：

1. 说明当前最该决策的问题是什么。
2. 给出有限、互斥、可选择的选项。
3. 解释为什么这个问题会影响复杂度、边界、架构或第一版范围。

P2 当前 Lab 则更像“需求规格正文补丁生成器”：

1. 它写正文的量不低。
2. 它没有把写入前后的判断过程讲清楚。
3. 它的问题规划没有稳定形成“一个关键问题推动一个关键决策”的感觉。

## 9. 根因判断

### 9.1 原错误对照的根因

上一版报告把“Brainstorming”误解为可以用一条参考 Prompt 模拟的效果组。这是错误的。真实 `brainstorming` skill 是 Codex 的流程技能，包含流程顺序、项目上下文探索、逐问澄清、设计审批和文档落地要求。它的行为来自 skill 规则和 Codex 会话状态，不是来自单次模型调用。

因此，模拟参考组的统计值不能作为判断依据。

### 9.2 P2 当前体验不理想的根因

基于 P2 真实数据和真实 skill 样本，当前 P2 的主要问题可以归纳为：

1. P2 的正文生成能力已经存在，但对话组织能力不足。
2. P2 的最终助手回复过度模板化，无法呈现“我为什么这么理解、为什么这么写、为什么下一步问这个”。
3. P2 的下一步规划没有稳定围绕关键产品决策展开，而是容易围绕需求规格章节或未闭合清单展开。
4. P2 的四阶段模型调用没有充分转化为用户可感知的沟通质量。
5. P2 目前更重“写入需求规格”，真实 `brainstorming` skill 更重“先把需求决策想清楚”。

## 10. 结论

本次修正后的结论如下：

1. P2 当前 Lab 可以连续生成临时正文，正文累计量并不低。
2. 用户认为效果不理想，不是因为系统完全没有输出内容，而是因为对话层缺少清晰的理解、判断、取舍和牵引。
3. 上一版“Brainstorming 参考组”是错误对照，已经作废，不能继续作为证据。
4. 真实 Codex `brainstorming` skill 的核心优势是流程化逐问澄清：先用户、再场景、再数据、再边界、再协同或质量约束。
5. P2 后续优化不应简单增加助手回复字数，而应让每轮回复明确承载：本轮理解、关键决策点、已吸收内容、仍未闭合问题、下一问理由。

## 11. 后续建议

后续如果要让 P2 Lab 靠近真实 `brainstorming` skill 的效果，建议优先处理：

1. 把下一步规划从“补哪个规格章节”调整为“当前最关键的产品决策是什么”。
2. 最终助手回复不要只列写入章节，应展示本轮理解、正文吸收、质量回看和下一问理由。
3. 下一问必须保持单点牵引，优先使用有限选项，且说明每个选项对范围、复杂度或架构的影响。
4. Review 阶段需要判断“本轮是否真正关闭了某个关键问题”，并把结果传给下一步规划。
5. 后续回归测试应继续使用真实 Codex `brainstorming` skill 作为行为参照，不能再用自造 Prompt 代替。
