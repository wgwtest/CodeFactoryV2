**测试对象：**

- `P2`：`xg-heuristic-orchestrator`

## 1. 测试目标

本次测试重点回答四个问题：

1. `P2` 和真实 `Codex Brainstorming` 在长轮次对话中分别如何做决策。
2. 两者的决策推进是否稳定，是否会出现重复、覆盖、跳跃或异常收束。
3. 在明确给出“最多 20 回合，到第 20 回合必须停止并产出草案”的条件下，两者的最终交付形态有什么差异。
4. 基于这些差异，`P2` 的优化重点应放在哪里。

## 6. 决策模式差异分析

### 6.1 P2：章节驱动、写入优先、对话压缩

从 60 回合数据看，P2 的核心决策模式是：

1. 先根据当前输入判断目标章节。
2. 立即尝试写入临时正文。
3. Review 判断当前章节是否“可接受”。
4. Planning 生成下一问。
5. 最终对话只保留“本轮写入了哪些章节 + 下一步确认”。

这带来三个后果：

1. `写入优先`：正文块增长很快。
2. `对话压缩`：用户看不到大部分判断过程。
3. `章节牵引过强`：下一步常围绕模板节点推进，而不是围绕“当前最关键的产品决策”推进。

### 6.2 Brainstorming：问题驱动、决策优先、文档延后

真实 `brainstorming` 的核心模式完全不同：

1. 每轮只抓一个关键决策点。
2. 通常给出互斥选项。
3. 明确说明为什么这个问题重要。
4. 在关键边界足够闭合前，不急于写需求正文。
5. 到后期再进入方案比较、闭合判断和文档草案输出。

这带来两个直接收益：

1. 用户始终知道“为什么现在问这个”。
2. 当进入文档输出时，草案已经建立在一串连续决策链上，而不是碎片 patch 上。

### 6.3 P2 的“整体复核”与 Brainstorming 的“草案交付”不同

两者都在后期进入回看阶段，但落点不同：

- `P2`：回看后仍倾向继续让用户“整体复核当前草案”
- `Brainstorming`：回看后会把已闭合决策直接组织成一版可阅读的需求草案

这说明 P2 目前缺的不是“回看阶段”，而是：

1. 回看结果如何驱动“最终成稿”。
2. 最终成稿如何进入用户可见层。

## 7. 关键问题定位

### 7.1 P2 的正文状态稳定性不足

P2 三组都发生了正文长度回落：

- P2-1 最大回落 696 字
- P2-2 最大回落 46 字
- P2-3 最大回落 713 字

这说明 P2 的临时正文不是稳定单调收敛，而存在覆盖、压缩或重组。对调试而言，这比“最终字数多少”更关键，因为它会弱化用户对成稿稳定性的感知。

### 7.2 P2 的长回复触发过晚且价值不稳定

60 个回合里，P2 只有 3 个回合助手回复超过 300 字，且都集中在第 18 回合左右。也就是说：

1. 绝大部分时间助手回复仍很短。
2. 长回复不是持续的，而像一次“整体回看爆发”。
3. 即便出现长回复，也不一定直接形成成稿交付。

### 7.3 Brainstorming 的收束点在 14-20 回合之间

真实 `Brainstorming` 的收束并不是固定发生在同一回合，但它的区间很稳定：

- 最早第 14 回合进入方案比较
- 最早第 18 回合进入草案输出
- 第 20 回合三组都能输出完整草案

这说明用“最多 20 回合”的口径测试它是合理的。

## 8. 可行优化方向

### 8.1 不要让 P2 继续只做“章节 patch 生成器”

P2 当前最强的是正文 patch 能力，但这不是用户最直接感受到的价值。优化方向应是：

1. 保留 patch 能力。
2. 让 patch 前后的判断进入用户可见层。
3. 让每轮回复承载“当前关键决策点”，而不是只承载“章节写入清单”。

### 8.2 引入“决策链状态”而不是只依赖章节树

P2 当前强绑定章节树，容易导致：

1. 追着模板节点跑。
2. 回答已给出后，仍围绕节点缺口重复推进。

建议在组织器里引入单独的“决策链状态”：

1. 主用户是否闭合
2. 主场景是否闭合
3. 数据模式是否闭合
4. 协同模式是否闭合
5. 输出形式是否闭合
6. 精度责任是否闭合
7. 部署边界是否闭合
8. 验收主链路是否闭合

章节写入继续存在，但下一问优先跟随决策链缺口，而不是章节缺口。

### 8.3 为 P2 增加“方案比较”阶段

真实 `Brainstorming` 的一个关键转折点是：

1. 连续澄清后进入 2-3 套方案比较。
2. 再要求用户确认或直接采用推荐方案。
3. 最后基于已确认方案出草案。

P2 当前缺这一步。建议在中后期加入：

- `option_comparison` 或 `solution_shape_comparison` 阶段

这样可以把散落的事实收束成一个“产品形态选择”，再进入成稿。

### 8.4 明确“第 N 回合必须成稿”的收束策略

本次测试已经说明：

- `Brainstorming` 在强制第 20 回合成稿时，能够给出较完整草案。
- `P2` 在第 20 回合仍倾向“请整体复核”。

因此 P2 需要一个显式收束规则：

1. 当关键决策链大部分闭合，或达到轮次阈值时，停止继续追问。
2. 触发“成稿模式”。
3. 向用户直接交付完整需求草案。
4. 把剩余未闭合项放在“待确认事项”章节，而不是继续保持对话悬而未决。

## 9. 最终结论

本次 3 组 × 20 回合长链路测试得出以下结论：

1. `P2` 的优势在于持续生成临时正文，但它的决策模式仍然是“章节驱动、写入优先、对话压缩”。
2. `P2` 的主要问题不是不会写，而是不会把“为什么这么写、为什么现在问这个、什么时候该停止追问并成稿”表达出来。
3. 真实 `Codex Brainstorming` 的优势在于“关键决策链驱动”：先一轮一轮钉住关键边界，再进入方案比较，再进入草案输出。
4. 对真实 `Brainstorming` 而言，5 回合测试明显不公平；20 回合口径是合理的，因为它的自然收束点通常在 14-20 回合之间。
5. 若要优化 `P2`，最值得做的不是单纯增加字数，而是：
   - 从章节驱动转向“决策链 + 章节双驱动”
   - 增加方案比较阶段
   - 增加显式成稿模式
   - 让回看结果直接驱动最终草案交付

## 10. 后续建议

建议后续把回归测试固定为两类：

1. **短链路测试**
   - 5 回合
   - 观察早期问题是否合理
   - 观察是否围绕关键决策点推进

2. **长链路测试**
   - 20 回合上限
   - 观察何时进入方案比较
   - 观察能否稳定成稿
   - 观察最终草案与待确认事项的质量

同时，P2 的下一轮优化设计应优先围绕：

1. 决策链状态模型
2. 方案比较阶段
3. 成稿触发条件
4. 用户可见层的判断解释

而不是继续围绕章节 patch 细修。
