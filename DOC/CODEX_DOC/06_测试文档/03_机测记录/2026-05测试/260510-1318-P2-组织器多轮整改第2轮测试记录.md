# 2026-05-10 P2 组织器多轮整改第 2 轮测试记录

## 1. 测试目的

本轮测试承接第 1 轮整改结果，继续验证 `brainstorm-v1` 与 `brainstorm-v1-dify-workflow` 在受控动态多轮会话中的交付质量。重点关注：

1. 未确认业务领域不得被模型用“军事、应急、城市规划”等示例主动具体化。
2. 用户首轮明确提出的“部署分析”不得被写成未确认、排除或待决定是否纳入。
3. 收束草案必须保留结果复核、性能约束和验收链条。
4. 状态回看请求不能被误判为草案交付或会话结束。
5. Provider 返回截断 JSON 时，平台应具备通用重试能力，避免收束阶段直接 400。

## 3. 测试输入

首轮输入仍使用态势分析系统基准输入。后续由受控动态考官按组织器下一问动态释放用户角色、软件定位、流程、功能、数据接口、边界范围、非功能、异常验收、状态回看和强制收束信息。

强制收束输入：

> 强制停止追问，基于当前所有已确认信息输出完整需求规格说明草案，并列出仍需后续确认事项。

状态回看输入：

> 你先回看一下：目前哪些关键决策已经闭合，哪些还没有闭合？先不要急着完整定稿。

## 4. 中间问题与修复复测

| 问题 | 触发位置 | 现象 | 修复 |
| --- | --- | --- | --- |
| 未确认领域示例污染 | `brainstorm-v1` 收束交付 | 待确认事项出现“具体业务领域（如军事、应急、城市规划等）” | 补强 `decision_state_delta` 与 `next_interaction_planning` prompt，交付说明和待确认事项不得列举未确认具体领域示例 |
| Provider JSON 截断 | `brainstorm-v1` 第 11 Turn 收束 | DeepSeek 返回未闭合 JSON，API 返回 400：`Unterminated string` | `DeepSeekRequirementAnalysisClient` 增加一次通用 JSON 修复重试 |
| 状态回看误判交付 | `brainstorm-v1` 第 10 Turn | 用户明确“先不要急着完整定稿”，但 `next_interaction.type=deliverable` | `next_interaction_planning` prompt 增加“状态回看不等同于交付草案”规则 |
| Dify 草案仍偏薄 | Dify 收束草案 | `REQ-3.6`、`REQ-5.1`、`REQ-6.2` 易退化为空占位 | Dify `document_projection` 节点补全结果复核、性能和验收链条，并发布 `P2草案补全` |
| Dify 复测环境缺参 | 后端重启后 Dify 第 1 Turn | `DIFY_API_KEY is not configured` | 使用 `.env.local` 显式启动测试后端；不把密钥写入代码或文档 |

## 7. 结论

1. 第 2 轮暴露的阻塞问题已完成整改并复测通过：本地组织器收束不再 400，状态回看不再误停，两个组织器最终产物均未出现未确认领域示例污染。
2. `brainstorm-v1` 的草案更丰富，但开放问题仍偏多；这是下一轮质量提升方向。
3. `brainstorm-v1-dify-workflow` 的草案字数仍偏短，但第 2 轮已确认结果复核、性能和验收链条不再丢失。
4. 当前可以进入第 3 轮，重点不再是接口阻塞，而是比较开放问题生命周期、草案深度、下一问质量和 Dify 产物信息密度。
