## 1. 原始输入

用户原始输入只明确了四类信息：

1. 目标是创建一个态势分析系统。
2. 系统应有态势展示能力。
3. 系统应有地理信息分析、通视量算、坡度分析和部署分析等工具。
4. 用户、使用模式和具体需求尚未想清楚，需要共同探索。

该输入不足以支撑一万字左右的需求规格说明，也不足以支撑工程需求章节的接口、功能、性能、安装操作和运行环境细化。

## 2. Codex 扩充策略

本轮测试按“先构造样本事实，再按组织器追问逐步释放”的方式执行，而不是一次性把全部事实塞给组织器。扩充策略如下：

1. 先限定软件定位和边界，避免模型把态势分析系统写成正式指挥决策系统。
2. 再补用户角色和典型流程，让需求功能模块有使用者、触发场景和业务闭环。
3. 然后重点补工程需求，包括接口需求、功能需求、性能需求、安装和操作要求。
4. 最后补运行环境、数据质量、安全约束、异常补偿和验收链路。
5. 在交互中优先回答组织器提出的问题；如果组织器长期没有问到工程需求关键缺口，动态考官按未释放主题补充事实。

## 3. 样本演进分层

| 层级 | 扩充主题 | 目的 | 对应释放领域 |
| --- | --- | --- | --- |
| L0 | 原始需求意图 | 保留用户真实起点，不替用户过度定义 | `initial_intent` |
| L1 | 软件定位与范围边界 | 明确科研分析和业务验证定位，排除自动决策、火力分配、强实时协同 | `software_positioning`, `scope_boundary` |
| L2 | 用户角色与典型流程 | 建立使用者、责任分工、主流程和结果复核闭环 | `user_roles`, `workflow` |
| L3 | 功能需求总分解 | 将功能按需求功能模块拆分，而不是按软件设计模块拆分 | `core_functions` |
| L4 | 功能模块细化 | 为工程管理、地图展示、标绘、空间分析、部署分析、成果输出补输入、处理、输出、异常和验收要点 | `function_module_details`, `analysis_module_details`, `result_management_details` |
| L5 | 接口需求 | 补文件导入导出、内网数据加载、输入输出对象、候选格式和失败补偿 | `interface_requirements`, `data_interfaces` |
| L6 | 性能与安装操作 | 补响应时间、并发、复杂分析耗时、安装初始化、参数配置、升级保留 | `quality_constraints`, `installation_operation` |
| L7 | 运行环境 | 补硬件需求、软件需求、数据库、浏览器、WebGIS、算法库和授权待确认项 | `runtime_environment` |
| L8 | 异常与验收 | 补异常补偿、验收任务链和通过标准 | `exceptions_acceptance`, `acceptance_details` |
| L9 | 回看与收束 | 要求组织器回看已闭合决策，并在停止追问时输出完整草案 | `review`, `convergence` |

## 4. 逐步释放方式

动态测试脚本中的 `DYNAMIC_EXAMINER_FACTS` 保存上述扩充主题。每个主题包括触发词、释放领域和测试输入正文。执行时的基本规则是：

1. 第一 turn 只发送用户原始起始描述。
2. 后续 turn 读取组织器的下一问和助手输出。
3. 如果下一问命中某个主题触发词，则释放该主题事实。
4. 如果组织器没有命中特定主题，则按未释放主题顺序补充下一块事实。
5. 当必要主题释放完成后，先要求组织器回看已闭合和未闭合决策，再强制停止追问并输出完整草案。

这种模式的作用是模拟真实用户在多轮沟通中逐步补充信息，同时保证测试样本能覆盖本轮关注的工程需求重点。

## 6. 局限

本扩充样本是为了验证组织器在信息充分条件下的成稿能力，不代表用户已经确认的真实项目需求。样本中的性能指标、部署环境、角色划分、接口格式和验收链路均为测试构造事实。正式项目使用时，应由用户或业务专家确认后再作为真实需求依据。
