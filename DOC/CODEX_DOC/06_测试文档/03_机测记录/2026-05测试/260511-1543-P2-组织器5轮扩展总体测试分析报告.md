- 最终正文有效字数和草案详实程度是否提升。

## 5. 关键发现

### 5.1 测试有效性依赖运行链路刷新

本批次确认：本地提示词、节点源码修改后，如果后端未重启或 Dify workflow 未发布，动态探针数据会产生误导。

后续每轮应强制记录：

- 本地后端是否已重启。
- Dify workflow 是否已同步并发布。
- Dify 发布标题、发布时间和 draft hash。

### 5.2 `brainstorm-v1` 的主要矛盾已转移

R5 后，`brainstorm-v1` 的成稿长度已经不是最主要问题。当前主要矛盾是探索阶段中段的下一问质量：

- 有时仍会让动态考官补小事实，说明问题不够高价值。
- 有时会触发 `small_guidance`，说明下一问与动态考官期待的决策链缺口不完全匹配。
- 需要继续优化 `next_interaction_planning` 的缺口排序和单问策略。

### 5.3 Dify 的主要矛盾是外部运行稳定性与发布治理

Dify workflow 合同输出较稳定，确认事实和确认决策数量稳定。但它依赖外部 workflow 和模型服务：

- 本地源码不发布，线上效果不变。
- Dify 内部模型断连会表现为 P2 API 400，但根因在远端 workflow。

## 6. 结论

本批次完成了 5 个有效迭代动作：

1. 建立双组织器基线。
2. 发现并修复 Dify 本地修改未进入远端运行链路的问题。
3. 重启后确认本地提示词变更真实生效。
4. 修复开放问题生命周期统计口径。
5. 修复 `brainstorm-v1` 收束草案未进入 `document_patch` 的问题。

最终结果：

- `brainstorm-v1` 最终正文从 R4 的 2321 提升到 R5 的 4733，活跃未闭合问题为 0。
- `brainstorm-v1-dify-workflow` 发布后最终正文从 1771 提升到 2450，合同输出保持稳定。
- 尚未解决的问题是探索阶段下一问质量，尤其是如何减少 `small_guidance` / `small_supplement`。

## 7. 后续建议

下一轮不建议继续单纯追求正文长度。建议聚焦：

1. 优化 `next_interaction_planning` 的缺口排序，让每一问优先服务决策链推进。
2. 为动态考官增加“下一问质量”专项指标，例如是否单问、是否承接上一轮、是否命中未释放领域。
3. Dify 侧增加发布记录字段回写到 `workflow.json`，避免本地文档与远端版本脱节。
4. 对 Dify 400 错误增加更清晰的错误归类展示：平台合同错误、远端 workflow 错误、远端模型服务错误应区分。
