## 1. 文档目的

本文定义 CodeFactoryV2 中 Base Platform 的共性持久化能力需求。该能力不是因 P3 当前需要保存软设文档而临时增加的一张表，也不是把所有阶段内部状态统一倒入平台交换层。

本文要解决的问题是：当 P2、P3、P4、P5 等阶段都出现“工作态可恢复、冻结态可审计、发布态可下游消费”的数据需求时，基础平台应提供怎样的共性持久化能力边界、生命周期约束和接入规范。

## 2. 背景与问题

当前系统已经存在两类基础平台持久化能力：

1. 平台交换资源持久化：`platform_exchange_artifacts` 和 `platform_exchange_consumptions` 用于登记跨阶段发布态资源和消费记录。
2. 工作区布局持久化：`workspace_layouts` 用于保存各阶段工作区的布局状态。

这些能力证明基础平台已经承担持久化底座职责，但它们仍是两个相对独立的能力点。当前 P3 软件设计系统暴露出新的需求：Dify 完成需规转软设后，生成的软设正文、设计基线、P4 投影、编辑回合和冻结包如果仍只保存在进程内存中，刷新页面或重启后就会丢失。

该问题不应通过 P3 私有临时存储解决，而应推动基础平台明确“共性持久化能力体系”。

## 3. 能力定位

Base Platform 共性持久化能力是面向各阶段业务系统的持久化底座。它负责提供统一的对象信封、生命周期、版本、快照、追溯、恢复和发布衔接机制。

它与既有平台交换层的关系是：

- 平台交换层只承接已发布、可下游消费的标准资源副本。
- 共性持久化能力覆盖从工作态保存、冻结快照到发布登记的完整持久化框架。
- 各阶段仍负责定义自己的业务对象、字段含义和业务命令。
- 基础平台负责共性元数据、存储规则、版本规则、恢复规则和跨阶段治理边界。

一句话定位：

```text
共性持久化能力是 Base Platform 中承接工作态恢复、冻结态审计和发布态资源登记的基础能力体系。
```

## 4. 持久化对象分层

系统必须区分三类持久化对象：

| 分层 | 定义 | 示例 | 是否进入平台交换层 |
| --- | --- | --- | --- |
| 工作态产物 | 阶段内部正在编辑、转换、沟通或调整的可恢复对象 | P3 设计会话、软设草稿、编辑 turns | 否 |
| 冻结态快照 | 阶段内部已通过检查、形成稳定版本但尚未必然被下游消费的快照 | P3 冻结设计包、设计基线快照 | 可作为发布候选 |
| 发布态平台资源 | 已发布、可被下游正式消费的标准资源副本 | `requirement_spec_package`、`software_design_package` | 是 |

该分层必须成为后续所有阶段接入持久化能力的共同约束。

## 5. 功能需求

### 5.1 工作态自动保存

系统应支持阶段业务系统在关键状态变化后自动保存工作态产物。保存动作可以由阶段服务触发，但必须使用基础平台定义的共性信封字段。

工作态保存至少应支持：

1. 创建工作态对象。
2. 更新当前快照。
3. 查询最近工作态对象。
4. 按业务作用域恢复对象。
5. 记录最近更新时间和写入来源。

### 5.2 快照与版本

系统应支持对工作态对象生成版本快照。快照不应被后续自动保存原地覆盖。

快照至少应包含：

1. 快照标识。
2. 业务对象标识。
3. 版本标签。
4. 生命周期状态。
5. 结构化 payload。
6. payload hash。
7. 来源追溯。
8. 创建时间。

### 5.3 生命周期管理

系统应为共性持久化对象提供统一生命周期字段。

首版生命周期建议为：

| 状态 | 含义 |
| --- | --- |
| `working` | 工作态，可被继续编辑和自动保存 |
| `draft_saved` | 用户显式保存过的草稿态 |
| `snapshot` | 已生成不可覆盖快照 |
| `frozen` | 已冻结，进入评审或发布候选 |
| `published` | 已作为平台交换资源发布 |
| `superseded` | 已被新版本替代 |
| `deleted` | 逻辑删除或不可见 |

阶段业务系统可以有自己的细分状态，但对接基础平台时必须映射到上述通用状态。

### 5.4 发布衔接

当阶段对象达到“可下游消费”边界时，系统应支持把冻结态对象发布为平台交换资源。

发布动作必须满足：

1. 只能从冻结态或明确允许发布的快照态产生。
2. 发布后形成 `ArtifactEnvelope`。
3. 发布资源必须具备独立 payload hash。
4. 发布资源必须记录 parent artifact 或 source trace。
5. 发布资源不得依赖上游运行态引用才能被消费。

### 5.5 查询与恢复

系统应支持按以下维度查询和恢复持久化对象：

1. 所属阶段。
2. 对象类型。
3. 业务作用域。
4. 生命周期状态。
5. 上游输入资源。
6. 最近更新时间。
7. 版本标签。

P3 这类工作台页面刷新后，必须能够通过上游输入包或最近会话恢复已生成软设产物。

### 5.6 追溯与审计

共性持久化对象必须支持最小追溯。

首版追溯至少包括：

1. 上游资源标识。
2. 生产阶段。
3. 生产对象标识。
4. 生产动作。
5. 生产时间。
6. payload hash。
7. 版本标签。

模型调用过程、编辑回合和运行日志可以由阶段侧定义 payload，但必须能被纳入共性追溯信封。

### 5.7 与布局持久化的关系

布局持久化属于共性持久化能力体系中的“视图状态持久化”子能力。它不负责保存业务产物正文。

系统必须保持：

```text
workspace_layouts 保存 UI 布局
work artifacts 保存阶段业务产物工作态
platform_exchange_artifacts 保存发布态平台资源
```

三者可以共享作用域和追溯概念，但不能混用表结构和业务语义。

## 6. 非功能需求

### 6.1 持久性

持久化对象必须保存到后端数据库或明确登记的对象存储。首版优先使用当前工程已有 SQLAlchemy 与 PostgreSQL/SQLite 测试机制。

### 6.2 一致性

同一次阶段业务命令产生的工作态更新、快照更新和发布记录应尽量处于同一后端事务内。短期无法做到时，必须在设计中明确补偿策略。

### 6.3 可扩展性

共性表结构不得固化 P3 专属字段。P3、P4、P6 等阶段必须通过 `artifact_type`、`object_type`、`scope_type`、`payload_schema_version` 和 payload 承载阶段差异。

### 6.4 可观测性

系统应能区分以下失败：

1. 持久化写入失败。
2. 快照 hash 冲突。
3. 生命周期状态不允许变更。
4. 发布前置条件不满足。
5. 恢复对象不存在。

### 6.5 安全与隔离

首版可以沿用 `owner_user_id=default`，但模型必须预留所有者字段，避免后续引入账号体系时重构数据结构。

## 7. 边界与非目标

本能力不负责：

1. 替代 P1 ~ P5 的业务服务。
2. 判断 P3 软件设计内容是否合理。
3. 把所有阶段运行中临时变量都上收为平台权威事实。
4. 把平台交换层改造成万能业务库。
5. 把布局 payload、业务产物 payload 和发布资源 payload 混存在同一语义对象里。

## 8. P3 首个接入要求

P3 作为首个深化接入阶段，至少应验证以下能力：

1. Dify 转换成功达到 `draft_ready` 后自动持久化工作态设计会话。
2. 页面刷新后可恢复软设正文、设计基线和 P4 投影。
3. 后端重启后仍可查询关联软设。
4. 点击保存草稿后产生明确 `draft_saved` 生命周期状态。
5. 冻结设计包后形成不可覆盖快照。
6. 发布给下游阶段时登记为平台交换资源。

## 9. 验收标准

1. 文档层面明确区分工作态、冻结态和发布态。
2. 基础平台文档能解释 `workspace_layouts`、工作态产物持久化和 `platform_exchange` 三者关系。
3. P3 需求文档能按基础平台约束描述软设产物持久化目标。
4. P3 设计文档能说明如何接入共性持久化能力，而不是私建临时存储。
5. 后续实现应能通过后端重启验证 P3 已生成软设不丢失。
