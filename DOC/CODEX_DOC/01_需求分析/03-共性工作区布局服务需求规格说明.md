# 共性工作区布局服务需求规格说明

**日期：** 2026-06-20
**适用工程：** CodeFactoryV2
**所属范围：** Base Platform（基础平台）共性能力
**首个接入阶段：** P3 软件设计系统

## 1. 文档目的

本文定义 CodeFactoryV2 中“共性工作区布局服务”的需求边界。

该服务用于解决各阶段工作区布局只能保存在浏览器本地、刷新页面或重启服务后容易丢失的问题。首个落地场景是 P3 软件设计工作区的布局持久化，但需求边界不是 P3 专用能力，而是面向 P2、P3、P6 及后续工具工作台的统一基础服务。

## 2. 背景与问题

当前 P3 软件设计工作区已经具备可拖拽、缩放、窗口选择和布局快照能力，但布局数据主要保存在浏览器 `localStorage` 中。该方式存在以下问题：

1. 只绑定当前浏览器、当前域名和当前端口，换浏览器或换运行入口后不可见。
2. 前端刷新、开发服务重启、浏览器数据清理后可能丢失。
3. 用户必须依赖手动“记录布局”动作，当前布局状态不一定自动保存。
4. 布局数据不进入后端，不具备版本、审计、迁移和跨工作树复用能力。
5. 不同阶段未来都会有布局，但如果各自实现，会形成多个不兼容的本地存储格式。

因此需要建立一个平台级布局服务，把“布局持久化”从单个页面的本地状态提升为可复用的基础能力。

## 3. 服务定位

共性工作区布局服务属于 Base Platform 的运行时基础服务。

它负责保存、查询、更新、删除和恢复用户在某一业务作用域下的工作区布局。业务阶段仍然负责解释布局含义，例如 P3 负责解释软件设计画布中各阶段窗口的位置、尺寸和当前视口，平台服务只负责按照统一信封保存布局负载。

一句话定位：

```text
共性工作区布局服务是面向各阶段工作台的布局状态持久化底座，不是 P3 内部业务表，也不是前端 localStorage 的简单替代文件。
```

## 4. 使用对象

### 4.1 用户对象

1. 研发人员或行业专家在各阶段工作区中调整布局后，希望下次打开仍然保持工作状态。
2. 多工作树或多运行入口使用同一后端时，希望布局由后端统一读取。
3. 平台维护人员需要观察、迁移或清理布局数据。

### 4.2 系统对象

1. P3 软件设计系统：首个接入对象，保存软件设计画布布局。
2. P6 平台门户与展示实验层：可复用布局服务保存门户视图或投影面板布局。
3. 后续 P2/P4/P5 工作台：可按自己的布局类型接入同一服务。

## 5. 核心概念

| 概念 | 定义 |
| --- | --- |
| WorkspaceLayout | 一份工作区布局记录。 |
| scope_type | 布局所属业务作用域类型，例如 `p3_design_session`。 |
| scope_id | 布局所属业务作用域标识，例如 P3 设计会话 `session_id`。 |
| layout_kind | 布局类型，用于区分不同工作台或不同画布格式，例如 `p3_design_morph_canvas@1`。 |
| layout_role | 布局角色，例如 `current_auto`、`named_snapshot`、`user_default`。 |
| payload_schema_version | 布局负载格式版本。 |
| payload_json | 阶段自定义布局正文，平台只做结构化保存和最小校验。 |

## 6. 功能需求

### 6.1 布局保存

系统应支持前端把当前工作区布局保存到后端。

保存时必须包含：

1. 布局所属作用域：`scope_type` 与 `scope_id`。
2. 布局类型：`layout_kind`。
3. 布局角色：自动当前布局、命名快照或用户默认布局。
4. 布局名称。
5. 负载格式版本。
6. 布局负载 JSON。

### 6.2 布局查询

系统应支持按照 `scope_type`、`scope_id`、`layout_kind` 查询布局列表。

查询结果应至少包含：

1. 布局标识。
2. 布局名称。
3. 布局角色。
4. 是否默认。
5. 负载格式版本。
6. 布局负载。
7. 创建时间、更新时间和最近使用时间。

### 6.3 当前布局自动保存

系统应支持每个作用域、每种布局类型保留一份自动当前布局。

当用户拖动窗口、缩放画布或切换当前窗口时，前端可以进行防抖保存。刷新页面或重启服务后，系统应优先恢复用户上一次实际工作状态。

### 6.4 命名快照

系统应保留“记录布局”一类手动快照能力。

命名快照用于保存用户认为有价值的布局方案，不能被自动保存覆盖。

### 6.5 默认布局

系统应支持把某个布局设为用户默认布局。

同一用户、同一作用域、同一布局类型下，只能有一份默认布局。设置新默认布局时，旧默认布局应自动取消默认状态。

### 6.6 布局更新与删除

系统应支持更新布局名称、角色、默认状态和负载内容，也应支持删除不再需要的布局。

删除布局不得删除业务阶段数据，例如 P3 设计会话、需求规格包或软件设计说明正文。

### 6.7 P3 首个接入

P3 软件设计工作区应作为首个接入方。

P3 首版布局负载应至少覆盖：

1. 当前激活窗口标识。
2. 画布视口位置和缩放比例。
3. 各阶段窗口的位置、尺寸和折叠状态。
4. 与设计会话关联的标识。
5. 布局格式版本。

### 6.8 本地存储兼容

系统上线后，前端可保留 `localStorage` 作为降级缓存或一次性迁移来源，但后端持久化应成为权威存储。

如果后端不可用，前端可以提示用户当前布局只能临时保存在本地。

## 7. 非功能需求

### 7.1 持久化

布局数据应持久化到后端数据库。首版优先使用当前工程已经使用的 SQLAlchemy 与 PostgreSQL/SQLite 测试数据库机制。

### 7.2 可扩展性

服务不得把 P3 字段固化到通用表结构中。不同阶段应通过 `layout_kind` 和 `payload_schema_version` 承载自己的布局格式。

### 7.3 兼容性

新增服务不得影响现有 P3 设计会话、P2 到 P3 数据流、Dify 服务调用和 P6 门户投影。

### 7.4 可观测性

服务应通过明确的 HTTP 状态码表达查询不到、保存失败、布局不存在等情况。首版不强制建立独立审计流，但数据库记录应包含创建时间、更新时间和最近使用时间。

### 7.5 安全与隔离

首版可以使用默认用户标识，但接口模型必须预留 `owner_user_id`，避免后续加入登录体系时需要重构表结构。

## 8. 边界与非目标

本服务不负责：

1. 决定 P3 软件设计业务内容如何生成或保存。
2. 保存需求规格、软件设计说明、P4 工单或 Dify 调用结果。
3. 实现画布渲染、拖拽算法或窗口碰撞逻辑。
4. 替代各阶段自己的业务服务。
5. 把所有前端状态集中到一个平台状态表。

## 9. 验收标准

首版验收至少满足以下条件：

1. P3 软件设计工作区布局保存后，刷新页面仍可恢复。
2. 后端服务重启后，P3 软件设计工作区仍可从数据库恢复布局。
3. P3 命名布局快照可以保存、查询和再次应用。
4. 同一业务作用域下可以区分自动当前布局和命名快照。
5. 后端存在接口测试覆盖布局创建、查询、更新、设默认和删除。
6. 前端存在测试或构建验证，确认 P3 接入不会破坏现有工作区渲染。
7. 新增服务以通用 `workspace-layouts` 能力暴露，不以 P3 专属表或 P3 专属接口作为唯一入口。
