# CodeFactoryV2 文档体系与军标文种映射分析

## 1. 文档目标

本文件用于回答一个容易被混淆、但对 `CodeFactoryV2` 至关重要的问题：

- 软件工厂平台自身的研发文档，与软件工厂未来生产出来的软件交付文档，到底是什么关系
- 当前已引入的美军 / DoD 软件文种，究竟约束的是平台自身，还是平台产物，还是两者都约束
- 当前仓库中的正式文档体系，哪些适合向标准文种靠拢，哪些不适合
- 现有标准覆盖是否已经足以支撑软件工厂的阶段验证，如果不足，缺口主要在哪里

本文件不是单纯列一个“本地文档对标准编号”的对照表，而是要建立一套后续长期可复用的解释框架。

## 2. 核心前提

### 2.1 `CodeFactoryV2` 是“生产软件的软件”

`CodeFactoryV2` 不是一个普通业务系统，而是一个软件工厂平台。它同时具有两种身份：

- 身份一：它自身是一个正在被研发、被设计、被验证的软件平台
- 身份二：它又是一个用于生产其他软件交付物的软件系统

因此，本项目天然存在两类不同但相关的文档对象：

- 平台自身的研发文档
- 平台产出的软件交付文档

如果不先把这两类对象区分开，后续讨论“哪些文档要按军标写、哪些不要按军标写”时就一定会混乱。

### 2.2 标准规范在本项目中具有双重用途

在 `CodeFactoryV2` 中，美军 / DoD 软件标准文种不是只发挥一种作用，而是同时可能发挥两种作用：

- 作用一：约束 `CodeFactoryV2` 平台自身如何被定义、设计、追溯和验证
- 作用二：约束 `CodeFactoryV2` 未来生成出来的软件交付物应当如何表达

因此，后续讨论标准采用时，不能再使用“这些规范只属于 P2/P3 产物层”这样的单线理解。

更准确的理解应当是：

- 平台研发层可以吸收标准中的工程控制点
- 平台产物层应当尽量直接对齐正式交付文种

## 3. 统一分析框架

### 3.1 三层对象模型

为避免继续出现“工程治理轴”和“交付文档轴”互相打架的问题，本文件采用三层模型统一分析：

#### 第一层：平台研发层

这一层回答的是：

- `CodeFactoryV2` 这个平台本身如何被研发
- 平台的边界、阶段、模块、接口和执行策略如何被表达

典型文档包括：

- 全局工程策略
- 本地工程策略映射
- 本地开发策略
- WBS 计划
- 平台总体设计
- 阶段设计说明
- 测试、验收、交接、过程记录

#### 第二层：平台产物模板层

这一层回答的是：

- 软件工厂用于生成软件交付物时，应使用什么样的标准模板
- 需求规格、设计说明、测试说明、发布说明等文种，应采用什么骨架和什么追溯关系

典型对象包括：

- `RequirementSpec`
- `SoftwareDesignDescription`
- 接口说明、数据库说明、测试说明、版本说明等模板族

#### 第三层：项目实例交付层

这一层回答的是：

- 当软件工厂真正接收一个具体项目时，最终会为该项目产出哪些正式文档实例

也就是说：

- 第二层是模板、规则和生成标准
- 第三层是某个实际项目被生成出来的正式交付成果

### 3.2 三层之间的关系

三层关系不是并列的，而是递进的：

- 平台研发层定义软件工厂如何工作
- 平台产物模板层定义软件工厂要生成什么样的文档
- 项目实例交付层承接模板层，形成具体项目的正式成果

因此，当前仓库里的正式文档体系，不应再被理解成“要不要整体军标化”的问题，而应理解成：

- 第一层以本地工程治理表达为主，吸收必要标准控制点
- 第二层以标准文种模板化为主
- 第三层以后续实际生成项目的正式交付物为主

## 4. 当前引入的标准对象

### 4.1 已明确进入项目主线的交付文种

当前仓库已经显式引入并落地到模板逻辑中的核心标准对象如下：

- `DI-IPSC-81433`
  - `Software Requirements Specification`
  - 适合软件级需求规格说明
- `DI-IPSC-81435`
  - `Software Design Description`
  - 适合软件级设计说明
- `DI-IPSC-82259`
  - `System/Subsystem Specification`
  - 适合平台级或系统级规格说明
- `DI-IPSC-82284`
  - `Software/Hardware Design Description`
  - 适合平台级或系统级设计说明

这些标准当前已经进入本地模板与参考逻辑，主要落点包括：

- `apps/api/app/software_design/reference_library.py`
- `DOC/CODEX_DOC/02_设计说明/04-P3-软件设计系统设计.md`

### 4.2 可作为工程治理参考的过程类文种

除了需求与设计类文种外，DoD / ASSIST 体系中也存在可以为工程治理轴提供参考的过程类对象。当前对本项目最有价值的不是“逐一照抄”，而是理解其控制意图。典型对象包括：

- `DI-IPSC-81427`
  - `Software Development Plan`
  - 偏研发计划、组织、过程、资源与里程碑控制
- `DI-SESS-81785`
  - `Systems Engineering Management Plan`
  - 偏系统工程技术路线、执行与管理
- `DI-MGMT-82133`
  - `Requirements Traceability Verification Matrix`
  - 偏需求、设计、验证之间的追溯矩阵

这意味着：

- 工程治理轴不是完全没有对应标准
- 只是它与当前本地治理文档之间，不存在像 `SRS / SDD` 那样简单的一一映射

### 4.3 尚未纳入主线但与完整交付闭环强相关的文种

如果后续要验证软件工厂是否具备更完整的软件研制交付能力，那么至少还应关注以下文种：

- `DI-IPSC-81434`
  - `Interface Requirements Specification`
- `DI-IPSC-81436`
  - `Interface Design Description`
- `DI-IPSC-81437`
  - `Database Design Description`
- `DI-IPSC-81438`
  - `Software Test Plan`
- `DI-IPSC-81439`
  - `Software Test Description`
- `DI-IPSC-81440`
  - `Software Test Report`
- `DI-IPSC-81441`
  - `Software Product Specification`
- `DI-IPSC-81442`
  - `Software Version Description`
- `DI-IPSC-81429`
  - `Software Transition Plan`

这些对象并不是当前 `P2 / P3` 主链的第一优先级，但如果未来要证明“软件工厂已经具备相对完整的软件研制文档能力”，它们迟早都要进入模板层讨论。

## 5. 当前正式文档体系的定位

### 5.1 `DOC/CODEX_DOC/` 不是单纯的军标交付仓

当前项目的正式文档根是：

- `DOC/CODEX_DOC/`

这套体系当前承载的是“平台研发层”的正式文档管理职责，主要用于：

- 固化本地工程策略
- 固化文档治理与工作方式
- 固化 WBS 与阶段计划
- 固化平台总体设计
- 固化阶段设计与实施边界
- 固化测试、验收与过程记录

因此，它本质上不是一个只围绕 `SRS / SDD / STP / STR` 展开的纯交付文种仓库。

### 5.2 这套文档体系当前更接近“平台研发文档根”

从职责上看，`DOC/CODEX_DOC/` 当前更准确的定位是：

- `CodeFactoryV2` 平台研发层的正式文档根

这意味着：

- 它允许存在大量不需要也不适合军标化的治理文档
- 同时也允许其中部分设计文档吸收或映射军标表达

因此，讨论“当前文档体系是否应整体迁移为军标风格”时，结论应当是否定的。

### 6.2 一个关键区分：`P3` 系统设计文档不等于 `P3` 输出文档

当前项目里最容易被混淆的，是这两个对象：

- `DOC/CODEX_DOC/02_设计说明/04-P3-软件设计系统设计.md`
  - 它描述的是：`P3` 这个设计系统本身如何工作
- `P3` 生成出来的 `SoftwareDesignDescription`
  - 它描述的是：被软件工厂生产出来的目标软件如何被设计

前者属于：

- 平台研发层

后者属于：

- 平台产物模板层 / 项目实例交付层

因此：

- 前者不应直接改写为 `SDD`
- 后者才是应当与 `81435 / 82284` 对齐的正式对象

## 7. 当前标准覆盖的真实能力边界

### 7.1 当前已经能够验证什么

基于当前已经引入的 `81433 / 81435 / 82259 / 82284`，本项目已经具备验证以下能力的基础：

- 软件工厂是否能够形成规范化的需求规格主链
- 软件工厂是否能够形成规范化的软件设计说明主链
- 软件级与平台 / 系统级对象是否能够分流选择不同模板
- 平台总体设计是否可以逐步向更正式的系统级设计表达靠拢

因此，如果当前阶段的问题是：

- “这个软件工厂能不能把需求规格说明和软件设计说明做成标准化产物”

那么答案是：

- 现有文种基础已经足够支撑主链验证

### 7.2 当前还不能宣称什么

如果当前阶段的问题升级为：

- “这个软件工厂是否已经具备较完整的软件研制文档生产能力”

那么答案是否定的。

原因不是因为 `P2 / P3` 没价值，而是因为当前文种集合还没有覆盖完整的软件交付闭环。当前明显不足的部分包括：

- 需求到设计到验证之间的正式追溯矩阵
- 接口与数据库类专门说明
- 测试计划、测试说明、测试报告链
- 产品规格、版本说明、移交 / 过渡说明

因此，当前系统更准确的成熟度判断应当是：

- 已能验证“需求与设计主链的标准化生成能力”
- 尚不能宣称“已经完整覆盖软件研制全过程文档能力”

### 7.3 当前最关键的缺口不是文档数量，而是闭环能力

从验证价值看，当前优先级最高的不一定是一次性把所有 DID 都补齐，而是优先补齐那些最能证明系统闭环能力的对象。

当前最关键的三个缺口是：

- `RTVM`
  - 证明需求、设计、实现、验证之间是否真正可追溯
- `STP / STD / STR`
  - 证明系统是否能够形成正式测试链
- `SPS / SVD / STrP`
  - 证明系统是否能够形成正式发布与交付基线

只有当这些对象逐步进入平台产物模板层并形成实例输出后，软件工厂才更接近“完整研制文档工厂”的定位。

## 8. 对当前文档体系的判断

### 8.1 哪些文档应当继续保持本地工程表达

以下对象本质上属于平台研发层的治理文档，应继续保持本地工程表达，不应为了形式统一而硬改成军标文种：

- 全局工程策略
- 本地工程策略映射
- 本地开发策略
- WBS 计划
- 过程记录
- 验收与交接记录

原因很简单：

- 这些文档服务的是平台研发协作，而不是外部交付
- 即便强行改写成军标语气，也不会提高当前项目的真实执行质量
- 反而会削弱本地工程治理的可操作性

### 8.2 哪些文档适合吸收过程类标准控制点

虽然不建议整体军标化，但平台研发层中仍有一部分文档值得吸收过程类标准的关键控制点，例如：

- 在平台总体设计和阶段设计中，吸收 `SEMP` 的系统工程约束思路
- 在 WBS、阶段计划和执行规则中，吸收 `SDP` 的计划与控制思路
- 在后续需求到设计到构建的链路中，吸收 `RTVM` 的追溯矩阵思路

这里的关键词不是：

- “一比一套模板”

而是：

- “吸收控制点”

### 8.3 哪些对象应当直接文种化

以下对象属于平台产物模板层，后续应尽量直接按正式交付文种推进：

- `P2` 的正式需求规格
- `P3` 的正式设计说明
- 接口 / 数据库 / 测试 / 发布 / 移交等后续模板族

这些对象不只是“可以参考标准”，而是“本来就应当成为标准化交付对象”。

## 9. 对后续升级路线的建议

### 9.1 当前阶段的合理目标

当前阶段最合理的目标不是：

- 把整个 `DOC/CODEX_DOC/` 一次性重写成军标体系

而是：

- 保持平台研发层文档体系稳定
- 在平台产物模板层继续深化 `P2 / P3` 主链
- 逐步补齐最关键的闭环文种

### 9.2 推荐的分步路线

建议按以下顺序推进：

#### 第一步：巩固主链

- 继续把 `P2` 的 `RequirementSpec` 与 `81433 / 82259` 对齐
- 继续把 `P3` 的 `SoftwareDesignDescription` 与 `81435 / 82284` 对齐

#### 第二步：补齐追溯与测试链

- 引入 `RTVM`
- 引入 `STP / STD / STR`

#### 第三步：补齐发布与交接链

- 引入 `SPS / SVD / STrP`

#### 第四步：按需扩展接口与数据库文种

- 引入 `IRS / IDD / DBDD`

这种顺序的好处是：

- 它与当前 `P2 -> P3 -> P4 -> P5` 的阶段演进是一致的
- 它优先解决“能不能形成闭环”的问题
- 它避免一开始就把大量低优先级文种堆进系统，造成模板膨胀

## 10. 总体结论

基于以上分析，当前更准确的总体判断应当是：

- `CodeFactoryV2` 的正式文档体系，本质上是平台研发层文档体系，不是纯交付文种仓
- 美军 / DoD 标准在本项目中具有双重用途
  - 一方面可为平台研发层提供工程控制点参考
  - 另一方面应直接约束平台产物模板层与项目实例交付层
- 当前已引入的 `81433 / 81435 / 82259 / 82284`，足以支撑需求与设计主链的标准化验证
- 但若要证明软件工厂已经具备相对完整的软件研制文档生产能力，当前仍明显不足
- 当前最关键的后续补齐方向，不是泛化增加大量文档，而是优先补齐追溯、测试、发布与交接闭环

因此，对本项目最合理的文档策略不是“整体军标化”，而是：

- 平台研发层保持本地工程治理表达
- 平台研发层按需吸收 `SDP / SEMP / RTVM` 等过程控制点
- 平台产物模板层持续按正式军标文种深化
- 项目实例交付层在未来具体项目中生成真实的标准化交付成果
