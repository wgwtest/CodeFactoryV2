# CodeFactoryV2 工程总体分析

## 1. 项目目标

`CodeFactoryV2` 旨在构建一个面向行业专家与研发团队协同使用的软件工厂平台。

核心目标不是单独做“知识库”或“低代码平台”，而是形成一条稳定主链：

`业务知识库 -> 需求分析系统 -> 软件设计系统 -> 工具仓库 -> 软件构建系统`

并由平台层承担统一观察、读侧集成、展示语言统一与前端展示实验承载。

## 2. 模块拆分

### 2.1 P1 业务知识库

职责：

- 接入源资料
- 进行结构化解析
- 抽取实体、事件、流程、规则、指标
- 治理、发布并形成知识仓
- 向后续模块输出可选业务元素和知识查询能力

关键纠偏：

- 业务知识库不是“被需求系统驱动后才存在”
- 业务知识库要主动向 `P2` 输出元素数据，供用户在建模时选择

### 2.2 P2 需求分析系统

职责：

- 面向不懂技术的行业专家进行交互式建模
- 以对象为起点组织需求，而不是依赖既有组件
- 允许选择领域知识元素，也允许现场创建临时元素并标记待入库
- 输出结构化 `RequirementSpec`

关键约束：

- `P2` 建模本身不依赖现成组件
- `P2` 的输出首先是结构化对象，可投影为说明书，但说明书不是唯一权威

### 2.3 P3 软件设计系统

职责：

- 消费 `P2` 的需求规格
- 先形成结构化软件设计对象
- 再投影为“软件设计说明”
- 经人工判断与校核后，导出模块级和子模块级工具化描述

关键纠偏：

- `P3` 不是直接产出两类并列终物
- 正确顺序是：`需求规格 -> 软件设计对象 -> 软件设计说明投影 -> 人工校核 -> 工具化描述`

### 2.4 P4 工具仓库

职责：

- 管理工具、组件、执行器与匹配规则
- 根据 `P3` 输出的工具化描述执行匹配、命中、注册和验证
- 沉淀工具/组件资产，支撑后续复用

关键边界：

- 工具匹配分析是工具仓库的重要能力，但应理解为“工具中台能力”，不是孤立的小功能

### 2.5 P5 软件构建系统

职责：

- 基于 `P3` 设计结果和 `P4` 可用资产进行装配、生成与执行
- 产出可运行软件或元数据应用

### 2.6 P6 平台门户、观察与前端展示实验层

职责：

- 提供首屏观察门户
- 提供 `P1 ~ P5` 的只读状态投影
- 统一平台级设计语言与前端展示基线
- 作为前端展示工具化实验层
- 不替代 `P1 ~ P5` 业务主链，不承担业务反写

## 3. 当前工程现状

从当前仓库可见内容看：

- `P1` 已有前后端页面、知识库管理、文档导入、审核发布、知识图谱等基础闭环
- `P2` 已有“应用需求建模器”方向文档和 `XX-P2-Sim` 模拟输入台方案
- `P3` 已有独立 `superpowers` 设计、计划和 issue mirror
- `P4` 已有独立 `superpowers` 设计、计划和 issue mirror
- `P6` 已有门户相关设计与计划草案

## 4. 当前主要缺口

### 4.1 文档根缺失

此前正式设计、执行计划、issue 镜像和过程产物主要堆叠在 `docs/superpowers/`，缺少一套符合全局工程策略的正式本地文档根。

### 4.2 P2 正式协作面不足

`P2` 已有设计草案，但当前仓库中尚未看到与 `P3 / P4` 同级的 `P2` issue tree mirror 和正式节点计划映射，后续需要补齐。

### 4.3 测试与过程文档目录未成体系

验收入口、机测记录、交接文档目前没有规范化归档根，后续会影响多轮协作和阶段回溯。

### 4.4 superpowers 与正式文档职责混用

`superpowers` 适合快速推演，但如果长期承担正式规范根，会导致：

- 草案和正式方案混在一起
- 路径引用不稳定
- 后续用户自有文档策略难以接入

## 5. 本轮重整目标

本轮文档治理只做三件事：

- 建立正式文档根 `DOC/CODEX_DOC/`
- 把现有工程理解、总体设计和 WBS 计划沉淀为正式文档
- 明确 `superpowers + 全局工程策略` 的协同规则

## 6. 后续建议

- `P2` 后续应补齐独立 issue tree mirror 与正式节点计划
- 每次新增正式阶段结论时，同步更新 `DOC/CODEX_DOC/04_研制计划/`
- 自测、验收、交接从后续迭代开始统一归档到 `DOC/CODEX_DOC/06_测试文档/` 与 `DOC/CODEX_DOC/07_过程文档/`
