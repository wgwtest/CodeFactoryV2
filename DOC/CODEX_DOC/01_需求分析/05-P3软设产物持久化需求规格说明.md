## 1. 文档目的

本文定义 P3 软件设计系统中软设产物持久化的业务需求。P3 不应自行建设临时、碎片化的存储机制，而应按照 Base Platform 共性持久化能力的生命周期、版本、快照和发布约束接入。

本文回答：

1. P3 需要持久化哪些软设产物。
2. 哪些对象属于工作态，哪些对象属于冻结态，哪些对象需要发布为平台资源。
3. 页面刷新、后端重启和多 worktree 运行时应如何恢复。
4. P3 与 Base Platform 的职责边界如何划分。

## 2. 背景与问题

当前 P3 Design Lab 通过 Dify 转换器生成软设草稿、设计基线和 P4 投影。但当前 `P3DesignLabSession` 仍主要保存在后端进程内存中，页面刷新后前端当前会话会丢失，后端重启后已生成软设也会丢失。

用户视角的问题是：

1. 需规转软设耗时较长，重复生成成本高。
2. 已生成的软设正文无法稳定恢复。
3. 关联软设只在当前后端进程内可见。
4. 保存草稿、生成投影、冻结设计包没有形成长期持久化事实。
5. P3 设计成果无法稳定进入后续 P4/P5/P6 链路。

## 3. 目标

P3 软设产物持久化应达到以下目标：

1. Dify 转换成功后立即自动保存。
2. 页面刷新后可以恢复当前或最近软设会话。
3. 后端重启后可以从数据库恢复关联软设。
4. 保存草稿应改变生命周期状态，而不是只改内存。
5. 冻结设计包应形成不可覆盖快照。
6. 发布给下游时应登记为 Base Platform 平台交换资源。
7. 布局持久化和业务产物持久化必须分离。

## 4. 持久化对象范围

P3 至少需要持久化以下对象：

| 对象 | 说明 | 首版保存方式 |
| --- | --- | --- |
| `P3DesignLabSession` | P3 设计会话聚合根 | 共性工作态产物 |
| `input_package` | P2 输入包快照引用和必要摘要 | session payload + source refs |
| `conversion` | 转换状态、策略、转换器、过程输出摘要 | session payload |
| `design_document` | 软件设计说明正文结构 | session payload |
| `design_baseline` | 结构化设计基线、模块、功能树、追溯 | session payload / 冻结快照核心 |
| `workorder_projection` | 面向 P4 的工单投影候选 | session payload |
| `turns` | 设计沟通和局部编辑回合 | session payload |
| `runtime_events` | 关键运行事件 | session payload |
| `check_result` | 检查结果 | session payload |
| `frozen_package` | 冻结设计包 | 不可覆盖快照 |

## 5. 生命周期需求

P3 业务状态必须映射到 Base Platform 共性生命周期：

| P3 状态 | 共性生命周期 | 含义 |
| --- | --- | --- |
| `conversion_pending` | `working` | 会话已创建，等待转换 |
| `conversion_running` | `working` | 转换执行中 |
| `draft_ready` | `working` | 已生成软设草稿，必须自动持久化 |
| `draft_saved` | `draft_saved` | 用户显式保存草稿 |
| `projection_ready` | `draft_saved` 或 `snapshot` | 已生成 P4 投影 |
| `patched` | `working` | 局部补丁已应用，形成新工作态版本 |
| `frozen` | `frozen` | 已冻结为不可覆盖设计包 |
| `published` | `published` | 已发布为下游可消费平台资源 |

## 6. 功能需求

### 6.1 自动保存

P3 在以下节点必须自动保存：

1. 创建设计会话后。
2. 基础转换成功后。
3. 基础转换失败后。
4. 提交设计回合后。
5. 应用局部补丁后。
6. 生成 P4 投影后。
7. 运行检查后。
8. 冻结设计包后。

其中基础转换成功后的 `draft_ready` 是最关键保存点。该状态必须保存完整软设正文和设计基线。

### 6.2 恢复

P3 页面应支持以下恢复方式：

1. 通过 `session_id` 直接恢复。
2. 通过 P2 输入包查询关联软设。
3. 默认打开最近更新的未冻结或已保存草稿。
4. 后端返回历史设计摘要，前端可点击进入编辑。

恢复后应同时恢复：

1. 软设正文。
2. 设计基线。
3. P4 投影。
4. turns。
5. runtime events。
6. 检查和冻结状态。

布局恢复仍由 `workspace_layouts` 负责。

### 6.3 草稿保存

用户点击保存草稿时，系统应：

1. 将当前会话生命周期映射为 `draft_saved`。
2. 更新持久化对象。
3. 保留最新 payload hash。
4. 追加保存事件。
5. 不创建平台交换发布资源。

### 6.4 冻结设计包

用户点击冻结设计包时，系统应：

1. 检查软设正文和设计基线存在。
2. 检查阻断项为 0。
3. 生成不可覆盖 `frozen_package`。
4. 创建冻结态快照。
5. 禁止原地修改冻结快照。
6. 允许后续从冻结快照创建修订。

### 6.5 发布到下游

P3 冻结设计包在需要交给 P4/P5/P6 时，应发布为平台交换资源。

首版建议资源类型：

| 发布资源类型 | 用途 |
| --- | --- |
| `software_design_package` | 完整软设设计包 |
| `software_design_baseline` | 下游构建或审查需要的设计基线 |
| `module_workorder_projection` | P4 工单候选输入 |

发布态资源必须由 Base Platform `platform_exchange` 登记，P3 不直接让下游读取 P3 内部表。

## 7. 查询需求

P3 至少需要以下查询能力：

1. 查询某个输入包的关联软设列表。
2. 查询某个软设会话详情。
3. 查询最近未冻结草稿。
4. 查询冻结设计包。
5. 查询已发布到平台交换层的资源标识。

关联软设列表必须来自持久化对象，而不是内存 `_sessions`。

## 8. 数据一致性需求

1. 转换成功后，返回给前端的会话与数据库保存的会话必须一致。
2. 生成投影后，`workorder_projection` 必须随会话一起保存。
3. 应用补丁后，正文、基线摘要、turns 和 runtime events 必须一起保存。
4. 冻结后，冻结包和会话状态必须一起保存。
5. 发布到平台交换层后，P3 持久化对象必须记录发布资源 id。

## 9. 错误处理

| 场景 | 用户侧表现 | 后端处理 |
| --- | --- | --- |
| 自动保存失败 | 显示保存失败，不承诺可恢复 | 返回错误并保留当前内存响应 |
| 转换成功但保存失败 | 明确提示产物未持久化 | 不标记 `draft_ready` 为已保存 |
| 恢复对象不存在 | 显示历史设计不存在 | 返回 404 |
| 冻结对象被修改 | 拒绝修改 | 返回 409 |
| 发布失败 | 保持冻结态 | 记录失败原因，允许重试 |

## 10. 与 Base Platform 的职责边界

| 职责 | P3 | Base Platform |
| --- | --- | --- |
| 定义软设对象结构 | 是 | 否 |
| 执行 Dify 转换 | 是 | 否 |
| 判断设计质量 | 是 | 否 |
| 保存工作态信封 | 调用 | 提供 |
| 管理生命周期通用状态 | 映射 | 提供 |
| 保存布局 | 调用 `workspace_layouts` | 提供 |
| 发布平台资源 | 发起 | 登记和分发 |
| 下游消费留痕 | 发起/消费 | 提供 |

## 11. 验收标准

1. 完成一次 P2 -> P3 基础转换后，刷新页面不需要重新生成。
2. 重启后端后，P3 输入包仍能列出关联软设。
3. 打开关联软设后，软设正文、设计基线和 P4 投影完整存在。
4. 保存草稿后，生命周期状态可查询。
5. 冻结设计包后，冻结快照不可被后续自动保存覆盖。
6. 发布给下游后，Base Platform 监控能看到 P3 发布资源。
7. 布局变化不会污染软设业务产物。

## 12. 非目标

首版不要求：

1. 新增账号权限体系。
2. 支持多人协同编辑冲突解决。
3. 对软设正文做段落级差异存储。
4. 将所有 Dify 原始 trace 完整长期保存。
5. 将 P3 所有前端 UI 状态保存为业务事实。

## 13. 需求结论

P3 软设产物持久化是 P3 业务可用性的基础要求，也是 Base Platform 共性持久化能力体系的首个深化接入场景。它必须同时满足工作态恢复、冻结态审计和发布态下游消费三类需求。
