# CODEX_DOC 到 JB_DOC 完整投影缺口矩阵

## 1. 文档定位

**文档类别：** 需求分析与投影治理文档  
**当前状态：** 基线  
**目标对象：** `CODEX_DOC -> JB_DOC` 文档体系映射  

本文件用于回答一个更严格的问题：

- 当 `JB_DOC` 被定义为 `CODEX_DOC` 的**投影层**而不是独立根时
- 当前哪些 `CODEX_DOC` 正式内容已经足够支撑 `JB_DOC` 做对等投影
- 哪些对象之所以还没法完整投影，不是因为 `JB_DOC` 不该有，而是因为 `CODEX_DOC` 本身还缺正式源内容

本文件不替代：

- `DOC/JB_DOC/04-映射与追溯/00-CODEX_DOC到JB_DOC来源映射总表.md`
- `DOC/JB_DOC/04-映射与追溯/01-标准覆盖缺口清单.md`

它与上述文档的区别是：

- 来源映射总表回答“当前已经怎么映射了”
- 标准覆盖缺口清单回答“当前标准对象缺什么”
- 本文件回答“如果按严格投影要求推进，`CODEX_DOC` 还缺什么、`JB_DOC` 还漏投什么”

## 2. 当前口径修正

本轮确认以下口径为后续工作的正式前提：

1. `DOC/CODEX_DOC/` 仍然是研发正式文档根。
2. `DOC/JB_DOC/` 不是独立替代根，而是 `CODEX_DOC` 的标准化投影层。
3. “严格投影”不等于逐文件机械复制，但要求：
   - `CODEX_DOC` 中每个重要正式对象，在 `JB_DOC` 中都必须有可追溯投影。
   - 不能只做一个总包文档，把 `CODEX_DOC` 中已有的阶段细节、专题细节、契约细节吞掉。
4. 若 `CODEX_DOC` 本身没有正式源内容，则 `JB_DOC` 不应伪造，只能标记“待补源内容”。

## 3. 判定规则

本文件统一使用两类判定：

### 3.1 A 类：已有源内容，仅需投影

定义：

- `CODEX_DOC` 中已经存在正式设计、正式计划或正式分析文档；
- 文档内容已经达到“可被标准化重组”的程度；
- 当前 `JB_DOC` 若只有总包吸收、摘要吸收或尚未建立对应对象，则问题属于“未投影完整”，不是“无源可投”。

### 3.2 B 类：源内容缺失，需先补 `CODEX_DOC`

定义：

- `CODEX_DOC` 中只有总纲、边界、字段名或原则性描述；
- 缺少足以支撑 `JB_DOC` 做完整投影的正式源内容；
- 若此时直接在 `JB_DOC` 中展开，会变成脱离 `CODEX_DOC` 的倒灌或自我发挥。

## 5. B 类细分规则：源内容缺失，但成熟度不同

本轮确认，原来的 `B` 类不能再被当作一个单层桶处理，而应进一步细分为两类：

### 5.1 `B1`：已具备补源条件，补完即可投影

定义：

- `CODEX_DOC` 中已经存在稳定对象名、职责边界、最小字段语义、消费面或约束规则；
- 缺的不是方向，而是“契约级落版”；
- 只要把这些内容整理成正式 schema / 状态机 / 接口契约文档，就可以继续向 `JB_DOC` 投影；
- 这类对象不应继续长期停留在“概念上知道缺什么”的状态。

### 5.2 `B2`：仍属硬缺口，暂不投影

定义：

- `CODEX_DOC` 中还没有足够稳定的正式源文入口；
- 或当前只有前置分析、后置预留、占位目录、策略口径；
- 如果现在直接在 `JB_DOC` 中展开，仍会变成脱离 `CODEX_DOC` 的倒灌或自我发挥。

## 8. 现阶段的真实判断

### 8.1 当前主要问题不是 `JB_DOC` 不适合做

当前最主要的问题不是“`JB_DOC` 不该细”，而是：

- 之前的 `JB_DOC` 实施策略更偏“上位标准文档包”
- 没有把 `CODEX_DOC` 里已经存在的阶段级、专题级正式设计继续投影进去

因此，`P1 / P2 / P3 / P4 / P6.1` 这部分的首要动作，不是继续争论 `JB_DOC` 要不要有，而是应该立即补全投影。

### 8.2 当前源侧缺口已不再是单层问题

当前真正的源侧缺口，应该被拆成两层：

1. `B1`：已具备补源条件的契约级缺口
   - 主要集中在 `P1 / P2 / P3 / P4`
   - 这类对象不缺方向，缺正式 schema / 状态机 / 接口文档
2. `B2`：仍属硬缺口的正式源文缺失
   - `P5` 独立正式设计
   - `P6.R1 / P6.R2`
   - 平台级测试、发布、移交、实例样例链

### 8.3 当前 `JB_DOC` 的缺口应分三种处置

- 对 A 类对象：
  - 直接补投影
- 对 `B1` 类对象：
  - 先在 `CODEX_DOC` 中补成正式契约
  - 补完后立即继续投影到 `JB_DOC`
- 对 `B2` 类对象：
  - 保持缺口标记
  - 不提前在 `JB_DOC` 中伪造完整正文

不能再把这些问题混成一句“`JB_DOC` 现在还不够完整”。

## 9. 建议的后续补齐顺序

建议严格按以下顺序推进：

1. 先补 A 类投影
   - `P1`
   - `P2`
   - `P3`
   - `P4` 总体与 4 个专题
   - `P6.1`
2. 并行补 `B1` 类源内容
   - `P1` 接口契约与产物 schema
   - `P2` 子结构 schema 与导出契约
   - `P3` 状态机与数据契约包
   - `P4` 协议级 API / 事件 / 错误码契约
3. `B1` 补完后立即继续投影
   - 不必等 `P5`、测试链或发布链全部补完才继续 `JB_DOC`
4. 最后处理 `B2` 硬缺口
   - 优先 `P5`
   - 再补 `P6.R1 / P6.R2`
   - 再补测试、发布、移交与项目实例链

这样做的原因是：

- 可以先把已经成熟的设计结论完整映射到 `JB_DOC`
- 同时把“马上可补源的契约缺口”和“仍需继续沉淀的硬缺口”分开
- 避免继续把“投影不足”、“可快速补源”和“硬缺源”混为一谈

## 10. 本轮结论

本轮结论明确如下：

1. `JB_DOC` 的正确定位是 `CODEX_DOC` 的严格投影层，而不是替代根。
2. 当前 `P1 / P2 / P3 / P4 / P6.1` 的大量正式内容，其实已经存在于 `CODEX_DOC`，只是尚未完整投影到 `JB_DOC`。
3. 原 `B` 类应继续细分为：
   - `B1`：已具备补源条件，补完即可投影
   - `B2`：仍属硬缺口，暂不投影
4. 当前最适合立即推进的是：
   - A 类投影补齐
   - `B1` 类契约级源文补齐
5. 后续所有“`JB_DOC` 不完整”的表述，都应拆解为：
   - `JB_DOC` 漏投
   - `CODEX_DOC` 的 `B1` 可补源缺口
   - `CODEX_DOC` 的 `B2` 硬缺口
