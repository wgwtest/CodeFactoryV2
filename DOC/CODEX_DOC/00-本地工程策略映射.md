# CodeFactoryV2 本地工程策略映射

本文件用于把 `CodexProject` 的全局工程策略映射为 `CodeFactoryV2` 的本地执行规则。

## 1. 本地路径判定

### 1.1 仓库主目录

- `CodeFactoryV2`

### 1.2 用户检查目录

- 当前项目默认与仓库主目录一致
- 用户查看页面、阅读文档、做人工验收时，应以当前仓库目录为准

### 1.3 正式文档根

- `DOC/CODEX_DOC/`

这是当前项目唯一的正式本地文档根。

### 1.4 正式原型与附图根

- 当前正式原型根：`DOC/CODEX_DOC/08_原型与附图/`
- 历史原型与评审记录根：`DOC/CODEX_DOC/07_过程文档/05_历史原型与评审记录/`

当前项目不再把 `03_规范与流程/04_原型与附图/` 作为默认正式原型入口。若后续因兼容旧引用短期保留该路径，必须在本文明确写成迁移兼容路径，不能与 `08_原型与附图/` 并列为当前事实源。

## 2. 三层协同映射

### 2.1 正式文档层

路径：

- `DOC/CODEX_DOC/`

职责：

- 沉淀长期有效的正式设计
- 沉淀 WBS 总纲和阶段计划
- 沉淀正式测试文档和过程文档
- 对外提供稳定引用路径

### 2.2 superpowers 工作层

路径：

- `docs/superpowers/`
- `.superpowers/`

职责：

- 承接 brainstorm、方案草案、执行计划、issue 镜像
- 支持快速推演和阶段性迭代

约束：

- `docs/superpowers/` 不是单一权威源
- `.superpowers/brainstorm/` 一类内容属于临时工作产物，不应被引用为正式规范
- 被用户确认、被项目采纳的结论，必须回写到 `DOC/CODEX_DOC/`
- 用户默认不会去读 `docs/superpowers/` 或 `.superpowers/brainstorm/`；当前项目的用户审阅事实源默认只有 `DOC/CODEX_DOC/`

### 2.3 远端协作层

载体：

- GitHub Project
- GitHub Issues
- Pull Requests

职责：

- 排程
- WBS 树投影
- 执行契约
- 评审反馈

约束：

- 远端路径默认引用仓库相对路径
- 正式文档优先引用 `DOC/CODEX_DOC/`
- `docs/superpowers/` 路径可作为工作过程证据引用，但不替代正式节点文档

## 3. 文档更新规则

### 3.1 正式设计更新触发条件

出现以下任一情况时，必须更新 `DOC/CODEX_DOC/`：

- 一级或二级 WBS 节点结构发生变化
- 平台模块边界、输入输出契约发生变化
- 用户明确确认某一份 `superpowers` 设计草案成为正式方案
- 新增阶段级功能说明、长期有效规范或正式验收口径

### 3.2 superpowers 文档的使用方式

允许继续使用 `superpowers` 的典型场景：

- 方案探索
- 设计草案
- 局部实现计划
- 历史过程证据
- 分支或并行线的工作过程文档

但后续开发必须遵守：

- 先有工作文档，不等于已经有正式规范
- 正式规范必须回写 `DOC/CODEX_DOC/`
- 如果 `DOC/CODEX_DOC/` 与 `docs/superpowers/` 冲突，以 `DOC/CODEX_DOC/` 为准

### 3.3 `superpowers / brainstorming` 强制回写门槛

当前项目对 `docs/superpowers/` 与 `.superpowers/brainstorm/` 固定采用如下口径：

1. 它们是工作层，不是用户默认审阅入口。
2. 因此，某项关键设计即使已经写进 `spec` 或 `brainstorming`，只要尚未进入 `DOC/CODEX_DOC/`，就不能默认认为用户已经看到或已经确认。
3. 只要工作层文档中形成以下任一类关键结论，就必须在同一轮同步回正式文档根：
   - 页面结构与关键交互
   - 对象模型、状态模型、输入输出契约
   - WBS 拆分、实施顺序、阶段边界
   - 原型、效果图、截图附图、设计依据和可视化评审结论
   - 导出、运行、监控、回流、验收等长期规则
4. 同步时必须按内容语义落到正式目录：
   - 设计规则落到 `02_设计说明/`
   - 共享接口、关键流程、设计实现映射落到 `03_规范与流程/`
   - WBS 与实施计划落到 `04_研制计划/`
   - 节点执行边界落到 `05_节点合同/`
   - 自测、验收、交接落到 `06_测试文档/` 与 `07_过程文档/`
   - 当前正式原型、效果图和附图落到 `08_原型与附图/`
   - 被替代或未通过的原型版本落到 `07_过程文档/05_历史原型与评审记录/`
5. 在以下动作之前，必须先完成正式文档根同步：
   - 向用户汇报“已设计 / 已明确 / 可以开发”
   - 让用户按文档检查或确认
   - 依据该结论进入编码
   - 编写正式自测、验收、交接文档
   - 执行正式 `git commit` / `git push`
6. 如果关键内容还只存在于工作层，则它只能被称为草稿、过程稿或内部推演材料，不能被称为正式设计、正式计划或用户已确认基线。

### 3.4 术语与对象命名可理解性规则

当前项目在正式文档中新增对象名、模块名、页面区块名、状态名或其他长期术语时，固定采用以下口径：

1. 默认先写中文主名，再在括号内补英文名、代码名或类名。
2. 不允许只写 `Delivery Order`、`Runtime Monitor`、`Build Attempt` 这类英文内部名而不给中文主名。
3. 如果术语会进入图、表、接口说明或验收文案，首次出现时必须能让不读源码的评审者直接理解其含义。
4. 对象模型和模块设计必须分开写：
   - 对象模型回答“系统保存什么事实”
   - 模块设计回答“谁负责处理这些事实”
5. 页面交互设计不得只写页面区块，还必须明确：
   - 该区块映射到哪个模块
   - 读取哪些输入
   - 写入哪些输出
   - 会影响哪些后续模块或对象状态
6. 对阶段级或节点级正式设计，默认至少补以下一种结构图：
   - 模块关系图
   - 对象与模块映射图
   - 页面区块与模块映射图

### 3.5 需求规格说明主文档与补充文档规则

当前项目明确继承 `project-engineering-strategy` 中关于需求规格说明文档的两层要求：**内容结构要求** 和 **补充治理流程要求**。

#### 3.5.1 主文档定位

对 `P2` 以及后续其他阶段中承担下游正式输入职责的需求规格说明类文档，固定采用：

- `主文档`：承载当前稳定、可引用、可冻结、可交付的结果版内容；
- `补充文档`：承载本轮拟新增、改写、重组、下沉到主文档的计划性内容。

补充文档在用户审核通过前，不得冒充主文档当前正式结论。

#### 3.5.2 主文档内容结构要求

当前项目中的需求规格说明类主文档，不得退化为：

- 零散条目汇总；
- 纯问答转写；
- 只有 patch 建议的碎片集合；
- 只有表单字段堆叠而没有章节语义的文档。

至少应稳定承载以下内容：

1. 文档目的、范围、设计口径、术语约定；
2. 总体业务目标、总体架构理解、阶段定位；
3. 总体分层、总体模块划分、模块间边界；
4. 关键角色、核心业务对象、对象关系、行为和状态变化；
5. 关键流程、关键规则、约束条件、边界和非目标；
6. 若系统包含前后端或多端协同，应分别写明：
   - 后端技术栈、分层原则、模块总览、模块职责、关键服务边界、关键数据对象；
   - 前端技术栈、分层原则、页面 / 工作台划分、视图模型、装载生命周期、状态机与交互状态；
7. 对每个关键子模块继续下钻说明：
   - 模块定位；
   - 输入输出；
   - 内部子模块组成；
   - 关键接口或命令；
   - 关键状态与异常处理；
   - 与其他模块的协作关系；
8. 完成条件、检查口径、冻结口径、验收关注点；
9. 面向下游阶段的正式输出对象、交接约束和消费方式。

#### 3.5.3 补充治理流程要求

只要改动涉及以下任一类型，默认不直接改主文档，而先写补充文档：

- 章节结构调整；
- 口径边界变化；
- 信息显著增删；
- 新增总体架构、总体分层、模块设计、状态机、装载生命周期等关键结构内容；
- 影响下游消费方式、冻结口径或正式输出对象。

补充文档至少应写明：

- 为什么补；
- 补哪些章节；
- 预计如何落版；
- 哪些内容仍待确认；
- 完成后如何回写主文档。

执行顺序固定为：

1. 先写补充计划 / 补充设计 / 补充说明；
2. 交用户审核补充方向；
3. 审核通过后，把最终采纳结论回写主文档；
4. 补充文档保留为过程依据，但不替代主文档承担长期结果职责。

#### 3.5.4 例外规则

若仅涉及：

- 错别字；
- 轻微措辞修正；
- 明显排版修正；
- 不改变章节语义的微调；

可直接修改主文档，不单独创建补充文档。

### 3.6 确认设计稿到代码实现规则

当前项目固定采用以下设计稿实现口径：

1. 一旦某个设计稿、样稿、静态原型图、HTML 原型、效果图或原型包被用户明确确认为当前实现依据，它就是 UI / 页面实现基线，不是“布局参考”或“视觉灵感”。
2. 实现时必须优先遵循已确认设计稿的：
   - 页面结构；
   - 核心区块；
   - 动作入口位置；
   - 信息层级；
   - 状态表达；
   - 视觉主次；
   - 关键文案；
   - 组件形态；
   - 目标视口和响应式降级要求。
3. 现有页面组织习惯、通用组件便利性、旧交互模式或“代码上更方便”的做法，不能覆盖已确认设计稿。若确需偏离，必须在编码前写明偏离点、原因、影响和待用户确认项。
4. 开发前必须把确认设计稿拆成“设计稿到代码转换清单”或等价验收清单，不能只拆成功能事项、接口事项或 DOM 元素事项。
5. 开发后必须完成截图对照：
   - 使用设计稿 / 原型截图作为基线；
   - 使用真实运行态截图作为实现结果；
   - 逐项列出一致项、偏离项、偏离原因和修正结论。
6. 发现偏离后，默认先修正再汇报；不能把第一次截图、单测通过、构建通过、接口通过、路由 `200 OK` 或“元素存在”当作设计一致性完成证据。
7. 对有已确认设计稿的页面，机测记录、验收方法或会话交接中必须能回溯：
   - 使用了哪份设计稿 / 原型包；
   - 运行态截图在哪里；
   - 设计稿到代码转换清单在哪里；
   - 哪些偏离已修正；
   - 哪些偏离仍需用户确认。
8. 本规则优先适用于 `DOC/CODEX_DOC/08_原型与附图/` 下的正式原型包；若历史原型被用户重新指定为当前实现依据，应先迁入或引用到正式原型事实源，再进入编码。

### 3.7 最终交付前复核规则

当前项目在准备向用户发送“已完成 / 可以验收 / 已交付”这类最终交付消息前，固定增加一次最终交付复核门。

本规则不替代 `brainstorming`、计划、TDD、系统化调试、代码评审、常规验证或截图验收；它只放在所有开发、验证和截图比对之后，作为最终汇报前的最后一道复核。

执行口径：

1. 重新读取本轮用户最新要求、当前正式事实源、已确认设计稿 / 原型包 / 正式规格，以及本轮实际改动文件。
2. 对代码交付，复核改动边界、关键数据流、状态机、接口契约、测试结果和未提交差异，确认没有把临时实现、旧页面惯性或未确认偏离带入交付。
3. 对原型驱动或 UI 页面交付，复核“设计稿到代码转换清单”、原型截图、运行态截图和差异结论，确认关键结构、主对象承载方式、交互模型、动作位置、状态表达和视觉主次与事实源一致。
4. 对文档交付，复核目标目录、文件命名、主文档 / 补充文档关系、事实源引用和待用户确认项。
5. 若发现阻断性偏离、证据缺口或无法自证的判断，先修正或明确标注为待确认，不得直接宣称完成。
6. 最终回复中必须简要说明本轮完成内容、执行过的关键验证 / 比对、剩余待用户确认项或无法完成项。

## 4. WBS 与执行契约映射

- WBS 权威树来源：GitHub parent/sub-issue
- 本地 WBS 正式镜像：`DOC/CODEX_DOC/04_研制计划/`
- 本地共享规范与流程入口：`DOC/CODEX_DOC/03_规范与流程/`
- 本地正式原型与附图入口：`DOC/CODEX_DOC/08_原型与附图/`
- 历史原型与评审记录入口：`DOC/CODEX_DOC/07_过程文档/05_历史原型与评审记录/`
- 阶段级、节点级长期说明：`DOC/CODEX_DOC/02_设计说明/`
- 节点级执行合同：`DOC/CODEX_DOC/05_节点合同/`
- 过程性计划与历史过程证据：`docs/superpowers/plans/`、`docs/superpowers/issues/`

### 4.1 WBS 读取口径

当前项目固定采用以下 WBS 读取规则：

1. GitHub parent/sub-issue 是 WBS 树唯一事实源。
2. GitHub Project 只作为投影视图，不替代 issue 树成为结构事实源。
3. 默认不再新增或维护本地 `issue tree mirror` 作为当前树状态入口。
4. 当需要确认当前节点标题、正文、父子关系、状态时，优先直接查询远端 GitHub。
5. 如果远端暂时不可访问，只能回退到仓库主工作树中的正式文档根：
   - 也就是当前项目主目录下的 `DOC/CODEX_DOC/`
   - 不使用隔离 `worktree` 或当前并行目录中的 mirror / 派生文件反推当前远端树
6. 这种回退结果只能被标记为：
   - `本地快照`
   - 或 `待远端复核`
7. 已有的 `docs/superpowers/issues/` 历史文件，只保留为过程证据或历史快照，不再作为当前 WBS 事实入口。

## 5. 分支与 worktree 策略

### 5.1 默认策略

- 默认在 `main` 推进
- 默认不使用 `git worktree`
- 默认从仓库主目录启动服务和进行用户验收

### 5.2 例外策略

只有在用户明确要求并行开发时，才允许建立独立分支或受控 worktree。

即使启用了并行线，也必须遵守：

- 用户可见成果先回到主工作区
- 正式文档先回写 `DOC/CODEX_DOC/`
- 不得长期让主线和并行线各自维护一套不同的正式规范

### 5.3 P1 审阅型 worktree 特例

`P1` 与其他阶段 worktree 的默认角色不同。P1 业务知识库的主要实现工作通常由其他同志主导完成，因此 `.worktrees/p1-knowledge-base-review` / `feat/p1-knowledge-base-review` 的默认定位是**审阅与建议型 worktree**，而不是 P1 主实现分支。

执行口径：

- 默认工作内容是差异审阅、运行验证、风险提示、验收反馈和建议文档整理。
- 对 P1 代码的较大结构性改动，先形成审阅意见、问题证据和改造建议；除非用户明确授权，不主动替代 P1 主负责人重写实现。
- 允许进行低风险、小范围修复，例如文档入口、验收说明、测试说明、轻微配置或可复现验证脚本补充。
- 正式启动服务、用户验收、提交和推送仍默认回到仓库主目录执行。
- 新会话进入该 worktree 时，先读取 `WORKTREE_GUIDE.md`，再读取 `CODEX_START_HERE.md` 和 `DOC/CODEX_DOC/` 下的正式 P1 文档。

## 6. 当前项目特别说明

- `P1` 已形成可运行的知识库最小闭环，但仍在抽取质量与展示逻辑上持续优化
- `P2` 已形成设计方向与模拟输入台文档，但正式独立执行契约仍需持续补齐
- `P3`、`P4` 已形成较完整的 `superpowers` 设计/计划/issue 镜像
- `P6` 已开始建立门户层文档，但需要纳入正式 WBS 体系

## 7. 后续执行口径

从本文件生效开始，本项目采用如下口径：

- `superpowers` 负责“快推演、快分解、快起草”
- `DOC/CODEX_DOC` 负责“正式落版、长期追踪、稳定引用”
- 后续方案开发以二者协同为准，不再让单一目录同时承担全部职责
