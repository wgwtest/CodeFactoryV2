# P2 组织器 5 轮迭代升级扩展研制计划

**文档性质：** 本批次执行计划  
**创建时间：** 2026-05-11  
**适用分支：** `feat/p2-requirement-analysis-system`  
**上位依据：** `DOC/CODEX_DOC/04_研制计划/02.06-WBS-P2-组织器多轮自测整改闭环-研制计划.md`

## 1. 目标

本批次在既有 6 轮 P2 组织器整改结果基础上，再执行最多 5 个完整迭代轮次，继续提升 `brainstorm-v1` 与 `brainstorm-v1-dify-workflow` 在态势分析系统样例上的需求探索、决策沉淀、下一问质量和最终草案详实度。

本批次不是把已知问题拆成 5 个固定任务。每一轮都必须按以下闭环执行：

```text
当轮测试
  -> 当轮问题诊断
  -> 当轮可整改问题全量整改
  -> 当轮复测
  -> 当轮记录与证据归档
  -> 进入下一轮
```

## 2. 测试对象

本批次主要测试和整改对象为：

- `brainstorm-v1`
- `brainstorm-v1-dify-workflow`

Codex `brainstorming` skill 作为参考标杆，不作为 P2 插件整改对象。本批次可以复用既有 Codex skill 对照记录；如当轮发现 P2 与 skill 的差距无法解释，应在分析报告中补充差距判断，但不要求每轮重新启动真实 Codex skill 会话。

## 3. 核心优化目标

本批次以质量向好为目标，不以“跑满 5 轮”为目标。优先观察以下变化：

1. 最终正文有效字数、平均正文块有效字数、实质正文块数和草案丰富度是否提升。
2. 已确认事实数、已确认决策数和事实到决策转化能力是否稳定。
3. 开放问题是否具备新增、关闭、延期或进入待确认事项的生命周期，而不是只增不减。
4. 下一问是否聚焦一个关键缺口，是否承接已确认内容，是否避免重复追问。
5. Dify workflow 是否在保持稳定合同输出的同时改善草案偏薄问题。
6. `brainstorm-v1` 是否在保持正文较丰富的同时降低开放问题膨胀和决策波动。

## 4. 修改边界

### 4.1 优先允许修改

- `orchestrators/xg/brainstorm-v1/**`
- `orchestrators/xg/brainstorm-v1-dify-workflow/**`
- Dify 工程 workflow、节点 Prompt、输出 schema 和节点连接
- 需求规格说明模板
- 组织器专属 prompt、schema、manifest、adapter
- 测试脚本、测试记录和分析 JSON

### 4.2 谨慎修改

P2 平台本体只允许修改通用机械能力，例如合同归一化、错误诊断、外部 workflow 日志、通用 JSON 修复、通用指标采集。不得把用户意图、章节语义、需求事实判断、下一问策略等业务逻辑写死在平台 Python 代码中。

## 5. 每轮执行规则

每轮默认使用 `scripts/p2_orchestrator_multiturn_probe.py` 的 `dynamic` 模式进行受控动态考官测试：

```bash
uv run python scripts/p2_orchestrator_multiturn_probe.py \
  --base-url http://127.0.0.1:8020 \
  --orchestrator brainstorm-v1 \
  --orchestrator brainstorm-v1-dify-workflow \
  --provider deepseek \
  --model provider-default \
  --template-id xg-template-81433-默认运算软件需求规格说明模板实例-v1-0 \
  --topic 态势分析系统需求规格探索 \
  --mode dynamic \
  --max-turns 20 \
  --output-dir .run-logs/p2-iteration-260511-roundN
```

如本地端口实际为 `8000`，允许把 `--base-url` 调整为 `http://127.0.0.1:8000`，但测试记录必须写明实际端口和原因。

## 6. 每轮记录要求

每轮至少保留：

- `.run-logs/p2-iteration-260511-roundN*/summary.json`
- `.run-logs/p2-iteration-260511-roundN*/<orchestrator>.summary.json`
- `.run-logs/p2-iteration-260511-roundN*/<orchestrator>.turns.metrics.jsonl`
- `.run-logs/p2-iteration-260511-roundN*/<orchestrator>.turns.raw.jsonl`
- `.run-logs/p2-iteration-260511-roundN*/<orchestrator>.final-session.json`

每轮正式记录写入：

```text
DOC/CODEX_DOC/06_测试文档/03_机测记录/2026-05测试/YYMMDD-HHMM-P2-组织器5轮扩展第N轮测试记录.md
```

如果当轮产生代码或 Dify workflow 修改，必须在测试记录中写明：

- 问题触发 Turn
- 复现输入
- 实际输出
- 期望输出
- 问题归属
- 修改文件或 Dify 节点
- 复测结果

## 8. 暂停与结束条件

允许提前停止的条件：

1. 两个组织器连续两轮无 400/500，显式收束均能生成可审阅草案。
2. 至少一个核心正文质量指标形成明确向好趋势。
3. 已确认事实和已确认决策稳定沉淀。
4. 剩余问题已明确归属到更大设计变更、外部权限或外部服务条件。

必须暂停的条件：

1. DeepSeek 或 Dify 外部模型额度不足导致无法完成有效 Turn。
2. Dify 工程无法访问或发布失败，且本轮问题属于 Dify workflow。
3. 测试脚本或数据采集存在明显错误，导致结论不可用。
4. 发现需要修改 P2 平台本体业务判断逻辑，必须先形成补充设计。
