# 00 P1 Mid Term 黄金样例并行总说明

## 共同目标

围绕黄金样例目录 `E:\project\Web\智能软件生成\知识构建原始材料\体系结构运行测试小规模v3\Mid Term`，把 P1 清洁版从“模块骨架 + 局部真实能力”推进到可演示的端到端样例：

- 能创建一个 Mid Term 知识库。
- 能导入和解析 8 个 DOCX。
- 能选择/冻结一版策略规则合同。
- 能启动抽取并实时显示运行状态。
- 能生成跨文档合并后的知识对象、关系和证据链。
- 能在知识成果和质量图谱中看懂产出质量。
- 能形成发布候选和系统间输出合同预览。

## 六条工作线

- W1：资料接入与解析预检。
- W2：策略规则与字段合同执行。
- W3：抽取运行与实时流。
- W4：知识生成与跨文档合并。
- W5：知识成果与图谱质量展示。
- W6：质量发布与系统间输出。

## 开工前必须先回复

每个并行线程在开始改代码前，必须先向主线程回复以下内容：

```text
工作线：W?
我理解的目标：
计划修改文件：
计划新增文件：
可能影响其它工作线的合同字段：
需要主线程后续合并时重点检查的风险：
```

只有计划清楚后再动手。不要一上来大范围搜索后直接改全局文件。

## 并行边界规则

- 每个线程只修改自己任务包中“允许修改范围”内的文件。
- 如果必须修改共享文件，先把理由写在最终回报里，并尽量做薄适配。
- 共享文件包括但不限于 `p1_refactor.py`、`contracts/**`、`runtime_contract.py`、`policy_config.py`、`P1CleanApp.css`、`registry.ts`。
- 不要跨模块直接读取其它模块内部 state。
- 模块间只能通过统一上下文和合同字段衔接：`archiveId`、`documentSetId`、`policyPackageVersionId`、`runtimeSnapshotId`、`publicationSnapshotId`。
- 旧 P1 页面只能作为参考，不允许整块搬进新 P1。

## 数据与 Git 规则

- 不做 git commit。
- 不 push。
- 不 reset。
- 不 checkout 覆盖其它线程改动。
- 不删除或清理其它线程文件。
- 不写入或提交 `.data/**`、`.codex-runtime/**`、本地样例源目录。
- 不上传本地样例资料。
- 如果发现工作区已有其它线程改动，必须保留并绕开，不要回滚。

## 合同变更规则

如果某条线新增或修改合同字段，必须在最终回报里明确写出：

- 新增字段名。
- 字段所属合同。
- 字段类型。
- 上游来源。
- 下游消费者。
- 是否兼容旧字段。
- 是否需要其它线程同步。

合同字段不要只藏在 UI 或 mock 数据里，必须有类型、adapter 或后端 schema 支撑。

## Mock 与 Fallback 规则

- 可以使用 fallback 保障页面可演示，但必须显式标注。
- 禁止把 fixture/mock 伪装成 live 正式结果。
- 如果接口还不存在，先在本模块 adapter 层收敛 fallback，不要让页面到处写临时判断。
- 最终回报必须列出仍然是 fallback/mock 的功能点。

## 验收优先级

优先保证下面这条端到端路径能跑通：

1. `/p1` 创建 Mid Term 知识库。
2. 进入 `资料接入`，看到 8 个 DOCX。
3. 进入 `策略规则`，看到冻结策略包和规则合同。
4. 进入 `抽取运行`，启动并看到 stream/polling 状态、事件流和运行图谱。
5. 进入 `知识成果`，看到知识对象、关系、证据和图谱。
6. 进入 `质量图谱`，看到质量指标和问题解释。
7. 进入 `发布输出`，看到发布候选状态。
8. 进入 `系统间输出`，明确是否可供应正式知识。
