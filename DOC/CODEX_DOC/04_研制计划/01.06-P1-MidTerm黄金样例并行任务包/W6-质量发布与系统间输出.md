## 目标

- 从 `runtimeSnapshotId`、质量报告和知识解析快照生成 `publicationSnapshotId`。
- 发布输出页面明确区分：抽取工作态、发布候选态、治理待确认、正式入库态。
- 系统间输出页面只暴露治理确认后的正式知识；如果尚未正式入库，必须清楚显示不可供应原因。
- 为后续 P2/P3/P6 系统提供稳定的读取合同说明和 API 预览。

## 系统间输出最低要求

- 明确合同版本。
- 明确是否正式入库。
- 明确可暴露 API 范围。
- 明确下游系统可读取的对象、关系、证据、版本号。
- 未正式入库时禁止显示为可供应。

## 与其它工作线的边界

- W5 负责质量展示，本工作线消费质量结果并生成发布候选。
- W4 负责知识生成，本工作线不重新合并知识。
- `/governance` 仍是人工治理职责，本工作线只展示候选和正式供应状态。

## 注意事项

- 发布候选不等于正式入库，页面和接口都必须明确区分。
- 系统间输出只能供应治理确认后的正式知识；候选态只能显示不可供应原因和预览。
- 不要改 `/governance` 人工治理页面职责。
- 如果使用 fixture 候选快照，必须在页面或合同中标明，不要伪装正式结果。
- 与 W5 共用质量结论时，只消费质量报告，不重新计算质量指标。

## 验收方式

- Mid Term 抽取完成后，进入顶部导航 `发布输出`。
- 页面显示机器已生成发布候选，且尚未治理确认时不会显示正式入库。
- 进入 `系统间输出`，如果没有正式入库，显示不可供应原因。
- 如果已有正式版本，系统间输出能显示正式知识供应合同和 API 范围。
- 所有状态都能追溯到 `publicationSnapshotId` 或正式版本 ID。
