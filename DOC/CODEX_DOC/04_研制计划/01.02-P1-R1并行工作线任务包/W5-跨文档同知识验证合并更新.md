# W5 - 跨文档同知识验证、合并与更新

## 新线程启动提示词

你正在接手 CodeFactoryV2 的 P1 业务知识库重构工作线 W5。仓库路径是 `E:\project\Web\智能软件生成\CodeFactoryV2`。本线目标是解决同一知识库中不同文档之间“相同知识”的验证、合并、替换、冲突和更新机制，并在规则变更后生成候选级增量重算计划。不要提交 git，不要提交本地数据内容，不要修改终端用户入口和正式治理发布页面。请先阅读 P1 重构设计中的“库级同知识验证、合并与更新机制”、R0 knowledge resolution contracts，再按本文件边界实现。

## 目标

- 为知识对象建立 `KnowledgeIdentityKey`，支持跨文档同知识识别。
- 生成 `CrossDocumentMatchCandidate`，说明相似度、证据、建议动作。
- 生成 `KnowledgeMergeDecision`，区分 merge、keep_separate、replace、mark_conflict。
- 生成 `CanonicalKnowledgeItem`，承接同知识合并后的候选/正式知识对象。
- 规则或策略变化后，生成 `KnowledgeUpdatePlan` 和 `ImpactSet`，只做候选级重算，不覆盖正式知识。

## 边界

- 负责同知识识别、合并决策、更新计划、影响面候选。
- 可以新增：
  - `apps/api/app/archive_knowledge/resolution`
  - `apps/api/app/archive_knowledge/identity`
  - `apps/web/src/features/p1/resolution`
- 可以补充 `knowledgeResolution.ts/py`、`impact.ts/py` 合同。
- 不负责质量指标算法本身，但可以消费 W4 输出。

- `KnowledgeQualityReport`

## 输出合同

- `KnowledgeIdentityKey`
- `CrossDocumentMatchCandidate`
- `KnowledgeMergeDecision`
- `CanonicalKnowledgeItem`
- `KnowledgeUpdatePlan`
- `ArchiveKnowledgeResolutionSnapshot`

## 禁止改动范围

- 不把候选合并结果直接写入正式知识库。
- 不跳过治理确认生成正式入库版本。
- 不用单一名称相等作为唯一同知识判断，至少要保留身份键、字段、证据、相似度解释。
- 不直接修改 `/governance` 页面职责。
- 不提交 git，不提交本地数据、运行产物、解析产物。

## 建议实现范围

- 先做确定性 identity key：知识类型、规范名称、业务范围、关键字段。
- 再做相似度候选：名称相似、字段重叠、证据锚点、来源文档。
- 合并决策必须记录规则执行记录和原因。
- stale 对象进入 update plan，不立即覆盖正式版本。
- API adapter 提供 `/api/p1/archives/{archive_id}/knowledge-resolution/latest` 的真实结构。

## 验收方式

- 两份文档中相同知识能生成 match candidate。
- 合并候选能解释为什么建议合并或保留。
- 规则变更后能输出最早重算阶段和受影响对象。
- 正式知识不会被候选重算直接覆盖。
