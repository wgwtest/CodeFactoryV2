# P2 组织器运行时深化解耦升级实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 `02.04` 已完成策略解释型组织器共享宿主 runtime 的基础上，继续消除 adapter 对宿主会话快照结构的理解，收敛业务命名阶段归约逻辑，并完成决策状态服务副本归属收口。

**Architecture:** 本阶段以“请求映射回宿主、阶段归约合同化、决策状态服务单一归属”为主线。策略解释型 adapter 不再构造 `SessionSnapshot`，宿主新增 `OrchestratorRunRequestMapper` 或等价对象统一构造 runtime input；`TurnStageReducer` 从业务阶段专用归约升级为按 `output_targets/adoption` 驱动的通用归约；启发式和 Brainstorm V1 插件目录不再保留 `decision_state_service.py` 副本。

**Tech Stack:** FastAPI, Pydantic, Python service layer, importlib, pytest.

### 本阶段新增解耦判据

1. 策略解释型 adapter 不得构造 `SessionSnapshot`。
2. 策略解释型 adapter 不得导入 `RequirementAnalysisTurnCreate`。
3. request 到 runtime input 的转换必须集中在宿主 runtime 层。
4. 通用运行时主流程不得依赖 `reduce_intent_stage`、`reduce_review_stage` 等业务命名归约方法。
5. 阶段输出必须按 `output_targets` 和 `adoption` 显式采纳。
6. 启发式组织器和 Brainstorm V1 插件目录不再保留 `decision_state_service.py` 副本。
7. 移除 `xg-strong-rule-orchestrator`，不再保留需求分析本地 runner 过渡例外。

## 10. 风险控制

1. 先加 adapter 架构护栏，再迁移 request mapper。
2. 阶段归约通用化必须保持旧阶段输出合同不变。
3. 删除 `decision_state_service.py` 副本前必须用 `rg` 和测试确认无引用。
4. 强规则组织器目录、发现结果和 API 入口必须被彻底删除。
5. 若归约器通用化影响范围过大，应允许先保留兼容方法，但主流程不得再依赖这些业务命名方法。
