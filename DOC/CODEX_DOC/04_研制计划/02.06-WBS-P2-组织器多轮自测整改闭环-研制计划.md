# P2 组织器多轮自测整改闭环研制计划

> **For agentic workers:** 本计划是 P2 需求分析组织器质量提升的工作模式约束。执行本计划时，不得把已知问题预拆成 10 个固定任务慢慢处理；每一轮必须把本轮测试发现的问题尽量全量整改、复测通过并归档后，才进入下一轮。

**Goal:** 建立 `brainstorm-v1` 与 `brainstorm-v1-dify-workflow` 两个组织器的多轮自测、诊断、整改、复测闭环，使组织器质量通过连续会话测试逐轮收敛。

**Architecture:** 每轮以“受控动态考官”多轮会话作为默认质量探针，固定 20 Turn 输入链只作为历史回归链路。测试发现的问题先按归属分类：插件、Dify workflow、Prompt/schema、需求规格说明模板、P2 平台通用合同。优先修改插件、Dify workflow、Prompt/schema 和模板；P2 平台本体只在确认属于通用机械合同或通用可观测能力时谨慎修改。

**Tech Stack:** FastAPI, Pydantic, pytest, pnpm/vitest, P2 orchestrator plugin contract, Dify Workflow, DeepSeek Chat, Markdown documentation.

## 2. 核心工作模式

### 2.1 正确迭代模式

本计划最多执行 10 个完整迭代轮次。每轮不是预设固定整改点，而是执行以下闭环：

```text
第 N 轮测试
  -> 第 N 轮问题诊断
  -> 第 N 轮全量整改
  -> 第 N 轮复测
  -> 第 N 轮报告归档
  -> 进入第 N+1 轮
```

进入下一轮的前提：

1. 本轮测试发现的问题已经全部分类。
2. 本轮可整改问题已经尽量全部整改。
3. 本轮阻塞问题已经通过复测。
4. 本轮遗留问题已经说明原因、归属和下一步处理条件。
5. 本轮设计补充、测试记录和变更说明已经归档。

### 2.2 错误迭代模式

禁止以下做法：

1. 把第一轮已发现问题拆成 10 轮慢慢修。
2. 只修一个最显眼问题就进入下一轮。
3. 用“下一轮再看”替代本轮能完成的整改。
4. 为了通过测试在 P2 平台里写业务判断硬编码。
5. 只看接口 `200 OK`，不分析会话质量。

## 3. 每轮固定流程

### 3.1 第 N 轮测试

测试对象：

- `brainstorm-v1`
- `brainstorm-v1-dify-workflow`

测试方式：

1. 默认使用 `态势分析系统` 样例下的受控动态考官策略。
2. 首轮只输入基准起始输入；后续轮次根据组织器的下一问、选项、结构化状态和正文投影动态回答。
3. 每轮考官输入最多覆盖一个主题，通常不超过 3 条事实；不得一次性释放完整角色表、功能表、流程表、数据表或验收表。
4. 固定 20 Turn 连续输入链仅作为历史回归链路，不能替代动态考官测试。
5. 每个组织器单独创建会话。
6. 每轮记录：
   - Turn 状态码
   - assistant 回复
   - decision state 指标
   - open questions 指标
   - document patch 指标
   - working document blocks
   - provider logs 或 external workflow logs
   - 失败请求与失败响应

最低数据字段：

```json
{
  "iteration": 1,
  "orchestrator_id": "brainstorm-v1",
  "turn_index": 12,
  "status": 200,
  "assistant_message": "",
  "confirmed_facts_count": 0,
  "open_questions_count": 0,
  "closed_questions_count": 0,
  "document_patch_count": 0,
  "working_document_blocks": 0,
  "examiner_action": "",
  "turn_control_mode": "",
  "error": null
}
```

### 3.2 第 N 轮问题诊断

每个问题必须归入以下类别之一：

| 类别 | 判定标准 | 优先修改对象 |
| --- | --- | --- |
| 插件合同问题 | 插件输出字段缺失、错配、违反 schema | 插件 schema、adapter、prompt |
| Dify workflow 问题 | Dify 节点分支、Prompt、输出归一化不合理 | Dify 工程 |
| Prompt/schema 问题 | 模型不知道应输出什么或输出约束不够 | Prompt、schema |
| 模板问题 | 模板无法承载合理章节或导致稳定错投影 | 需求规格说明模板 |
| 平台通用合同问题 | 多组织器共同需要的机械校验、归一化、日志能力 | P2 平台 |
| 测试脚本问题 | 测试环境、代理、脚本采集错误 | 测试工具 |

诊断必须写清：

1. 触发 Turn。
2. 复现输入。
3. 实际输出。
4. 期望输出。
5. 问题归属。
6. 当轮整改策略。

### 3.3 第 N 轮全量整改

整改顺序：

1. 先修阻塞性合同错误。
2. 再修收束成稿失败。
3. 再修开放问题生命周期。
4. 再修重复追问和下一问质量。
5. 再修正文投影、草案质量和模板承载。
6. 最后修日志和分析便利性。

当轮发现的问题原则上当轮全部修复。

允许进入下一轮的未修问题只包括：

1. 缺少外部权限或外部服务不可达。
2. 必须等待用户提供 Dify 工程地址或账号。
3. 已确认属于更大范围设计变更，需要单独计划。
4. 修复风险超过本轮收益，且有明确记录。

### 3.4 第 N 轮复测

复测必须至少覆盖：

1. 本轮失败 Turn 的最小复现。
2. 受控动态考官完整会话。
3. 如涉及历史回归问题，再补跑固定 20 Turn 连续会话。
4. 两个组织器横向对比。
5. `git diff --check`。
6. 相关后端/前端自动测试。

复测未通过时，不进入下一轮。

### 3.5 第 N 轮报告归档

每轮至少生成两类文档：

1. 测试记录：


## 4. 修改边界

### 4.1 优先允许修改

允许并鼓励优先修改：

1. `orchestrators/xg/brainstorm-v1/**`
2. `orchestrators/xg/brainstorm-v1-dify-workflow/**`
3. Dify 工程中的 workflow、节点 Prompt、输出 schema、节点连接
4. 需求规格说明模板
5. 组织器专属 prompt、schema、manifest、adapter
6. 测试脚本和测试记录

### 4.2 谨慎修改 P2 平台本体

P2 平台本体修改必须满足至少一个条件：

1. 属于通用机械合同能力，例如 `plan_ref` 与 `target_anchor_plan` 的一致性归一化。
2. 属于通用可观测能力，例如 external workflow log。
3. 属于通用错误诊断能力，例如合同错误定位到具体 patch。
4. 两个以上组织器都需要同一平台能力，且插件侧无法合理解决。

禁止在 P2 平台本体中写入：

1. 用户意图中文关键词判断。
2. 章节语义匹配规则。
3. 需求事实业务判断。
4. “某组织器专用”的硬编码分支。

### 4.3 模板修改条件

可以修改需求规格说明模板，但必须满足：

1. 测试证明现有模板无法稳定承载某类合理需求内容。
2. 修改后能提升多个组织器或多个场景的章节投影质量。
3. 修改记录中说明旧模板问题、新模板变化、兼容影响。

### 5.4 P-Test 可视化使用方式

如本计划执行后需要生成可视化测试分析，应按以下链路执行：

```text
本研制计划中的指标定义
  -> 单轮测试记录、交互证据附件、最终工作正文、整改说明
  -> Codex 读取并分析
  -> 生成 analysis.json
  -> P-Test HTML 模板展示
```

其中：

1. Codex 负责读取指标定义、读取测试执行产物、做必要的统计和证据化判断。
2. `analysis.json` 负责承载指标定义、指标数据、证据链接、局限说明和总体结论。
3. HTML 模板只负责稳定展示 `analysis.json`，不得在页面中写死 P2 专有判断。
4. 每个评估指标应拥有自己的趋势图；横轴为轮次，同图中叠加多个被测组织器序列。
5. 批次概览只展示少量背景信息；整改时间线只做辅助说明；证据附件通过链接下钻。
6. 若分析过程中发现需要新增指标，应先更新本计划或形成指标补充说明，再生成新的 `analysis.json`。

### 5.5 最低通过标准

最低通过标准：

1. 两个组织器均完成受控动态考官会话，无 400/500。
2. 显式收束 Turn 必须进入 `draft_delivery` 或 `draft_with_gaps`。
3. `contract_error_count=0`。
4. 开放问题不能只增不减，必须出现关闭或延期。
5. Dify 组织器必须产生可审计 external workflow log。

## 6. 10 轮上限的含义

“10 轮”不是 10 个预拆任务，而是最多 10 次完整质量闭环。

### 第 1 轮启动项

第 1 轮以主分支新增的受控动态样例策略重新启动。旧固定链路中已知问题仍作为辅助观察项，但不得覆盖动态考官策略：

1. `brainstorm-v1` 第 12 Turn `plan_ref` 合同错误。
2. 本地组织器开放问题膨胀。
3. 显式收束意图没有稳定执行。
4. Dify workflow 可观测性不足。

第 1 轮必须先按动态考官策略重新采集证据，再结合已知问题全量整改；历史 20 Turn 链路只在需要验证收束交付或复现旧缺陷时补跑。

### 第 2 至第 10 轮

第 2 至第 10 轮不预设整改内容。

每轮按测试结果重新发现问题，并把本轮发现的问题尽量全部整改。

如果某一轮达到最低通过标准和增强通过标准，可以提前结束，不必机械执行满 10 轮。

## 7. 结束条件

满足以下条件时，可以结束多轮整改：

1. 两个组织器连续两轮受控动态考官测试均无 400/500。
2. 显式收束均能进入草案或带缺口草案。
