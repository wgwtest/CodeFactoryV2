# P1-P5 到 P6 状态输出接口规范

> 归档说明：本文件作为 `P1 ~ P5 -> P6` 平台状态输出的跨阶段共享规范。凡涉及阶段概览、入口状态、核心指标、健康状态、门户节点状态负载和订阅事件包络，均以本文件为统一约束来源。
>
> 维护规则：后续若 `P1 ~ P5` 任一阶段补充对 `P6` 的状态输出能力，必须先对照本规范补齐字段与语义；若需新增共享字段或调整统一枚举，必须先回写本文件，再同步回写对应阶段正式设计与 `P6.2` 消费侧设计。

**日期：** 2026-04-20

**适用范围：**
- `P1` 业务知识库
- `P2` 需求分析系统
- `P3` 软件设计系统
- `P4` 工具仓库
- `P5` 软件构建系统
- `P6.2` 跨阶段只读集成与状态投影

## 1. 规范定位

本规范回答的不是“`P6` 页面该怎么摆字段”，而是“`P1 ~ P5` 若要向 `P6` 输出平台状态，最小必须输出什么、字段语义如何统一、哪些差异字段必须保留”。

本规范固定以下边界：

- 它是 `P1 ~ P5 -> P6` 的共享接口规范来源。
- 它只约束读侧状态输出，不约束阶段内部写入命令和私有领域对象。
- 它定义跨阶段统一最小契约与节点状态负载映射规则。
- 它不替代各阶段自己的正式设计；阶段内部来源、计算逻辑和刷新机制仍由各阶段正式文档负责说明。

## 2. 适用范围

本规范适用于以下输出场景：

- `P6.1` 门户首页展示五阶段系统状态卡
- 串行观察页展示阶段概览、核心指标和健康告警
- `P6.4` 把阶段状态作为展示实验输入
- 后续任意需要消费 `P1 ~ P5` 平台状态的只读视图

本规范当前不覆盖以下内容：

- 阶段内部写接口
- 阶段私有页面临时状态
- 非平台级、仅供单一子页面使用的调试字段
- 直接读取数据库表结构的实现细节

## 3. 职责分工

### 3.1 阶段侧职责

`P1 ~ P5` 各阶段负责：

- 生产正式状态事实
- 解释本阶段差异字段的业务语义
- 标注字段来源、更新时间和健康状态来源
- 提供最小查询接口，条件允许时再补充订阅接口

如果某阶段需要配置“状态从哪里来、何时刷新、失败时如何降级”，该配置应在本阶段正式设计或本阶段专题设计中定义，而不是交给 `P6.1` 页面临时拼装。

### 3.2 平台侧职责

`P6.2` 负责：

- 消费各阶段最小状态输出契约
- 统一映射为 `StageSnapshot`、`StageNodeStatusPayload`、`PortalProjection`
- 统一做新鲜度判断、降级标记和聚合告警

因此，`P6.2` 是消费与映射层，本规范是跨阶段共享约束层。

### 3.3 页面侧职责

`P6.1`、串行观察页和 `P6.4` 只消费 `P6.2` 输出的归一化对象，不应直接绕过平台去拼接 `P1 ~ P5` 的私有字段。

## 4. 查询接口统一契约

每个阶段至少需要提供以下四类查询对象：

1. `StageOverview`
2. `StageEntryProjection`
3. `StageMetricProjection`
4. `StageHealthProjection`

推荐最小字段如下：

| 对象 | 最小字段 | 说明 |
| --- | --- | --- |
| `StageOverview` | `stage_id`、`stage_name`、`primary_status`、`summary`、`updated_at` | 阶段概览主对象 |
| `StageEntryProjection` | `entry_route`、`entry_available`、`entry_reason` | 阶段入口是否可用及原因 |
| `StageMetricProjection` | `key`、`label`、`value`、`unit`、`trend` | 供门户和观察页展示的核心指标 |
| `StageHealthProjection` | `health_level`、`message`、`source`、`captured_at` | 健康状态与诊断来源 |

接口形态可以是 `HTTP / RPC / 内部服务调用`，但语义层必须遵循本规范。

## 5. 平台统一骨架字段

无论阶段差异多大，向 `P6` 输出时都必须具备以下统一骨架字段：

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `stage_id` | 是 | 阶段标识，固定为 `P1 ~ P5` |
| `stage_name` | 是 | 阶段显示名称 |
| `primary_status` | 是 | 阶段当前主状态 |
| `summary` | 是 | 门户摘要文案，1 行可读 |
| `entry_route` | 是 | 进入该阶段主操作入口的路由或地址 |
| `entry_available` | 是 | 主入口当前是否可用 |
| `updated_at` | 是 | 本次状态事实最近刷新时间 |
| `freshness` | 是 | 平台统一新鲜度枚举 |
| `health_level` | 是 | 平台统一健康等级 |

统一骨架字段的目标是保证：

- 门户页最少可以稳定画出五个系统节点
- 串行观察页最少可以稳定显示阶段状态与可进入性
- 阶段不可用时，平台也能明确告诉用户“不可用”和“为什么”

## 6. 五阶段差异字段规范

统一骨架之外，各阶段还必须输出能够支撑节点差异展示的最小差异字段。

### 6.1 P1 业务知识库

`P1` 节点应强调“知识资产规模与发布状态”。

| 类别 | 必需字段 | 用途 |
| --- | --- | --- |
| 主显示 | `knowledge_base_name`、`latest_publish_status` | 形成节点主标题与主状态补充文案 |
| 核心指标 | `published_knowledge_count`、`source_document_count` | 展示知识沉淀规模与来源规模 |
| 辅助信息 | `graph_entry_available`、`latest_publish_at` | 展示图谱入口可用性与最近发布时间 |

### 6.2 P2 需求分析系统

`P2` 节点应强调“需求建模进度与规格产出状态”。

| 类别 | 必需字段 | 用途 |
| --- | --- | --- |
| 主显示 | `active_requirement_batch_name`、`spec_status` | 形成当前需求批次与规格状态摘要 |
| 核心指标 | `active_requirement_count`、`modeled_requirement_count` | 展示需求总量与完成建模量 |
| 辅助信息 | `spec_entry_available`、`latest_analysis_at` | 展示规格入口可达性与最近分析时间 |

### 6.3 P3 软件设计系统

`P3` 节点应强调“设计单状态、冻结状态和评审压力”。

| 类别 | 必需字段 | 用途 |
| --- | --- | --- |
| 主显示 | `current_design_order_name`、`freeze_status`、`review_status` | 形成设计单主线文案 |
| 核心指标 | `active_design_order_count`、`review_pending_count` | 展示正在推进的设计单数量与待评审量 |
| 辅助信息 | `design_entry_available`、`latest_review_or_freeze_at` | 展示软设入口与最近冻结/评审时间 |

### 6.4 P4 工具仓库

`P4` 节点应强调“供给覆盖、需求单处理与演进巡检”。

| 类别 | 必需字段 | 用途 |
| --- | --- | --- |
| 主显示 | `current_supply_snapshot_name`、`tool_demand_status`、`evolution_status` | 形成当前供给快照摘要 |
| 核心指标 | `active_supply_snapshot_count`、`tool_demand_open_count` | 展示供给规模与待处理需求单数量 |
| 辅助信息 | `toolhub_entry_available`、`latest_supply_or_inspection_at` | 展示工具仓入口与最近供给/巡检时间 |

### 6.5 P5 软件构建系统

`P5` 节点应强调“交付主单推进、尝试结果与缺口回流”。

| 类别 | 必需字段 | 用途 |
| --- | --- | --- |
| 主显示 | `current_delivery_order_name`、`latest_attempt_status`、`gap_feedback_status` | 形成当前交付主单摘要 |
| 核心指标 | `active_delivery_order_count`、`review_pending_attempt_count` | 展示正在推进的交付数与待批阅尝试数 |
| 辅助信息 | `build_entry_available`、`latest_delivery_or_review_at` | 展示构建入口与最近交付/批阅时间 |

### 6.6 差异字段配置位置

差异字段的“事实来源与计算逻辑”应配置在各阶段正式设计中：

- `P1` 在 `P1` 正式设计或其专题设计中说明知识发布与图谱入口来源
- `P2` 在 `P2` 正式设计中说明需求批次、规格状态和分析时间来源
- `P3` 在 `P3` 正式设计中说明设计单、冻结状态和评审状态来源
- `P4` 在 `P4` 正式设计中说明供给快照、需求单和巡检状态来源
- `P5` 在 `P5` 正式设计或 `P5.1` 节点设计中说明交付主单、尝试状态和缺口状态来源

本规范只定义这些字段在跨阶段输出时必须存在，不替各阶段定义内部实现。

## 7. 节点状态负载映射规范

为保证门户节点可统一实施，每个阶段当前稳定快照必须能映射出一个 `StageNodeStatusPayload`：

```json
{
  "stage_id": "P3",
  "headline_value": "设计单-2026-041",
  "summary_line": "已冻结，待 2 项评审处理",
  "metric_items": [
    { "key": "active_design_order_count", "label": "进行中设计", "value": 3 },
    { "key": "review_pending_count", "label": "待评审", "value": 2 }
  ],
  "entry_badge": {
    "label": "设计入口可用",
    "status": "available"
  },
  "health_badge": {
    "label": "健康",
    "status": "healthy"
  },
  "timestamp_label": "10 分钟前更新",
  "degraded_hint": null
}
```

字段约束如下：

| 字段 | 说明 |
| --- | --- |
| `headline_value` | 节点第一关注点，只显示 1 个主值 |
| `summary_line` | 节点摘要文案，长度控制在 1 行 |
| `metric_items` | 2 到 3 个核心指标项，禁止把长指标列表直接塞进节点 |
| `entry_badge` | 入口状态徽标，最少区分 `available / unavailable` |
| `health_badge` | 健康状态徽标，最少区分 `healthy / warning / critical` |
| `timestamp_label` | 面向用户的时间标签 |
| `degraded_hint` | 降级时提示原因，正常时为空 |

映射规则固定为：

- `headline_value` 优先使用阶段最能代表当前主对象的名称或编号
- `summary_line` 由 `summary` 加必要差异状态拼接
- `metric_items` 必须来自本规范第 6 章定义的最少核心指标
- `entry_badge` 来自 `StageEntryProjection`
- `health_badge` 来自 `StageHealthProjection`
- `timestamp_label` 由 `updated_at` 与平台时间格式化规则生成

## 8. 订阅接口规范

当阶段具备订阅能力时，推荐输出统一事件包络：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `event_type` | 是 | 事件类型 |
| `stage_id` | 是 | 阶段标识 |
| `timestamp` | 是 | 事件发生时间 |
| `payload` | 是 | 事件负载 |
| `source` | 是 | 事件来源 |

首版建议固定以下事件类型：

- `stage_status_changed`
- `metrics_changed`
- `health_changed`
- `entry_changed`
- `alert_created`

订阅接口是增强能力，不是首版上线前提；但一旦提供，事件字段语义必须与查询接口一致。

## 9. 新鲜度与降级规范

平台统一新鲜度建议至少区分：

- `fresh`
- `stale`
- `expired`
- `unavailable`

平台统一降级语义建议至少区分：

- `no_data`
- `source_unavailable`
- `stale_snapshot`
- `partial_metrics_missing`

约束如下：

- 阶段侧负责给出 `updated_at` 和健康采集时间
- `P6.2` 负责把原始时间转换为统一 `freshness`
- 降级时必须同时返回 `degraded_reason` 或 `degraded_hint`
- 不允许用旧快照伪装成“实时正常数据”

## 12. 验收要求

当任一阶段声称“已具备向 `P6` 输出平台状态能力”时，至少应满足以下验收项：

1. 能返回第 4 章定义的四类最小查询对象。
2. 能返回第 5 章定义的统一骨架字段。
3. 能返回本阶段对应的第 6 章差异字段。
4. 能映射出第 7 章定义的 `StageNodeStatusPayload`。
5. 接口不可用或数据过期时，能输出明确的新鲜度与降级信息。
6. 本阶段正式设计已显式引用本规范。
7. `P6.2` 已显式引用本规范，并说明平台消费映射关系。
