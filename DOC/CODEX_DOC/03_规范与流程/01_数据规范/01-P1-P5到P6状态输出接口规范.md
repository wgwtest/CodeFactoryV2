# P1-P5 到 P6 状态输出接口规范

> 归档说明：本文件作为 `P1 ~ P5 -> P6` 平台状态输出的跨阶段共享规范。凡涉及阶段概览、入口状态、核心指标、健康状态、门户节点状态负载和订阅事件包络，均以本文件为统一约束来源。
>
> 维护规则：后续若 `P1 ~ P5` 任一阶段补充对 `P6` 的状态输出能力，必须先对照本规范补齐字段与语义；若需新增共享字段或调整统一枚举，必须先回写本文件，再同步回写对应阶段正式设计与 `P6.2` 消费侧设计。

**日期：** 2026-04-20

**适用范围：**
- `P1` 业务知识库
- `P2` 需求分析系统
- `P3` 软件设计系统
- `P4` 工具仓库
- `P5` 软件构建系统
- `P6.2` 跨阶段只读集成与状态投影

## 1. 规范定位

本规范回答的不是“`P6` 页面该怎么摆字段”，而是“`P1 ~ P5` 若要向 `P6` 输出平台状态，最小必须输出什么、字段语义如何统一、哪些差异字段必须保留”。

本规范固定以下边界：

- 它是 `P1 ~ P5 -> P6` 的共享接口规范来源。
- 它只约束读侧状态输出，不约束阶段内部写入命令和私有领域对象。
- 它定义跨阶段统一最小契约与节点状态负载映射规则。
- 它不替代各阶段自己的正式设计；阶段内部来源、计算逻辑和刷新机制仍由各阶段正式文档负责说明。

## 2. 适用范围

本规范适用于以下输出场景：

- `P6.1` 门户首页展示五阶段系统状态卡
- 串行观察页展示阶段概览、核心指标和健康告警
- `P6.4` 把阶段状态作为展示实验输入
- 后续任意需要消费 `P1 ~ P5` 平台状态的只读视图

本规范当前不覆盖以下内容：

- 阶段内部写接口
- 阶段私有页面临时状态
- 非平台级、仅供单一子页面使用的调试字段
- 直接读取数据库表结构的实现细节

## 3. 职责分工

### 3.1 阶段侧职责

`P1 ~ P5` 各阶段负责：

- 生产正式状态事实
- 解释本阶段差异字段的业务语义
- 标注字段来源、更新时间和健康状态来源
- 提供最小查询接口，条件允许时再补充订阅接口

如果某阶段需要配置“状态从哪里来、何时刷新、失败时如何降级”，该配置应在本阶段正式设计或本阶段专题设计中定义，而不是交给 `P6.1` 页面临时拼装。

### 3.2 平台侧职责

`P6.2` 负责：

- 消费各阶段最小状态输出契约
- 统一映射为 `StageSnapshot`、`StageNodeStatusPayload`、`PortalProjection`
- 统一做新鲜度判断、降级标记和聚合告警

因此，`P6.2` 是消费与映射层，本规范是跨阶段共享约束层。

### 3.3 页面侧职责

`P6.1`、串行观察页和 `P6.4` 只消费 `P6.2` 输出的归一化对象，不应直接绕过平台去拼接 `P1 ~ P5` 的私有字段。

## 4. 查询接口统一契约

每个阶段至少需要提供以下四类查询对象：

1. `StageOverview`
2. `StageEntryProjection`
3. `StageMetricProjection`
4. `StageHealthProjection`
5. `P6DisplayExportContract.v2`

推荐最小字段如下：

| 对象 | 最小字段 | 说明 |
| --- | --- | --- |
| `StageOverview` | `stage_id`、`stage_name`、`primary_status`、`summary`、`updated_at` | 阶段概览主对象 |
| `StageEntryProjection` | `entry_route`、`entry_available`、`entry_reason` | 阶段入口是否可用及原因 |
| `StageMetricProjection` | `key`、`label`、`value`、`unit`、`trend` | 供门户和观察页展示的核心指标 |
| `StageHealthProjection` | `health_level`、`message`、`source`、`captured_at` | 健康状态与诊断来源 |
| `P6DisplayExportContract.v2` | `system_overall_metrics`、`live_counters`、`flow_ports`、`connected_users`、`queue_projection`、`display_binding`、`source_trace` | 供 `P6.1` 五系统节点卡按原型直接展示的展示合同 |

接口形态可以是 `HTTP / RPC / 内部服务调用`，但语义层必须遵循本规范。

### 4.1 展示流语义约束

`P6DisplayExportContract.v2` 中的 `flow_ports` 只描述单个阶段卡片的输入输出端口。`P6.2` 必须把阶段端口配对，派生出 `PortalFlow` 数据流语义。

端口与队列的首屏约束：

- `P1` 的外部知识入库不作为左侧外部输入端口输出给门户画布；门户用 `active_knowledge_intake_rate` 和 `queue_projection` 表达“知识正在入库、排队吸收、完成后顺序前移”。
- `P1` 的业务输出只允许是 `发布态知识 -> P2`。
- `P3` 除主链 `模块工单包 -> P4` 外，可输出 `设计基线 -> P5` 辅助流，用于 P6 语义画布展示软件设计系统向软件构建系统同步可构建设计基线。
- `P6` 只作为观察系统，不得出现在 `P1 ~ P5` 的业务输出端口中。

每个输出端口至少必须能支持以下判断：

| 判断项 | 来源字段 | 说明 |
| --- | --- | --- |
| 输出对象是什么 | `label` | 例如发布态知识、需求规格、模块工单包、工具供给、交付目录 |
| 输出到哪里 | `connected_target` | 必须是主链下游阶段或终端交付目录 |
| 当前速率是多少 | `current_rate` | 用于连线流速、粒子密度或标签展示 |
| 是否终端输出 | `terminal` | 只有 `P5 -> 交付目录` 为 `true` |

`P6.2` 派生的 `PortalFlow` 至少应具备以下语义字段：

| 字段 | 含义 |
| --- | --- |
| `semantic_type` | 数据流类型，例如 `knowledge_supply`、`requirement_to_design`、`tool_match`、`design_baseline_to_build`、`delivery_execution` |
| `payload_label` | 输送对象名称，例如发布态知识、需求规格、模块工单包 |
| `current_rate` | 当前流速，来自端口或实时计数 |
| `health_level` | 流健康状态，来自上下游健康状态和端口可用性 |
| `symbol_hint` | 象形符号建议，例如知识点、规格页、工单包、设计基线、工具、目录 |

这些字段是连线设计和图例设计的语义事实源。前端不得只根据颜色或硬编码文案推断“线里流的是什么”。

## 5. 平台统一骨架字段

无论阶段差异多大，向 `P6` 输出时都必须具备以下统一骨架字段：

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `stage_id` | 是 | 阶段标识，固定为 `P1 ~ P5` |
| `stage_name` | 是 | 阶段显示名称 |
| `primary_status` | 是 | 阶段当前主状态 |
| `summary` | 是 | 门户摘要文案，1 行可读 |
| `entry_route` | 是 | 进入该阶段主操作入口的路由或地址 |
| `entry_available` | 是 | 主入口当前是否可用 |
| `updated_at` | 是 | 本次状态事实最近刷新时间 |
| `freshness` | 是 | 平台统一新鲜度枚举 |
| `health_level` | 是 | 平台统一健康等级 |

统一骨架字段的目标是保证：

- 门户页最少可以稳定画出五个系统节点
- 串行观察页最少可以稳定显示阶段状态与可进入性
- 阶段不可用时，平台也能明确告诉用户“不可用”和“为什么”

## 6. 五阶段差异字段规范

统一骨架之外，各阶段还必须输出能够支撑节点差异展示的最小差异字段。

### 6.1 P1 业务知识库

`P1` 节点应强调“知识资产规模、发布状态、外部知识入库队列和对 `P2` 的知识供给”。

| 类别 | 必需字段 | 用途 |
| --- | --- | --- |
| 总体指标 | `knowledge_repository_count`、`published_knowledge_count`、`domain_directory_count`、`contributor_count` | 展示系统累计知识资产，不展示临时批次 |
| 实时计数 | `active_knowledge_intake_rate`、`active_p2_supply_rate` | 展示正在入库与正在供给 `P2` 的速率 |
| 展示端口 | 门户画布不输出左侧外部入库端口；右侧输出 `发布态知识 -> P2` | 只允许输出到 `P2`，不得追加 `P3/P4/P6` 等牵强端口；外部知识入库由底部队列表达 |
| 接入与队列 | `connected_users`、`queue_projection` | 顶部方形用户积木；底部知识挂载队列，按消化完成后顺序前移 |

### 6.2 P2 需求分析系统

`P2` 节点应强调“需求分析系统的累计承载、知识接入和规格输出”。

| 类别 | 必需字段 | 用途 |
| --- | --- | --- |
| 总体指标 | `supported_software_count`、`requirement_spec_count`、`business_object_count` | 展示系统累计支持软件、规格与业务对象 |
| 实时计数 | `active_knowledge_receive_rate`、`active_spec_output_rate` | 展示从 `P1` 接入知识与向 `P3` 输出规格的速率 |
| 展示端口 | 左侧输入 `发布态知识 <- P1`；右侧输出 `需求规格 -> P3` | 主链固定承接 `P1` 并输出到 `P3` |
| 接入与队列 | `connected_users`、`queue_projection` | 行业用户以内化的顶部用户积木展示，不再作为独立门户节点 |

### 6.3 P3 软件设计系统

`P3` 节点应强调“软件设计系统的累计设计资产和工单包输出”。

| 类别 | 必需字段 | 用途 |
| --- | --- | --- |
| 总体指标 | `supported_software_count`、`design_baseline_count`、`work_order_package_count` | 展示系统累计支持软件、设计基线和工单包 |
| 实时计数 | `active_requirement_input_rate`、`active_workorder_output_rate`、`active_design_baseline_sync_rate` | 展示规格接入、工单输出和设计基线同步速率 |
| 展示端口 | 左侧输入 `需求规格 <- P2`；右侧输出 `模块工单包 -> P4`；辅助输出 `设计基线 -> P5` | 主链固定承接 `P2` 并输出到 `P4`；辅助流同步可构建设计基线到 `P5` |
| 接入与队列 | `connected_users`、`queue_projection` | 顶部展示架构/评审等接入角色，底部展示设计生成队列 |

### 6.4 P4 工具仓库

`P4` 节点应强调“工具仓库的累计工具资产、匹配过程和工具供给输出”。

| 类别 | 必需字段 | 用途 |
| --- | --- | --- |
| 总体指标 | `tool_definition_count`、`domain_catalog_count`、`tool_supply_result_count` | 展示系统累计工具定义、领域目录和供给结果 |
| 实时计数 | `active_matching_rate`、`active_supply_output_rate` | 展示正在匹配与工具供给速率 |
| 展示端口 | 左侧输入 `模块工单包 <- P3`；右侧输出 `工具供给 -> P5` | 主链固定承接 `P3` 并输出到 `P5` |
| 接入与队列 | `connected_users`、`queue_projection` | 顶部展示治理/工具开发接入角色，底部展示工具供给队列 |

### 6.5 P5 软件构建系统

`P5` 节点应强调“软件构建系统的累计构建事实和最终交付目录输出”。

| 类别 | 必需字段 | 用途 |
| --- | --- | --- |
| 总体指标 | `supported_software_count`、`delivery_version_count`、`build_attempt_count` | 展示系统累计支持软件、交付版本和构建尝试 |
| 实时计数 | `active_assembly_count`、`delivery_catalog_output_rate` | 展示正在装配对象与目录输出速率 |
| 展示端口 | 左侧输入 `工具供给 <- P4`；辅助输入 `设计基线 <- P3`；右侧输出 `交付目录 -> 交付目录`，且 `terminal=true` | `P5` 是五阶段主链终点，终端输出只能是交付目录；`P3 -> P5` 不表示 `P5` 输出到 `P6` |
| 接入与队列 | `connected_users`、`queue_projection` | 顶部展示构建/验证接入角色，底部展示构建交付队列 |

### 6.6 差异字段配置位置

差异字段的“事实来源与计算逻辑”应配置在各阶段正式设计中：

- `P1` 在 `P1` 正式设计或其专题设计中说明知识发布与图谱入口来源
- `P2` 在 `P2` 正式设计中说明需求批次、规格状态和分析时间来源
- `P3` 在 `P3` 正式设计中说明设计单、冻结状态和评审状态来源
- `P4` 在 `P4` 正式设计中说明供给快照、需求单和巡检状态来源
- `P5` 在 `P5` 正式设计或 `P5.1` 节点设计中说明交付主单、尝试状态和缺口状态来源

本规范只定义这些字段在跨阶段输出时必须存在，不替各阶段定义内部实现。

字段约束如下：

| 字段 | 说明 |
| --- | --- |
| `headline_value` | 节点第一关注点，表达阶段总体累计状态，不表达临时批次 |
| `summary_line` | 节点实时摘要文案，表达正在输入、正在输出或正在处理 |
| `metric_items` | 兼容旧卡片的 2 个核心指标缩略项 |
| `system_overall_metric_items` | 中段总体累计指标，必须来自正式阶段设计或展示合同，不得使用“进行中批次”替代总体状态 |
| `live_counter_items` | 下段实时输入 / 输出 / 处理计数，用于表达数据正在流动 |
| `flow_port_items` | 接口和连接对象，必须遵守 `P1 -> P2 -> P3 -> P4 -> P5 -> 交付目录` 主链，并额外允许 `P3 -> P5` 设计基线辅助流；`P1` 外部入库不作为左侧端口 |
| `connected_user_items` | 顶部方形用户积木，不允许用独立行业用户节点替代 |
| `queue_projection` | 底部挂载队列，`advance_rule` 固定表达完成后顺序前移 |
| `display_binding` | 原型区域绑定与原型来源，用于追踪展示依据 |
| `source_trace` | 每个总体指标的设计依据、事实对象和计算口径 |
| `entry_badge` | 入口状态徽标，最少区分 `available / unavailable` |
| `health_badge` | 健康状态徽标，最少区分 `healthy / warning / critical` |
| `timestamp_label` | 面向用户的时间标签 |
| `degraded_hint` | 降级时提示原因，正常时为空 |

映射规则固定为：

- `headline_value` 优先使用阶段总体累计状态摘要
- `summary_line` 由实时输入 / 输出 / 处理计数拼接
- `metric_items` 必须来自总体指标的缩略映射
- `entry_badge` 来自 `StageEntryProjection`
- `health_badge` 来自 `StageHealthProjection`
- `timestamp_label` 由 `updated_at` 与平台时间格式化规则生成
- `flow_port_items` 的主链输出端口每阶段只能有一个；`P3` 可额外输出 `设计基线 -> P5` 辅助端口；`P5` 输出端口必须 `terminal=true`
- `P1` 不输出左侧外部知识入库端口，`active_knowledge_intake_rate` 与底部 `queue_projection` 承担入库表达

## 8. 订阅接口规范

当阶段具备订阅能力时，推荐输出统一事件包络：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `event_type` | 是 | 事件类型 |
| `stage_id` | 是 | 阶段标识 |
| `timestamp` | 是 | 事件发生时间 |
| `payload` | 是 | 事件负载 |
| `source` | 是 | 事件来源 |

首版建议固定以下事件类型：

- `stage_status_changed`
- `metrics_changed`
- `health_changed`
- `entry_changed`
- `alert_created`

订阅接口是增强能力，不是首版上线前提；但一旦提供，事件字段语义必须与查询接口一致。

## 9. 新鲜度与降级规范

平台统一新鲜度建议至少区分：

- `fresh`
- `stale`
- `expired`
- `unavailable`

平台统一降级语义建议至少区分：

- `no_data`
- `source_unavailable`
- `stale_snapshot`
- `partial_metrics_missing`

约束如下：

- 阶段侧负责给出 `updated_at` 和健康采集时间
- `P6.2` 负责把原始时间转换为统一 `freshness`
- 降级时必须同时返回 `degraded_reason` 或 `degraded_hint`
- 不允许用旧快照伪装成“实时正常数据”

## 12. 验收要求

当任一阶段声称“已具备向 `P6` 输出平台状态能力”时，至少应满足以下验收项：

1. 能返回第 4 章定义的四类最小查询对象。
2. 能返回第 5 章定义的统一骨架字段。
3. 能返回本阶段对应的第 6 章差异字段。
4. 能映射出第 7 章定义的 `StageNodeStatusPayload`。
5. 接口不可用或数据过期时，能输出明确的新鲜度与降级信息。
6. 本阶段正式设计已显式引用本规范。
7. `P6.2` 已显式引用本规范，并说明平台消费映射关系。
