# P2-需求分析系统设计-260505-轮次多阶段模型调用补充

## 1. 文档定位

本文是《P2-需求分析系统设计.md》的 2026-05-05 补充设计，专门回答“一个 Turn 如何在同一轮内进行多次模型调用、服务端复核和闭环判断”这个问题。

本文不是过程纪要，也不是实现流水账。它的作用是把一个关键结论固定下来：

> **Turn 不是一次模型调用。Turn 是一次会话内的单轮执行闭环；一轮内部可以有多个阶段，每个阶段可以调用一次模型，也可以由服务端规则执行。**

因此，本文要补的不是一个孤立小点，而是一组必须同时成立的设计边界：

- 轮次状态机如何分层；
- 轮次执行如何分阶段；
- 哪些行为必须写死在代码里；
- 哪些内容应该交给组织器策略或提示词；
- 多阶段调用的日志如何审计；
- 哪些章节必须回写到主文档才能形成完整设计。

## 2. 设计结论

### 2.1 这不是只补 `6.6.2.5` 和 `6.6.5`

如果只改 `6.6.2.5 轮次状态机` 和 `6.6.5 轮次执行设计`，只能解释“轮次内部有多阶段”这件事的表层流程，不能把实现边界讲清楚。

因为真正落代码时，还会同时影响：

- `6.6.3 模块运行编排设计`：模块入口如何路由到多阶段轮次；
- `6.6.6.2 内部接口`：阶段输入输出契约如何定义；
- `6.6.7.4 轮次执行子模块`：类职责如何切分；
- `6.6.8.4 模型调用审计`：一轮多次调用如何落日志；
- `6.6.9.2 错误处理`：某一阶段失败时如何保留前序阶段结果。

所以，本次设计的正确理解是：

> **`6.6.2.5` 和 `6.6.5` 是核心，但 `6.6.7.4` 必须重写，`6.6.6.2`、`6.6.8.4` 和 `6.6.9.2` 也要同步收口。**

### 2.2 多阶段能力的本质

一轮 Turn 内部的能力，不是“让模型多说几句”，而是把一次用户输入拆成可审计、可回放、可回退的阶段链。

建议的标准阶段是：

1. `understand`：理解输入、识别承接关系、提炼关键事实；
2. `write`：生成正文补写候选和 patch；
3. `apply`：服务端把 patch 写入临时正文；
4. `review`：基于已写入的临时正文回看是否闭环；
5. `decide`：决定关闭、继续追问还是进入下一节点。

这五个动作里：

- `understand` 和 `write` 可以由模型参与；
- `apply` 必须由服务端完成；
- `review` 可以是模型复核，也可以是规则复核，但必须基于“已应用后的临时正文”；
- `decide` 必须由轮次引擎和组织器策略共同收束，不能直接等于模型原文。

### 2.3 硬编码与提示词的边界

为了避免“组织器看起来很聪明，但实际上什么都靠 prompt 硬拼”的情况，必须把边界划清楚。

**必须硬编码的内容：**

- 轮次状态机；
- 多阶段执行顺序；
- 阶段之间的输入输出契约；
- 临时正文先写后审的顺序；
- 失败阶段的保存与审计规则；
- Provider 日志的分层记录规则；
- 轮次闭环判定权归属。

**适合放入组织器策略 / 提示词的内容：**

- 这一轮具体该问什么；
- 正文 patch 如何措辞；
- 下一轮建议问题如何生成；
- 在同一阶段里偏重事实、约束还是选择项；
- 某类知识领域的表达风格和启发式偏好。

如果把前者也交给 prompt，系统就会变成不可审计的黑盒；如果把后者都写死在代码里，组织器就会失去可替换性。

### 2.4 为什么 `6.6.7.4` 必须重写

`6.6.7.4 轮次执行子模块` 不是一个“补充说明”就能解决的小节，因为它对应的是后端的真实编码边界。

它必须重写，原因有三点：

1. 它决定轮次引擎是否只是“单次调用包装器”，还是“多阶段执行控制器”。
2. 它决定 `TurnContextBuilder`、`TurnStageExecutor`、`TurnAuditService`、`NextInteractionService` 这些类是松散拼贴，还是有明确调用链。
3. 它决定模型调用日志是“每轮一条”，还是“每阶段一条，轮次汇总一组”。

所以，`6.6.7.4` 的目标不是把更多类名堆进去，而是把“轮次执行”的真实分层讲清楚。

## 4. 主文档落地要求

本文的结论只有在写回主文档后才算完成。主文档至少要吸收以下稳定结论：

1. 一轮 Turn 可以包含多次模型调用。
2. 模型调用次数由组织器阶段策略决定，不由前端或一次性 prompt 决定。
3. 临时正文必须先应用，再回看，再决定是否闭环。
4. 任何阶段失败都不能抹掉已发生的调用日志。
5. `TurnExecutionResult` 只保存最终收束结果，阶段候选要通过 `TurnStageResult` 和 `ProviderCallLog` 保留。
6. `6.6.7.4` 要按真实类职责重写，而不是只在原有文字后追加。

## 5. 验收标准

补充设计完成后，应能被下面这些问题直接验证：

- 这一轮为什么会有两次或三次模型调用？
- 第二次调用依赖的输入是什么？
- 第二次调用看到的是原始输入，还是已写入临时正文后的输入？
- 如果 review 阶段失败，前面的 write 阶段会不会丢？
- 调用日志里能不能看出每个阶段分别做了什么？
- 当前 Turn 为什么结束，依据在哪里？

如果这几个问题答不出来，说明 `6.6.2.5` 和 `6.6.5` 还没有真正补完，更说明 `6.6.7.4` 还不能按目标设计落地。
