# P2-需求分析系统设计-260505-Lab临时正文驱动补充

> 本文件是 `P2-需求分析系统设计.md` 的评审前补充详设，目标是修正当前 `P2 XG 需求分析组织器 Lab` 中“临时正文已存在，但展示与数据组织方式仍停留在章节卡片层，无法形成真实文档证据面”的问题。
>
> 本文件当前不直接并入主设计文档，先用于评审。评审通过后，再将稳定结论归并到《P2-需求分析系统设计.md》的第五章和第六章相关章节。

**日期：** 2026-05-05

## 1. 问题定义

### 1.1 当前问题

当前 Lab 已经具备以下中间产物：

- `document_patch`
- `questions`
- `facts`
- `patches`
- `spec_tree`
- `next_interaction`
- `turn_audit`
- `working_document`

但当前 `working_document` 的实现与展示仍然存在根本偏差：

1. 前端主视图仍按“章节卡片列表”展示，而不是按“整份需求规格说明正文”展示。
2. 当前设计默认“一轮主要更新一个章节”，这与真实需求规格补充过程不一致。一轮输入可能命中多个章节，甚至跨章节补充。
3. 章节被错误地作为前端主组织形态。实际上章节只是模板锚点，不应取代正文文档本体。
4. 当前闭环判断虽然引入了 `working_document`，但其证据面仍然偏向“章节是否已有内容”，没有形成真实的正文工作面。

因此当前系统会给用户造成错误直觉：

```text
系统像是在逐章节填卡片
而不是在逐轮把内容写进一份真实需求规格说明
```

### 1.2 本补充的目标

本补充的目标不是让 Lab 写入正式需求规格说明文档，而是让 Lab 增加一个**会话内临时正文文档工作面**，同时修正其数据模型和界面形态，使它满足以下目标：

- 让用户看到一份连续的、接近真实 A4 纸文档的需求规格说明草稿；
- 让同一轮命中的多个正文位置都能被明确标记；
- 让系统围绕正文工作面进行回看，而不是围绕章节卡片进行机械推进；
- 让完成度树退回为辅助视图，正文重新成为第一证据面。

## 2. 核心设计结论

### 2.1 证据层级重排

在新的 Lab 设计中，证据层级应调整为：

```text
第一证据：临时正文文档 working_document
第二证据：正文片段回看结果 target_review / block_review
第三证据：全局回看结果 global_review
第四证据：需求规格完成度树 spec_tree
第五证据：沟通路径与 Turn 审计
```

完成度树只负责表达：

- 当前模板节点结构；
- 当前焦点节点；
- 哪些节点已关闭；
- 哪些节点仍待确认；
- 正文大体覆盖到了哪些节点。

真正决定“这一轮是否足够”的依据，必须是：

```text
临时正文文档中，与当前目标节点相关的正文是否已经形成可接受表达
```

### 2.2 临时正文的定位

临时正文不是：

- 正式需求规格说明文档；
- 专家工作台右侧的标准正文；
- 可冻结文档；
- P3 可直接消费对象；
- “章节卡片集合”。

临时正文是：

- Lab 会话内部的工作草稿；
- 接近真实需求规格说明正文的连续文档视图；
- 组织器一轮或多轮收束过程中的主证据面；
- 多轮次补充痕迹的承载面；
- 章节锚点、回看和闭环判断的正文依据。

### 2.3 基本原则

1. Lab 允许写临时正文，但不写正式正文。
2. 临时正文的前端主视图必须是一份连续的 A4 文档，而不是章节卡片。
3. 章节和条款只作为内部锚点，不作为前端主展示单位。
4. 一轮中允许命中多个正文位置，每个位置都必须有独立的修订痕迹。
5. 同一轮命中的多个位置共用同一个 `turn_id` 和同一种修订颜色。
6. 临时正文只显示当前生效正文，不保留被替换掉的旧文字。
7. 一轮内允许多次调用模型或规则，但每次调用都必须围绕临时正文推进。
8. 固定执行顺序必须是“先写候选，再应用到正文，再回看正文，再决定是否闭环”。
9. 关闭节点必须基于正文充分性判断，不能因为 patch 存在就关闭。

## 3. 前端详设补充

### 3.1 会话摘要区重构目标

`会话摘要 / 过程产物` 区块仍保留三视图结构：

```text
会话摘要 / 过程产物
  -> Tab 1：临时正文（默认主视图）
  -> Tab 2：需求规格完成度树
  -> Tab 3：沟通路径
```

但 `临时正文` 视图的含义发生变化：

- 不是“章节块列表”；
- 不是“按 section 一卡一块浏览”；
- 而是一份连续排版的需求规格说明草稿。

### 3.2 页面结构调整

`SessionTab` 页面结构从：

```text
CLI 式问答区
  + 会话摘要 / 过程产物
    + 临时正文（章节卡片）
    + 完成度树
    + 沟通路径
```

调整为：

```text
CLI 式问答区
  + 会话摘要 / 过程产物
    + 临时正文（A4 连续文档）
    + 完成度树
    + 沟通路径
```

### 3.3 临时正文主工作面结构

临时正文主工作面建议结构：

```text
working_document_view
  -> 文档标题
  -> A4 页面序列
    -> 文档标题块
    -> 章节标题块
    -> 正文段落块
    -> 列表块
    -> 空占位块
  -> 修订痕迹层
    -> 页边修订标记
    -> 正文轻微高亮
```

#### 3.3.1 文档视觉目标

临时正文应在视觉上尽量接近 Word 中正在编辑的需求规格说明正文：

- 使用白色纸页背景；
- 按 A4 纵向文档排版；
- 页面之间保留明显页距；
- 文本主体连续排版；
- 章节标题、条款标题、正文段落和列表项按文档顺序出现。

前端不再显示“章节卡片头 + 章节标签 + patch 标签”这类卡片式视觉结构。

关键约束：

1. 主工作面是**整份文档**。
2. 文档内部当然有章节、条款和段落，但这些是正文结构，不是界面卡片。
3. 一轮补写可以同时影响多个正文位置，允许跨章节命中。
4. 跨章节命中不意味着页边标记必须拆成多个；页边标记按本轮修订事件聚合，正文片段负责局部高亮和追溯。

#### 3.3.2 A4 页面规则

建议的前端页面规则：

| 区域 | 作用 |
| --- | --- |
| 左右页边距 | 提供真实文档阅读感，不用于堆叠业务控件 |
| 正文排版区 | 展示标题、章节、正文段落和列表 |
| 页边修订标记区 | 显示本轮或历史轮次的修订痕迹 |
| 页面阴影与页距 | 让用户直观看到“这是一份文档”，不是卡片容器 |

正文区和修订标记区必须是同一份文档的两层，不得分裂成“左边正文，右边章节卡片”。

### 3.4 文档块与正文片段

前端渲染层不再以 `section` 为主，而以 `document_block` 为主。

建议的可渲染块类型：

| 块类型 | 说明 |
| --- | --- |
| `document_title` | 文档总标题，例如 `81433号需求规格说明（Lab 临时正文）` |
| `section_heading` | 一级或二级章节标题 |
| `clause_heading` | 条款标题 |
| `paragraph` | 正文段落 |
| `bullet_list` | 项目符号或列表 |
| `placeholder` | 当前尚未写出正文但保留结构位置的占位块 |

要点：

- 文档块按模板顺序和正文顺序连续排布；
- 一个块可以关联一个或多个模板锚点；
- 一轮可以在文档流中生成多个正文块或更新多个已有块；
- 用户看到的是文档流，不是按章节拆出来的面板集合。

### 3.5 修订痕迹展示规则

#### 3.5.1 总体规则

修订痕迹采用：

- **页边修订标记**
- **正文轻微高亮**

而不是：

- 删除线旧文字；
- 红绿 diff 面板；
- 悬浮章节卡片。

#### 3.5.2 同一轮多位置命中规则

当同一轮输入命中多个位置时：

- 页边修订标记按**修订事件**聚合展示，一轮用户输入默认形成一个修订事件；
- 页边默认只显示一个修订事件标记，不按章节或片段拆成多个主标记；
- 标记展示该轮输入摘要、命中位置数量、命中的规格节点和补充原因；
- 标记位置按该轮全部命中片段在正文中的首次出现位置确定，尽量贴近第一次被修订的位置；
- 点击标记时，同时高亮该轮命中的全部正文片段；
- 同一轮命中的全部片段共用同一个 `turn_id` 和同一种修订色。

#### 3.5.3 正文轻微高亮规则

正文高亮应满足：

- 只对本轮或某历史轮次最终生效的正文片段做轻微背景高亮；
- 不显示旧文字；
- 不做粗重底色；
- 高亮要足够淡，保证文档仍以正文阅读为主，而不是以彩色标注为主。

#### 3.5.4 页边修订标记规则

页边修订标记建议包含：

- `turn-0009` 这类轮次编号；
- 与本轮第一次命中的正文片段垂直对齐；
- 鼠标悬停时显示简要说明；
- 点击后展示该轮修订事件的审计卡片。

### 3.6 页边标记交互

用户点击页边修订标记后，页面应弹出一个小审计卡片。建议内容如下：

| 字段 | 含义 |
| --- | --- |
| `turn_id` | 该修订事件来自哪一轮 |
| 用户输入摘要 | 本轮用户输入的简要概括 |
| 补充原因 | 为什么把这段文字写到这里 |
| 命中片段数量 | 本轮影响了几个正文位置 |
| 命中的规格节点 | 这一轮关联了哪些 `spec_tree` 节点 |
| 跳转入口 | 跳到 `当前 Turn 审计` |

该交互的目标是：

- 保持正文视图干净；
- 审计链又能随时被追溯；
- 不把过多审计字段直接塞回正文。

### 3.7 完成度树的角色变化

完成度树保留，但职责变为：

- 显示模板节点结构；
- 显示当前焦点节点；
- 显示节点状态；
- 辅助对照正文覆盖范围；
- 辅助定位哪些节点仍待确认。

完成度树不再直接承载“本轮正文够不够”的主判断。

### 3.8 当前 Turn 视图补充

`Current Turn` 审计视图需要从“应用章节”概念升级到“文档位置与修订片段”概念。

新增或调整后的审计项建议如下：

| 顺序 | 字段 | 含义 |
| --- | --- | --- |
| 1 | 上轮系统留题 | 上轮是否留题、留了什么 |
| 2 | 本轮用户输入 | 用户本轮原始输入 |
| 3 | 输入承接判断 | 用户输入与上轮留题的关系 |
| 4 | 写入候选 patch | 本轮候选正文补充 |
| 5 | 临时正文应用结果 | 具体写入了哪些文档块、哪些正文片段 |
| 6 | 片段回看结果 | 当前目标片段或目标块是否已可接受 |
| 7 | 全局回看结果 | 对整份文档还缺什么 |
| 8 | 本轮闭环判断 | 为什么关闭 / 为什么继续追问 |
| 9 | 下一轮交互设计 | 下一轮问什么、为什么问 |
| 10 | 决策依据 | 正文工作面、回看结果、规格树状态和规则依据 |

“临时正文应用结果”不再只写“应用章节：REQ-2.1”，而应至少展示：

- `applied_block_ids`
- `applied_fragment_ids`
- `turn_id`
- 本轮命中的正文片段摘要

### 3.9 调用日志视图补充

调用日志中的 `Provider Request` 和 `Provider Response` 需要能够解释“本轮模型到底看到了哪份文档、哪几个正文块、哪几个片段”。

因此日志 schema 需要新增或调整：

| 字段路径 | 含义 |
| --- | --- |
| `provider_request.prompt_bundle.working_document_json` | 当前会话临时正文全文快照 |
| `provider_request.prompt_bundle.current_block_draft` | 当前焦点文档块或片段草稿 |
| `provider_request.prompt_bundle.review_goal` | 本轮回看的目标 |
| `provider_request.prompt_bundle.target_fragment_ids` | 本轮重点审查的片段 id |
| `provider_response.review_json` | 片段级或块级回看结果 |

## 4. 后端详设补充

### 4.1 会话状态新增对象

`RequirementAnalysisSession.payload` 需要继续保留 `working_document`，但其结构不应再以 `sections[]` 作为前端主语义。

建议改为：

```json
{
  "working_document": {
    "document_id": "lab-working-document",
    "title": "81433号需求规格说明（Lab 临时正文）",
    "template_id": "81433号",
    "topic": "态势分析系统需求规格探索",
    "blocks": [],
    "revision_fragments": []
  }
}
```

### 4.2 文档块与修订片段模型

- `blocks[]` 表示当前生效正文；
- `revision_fragments[]` 表示这些正文最近由哪些轮次补入；
- `anchor_path` 表示它在模板条款树中的定位锚点；
- `revision_fragments[]` 用于内部追溯与正文高亮定位；
- 页边修订标记由投影视图按 `turn_id` 聚合为 `revision_event` 后生成，不直接以单个 `revision_fragment` 作为用户可见主对象。

#### 4.2.1 `document_block`

`document_block` 用于表达整份临时正文中的可渲染文档单元。

需求规格说明仍然有章节和条款，但在后端模型中，它们不应再直接等同于前端工作面的“显示卡片”。

更准确的关系是：

```text
模板条款树
  -> 提供 anchor_path
    -> anchor_path 绑定到 working_document.blocks
      -> blocks 组成连续正文
        -> revision_fragments 记录轮次补写痕迹
          -> revision_event 聚合为页边标记
```

因此：

- 章节是结构锚点；
- 正文块是显示与审查单元；
- 修订事件是页边标记单元；
- 修订片段是来源追溯与局部高亮单元。

#### 4.2.2 `revision_event`

`revision_event` 是前端页边标记的聚合对象。它不替代 `revision_fragment`，只负责把同一轮用户输入造成的多个正文片段命中合并成一个可点击、可审计的页边标记。

建议结构：

```json
{
  "revision_event_id": "rev-turn-0009",
  "turn_id": "turn-0009",
  "fragment_ids": ["frag-0012", "frag-0013"],
  "first_anchor_path": "1.1/编写目的",
  "hit_spec_nodes": ["SPEC-GEN-1.1", "SPEC-GEN-1.2"],
  "user_input_summary": "用户确认目标是运算软件需求规格说明",
  "supplement_reason": "补入编写目的和适用范围",
  "display_color_token": "rev-09"
}
```

### 4.3 Patch 模型需要从“章节补丁”改为“正文片段操作”

`document_patch` 的目标不再是“给某章节塞一段内容”，而是“对正文指定位置执行补写或替换操作”。

建议操作类型至少包括：

- `insert_before_block`
- `insert_after_block`
- `append_to_block`
- `replace_range`
- `create_block_after_anchor`

示例：

```json
[
  {
    "patch_id": "patch-0003",
    "anchor_path": "2.1/软件定位",
    "target_block_id": "blk-0012",
    "operation": "append_to_block",
    "content": "首版聚焦运算能力与约束表达，不覆盖协同调度闭环。",
    "reason": "补入阶段边界"
  }
]
```

### 4.4 一轮执行链必须围绕正文展开

补充后的执行链应调整为：

```text
用户输入
  -> 输入解释
    -> 候选正文补写
      -> 应用到 working_document
        -> 生成 revision_fragments
          -> 目标范围回看
            -> 全局回看
              -> 更新完成度树
                -> 形成本轮闭环判断
                  -> 生成下一轮交互
```

这里的关键约束是：

1. `turn` 的起点是用户输入。
2. 组织器不能跳过“正文应用后回看”。
3. 完成度树更新发生在回看之后，而不是回看之前。

### 4.5 回看对象从“章节”改为“目标范围”

由于一轮补写可能跨多个位置，回看不应再硬编码为 `section_review` 这类章节级对象。

建议统一改为：

- `target_review`：本轮命中范围是否已形成可接受表达；
- `global_review`：整份临时正文从当前视角看还缺什么。

`target_review` 的判断对象可以是：

- 一个条款下的一个正文块；
- 同一条款下的多个正文块；
- 跨条款的一组命中片段。

建议结构：

```json
{
  "block_id": "blk-0031",
  "block_type": "paragraph",
  "order": 310,
  "anchor_spec_node_ids": ["SPEC-REQ-3.2"],
  "anchor_section_titles": ["3 功能需求 / 核心业务流程"],
  "text": "分析师登录系统后，选择分析工具并输入相关数据，系统进行处理并展示分析结果。",
  "last_turn_id": "turn-0009",
  "active_revision_id": "frag-0012"
}
```

### 4.6 修订片段模型 `revision_fragment`

说明：本节与 `4.2.1 document_block`、`4.2.2 revision_event` 同属文档块与修订模型。为便于说明与后续审查，这里单独展开修订片段对象。

`revision_fragment` 用于表达“哪一轮把哪段当前生效文字写到了文档的哪个位置”。

建议结构：

```json
{
  "fragment_id": "frag-0012",
  "turn_id": "turn-0009",
  "block_id": "blk-0031",
  "anchor_spec_node_ids": ["SPEC-REQ-3.2"],
  "source_patch_ids": ["P-007"],
  "display_color_token": "rev-09",
  "summary": "补充核心业务流程主线。",
  "review_status": "waiting_review"
}
```

要点：

- 一轮可以产生多个 `revision_fragment`；
- 多个 fragment 可以落在不同 block；
- 同一轮多个 fragment 共用 `turn_id` 和颜色 token；
- 文档主视图只展示当前生效的 `text`，旧文字不保留在正文层。

### 4.7 一轮执行结果新增对象

`RequirementAnalysisTurn` 需要从“章节应用结果”升级为“文档块与修订片段应用结果”。

建议新增或调整：

```json
{
  "spec_execution": {
    "document_patch": [],
    "working_document_update": {
      "applied_block_ids": ["blk-0031", "blk-0048"],
      "applied_fragment_ids": ["frag-0012", "frag-0013"],
      "before": "...",
      "after": "..."
    }
  },
  "post_update_review": {
    "target_review": {
      "status": "insufficient",
      "reason": "核心业务流程主线已形成，但异常与补偿处理仍未落到正文。",
      "missing_aspects": ["失败处理", "人工复核"]
    },
    "global_review": {
      "status": "continue_same_target",
      "summary": "当前仍需围绕核心业务流程补齐异常与补偿处理。",
      "remaining_gaps": ["失败处理", "人工复核"]
    }
  }
}
```

### 4.8 一轮执行链风险说明

当前执行链偏向：

```text
输入 -> patch -> 投影到树 -> 回看 -> 下一轮
```

目标执行链应调整为：

```text
输入
  -> 生成候选 patch
    -> 投影到目标锚点
      -> 应用到临时正文文档流
        -> 形成正文块和修订片段
          -> 片段级 / 块级回看
            -> 全局回看
              -> 更新完成度树
                -> 形成闭环判断
                  -> 生成下一轮交互
```

也就是：

1. `patch` 不是最终判断对象；
2. 文档流才是回看对象；
3. 完成度树应在回看之后更新，不应在回看之前就机械关闭。

### 4.9 完成度树更新规则调整

当前风险在于：

```text
只要 patch 命中当前节点，就容易关闭节点
```

目标规则应改为：

```text
只有当正文回看结果确认“当前目标已经形成可接受表达”
才允许关闭当前节点
否则
当前节点保持 partial 或 waiting_review
```

建议保留或补充以下节点状态：

- `open`
- `partial`
- `waiting_review`
- `closed`

其中：

- `partial` 表示已有正文草稿，但不够闭环；
- `waiting_review` 表示新片段已写入，但当前轮尚未完成正文回看。

### 4.10 临时正文应用服务

建议保留并升级：

```text
WorkingDocumentService
```

职责从“维护章节内容”升级为“维护文档块与修订片段”：

1. 将 `document_patch` 应用到 `working_document.blocks`；
2. 生成或更新当前生效的正文块；
3. 记录来源 patch、来源 turn 和来源锚点；
4. 生成 `revision_fragment`；
5. 提供块快照或片段快照供 review 阶段使用；
6. 输出应用前后差异供 Turn 审计展示。

建议接口：

| 方法 | 输入 | 输出 |
| --- | --- | --- |
| `apply_patches` | `working_document`、`document_patch[]`、投影锚点 | `working_document_update` |
| `get_block_snapshot` | `working_document`、`block_id` | `block_draft` |
| `get_fragment_snapshot` | `working_document`、`fragment_id` | `fragment_draft` |
| `build_review_context` | `working_document`、当前目标锚点 | review 阶段上下文 |

### 4.11 回看服务

建议保留并升级：

```text
WorkingDocumentReviewService
```

职责从“检查章节是否非空”升级为“检查与当前目标相关的正文块或正文片段是否已经形成可接受表达”：

1. 检查当前目标关联的正文块是否已经具备足够表达；
2. 检查本轮新增片段是否真正覆盖了当前目标问题；
3. 判断是否继续追问当前目标；
4. 给出全局回看摘要。

输出建议：

```json
{
  "target_review": {
    "status": "sufficient | insufficient",
    "reason": "...",
    "missing_aspects": ["边界", "阶段范围"]
  },
  "global_review": {
    "status": "continue_same_target | move_next_node | whole_document_review",
    "summary": "...",
    "remaining_gaps": []
  }
}
```

### 4.12 临时正文投影视图服务

建议新增：

```text
WorkingDocumentProjectionService
```

职责：

1. 将 `working_document` 投影为前端可直接渲染的 A4 文档视图；
2. 按轮次聚合修订片段，生成 `revision_event` 与页边修订标记；
3. 生成页边审计卡片所需的摘要字段；
4. 供 `SessionTab` 与 `Current Turn` 共同复用。

## 5. 请求规划与提示词补充

### 5.1 当前问题

当前多阶段策略虽然宣称：

```text
write -> review
```

但 `review` 阶段并没有真正围绕“文档流中的正文片段”做回看，它更像一个服务端补充摘要阶段，不足以支撑真正的正文闭环判断。

### 5.2 目标多阶段策略

建议将启发式组织器的 Turn 策略明确为：

```text
interpret
  -> write
    -> apply
      -> review
        -> decide
```

其中：

- `interpret`：理解用户输入与当前目标的关系；
- `write`：生成候选 patch、事实、开放问题；
- `apply`：服务端将 patch 应用到 `working_document` 文档流；
- `review`：基于应用后的正文块和修订片段做充分性回看；
- `decide`：服务端根据 review 结果形成闭环决策和下一轮交互。

说明：

- `apply` 与 `decide` 可以是服务端规则阶段，不一定调用模型；
- `review` 可以先由服务端规则实现，后续再接模型；
- 若后续接模型，模型看到的对象必须是“文档流 + 当前目标 + 本轮片段”，而不是“章节卡片”。

### 5.3 Prompt Bundle 必须新增的上下文

如果 `review` 阶段调用模型，必须在 Prompt Bundle 中新增：

| 字段 | 含义 |
| --- | --- |
| `working_document_json` | 当前会话临时正文全文快照 |
| `current_target_block_ids` | 当前目标相关的正文块 id |
| `current_target_fragment_ids` | 当前轮新增片段 id |
| `current_target_text` | 当前目标块或片段的正文内容 |
| `current_target_question` | 当前目标仍要解决的问题 |
| `recent_patch_list` | 本轮候选 patch 列表 |
| `remaining_open_questions` | 会话仍待确认的问题 |
| `review_goal` | 本轮 review 的审查目标 |

### 5.4 Write 阶段输出约束

`write` 阶段输出不再直接被当成最终决策，而只是候选材料。

建议结构：

```json
{
  "organizer_interpretation": {},
  "candidate_patch": [],
  "candidate_facts": [],
  "candidate_open_questions": [],
  "candidate_next_interaction": {}
}
```

### 5.5 Review 阶段输出约束

`review` 阶段应聚焦正文充分性，而不是重新编整轮输出。

建议结构：

```json
{
  "target_review": {
    "status": "sufficient | insufficient",
    "reason": "...",
    "missing_aspects": []
  },
  "rewrite_advice": [
    {
      "block_id": "blk-0031",
      "operation": "replace_or_append",
      "content": "..."
    }
  ],
  "recommended_next_focus": {
    "mode": "continue_same_target | move_next_target",
    "reason": "..."
  }
}
```

### 5.6 Decide 阶段规则

`decide` 阶段必须使用如下规则：

1. 若 `target_review.status == insufficient`，则：
   - 不关闭当前节点；
   - 当前节点保持 `partial` 或 `waiting_review`；
   - 下一轮交互继续围绕同一目标缺口追问。

2. 若 `target_review.status == sufficient`，则：
   - 允许关闭当前节点；
   - 再根据 `global_review` 决定进入下一节点还是整体复核。
