## 1. 本次同步判断

当前 `P2 XG 需求分析组织器 Lab` 的真实系统已经明显超过早期“简单组织器配置 + 问答验证”的形态。它现在更接近一个完整的组织器运行诊断台：

1. 配置页已经包含组织器插件、Provider、模板实例、模板基础版本、启动参数和 Markdown 模板编辑能力。
2. 会话页已经包含 CLI 式问答，以及结构化状态、临时正文、需求规格完成度树、沟通路径四类过程产物。
3. 当前 Turn 页已经承担单轮业务审计，而不是只展示用户输入和模型输出。
4. 调用日志页已经按 Provider / Runner 调用表达模型调用证据，并与当前 Turn 审计分工。

因此，后续设计同步不能只按 `需求输入事项` 的业务化设想覆盖 Lab，也不能把 Lab 降格描述为简单配置页。主设计文档需要在“面向用户工作流”和“Lab 真实运行诊断台”之间建立明确分层。

## 2. 当前代码事实

### 2.1 前端入口事实

当前真实前端入口为：

`apps/web/src/pages/RequirementAnalysisLabPage.tsx`

该页面显式定义四个一级 Tab：

| Tab | 当前职责 |
| --- | --- |
| 组织器配置 | 加载和选择组织器、Provider、模板实例，维护模板内容，启动验证会话 |
| 会话管理 | 展示会话消息、快捷选项、输入框和会话过程产物 |
| 当前 Turn | 展示当前轮次审计，校验 `turn_audit_schema` 必需字段 |
| 调用日志 | 展示 Provider / Runner 调用列表和调用详情 |

这说明当前 Lab 的一级结构已经稳定，不宜在原型和设计中重新改成事项列表、业务首页或单页表单。

### 2.2 启动与配置事实

`useRequirementAnalysisLabBootstrap.ts` 启动时并行加载：

| 加载对象 | 前端函数 | API |
| --- | --- | --- |
| Lab 配置 | `getRequirementAnalysisLabConfig()` | `GET /requirement-analysis/lab-config` |
| 组织器 | `getRequirementAnalysisOrchestrators()` | `GET /requirement-analysis/orchestrators` |
| Provider | `getRequirementAnalysisProviders()` | `GET /requirement-analysis/providers` |
| 模板实例 | `getRequirementAnalysisTemplates()` | `GET /requirement-analysis/templates` |
| 基础模板 | `getRequirementAnalysisTemplateBases()` | `GET /requirement-analysis/template-bases` |

配置页还支持：

| 操作 | 前端函数 | API |
| --- | --- | --- |
| 重新扫描组织器 | `reloadRequirementAnalysisOrchestrators()` | `POST /requirement-analysis/orchestrators/reload` |
| 新建模板实例 | `createRequirementAnalysisTemplate()` | `POST /requirement-analysis/templates` |
| 保存模板实例 | `saveRequirementAnalysisTemplate()` | `PUT /requirement-analysis/templates/{template_id}` |
| 删除模板实例 | `deleteRequirementAnalysisTemplate()` | `DELETE /requirement-analysis/templates/{template_id}` |
| 保存为基础模板 | `saveRequirementAnalysisTemplateAsBase()` | `POST /requirement-analysis/templates/{template_id}/save-as-base` |

这部分能力已经是可操作的配置管理，不应再被文档描述为“仅选择一个组织器并启动”。

### 2.3 会话与 Turn 事实

当前会话生命周期接口为：

| 操作 | 前端函数 | API |
| --- | --- | --- |
| 创建会话 | `createRequirementAnalysisSession()` | `POST /requirement-analysis/sessions` |
| 查询会话 | `getRequirementAnalysisSession()` | `GET /requirement-analysis/sessions/{session_id}` |
| 创建 Turn | `createRequirementAnalysisTurn()` | `POST /requirement-analysis/sessions/{session_id}/turns` |

会话页的右侧 `SessionSummary` 已经形成四个内部视图：

1. `DecisionStateDocumentView`：结构化状态 A4 视图。
2. `WorkingDocumentView`：Lab 临时正文 A4 视图和修订标注。
3. `SpecCompletionTree`：需求规格完成度树。
4. `TurnPathView`：沟通路径。

这说明当前 Lab 的主状态不是临时正文，也不是完成度树，而是结构化状态与多个投影视图并存。

### 2.4 当前 Turn 与调用日志分工事实

当前 `TurnTab` 会通过 `validateRequirementAnalysisTurnProtocol` 校验 `turn_audit_schema.required_fields`。这说明 Turn 审计已经是协议化对象，不是随意渲染的日志。

调用日志页 `LogTab` 和 `ProviderLogDetail` 则围绕 `provider_log_schema` 展示：

1. 概览。
2. 当前 turn 上下文。
3. 输出格式要求。
4. 请求。
5. 原始输出。
6. 输出后处理。

因此，文档需要保持以下边界：

```text
当前 Turn 审计解释“系统为什么这样处理本轮”。
Provider 调用日志解释“某个模型 / Runner 调用输入了什么、输出了什么、如何归一化和采纳”。
```

两者不能合并为一个通用运行日志。

## 3. 可能需要同步的设计文档口径

### 3.1 Lab 定位需要补充

旧文档中如果仍把 Lab 描述为“组织器验证页”或“简单配置页”，需要升级为：

```text
Lab 是 P2 需求分析组织器的运行诊断台和高级验证入口，负责暴露组织器插件、Provider、模板实例、会话过程产物、Turn 审计和模型调用日志。
```

它不是普通用户的唯一业务入口，也不是正式需求规格说明编辑器。

### 3.2 配置页能力需要补齐

主设计文档后续应补齐配置页至少包含：

1. 组织器插件注册表和可观测等级。
2. Provider 可用性和选择。
3. 启动课题、启动模板实例和写入策略。
4. 模板实例列表、基础模板来源、模板元数据和 Markdown 内容编辑。
5. 模板实例保存、删除和保存为基础模板。
6. 组织器重新扫描。

### 3.3 会话过程产物需要按真实 Tabs 写清

后续文档应把会话页明确拆为：

| 视图 | 设计职责 |
| --- | --- |
| CLI 式问答区 | 承载用户输入、助手回应和快捷选项 |
| 结构化状态 | 探索阶段权威业务状态的用户可读投影 |
| 临时正文 | 结构化状态和文档 patch 的 A4 临时正文投影 |
| 完成度树 | 需求规格模板节点的完成状态投影 |
| 沟通路径 | turn 与影响节点、回答摘要和下一轮路径的追踪 |

### 3.4 当前 Turn 审计需要按阶段链路描述

旧文档如果只说“展示当前 Turn”，需要升级为：

1. 组织器插件。
2. 上轮系统留题。
3. 本轮用户输入。
4. 输入承接判断。
5. 结构化状态增量。
6. 阶段执行审计。
7. 规格补充执行。
8. 临时正文应用结果。
9. 目标范围回看。
10. 全局回看。
11. 下一轮交互设计。

### 3.5 调用日志需要保持 Provider 边界

后续文档应避免把 Provider 调用日志泛化为所有后台调用日志。当前真实设计更精确：

```text
ProviderLog 只记录模型 Provider 或本地 Runner 调用。
服务端内部规则、投影、状态应用和回看应进入 Turn 审计，不进入 ProviderLog。
```

## 4. 与“面向用户工作流升级补充”的关系

`P2-需求分析系统设计-260512-1904-面向用户工作流升级补充.md` 提出了“需求分析事项”作为业务入口的方向。该方向仍有价值，但不能直接替代当前 Lab 设计。

建议重新界定两者关系：

| 层级 | 推荐定位 |
| --- | --- |
| 面向用户业务入口 | 未来可以是需求分析事项、专家需求规格编写工作台或统一 P2 首页 |
| Lab | 组织器运行诊断台，高级配置、验证、审计和模型调用追溯入口 |
| 正式文档工作区 | 需求规格说明正文编辑、缺口检查、冻结和输出 |

因此，后续若继续推进“需求分析事项”，应新增一个业务入口或把它挂接到现有正式工作台，而不是把当前 Lab 的真实复杂配置页改造成事项首页。

## 5. 建议的主文档同步策略

建议分三步同步，不在本轮直接改主文档。

### 5.1 第一步：先确认 v6 原型

以 `2026-05-12-213000-CodeFactoryV2-P2-Brainstorming-Lab真实系统对齐原型-v6` 作为当前 Lab 原型事实源，确认：

1. 是否认可继续保留真实四 Tab。
2. 是否认可配置页复杂度。
3. 是否认可 Turn 审计和 Provider 调用日志分工。

### 5.2 第二步：局部修订主文档 Lab 章节

用户确认后，再把主文档中 Lab 相关章节局部升级，优先修：

1. Lab 定位。
2. Lab 前端结构。
3. 配置页对象。
4. 会话过程产物。
5. Turn 审计协议。
6. Provider 调用日志边界。

不建议同时重写 P2 全部目标态，以免把运行事实和未来事项工作流混在一起。

### 5.3 第三步：另起业务入口设计

如果继续推进“需求分析事项”，建议作为独立补充稿或新版本原型处理，明确回答：

1. 事项是否作为 P2 首页对象。
2. 事项和 `RequirementAnalysisSession`、`RequirementAuthoringDocument`、`RequirementSpec` 的关系。
3. 普通用户入口如何跳转到 Lab 高级诊断。
4. 哪些配置默认隐藏，哪些保留给高级用户。

## 6. 本轮不直接回写主文档的理由

1. 真实系统与 v5 事项化原型存在方向差异，需要先确认 v6。
2. 主文档很可能已有部分 Lab 最新内容，直接大范围回写容易重复或覆盖已有设计。
3. 当前问题主要是“原型和文档是否与代码同步”，应先建立同步清单，再决定回写粒度。
4. 业务入口升级和 Lab 运行诊断台不是同一层级，不应在同一轮改动里混合定稿。

## 7. 后续验收口径

后续同步主文档时，应以以下检查项验收：

1. 主文档是否明确 Lab 是高级诊断台，不是普通业务首页。
2. 主文档是否列出真实配置页对象，而不是只写组织器选择。
3. 主文档是否说明结构化状态、临时正文、完成度树和沟通路径的关系。
4. 主文档是否说明当前 Turn 审计字段和阶段链路。
5. 主文档是否保持 Provider 调用日志与 Turn 审计的边界。
6. 主文档是否避免用“需求分析事项”替换当前 Lab 的真实运行对象。
