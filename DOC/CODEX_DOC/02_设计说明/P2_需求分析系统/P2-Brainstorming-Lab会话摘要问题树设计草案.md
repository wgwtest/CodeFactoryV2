# P2 Brainstorming Lab 会话摘要问题树设计草案

**日期：** 2026-05-01

**文档状态：** 草案，待用户评审

> 2026-05-01 修订说明：本文件 1-7 节记录了从线性摘要升级为 `Q/F/P` 问题树的第一版思路。经实测评审，该方案仍然把过程产物混入主树，不能回答“需求规格说明补齐到什么程度”。自第 8 节起，完成度树作为覆盖度视图保留；原“提问路径”表述已修订为“沟通路径”，并以 `P2-Brainstorming-Turn引擎与状态机设计.md` 的用户输入驱动模型为当前基线。

## 1. 设计背景

当前 `P2 Brainstorming Lab` 的“会话摘要 / 过程产物”已经从字符串列表升级为 `QuestionItem / ConfirmedFact / DocumentPatchProposal` 三类对象，但实际观感仍有两个问题：

1. 信息不够紧凑。`Q-001`、状态、问题文本、事实、Patch 分散成多行卡片，缺少层级结构。
2. 线性列表不符合 Brainstorming 的真实过程。一个问题被确认后，可能产生事实、文档建议和顺延问题；这些关系用并列列表展示不直观。

因此，下一版会话摘要区建议改为 **面向需求规格说明文档撰写的问题树**。

## 2. 决策约束

问题树不是泛化知识图、任务树或项目管理树。

它必须服务于 `P2` 的核心目标：

```text
通过 Brainstorming Lab 验证如何把专家问答过程转化为可写入需求规格说明的结构化材料。
```

因此，问题树的组织导向必须优先参考：

- 当前需求规格说明模板章节。
- 当前文档撰写目标。
- 待补齐的需求规格信息。
- 已确认事实如何支持某个章节正文。
- `document_patch` 如何落到目标章节。

如果某个问题不能帮助需求规格说明成文，它不应成为主树节点，只能作为调试信息、风险或注记处理。

## 3. 核心设计

### 3.1 树的主轴

问题树的主轴不是时间线，而是文档结构。

推荐结构：

```text
需求规格说明
├─ 1.1 系统目标
│  ├─ Q-001 系统定位是什么？             已确认
│  │  ├─ F-001 系统定位为空域计算分析工具
│  │  └─ P-001 -> 1.1 系统目标
│  └─ Q-002 是否需要说明离线或弱网运行？  待确认
├─ 1.2 用户角色
│  └─ Q-003 主要用户是谁？               待确认
└─ 2.1 输入数据
   └─ Q-004 输入数据来源是什么？         待确认
```

树根代表需求规格说明文档或当前模板对象。

第一层优先是模板章节或分析主题：

- 如果模板章节明确，挂到章节下，例如 `1.1 系统目标`。
- 如果章节暂不明确，挂到 `未归类澄清项`。
- 如果问题是跨章节约束，挂到 `全局约束 / 横切问题`。

第二层是问题节点。

问题节点下面挂：

- 已确认事实。
- 文档修补建议。
- 顺延问题。
- 风险或注记。

### 3.2 问题节点

问题节点是树的核心。

字段建议：

```json
{
  "question_id": "Q-001",
  "title": "系统定位是什么？",
  "content": "系统更偏向计算分析工具、协同规划平台，还是二者都有？",
  "status": "confirmed",
  "section_id": "1.1",
  "section_title": "系统目标",
  "parent_question_id": null,
  "source_turn_id": "turn-0001",
  "resolution_fact_ids": ["F-001"],
  "child_question_ids": ["Q-002"]
}
```

状态含义：

| 状态 | 含义 |
| --- | --- |
| `open` | 待确认 |
| `confirmed` | 已确认，并已经形成事实或结论 |
| `review` | 需复核，模型不确定或用户回答不完整 |
| `superseded` | 被更具体的新问题替代 |
| `cancelled` | 已取消，不再需要确认 |

关键规则：

- 用户回答某个问题后，该问题必须发生状态变化，不能继续显示为待确认。
- 如果用户回答不足以确认，状态应变为 `review`，并生成更具体的子问题。
- 如果用户自由输入了新约束，系统应判断它是：
  - 回答了当前问题；
  - 形成了新事实；
  - 引出了新的待确认问题；
  - 或需要挂到其他章节。

### 3.3 事实节点

事实节点是文档撰写的材料，不是对话摘要。

字段建议：

```json
{
  "fact_id": "F-001",
  "content": "系统初步定位为空域计算分析工具。",
  "section_id": "1.1",
  "source_question_ids": ["Q-001"],
  "source_turn_id": "turn-0001"
}
```

显示规则：

```text
F-001 系统初步定位为空域计算分析工具
      来源 Q-001 / turn-0001
```

事实节点只展示紧凑摘要。详细解释放到 hover、展开态或当前 Turn 视图中。

### 3.4 文档建议节点

文档建议节点必须解释“为什么建议写这里”。

字段建议：

```json
{
  "patch_id": "P-001",
  "target_section": "1.1 系统目标",
  "status": "proposed",
  "source_fact_ids": ["F-001"],
  "source_question_ids": ["Q-001"],
  "content": "本系统面向空域领域专家，支持围绕空域运算任务进行输入组织、计算分析与结果确认。"
}
```

显示规则：

```text
P-001 -> 1.1 系统目标      待采纳
      来源 F-001 / Q-001
```

`target_section` 的来源必须明确：

- 模板章节匹配：可直接显示章节编号。
- 模型建议章节：显示为 `建议章节：1.1 系统目标`。
- 未能归类：显示为 `未绑定模板章节`。

## 4. UI 原型草案

右侧摘要区建议改为紧凑树形结构。

```text
会话摘要 / 文档撰写树

1.1 系统目标                                      2 问题 / 1 事实 / 1 建议
  ✓ Q-001 系统定位是什么？                         F-001  P-001
      F-001 系统定位为空域计算分析工具              turn-0001
      P-001 -> 1.1 系统目标                         待采纳
  ? Q-002 是否需要说明离线或弱网运行？              待确认

1.2 用户角色                                      1 问题
  ? Q-003 主要用户是谁？                           待确认

2.1 输入数据                                      1 问题
  ? Q-004 输入数据来源是什么？                     待确认

未归类澄清项
  ! Q-005 “实时性要求”应归入性能还是接口？          需复核
```

视觉规则：

- 节点尽量单行展示，必要时截断或换行到第二行。
- 状态符号放在最前：`?` 待确认，`✓` 已确认，`!` 需复核，`↪` 被替代。
- 编号、标题、状态、关联编号放在同一行，避免卡片式大面积留白。
- 默认只展开当前活跃章节和当前路径。
- 用户可展开某个问题查看完整事实、Patch 文本和来源 Turn。

## 5. 状态更新规则

每一轮 `BrainstormTurn` 返回后，后台应产生树变更，而不是只返回列表增量。

建议输出协议：

```json
{
  "question_tree_updates": [
    {
      "operation": "update",
      "question_id": "Q-001",
      "status": "confirmed",
      "resolution_fact_ids": ["F-001"]
    },
    {
      "operation": "create",
      "question_id": "Q-002",
      "parent_question_id": "Q-001",
      "section_id": "1.1",
      "title": "是否需要说明离线或弱网运行？",
      "status": "open"
    }
  ],
  "fact_updates": [
    {
      "operation": "create",
      "fact_id": "F-001",
      "section_id": "1.1",
      "source_question_ids": ["Q-001"],
      "content": "系统初步定位为空域计算分析工具。"
    }
  ],
  "patch_updates": [
    {
      "operation": "create",
      "patch_id": "P-001",
      "target_section": "1.1 系统目标",
      "source_fact_ids": ["F-001"],
      "source_question_ids": ["Q-001"],
      "status": "proposed"
    }
  ]
}
```

前端不自己推断问题是否已确认。状态必须来自 `Brainstorming Service` 的结构化结果。

## 6. 与正式需求规格文档的关系

问题树只在 Lab 中验证过程。

它不等同于正式需求规格说明正文，也不直接替代文档编辑器。

它的作用是：

1. 证明问答过程能被组织成可追踪的文档撰写材料。
2. 证明每条事实能追溯到问题和 Turn。
3. 证明每条文档建议能追溯到事实、问题和模板章节。
4. 为后续正式 P2 专家工作台提供“问答到正文”的转换依据。

因此，问题树不能偏离文档撰写目标。它的任何节点都应能回答：

```text
这个节点帮助需求规格说明哪个章节成文？
如果不能，它为什么还应该出现在 Lab 过程产物中？
```

## 7. 实现前待确认点

建议确认以下设计点后再编码：

1. 树第一层是否固定为需求规格模板章节？
   - 推荐：优先模板章节，另设 `未归类澄清项` 和 `全局约束`。

2. 问题树默认展开策略？
   - 推荐：默认展开当前活跃章节和最新 Turn 相关路径，其他章节折叠。

3. `document_patch` 是否直接挂在问题下，还是只挂在事实下？
   - 推荐：挂在问题节点下，但显示来源事实；因为用户更容易从问题理解 Patch 的来源。

4. 是否保留独立的“已确认事实”列表？
   - 推荐：不作为主展示，只在树内展示；可在调试区或筛选视图中提供列表。

## 8. 2026-05-01 修正版：完成度树与沟通路径分离

实测后确认，仅把 `Question / Fact / Patch` 做成树仍然不够。它仍然是过程产物树，不是需求规格说明的目标树。

新的主结论：

```text
会话摘要主视图必须是“需求规格完成度树”，不是 Q/F/P 过程产物列表。
```

### 8.1 双视角

会话摘要区拆成两个视角：

1. `需求规格完成度树`：目标视角，回答“规格说明还缺什么，哪些节点已关闭”。
2. `沟通路径`：过程视角，回答“每轮用户输入如何影响了哪些目标节点”。

`Fact` 和 `DocumentPatch` 仍然保留为内部材料，但不再作为主树节点直接铺开。

### 8.2 完成度树结构

完成度树根来自规格说明目标，不来自模型临时问题。

推荐初始结构：

```text
需求规格完成度树
├─ 1. 系统概述
│  ├─ 系统要做什么？
│  ├─ 系统边界是什么？
│  └─ 主要目标和非目标是什么？
├─ 2. 用户与使用场景
│  ├─ 谁使用这个系统？
│  ├─ 用户如何使用系统？
│  └─ 是否存在管理者或协作者？
├─ 3. 功能需求
│  ├─ 核心功能有哪些？
│  ├─ 输入数据是什么？
│  ├─ 输出结果是什么？
│  └─ 功能优先级是什么？
├─ 4. 非功能需求
│  ├─ 性能要求是什么？
│  ├─ 安全要求是什么？
│  └─ 部署运行约束是什么？
└─ 5. 验收与约束
   ├─ 验收标准是什么？
   ├─ 外部接口有哪些？
   └─ 风险与假设是什么？
```

节点字段：

```json
{
  "node_id": "SPEC-1.1",
  "title": "系统要做什么？",
  "target_section": "1.1 系统目标",
  "status": "open|partial|closed|skipped",
  "answer_summary": "系统初步定位为空域计算分析工具",
  "completion_reason": "turn-0001 用户已确认",
  "children": []
}
```

### 8.3 历史推进规则与当前修订

第一版曾认为，每轮 Brainstorming 不应先问“模型想问的问题”，而应先定位当前目标叶子：

```text
读取 spec_tree
  -> 找到第一个 open 叶子节点 active_spec_node_id
  -> 围绕该节点生成提问
  -> 用户回答
  -> 更新该节点 answer_summary / status
  -> 写入 turn_path
  -> 推进到下一个 open 叶子节点
```

该推进规则已经被后续 Turn 引擎设计修订，不再作为当前实现基线。当前规则是：

```text
用户输入启动 Turn
  -> 读取上一轮建议话题
  -> 判断用户输入是否承接、改题、反驳或补充
  -> 回应用户本轮真实诉求
  -> 将影响投影到一个或多个完成度树节点
  -> 可选地产生下一轮建议话题
```

节点状态仍然可以更新，但它是 Turn 处理后的投影结果，不是 Turn 的起点。

节点状态规则：

- 用户输入明确补齐某节点，且足以形成规格正文摘要：`closed`。
- 用户输入只部分补齐某节点：`partial` 或生成更具体的建议话题。
- 用户明确暂不需要：可记为 `closed`，`answer_summary` 写明“第一阶段不需要”。
- 当前节点不适用：`skipped`。

### 8.4 沟通路径

沟通路径独立记录每轮用户输入对完成度树的影响：

```json
{
  "turn_id": "turn-0001",
  "previous_suggestion_id": null,
  "user_input_summary": "系统初步定位为空域计算分析工具",
  "input_relation": "none",
  "affected_node_ids": ["SPEC-1.1"],
  "closed_node_ids": ["SPEC-1.1"],
  "next_suggestion_id": "suggestion-0001"
}
```

这个视角可以作为调试、审计和回放依据，但不应取代完成度树。

### 8.5 UI 规则

右侧主视图显示：

```text
需求规格完成度树                  current focus: SPEC-1.2

✓ 1. 系统概述                    部分完成
  ✓ 系统要做什么？                1.1 系统目标     已关闭
    回答摘要：系统初步定位为空域计算分析工具
  ? 系统边界是什么？              1.2 系统边界     待确认
  ? 主要目标和非目标是什么？       1.3 目标与非目标 待确认

沟通路径
turn-0001  SPEC-1.1  用户输入补齐系统定位
```

`F-xxx` 和 `P-xxx` 只在节点详情、当前 Turn 或调试视图中展示，不作为完成度树的主节点。

### 8.6 当前实现落点

当前实现已将以下字段加入 `BrainstormSession`：

- `spec_tree`
- `active_spec_node_id`（历史字段，后续应替换为 `current_focus_node_id` 或由 Turn 的 `affected_spec_nodes` 推导）
- `turn_path`

前端 `会话摘要 / 过程产物` 已改为：

- 主视图：`需求规格完成度树`
- 辅助视图：`沟通路径`

旧的 `questions / facts / patches` 仍然作为内部材料保留，以支持正文建议、来源追溯和 Turn 调试。

## 9. 2026-05-01 阶段性实验记录：模板目标树与 Turn 决策审计

实测截图暴露两个根因：

1. 完成度树只是代码手写的两层浅表清单，不是从规格模板对象推导出来。
2. `active_spec_node_id` 在推进，但 Provider 提问没有被强制绑定到该节点，导致树上走到“用户与角色”，左侧却问“外部数据导入”。

因此，本阶段曾尝试把完成度树改为从当前 `RequirementDocumentTemplate` 的 `sections / clauses` 生成，并让组织器围绕当前模板节点推进。

> 重要修订：该 active 节点驱动方案已被后续 `P2-Brainstorming-Turn引擎与状态机设计.md` 取代。本文第 9 节保留为阶段性实验记录，用于解释为什么曾经这样实现，以及为什么后续不再以它作为基线。

首版 `81433号` 内置模板的目标树形态为：

```text
需求规格说明完成度树（81433号）
├─ 1 总则
│  └─ REQ-1.1 编写目的
├─ 2 项目概述
│  └─ REQ-2.1 软件定位
├─ 3 功能需求
│  ├─ REQ-3.1 用户与角色
│  ├─ REQ-3.2 核心业务流程
│  └─ REQ-3.3 异常与补偿
├─ 4 非功能需求
│  └─ REQ-4.1 性能与可靠性
└─ 5 验收准则
   └─ REQ-5.1 验收准则
```

每个叶子节点增加 `question` 字段。

示例：

```json
{
  "node_id": "SPEC-REQ-3.1",
  "title": "REQ-3.1 用户与角色",
  "target_section": "3 功能需求 / 用户与角色",
  "question": "谁使用这个系统？请说明主要用户角色、职责和是否存在协作者或管理员。"
}
```

### 9.1 已废弃的组织器强约束

本阶段曾设想组织器每轮按下面顺序运行：

```text
读取 active_spec_node
  -> Provider 只允许围绕 active_spec_node.question 吸收用户回答
  -> document_patch.section 强制等于 active_spec_node.target_section
  -> 服务端判断当前节点是否关闭
  -> 如果关闭，按模板顺序选择下一个 open 叶子
  -> next_question 强制改写为下一个 open 叶子的 question
```

这意味着模型可以生成措辞、摘要和候选选项，但不能自由跳章节。

实测后确认，这个约束过强。它解决了模型偏题问题，但引入了新的错误：

- Turn 被错误理解为“系统提问、用户回答”。
- 用户主动输入、反驳、改题、补充时，系统仍会尝试把它塞回当前节点。
- 需求规格完成度树变成了流程控制器，而不是覆盖度视图。
- 当前 Turn 审计只能解释“节点为什么关闭”，不能解释“用户本轮诉求是否被回应”。

因此，该强约束不再作为后续实现基线。

### 9.2 当前 Turn 改为用户输入驱动的决策审计视图

`当前 Turn` 不再只是输入输出对象查看页，而是组织器决策审计页。

每轮必须展示：

- `承接话题`：上一轮系统给出的建议话题是什么；首轮可以为空。
- `本轮用户输入`：用户原文输入，Turn 从这里开始。
- `输入关系判断`：用户是采纳、部分承接、改题、反驳、补充，还是忽略上一轮建议。
- `系统理解与回应`：组织器如何理解用户输入，并如何对用户回应。
- `本轮闭环判断`：用户本轮关心的问题是否已经被回应，而不是某个模板节点是否被机械关闭。
- `影响的规格节点`：本轮影响了哪些模板章节，可为 0、1 或多个。
- `本轮状态变化`：事实、问题、Patch、风险、注记如何变化。
- `下一轮建议话题`：系统建议下一轮聊什么，可为空。
- `决策依据`：组织器的判断链。

这可以回答用户关心的问题：

```text
上一轮建议是什么？
用户本轮是否承接了上一轮建议？
用户真正想表达或要求系统处理的是什么？
系统为什么这样回应？
本轮是否闭环了用户的诉求？
本轮对需求规格完成度树产生了什么投影影响？
下一轮建议为什么是这个方向？
```

### 9.3 与沟通路径的分工

`需求规格完成度树` 是目标视角。

`沟通路径` 是回放视角，记录每轮用户输入、系统回应、影响节点和建议话题，不再等同于“系统提问路径”。

`当前 Turn` 是决策审计视角。

三者不能混用：

- 完成度树只显示模板目标节点覆盖状态。
- 沟通路径只显示每轮用户输入和组织器处理轨迹。
- 当前 Turn 才展示本轮承接关系、决策链、闭环判断、Patch 和 Provider 细节。
- 完成度树不能替代 Turn 起点；Turn 必须从用户输入开始。
