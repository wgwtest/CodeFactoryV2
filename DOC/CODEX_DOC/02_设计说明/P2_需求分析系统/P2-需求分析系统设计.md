## 0. 2026-04-30 基线修订

`P2` 后续实现的主产品口径已经从“应用需求建模器”修订为“可配置标准需求规格说明编写系统”。

本轮修订的正式入口为：

- `DOC/CODEX_DOC/02_设计说明/P2_需求分析系统/P2-可配置需求规格说明编写系统设计.md`
- `DOC/CODEX_DOC/02_设计说明/P2_需求分析系统/P2-需求规格编写系统原型设计.md`

新的核心结论如下：

- 专家正面工作对象是标准需求规格说明文档，而不是低代码模型或单纯结构化表单。
- 左侧输入区提供 `问答模式 / 表单模式` 两个同源输入 `Tab`，缺口补齐属于问答模式能力。
- 右侧显示完整标准规格正文，专家可轻量编辑正文文字。
- 条款批注不常驻，点击或聚焦条款时以浮层显示系统解读、缺口、来源和 `P3` 映射。
- 规格模板、表单模板、字段映射、问答策略、缺口检查规则和知识库绑定都必须可配置。
- `81433 / 82259` 只作为首版内置默认模板，模板对象本身必须可替换、可版本化。
- 结构化 `RequirementSpec` 仍然存在，但其职责是后台事实状态和冻结后下游包。
- `P3` 只消费专家冻结后的正式版本。
- 专家工作台原型默认采用 `2:3` 分屏，并提供 `1:1` 切换。
- 问答模式采用 `CLI` 式连续协作，右侧正文随对话持续生成和修补。
- 表单模式是按标准章节组织的结构化校对台，与问答和正文同源。

若本文件早期章节与上述新基线发生冲突，以 `P2 可配置需求规格说明编写系统设计` 专题设计为准。

## 1. 设计定位

`P2` 的目标是在 `P1` 已发布知识仓之上，为专业知识专家提供一个可配置、可审阅、可冻结的标准需求规格说明编写系统，把专家输入沉淀为标准需求规格说明文档，并同步形成结构化 `RequirementSpec` 包。

`P2` 首版不是组件装配台，也不是低代码原型生成器，而是：

- 知识仓与软件设计系统之间的过渡层
- 专家输入到标准需求规格说明之间的编写层
- 标准需求规格说明到结构化 `RequirementSpec` 包之间的冻结层
- 面向专业知识专家的规格编写工作台

## 2. 目标与边界

### 2.1 首版负责

- 提供面向专业知识专家的需求规格编写工作台
- 支持 `问答模式 / 表单模式` 两种同源输入
- 实时呈现完整标准需求规格说明正文
- 支持条款批注浮层、缺口检查和冻结版本
- 消费 `P1` 的发布态知识库作为可选来源引用
- 提供配置与模板管理台，配置规格模板、表单模板、字段映射、问答策略和缺口检查规则
- 冻结后输出标准规格说明文档和结构化 `RequirementSpec` 包

### 2.2 首版不负责

- 组件命中推荐和复用判断
- 软件设计说明生成
- 工具仓库资产管理
- 可运行原型生成
- BPMN / 泳道图编辑器
- 面向技术人员的专业低代码建模工具

## 3. 目标用户与交互原则

### 3.1 目标用户

首版目标用户分为两类：

- 专业知识专家和需求规格编写者：使用专家工作台编写、审阅、冻结标准需求规格说明
- 管理员和开发者：使用配置与模板管理台维护模板、表单、映射、问答和缺口检查规则

### 3.2 设计原则

- 专家正面工作对象是标准需求规格说明正文
- 问答模式和表单模式是同源输入方式，不是两套系统
- 结构化对象是后台事实状态和冻结后的下游包
- 标准正文保持纯净，批注层按条款浮层展开
- 先写需求规格，不混入组件与实现细节

### 3.3 对象优先于流程

`P2` 必须坚持“对象优先于流程”的建模逻辑。

原因：

- 对象建模要素比流程更完整
- 系统要支持探索新流程，而不只是复现既有流程
- 多对象跨流程应用是核心目标场景

## 4. 页面形态与工作台骨架

### 4.1 双形态输入

`P2` 正式支持两种互补输入形态：

- `问答模式`
- `表单模式`

二者是同一规格语义状态的不同输入入口，不是两套割裂系统。问答回答会回填相关表单字段，表单修改会更新问答上下文。

### 4.2 默认主路径

首版默认路径固定为：

`选择规格模板与知识库 -> 问答或表单输入 -> 标准正文实时更新 -> 缺口检查 -> 专家冻结 -> 输出给 P3`

含义：

- 用户先选择适用的规格模板和来源知识库
- 再通过问答或表单录入需求内容
- 系统基于模板、映射和缺口规则更新标准正文
- 专家检查条款批注和缺口后冻结正式版本

### 4.3 页面骨架

首版专家工作台采用左右两半：

- 左侧：输入区，以 `Tab` 切换问答模式和表单模式
- 右侧：标准需求规格说明正文

条款批注不常驻。用户点击或聚焦条款时，以浮层展示语义解释、来源引用、结构化字段映射、`P3` 映射建议、缺口提示和待确认项。

## 5. 建模对象与阶段路径

### 5.1 建模核心单元

`P2` 的最小可解释单元不是裸流程节点，而是 `动作 / 任务`：

- `参与方`
- `业务对象`
- `行为`
- `结果 / 状态变化`

### 5.2 标准建模步骤

首版按以下 6 段推进：

1. 业务目标收敛
2. 使用对象与范围收敛
3. 自建模块
4. 模块内动作建模
5. 模块链路与交接动作
6. 自动页面建议与输出

### 5.3 模块与交接

模块由用户自行创建，至少填写：

- 模块名
- 一句用途

系统在读到模块名和用途后，再推荐：

- 动作候选
- 参与方
- 业务对象
- 候选交接点

多个模块之间通过 `交接动作` 连接，而不是只保留孤立模块列表。

## 6. 推荐体系

### 6.1 推荐来源

`P2` 的推荐来自三层：

- 通用应用知识
- `P1` 已发布领域知识
- 用户当前输入

### 6.2 推荐触发规则

至少支持以下触发：

- 写完 `模块名 + 用途` 后推荐动作候选
- 新建动作后推荐参与方、业务对象和结果状态
- 形成多个模块后推荐模块间交接动作
- 模块与动作骨架稳定后推导页面模板建议

### 6.3 来源标识

每个建模项都必须带来源：

- `recommended_common`
- `recommended_domain`
- `manual`
- `temporary_pending_intake`

### 6.4 推荐解释

系统至少要能解释：

- 为什么推荐某类通用模式
- 为什么某个知识项与当前模块或动作相关
- 为什么建议某个交接点或页面模板

## 7. 输出模型

`P2` 的专家正面输出是标准需求规格说明文档。

结构化对象不是取消，而是调整为后台事实状态和冻结后下游包。首版至少包含：

- `RequirementDocumentTemplate`：规格模板对象
- `RequirementFormTemplate`：表单模板对象
- `RequirementQuestionnairePolicy`：问答策略对象
- `RequirementSpecDocument`：规格实例文档对象
- `RequirementSemanticState`：规格语义状态对象
- `RequirementClauseAnnotation`：条款批注对象

设计要求：

- 标准需求规格说明正文是专家审阅和冻结的主产物
- `RequirementSemanticState` 是问答、表单、正文和结构化包共享的后台事实状态
- 每个章节、条款和结构化字段必须具备稳定标识
- 每个来源知识引用、待确认映射和缺口提示必须可追溯
- 冻结后同时输出标准文档、结构化 `RequirementSpec` 包和条款批注追溯信息

## 8. 标准正文与草稿机制

### 8.1 标准正文

首版标准正文至少支持：

- 完整规格模板骨架
- 章节导航和条款聚焦
- 待补齐章节状态
- 正文轻量编辑
- 条款批注浮层
- 导出预览
- 冻结版本

### 8.2 草稿状态

首版支持：

- `draft`
- `checking`
- `ready_to_freeze`
- `frozen`
- `submitted_to_p3`
- `archived`

### 8.3 最小完成条件

至少满足以下条件，才能标记完成：

- 已选择可用规格模板
- 已绑定或明确不绑定来源知识库
- 必填章节已补齐
- 阻断型缺口检查通过
- 正文与结构化语义状态不存在未确认阻断映射
- 已生成可供 `P3` 消费的冻结结构化包

## 9. `P2-Sim` 的正式定位

`P2-Sim` 不是替代真实 `P2` 的旁路功能，而是 `P2` 的轻量模拟输入台，用于：

- 从预置样板生成最小 `RequirementSpec`
- 一键写入现有 `requirements/specs` 池
- 为 `P3` 提供可重复、可操作的上游联调入口

首版约束：

- 不增加“推送到 P3”假动作
- 行为保持与真实上游一致，即提交需求规格说明即可
- 只提供轻量样板和预览，不做完整需求编辑器

## 10. 与上下游的契约边界

### 10.1 与 `P1` 的边界

`P2` 只消费 `P1` 的已发布知识结果，不允许读取：

- 候选知识
- 治理工作态
- 审核中间数据

首版正式输入包括：

- 发布态流程清单
- 发布态实体/事件清单
- 单项详情
- 关系邻域
- 知识引用元信息

### 10.2 与 `P3` 的边界

串行关系固定为：

`P1 -> P2 -> P3`

`P2` 向 `P3` 只输出：

- 冻结后的标准需求规格说明文档
- 冻结后的结构化 `RequirementSpec` 包
- 条款批注和追溯信息
- 冻结版本元信息

`P3` 不应直接读取 `P2` 的草稿态、交互式临时状态或未确认批注。

## 11. 核心功能模块与首版范围

首版建议拆为 7 个模块：

- 专家需求规格编写工作台
- 配置与模板管理台
- 规格模板服务
- 表单模板与字段映射服务
- 问答策略与缺口检查服务
- 需求规格文档与语义状态服务
- 冻结输出与 `P3` 交接服务

首版最小实现范围固定为：

- 专家工作台左右两半布局
- 左侧 `问答模式 / 表单模式` 同源输入
- 右侧标准需求规格说明正文
- 条款批注浮层
- 规格模板、表单模板、字段映射、问答规则和缺口检查规则配置
- 草稿保存、缺口检查、冻结版本
- 冻结后输出标准文档和结构化 `RequirementSpec` 包

## 12. 验收口径

首版验收只看以下问题是否成立：

1. 专家能否选择规格模板和知识库，在标准需求规格正文中工作
2. 问答模式和表单模式是否同源，并能共同更新同一份正文
3. 专家是否能轻量编辑正文，同时不破坏模板骨架和编号规则
4. 条款批注浮层是否能解释来源、缺口、结构化映射和 `P3` 映射
5. 配置台是否能配置规格模板、表单模板、字段映射、问答规则和缺口检查规则
6. 冻结前检查是否能阻断关键缺口
7. 冻结后是否能稳定导出标准文档和结构化 `RequirementSpec` 包给 `P3`
