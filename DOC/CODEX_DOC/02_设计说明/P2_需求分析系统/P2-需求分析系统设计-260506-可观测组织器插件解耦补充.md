# P2 可观测组织器插件解耦升级设计

## 1. 文档定位

- 文档日期：2026-05-06
- 文档归属分支：`feat/p2-validation-workflow`
- 当前 worktree：`/home/wgw/CodexProject/CodeFactoryV2/.worktrees/p2-validation-workflow`
- 设计主题：将当前 `P2` 需求分析 Lab 中的组织器升级为“可观测组织器插件”，使后续可在不重写 `P2` 主流程的前提下切换自研组织器、`Dify workflow` 组织器或其他远端组织器实现。

本设计只服务于当前分支的 `P2 validation workflow` 主线，不为另一个并行 `P2` 分支提供“专家工作台重做方案”，也不在本轮要求真实接入 `Dify`。

---

## 2. 背景与问题

当前 `P2` 已经具备以下基础：

1. `orchestrators/xg/...` 已形成组织器包目录。
2. `apps/api/app/orchestrators/` 已具备包装载、Prompt 解析、Schema 解析、本地 runner 执行等宿主能力。
3. `apps/api/app/requirement_analysis/turn_engine.py` 已形成 `intent -> write -> apply -> review -> next_interaction -> decide` 的轮次执行链。
4. 当前 Lab 已有 `working_document`、`working_document_update`、`review_after_apply`、`provider_logs` 等过程观测面。

但当前结构仍存在以下耦合：

1. `P2` 主流程直接理解并驱动固定阶段顺序，组织器仍是“半插件”。
2. 组织器内部能力与 `turn_engine`、`turn_stage_executor`、`turn_stage_reducer`、`working_document_service` 之间边界不够清晰。
3. 未来若要接 `Dify workflow`，只能把 `Dify` 塞进现有阶段链，仍不能真正做到“切换组织器即可替换实现”。
4. 虽然当前已经能输出过程数据，但这些过程数据仍有部分是由 `P2` 主流程自行推导，而不是由组织器插件统一输出合同表达。

因此，本轮不是单纯“接 Dify”，而是先将组织器升级为：

```text
Observable Orchestrator Plugin
可观测组织器插件
```

其含义为：

1. `P2` 不关心组织器内部如何编排。
2. `P2` 通过稳定输入合同调用组织器插件。
3. 组织器插件必须通过稳定输出合同返回正文结果、补丁结果、过程结果、审计结果和下一轮交互结果。
4. 自研组织器保留完整过程观测能力。
5. `Dify` 组织器允许只提供有限过程观测能力，但仍接入同一插件合同。

## 4. 升级目标

本轮目标不是让 `P2` 失去过程观测，而是让过程观测从“主流程内部硬编码推导”升级为“插件标准化输出”。

目标定义如下：

1. 将当前组织器升级为可切换插件。
2. 保持现有自研组织器完整观测能力不退化。
3. 允许后续新增 `Dify workflow` 插件实现。
4. `P2` 主流程从“组织器内部阶段编排者”降级为“组织器插件宿主与结果归一化者”。
5. 页面与会话状态继续可以观察正文、补丁、回看、阶段审计、日志和决策轨迹。

## 5. 核心原则

### 5.1 黑盒不是不可观测

本设计中的“黑盒”仅表示：

1. `P2` 不依赖组织器内部实现细节。
2. `P2` 不依赖组织器内部固定阶段链。

它不表示：

1. 丢失阶段审计。
2. 丢失日志。
3. 丢失文档 patch。
4. 丢失 review 结果。
5. 丢失状态推进依据。

### 5.2 统一合同优先于统一实现

不同组织器可以有不同内部实现：

1. 本地 Python runner。
2. 当前阶段化 prompt 解释模式。
3. `Dify workflow`。
4. 远端组织器服务。

但它们必须遵守统一输入输出合同。

### 5.3 能力分级而非假装等价

不同组织器的观测深度可以不同。

例如：

1. 自研组织器可提供完整 `stage_audits`、`provider_logs`、`decision_trace`。
2. `Dify` 插件可能只提供 `filled_document_text` 和有限 `workflow_trace`。

系统应通过能力声明和降级展示处理差异，而不是强迫所有插件具备相同观测深度。

### 5.4 当前分支先做解耦，不做真实 Dify 联调

本轮重点是把系统解成可切换插件宿主，`Dify` 只作为插件类型预留和 fake response 验证对象，不在本轮引入真实环境依赖。

## 6. 目标架构

### 6.1 升级前

当前主链可概括为：

```text
TurnEngine
  -> build TurnContext
  -> plan stages
  -> run intent
  -> run write
  -> apply patches
  -> run review
  -> run next interaction
  -> decide
  -> persist session state
```

其中组织器虽然已经包化，但 `P2` 主流程仍知道固定阶段结构。

### 6.2 升级后

目标主链改为：

```text
TurnEngine
  -> build OrchestratorRunRequest
  -> resolve plugin manifest
  -> invoke plugin adapter
  -> validate OrchestratorRunResult
  -> normalize result
  -> apply/save/display
  -> persist session state
```

组织器插件内部可以自由采用：

1. 固定阶段化执行。
2. `Dify workflow` 执行。
3. 远端服务执行。
4. runner 直接返回。

### 6.3 模块结构

建议新增或重组为以下结构：

```text
apps/api/app/orchestrators/
  plugin_contracts.py
  plugin_registry.py
  plugin_result_normalizer.py
  adapters/
    local_xg_plugin.py
    dify_workflow_plugin.py
    remote_service_plugin.py
```

现有：

```text
apps/api/app/orchestrators/package_loader.py
apps/api/app/orchestrators/runner_host.py
apps/api/app/orchestrators/stage_*
```

保留并下沉为本地自研插件内部依赖，而不是继续直接暴露给 `turn_engine` 作为主流程固定结构。

## 9. 当前自研组织器的迁移方式

### 9.1 基本策略

当前自研组织器不应被废弃，而应成为首个完整实现的可观测插件。

做法为：

1. 保留现有 `orchestrators/xg/...` 包结构。
2. 保留当前本地 runner、Prompt、Schema、Adoption、Artifact Rules。
3. 新增 `LocalXGOrchestratorPluginAdapter` 包装现有阶段链。
4. 由该适配器输出统一 `OrchestratorRunResult`。

### 9.2 迁移后关系

升级后：

1. `package_loader.py` 仍负责装载自研组织器包。
2. `runner_host.py` 仍负责本地 runner 或 stage prompt bundle 相关能力。
3. 这些能力只服务于 `LocalXGOrchestratorPluginAdapter`。
4. `turn_engine.py` 不再直接依赖具体的 `intent/write/review/next` 阶段结构。

### 9.3 阶段链内部保留

本轮不要求删除当前阶段链，只要求把它从 `P2` 主流程上移除为插件内部实现。

即：

```text
当前阶段链继续存在
但它的宿主从 TurnEngine 主流程
迁移为 LocalXGOrchestratorPlugin 内部实现
```

## 10. Dify 插件预留方案

### 10.1 本轮定位

本轮不真实接 `Dify`，只定义 `Dify` 插件适配位。

新增：

```text
DifyWorkflowOrchestratorPluginAdapter
```

其职责为：

1. 接收 `OrchestratorRunRequest`
2. 映射为 `Dify workflow` 的输入结构
3. 接收 `Dify` 结果
4. 转换为 `OrchestratorRunResult`

### 10.2 本轮实现约束

本轮只要求：

1. 定义插件 manifest 结构
2. 定义 fake response 映射
3. 定义能力声明
4. 能在测试中被选择并成功返回合同对象

本轮不要求：

1. 真实网络联调
2. 真实工作流上传
3. 真实节点日志抓取
4. 真实 API Key 配置

### 10.3 Dify 与本分支关系

`Dify` 在本分支中的角色仅为：

```text
验证“插件宿主 + 插件合同”架构可以承载外部工作流组织器
```

而不是：

```text
本轮必须切换生产组织器到 Dify
```

## 11. TurnEngine 职责重构

### 11.1 升级前职责

当前 `RequirementAnalysisTurnEngine` 同时承担：

1. 轮次上下文构造
2. 阶段规划
3. 阶段执行
4. 正文 patch 应用
5. review 输入构造
6. next interaction 输入构造
7. closure decision 构造
8. 会话状态更新

### 11.2 升级后职责

升级后 `TurnEngine` 的目标职责为：

1. 读取会话状态
2. 构造 `OrchestratorRunRequest`
3. 选择插件
4. 调用插件
5. 校验 `OrchestratorRunResult`
6. 归一化结果
7. 持久化会话状态
8. 组装 API 输出

### 11.3 仍保留在主流程的能力

以下能力仍保留在 `P2` 主流程：

1. 会话状态持久化
2. 模板对象读取
3. `working_document` 权威写入
4. 正式冻结与导出
5. API 响应归一化

### 11.4 下沉到插件的能力

以下能力应逐步下沉到插件内部：

1. 固定阶段顺序定义
2. 具体 Prompt 选择
3. 阶段性模型调用策略
4. 阶段结果采用策略
5. 下一轮交互规划逻辑

## 12. Working Document 与状态观测策略

### 12.1 原则

解耦后，`working_document` 仍然是当前分支的主证据面。

无论插件内部如何组织：

1. `P2` 都要拿到临时正文变化结果。
2. `P2` 都要能展示当前轮正文应用结果。
3. `P2` 都要能展示 review 与下一轮交互结果。

### 12.2 对自研插件

自研插件应继续输出：

1. `document_patch`
2. `working_document_update`
3. `review_after_apply_result`
4. `stage_audits`
5. `provider_logs`
6. `decision_trace`

### 12.3 对 Dify 插件

`Dify` 插件至少输出：

1. `filled_document_text` 或可转成正文更新的数据
2. `assistant_message`
3. `next_question`
4. `quick_options`
5. `raw_workflow_trace`（若可获得）

当其无法提供细粒度 patch 或 review 时，系统允许：

1. 视图降级
2. 空的 `stage_audits`
3. 空的 `provider_logs`
4. 空的 `decision_trace`

但不能使主流程报错。

## 16. 风险与取舍

### 16.1 风险：合同过大

如果一开始把所有过程字段都做成强制字段，会导致 `Dify` 类插件难以接入。

处理策略：

1. 核心字段强制
2. 观测字段按能力声明开放

### 16.2 风险：TurnEngine 迁移时回归

当前 `turn_engine` 已经承担大量现有逻辑，直接大改会有回归风险。

处理策略：

1. 先加适配层
2. 再逐步收缩主流程职责
3. 保持现有测试绿灯后再继续收缩

### 16.3 风险：跨分支职责混乱

如果本分支开始重做专家工作台，会和另一个 `P2` 分支产生重复建设。

处理策略：

1. 在文档中明确边界
2. 本分支只改 Lab 与组织器宿主
3. 正式文档对象接口作为唯一共享边界

---

## 17. 最终设计结论

本轮 `feat/p2-validation-workflow` 应形成以下目标态：

1. `P2` 需求分析 Lab 不再固定绑定某一套组织器内部阶段链。
2. 当前自研组织器升级为首个完整观测插件实现。
3. `Dify workflow` 升级为首个有限观测插件预留类型。
4. `TurnEngine` 从组织器阶段编排者升级为组织器插件宿主。
5. `working_document`、review、日志、决策轨迹等当前分支核心观测能力继续保留。

一句话概括：

```text
在 feat/p2-validation-workflow 中先完成“可观测组织器插件宿主”解耦，
再以插件方式切入 Dify，而不是先把 Dify 硬塞进当前固定阶段链。
```
