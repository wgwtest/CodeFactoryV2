## 1. 设计定位

`P2-P1 场景数据发生器` 用于支撑 `P2` 首版可用闭环：在缺少稳定真实 `P1` 发布态知识时，生成确定性的模拟 `P1` 知识包，并交付标准 `RequirementAuthoringSession`，供 `P2` 专家需求规格编写工作台完成问答、表单、缺口检查、冻结和 `P3` 可消费包输出。

它不是随机造数器，也不是编辑器里的设置弹窗。它是独立功能工作台：发生器负责配置、物化、验证和交付；`P2` 编辑器只消费标准会话输入，不感知数据来源是真实还是模拟。

发生器工作台需要让开发者或验收人员看到：

- 场景目录、模板绑定和知识物化状态
- 模拟 `P1` 知识源的内部可追溯信息
- 问答规则、自动补齐、缺口检查和冻结候选
- 打开普通 `P2` 编辑器的会话入口

`P2` 编辑器需要保持：

- 左侧 `问答模式 / 表单模式` 同源输入
- 右侧标准需求规格说明正文持续生成
- 来源无感的知识库绑定状态
- 缺口检查可执行
- 冻结结果可供 `P3` 消费

## 2. 首版目标

首版目标采用完整 `P2` 闭环：

1. 选择一个确定性场景包。
2. 物化模拟 `P1` 发布态知识。
3. 创建绑定该知识包的标准 `P2` authoring session。
4. 通过规则型 `Brainstorming` 回答专家短输入。
5. 自动补齐剩余关键字段。
6. 执行缺口检查。
7. 冻结为 `P3` 可消费结构化包。

首版不纳入 `P6` 门户状态联动，不接真实大模型自由生成正文，不提前混入 `P3/P4/P5` 的设计、工具或构建细节。

## 3. 真数据与假数据边界

| 数据对象 | 首版来源 | 性质 | 说明 |
| --- | --- | --- | --- |
| 需求规格模板 | 本地模板配置 | 真 | `81433`、`82259` 等模板作为标准规格骨架，不造假。 |
| `P2` 工作台 | 现有正式页面与 API | 真 | 编辑器只消费标准会话输入，不显示发生器内部来源。 |
| `P1` 发布态知识 | 场景包物化 | 假但按真形态造 | 包含文档、实体、流程、事件、关系、证据和发布信息。 |
| 专家输入 | 用户输入加场景脚本 | 真/假混合 | 用户仍可真实短答或自由补充，场景包提供可复现脚本。 |
| Brainstorming 决策 | `mock_rule` | 假实现 | 规则型、确定性，后续可替换为 LLM。 |
| 冻结包 | `P2` 主流程生成 | 真 | 来源可以是假知识，但冻结结构和检查逻辑必须真实。 |

## 4. 场景包模型

场景包是稳定业务样例，不是随机模板。首版默认场景为：

- `scenario_id`：`airspace-collaboration`
- `scenario_name`：`空域协同规划软件`
- `default_template_code`：`81433`
- `mock_archive_id`：`mock-airspace-p1`

场景包至少包含：

- `p1_knowledge_seed`：模拟 `P1` 发布态知识种子
- `p2_authoring_seed`：`P2` 文档初始字段、标题、分屏比例和快捷输入
- `conversation_seed`：规则型问答脚本、字段补丁和自动补齐字段
- `expected_output`：自动化验收所需字段和正文片段

首版预填字段：

- `application_name`
- `domain_scope`
- `target_users`
- `main_process`

首版通过问答或自动补齐生成：

- `normal_flow`
- `exception_flow`
- `non_functional`
- `acceptance_criteria`

## 5. 模拟 P1 知识形态

模拟 `P1` 知识必须写成接近真实发布态知识的结构，而不是直接写 `P2` 表单字段。

首版知识包包含：

- `summary`
- `publication`
- `documents`
- `entities`
- `processes`
- `events`
- `relations`

空域协同规划场景中的核心知识项包括：

- 业务对象：协同任务、冲突窗口
- 业务流程：协同规划与冲突处置
- 控制事件：会签超时提醒
- 关键规则：发现冲突窗口后不得直接发布规划方案
- 证据片段：每个核心对象、流程、事件都必须有可回溯证据

## 6. Brainstorming Contract

无论首版规则引擎还是后续大模型，都必须返回同一种结构化结果：

```json
{
  "assistant_message": "已补入会签超时和人工确认约束。",
  "field_patches": {
    "exception_flow": "系统应在方案会签超时后提醒责任人，并允许人工确认后继续处理。"
  },
  "clause_patches": [],
  "next_questions": [
    {
      "question_id": "q-next-gap",
      "prompt": "继续补齐异常流程、非功能要求或验收准则？",
      "suggested_replies": ["加超时", "补验收", "自动补齐"]
    }
  ],
  "source_refs": [
    {
      "archive_id": "mock-airspace-p1",
      "item_id": "process-collaboration-planning",
      "evidence_id": "ev-process-001"
    }
  ],
  "confidence": 0.92,
  "blocking_risks": []
}
```

后端写入约束：

- `field_patches` 只能写入当前模板允许的字段。
- `clause_patches` 只能写入当前模板存在的条款。
- `source_refs` 必须能对应模拟或真实 `P1` 知识项。
- 低置信度或无法映射内容不得直接覆盖标准正文。
- 冻结前仍以缺口检查为准，`Brainstorming` 不能绕过缺口规则。

## 7. API 入口

首版新增正式 `P2` API：

- `GET /api/requirement-authoring/scenarios`
- `POST /api/requirement-authoring/scenarios/{scenario_id}/materialize`
- `POST /api/requirement-authoring/documents/{document_id}/scenario-turns`
- `POST /api/requirement-authoring/documents/{document_id}/auto-complete`

既有冻结入口继续复用：

- `POST /api/requirement-authoring/documents/{document_id}/check`
- `POST /api/requirement-authoring/documents/{document_id}/freeze`

## 8. 独立页面与编辑器交付边界

场景发生器应提供独立页面或独立工作台，不放入 `P2` 专家工作台的 `设置` 弹层。发生器和编辑器之间是交付关系，不是内嵌关系。

发生器工作台交互要求：

- 可选择场景包。
- 可绑定规格模板和知识包形态。
- 可点击生成标准 authoring session。
- 可显示发生器内部审计信息，包括 mock 知识包、规则引擎、fixture 版本和复现证据。
- 可执行场景问答、自动补齐、缺口检查和冻结候选验证。
- 可打开普通 `P2` 编辑器会话。

`P2` 编辑器交互要求：

- 只接收 `RequirementAuthoringSession`、知识包、模板、文档状态和问答上下文。
- 不显示 `mock`、`模拟`、`场景发生器`、fixture id 或规则引擎名。
- 不根据真假来源改变编辑器 UI 分支。
- 问答模式可输入 `加超时` 等短输入。
- 可点击 `自动补齐`。
- 可执行 `缺口检查` 和 `冻结版本`。

## 9. LLM 替换边界

首版不要求真实大模型接入。后续接入时，只替换 `Brainstorming` 决策引擎：

- `mock_rule`：确定性规则，首版默认
- `llm_assisted`：结构化大模型输出，后续启用
- `disabled`：只记录输入，不自动修补

大模型不得直接写数据库正文；它只能返回结构化补丁，由后端校验后写入。

## 10. 验收口径

首版验收必须覆盖：

1. 能列出 `airspace-collaboration` 场景。
2. 能物化 `mock-airspace-p1` 模拟知识包。
3. 能创建 `空域协同规划软件需求规格说明` 文档。
4. 能在发生器独立工作台显示模拟知识源和复现审计信息。
5. 输入 `加超时` 后，标准正文出现会签超时要求。
6. 自动补齐后阻断缺口为 `0`。
7. 冻结后 `frozen_package.p3_consumable = true`。
8. 冻结包中包含应用名称、核心流程、异常规则和验收准则。
9. 打开 `P2` 编辑器后，界面不得显示 `mock`、`模拟`、`场景发生器`、fixture id 或规则引擎名。

## 11. 设计结论

`P2-P1 场景数据发生器` 是 `P2` 首版闭环验收的关键数据底座。它的正式价值不是“造假数据”，而是用可复现的确定性场景把 `P1` 知识输入、`P2` 需求规格编写、缺口检查、冻结和 `P3` 消费契约串成一条可验证链路。
