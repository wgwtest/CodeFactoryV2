# P2 组织器插件输出物化层升级设计说明

> 状态：待确认。
>
> 用途：本文说明 `P2` 当前组织器插件输出无法稳定落入会话状态的问题、成因、风险边界和升级方案。本文只讨论设计和实施策略，不代表已完成代码修改。
>
> 维护规则：若 `P2` 组织器插件合同、`PluginTurnResultMaterializer`、本地 Brainstorm 插件接入路径或 Dify 型插件输出结构发生变化，应同步更新本文。

**日期：** 2026-05-08

**适用范围：**

- `P2` 需求分析系统
- 本地 Brainstorm v1 组织器
- Dify workflow 型组织器
- 组织器插件输出合同到 `P2` 会话状态的物化链路

## 1. 背景

`P2` 当前目标是把组织器做成可插拔黑盒：页面和会话服务不关心组织器内部如何编排，只关心组织器按公共合同输出结构化结果。组织器可以是本地 Brainstorm v1，也可以是 Dify workflow，未来也可以是其他外部工作流或模型编排系统。

近期真实联调 `brainstorm-v1-dify-workflow` 时发现：

1. Dify workflow 已能返回结构化 `document_patch`。
2. Dify 最终草案分支可返回多章节补丁，例如 7 个章节 patch。
3. `P2` 会话最终只落入 1 个合成 patch。
4. `working_document.blocks` 只有 1 个块，所有章节内容被堆入 `REQ-1.1 / 编写目的`。

这说明问题不再主要是 Dify 生成能力，而是平台对插件输出合同的消费能力不足。

## 2. 当前链路

当前 `P2` Turn 链路可概括为：

```text
P2 SessionService
  -> RequirementAnalysisTurnEngine
  -> load_orchestrator_plugin_adapter(...)
  -> adapter.run(OrchestratorRunRequest)
  -> TurnExecutionResult
  -> SessionService.apply_turn_execution_result(...)
```

其中不同组织器目前存在两类接入方式。

### 2.1 本地 Brainstorm v1 路径

本地 `brainstorm-v1` / `xg-heuristic-orchestrator` adapter 当前调用平台内部运行时：

```text
adapter
  -> runtime_host.run_policy_interpreted(...)
  -> TurnExecutionResult
  -> raw_output.turn_execution_result
```

该路径直接产出 `P2` 内部 `TurnExecutionResult`，因此不会经过 `PluginTurnResultMaterializer`。

### 2.2 Dify workflow 路径

`brainstorm-v1-dify-workflow` 调用真实 Dify Workflow API：

```text
Dify Workflow API
  -> result_json
  -> OrchestratorRunResult
  -> PluginTurnResultMaterializer
  -> TurnExecutionResult
```

该路径依赖 `PluginTurnResultMaterializer` 将标准插件输出合同转换为 `P2` 会话状态。

## 3. 问题描述

### 3.1 表层问题

Dify 原始输出中存在多条结构化补丁：

```json
{
  "document_patch": [
    {
      "target_section": "1 总则 / 编写目的",
      "anchor_path": "REQ-1.1",
      "content": "..."
    },
    {
      "target_section": "3 功能需求 / 核心业务流程",
      "anchor_path": "REQ-3.2",
      "content": "..."
    }
  ]
}
```

但平台物化后变成单条合成补丁：

```json
{
  "plan_ref": "AP-PLUGIN-001",
  "operation": "append_or_update",
  "content": "整篇 filled_document_text",
  "write_policy": "patch_suggestion_only"
}
```

结果是：

- `turn.spec_execution.document_patch` 丢失章节粒度。
- `turn.spec_execution.target_anchor_plan` 只有一个合成锚点。
- `session.working_document.blocks` 无法按章节展开。
- 页面临时正文显示被压扁为单块内容。

### 3.2 架构问题

更深层问题是当前组织器插件接入仍有双轨制：

| 路径 | 输出形态 | 是否经过通用物化层 |
| --- | --- | --- |
| 本地 Brainstorm v1 | 直接返回 `TurnExecutionResult` | 否 |
| Dify workflow | 返回 `OrchestratorRunResult` | 是 |

这不是按 `plugin_id` 写死的显式 `if/else`，但仍然是接口层面的双轨制。它带来的问题是：

1. 本地 Brainstorm 绕过了公共物化层。
2. 公共物化层长期只承担简单兜底逻辑，没有被完整验证。
3. Dify 作为真正黑盒插件接入后，暴露了公共物化层不能完整消费 `document_patch` 的问题。

从“组织器黑盒可插拔”的标准看，当前状态不能视为严格解耦完成。

## 4. 根因分析

### 4.1 `PluginTurnResultMaterializer` 仍按整篇文本兜底思路实现

当前物化层的核心假设是：

```text
插件可能只返回 filled_document_text
平台用 AP-PLUGIN-001 把整篇文本挂到当前 active_spec_node
```

这个假设适合早期假 Dify 或整篇正文输出样板，但不适合已经返回结构化 `document_patch` 的真实插件。

### 4.2 标准合同字段与工作文档服务字段之间缺少桥接

`WorkingDocumentService.apply_patches(...)` 已经支持多个 block，它依赖：

- `document_patch[].plan_ref`
- `target_anchor_plan[].plan_id`
- `target_anchor_plan[].anchor_path`
- `target_anchor_plan[].display_heading`

Dify 输出更自然地包含：

- `document_patch[].target_section`
- `document_patch[].anchor_path`
- `document_patch[].content`

两者之间需要平台物化层进行合同级桥接。当前桥接没有实现，因此多章节 patch 被压扁。

### 4.3 本地 Brainstorm 历史路径掩盖了公共物化层缺陷

本地 Brainstorm v1 直接返回 `TurnExecutionResult`，它已经完成：

- 规格节点选择
- 锚点计划
- 文档补丁应用
- 过程审计
- 下一轮交互

因此本地路径不会暴露 `OrchestratorRunResult -> TurnExecutionResult` 这一公共转换层的不足。

## 5. 设计原则

### 5.1 不按插件名写特殊分支

平台不得出现类似逻辑：

```python
if plugin_id == "brainstorm-v1-dify-workflow":
    ...
```

正确策略是按公共合同字段处理：

```text
如果 final_output.document_patch 非空：
  消费结构化 document_patch
否则如果 final_output.filled_document_text 非空：
  使用 filled_document_text 兜底生成单 patch
否则：
  不更新 working_document，仅保留交互和状态输出
```

这是合同分支，不是插件分支。

### 5.2 保持旧插件兼容

只返回 `filled_document_text` 的旧插件仍应可用。不能因为支持结构化 patch 而破坏当前 `xg-dify-workflow-orchestrator` 这类整篇文本样板插件。

### 5.3 本地 Brainstorm 短期不强行迁移

本地 Brainstorm v1 当前仍可保持原路径，避免在 Dify 修复中扩大变更范围。短期目标是修复公共物化层，长期目标才是统一所有组织器路径。

### 5.4 过程观测能力不因黑盒化丢失

黑盒化不等于状态不可见。组织器可通过公共字段暴露过程信息：

- `process_output.stage_audits`
- `process_output.decision_trace`
- `process_output.provider_logs`
- `state_output.decision_state_delta`
- `state_output.decision_state_document`
- `raw_output.raw_workflow_trace`

平台统一接收这些字段，不应要求平台了解组织器内部节点实现。

## 6. 升级目标

### 6.1 短期目标

修复 `PluginTurnResultMaterializer`，使所有黑盒插件都能按公共合同落入 `P2` 状态：

1. 优先消费 `final_output.document_patch`。
2. 自动补齐缺失的 `plan_ref`。
3. 自动生成或补齐 `target_anchor_plan`。
4. 让 `WorkingDocumentService` 按章节生成多个 block。
5. 保留 `filled_document_text` 单 patch 兜底能力。

### 6.2 中期目标

收敛组织器接入路径：

1. 本地 Brainstorm v1 adapter 逐步改为输出标准 `OrchestratorRunResult`。
2. 平台统一通过公共物化层生成 `TurnExecutionResult`。
3. 本地 Brainstorm 的完整过程数据通过 `process_output` 和 `state_output` 暴露。
4. 平台不再依赖本地组织器直接构造内部会话状态。

### 6.3 长期目标

形成真正可插拔组织器模型：

```text
插件目录
  -> manifest
  -> adapter
  -> 标准 OrchestratorRunResult
  -> 平台统一物化
  -> P2 会话状态
```

平台只认识插件合同，不认识插件内部阶段。

## 7. 方案设计

### 7.1 `document_patch` 标准化策略

新增或调整物化层内部标准化逻辑：

```text
输入：plugin_model_output.document_patch
输出：normalized_document_patch, target_anchor_plan
```

处理规则：

1. 忽略非 dict patch。
2. 忽略 `content` 为空的 patch。
3. `operation` 缺失时默认为 `append_or_update`。
4. `write_policy` 缺失时使用 session.write_policy。
5. `plan_ref` 缺失时生成稳定编号，例如 `AP-PLUGIN-001`、`AP-PLUGIN-002`。
6. `anchor_path` 优先级：
   - patch.anchor_path
   - patch.target_section
   - active_spec_node.node_id 去掉 `SPEC-`
   - `REQ-1.1`
7. `display_heading` 优先级：
   - patch.target_section
   - patch.display_heading
   - anchor_path
   - active_spec_node.target_section
8. 每条 patch 都要有对应 `target_anchor_plan`。

### 7.2 `target_anchor_plan` 生成策略

当插件未显式返回 `target_anchor_plan` 时，物化层按 patch 生成：

```json
{
  "plan_id": "AP-PLUGIN-001",
  "decision_type": "append_existing_clause",
  "template_clause_id": "REQ-3.2",
  "canonical_clause_heading": "3 功能需求 / 核心业务流程",
  "display_heading": "3 功能需求 / 核心业务流程",
  "anchor_path": "REQ-3.2",
  "reason": "由组织器插件 document_patch 自动物化。",
  "confidence": "medium"
}
```

如果 patch 的 `anchor_path` 是中文章节路径，例如 `3 功能需求 / 核心业务流程`，也可以直接作为 `anchor_path` 使用。`WorkingDocumentService` 已支持按中文路径生成 block 排序和标题。

### 7.3 `filled_document_text` 兜底策略

只有在 `document_patch` 为空时，才使用旧逻辑：

```json
{
  "plan_ref": "AP-PLUGIN-001",
  "operation": "append_or_update",
  "content": "filled_document_text",
  "write_policy": "patch_suggestion_only"
}
```

该兜底 patch 仍挂到当前活动规格节点，保证旧插件行为不变。

### 7.4 状态输出策略

物化层应继续保留：

- `assistant_message`
- `next_interaction`
- `quick_options`
- `decision_trace`
- `stage_audits`
- `confirmed_facts_delta`
- `open_questions_delta`
- `raw_plugin_response`

修改范围只应聚焦在：

- `spec_execution.document_patch`
- `spec_execution.target_anchor_plan`
- `spec_execution.affected_spec_nodes`
- `spec_execution.working_document_update`
- `state_patch.document_patch`
- `state_patch.working_document`

## 8. 回归风险与防护

### 8.1 对本地 Brainstorm v1 的风险

短期修改理论上不应影响本地 Brainstorm v1，因为它当前直接返回 `TurnExecutionResult`，不经过 `PluginTurnResultMaterializer`。

但这不能作为“严格解耦完成”的证据，只能说明短期改动风险边界较小。

防护措施：

- 保留本地 Brainstorm 现有测试。
- 增加架构保护测试，确保本次修改不触碰本地 Brainstorm adapter 和 runtime 行为。
- 中期迁移前单独设计本地 Brainstorm 标准输出改造方案。

### 8.2 对旧 Dify 样板插件的风险

`xg-dify-workflow-orchestrator` 当前可能只返回 `filled_document_text`，不返回结构化 patch。

防护措施：

- 保留 `filled_document_text` 兜底。
- 增加测试验证无 `document_patch` 时仍生成单 patch。

### 8.3 对真实 Dify 插件的风险

真实 Dify 可能返回：

- patch 有 `target_section` 但没有 `anchor_path`
- patch 有 `anchor_path` 但没有 `plan_ref`
- patch 有空 content
- patch 顺序不稳定

防护措施：

- 按合同字段补齐。
- 忽略空 content。
- 使用 patch 顺序生成稳定 plan id。
- 不因单条无效 patch 影响其他有效 patch。

### 8.4 防止重新引入插件名分支

应增加架构 guard：

- `PluginTurnResultMaterializer` 中不得按具体 `plugin_id`、`orchestrator_id` 做逻辑分支。
- 允许读取 `result.plugin` 用于记录和审计，不允许用于决定 patch 物化行为。

## 10. 验收标准

本升级完成后，至少满足：

1. `PluginTurnResultMaterializer` 不按插件 ID 写特殊逻辑。
2. 插件返回多章节 `document_patch` 时，P2 保留多条 patch。
3. `working_document.blocks` 按章节生成多个 block。
4. 插件只返回 `filled_document_text` 时，旧兜底行为仍可用。
5. 本地 Brainstorm v1 回归测试不退化。
6. 真实 Dify workflow 复测通过。
7. 正式测试记录已更新。

## 11. 当前建议结论

当前问题应定义为：

```text
平台组织器插件输出物化层未完整消费公共合同字段 document_patch。
```

不应定义为：

```text
Dify 插件需要平台写专用适配逻辑。
```

建议先执行短期修复：升级 `PluginTurnResultMaterializer` 的合同级物化能力，同时通过测试约束“不按插件名分支”。待 Dify 链路稳定后，再单独规划本地 Brainstorm v1 统一输出标准 `OrchestratorRunResult` 的中期改造。
