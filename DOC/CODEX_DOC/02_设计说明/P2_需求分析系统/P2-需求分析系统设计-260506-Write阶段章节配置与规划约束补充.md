# P2-需求分析系统设计-260506-Write阶段章节配置与规划约束补充

> 本文件是 `P2-需求分析系统设计.md` 的独立补充方案。  
> 本文件当前只回答一个问题：`write` 阶段如何在不依赖 Python 硬编码业务判断的前提下，稳定完成“章节定位、章节细化、正文 patch 生成、章节复核”的闭环。

## 1. 补充目标

本补充专门解决当前 `P2 XG 需求分析组织器 Lab` 中临时正文章节锚点不稳定的问题。

当前问题并不是前端显示层单独造成的，而是后端存在三类混用来源：

1. 模型在 `document_patch.section` 中输出自由文本章节名；
2. 宿主将自由文本章节名直接写入 `working_document.blocks.anchor_path`；
3. 显示层再用局部编号推断规则把部分锚点转成 `1.1 / 2.4`，未命中的锚点继续显示为 `章节 / 小节`。

这会导致同一份临时正文中同时出现：

- `1 总则 / 背景`
- `1.1 编写目的`
- `2 总体描述 / 产品概述`
- `2.4 用户特征`

这类混搭不是可接受的设计结果。

本补充的目标是：

1. 明确“章节配置规则”是什么；
2. 明确这类规则应在 `write` 阶段如何被读取和使用；
3. 明确为什么“章节规划”不能由 Python 硬编码推断，也不宜拆成独立顶层阶段；
4. 明确 `write / review / Python` 三者在章节规划问题上的职责边界；
5. 为后续补回主设计文档和编码重构提供稳定依据。

## 2. 核心判断

### 2.1 章节规划属于 `write`，但必须成为 `write` 内部的独立对象

章节规划本质上是“本轮输入写到哪里、是补写、修订还是新增子主题”的业务决策，因此它属于 `write`。

但它不能继续作为 `write` 阶段里一段隐含思考混在正文 patch 中。  
它必须在 `write` 的输出协议中被单独显式化，否则会继续出现两个问题：

1. 模型一边发明章节，一边写正文，导致“写到哪里”和“写了什么”混成一团；
2. Python 宿主只能拿自由文本章节名去猜模板位置，最终被迫承接业务判断。

因此，本补充不建议把“章节规划”新增为一个独立顶层阶段，而是建议：

- 保持四阶段主链路不变；
- 在 `write` 阶段内部，把“章节规划”升级为一类明确输出对象；
- 让正文 patch 必须引用章节规划结果，而不允许再直接携带自由文本章节锚点作为权威身份。

### 2.2 为什么不把章节规划拆成独立顶层阶段

章节规划与正文生成之间是强耦合关系，不宜拆成两个顶层模型调用阶段。

如果拆成：

`intent -> chapter_planning -> write -> review -> next`

则会引入一个新的不一致来源：

1. `chapter_planning` 先决定写哪些章节；
2. `write` 在真正写正文时，又可能重新理解用户输入；
3. 规划目标与实际 patch 命中目标可能偏离；
4. 宿主必须再做“规划结果与 patch 是否一致”的解释型修正。

这会把问题从“模型自由发明章节”变成“模型前后两次调用对同一输入形成两套章节判断”。

因此，本补充的判断是：

- **章节规划在逻辑上必须独立定义；**
- **章节规划在执行上不应升格为独立顶层阶段；**
- **它应作为 `write` 阶段内部先产出的第一类对象，被同一轮 `write` 结果直接引用。**

换句话说：

- `write` 不是“直接写 patch”；
- `write` 是“先输出章节规划，再输出引用该规划的 patch”。

## 3. 章节配置规则是什么

### 3.1 章节配置规则不是一张自由文本小表

章节配置规则不是：

- Python 里写死的标题推断表；
- 前端临时根据 `章节 / 小节` 拆分得到的编号；
- 模型自己脑补的通用需求规格说明目录。

章节配置规则应当是一个由模板和组织器共同定义的结构化对象，本文称为：

`章节配置上下文（ChapterConfigurationContext）`

章节配置上下文必须保持模板无关。

也就是说，本设计不能假定所有需求规格模板都长得像 `81433`，也不能把 `81433` 的粗粒度章节形态当成全系统标准。  
不同模板可能有不同形态：

1. 有的模板章节较粗，只提供少量一级条款；
2. 有的模板章节较细，已经明确到二级或三级条款；
3. 有的模板允许在条款内新增子主题；
4. 有的模板结构非常刚性，不允许运行时新增任何章节或子主题；
5. 有的模板本身可编辑，当前会话应读取用户或配置台调整后的最新版本。

因此，`write` 不是“按固定模板范式写正文”，而是“先分析当前模板形态，再按当前模板形态允许的方式规划写入位置”。

### 3.2 章节配置上下文的组成

`ChapterConfigurationContext` 至少应包含以下内容：

| 字段 | 含义 | 来源 |
| --- | --- | --- |
| `template_id` | 当前会话绑定的模板编号 | 会话 |
| `template_sections` | 模板规定的顶层章节列表 | 模板配置 |
| `template_clauses` | 模板规定的一级条款列表 | 模板配置 |
| `canonical_clause_map` | `clause_id -> 标准标题/标准编号/标准锚点` | 模板配置 |
| `allowed_extension_profiles` | 每个模板条款允许细化的子主题类型或细化方式 | 模板配置或组织器策略 |
| `existing_subtopics` | 当前临时正文里已经形成的细化子主题 | 临时正文 |
| `numbering_policy` | 模板条款编号与子主题编号的显示规则 | 模板配置 |
| `forbidden_actions` | 本轮明确不允许的结构行为 | 组织器策略 |
| `template_shape_policy` | 当前模板形态约束，如粗粒度、细粒度、可扩展、刚性、可编辑 | 模板配置或会话配置 |
| `template_revision_policy` | 模板是否允许被本轮需求分析过程建议修订 | 模板配置或权限配置 |

### 3.3 章节配置规则的设计原则

章节配置规则必须遵守以下原则：

1. 顶层章节与一级条款由模板定义，不允许模型自由发明新的一级编号。
2. 如果模板本身较粗，可以允许在模板条款下面细化子主题，但细化必须挂靠合法父条款。
3. 细化子主题是“条款内部组织”，不是“发明新的模板一级条款”。
4. 章节显示编号必须来自规则对象，而不能来自 Python 的标题猜测。
5. 任意正文块都必须能追溯到一个模板条款父节点。

### 3.4 模板形态分析规则

在 `write` 阶段生成正文 patch 之前，模型必须先分析当前模板形态。

模板形态分析不是为了生成正文，而是为了确定本轮能以哪种方式组织章节。

推荐模板形态分类如下：

| 模板形态 | 含义 | `write` 中的处理方式 |
| --- | --- | --- |
| `fine_grained_fixed` | 模板已经给出足够细的条款，且不允许新增子主题 | 只能命中既有条款，不能新增子主题 |
| `fine_grained_extensible` | 模板条款较细，但允许在条款下新增细化说明 | 优先命中既有条款；必要时创建条款内子主题 |
| `coarse_grained_extensible` | 模板条款较粗，允许在条款下细化子主题 | 必须先选择父条款，再创建子主题 |
| `coarse_grained_fixed` | 模板条款较粗，但结构刚性，不允许新增子主题 | 只能在父条款下写正文，不得生成新标题 |
| `editable_template` | 模板本身允许被配置台或用户修订 | `write` 只能提出模板修订建议，不能在本轮直接改模板 |

### 3.5 可编辑模板与刚性模板的处理差异

如果当前模板是可编辑模板，`write` 可以输出两类结果：

1. 正文 patch：写入当前已生效模板允许的条款或子主题；
2. 模板修订建议：建议配置台新增、拆分、重命名或调整条款。

但模板修订建议不能在当前 turn 内自动变成已生效模板结构。  
否则会导致同一轮中“模板规则”和“正文写入规则”同时变化，后续审计无法判断正文到底遵守的是哪个版本的模板。

如果当前模板是刚性模板，`write` 不得新增子主题，也不得提出伪编号。  
即使用户输入中出现了“背景、范围、产品概述、用户特征”等细粒度内容，也只能把这些内容写入已有父条款正文中，不能把它们变成新的显示标题。

### 3.6 81433 模板只能作为当前案例，不是通用模板范式

当前默认 `81433` 模板的结构较粗，示意如下：

- `1 总则 / 编写目的`
- `2 项目概述 / 软件定位`
- `3 功能需求 / 用户与角色`
- `3 功能需求 / 核心业务流程`
- `3 功能需求 / 异常与补偿`
- `4 非功能需求 / 性能与可靠性`
- `5 验收准则 / 验收准则`

这意味着：

1. `81433` 的一级条款本身并不细；
2. 模型在交互中完全可能感知到“背景、范围、产品概述、用户特征”等更细的结构需求；
3. 这类细化不能直接变成新的模板一级条款；
4. 它们必须作为某个模板条款下的细化子主题存在。

例如：

- “背景”可以是 `REQ-1.1 编写目的` 下的子主题；
- “用户特征”可以是 `REQ-3.1 用户与角色` 下的子主题；
- “产品概述”可以是 `REQ-2.1 软件定位` 下的子主题。

但上述判断只适用于当前 `81433` 默认模板在“粗粒度且允许细化”策略下的案例。  
如果换成更细或更刚性的模板，`write` 必须重新根据该模板的 `ChapterConfigurationContext` 分析，不允许沿用 `81433` 的处理方式。

## 4. `write` 阶段如何使用章节配置规则

### 4.1 `write` 阶段的内部执行顺序

`write` 阶段内部应按下述顺序工作：

1. 读取 `IntentUnderstandingResult`；
2. 读取 `ChapterConfigurationContext`；
3. 分析当前模板形态，形成 `template_shape_assessment`；
4. 基于模板形态、当前模板条款和现有子主题，形成本轮章节规划；
5. 基于章节规划生成正文 patch；
6. 生成本轮简要解释；
7. 将“模板形态分析 + 章节规划结果 + patch”一起返回。

其中第 3 步、第 4 步和第 5 步都属于 `write`，但第 3 步和第 4 步的结果必须显式返回。

这意味着一次 `write` 模型调用内部必须按顺序完成：

`分析模板形态 -> 章节规划 -> 正文写入`

该顺序必须体现在输出 schema 中，而不能只写在 Prompt 自然语言说明中。

### 4.2 `write` 阶段内部必须区分三类写入动作

`write` 在章节规划时，至少要区分以下三类动作：

| 动作类型 | 含义 | 是否允许 |
| --- | --- | --- |
| `append_existing_clause` | 在已有模板条款下补充正文 | 允许 |
| `revise_existing_anchor` | 修订已有模板条款或已有子主题正文 | 允许 |
| `create_subtopic_under_clause` | 在合法模板条款下新增细化子主题 | 允许，但必须挂靠父条款 |

不允许的动作：

| 动作类型 | 原因 |
| --- | --- |
| `invent_new_template_clause` | 会破坏模板一级条款边界 |
| `invent_new_section_number` | 会把临时正文变成模型自由目录 |
| `rebind_patch_by_python_guess` | 会把业务判断退回到宿主硬编码 |

### 4.3 `write` 阶段必须先回答的业务问题

在真正写正文之前，`write` 必须先明确回答：

1. 本轮输入是补充已有条款，还是修订已有条款？
2. 如果是修订，修订的是已有模板条款，还是已有子主题？
3. 如果是新增，新增的是正文内容，还是新增子主题？
4. 如果新增子主题，它挂在哪个模板条款下面？
5. 如果当前模板太粗，本轮新增子主题的编号和显示名按什么规则生成？
6. 如果当前模板不允许新增子主题，本轮内容如何并入已有父条款？
7. 如果当前模板可编辑，哪些内容只是模板修订建议，哪些内容可以进入当前正文？

这些都属于 `write` 内部的模型判断，不应回退给 Python 做标题比对。

### 4.4 单次模型调用是否能稳定完成三步

“分析模板形态、章节规划、正文写入”在逻辑上是三个步骤，但它们都服务于 `write` 的同一个目标：生成符合当前模板规则的正文 patch。

因此，目标态优先采用单次 `write` 模型调用完成三步，前提是满足以下条件：

1. Prompt 明确要求模型按固定顺序输出；
2. 输出 schema 强制包含 `template_shape_assessment`、`target_anchor_plan` 和 `document_patch`；
3. `document_patch` 必须引用 `target_anchor_plan.plan_id`；
4. `target_anchor_plan` 必须引用 `template_shape_assessment` 的结论；
5. `review_after_apply` 必须复核三者是否一致。

如果模型在实践中不能稳定完成这三步，不能立刻把章节规划拆成每轮独立顶层阶段。  
更合理的降级路径是：

1. 将模板形态分析提升为会话级或模板级预处理结果；
2. 由宿主在启动会话时把模板配置渲染成 `ChapterConfigurationContext`；
3. 必要时允许模型在会话启动时生成一次 `TemplateShapeAssessment`；
4. 每轮 `write` 只读取已冻结的模板形态分析结果，再执行章节规划和正文写入。

这样既降低单次 `write` 调用的认知负担，又不会制造“每轮章节规划阶段与正文写入阶段互相偏离”的问题。

只有在以下情况同时出现时，才考虑把章节规划独立成顶层模型阶段：

1. 模板形态分析已经前置，但 `write` 仍无法稳定完成章节规划与正文写入；
2. `review` 多次发现章节规划错误而非正文质量错误；
3. 章节规划需要独立失败、独立重试、独立人工确认。

在此之前，章节规划仍应保持为 `write` 内部的第一类结构化产物。

## 5. `write` 阶段的新增输出对象

### 5.1 现有 `document_patch.section` 不再作为权威章节身份

现有结构的问题在于：

```json
{
  "section": "2 总体描述 / 用户特征",
  "content": "..."
}
```

这里的 `section` 是自由文本，宿主只能拿它做模糊匹配或回退。

这不应继续作为权威锚点。

### 5.2 目标输出结构

`write` 阶段应新增一个显式对象：

`target_anchor_plan`

推荐结构如下：

```json
{
  "template_shape_assessment": {
    "shape_type": "coarse_grained_extensible",
    "reason": "当前模板只提供较粗的一级条款，但章节配置允许在父条款下新增子主题。",
    "allowed_write_modes": [
      "append_existing_clause",
      "revise_existing_anchor",
      "create_subtopic_under_clause"
    ],
    "forbidden_write_modes": [
      "invent_new_template_clause",
      "invent_new_section_number"
    ]
  },
  "target_anchor_plan": [
    {
      "plan_id": "AP-001",
      "decision_type": "create_subtopic_under_clause",
      "template_clause_id": "REQ-3.1",
      "canonical_clause_heading": "3.1 用户与角色",
      "subtopic_action": "create",
      "subtopic_key": "user-profile",
      "subtopic_title": "用户特征",
      "display_heading": "3.1.1 用户特征",
      "template_shape_ref": "coarse_grained_extensible",
      "reason": "本轮输入主要补充角色类别、职责分工和使用方式，应挂在用户与角色下细化。",
      "evidence": [
        "MULT，多种角色（如分析师、审核员、管理员）",
        "固定工作站，单机离线"
      ],
      "confidence": "high"
    }
  ],
  "document_patch": [
    {
      "plan_ref": "AP-001",
      "operation": "append_or_update",
      "content": "系统面向分析师、审核员和管理员三类用户。"
    }
  ]
}
```

### 5.3 这个结构解决了什么问题

这个结构至少解决四个问题：

1. `write` 先说清楚“写到哪里”，再说“写什么”；
2. `document_patch` 不再引用自由文本章节名；
3. 宿主不再需要根据 `section` 去做业务猜测；
4. `review` 可以显式复核“章节规划是否合理、patch 是否服从规划”。
5. 模型必须先说明当前模板形态，再说明为什么本轮允许新增、修订或只能并入父条款。

## 6. 当前模板较粗时如何细化

### 6.1 细化不是发明新的模板一级编号

当模板条款较粗，而本轮输入需要更细组织时，允许创建“子主题”，但不允许发明新的模板一级条款。

例如：

- 不允许直接生成 `2.4 用户特征`，因为当前模板并不存在 `2.4` 这个一级条款；
- 允许在 `REQ-3.1 用户与角色` 下新增一个子主题 `3.1.1 用户特征`。

### 6.2 子主题的规则来源

子主题的创建与命名必须遵守当前章节配置规则：

1. 父条款必须是模板中存在的 `clause_id`；
2. 子主题编号由 `numbering_policy` 生成；
3. 子主题显示名必须由模型在 `write` 中明确给出；
4. 子主题是否允许创建，应由模板配置或组织器策略声明；
5. 宿主只验证其是否合法，不负责判断“这个子主题是否语义合理”。

如果 `template_shape_assessment.shape_type = coarse_grained_fixed`，则本节的子主题创建规则不启用。  
此时 `write` 只能把细粒度内容写入父条款正文，不能生成新的子主题标题。

如果 `template_shape_assessment.shape_type = editable_template`，则 `write` 可以同时输出模板修订建议，但正文 patch 仍必须遵守本轮开始时已经生效的模板结构。

### 6.3 子主题编号的目标口径

正文显示层应统一使用以下口径：

- 模板一级条款：`3.1 用户与角色`
- 该条款下细化子主题：`3.1.1 用户特征`
- 同一父条款下第二个细化子主题：`3.1.2 使用模式`

这样可以避免当前这种：

- 一部分显示为 `2.4`
- 一部分显示为 `2 总体描述 / 产品概述`

的混搭状态。

### 6.4 模板细化与模板扩展不是一回事

本补充只讨论“在模板条款内部细化子主题”的策略，不讨论直接扩展模板正式一级条款。

如果后续需要让 `81433` 本身从：

- `1 总则 / 编写目的`

扩展成：

- `1.1 编写目的`
- `1.2 背景`
- `1.3 适用范围`

那是模板配置本身的升级，不应由单轮 `write` 临时发明。

## 7. `review` 在这件事上负责什么

`review` 不负责第一次决定章节，但负责复核 `write` 的章节规划是否合理。

### 7.1 `review` 必须审查的两个层面

1. **章节规划层面**
   - `template_shape_assessment` 是否准确反映当前模板形态？
   - 本轮 patch 是否命中了合理父条款？
   - 新增子主题是否挂在了正确父条款下？
   - 是否出现“为了写内容而发明章节”的问题？
   - 如果模板刚性较强，是否错误创建了子主题？
   - 如果模板可编辑，是否把模板修订建议错误当成了正文结构？

2. **正文充分性层面**
   - 写入后的正文是否足以支撑该条款或子主题？
   - 是否还缺少关键事实？
   - 是否需要重写、收窄、回退到父条款合并表达？

### 7.2 `review` 的目标输出

`review` 至少应补充以下字段：

```json
{
  "template_shape_review": {
    "status": "acceptable | questionable | wrong_shape",
    "reason": "......"
  },
  "anchor_plan_review": {
    "status": "acceptable | questionable | wrong_target",
    "reason": "......",
    "affected_plan_refs": ["AP-001"],
    "suggested_reanchor": []
  }
}
```

注意：

- `review` 可以指出本轮章节规划不合理；
- `review` 可以要求下一轮继续补；
- `review` 不能自己重新生成新的正文 patch 并直接改写。

## 8. Python 宿主在这里到底能做什么

Python 宿主在章节规划问题上只做三类事情：

### 8.1 协议校验

例如：

1. `target_anchor_plan` 是否存在；
2. `plan_id` 是否唯一；
3. `document_patch.plan_ref` 是否都能命中一个已有 `plan_id`；
4. `template_clause_id` 是否存在于当前模板；
5. `decision_type` 是否属于允许枚举值。
6. `template_shape_assessment.shape_type` 是否属于允许枚举值。
7. `target_anchor_plan.template_shape_ref` 是否与本轮模板形态分析结果一致。

### 8.2 配置约束校验

这些校验并非硬编码业务判断，而是执行当前配置规则：

1. 某个 `template_clause_id` 是否允许创建子主题；
2. `numbering_policy` 是否允许生成 `3.1.1` 这类显示编号；
3. 是否命中了已存在子主题而不是重复新建。

这里的判断依据来自：

- 模板配置；
- 组织器策略；
- 当前工作文档状态。

而不是来自 Python 里写死的一张章节词表。

### 8.3 阻断与报错

如果 `write` 输出结构非法，宿主应：

1. 记录结构协议错误；
2. 中止本轮采纳；
3. 将失败原因写入调用日志和 turn 审计；
4. 不再偷偷使用回退规则去猜“模型想写哪里”。

换句话说，**不合法应阻断，不应靠宿主脑补修正。**

## 9. Prompt 资产应如何补充

### 9.1 `write` 的输入必须新增章节配置上下文

`write` 请求上下文中必须加入：

| 字段 | 说明 |
| --- | --- |
| `chapter_configuration_context` | 当前模板条款、允许细化规则、当前已存在子主题、显示编号规则 |
| `working_document_index` | 当前临时正文已存在的条款 / 子主题索引 |
| `intent_understanding_result` | 本轮真实意图 |
| `stage_task_definition` | 本轮写作任务定义 |
| `template_shape_assessment` | 如果会话级已经完成模板形态分析，则作为本轮 write 的前置上下文 |

### 9.2 `write.system.md` 必须新增的明确要求

`write.system.md` 应明确增加以下约束：

1. 不允许直接输出自由文本 `section` 作为最终权威锚点；
2. 必须先生成 `target_anchor_plan`；
3. 每个 `document_patch` 都必须引用一个 `plan_ref`；
4. 如果模板较粗，只能在合法父条款下新增子主题；
5. 不允许发明新的模板一级编号；
6. 不允许把“背景、范围、产品概述、用户特征”直接写成新的模板一级条款。
7. 必须先分析当前模板形态，不能把 `81433` 或任何单一模板形态当成默认范式。
8. 如果模板不允许新增子主题，必须把细粒度内容并入父条款正文。
9. 如果模板可编辑，模板修订建议必须与正文 patch 分开输出。

### 9.3 `review_after_apply.system.md` 必须新增的明确要求

`review_after_apply.system.md` 应新增以下约束：

1. 必须审查 `target_anchor_plan` 与应用后正文是否一致；
2. 必须审查 `template_shape_assessment` 是否符合当前模板形态；
3. 必须指出本轮章节规划是否合理；
4. 如果章节挂靠错误，应明确指出错误原因；
5. 如果模板形态分析错误，应把它和正文质量问题区分开；
6. 不允许自己重新编造新的 patch；
7. 不允许把章节规划错误偷偷吞掉，只给“正文还不够”这类模糊结论。

## 10. 本补充的最终设计结论

### 10.1 结论一：章节规划不能再留在 Python 硬编码里

Python 宿主不应再根据：

- `背景`
- `范围`
- `产品概述`
- `用户特征`

这类中文标题去硬猜它们对应哪个模板条款，也不应继续靠硬编码词表把部分标题投影成 `2.4`。

### 10.2 结论二：章节规划不应新增为独立顶层阶段

它与正文生成高度耦合，拆成独立顶层阶段会引入“规划结果与实际写入偏离”的新问题。

### 10.3 结论三：章节规划必须成为 `write` 内部的第一类输出对象

`write` 必须从：

“直接输出正文 patch”

升级为：

“先输出章节规划，再输出引用该规划的正文 patch”

### 10.4 结论四：模板粗粒度不等于禁止细化

如果模板较粗，是否可以细化取决于当前模板形态和章节配置规则，而不是由 `81433` 的案例决定。  
在允许细化的模板中，细化必须：

1. 挂靠合法父条款；
2. 按章节配置规则生成子主题编号；
3. 不能伪装成新的模板一级条款。

在不允许细化的模板中，模型必须把细粒度内容并入父条款正文。  
在可编辑模板中，模型可以提出模板修订建议，但不能在本轮直接把建议当成已生效结构使用。

### 10.5 结论五：Review 要复核章节规划，但不替代章节规划

`review` 负责复核，不负责第一次做章节定位。  
如果把章节定位推给 `review`，系统会退化成“先乱写，再回头解释”的补救模式。

## 11. 本补充对后续主文档修订的影响

如果本补充被确认合理，则后续主文档至少需要补回以下位置：

1. `6.6.4 轮次执行设计`
   - 明确 `write` 阶段内部包含“章节规划 -> patch 生成”的结构；

2. `6.6.5 阶段运行时上下文与结果对象`
   - 新增 `ChapterConfigurationContext`；
   - 新增 `TemplateShapeAssessment`；
   - 新增 `target_anchor_plan`；

3. `6.6.6 模块接口设计`
   - 明确 `write` 输出协议从自由文本 `section` 升级为 `plan_ref` 引用；

4. `6.6.7 内部功能组成与类划分`
   - 说明由哪个子模块组装章节配置上下文；
   - 说明由哪个子模块校验 `target_anchor_plan`；

5. Prompt 与 Schema 相关设计章节
   - 为 `write` 和 `review_after_apply` 增补新的输入输出约束。

## 12. 本补充的验收判断

如果该策略被真正落地，则应能满足以下判断条件：

1. 临时正文块的权威锚点不再是自由文本章节字符串；
2. 任何正文 patch 都必须显式引用一个章节规划对象；
3. 当前会话中不会再因为缺少模板形态分析而同时出现：
   - `2 总体描述 / 产品概述`
   - `2.4 用户特征`
   - `3.1 用户与角色`
   这类无规则混搭；
4. 模板粗粒度且允许细化时，可以产生 `3.1.1 用户特征` 这类子主题；
5. 模板粗粒度但不允许细化时，不会产生新的子主题标题；
6. 模板可编辑时，模板修订建议与本轮正文 patch 分开表达；
7. 这类子主题必须能追溯到合法父条款；
8. Python 宿主可以校验结构合法性，但不再负责章节语义猜测；
9. `review` 能明确指出“模板形态判断错误”“章节挂靠错误”和“正文写得不够”是三类不同问题。
