# P2-需求分析系统设计-260505-Lab临时正文驱动补充

> 本文件是《P2-需求分析系统设计.md》的评审前补充详设，目标是解决当前 `P2 XG 需求分析组织器 Lab` 中“只有完成度树与 patch 建议、没有真实需求规格正文工作面，导致组织器只能机械推进而无法围绕正文闭环判断”的问题。
>
> 本文件只描述目标态补充设计，不描述实现步骤；待评审通过后，再将稳定结论归并到《P2-需求分析系统设计.md》的第五章和第六章。

**日期：** 2026-05-05

## 1. 补充背景与问题界定

### 1.1 当前失配点

当前 Lab 已经具备以下中间产物：

- `document_patch`
- `questions`
- `facts`
- `patches`
- `spec_tree`
- `next_interaction`
- `turn_audit`

但这些对象仍停留在“结构化过程产物”层面，没有被组织成一个可阅读、可审查、可回看的**临时需求规格正文**。

当前系统的主要问题不是“有没有 patch”，而是“patch 之后用户仍看不到一个真正的需求规格说明草稿”。这会直接导致四个失配：

1. 用户看不到“本轮到底把正文写成了什么样”。
2. 组织器无法基于正文质量做回看，只能基于 patch 是否存在做机械判断。
3. 完成度树被误当成主证据，而不是辅助证据。
4. 当前 Lab 的临时正文模型仍偏向“章节卡片 / 条块展示”，而不是“真实文档工作面”。

### 1.2 本次补充要解决的问题

本次补充不改变 Lab 的定位。Lab 仍然不是正式需求规格说明编辑器，也不直接产出冻结版文档。

本次补充要解决的是：

```text
让 Lab 在会话内部维护一份真实可阅读的临时需求规格正文，
并让组织器围绕这份正文做：
  写入
  回看
  闭环判断
  下一轮交互设计
```

### 1.3 补充后的判断标准

补充完成后，Lab 的一轮执行不应再被理解为：

```text
用户输入 -> 生成 patch -> 命中树节点 -> 继续提问
```

而应被理解为：

```text
用户输入
  -> 生成正文候选补写
    -> 写入临时正文
      -> 围绕临时正文回看
        -> 更新问题树和节点状态
          -> 形成下一轮沟通设计
```

## 2. 核心设计结论

### 2.1 临时正文是 Lab 的主证据面

补充后的证据层级应调整为：

```text
第一证据：临时正文 working_document
第二证据：目标范围回看结果 target_review
第三证据：全局回看结果 global_review
第四证据：需求规格完成度树 spec_tree
第五证据：沟通路径与当前轮次审计 turn_audit
```

其中：

- **临时正文**负责证明“系统实际写出了什么”。
- **目标范围回看**负责判断“本轮补写是否已经足够”。
- **完成度树**只负责显示“哪些条款已覆盖、哪些仍待确认”。

### 2.2 临时正文必须与真实需求规格正文同构

Lab 中的临时正文，不允许再设计成一套独立的“章节卡片式工作面”。

它必须与专家工作台右侧的标准需求规格正文保持**同构**：

- 同样是文档形态；
- 同样按需求规格说明的章节与条款自然排布；
- 同样以连续正文为主；
- 差异只在于：Lab 额外显示修订痕迹和审计联动。

换言之：

```text
Lab 临时正文 = 带审计和修订痕迹的需求规格说明草稿
```

而不是：

```text
若干章节摘要卡片
```

### 2.3 主视图必须是 A4 连续正文，不是章节卡片

临时正文的前端主视图必须模拟 Word 式文档工作面：

- 采用 A4 纸样式页面；
- 多页时纵向连续堆叠；
- 页面中展示真实需求规格正文；
- 用户第一眼看到的是“这是一份文档”，而不是“这是几个章节块”。

章节和条款仍然存在，但它们只作为**内部锚点**与**定位索引**存在，不再作为主界面布局单元。

### 2.4 修订展示采用“页边标注 + 正文轻微高亮”

临时正文采用如下修订呈现规则：

1. 正文区只显示**当前有效文本**。
2. 不显示被替换前的旧文本。
3. 每一轮新增或改写的位置，使用**轻微高亮**标识。
4. 同时在页边显示**修订标记**。
5. 若同一轮命中多个位置，则每个位置各自显示一个页边标记。
6. 同一轮的多个页边标记共享：
   - 同一 `turn_id`
   - 同一颜色标识
   - 同一审计来源

这对应用户已经确认的表现方式：

```text
Word 修订痕迹那种页边标注 + 正文轻微高亮
```

### 2.5 完成度树退为辅助视图

完成度树继续保留，但只承担以下职责：

- 展示模板条款结构；
- 展示当前焦点节点；
- 展示节点状态；
- 辅助解释临时正文已覆盖了哪些条款；
- 辅助解释下一轮为何还要继续追问。

完成度树不再承载“正文够不够”的主判断。

## 3. 前端补充设计

### 3.1 会话摘要区的主次关系调整

当前 `会话摘要 / 过程产物` 区域，应从“以完成度树为主”调整为“以临时正文为主”。

目标结构调整为：

```text
会话摘要 / 过程产物
  -> Tab 1：临时正文（默认主视图）
  -> Tab 2：需求规格完成度树
  -> Tab 3：沟通路径
```

其中：

- 默认进入 `临时正文`；
- 完成度树按需查看；
- 沟通路径保留，但不再挤占正文工作面。

### 3.2 临时正文工作面的目标形态

临时正文工作面应表现为一个连续的文档阅读与审查界面，而不是“分章节卡片”。

推荐结构如下：

```text
working_document_view
  -> 文档页栈（A4）
    -> 页面头
      -> 文档标题
      -> 模板标识
      -> 会话课题
    -> 文档正文
      -> 标题块
      -> 条款标题块
      -> 正文段落块
      -> 列表块
      -> 表格占位块（如后续需要）
    -> 页边修订标记层
```

这里的关键点是：

1. 主工作面是**整份文档**。
2. 文档内部当然有章节、条款和段落，但这些是正文结构，不是界面卡片。
3. 一轮补写可以同时影响多个正文位置，允许跨章节命中。

### 3.3 修订标记交互规则

页边修订标记的交互规则如下：

1. 标记绑定到正文中的具体命中位置。
2. 点击页边标记，弹出小型审计卡片。
3. 审计卡片必须至少显示：
   - `turn_id`
   - 用户输入摘要
   - 本轮补写原因
   - 命中的规格节点
   - 跳转到 `当前 Turn 审计` 的入口
4. 如果一个 `turn` 命中多个位置，则：
   - 每个位置各自显示页边标记；
   - 同色；
   - 同 `turn_id`；
   - 点击任一标记都能看到该位置对应的补写说明。

### 3.4 正文展示规则

临时正文的正文展示必须遵守以下规则：

1. 永远展示“当前生效版本”的正文。
2. 不在正文里显示删除线、旧文本或替换前文本。
3. 修订痕迹只通过：
   - 页边标记；
   - 轻微背景高亮；
   - 审计卡片；
   来表达。
4. 若用户不关心修订来源，直接阅读正文时，应能把它当作一份连贯的需求规格说明草稿来阅读。

### 3.5 完成度树视图的角色变化

完成度树视图仍然要保留，但它不再是“正文”的替代品。

完成度树只需要表达：

- 条款树结构；
- 节点状态，例如：
  - `open`
  - `partial`
  - `waiting_review`
  - `closed`
- 当前焦点节点；
- 当前节点与正文命中位置的关联。

完成度树不再负责直接展示补写后的正文内容。

### 3.6 当前轮次审计视图的补充

`当前 Turn 审计` 需要能解释“本轮为什么这样推进”，因此需要与临时正文联动。

建议审计项至少包括：

| 顺序 | 字段 | 含义 |
| --- | --- | --- |
| 1 | 上轮系统留题 | 上一轮留给用户的建议话题或明确问题 |
| 2 | 本轮用户输入 | 本轮原始输入 |
| 3 | 输入承接判断 | 本轮输入与上轮留题的关系 |
| 4 | 组织器理解 | 组织器如何解释这次输入 |
| 5 | 候选补写 | 本轮拟补写到正文的候选内容 |
| 6 | 正文应用结果 | 实际命中了哪些正文位置，写成了什么 |
| 7 | 目标范围回看 | 当前目标范围是否已经足够 |
| 8 | 全局回看 | 整体文档还缺什么 |
| 9 | 本轮闭环判断 | 为什么继续追问或为什么转移焦点 |
| 10 | 下一轮交互设计 | 下轮准备问什么、为什么问 |
| 11 | 决策依据链 | 规则、模型输出、正文状态、树状态的依据链 |

### 3.7 调用日志视图需要能看到正文上下文

调用日志中的 `Provider Request` 与 `Provider Response`，必须足以解释：

```text
模型本轮到底看到了哪部分正文
模型本轮对哪部分正文进行了补写或审查
```

因此，调用日志不应只停留在“用户输入 + prompt 字符串”，还需要能回放正文上下文。

## 4. 后端补充设计

### 4.1 临时正文对象模型重构方向

`working_document` 不应再按 `sections[]` 组织，而应按“连续文档 + 修订片段”组织。

建议结构：

```json
{
  "working_document": {
    "document_id": "lab-working-document",
    "title": "81433号需求规格说明（Lab 临时正文）",
    "template_id": "template-81433",
    "topic": "运算软件需求规格说明",
    "blocks": [
      {
        "block_id": "blk-0001",
        "anchor_path": "1.1/编写目的",
        "block_type": "paragraph",
        "order_index": 10,
        "text": "本规格说明用于定义运算软件的建设目标、适用范围和主要能力。",
        "last_turn_id": "turn-0001",
        "source_fragment_ids": ["frag-0001"]
      }
    ],
    "revision_fragments": [
      {
        "fragment_id": "frag-0001",
        "turn_id": "turn-0001",
        "color_token": "turn-color-01",
        "target_block_id": "blk-0001",
        "apply_mode": "append",
        "start_offset": 0,
        "end_offset": 30,
        "user_input_summary": "用户确认要建设运算软件需求规格说明",
        "supplement_reason": "补入编写目的的首句定义",
        "hit_spec_nodes": ["1.1", "1.2"]
      }
    ]
  }
}
```

其中：

- `blocks[]` 表示当前生效正文；
- `revision_fragments[]` 表示这些正文最近由哪些轮次补入；
- `anchor_path` 表示它在模板条款树中的定位锚点；
- `revision_fragments[]` 用于驱动页边修订标记和审计卡片。

### 4.2 章节只作为锚点，不作为正文主容器

需求规格说明仍然有章节和条款，但在后端模型中，它们不应再直接等同于前端工作面的“显示卡片”。

更准确的关系是：

```text
模板条款树
  -> 提供 anchor_path
    -> anchor_path 绑定到 working_document.blocks
      -> blocks 组成连续正文
        -> revision_fragments 记录轮次补写痕迹
```

因此：

- 章节是结构锚点；
- 正文块是显示与审查单元；
- 修订片段是来源追溯单元。

### 4.3 Patch 模型需要从“章节补丁”改为“正文片段操作”

`document_patch` 的目标不再是“给某章节塞一段内容”，而是“对正文指定位置执行补写或替换操作”。

建议操作类型至少包括：

- `insert_before_block`
- `insert_after_block`
- `append_to_block`
- `replace_range`
- `create_block_after_anchor`

示例：

```json
[
  {
    "patch_id": "patch-0003",
    "anchor_path": "2.1/软件定位",
    "target_block_id": "blk-0012",
    "operation": "append_to_block",
    "content": "首版聚焦运算能力与约束表达，不覆盖协同调度闭环。",
    "reason": "补入阶段边界"
  }
]
```

### 4.4 一轮执行链必须围绕正文展开

补充后的执行链应调整为：

```text
用户输入
  -> 输入解释
    -> 候选正文补写
      -> 应用到 working_document
        -> 生成 revision_fragments
          -> 目标范围回看
            -> 全局回看
              -> 更新完成度树
                -> 形成本轮闭环判断
                  -> 生成下一轮交互
```

这里的关键约束是：

1. `turn` 的起点是用户输入。
2. 组织器不能跳过“正文应用后回看”。
3. 完成度树更新发生在回看之后，而不是回看之前。

### 4.5 回看对象从“章节”改为“目标范围”

由于一轮补写可能跨多个位置，回看不应再硬编码为 `section_review`。

建议统一改为：

- `target_review`：本轮命中范围是否已形成可接受表达；
- `global_review`：整份临时正文从当前视角看还缺什么。

`target_review` 的判断对象可以是：

- 一个条款下的一个正文块；
- 同一条款下的多个正文块；
- 跨条款的一组命中片段。

示例：

```json
{
  "target_review": {
    "status": "insufficient",
    "review_target": [
      "1.1/编写目的",
      "1.2/适用范围"
    ],
    "reason": "已写入软件目标，但尚未明确不纳入范围的内容。",
    "missing_aspects": [
      "阶段边界",
      "排除项"
    ]
  },
  "global_review": {
    "status": "continue_same_topic",
    "summary": "仍需先补齐总则范围边界，再进入角色与使用场景。"
  }
}
```

### 4.6 完成度树的更新门禁

完成度树节点是否可以关闭，必须以后写入正文后的回看结果为门禁条件。

规则应调整为：

1. 若 `target_review.status == insufficient`，则：
   - 当前节点不得关闭；
   - 状态维持 `partial` 或 `waiting_review`；
   - 下一轮继续围绕当前缺口追问。
2. 若 `target_review.status == sufficient`，则：
   - 允许关闭当前节点；
   - 再由 `global_review` 决定是否转移到下一个节点。

### 4.7 后端子服务建议

围绕临时正文，建议补充三个明确的内部子服务：

#### 4.7.1 临时正文服务 `WorkingDocumentService`

职责：

1. 维护 `working_document.blocks`；
2. 执行 `document_patch`；
3. 生成 `revision_fragments`；
4. 维护块与锚点的映射关系；
5. 输出应用前后差异对象。

#### 4.7.2 临时正文回看服务 `WorkingDocumentReviewService`

职责：

1. 基于命中范围构建回看上下文；
2. 产出 `target_review`；
3. 产出 `global_review`；
4. 给出下一轮是否继续同一问题的判断依据。

#### 4.7.3 临时正文投影视图服务 `WorkingDocumentProjectionService`

职责：

1. 将 `working_document` 投影为前端可直接渲染的 A4 文档视图；
2. 生成正文块与页边修订标记的映射；
3. 生成页边审计卡片所需的摘要字段；
4. 供 `SessionTab` 与 `Current Turn` 共同复用。

## 5. 请求规划与提示词补充

### 5.1 提示词的目标要从“提问”转为“围绕正文补写与回看”

在这次补充后，模型的目标不能只剩下：

- 理解用户输入；
- 提一个下一轮问题。

它还必须参与：

- 把用户输入转成需求规格正文候选内容；
- 围绕候选内容解释为什么这样补写；
- 判断当前正文是否已经足够；
- 给出下一轮继续追问的依据。

### 5.2 组织器与大模型的职责边界

这里必须明确“什么由系统硬规则负责，什么由模型负责”。

#### 5.2.1 由组织器和系统规则负责

- `turn` 以用户输入作为起点；
- 上轮留题与本轮输入的承接关系记录；
- `document_patch` 应用到 `working_document`；
- `revision_fragments` 生成与颜色归组；
- `target_review` / `global_review` 的执行顺序；
- 完成度树状态更新门禁；
- 当前轮次审计链落盘；
- Provider 调用日志记录。

#### 5.2.2 由模型负责

- 解释本轮用户输入的真实意图；
- 生成正文候选补写内容；
- 生成补写原因与命中节点解释；
- 结合正文上下文判断当前是否足够；
- 生成下一轮建议话题或问题表述。

换言之：

```text
组织器负责流程和状态机，
模型负责理解、写作、审查和建议。
```

### 5.3 一轮中允许多阶段，但每阶段目标必须明确

建议把一轮内部多阶段明确为：

```text
interpret
  -> write
    -> apply
      -> review
        -> decide
```

其中：

- `interpret`：解释用户输入与上轮留题的关系；
- `write`：生成候选正文补写；
- `apply`：服务端把补写写入 `working_document`；
- `review`：围绕写入后的正文做目标范围回看和全局回看；
- `decide`：生成节点状态变化与下一轮交互设计。

这里允许：

- `apply` 为纯规则阶段；
- `decide` 为纯规则阶段；
- `review` 初版可由规则实现，后续也可换成模型。

### 5.4 Prompt Bundle 必须新增的正文上下文

无论是 `write` 还是 `review` 阶段，Prompt Bundle 都必须能提供正文上下文。

建议至少包含：

| 字段 | 含义 |
| --- | --- |
| `template_outline` | 当前模板条款骨架 |
| `working_document_json` | 当前临时正文全文快照 |
| `working_document_excerpt` | 与本轮目标最相关的正文摘录 |
| `review_target_paths` | 本轮重点条款锚点 |
| `previous_system_topic` | 上轮系统留题或建议话题 |
| `current_user_input` | 本轮用户原始输入 |
| `recent_revision_fragments` | 最近几轮的正文命中片段 |
| `open_questions` | 当前仍待确认的问题 |
| `review_goal` | 本轮 review 要检查什么 |
| `output_schema` | 当前阶段要求的输出契约 |

### 5.5 输出契约需要体现“正文命中位置”

在补充后的设计里，模型输出不能只告诉系统“写了什么”，还必须告诉系统“写到了哪里”。

因此候选输出至少应包括：

```json
{
  "candidate_patch": [
    {
      "anchor_path": "1.1/编写目的",
      "operation": "append_to_block",
      "content": "本需求规格说明用于定义运算软件首版的建设目标、范围边界和核心能力。",
      "reason": "根据用户明确的目标补入编写目的"
    }
  ],
  "candidate_open_questions": [],
  "candidate_next_interaction": {
    "mode": "question",
    "summary": "继续确认首版范围排除项"
  }
}
```

### 5.6 Review 输出契约需要围绕正文充分性

`review` 阶段的输出重点不应是“再编一遍摘要”，而应是：

```json
{
  "target_review": {
    "status": "insufficient",
    "review_target": [
      "1.1/编写目的",
      "1.2/适用范围"
    ],
    "reason": "目标已出现，但范围排除项仍缺失。",
    "missing_aspects": [
      "不纳入范围事项"
    ]
  },
  "global_review": {
    "status": "continue_same_topic",
    "summary": "总则仍未闭环，不建议进入下一大章。"
  }
}
```

## 8. 本补充的最终判断

本补充的最终判断只有两条：

1. Lab 不写正式正文没有问题，但必须写一份**与真实需求规格正文同构的临时正文**。
2. 组织器不能只围绕完成度树和 patch 机械推进，必须围绕这份临时正文做补写、回看、闭环和下一轮设计。
