# P2-需求分析系统设计-260505-Lab临时正文驱动补充

> 本文件是 `P2-需求分析系统设计.md` 的评审前补充详设，目标是解决当前 `P2 XG 需求分析组织器 Lab` 中“只有完成度树与 patch 建议，没有临时正文工作面，导致闭环判断依据不足”的问题。
>
> 本文件当前不直接并入主设计文档，先用于评审。评审通过后，再将稳定结论归并到《P2-需求分析系统设计.md》的第五章和第六章相关章节。

**日期：** 2026-05-05

## 1. 问题定义

### 1.1 当前问题

当前 Lab 的一轮执行，已经具备以下中间产物：

- `document_patch`
- `questions`
- `facts`
- `patches`
- `spec_tree`
- `next_interaction`
- `turn_audit`

但这些对象仍然停留在“结构化过程产物”层面，没有被进一步组织成一个可阅读、可审查、可回看的**临时需求规格正文**。

因此当前系统的闭环判断主要依赖：

```text
本轮是否生成了 patch
  -> patch 是否匹配到了完成度树节点
    -> 当前节点是否被关闭
      -> 是否切换到下一个节点
```

这会导致三个直接问题：

1. 用户看不到“本轮到底写进了什么正文”。
2. 系统无法基于正文质量做回看，只能基于 `patch` 是否存在做机械判断。
3. 完成度树被错误地当成了主证据，而不是辅助证据。

### 1.2 本补充的目标

本补充的目标不是让 Lab 写入正式需求规格说明文档，而是让 Lab 增加一个**会话内临时正文工作面**，作为：

- 一轮多次调用的中间判断依据；
- 用户审查组织器能力的主证据；
- 完成度树状态变化的来源依据；
- 当前 Turn 审计视图的回看对象。

## 2. 核心设计结论

### 2.1 证据层级重排

在新的 Lab 设计中，证据层级应当调整为：

```text
第一证据：临时正文 working_document
第二证据：章节级回看结果 section_review
第三证据：全局回看结果 global_review
第四证据：需求规格完成度树 spec_tree
第五证据：沟通路径与 Turn 审计
```

完成度树不再是“我写得够不够”的主依据，它只负责表达：

- 当前写到了哪个模板节点；
- 哪些节点已关闭；
- 哪些节点仍待确认；
- 当前焦点在哪个节点。

真正决定“这一轮是否足够”的依据，必须是：

```text
patch 应用后的临时正文是否已经形成可接受的章节表达
```

### 2.2 临时正文的定位

临时正文不是：

- 正式需求规格说明文档；
- 专家工作台右侧的标准正文；
- 可冻结文档；
- P3 可消费对象。

临时正文是：

- Lab 会话内部的工作草稿；
- 组织器多阶段推理的中间工作面；
- 用户观察组织器是否真的“在写东西”的证据面；
- 完成度树闭环判断的正文依据。

### 2.3 基本原则

1. Lab 允许写临时正文，但不写正式正文。
2. 一轮中允许多次调用模型或规则，但每次调用都必须围绕临时正文推进。
3. “先写 patch，再应用 patch，再回看正文，再决定是否闭环”必须成为固定执行顺序。
4. 关闭节点必须基于临时正文的章节级充分性判断，不能仅因为生成了 patch 就关闭。

## 3. 前端详设补充

### 3.1 会话摘要区重构目标

当前 `会话摘要 / 过程产物` 区块以完成度树为主，这不再满足要求。

目标形态调整为：

```text
会话摘要 / 过程产物
  -> Tab 1：临时正文（默认展开，主视图）
  -> Tab 2：需求规格完成度树（需要时切换查看）
  -> Tab 3：沟通路径（保留）
```

其中：

- 默认主视图必须是临时正文。
- 完成度树退为辅助视图。
- 沟通路径保留，但不再挤占临时正文主工作面。

### 3.2 页面结构调整

`SessionTab` 页面结构从：

```text
CLI 式问答区
  + 会话摘要 / 过程产物
    + 完成度树
    + 沟通路径
```

调整为：

```text
CLI 式问答区
  + 会话摘要 / 过程产物
    + 临时正文 Tab（默认）
    + 完成度树 Tab
    + 沟通路径 Tab
```

### 3.3 临时正文工作面结构

临时正文工作面建议结构：

```text
working_document
  - 文档标题（模板标题 + 会话课题）
  - 章节列表
    - 章节标题
    - 当前正文内容
    - 最近一次来源 patch
    - 最近一次回看状态
```

每个章节块建议显示：

| 区块 | 含义 |
| --- | --- |
| 章节标题 | 例如 `2 项目概述 / REQ-2.1 软件定位` |
| 当前正文 | patch 应用后的临时正文 |
| 最近来源 | 哪个 `turn_id`、哪个 `patch_id` 改了它 |
| 回看状态 | `待回看 / 仍不足 / 基本可接受 / 已关闭` |

### 3.4 完成度树的角色变化

完成度树保留，但职责变为：

- 显示模板节点结构；
- 显示当前焦点节点；
- 显示节点状态；
- 辅助对照临时正文已覆盖到哪些节点。

完成度树不再直接承载“足够不够”的主判断。

### 3.5 当前 Turn 视图补充

`Current Turn` 审计视图需要补充能够解释“为什么本轮判定关闭或继续”的正文依据。

新增审计项建议如下：

| 顺序 | 字段 | 含义 |
| --- | --- | --- |
| 1 | 上轮系统留题 | 上轮是否留题、留了什么 |
| 2 | 本轮用户输入 | 用户本轮原始输入 |
| 3 | 输入承接判断 | 用户输入与上轮留题的关系 |
| 4 | 写入候选 patch | 本轮先生成了哪些 patch |
| 5 | 临时正文应用结果 | patch 应用到哪个章节，应用后正文是什么 |
| 6 | 章节回看结果 | 当前章节是否已形成可接受表达 |
| 7 | 全局回看结果 | 对整体正文还缺什么 |
| 8 | 本轮闭环判断 | 为什么关闭 / 为什么继续追问 |
| 9 | 下一轮交互设计 | 下一轮问什么、为什么问 |
| 10 | 决策依据 | 规则、模型、当前草稿和节点状态的依据链 |

### 3.6 调用日志视图补充

调用日志中的 `Provider Request` 和 `Provider Response` 需要能够解释“本轮模型到底看到了什么正文”。

因此日志 schema 需要新增：

| 字段路径 | 含义 |
| --- | --- |
| `provider_request.prompt_bundle.working_document_json` | 本轮调用时带给模型的临时正文快照 |
| `provider_request.prompt_bundle.current_section_draft` | 当前焦点章节的正文草稿 |
| `provider_request.prompt_bundle.review_target` | 本轮回看要检查的章节或对象 |
| `provider_response.review_json` | 模型或规则给出的章节回看结果 |

## 4. 后端详设补充

### 4.1 会话状态新增对象

`RequirementAnalysisSession.payload` 需要新增 `working_document`。

建议结构：

```json
{
  "working_document": {
    "document_id": "lab-working-document",
    "title": "81433号需求规格说明（Lab 临时正文）",
    "sections": [
      {
        "section_id": "REQ-2.1",
        "target_section": "2 项目概述 / 软件定位",
        "content": "软件定位为：态势分析系统。",
        "source_patch_ids": ["P-001"],
        "last_turn_id": "turn-0001",
        "review_status": "insufficient",
        "review_reason": "已写出定位，但尚未明确领域边界与阶段不做事项。"
      }
    ]
  }
}
```

### 4.2 Turn 结果新增对象

`RequirementAnalysisTurn` 需要补充能表达临时正文应用与回看的对象。

建议新增：

```json
{
  "spec_execution": {
    "document_patch": [],
    "working_document_update": {
      "applied_section_ids": ["REQ-2.1"],
      "before": "...",
      "after": "..."
    }
  },
  "post_update_review": {
    "section_review": {
      "status": "insufficient",
      "reason": "定位已写入，但边界与阶段约束缺失。"
    },
    "global_review": {
      "status": "continue",
      "summary": "当前仍需围绕软件定位补齐边界和第一阶段不做事项。"
    }
  }
}
```

### 4.3 一轮执行链重排

当前执行链偏向：

```text
输入 -> patch -> 投影到树 -> 回看 -> 下一轮
```

目标执行链应调整为：

```text
输入
  -> 生成候选 patch
    -> 应用到临时正文
      -> 章节级回看
        -> 全局回看
          -> 更新完成度树
            -> 形成闭环判断
              -> 生成下一轮交互
```

也就是：

1. patch 不是最终判断对象；
2. 临时正文才是回看对象；
3. 完成度树在回看之后更新，不应在回看之前就机械关闭。

### 4.4 完成度树更新规则调整

当前风险在于：

```text
只要 patch 命中当前节点，就容易关闭节点
```

目标规则应改为：

```text
只有当 section_review.status == sufficient / acceptable
  才允许关闭当前节点
否则
  当前节点保持待确认或部分完成
```

建议新增状态：

- `open`
- `partial`
- `waiting_review`
- `closed`

其中：

- `partial` 表示已有正文草稿，但不够闭环；
- `waiting_review` 表示 patch 已应用，但尚未完成本轮回看。

### 4.5 临时正文应用服务

建议新增后端子服务：

```text
WorkingDocumentService
```

职责：

1. 将 `document_patch` 应用到 `working_document.sections`；
2. 维护章节内容；
3. 记录来源 patch、来源 turn；
4. 提供章节快照供 review 阶段使用；
5. 输出应用前后对比信息供 Turn 审计展示。

建议接口：

| 方法 | 输入 | 输出 |
| --- | --- | --- |
| `apply_patches` | `working_document`、`document_patch[]` | `working_document_update` |
| `get_section_snapshot` | `working_document`、`section_id` | `section_draft` |
| `build_review_context` | `working_document`、`active_section_id` | review 阶段上下文 |

### 4.6 回看服务

建议新增：

```text
WorkingDocumentReviewService
```

职责：

1. 检查当前章节是否已形成可接受表达；
2. 检查当前章节还缺哪些关键槽位；
3. 决定是否继续追问当前节点；
4. 给出全局回看摘要。

输出建议：

```json
{
  "section_review": {
    "status": "sufficient | insufficient",
    "reason": "...",
    "missing_aspects": ["边界", "第一阶段不做事项"]
  },
  "global_review": {
    "status": "continue_same_topic | move_next_node | whole_document_review",
    "summary": "...",
    "remaining_gaps": []
  }
}
```

## 5. 请求规划与提示词补充

### 5.1 当前问题

当前多阶段策略是：

```text
write -> review
```

但 `review` 阶段并没有针对“临时正文”做回看，它只是服务端生成一段复核摘要，仍然不是基于真实章节草稿做审查。

这就导致：

- 看似多阶段；
- 实际缺少“正文应用后回看”这一步。

### 5.2 目标多阶段策略

建议将启发式组织器的 Turn 策略明确为：

```text
write
  -> apply
    -> review
      -> decide
```

其中：

- `write`：生成候选 patch、事实、开放问题；
- `apply`：服务端将 patch 应用到 `working_document`；
- `review`：基于应用后的章节正文做充分性回看；
- `decide`：服务端根据 review 结果形成闭环决策和下一轮交互。

说明：

- `apply` 与 `decide` 可以是服务端规则阶段，不一定调用模型；
- `review` 可以先由服务端规则实现，后续再接模型。

### 5.3 Prompt Bundle 必须新增的上下文

如果 `review` 阶段调用模型，必须在 Prompt Bundle 中新增：

| 字段 | 含义 |
| --- | --- |
| `working_document_json` | 当前会话临时正文全文快照 |
| `current_section_draft` | 当前焦点章节正文草稿 |
| `current_section_target` | 当前章节在模板中的目标描述 |
| `current_section_question` | 当前章节当前要解决的问题 |
| `recent_patch_list` | 本轮候选 patch 列表 |
| `remaining_open_questions` | 会话仍待确认的问题 |
| `review_goal` | 本轮 review 的审查目标 |

### 5.4 Write 阶段输出约束

`write` 阶段输出不再直接被当成最终决策，而只是候选材料。

建议结构：

```json
{
  "organizer_interpretation": {},
  "candidate_patch": [],
  "candidate_facts": [],
  "candidate_open_questions": [],
  "candidate_next_interaction": {}
}
```

### 5.5 Review 阶段输出约束

`review` 阶段应聚焦正文充分性，而不是重新编整轮输出。

建议结构：

```json
{
  "section_review": {
    "status": "sufficient | insufficient",
    "reason": "...",
    "missing_aspects": []
  },
  "rewrite_advice": [
    {
      "section": "2 项目概述 / 软件定位",
      "operation": "replace_or_append",
      "content": "..."
    }
  ],
  "recommended_next_focus": {
    "mode": "continue_same_section | move_next_section",
    "reason": "..."
  }
}
```

### 5.6 Decide 阶段规则

`decide` 阶段必须使用如下规则：

1. 若 `section_review.status == insufficient`，则：
   - 不关闭当前节点；
   - 当前节点保持 `partial`；
   - 下一轮交互继续围绕同一章节缺口追问。

2. 若 `section_review.status == sufficient`，则：
   - 允许关闭当前节点；
   - 再根据 `global_review` 决定进入下一节点还是整体复核。
