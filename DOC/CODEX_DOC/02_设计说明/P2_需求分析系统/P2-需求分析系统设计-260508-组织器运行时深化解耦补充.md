## 1. 文档定位

`260507` 运行时真解耦补充和 `02.04` 实施已经解决了第一层关键问题：

1. 策略解释型组织器 adapter 不再创建数据库连接。
2. 策略解释型组织器 adapter 不再构造 `RequirementAnalysisSessionService`。
3. `xg-heuristic-orchestrator` 与 `brainstorm-v1` 不再各自复制一套阶段 runtime。
4. 两者共用宿主侧 `PolicyInterpretedRuntime`。
5. 阶段计划不再根据 `stage_id` 字符串推断 `stage_kind`。

但实施后仍能识别出更深一层的边界问题。本文用于把这些问题从“实施后发现的技术判断”提升为明确设计约束和后续研发依据。

本文讨论的是 `02.04` 之后的深化解耦，不否定 `02.04` 的完成状态。

## 2. 新识别问题

### 2.1 adapter 仍在构造会话快照

当前 `xg-heuristic-orchestrator` 与 `brainstorm-v1` 的 adapter 已不再构造数据库和会话服务，但仍在 `_session_snapshot()` 中把 `OrchestratorRunRequest` 转换成 `SessionSnapshot`。

这说明 adapter 仍然知道：

- session 字段如何映射到 `SessionSnapshot`；
- document context 中哪些字段进入 payload；
- payload 应补哪些默认字段；
- turn 历史、消息、工作文档、规格树等宿主状态槽如何命名。

这些内容不是组织器差异逻辑，而是宿主请求模型到运行时输入模型的转换逻辑。继续放在 adapter 中，会让每个插件复制一套宿主会话快照构造规则。

### 2.2 阶段归约器仍按业务阶段命名

当前 `TurnStageReducer` 已位于宿主 runtime 包，但其方法仍以业务阶段命名：

- `reduce_intent_stage`
- `reduce_decision_state_delta_stage`
- `reduce_write_stage`
- `reduce_review_stage`
- `reduce_next_interaction_stage`

这意味着通用 runtime 虽然不再按 `stage_id` 文本猜测阶段类型，但仍显式理解“意图理解、决策状态增量、Review、下一步交互”等业务阶段。

这种实现可作为过渡形态，但并不是理想的策略解释型 runtime。理想形态应由阶段的 `output_targets`、`adoption_id`、`schema_id` 和 `failure_policy` 驱动归约，而不是由 Python 方法名绑定业务阶段。

### 2.3 决策状态服务仍有插件目录副本

当前运行路径已经使用宿主侧：

```text
apps/api/app/orchestrators/runtime/decision_state_service.py
```

但以下插件目录中仍保留 `decision_state_service.py` 副本：

```text
orchestrators/xg/xg-heuristic-orchestrator/decision_state_service.py
orchestrators/xg/brainstorm-v1/decision_state_service.py
```

如果该服务只是结构化状态的机械合并、去重、规范化和展示渲染，则它属于宿主确定性基础设施，不应继续保留在插件目录。

如果某个组织器需要差异化的状态 schema 或状态合并策略，也不应通过复制 Python service 表达，而应通过显式 schema、adoption、state merge policy 等资产表达。

### 2.4 强规则组织器已移除

`xg-strong-rule-orchestrator` 最初作为本地 runner 对照路径保留。后续实现决策已明确：直接移除该组织器，不再作为需求分析系统的可选组织器或过渡例外。

移除后，需求分析组织器范围收敛为：

1. `xg-heuristic-orchestrator`
2. `brainstorm-v1`

## 3. 深化解耦目标

本阶段目标是把组织器 adapter 与宿主会话结构进一步隔离，并把阶段归约从“业务阶段专用函数”升级为“显式合同驱动的通用归约”。

目标态应满足：

1. 策略解释型 adapter 不再构造 `SessionSnapshot`。
2. `SessionSnapshot` 构造由宿主 runtime host 或专门的 request mapper 统一负责。
3. adapter 只承担插件入口适配和结果包装，不理解宿主 payload 内部槽位。
4. `PolicyInterpretedRuntime` 不再通过 `reduce_intent_stage` 等业务方法驱动阶段输出采纳。
5. 阶段输出采纳由 `output_targets`、`adoption_id`、`schema_id` 和阶段结果顺序驱动。
6. 决策状态服务副本完成归属判断；若属于机械基础设施，则删除插件副本并增加架构护栏。
7. 不再保留强规则组织器过渡路径，组织器宿主只维护启发式与 Brainstorm V1 两条需求分析链路。

## 4. 目标边界模型

### 4.1 adapter 目标边界

深化后的策略解释型 adapter 应只承担三项职责：

| 职责 | 说明 |
| --- | --- |
| 接收统一 `OrchestratorRunRequest` | 不自行解释宿主 payload 结构 |
| 调用宿主运行端口 | 例如 `runtime_host.run_policy_interpreted(request, manifest)` 或等价入口 |
| 包装统一 `OrchestratorRunResult` | 将 `TurnExecutionResult` 映射为插件合同输出 |

不应承担：

- `SessionSnapshot` 构造；
- payload 默认字段补齐；
- 会话状态槽位命名；
- 规格树、工作文档、消息历史的宿主结构映射；
- 数据库或会话服务生命周期管理。

### 4.2 宿主请求映射对象

应新增宿主侧请求映射对象，建议命名为：

```text
OrchestratorRunRequestMapper
```

职责：

```text
input:
  - OrchestratorRunRequest
  - OrchestratorPluginManifest

output:
  - SessionSnapshot
  - RequirementAnalysisTurnCreate

responsibility:
  - 统一读取 request.session / request.turn / request.document_context
  - 统一补齐 payload 默认字段
  - 统一填充 orchestrator_id / provider_id / model / template_id
  - 保证所有策略解释型插件看到同一种运行时输入
```

该对象属于宿主运行时基础设施，不属于组织器插件。

### 4.3 通用阶段归约对象

应把 `TurnStageReducer` 从业务阶段专用归约器升级为通用阶段归约器。

目标形态：

```text
StageResultReducer
  input:
    - TurnStagePlan
    - list[TurnStageResult]
    - stage output schema
    - adoption policy
  output:
    - stage_output_slots
    - adopted_output
    - stage_audit

  rule:
    - 只按 stage_id 定位阶段结果
    - 只按 output_targets 写入中间槽
    - 只按 adoption_id / adopt_fields 采纳字段
    - 不写 reduce_intent_stage / reduce_review_stage 这类业务方法
```

### 4.4 决策状态服务归属

决策状态服务应被拆分为两类职责：

| 职责 | 归属 | 说明 |
| --- | --- | --- |
| 状态 schema 定义 | 组织器资产或宿主通用 schema | 可由组织器声明差异 |
| 状态增量合法性校验 | 宿主 runtime | 确定性校验 |
| 状态机械合并、去重、编号 | 宿主 runtime | 不含业务语义判断 |
| 状态展示渲染 | 宿主 runtime / 前端视图模型 | 可配置展示形态 |
| 判断哪些事实该进入状态 | 模型阶段 | 不写入 Python 判断 |

如果当前插件副本只包含机械合并和渲染，则应删除。

## 5. 深化后的运行流程

策略解释型组织器运行流程应调整为：

```text
TurnEngine
  -> build OrchestratorRunRequest
  -> load adapter with runtime_host
  -> adapter.run(request)
      -> runtime_host.run_policy_interpreted(request, manifest)
          -> OrchestratorRunRequestMapper.build_runtime_input(...)
          -> PolicyInterpretedRuntime.run_turn(session_snapshot, turn_payload)
          -> StagePlanBuilder.build(...)
          -> for each configured stage:
               build StageRuntimeContext by input_sources
               execute stage by execution_mode
               validate output by schema_id
               reduce output by output_targets + adoption_id
          -> materialize TurnExecutionResult
      -> adapter wraps OrchestratorRunResult
```

关键变化是：

1. adapter 不再构造 `SessionSnapshot`。
2. runtime 不再调用业务命名归约函数。
3. 阶段输出进入统一 `stage_output_slots`。
4. 后续上下文从 `stage_output_slots` 按 `input_sources` 读取。

## 6. 允许硬编码与禁止硬编码边界

### 6.1 仍允许写在代码中的内容

以下仍属于确定性基础设施：

1. request 到 `SessionSnapshot` 的字段映射。
2. payload 默认槽位补齐。
3. stage 迭代顺序。
4. `stage_id` 唯一性校验。
5. schema 校验。
6. adoption 字段白名单过滤。
7. 输出槽位合并。
8. 状态增量机械合并。
9. 错误阻断、审计记录和调用日志生成。

### 6.2 不应写在代码中的内容

以下仍不应写在 Python 硬编码中：

1. 用户意图判断。
2. 章节匹配策略。
3. 哪个问题更值得追问。
4. 某个阶段输出是否“业务上足够好”。
5. Brainstorm 式启发追问策略。
6. 模板形态判断。
7. 某类组织器专有阶段链路。

## 7. 分阶段升级路径

### 7.1 阶段一：请求映射回宿主

1. 新增 `OrchestratorRunRequestMapper`。
2. 将启发式组织器和 Brainstorm V1 adapter 中 `_session_snapshot()` 迁入 mapper。
3. `runtime_host` 提供 `run_policy_interpreted(request, manifest)`。
4. adapter 不再导入 `SessionSnapshot` 和 `RequirementAnalysisTurnCreate`。
5. 增加架构测试，禁止策略解释型 adapter 出现 `_session_snapshot`、`SessionSnapshot`、`RequirementAnalysisTurnCreate`。

### 7.2 阶段二：归约器通用化

1. 新增 `StageOutputSlots` 或等价结构。
2. 新增 `StageResultReducer.reduce_stage(...)` 通用方法。
3. 按 `output_targets` 写槽，按 `adopt_fields` 采纳。
4. 将 `reduce_intent_stage`、`reduce_decision_state_delta_stage`、`reduce_review_stage`、`reduce_next_interaction_stage` 改为兼容层或删除。
5. 增加测试，断言新增阶段只需改 `spec_strategy.json` 和资产，不需要改 runtime 主流程。

### 7.3 阶段三：决策状态服务归属收口

1. 检查插件目录 `decision_state_service.py` 是否仍有运行时引用。
2. 若无引用，删除启发式和 Brainstorm V1 插件目录副本。
3. 增加架构护栏，禁止策略解释型插件目录保留 `decision_state_service.py`。
4. 若未来需要组织器差异化决策状态 schema，通过 schema/adoption/state policy 资产表达。

### 7.4 阶段四：移除强规则组织器残留边界

1. 删除 `xg-strong-rule-orchestrator` 插件目录。
2. 删除插件发现、运行时和 API 对该组织器的可见性。
3. 删除“强规则组织器作为过渡例外”的测试与文档表述。
4. 后续不再评估该组织器迁入策略解释型 runtime。

## 8. 验收标准

完成本深化阶段后，应满足：

1. `xg-heuristic-orchestrator/adapter.py` 和 `brainstorm-v1/adapter.py` 不再出现 `_session_snapshot`。
2. 策略解释型 adapter 不再导入 `SessionSnapshot`。
3. 策略解释型 adapter 不再导入 `RequirementAnalysisTurnCreate`。
4. request 到 runtime input 的映射集中在宿主 mapper。
5. 通用 runtime 不再暴露业务命名的 `reduce_*_stage` 作为主流程依赖。
6. 阶段输出采纳由 `output_targets` 和 `adoption` 驱动。
7. 策略解释型插件目录不再保留 `decision_state_service.py` 副本。
8. 强规则组织器不再出现在发现结果、API 可选项和运行时分支中。
9. 既有 P2 Lab mock provider 和 DeepSeek provider 测试不退化。

## 9. 风险与取舍

### 9.1 风险

1. 请求映射回宿主会影响所有本地策略解释型组织器入口，必须先加测试。
2. 归约器通用化容易把业务字段采纳逻辑改坏，需要先建立阶段输出槽位快照测试。
3. 删除 `decision_state_service.py` 插件副本前必须确认没有动态导入或测试引用。
4. 强规则组织器已删除，后续不再作为本地 runner 特例维护。

### 9.2 取舍

本阶段后续不再保留强规则组织器相关重构议题。原因是：

1. 需求分析组织器最终只保留启发式与 Brainstorm V1 两条有效链路。
2. 删除本地 runner 特例能直接减少宿主分支与测试负担。
3. 继续维护强规则链路不会为当前目标提供额外价值。

因此，本阶段不再要求强规则组织器保持可运行。

## 10. 评审关注点

请重点评审：

1. 是否同意 `SessionSnapshot` 构造属于宿主，不属于插件 adapter。
2. 是否同意 `TurnStageReducer` 的业务命名归约方法只是过渡形态。
3. 是否同意阶段输出应按 `output_targets/adoption` 通用采纳。
4. 是否同意删除策略解释型插件目录的 `decision_state_service.py` 副本。
5. 是否同意将强规则组织器从需求分析系统中完全移除。
