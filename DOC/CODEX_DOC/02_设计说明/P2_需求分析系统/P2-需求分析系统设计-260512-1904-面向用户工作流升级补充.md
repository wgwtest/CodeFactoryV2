# P2 需求分析系统设计 - 260512 面向用户工作流升级补充

**文档日期：** 2026-05-12

**文档性质：** 设计补充稿。本文用于梳理 `P2 需求分析系统` 从组织器 Lab 能力走向面向业务用户可用前端工具的升级方向，先作为待评审设计分析依据。待用户确认后，再决定是否回并到 `P2-需求分析系统设计.md` 或进入实施计划。

## 1. 背景与判断

当前 `P2` 的组织器 Lab、模板实例、Provider、Turn 协议、工作文档、调用日志和测试链路已经比较完整，能够支撑“需求分析能力验证”和“组织器效果比较”。但它还没有完全变成业务用户可以自然使用的前端工具。

用户当前提出的核心业务判断是：

```text
需求分析的正面入口应当是一个可管理的需求分析输入。
用户新建一个输入，系统围绕这个输入完成组织器配置、需求收敛、正文生成、检查和输出。
大体上是一条输入对应一个输出。
```

这个判断是成立的，但需要补一个关键区分：

```text
用户口中的“输入”不应等同于单条聊天消息，也不应等同于 Lab 会话。
它应是一个持久化的需求分析事项，承载标题、初始描述、领域知识、模板、组织器配置、分析过程和最终需求规格说明输出。
```

因此，面向用户的 `P2` 应从“先配置 Lab 再发起会话”升级为“先新建需求分析事项，再自动进入合适的分析工作台”。组织器、Provider、模板和审计日志仍然存在，但默认应退到系统配置和高级诊断层，不成为普通用户开始工作的第一步。

## 2. 真实用户工作流

### 2.1 工作对象

面向用户的正面工作对象建议定义为：

```text
需求分析事项
```

它代表用户希望系统分析的一次软件需求输入。一个需求分析事项至少包含：

| 字段 | 含义 |
| --- | --- |
| 事项标题 | 用户可识别的需求分析名称，例如“空域态势分析系统需求分析” |
| 初始描述 | 用户第一次输入的业务背景、目标、问题或已有材料摘要 |
| 领域知识绑定 | 来自 `P1` 发布态知识或联调模拟知识的知识包 |
| 需求规格模板 | 例如 81433 软件级需求规格说明模板实例 |
| 组织器配置 | 系统默认选择的组织器、Provider、模型和写入策略 |
| 分析过程 | 多轮 Turn、用户补充、组织器输出、过程审计和调用日志 |
| 工作文档 | 当前正在生成和修订的标准需求规格说明正文 |
| 最终输出 | 冻结后的需求规格说明和可交给 `P3` 的结构化包 |

“一条输入对应一个输出”在产品口径上应理解为：

```text
一个需求分析事项 -> 一个当前有效需求规格说明输出
```

同一事项内部可以有多轮对话、多个草稿修订和一次或多次冻结版本，但列表和业务入口上仍按一个事项管理。

### 2.2 主流程

真实用户主流程建议如下：

```text
进入 P2 需求分析首页
  -> 查看需求分析事项列表
  -> 新建需求分析事项
  -> 填写标题、初始描述，选择或默认绑定领域知识和模板
  -> 系统自动套用组织器配置档案
  -> 进入需求分析工作台
  -> 用户通过问答、表单或正文轻改持续补充需求事实
  -> 组织器维护语义状态、开放问题、正文 patch 和下一轮交互
  -> 工作台实时呈现需求规格说明草稿
  -> 用户运行缺口检查
  -> 用户确认并冻结
  -> 系统输出需求规格说明和 `P3` 可消费包
```

该流程中，用户可以随时保存、退出、重新打开、重命名、删除或归档事项。系统应保存当前进度，而不是要求用户记住某个 Lab 会话。

### 2.3 管理流程

需求分析首页需要支撑用户对事项的日常管理：

| 用户动作 | 目标 |
| --- | --- |
| 新建 | 创建一个新的需求分析事项，并自动创建默认工作文档和会话上下文 |
| 打开 | 继续编辑已有事项，恢复最新工作文档、语义状态和对话过程 |
| 重命名 | 修改事项标题，便于业务管理 |
| 保存 | 显式保存当前上下文；同时支持关键操作自动保存 |
| 删除 | 删除未冻结或不再需要的事项，首版可采用软删除或二次确认硬删除 |
| 归档 | 对已冻结或历史事项做非活跃管理 |
| 复制 | 可选，用已有事项生成一个新事项，便于相似需求复用 |
| 筛选 | 按状态、模板、知识包、更新时间和输出状态查找事项 |

### 2.4 高级配置流程

普通业务用户不应先面对组织器、Provider、模型和写入策略。推荐流程是：

```text
新建事项时默认套用“需求分析配置档案”
  -> 用户可直接开始分析
  -> 高级用户可展开“高级设置”
  -> 查看或切换组织器、Provider、模板实例和写入策略
  -> Lab 仍作为诊断入口保留
```

配置档案可以是：

| 配置档案 | 默认用途 |
| --- | --- |
| 标准需求分析 | 默认业务入口，追求稳定收敛和可读正文 |
| 强审计分析 | 对过程可追溯要求高时使用 |
| Dify 稳定成稿 | 外部工作流验证稳定时使用 |
| 本地规则验证 | 开发调试或无模型环境使用 |

## 3. 当前功能与真实工作流差异

### 3.1 现有能力概览

当前代码中已经存在三条相关能力线：

| 能力线 | 主要入口 | 当前特点 |
| --- | --- | --- |
| 结构化需求模型 | `/requirements`、`RequirementSpec` | 支持需求模型列表、新建、打开、保存，偏业务对象建模 |
| 专家需求规格编写工作台 | `/requirement-authoring`、`RequirementAuthoringDocument` | 支持文档新建、打开、删除、保存、问答、表单、缺口检查和冻结 |
| 需求分析组织器 Lab | `/p2-requirement-analysis-lab`、`RequirementAnalysisSession` | 支持模板、组织器、Provider、会话、Turn、工作文档、过程物化和日志 |

这些能力分别解决了不同问题，但尚未合成一个统一的业务用户工作流。

### 3.2 差异一：业务入口不统一

当前用户可能看到多个近似入口：

- `应用需求建模`
- `专家需求规格编写工作台`
- `P2 需求分析组织器 Lab`

它们分别对应模型、文档和组织器，但业务用户真正想管理的是“我要分析的这条需求输入”。如果入口不统一，用户会难以判断应该在哪个页面新建、在哪个页面继续、在哪个页面看输出。

目标态应把 `需求分析事项` 作为 P2 首页的统一入口，其他对象成为该事项下的内部资源。

### 3.3 差异二：Lab 配置暴露过早

`RequirementAnalysisLabPage` 当前先展示组织器配置、Provider、模板实例和启动参数，然后创建会话。这适合研发测试和组织器对比，但不适合业务用户。

面向业务用户时，系统应先让用户创建需求分析事项，配置由系统根据默认档案自动生成。用户只有在需要调试或比较效果时，才进入高级设置或 Lab。

### 3.4 差异三：组织器能力尚未成为用户工作台的默认执行引擎

`RequirementAuthoringPage` 已有较完整的用户工作台形态，包括新建、打开、删除、保存、问答、表单、文档预览、缺口检查和冻结。但当前问答执行仍偏规则示例逻辑，尚未稳定接入 `RequirementAnalysisSession`、Turn 协议、组织器输出、Provider 审计和 Lab 工作文档物化链路。

反过来，`RequirementAnalysisLabPage` 已有较强的组织器能力，但缺少用户事项列表、业务化 CRUD 和冻结输出工作流。

### 3.5 差异四：数据对象存在重叠

当前存在三个容易被用户或开发者混淆的对象：

| 对象 | 当前职责 | 缺口 |
| --- | --- | --- |
| `RequirementSpec` | 结构化需求模型和 P3 输入包的一部分 | 偏对象模型，不承载完整分析过程 |
| `RequirementAuthoringDocument` | 标准需求规格说明工作文档 | 用户工作台较完整，但组织器接入不足 |
| `RequirementAnalysisSession` | 组织器 Lab 会话和 Turn 状态 | 执行能力强，但不是业务列表对象 |

目标态不一定立即合并表结构，但必须在产品和接口层定义清楚：

```text
需求分析事项是用户入口。
RequirementAuthoringDocument 是事项的标准正文工作文档。
RequirementAnalysisSession 是事项的组织器执行会话。
RequirementSpec / frozen_package 是事项的冻结输出和下游交换包。
```

## 4. 升级方案比较

### 4.1 方案 A：以专家需求规格编写工作台为主入口，接入组织器执行链路

做法：

1. 保留 `/requirement-authoring` 作为面向用户的主工作台。
2. 在其文档列表和新建流程上强化“需求分析事项”概念。
3. 新建事项时自动创建或绑定 `RequirementAnalysisSession`。
4. 问答输入不再只走本地规则示例逻辑，而是调用组织器 Turn 执行链路。
5. 组织器输出的正文 patch、开放问题、决策状态和日志同步回工作文档。
6. Lab 保留为高级诊断页，可从事项进入查看同一会话的过程细节。

优点：

- 当前 `RequirementAuthoringPage` 已经具备最多业务用户所需动作。
- 文档预览、表单、缺口检查、冻结输出已经靠近目标态。
- 可以把 Lab 从“主入口”降回“高级诊断和研发验证入口”。
- 对用户认知最自然：用户从文档事项开始，而不是从组织器配置开始。

缺点：

- 需要打通 `RequirementAuthoringDocument` 与 `RequirementAnalysisSession` 的生命周期。
- 需要定义组织器 patch 如何写入正式工作文档，避免 Lab 工作文档和用户工作文档分裂。
- 需要补事项级状态和列表筛选能力。

结论：推荐作为主方案。

### 4.2 方案 B：把组织器 Lab 产品化，补齐事项 CRUD

做法：

1. 在 `/p2-requirement-analysis-lab` 前面新增事项列表和新建入口。
2. 新建事项后仍进入 Lab，但默认折叠组织器、Provider 和日志配置。
3. 在 Lab 内补齐保存、打开、删除、冻结输出和 P3 包生成。

优点：

- 能最大限度复用最新组织器能力。
- 短期可以较快把“新建输入 -> 启动会话”跑通。

缺点：

- Lab 页面当前信息密度和调试语义较强，业务用户会被内部概念干扰。
- 冻结、缺口检查和文档编辑能力会与 `RequirementAuthoringPage` 重复建设。
- 容易把研发验证入口误升级为正式业务入口。

结论：可作为过渡验证方案，不建议作为最终主入口。

### 4.3 方案 C：新增独立 P2 需求分析事项中心

做法：

1. 新建 `/requirement-analysis` 或 `/p2-requirements` 页面作为事项中心。
2. 事项中心统一编排文档、会话、模板、知识绑定和输出包。
3. 现有 `RequirementAuthoringPage` 和 Lab 都作为事项中心下的子视图或能力组件。

优点：

- 信息架构最干净。
- 可以从一开始按“事项”设计所有接口和状态。

缺点：

- 首版改动范围最大。
- 需要重新整合已有两个页面，短期容易产生第三套前端。
- 在现有工作台已经具备大量能力的情况下，投入产出比不如方案 A。

结论：适合作为中长期信息架构目标，不建议作为下一轮首要实现方式。

## 5. 推荐目标设计

推荐采用：

```text
方案 A 为主，方案 C 的“事项中心”概念作为产品信息架构目标，Lab 保留为高级诊断入口。
```

也就是说，下一轮不应直接把 Lab 改成业务系统，而应把用户工作流落在“需求分析事项 / 需求规格编写工作台”上，并把组织器能力接入其后台执行链路。

### 5.1 用户侧页面结构

目标页面结构建议如下：

```text
P2 需求分析
  需求分析事项列表
    - 新建事项
    - 打开事项
    - 重命名
    - 删除 / 归档
    - 状态筛选
  事项工作台
    - 事项基本信息
    - 问答输入
    - 表单校对
    - 标准需求规格说明正文
    - 缺口检查
    - 冻结输出
    - 高级设置
    - 组织器诊断
  组织器 Lab
    - 仅面向高级调试和组织器对比
```

首版可以复用 `/requirement-authoring` 作为事项工作台，不必立即新增第三个大页面。但页面标题和按钮文案应逐步从“文档”调整为“需求分析事项 / 需求规格说明”，降低用户理解成本。

### 5.2 新建事项流程

新建事项应采用轻量表单，而不是先进入 Lab 配置页：

| 字段 | 首版策略 |
| --- | --- |
| 事项标题 | 必填；默认“未命名软件需求规格说明” |
| 初始描述 | 可选但强烈推荐；如果填写，创建后自动作为首轮输入进入组织器 |
| 领域知识 | 默认使用当前 active archive；允许选择“不绑定” |
| 需求规格模板 | 默认选中已激活模板；允许切换 |
| 配置档案 | 默认“标准需求分析”；高级设置中可改 |

创建成功后系统自动执行：

```text
创建需求分析事项
  -> 创建 RequirementAuthoringDocument
  -> 绑定模板和领域知识
  -> 根据配置档案解析组织器、Provider、模型和写入策略
  -> 创建 RequirementAnalysisSession
  -> 如果有初始描述，自动提交首轮 Turn
  -> 打开事项工作台
```

### 5.3 事项状态机

建议事项状态机如下：

| 状态 | 含义 | 用户可执行动作 |
| --- | --- | --- |
| `draft_input` | 已新建，初始输入尚少 | 编辑、补充、删除 |
| `analyzing` | 正在通过问答或表单收敛需求 | 继续输入、保存、运行检查 |
| `draft_generated` | 已形成可读需求规格草稿 | 编辑、检查、继续补充 |
| `checking` | 正在或刚完成缺口检查 | 查看缺口、修补 |
| `ready_to_freeze` | 阻断缺口已处理 | 冻结、继续修订 |
| `frozen` | 已冻结正式输出 | 查看、导出、提交 P3、归档 |
| `submitted_to_p3` | 已提交给 P3 | 查看、归档 |
| `archived` | 已归档 | 只读查看、恢复 |

当前 `RequirementAuthoringDocument` 已有 `draft / checking / ready_to_freeze / frozen / submitted_to_p3 / archived`，可以作为首版承载基础。新增 `analyzing / draft_generated` 是否单独落库，可在实施计划中根据兼容成本决定。

### 5.4 后端对象关系

目标对象关系建议如下：

```text
RequirementAnalysisWorkItem
  -> RequirementAuthoringDocument
  -> RequirementAnalysisSession
  -> RequirementSpec / frozen_package
```

首版可有两种落地方式：

| 方式 | 说明 |
| --- | --- |
| 轻量方式 | 暂不新增表，以 `RequirementAuthoringDocument` 作为事项主表，在 `semantic_state` 中记录 `analysis_session_id`、配置档案和初始输入 |
| 稳定方式 | 新增 `RequirementAnalysisWorkItem` 主表，显式关联文档、会话和输出包 |

推荐首轮采用轻量方式，降低改造范围；当事项筛选、版本、多人协作、归档统计变复杂后，再升级为独立主表。

### 5.5 组织器接入方式

组织器应成为事项工作台的后台执行引擎：

```text
用户在事项工作台提交问答输入
  -> 前端调用事项级发送接口
  -> 服务端读取事项绑定的 RequirementAnalysisSession
  -> 调用组织器 Turn 执行链路
  -> 产出 spec_execution、document_patch、decision_delta、next_interaction
  -> 将可写入内容同步到 RequirementAuthoringDocument
  -> 返回更新后的事项详情
```

写入策略必须保留：

| 策略 | 行为 |
| --- | --- |
| `patch_suggestion_only` | 只形成建议和高亮，不直接覆盖正式正文 |
| `auto_draft` | 可自动写入草稿正文，但保留可回看修订来源 |
| `user_confirmed` | 用户确认后写入正文 |

面向业务用户的默认策略建议为 `auto_draft` 或“建议自动进入草稿但可撤回”。如果继续使用 `patch_suggestion_only`，用户会感到系统一直在分析但没有真正成稿。

### 5.6 Lab 的新定位

Lab 不应消失，但定位应调整为：

```text
组织器高级诊断台
```

它服务于：

- 组织器插件调试。
- Provider 调用排查。
- Dify 工作流对比。
- Turn 协议审计。
- 测试报告证据采集。

业务用户工作台可以提供“查看组织器诊断”入口，打开同一事项对应的 Lab 视图，但不要求普通用户先进入 Lab。

## 6. 下一轮升级范围建议

### 6.1 首轮最小升级

首轮建议只做能闭合用户主流程的内容：

1. 统一产品口径：将用户入口定义为“需求分析事项”。
2. 调整或扩展 `/requirement-authoring` 页面，使其列表和新建流程承载事项概念。
3. 新建事项时支持初始描述。
4. 新建事项后自动创建或绑定 `RequirementAnalysisSession`。
5. 问答输入接入组织器 Turn 链路，而不是只走本地规则示例逻辑。
6. 将组织器输出同步到当前标准需求规格说明草稿。
7. 保留缺口检查和冻结能力。
8. 提供高级诊断入口跳转到 Lab。

### 6.2 暂不纳入首轮

以下能力暂不建议首轮展开：

| 能力 | 原因 |
| --- | --- |
| 多人协作编辑 | 会引入权限、冲突和实时同步问题 |
| 多版本分支管理 | 当前只需保证一个事项有一个当前有效输出 |
| 完整导出 DOCX / PDF | 可以在冻结输出稳定后再做 |
| 新增独立事项中心大页面 | 现有工作台可先承载，避免第三套页面 |
| 复杂组织器配置市场 | 首轮用配置档案即可 |

## 7. 验收口径

升级完成后，至少应满足以下验收条件：

1. 用户可以在 P2 入口查看需求分析事项列表。
2. 用户可以新建、打开、保存、重命名、删除或归档一个事项。
3. 用户新建事项后，不需要理解组织器、Provider 和模型配置，也可以开始输入需求。
4. 系统能根据默认配置自动创建组织器会话。
5. 用户的首轮初始描述可以进入组织器 Turn 链路。
6. 组织器输出能反映到同一事项的标准需求规格说明草稿中。
7. 用户可以运行缺口检查并冻结需求规格说明。
8. 冻结结果能继续作为 `P3` 可消费输入。
9. 高级用户可以查看同一事项对应的组织器日志和 Turn 诊断。
10. 旧 Lab 能力不被删除，仍可用于组织器对比测试和过程证据采集。

## 8. 风险与控制

### 8.1 对象重复风险

风险：

```text
RequirementSpec、RequirementAuthoringDocument、RequirementAnalysisSession 三个对象都像“需求分析对象”。
```

控制：

```text
产品入口只暴露“需求分析事项”。
后端内部明确文档、会话、输出包的职责。
接口返回中避免让前端自行拼装多个对象的业务含义。
```

### 8.2 Lab 过度产品化风险

风险：

```text
直接把 Lab 加上 CRUD 后上线，会让用户面对过多内部配置。
```

控制：

```text
Lab 保持高级诊断定位。
业务入口隐藏组织器细节，只暴露配置档案。
```

### 8.3 “一输入一输出”过度简化风险

风险：

```text
真实需求分析可能需要多轮草稿、冻结版本和后续修订。
```

控制：

```text
产品上坚持一个事项对应一个当前有效输出。
内部允许保留修订历史和冻结版本。
```

### 8.4 自动写入质量风险

风险：

```text
组织器自动写入正文可能把未确认内容写成正式需求。
```

控制：

```text
首版保留写入策略和来源高亮。
关键章节可要求用户确认。
冻结前必须经过缺口检查和人工确认。
```

## 9. 设计结论

`P2` 下一步不应继续只扩展 Lab，也不应把业务用户入口建立在组织器配置页上。更合理的目标是：

```text
以需求分析事项为用户入口，
以需求规格说明工作台为主要工作界面，
以 XG 组织器为后台执行引擎，
以 Lab 作为高级诊断和测试证据入口。
```

这能把当前已经较成熟的组织器流程、模板体系、Provider 审计和工作文档能力转化为用户能理解的业务流程：新建一条需求分析输入，持续补充和收敛，得到一份可检查、可冻结、可交给 `P3` 的需求规格说明输出。
