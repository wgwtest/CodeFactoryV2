## 1. 本轮结论

本轮设计结论如下：

1. `P2` 面向用户的正面入口应补充 `需求规格说明管理` 页签，作为 `4.1`，放在现有组织器配置、会话、当前 Turn 和调用日志之前。
2. `4.1` 只承担需规对象列表和对象级动作，不合并 `4.2` 组织器配置，不恢复右侧“当前需规”详情面板。
3. 每条需规的主要行内动作收敛为 `进入配置` 和 `发布`。
4. `新建需规` 必须通过模态窗口完成，窗口只收集最小业务输入，不承载完整组织器配置。
5. `发布` 是 `P2 -> P3` 的边界动作，语义是冻结当前版本并生成 `P3` 可接收输入，不是普通导出按钮。
6. 发布后的版本默认不可直接编辑；后续修改应形成修订草稿或新版本，再重新发布。
7. 当前代码已经具备文档工作台、组织器 Lab 和结构化规格三条能力线，但还缺少把三者串成“需规对象”的统一产品入口和生命周期。

## 2. 当前代码事实

### 2.1 现有三条能力线

当前实现中与本设计相关的能力线如下：

| 能力线 | 前端页面 | API 路由 | 当前对象 | 当前职责 |
| --- | --- | --- | --- | --- |
| 组织器 Lab | `RequirementAnalysisLabPage` | `/requirement-analysis/*` | `RequirementAnalysisSession`、`RequirementAnalysisTurn` | 配置组织器、Provider、模板实例，启动会话，执行 Turn，展示结构化状态、临时正文、完成度树和 Provider 调用日志 |
| 需求规格编写工作台 | `RequirementAuthoringPage` | `/requirement-authoring/*` | `RequirementAuthoringDocument` | 新建 / 打开 / 删除 / 保存文档，问答模式，表单模式，条款批注，缺口检查，冻结版本和 `P3` 可消费包 |
| 结构化需求模型 | `RequirementsPage` | `/requirements/*` | `RequirementSpec` | 管理结构化需求对象、业务对象、流程、规则和非功能约束，服务下游结构化消费 |

这三条线都有效，但当前还不是一个统一的用户工作流：

- Lab 的入口先面对组织器配置，不先面对“我要管理哪份需规”。
- 需求规格编写工作台已经具备文档级 CRUD 和冻结能力，但组织器执行链路没有成为默认引擎。
- `RequirementSpec` 偏结构化交换对象，不适合作为普通用户直接编辑的主入口。

### 2.2 当前 Lab 页面事实

当前 `RequirementAnalysisLabPage` 的页面分工是：

| 当前页签 | 代码对象 | 当前说明 |
| --- | --- | --- |
| 组织器配置 | `ConfigTab` | 选择组织器、Provider、模板实例，编辑模板，启动会话 |
| 会话管理 | `SessionTab` | 展示消息、快捷选项、输入框、结构化状态、临时正文、完成度树和沟通路径 |
| 当前 Turn | `TurnTab` | 展示本轮输入理解、影响节点、patch、闭环判断、阶段审计和协议校验 |
| 调用日志 | `LogTab` | 展示 Provider / Runner 调用列表和调用详情 |

缺口是：当前 Lab 没有 `需求规格说明管理` 页签，也没有把 Lab 会话挂到一个用户可管理的需规对象下面。

### 2.3 当前工作台事实

当前 `RequirementAuthoringPage` 已经具备：

- `新建文档`
- `打开文档 / 草稿`
- `删除文档`
- `保存草稿`
- `问答模式`
- `表单模式`
- `缺口检查`
- `冻结版本`
- `P3 可消费` 状态提示

因此，目标设计不应重新发明一套完整文档编辑器。`4.1` 需规管理页签只补用户入口和对象生命周期；正文编辑、问答、检查和冻结能力应复用或对齐现有工作台能力。

## 3. 目标用户工作流

目标用户工作流为：

```text
进入 P2 需求分析系统
  -> 打开 4.1 需求规格说明管理
    -> 查看需规列表
    -> 新建需规
      -> 在模态窗口填写标题、初始说明、模板和创建后动作
      -> 系统创建需规对象，并自动准备默认组织器配置
    -> 进入 4.2 组织器配置
      -> 查看或调整模板、组织器、Provider、知识绑定和写入策略
    -> 进入 4.3 会话管理
      -> 通过问答或快捷选项持续补充需求事实
      -> 系统维护结构化状态、临时正文和完成度树
    -> 在 4.4 当前 Turn 和 4.5 调用日志中审计过程
    -> 运行缺口检查
    -> 发布
      -> 冻结当前版本
      -> 生成 P3 可接收包
      -> 列表状态变为 P3 可接收 / 已发布
```

该流程的产品口径是：

```text
一个需规对象 -> 一个当前有效的需求规格说明输出
```

同一个需规对象内部可以存在多轮会话、多次草稿修订和多个版本记录，但用户列表上仍按一个需规对象管理。

## 4. 页面职责分工

### 4.1 需求规格说明管理

`4.1` 是列表页，只负责对象级管理，不展示复杂详情面板。

页面内容：

| 区域 | 设计职责 |
| --- | --- |
| 顶部动作 | `新建需规`，可选搜索、状态筛选、刷新 |
| 列表列 | 需规名称、状态、模板、知识绑定、最近更新、P3 状态、操作 |
| 行内动作 | `进入配置`、`发布` |
| 空状态 | 引导用户新建第一份需求规格说明 |
| 发布态标识 | 对已发布版本显示 `P3 可接收` / `已发布` |

不可做的事：

- 不在右侧放“当前需规”大详情面板。
- 不在本页展开组织器、Provider、模板正文或调用日志。
- 不把 `打开 / 编辑 / 进入配置` 三个语义重复动作同时放在列表行内。

### 4.1.1 新建需规模态窗口

点击 `新建需规` 后弹出模态窗口。

首版建议字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 需规名称 | 是 | 列表主标题，也是默认工作文档标题 |
| 初始说明 | 否 | 用户对业务背景、目标、问题和已有材料的初始描述 |
| 需求规格模板 | 是 | 默认使用当前系统推荐模板，例如 81433 软件级需求规格说明模板实例 |
| 领域知识 | 否 | 可绑定 `P1` 发布态知识，也允许首版为空 |
| 创建后动作 | 是 | 默认 `创建并进入配置`，可选 `仅创建` |

新建窗口的边界：

- 只收集最小业务输入。
- 不在窗口中塞入完整组织器配置。
- 不要求用户理解 Provider、Runner、Turn、日志等内部概念。
- 创建成功后应形成一个可在 `4.1` 列表中看见的需规对象。

### 4.2 组织器配置

`4.2` 继续保持真实系统复杂度，不回退为简单选择器。

页面职责：

- 显示当前选中的需规对象上下文。
- 选择或确认组织器。
- 选择或确认模型 Provider。
- 选择或编辑模板实例。
- 选择写入策略。
- 创建或恢复当前需规对象下的分析会话。

`进入配置` 的语义是：进入当前需规对象的组织器配置工作台。它不是单纯“打开文档”，也不是直接跳到发布态详情。

### 4.3 会话管理

`4.3` 是当前需规对象下的需求分析会话页。

页面职责：

- 展示该需规对象绑定的 `RequirementAnalysisSession`。
- 支持用户发送输入和选择快捷选项。
- 展示消息历史、结构化状态、临时正文、完成度树和沟通路径。
- 不承担对象列表管理。

若当前需规对象尚未创建会话，本页应提示先完成 `4.2` 配置并启动会话。

### 4.4 当前 Turn

`4.4` 是当前需规对象下的单轮审计视图。

页面职责：

- 展示当前 `RequirementAnalysisTurn`。
- 解释本轮用户输入如何被理解。
- 展示影响的规格节点、正文 patch、状态变更、闭环判断和下一轮交互。
- 展示阶段审计，校验 `turn_audit_schema` 必需字段。

该页不是聊天记录页；聊天和继续输入仍在 `4.3`。

### 4.5 调用日志

`4.5` 是当前需规对象下的模型 Provider 调用证据页。

页面职责：

- 展示当前会话关联的 Provider / Runner 调用日志。
- 展示 `provider_request`、`provider_response`、`provider_normalized_output` 和 `service_output` 四层证据。
- 按 `turn_id`、`stage_id` 和 `provider_id` 追踪模型调用。

该页不替代 `4.4` 的 Turn 审计，也不展示后端所有内部函数调用。

## 5. 对象模型边界

### 5.1 用户可见对象：需求规格说明对象

本轮建议把用户可见对象命名为：

```text
需求规格说明对象
```

也可在实现讨论中暂称为 `需规对象` 或 `RequirementSpecWorkItem`。它是产品层的聚合对象，不要求立即等同于某一张已有表。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `spec_item_id` | 需规对象 ID |
| `title` | 需规名称 |
| `initial_description` | 新建时填写的初始说明 |
| `status` | 需规对象生命周期状态 |
| `template_id` | 当前需求规格模板 |
| `knowledge_binding` | 当前领域知识绑定 |
| `authoring_document_id` | 关联的标准需求规格说明工作文档 |
| `analysis_session_id` | 关联的组织器分析会话 |
| `published_requirement_spec_id` | 已发布后生成或关联的结构化 `RequirementSpec` |
| `published_package_id` | 已发布后生成的 P3 可接收包 |
| `version` | 当前版本号或修订号 |
| `p3_consumable` | 当前发布版本是否可被 P3 接收 |
| `created_at` / `updated_at` | 创建与更新时间 |

首版实现可以通过一个门面 DTO 聚合现有对象，不必须立即新增完整持久化聚合表。但无论实现方式如何，前端和 API 都应向用户呈现统一的需规对象。

### 5.2 内部对象职责

| 对象 | 目标职责 | 不应承担 |
| --- | --- | --- |
| `RequirementAuthoringDocument` | 标准需求规格说明工作文档，承载正文、表单字段、问答、批注、检查和冻结包 | 不直接承担组织器 Provider 调用日志 |
| `RequirementAnalysisSession` | 组织器执行会话，承载 Turn、结构化状态、临时正文、完成度树、下一轮交互和 Provider 调用日志 | 不作为用户列表的唯一主对象 |
| `RequirementAnalysisTurn` | 单轮组织器审计对象 | 不承担长期版本管理 |
| `RequirementSpec` | 冻结或发布后的结构化下游消费对象 | 不作为用户正文编辑器 |
| `RequirementAnalysisTemplate` / `RequirementAuthoringTemplate` | 模板配置对象 | 不承担具体需规生命周期 |

核心关系应收敛为：

```text
需求规格说明对象
  -> 关联 RequirementAuthoringDocument
  -> 关联 RequirementAnalysisSession
  -> 发布后生成 RequirementSpec / P3 input package
```

### 5.3 是否新增持久化对象的判断

存在两种实现口径：

| 口径 | 做法 | 风险 |
| --- | --- | --- |
| 门面聚合 | 以 `RequirementAuthoringDocument` 为主锚点，新增必要元数据和 API 聚合 `RequirementAnalysisSession`、`RequirementSpec` | 短期快，但文档对象会承担部分事项管理语义 |
| 独立需规对象 | 新增 `RequirementSpecWorkItem` 作为聚合根，文档、会话和发布包都挂到它下面 | 边界更干净，但实施和迁移成本更高 |

本补充稿建议：首版可以采用门面聚合或轻量独立聚合，但必须在 API 和前端层形成统一的需规对象；不要让用户在三个页面分别管理三套对象。

## 6. 生命周期与状态机

### 6.1 状态定义

建议状态机：

| 状态 | 含义 | 可执行动作 |
| --- | --- | --- |
| `draft` | 已新建，尚未完成配置或分析 | 进入配置、编辑标题、删除 |
| `configured` | 已完成模板、知识、组织器和 Provider 配置 | 进入配置、启动 / 恢复会话、删除 |
| `analyzing` | 已启动会话，正在通过 Turn 收敛需求 | 进入配置、继续会话、运行检查 |
| `ready_to_publish` | 阻断型缺口已处理，可发布 | 进入配置、发布 |
| `published_to_p3` | 当前版本已冻结并可被 P3 接收 | 查看配置、创建修订草稿、归档 |
| `revision_draft` | 基于已发布版本创建的修订草稿 | 进入配置、继续分析、重新发布 |
| `archived` | 历史归档 | 查看 |
| `deleted` | 删除或软删除 | 默认不展示 |

当前代码中的 `RequirementAuthoringDocumentStatus` 已包含 `draft`、`checking`、`ready_to_freeze`、`frozen`、`submitted_to_p3`、`archived`，可以作为实现映射基础，但产品层状态需要围绕 `发布到 P3` 表达清楚。

### 6.2 新建动作

`新建需规` 的状态变化：

```text
无对象
  -> 用户填写新建模态窗口
  -> 创建需求规格说明对象
  -> 创建或准备 RequirementAuthoringDocument
  -> 写入默认模板、标题、初始说明和可选知识绑定
  -> 状态进入 draft
  -> 默认跳转 4.2 组织器配置
```

若选择 `仅创建`，则停留在 `4.1` 列表，新对象出现在列表顶部。

### 6.3 进入配置动作

`进入配置` 的状态变化：

```text
draft / configured / analyzing / ready_to_publish
  -> 打开 4.2 组织器配置
  -> 加载该需规对象的模板、知识绑定、组织器、Provider、写入策略和会话引用
```

约束：

- 未选择需规对象时，`4.2` 应展示空状态。
- 已发布对象进入配置时，首版建议只读查看；如需修改，应先创建修订草稿。
- 不应通过 `进入配置` 隐式发布或隐式删除任何对象。

### 6.4 发布动作

`发布` 的状态变化：

```text
ready_to_publish
  -> 锁定当前工作文档版本
  -> 生成冻结包
  -> 生成或更新结构化 RequirementSpec
  -> 标记 P3 可接收
  -> 状态进入 published_to_p3
```

发布前置条件：

- 已存在需求规格说明对象。
- 已存在可冻结的工作文档。
- 当前无正在运行的 Turn。
- 阻断型缺口检查通过，或用户具备明确的强制发布权限。
- 当前版本的模板、知识绑定和组织器配置可追溯。
- 能生成 `P3` 可接收包。

发布后约束：

- 发布版本不可作为普通草稿直接修改。
- 列表展示 `P3 可接收`。
- `P3` 只读取发布后的正式版本，不读取草稿、临时正文、未确认批注和 Lab 实验态数据。
- 修改已发布内容时，应创建修订草稿或新版本，再重新发布。

### 6.5 删除与归档动作

删除和归档不是本轮原型重点，但应预留边界：

| 动作 | 建议口径 |
| --- | --- |
| 删除草稿 | 允许，需二次确认，可采用软删除 |
| 删除已发布版本 | 首版不建议支持；可改为归档 |
| 归档已发布对象 | 允许从活跃列表移除，但不影响 P3 已接收版本 |
| 恢复归档 | 可作为后续能力 |

## 7. 发布到 P3 的边界

`发布` 是 `P2` 和 `P3` 的系统边界。

`P2` 发布时应输出：

| 输出 | 说明 |
| --- | --- |
| 冻结需求规格说明正文 | 面向人审阅的正式文档 |
| 结构化 `RequirementSpec` | 面向 `P3` 软件设计系统的结构化输入 |
| 来源与追溯信息 | 模板、知识绑定、主要输入、关键 Turn、冻结时间 |
| 批注与缺口结果 | 可供 `P3` 判断风险和待确认事项 |
| `p3_consumable` 标识 | 明确该版本可以被 P3 接收 |

`P3` 不应消费：

- 未发布草稿。
- Lab 临时正文。
- 未确认批注。
- 组织器内部状态。
- Provider 原始日志。

Provider 原始日志可作为审计证据保留在 `P2`，但不是 `P3` 的正常输入。

## 8. API 设计补充建议

为避免前端直接拼接三套对象，建议增加一层需规对象门面 API。命名可在实现前确认，本文暂用 `/requirement-analysis/spec-items`。

建议接口：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/requirement-analysis/spec-items` | 查询 `4.1` 需规对象列表 |
| `POST` | `/requirement-analysis/spec-items` | 新建需规对象，对应新建模态窗口 |
| `GET` | `/requirement-analysis/spec-items/{id}` | 读取需规对象详情和关联资源 |
| `PATCH` | `/requirement-analysis/spec-items/{id}` | 修改标题、初始说明、模板、知识绑定等元数据 |
| `POST` | `/requirement-analysis/spec-items/{id}/configure` | 保存组织器配置，关联或创建分析会话 |
| `POST` | `/requirement-analysis/spec-items/{id}/publish` | 冻结并发布到 P3 |
| `POST` | `/requirement-analysis/spec-items/{id}/revision` | 基于已发布版本创建修订草稿 |
| `DELETE` | `/requirement-analysis/spec-items/{id}` | 删除草稿或软删除对象 |

该 API 可以在服务层复用现有：

- `/requirement-authoring/documents`
- `/requirement-authoring/documents/{id}/check`

## 10. 与主设计文档的关系

主设计文档当前已经定义：

- `P2` 输出冻结需求规格说明和 `RequirementSpec` 包给 `P3`。
- `RequirementAuthoringDocument` 承担标准正文工作文档。
- `RequirementAnalysisSession` 承担需求分析组织器会话。
- `RequirementSpec` 承担结构化规格和下游交换。
- `P3` 只消费冻结后的正式版本。

本文不推翻主设计文档，而是补充一个更明确的用户入口和对象生命周期：

```text
需求规格说明对象
  -> 管理 RequirementAuthoringDocument
  -> 关联 RequirementAnalysisSession
  -> 发布 RequirementSpec / P3 input package
```

待本文评审通过后，主设计文档需要同步的位置包括：

1. 前端页面章节：补 `4.1 需求规格说明管理`。
2. 对象模型章节：补“需求规格说明对象 / 需规对象”的产品聚合边界。
3. 状态机章节：补 `发布到 P3` 的产品层状态。
4. API 章节：补需规对象门面 API 或说明采用现有对象组合。
5. 上下游边界章节：明确 `发布` 与 `冻结` 的关系。

## 11. 非目标

本轮补充不做以下设计决策：

1. 不设计 `P3` 接收后的详细页面。
2. 不决定完整多版本差异对比、回滚和审批流。
3. 不重构当前主界面视觉布局。
4. 不把 `4.1` 与 `4.2` 合并。
5. 不把 Lab 简化为普通聊天页。
6. 不把 Provider 调用日志作为 `P3` 正常输入。
7. 不立即更新主设计文档。

## 12. 可实施性判断

当前已经具备进入代码实现设计评审的基础，但不建议直接开工改代码。原因是：

- v9 原型已经明确了 `4.1`、新建弹窗、`进入配置 / 发布` 和 `P3 可接收` 的产品形态。
- 当前代码已有文档工作台、Lab 会话、Turn 审计、Provider 调用日志、冻结包和结构化 `RequirementSpec` 能力。
- 仍需在实施前确认采用“门面聚合”还是“独立需规对象”作为首版实现方式。

建议下一步先评审本文。若本文方向通过，再补一份实施计划，至少明确：

1. 是否新增持久化 `RequirementSpecWorkItem`。
2. `发布` 是否复用现有 `freeze` 服务，还是新增 `publish` 服务包一层。
3. `RequirementAuthoringDocument` 与 `RequirementAnalysisSession` 的关联字段放在哪里。
4. `P3` 接收端消费 `RequirementSpec` 还是消费新的 `P2 input package`。
5. 已发布后的修订草稿采用复制文档、版本号，还是同对象新 revision。
