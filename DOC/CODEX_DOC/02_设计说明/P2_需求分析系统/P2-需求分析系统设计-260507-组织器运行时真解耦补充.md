# P2 需求分析系统设计 - 260507 组织器运行时真解耦补充

## 1. 文档定位

本文是 `P2-需求分析系统设计.md` 的进一步解耦补充稿，用于说明目录插件化之后，需求规格组织器运行时仍需继续升级的边界、目标结构和实施依据。

本文不是过程记录，也不是现状说明的补丁集合。本文给出下一阶段的目标态设计，供评审后再归并到主设计说明。

## 2. 背景与问题判断

前一阶段已完成组织器目录发现、manifest 注册、adapter 装载、统一 `OrchestratorRunRequest` / `OrchestratorRunResult` 合同和显式 reload。这说明组织器已经从“后端静态注册对象”升级为“目录可插拔插件包”。

但该阶段主要解决的是插件发现与入口分发，并未完全解决运行时边界。经检查，`xg-heuristic-orchestrator` 与 `brainstorm-v1` 都仍存在如下问题：

| 问题 | 表现 | 影响 |
| --- | --- | --- |
| 插件 adapter 反向构造宿主服务 | adapter 内部创建数据库 session 并构造 `RequirementAnalysisSessionService` | 插件仍知道宿主持久化和服务组装方式 |
| 插件 runtime 直接依赖宿主内部服务 | runtime 直接导入 `app.requirement_analysis.*` 的上下文、投影、审计、工作文档、Provider 等服务 | 插件不是依赖稳定端口，而是依赖宿主内部实现 |
| 阶段流程在 Python 中固化 | runtime 按 `intent`、`decision_state_delta`、`review`、`next_interaction` 等 stage kind 分段执行 | 阶段策略变化需要改 Python，而不是改组织器描述包 |
| 阶段 kind 存在字符串推断 | planner 根据 `stage_id` 中的关键词推断阶段类型 | 配置不显式，错误阶段名可能被静默误判 |
| mock 行为承载业务样例 | 本地 mock provider 按阶段生成业务形态输出 | mock 与真实模型策略边界不够清晰 |
| 启发式组织器与 Brainstorm V1 运行体同源复制 | 两个插件保留大量同构 runtime 文件 | 维护时容易一处修复、另一处遗漏 |

因此，当前状态应判定为：

```text
入口插件化：已完成。
目录可插拔：已完成。
组织器资产外置：部分完成。
运行时真解耦：未完成。
业务决策外置：未完全完成。
```

## 3. 解耦目标

下一阶段目标不是继续移动文件，而是建立明确的运行时端口边界，使组织器成为只依赖合同和端口的策略单元。

目标态应满足以下判据：

1. 组织器 adapter 不创建数据库连接，不构造 `RequirementAnalysisSessionService`，不直接写会话状态。
2. 组织器包内代码不得直接依赖 `app.requirement_analysis.*` 的内部服务；允许依赖稳定合同模块和运行时端口协议。
3. 组织器阶段顺序、阶段输入、阶段输出、采用策略、失败策略由组织器描述包显式声明，Python runtime 只做通用编排。
4. Python 可以保留状态机推进、合同校验、端口调用、结果物化等确定性基础设施，但不得承担用户意图判断、章节业务匹配、下一轮交互策略等业务决策。
5. `xg-heuristic-orchestrator` 与 `brainstorm-v1` 不再各自持有一份复制的 XG 阶段 runtime；共性运行能力应进入宿主稳定运行时或共享 SDK，差异留在组织器包资产中。
6. 前端和 API 只感知统一轮次结果、模型调用日志、阶段审计和投影视图，不依赖某个组织器内部阶段名。

## 4. 目标边界模型

### 4.1 总体分层

目标态采用四层结构：

```text
需求分析会话层
  - 负责会话生命周期、状态保存、轮次创建、结果回写、API 暴露。

组织器宿主层
  - 负责插件发现、adapter 装载、稳定端口注入、合同校验、审计落点。

组织器运行层
  - 负责根据组织器描述包执行阶段策略。
  - 不拥有数据库，不拥有会话长期状态，不直接写正式文档。

组织器描述包层
  - 负责声明策略、阶段、prompt、schema、adoption、示例、测试和可选本地 runner。
```

### 4.2 宿主与组织器职责

| 责任 | 需求分析会话层 | 组织器宿主层 | 组织器运行层 / 插件 |
| --- | --- | --- | --- |
| 会话创建与保存 | 是 | 否 | 否 |
| 数据库连接管理 | 是 | 否 | 否 |
| 插件发现与装载 | 否 | 是 | 否 |
| 稳定运行端口提供 | 否 | 是 | 使用 |
| 阶段策略声明 | 否 | 校验 | 是 |
| 阶段模型调用 | 否 | 提供端口 | 按策略调用 |
| 用户意图判断 | 否 | 否 | 通过模型阶段完成 |
| 章节规划与状态增量 | 否 | 否 | 通过模型阶段完成 |
| 结构化状态采纳 | 是 | 可协助校验 | 输出候选 |
| 过程日志与审计 | 保存 | 构造基础审计 | 输出阶段审计材料 |
| 正式文档写入 | 是 | 否 | 否 |

## 5. 运行时端口设计

### 5.1 端口设计原则

运行时端口是组织器可使用的稳定能力，不是宿主内部服务对象的直接暴露。端口接口应以“能力”命名，而不是以当前实现类命名。

组织器可以使用端口，但不能知道端口背后的数据库、FastAPI service、SQLAlchemy session 或内部服务组装方式。

### 5.2 建议端口清单

| 端口 | 职责 | 典型方法 | 是否允许插件调用 |
| --- | --- | --- | --- |
| `TurnContextPort` | 构造当前 turn 的只读上下文 | `build_context(session_snapshot, turn_input)` | 是 |
| `StagePromptPort` | 根据阶段和上下文组装 prompt bundle | `build_prompt_bundle(orchestrator_id, stage, context)` | 是 |
| `ModelProviderPort` | 调用模型提供方或本地 runner | `run_stage(orchestrator_id, stage, prompt_bundle)` | 是 |
| `ContractValidationPort` | 校验阶段输出和最终输出 | `validate_stage_output(stage, output)` | 是 |
| `DecisionStatePort` | 规范化和应用结构化决策状态增量 | `normalize_delta(...)`、`apply_delta(...)` | 是，但只处理结构化机械合并 |
| `ProjectionPort` | 将候选输出投影到规格树或工作文档视图 | `project(...)` | 是，但不得做业务判断 |
| `WorkingViewPort` | 渲染探索阶段 A4 视图、完成度树和临时正文视图 | `render_decision_state_view(...)` | 是 |
| `AuditPort` | 生成统一阶段审计、模型调用日志和决策轨迹 | `record_stage_call(...)`、`build_turn_audit(...)` | 是 |

这些端口可以由宿主实现，也可以由测试替身实现。插件只能面向端口编程。

### 5.3 不应暴露给插件的对象

| 对象 | 不应暴露原因 |
| --- | --- |
| `SessionLocal` | 数据库连接生命周期属于宿主 |
| `RequirementAnalysisSessionService` | 它是会话应用服务，不是组织器运行端口 |
| API route / FastAPI dependency | 插件不能绑定 Web 层 |
| SQLAlchemy ORM model | 插件不能感知持久化表结构 |
| 前端视图模型 | 插件只输出合同，不关心页面状态 |

## 6. 组织器 adapter 目标形态

### 6.1 当前问题

当前本地 XG 插件 adapter 在 `_runtime()` 内部创建数据库 session，再构造 `RequirementAnalysisSessionService`，并从该 service 上拆出十多个内部服务传入 runtime。

这使 adapter 同时承担了三件不该承担的职责：

1. 宿主服务组装。
2. 数据库连接生命周期管理。
3. 组织器 runtime 依赖注入。

### 6.2 目标形态

adapter 目标态只承担“插件入口适配”：

```text
LocalXGOrchestratorPluginAdapter
  input: OrchestratorRunRequest + OrchestratorRuntimeHost
  output: OrchestratorRunResult
  responsibility:
    - 读取插件 manifest 和 package 资产
    - 将请求交给通用策略运行器或插件 runner
    - 返回统一合同结果
```

adapter 不得创建 `SessionLocal`，不得构造 `RequirementAnalysisSessionService`，不得直接访问数据库。

## 7. 策略运行器目标形态

### 7.1 从“本地 XG runtime”升级为“通用策略运行器”

当前 `local_xg_turn_runtime.py` 按固定 XG 阶段链执行。目标态应把它升级为通用策略运行器：

```text
PolicyInterpretedRuntime
  1. 读取 spec_strategy.turn_strategy.stages
  2. 按显式顺序迭代 stage
  3. 根据 stage.input_sources 组装阶段上下文
  4. 根据 stage.execution_mode 决定模型调用、本地 runner 或纯系统阶段
  5. 根据 stage.schema_id 校验输出
  6. 根据 stage.adoption_id 采纳字段
  7. 进入下一 stage
  8. 输出 OrchestratorRunResult
```

通用策略运行器不应该知道 `intent_understanding`、`decision_state_delta`、`next_interaction_planning` 的业务含义。它只知道：

- 这是一个 stage。
- 这个 stage 要哪些输入。
- 这个 stage 是否调用模型。
- 这个 stage 输出要满足哪个 schema。
- 这个 stage 的哪些字段可被采纳。

### 7.2 阶段依赖显式化

每个 stage 必须显式声明：

| 字段 | 说明 |
| --- | --- |
| `stage_id` | 稳定阶段标识，不允许 runtime 根据字符串猜测 |
| `stage_kind` | 仅作为展示和审计分类，不能作为业务分支核心 |
| `execution_mode` | `model`、`system`、`local_runner`、`remote_service` |
| `prompt_id` | 模型阶段使用的 prompt 资产 |
| `schema_id` | 输出格式要求 |
| `adoption_id` | 结果采用策略 |
| `input_sources` | 该阶段可读取的上下文来源 |
| `output_targets` | 该阶段产出写入哪个中间槽 |
| `failure_policy` | 失败时阻断、跳过、降级或终止 |

如果配置缺失，应在计划构建阶段报错，而不是由 Python 推断。

## 8. 业务决策与硬编码边界

### 8.1 允许硬编码的内容

以下内容属于确定性基础设施，可以写在 Python 中：

1. turn 从用户输入开始。
2. 会话、轮次、阶段的编号和生命周期推进。
3. 插件目录发现和 manifest 校验。
4. JSON schema 校验。
5. prompt bundle 的机械拼装。
6. 阶段输出字段的采纳、阻断、审计落点。
7. 结构化状态对象的机械合并、去重、版本记录。
8. 模型调用失败时终止本轮并返回明确错误。

### 8.2 不应硬编码的内容

以下内容属于业务判断或智能判断，应由模型阶段、组织器策略或模板配置承担：

1. 用户真实意图判断。
2. 用户输入与上一轮问题的承接关系。
3. 章节匹配、章节新增、章节细化策略。
4. 需求规格模板形态判断。
5. 当前输入是否足够推进决策链。
6. 下一轮应该问什么、给什么选项。
7. 输出是否对决策链有实质推进。
8. Brainstorm 式启发追问策略。

## 9. 启发式组织器与 Brainstorm V1 的关系

### 9.1 当前关系

`xg-heuristic-orchestrator` 和 `brainstorm-v1` 当前都属于需求规格组织器实例。两者都已具备目录插件形态，也都存在运行体与宿主内部服务耦合的问题。

Brainstorm V1 不是唯一未解耦对象；它继承了原启发式组织器的运行结构问题。

### 9.2 目标关系

下一阶段不应继续维护两套同源 runtime。目标态应为：

```text
orchestrators/xg/xg-heuristic-orchestrator/
  - manifest.json
  - spec_strategy.json
  - prompts/
  - schemas/
  - adoption/
  - examples/
  - tests/

orchestrators/xg/brainstorm-v1/
  - manifest.json
  - spec_strategy.json
  - prompts/
  - schemas/
  - adoption/
  - examples/
  - tests/

apps/api/app/orchestrators/runtime/
  - policy_interpreted_runtime.py
  - runtime_ports.py
  - stage_plan.py
  - stage_context.py
  - stage_reducer.py
```

两者共享宿主通用运行器，差异体现在组织器描述包资产，而不是复制 runtime Python。

## 10. 升级路径

### 10.1 阶段一：建立运行时端口与架构护栏

目标：先把“允许依赖什么、不允许依赖什么”落实成代码边界和测试边界。

工作内容：

1. 新增稳定运行端口协议。
2. 新增 `OrchestratorRuntimeHost`，由宿主创建并注入 adapter。
3. 新增架构测试，禁止组织器包直接导入：
   - `app.db.*`
   - `app.requirement_analysis.session_service`
   - `app.requirement_analysis.*` 内部服务，除明确允许的合同对象外
4. 明确允许导入的稳定合同模块，例如：
   - `app.orchestrators.plugin_contracts`
   - `app.orchestrators.runtime_ports`
   - `app.orchestrators.runtime_contracts`

### 10.2 阶段二：移除 adapter 的宿主服务构造

目标：插件 adapter 不再自己创建数据库和会话服务。

工作内容：

1. 修改 adapter 装载器，使 adapter 初始化时接收 `runtime_host`。
2. 修改 `xg-heuristic-orchestrator` 与 `brainstorm-v1` adapter，删除 `SessionLocal` 和 `RequirementAnalysisSessionService` 构造。
3. adapter 只通过 `runtime_host.run_policy_interpreted(request, package)` 或等价端口运行。
4. 保留原外部合同输出，确保前端和 API 不退化。

### 10.3 阶段三：抽出通用策略运行器

目标：从两个插件目录中抽出同源 `local_xg_turn_runtime.py`，变成宿主通用 `PolicyInterpretedRuntime`。

工作内容：

1. 通用运行器按 `spec_strategy.turn_strategy.stages` 迭代阶段。
2. 删除按 `intent`、`review`、`decision_state_delta`、`next_interaction` 写死的主流程分支。
3. 阶段上下文按 `input_sources` 声明组装。
4. 阶段输出按 `output_targets` 和 `adoption` 声明采纳。
5. 缺少必要字段时阻断本轮，而不是推断默认业务含义。

### 10.4 阶段四：收敛组织器包资产

目标：让组织器差异真正落在包资产中。

工作内容：

1. 重新整理 `xg-heuristic-orchestrator/spec_strategy.json`。
2. 重新整理 `brainstorm-v1/spec_strategy.json`。
3. 将 stage kind 推断、默认 input sources、默认 adopt fields 从 Python 转为显式配置。
4. mock 输出改为 fixture 或组织器包内测试资产，不再作为宿主 Provider 的业务分支。
5. 组织器包内保留必要本地 runner 时，也必须只依赖运行端口合同。

### 10.5 阶段五：回归文档和测试

目标：让实现与设计一致。

工作内容：

1. 将本补充稿中通过评审的内容归并到 `P2-需求分析系统设计.md` 的组织器设计、轮次执行设计和接口设计章节。
2. 更新 `02.03-WBS-P2-组织器真解耦升级-研制计划.md`，说明目录插件化已完成、运行时端口解耦为下一阶段。
3. 增加运行时端口级单元测试。
4. 增加组织器包禁用宿主内部服务导入的架构测试。
5. 对 `xg-heuristic-orchestrator` 与 `brainstorm-v1` 各跑一轮 mock 和真实 provider 可用性测试。

## 11. 验收标准

完成本升级后，至少满足以下标准：

1. `orchestrators/xg/*/adapter.py` 中不再出现 `SessionLocal`。
2. `orchestrators/xg/*/adapter.py` 中不再构造 `RequirementAnalysisSessionService`。
3. `orchestrators/xg/*` 内不再直接导入宿主内部业务服务，除稳定合同和运行端口外。
4. `xg-heuristic-orchestrator` 与 `brainstorm-v1` 不再各自持有复制的 `local_xg_turn_runtime.py`。
5. 阶段计划不再根据 `stage_id` 字符串推断 `stage_kind`。
6. 新增组织器阶段时，只修改组织器包资产和必要 schema，不修改通用 runtime 主流程。
7. 组织器移除、reload、恢复的目录插件化验收继续通过。
8. P2 Lab 的调用日志仍能展示每个模型 / runner 阶段的请求、当前 turn 上下文、输出格式要求、原始输出和输出后处理。
9. 真实模型失败时，本轮直接失败并保留错误审计，不做无模型兜底业务判断。
10. 前端不依赖具体组织器阶段名，只依赖后端返回的阶段审计和调用日志数据。

## 12. 风险与取舍

### 12.1 风险

1. 抽出通用策略运行器会触碰当前最核心的 turn 执行链，回归测试必须充分。
2. 若一次性移除全部本地 runtime，可能造成启发式组织器和 Brainstorm V1 同时不可用。
3. 若端口设计过细，会把宿主内部服务换一种名字继续泄露给插件。
4. 若端口设计过粗，组织器包又会难以表达可观测阶段细节。

### 12.2 取舍

建议采用“端口先行、运行器渐进替换”的方式，而不是一次性重写：

1. 先加端口和架构测试。
2. 再改 adapter 注入方式。
3. 再抽通用运行器。
4. 最后删除插件内复制 runtime。

这样可以在每一步都保持 P2 Lab 可运行，也能明确定位失败来自端口、运行器还是组织器资产。

请重点评审以下问题：

1. 是否同意“目录插件化已完成，但运行时真解耦未完成”的判断。
2. 是否同意 adapter 不应创建数据库 session 和会话服务。
3. 是否同意组织器包不得直接依赖 `app.requirement_analysis.*` 内部服务。
4. 是否同意把共性阶段运行能力收敛为宿主通用策略运行器。
5. 是否同意阶段行为必须由 `spec_strategy.json`、prompt、schema、adoption 显式声明，Python 不做业务推断。
6. 是否需要保留插件包内本地 runner；如果保留，它应作为 `local_runner` stage，而不是完整复制宿主运行体。
