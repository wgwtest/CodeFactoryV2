# P2 Requirement Analysis 混合型启发式需求收束策略设计

**日期：** 2026-05-01

**文档状态：** 策略设计草案，供后续 Turn 引擎与 Lab 原型升级使用

## 1. 设计背景

`P2 Requirement Analysis Orchestrator Lab` 的目标不是创建一个通用聊天机器人，也不是创建一个固定问卷式需求采集工具。

它有一个强约束：

```text
最终必须帮助用户完成一份合规、清晰、可继续进入后续设计与实现阶段的需求规格说明文档。
```

但如果系统只围绕需求规格模板逐项提问，就会退化为问卷或向导：

```text
系统发现一个空节点 -> 系统提问 -> 用户回答 -> 系统关闭节点 -> 系统进入下一个节点
```

这种模式的问题是：

- 用户容易感觉是在被系统盘问，而不是被帮助思考。
- 系统容易机械推进文档节点，而不是理解用户当前真正关心的问题。
- 用户的反驳、补充、犹豫、改题、比较和自由探索，容易被压扁成“是否回答了上一题”。
- 系统可能过早把探索性表达写成稳定需求，导致后续文档出现误收束。

因此，P2 Requirement Analysis 需要采用混合型策略：

```text
前半段像设计伙伴，帮助用户想清楚；
后半段像规格收束器，把想清楚的内容沉淀为文档。
```

本策略文档的目标是定义这种混合型 Requirement Analysis 的上层工作方式，为后续 Turn 引擎、Current Turn 视图、状态机和协议升级提供依据。

## 2. 策略定位

P2 Requirement Analysis 的定位应从：

```text
需求规格补充执行引擎
```

升级为：

```text
面向需求规格文档收束的启发式设计对话引擎
```

它的核心职责不是“按模板问完所有问题”，而是：

```text
用启发式设计对话，帮助用户逐步形成更清晰、更稳定、可写入的需求规格内容。
```

该定位包含两个边界：

1. 它不是纯聊天。所有对话最终都要服务于目标需求规格文档。
2. 它不是纯填表。系统不能只按模板节点机械提问和关闭节点。

正确关系应为：

```text
用户输入驱动对话
启发策略帮助思考
规格模板提供收束目标
需求规格文档是最终落点
```

## 3. 三层目标

P2 Requirement Analysis 同时服务三层目标。

### 3.1 交互目标

交互目标是：

```text
让用户感觉自己是在被帮助思考，而不是被系统盘问。
```

系统应支持：

- 用户自由发起话题。
- 用户回答上一轮问题。
- 用户只回答一部分。
- 用户选择 A/B/C 快捷选项。
- 用户补充约束。
- 用户反驳系统假设。
- 用户主动改题。
- 用户要求系统帮忙整理、举例或比较方案。

交互目标关注的是：

```text
系统是否顺着用户当前认知状态推进，而不是强行把用户拉回模板节点。
```

### 3.2 收束目标

收束目标是：

```text
把松散想法逐步收束成可写入、可审查、可继续使用的需求规格内容。
```

系统必须区分：

- 哪些内容只是探索。
- 哪些内容是用户倾向。
- 哪些内容是候选方案。
- 哪些内容已经被用户确认。
- 哪些内容可以写成规格正文。
- 哪些内容只能作为过程注记或待确认项。

收束目标关注的是：

```text
系统是否把“想法”转化成了合适粒度、合适确定性的规格材料。
```

### 3.3 合规目标

合规目标是：

```text
最终需求规格说明文档必须完整、清晰、一致、可追踪，并能支撑后续设计与实现。
```

系统应持续回看：

- 文档章节覆盖是否足够。
- 关键概念是否明确。
- 用户角色是否清楚。
- 使用场景是否成立。
- 范围边界是否清楚。
- 非目标是否明确。
- 约束与前文是否冲突。
- 是否存在无法进入后续阶段的重大缺口。

合规目标关注的是：

```text
当前对话是否真实推动了目标文档走向可交付状态。
```

## 4. 总体流程

混合型策略下，一个 Requirement Analysis Turn 仍然从用户输入开始，但不应立即进入规格补充。

推荐流程：

```text
上轮交互对象（可选）
-> 用户输入
-> 输入承接判断
-> 对话意图识别
-> 文档缺口识别
-> 启发策略决策
-> 探索处理
-> 规格收束执行
-> 补充后状态回看
-> 本轮闭环判断
-> 下一轮推进策略
-> 下一轮交互设计（可选）
```

其中：

- `输入承接判断` 解释用户输入和上一轮系统留题的关系。
- `对话意图识别` 判断用户这一轮需要什么类型的帮助。
- `文档缺口识别` 判断当前最影响文档合规的认知缺口是什么。
- `启发策略决策` 决定本轮是直接收束、澄清、比较、重构还是暂缓写入。
- `探索处理` 帮助用户想清楚，而不是急着写正文。
- `规格收束执行` 只把足够稳定的内容写入或建议写入规格。

关键原则：

```text
先帮助用户想清楚，再把想清楚的内容收束进文档。
```

## 5. 探索段与收束段

每个 Turn 应被理解为两段式闭环：

```text
探索段 -> 收束段
```

### 5.1 探索段

探索段负责理解和启发。

它回答：

- 用户这轮真正想表达什么？
- 用户是在给事实，还是在表达倾向？
- 用户是在回答上一题，还是在改题？
- 用户是否需要系统给例子、方案或结构？
- 当前描述背后隐藏了什么需求缺口？
- 是否存在冲突、跳跃或过早细节化？

探索段产物包括：

- 对话意图。
- 当前理解摘要。
- 隐含缺口。
- 候选方案。
- 推荐判断。
- 仍需确认的问题。

探索段不直接等同于正式规格写入。

### 5.2 收束段

收束段负责沉淀和回看。

它回答：

- 哪些内容已经足够稳定？
- 哪些内容可以进入正式规格？
- 哪些内容只能作为候选补丁？
- 哪些内容只能作为过程注记？
- 哪些规格节点被影响？
- 当前文档状态是否前进？
- 下一步应该继续同一缺口，还是切换到其他缺口？

收束段产物包括：

- 确认事实。
- 候选事实。
- 规格正文建议。
- 过程注记。
- 影响的规格节点。
- 状态变化。
- 补充后回看。

## 6. 对话意图识别

现有 `input_relation` 只能解释用户输入和上一轮系统留题之间的关系。混合型策略还需要识别用户当前的对话意图。

建议新增 `conversation_intent`：

```json
{
  "conversation_intent": {
    "type": "express_preference",
    "summary": "用户表达了对系统定位的倾向，但尚未给出范围边界。",
    "reason": "用户没有直接给出完整规格事实，而是在比较不同产品方向。"
  }
}
```

建议枚举：

| 枚举 | 含义 | 推荐处理 |
| --- | --- | --- |
| `provide_fact` | 用户提供明确事实 | 优先收束 |
| `express_preference` | 用户表达倾向 | 总结倾向，确认边界 |
| `compare_options` | 用户比较方案 | 给出方案取舍和推荐 |
| `seek_suggestion` | 用户请求建议 | 提供 2-3 个方向 |
| `clarify_scope` | 用户界定范围 | 收束范围与非目标 |
| `raise_constraint` | 用户补充约束 | 写入约束或风险 |
| `challenge_assumption` | 用户反驳系统假设 | 修正理解，避免强收束 |
| `ask_for_example` | 用户要求举例 | 用例子启发，不急着写正文 |
| `request_structuring` | 用户要求整理 | 先结构化，再判断写入 |
| `free_exploration` | 用户自由发散 | 提炼主题，寻找高价值缺口 |

该字段的目的不是限制用户，而是帮助系统选择正确的协作方式。

## 7. 文档缺口识别

需求规格完成度树可以显示哪些章节已有材料，但 Requirement Analysis 需要识别更具体的“认知缺口”。

建议新增 `spec_gap_analysis`：

```json
{
  "spec_gap_analysis": {
    "current_gap": "软件定位已有倾向，但第一阶段边界仍不清楚。",
    "gap_type": "missing_scope_boundary",
    "why_this_gap_matters": "如果不明确第一阶段不做什么，后续功能范围会持续膨胀。",
    "can_write_now": false,
    "recommended_action": "clarify_one_point"
  }
}
```

建议缺口类型：

| 类型 | 含义 |
| --- | --- |
| `missing_core_positioning` | 缺少软件核心定位 |
| `missing_primary_actor` | 缺少主要用户角色 |
| `missing_usage_scenario` | 缺少典型使用场景 |
| `missing_scope_boundary` | 缺少范围边界 |
| `missing_success_criteria` | 缺少成功标准 |
| `missing_non_goals` | 缺少非目标 |
| `missing_workflow_detail` | 缺少业务流程细节 |
| `missing_constraint` | 缺少约束条件 |
| `conflicting_statements` | 当前表述与前文冲突 |
| `premature_detail_without_context` | 细节过早，但上层背景不足 |

系统选择下一步时，应优先考虑：

```text
哪个缺口最影响目标文档继续合规收束。
```

而不是简单选择：

```text
完成度树上第一个 open 节点。
```

## 8. 启发策略决策

混合型策略的关键能力是：系统不默认每轮都提问，也不默认每轮都写正文，而是先选择启发策略。

建议新增 `facilitation_strategy`：

```json
{
  "facilitation_strategy": {
    "mode": "offer_options",
    "reason": "用户表达了模糊方向，但还没有形成稳定选择；给出候选方向更容易推进判断。",
    "expected_outcome": "用户选择或修正一个软件定位方向。"
  }
}
```

建议模式：

### 8.1 direct_capture

适用场景：

```text
用户已经给出明确、稳定、可写入的内容。
```

处理方式：

```text
直接收束为确认事实和规格正文建议。
```

### 8.2 clarify_one_point

适用场景：

```text
用户方向基本清楚，但有一个关键缺口阻止稳定写入。
```

处理方式：

```text
只追问一个高价值澄清点。
```

### 8.3 offer_options

适用场景：

```text
用户表达模糊，或自己也还没想清楚。
```

处理方式：

```text
给出 2-3 个贴近文档目标的候选方向，并说明推荐项。
```

### 8.4 compare_approaches

适用场景：

```text
用户正在比较多个方案，或某个需求存在明显路线选择。
```

处理方式：

```text
列出方案、适用条件、代价、风险和推荐。
```

### 8.5 reflect_and_reframe

适用场景：

```text
用户说了很多，但结构散或层次混杂。
```

处理方式：

```text
先总结系统理解，再把内容重构成更清晰的需求维度。
```

### 8.6 challenge_gently

适用场景：

```text
用户当前说法存在冲突、跳跃、范围失衡或难以实现的隐含假设。
```

处理方式：

```text
礼貌指出问题，并把讨论拉回可落地的判断点。
```

### 8.7 defer_document_write

适用场景：

```text
本轮价值在启发或澄清，不适合立即写入规格正文。
```

处理方式：

```text
形成探索注记或待确认项，不强行生成正式正文。
```

## 9. 文档写入级别

为了避免把探索性表达误写成稳定需求，建议将规格写入分为三个级别。

### 9.1 confirmed_write

含义：

```text
用户已经明确确认，且内容与现有文档不冲突，可以进入正式需求规格正文。
```

适用：

- 明确事实。
- 明确范围。
- 明确角色。
- 明确约束。
- 明确非目标。

### 9.2 candidate_patch

含义：

```text
内容有较高价值，但仍需要用户确认或后续上下文验证。
```

适用：

- 系统根据用户表达整理出的候选正文。
- 用户倾向明确但边界未完全明确。
- 多方案中推荐方案的草案文本。

### 9.3 process_note

含义：

```text
内容只进入过程区，用于保留思考痕迹，不进入正式规格正文。
```

适用：

- 用户自由发散。
- 用户提出疑问。
- 方案比较过程。
- 暂时无法裁决的冲突。
- 系统发现的风险或待确认点。

建议 `document_patch` 增加写入级别：

```json
{
  "section": "2 项目概述 / 软件定位",
  "operation": "append_or_update",
  "content": "本软件第一阶段定位为面向领域专家的计算分析工具。",
  "write_level": "candidate_patch",
  "reason": "用户选择了计算分析工具方向，但第一阶段边界尚未完全确认。"
}
```

## 10. 方案比较能力

Superpowers 式 Requirement Analysis 的核心价值之一，是在用户还没有想清楚时，主动提供可比较的方案。

P2 Requirement Analysis 应将方案比较升级为正式能力，而不是偶发回答。

建议新增 `approach_exploration`：

```json
{
  "approach_exploration": {
    "triggered": true,
    "topic": "软件定位",
    "options": [
      {
        "key": "A",
        "label": "计算分析工具",
        "fit": "适合第一阶段快速形成可用能力。",
        "tradeoff": "协同与管理能力会较弱。",
        "risk": "后续若扩展为平台，需要补充权限、协作和项目管理能力。"
      },
      {
        "key": "B",
        "label": "协同规划平台",
        "fit": "适合多角色共同维护规划结果。",
        "tradeoff": "范围更大，首阶段复杂度明显增加。",
        "risk": "容易过早进入权限、流程和协作细节。"
      }
    ],
    "recommended_option": "A",
    "recommendation_reason": "当前阶段更需要先验证核心分析能力，平台化能力可以作为后续演进方向。"
  }
}
```

方案比较适用于：

- 软件定位。
- 用户角色。
- 首阶段范围。
- 工作流形态。
- 数据输入方式。
- 输出物形态。
- 系统边界。
- 自动化程度。

方案比较输出应遵循：

```text
推荐项在前，说明为什么；
每个方案说明适用条件、代价和风险；
不要只列选项，不给判断。
```

## 11. 下一轮推进策略

`next_interaction` 不应只是“下一题”。它应由更上层的推进策略驱动。

建议新增 `next_step_strategy`：

```json
{
  "next_step_strategy": {
    "goal": "确认第一阶段范围边界",
    "mode": "continue_same_gap",
    "reason": "软件定位已有方向，但如果不确认不做什么，文档仍无法稳定收束。",
    "target_spec_node_ids": ["SPEC-REQ-2.1", "SPEC-REQ-2.3"]
  }
}
```

建议模式：

| 模式 | 含义 |
| --- | --- |
| `continue_same_gap` | 继续围绕当前缺口推进 |
| `switch_to_next_gap` | 当前缺口已足够，切换到下一个关键缺口 |
| `offer_comparison` | 下一轮适合让用户比较方案 |
| `request_example` | 下一轮适合请用户给具体例子 |
| `invite_free_expression` | 暂不提具体题，邀请用户自由补充 |
| `pause_for_review` | 暂停推进，请用户审阅已形成内容 |

`next_interaction` 仍可存在，但它只是推进策略的具体表达。

正确关系：

```text
next_step_strategy 决定为什么推进
next_interaction 决定如何呈现给用户
```

## 12. Current Turn 视图升级

当前 Turn 视图不应只展示协议字段，而应展示系统如何帮助用户思考并完成文档收束。

推荐展示顺序：

1. `本轮用户输入`
   - 显示用户原文。
   - 若命中快捷选项，显示完整选项语义。
2. `系统如何理解这轮输入`
   - 显示输入承接关系。
   - 显示对话意图。
3. `当前关键文档缺口`
   - 显示缺口类型。
   - 显示为什么这个缺口重要。
4. `本轮启发策略`
   - 显示系统为什么选择直接收束、澄清、比较、重构或暂缓写入。
5. `探索结果`
   - 显示候选方案、推荐判断、待确认点。
6. `规格收束执行`
   - 显示确认事实、候选正文、过程注记和影响节点。
7. `补充后状态回看`
   - 显示当前文档是否前进、还缺什么。
8. `本轮闭环判断`
   - 显示本轮是否已经吸收用户输入，是否需要继续同一缺口。
9. `下一轮推进策略`
   - 显示下一步为什么这样推进。
10. `下一轮交互对象`
   - 显示问题、选项或自由补充邀请。

视图目标应从：

```text
协议审计视图
```

升级为：

```text
思考过程视图 + 文档收束视图
```

## 13. 与现有 Turn 协议的关系

本策略不是推翻现有 `RequirementAnalysisTurn` 协议，而是在其前半段增加更强的启发式判断能力。

现有能力应保留：

- `previous_interaction`
- `user_input`
- `normalized_input`
- `input_relation`
- `spec_execution`
- `post_update_review`
- `closure_decision`
- `next_interaction`
- `decision_trace`

建议新增能力：

- `conversation_intent`
- `spec_gap_analysis`
- `facilitation_strategy`
- `approach_exploration`
- `write_level`
- `next_step_strategy`

升级后的 Turn 主线可表达为：

```text
用户输入
-> 承接判断
-> 意图识别
-> 缺口识别

```

## 15. 验收标准升级

后续实现应在原有 Turn 验收基础上，增加以下策略级验收：

1. 用户自由表达时，系统能识别对话意图，而不是只判断是否回答上一题。
2. 用户表达模糊倾向时，系统能给出 2-3 个候选方向和推荐判断。
3. 用户比较方案时，系统能说明方案适用条件、代价和风险。
4. 用户反驳系统假设时，系统能修正状态，并避免把旧假设继续写入正文。
5. 用户只是探索时，系统能生成 `process_note`，而不是强行生成正式规格正文。
6. 用户给出明确事实时，系统能生成 `confirmed_write`。
7. 用户给出有价值但未完全确认的内容时，系统能生成 `candidate_patch`。
8. 系统能解释当前最关键文档缺口是什么，以及为什么优先处理它。
9. 系统能解释本轮采用的启发策略，而不是只展示下一题。
10. 下一轮交互由 `next_step_strategy` 驱动，不能机械推进完成度树的第一个 open 节点。
11. Current Turn 视图能同时展示思考过程和文档收束结果。
12. 系统不会因为文档合规目标而压制用户改题、补充、质疑或自由探索。

## 16. 结论

P2 Requirement Analysis 的优化方向不是创建更复杂的问卷，也不是创建不受约束的自由聊天。

它应升级为：

```text
混合型启发式需求收束策略
```

核心原则是：

```text
前半段更像设计伙伴：
识别意图、发现缺口、比较方案、启发判断。

后半段更像规格收束器：
确认事实、生成补丁、回看状态、推动文档合规。
```

这样可以同时满足两个目标：

- 保留 Requirement Analysis 的启发性和协作感。
- 保证最终产物仍然稳定收束到目标需求规格说明文档。
