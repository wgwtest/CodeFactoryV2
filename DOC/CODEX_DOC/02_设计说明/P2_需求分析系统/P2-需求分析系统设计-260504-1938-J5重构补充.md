# P2-需求分析系统设计-260504-J5重构补充

## 1. 文档定位

本文是《P2-需求分析系统设计》的 2026-05-04 补充设计，专门记录下一轮 J5 解耦重构的依据、目标、迁移顺序和验收判据。

本文不替代主设计文档。主设计文档中的 `6.6 需求分析会话与运算模块` 描述当前阶段的目标软件设计；本文描述“为什么要进入下一轮重构，以及从当前实现走向目标设计应怎样推进”。

因此，两份文档的关系如下：

| 文档 | 作用 | 内容边界 |
| --- | --- | --- |
| `P2-需求分析系统设计.md` | 主软件设计说明 | 描述目标模块、状态机、接口、类划分、契约对象和边界约束 |
| 本补充文档 | J5 重构执行依据 | 描述当前实现问题、目标依赖方向、迁移步骤和完成判据 |

主设计文档吸收本文中已经成立的设计概念，包括 `TurnContext`、显式依赖注入、规格投影服务、下一轮交互服务、多阶段调用日志和轮次执行结果契约。本文保留过程性判断，避免主设计文档变成重构流水账。

## 2. 当前实现问题

当前实现的外部 API 基本稳定，主要问题集中在内部依赖方向和类职责边界。

| 问题 | 当前表现 | 影响 | J5 处理原则 |
| --- | --- | --- | --- |
| 会话服务过重 | `RequirementAnalysisSessionService` 同时创建会话、序列化 DTO、装配子服务、暴露大量以下划线开头的委托方法 | 会话服务看起来像总控制器，其他服务难以独立测试 | 会话服务只保留会话生命周期、保存和 DTO 投影，把轮次所需能力显式注入轮次引擎 |
| 轮次引擎反向依赖上层对象 | `RequirementAnalysisTurnEngine` 通过上层服务回调输入归一化、组织器运行、完成度树更新等能力 | 类之间真实输入输出不清楚，重构风险被隐藏 | 将轮次引擎依赖改为构造函数注入的服务对象 |
| 轮次上下文没有独立对象 | 上一轮交互、用户输入、归一化输入、活动节点等在单个方法内临时拼装 | 组织器和模型提供方很难获得稳定上下文契约 | 拆出 `TurnContextBuilder` 和 `TurnContext` |
| 投影和收束职责混合 | 输出收束服务同时处理 patch 章节兜底、下一问题生成和影响节点投影 | 规格投影、下一轮交互和输出规范化边界混杂 | 拆出 `SpecProjectionService` 和 `NextInteractionService`，输出收束服务只做输出规范化 |
| 模型调用日志由轮次引擎内部生成 | 模型调用日志在轮次执行代码中直接组装 | 调用日志结构难以独立测试，也不利于多阶段模型调用 | 拆出 `ProviderCallLogService` |
| 目标阶段策略尚未独立 | 提示词解释型组织器和本地 runner 运行方式没有统一阶段策略对象 | `write_then_review` 等多阶段策略难以落地 | 引入 `TurnStrategyService` 与 `TurnStageExecutor` |

## 3. 目标依赖方向

J5 重构后的内部依赖必须从外到内单向流动，禁止子服务通过反向回调访问上层服务。

```text
RequirementAnalysisApplicationService
  -> RequirementAnalysisSessionService
    -> RequirementAnalysisSessionRepository
    -> RequirementSpecTreeService
    -> RequirementAnalysisTurnEngine
       -> TurnContextBuilder
       -> InputNormalizer
       -> InputRelationClassifier
       -> TurnStrategyService
       -> TurnStageExecutor
       -> RequirementAnalysisProviderCallService
       -> SpecProjectionService
       -> RequirementAnalysisSummaryArtifactService
       -> RequirementSpecTreeService
       -> RequirementAnalysisTurnOutputService
       -> NextInteractionService
       -> RequirementAnalysisTurnAuditService
       -> ProviderCallLogService
```

依赖方向约束：

- `RequirementAnalysisApplicationService` 只调用会话服务，不直接调用轮次引擎和模型提供方。
- `RequirementAnalysisSessionService` 负责创建会话、读取会话、保存会话和序列化会话 DTO。
- `RequirementAnalysisTurnEngine` 接收会话聚合对象和用户输入命令，返回 `TurnExecutionResult`，不直接保存仓储。
- `TurnContextBuilder` 只读取会话 payload 并构造 `TurnContext`，不调用模型。
- `RequirementAnalysisProviderCallService` 只调用模型、runner 或 mock，并返回候选输出和调用审计原料。
- `ProviderCallLogService` 专门把调用审计原料转成 `provider_logs[]` 条目。
- `SpecProjectionService` 只决定“本轮影响哪些规格节点”，不关闭节点。
- `RequirementSpecTreeService` 只初始化、查找和更新完成度树。
- `NextInteractionService` 只生成下一轮交互对象，不修改模型原始输出。
- `RequirementAnalysisTurnAuditService` 只生成审计对象，不回写会话。

## 4. 目标类与输入输出

J5 重构应优先落实以下类和对象。这里列的是编码目标，不要求一次性支持所有高级策略，但每个类必须在职责上可独立测试。

| 类 / 对象 | 类型 | 输入 | 输出 | 职责 |
| --- | --- | --- | --- | --- |
| `RequirementAnalysisSessionService` | 会话领域服务 | 会话创建命令、`session_id`、`TurnExecutionResult` | 会话详情 DTO、会话聚合对象 | 管理会话生命周期、初始状态、保存和序列化 |
| `RequirementAnalysisTurnEngine` | 轮次执行引擎 | `RequirementAnalysisSession`、`RequirementAnalysisTurnCreate` | `TurnExecutionResult` | 编排单轮处理链路，形成最终轮次结果 |
| `TurnContextBuilder` | 上下文构建服务 | 会话聚合对象、轮次 id、用户输入、上一轮快捷选项 | `TurnContext` | 构造本轮输入、上一轮交互、活动节点、近期上下文 |
| `TurnStrategyService` | 组织器策略解析服务 | 组织器描述包、`TurnContext` | `TurnStrategy` | 决定本轮采用单调用、双调用或本地 runner 策略 |
| `TurnStageExecutor` | 阶段执行服务 | 阶段定义、`TurnContext`、模型提供方配置 | `TurnStageResult` | 执行单个模型阶段或 runner 阶段 |
| `SpecProjectionService` | 规格投影服务 | `spec_tree`、active 节点、模型候选 patch / section | `SpecProjectionResult` | 判断本轮影响的规格节点，防止机械绑定 active 节点 |
| `RequirementAnalysisSummaryArtifactService` | 过程产物归并服务 | 候选输出、投影结果、现有问题事实 patch | `ArtifactUpdateResult` | 更新 facts、questions、patches、answer_summary |
| `RequirementSpecTreeService` | 完成度树服务 | 模板、组织器策略、投影结果、回答摘要 | `SpecTreeUpdateResult` | 初始化和更新完成度树 |
| `RequirementAnalysisTurnOutputService` | 输出规范化服务 | 模型输出、会话配置、投影结果 | 规范化模型输出、patch 兜底结果 | 保证输出字段完整且章节可追踪 |
| `NextInteractionService` | 下一轮交互服务 | 下一 open 节点、闭环判断、组织器候选建议、快捷选项规则 | `next_interaction` | 生成开放问题、选择题、自由继续或完成复核 |
| `RequirementAnalysisTurnAuditService` | 轮次审计服务 | `TurnContext`、输入关系、规格执行、状态变化、下一轮交互 | 当前 Turn 审计对象和 `decision_trace` | 解释本轮为何这样处理 |
| `RequirementAnalysisProviderCallService` | 模型调用服务 | 组织器、会话、`TurnContext`、阶段 prompt | `ProviderRunResult` | 调用 mock、DeepSeek、本地 runner |
| `ProviderCallLogService` | 调用日志服务 | 模型调用审计原料、最终服务输出、turn id | `ProviderCallLog` | 统一生成调用日志，支持多阶段调用 |

## 5. 核心内部契约

J5 重构应优先建立以下内部契约对象。它们可以先用 `dataclass` 或 Pydantic 模型实现；关键是字段稳定、含义清楚。

```text
TurnContext
  turn_id: str
  turn_index: int
  session_id: str
  topic: str
  template_id: str
  knowledge_package_id: str
  orchestrator_id: str
  provider_id: str
  model: str
  write_policy: str
  user_input: str
  normalized_input: dict
  previous_interaction: dict
  input_relation: dict
  spec_tree: list[dict]
  active_spec_node_id: str | None
  active_spec_node: dict
  questions: list[dict]
  facts: list[dict]
  patches: list[dict]
  last_quick_options: list[dict]
```

```text
ProviderRunResult
  provider_id: str
  model: str
  orchestrator_id: str
  orchestrator_mode: str
  normalized_output: dict
  raw_model_response: dict
  provider_request: dict
  provider_response: dict
```

```text
SpecProjectionResult
  projection_spec_node_id: str
  projection_spec_node: dict
  affected_spec_nodes: list[dict]
  fallback_used: bool
  reason: str
```

```text
ArtifactUpdateResult
  questions: list[dict]
  facts: list[dict]
  patches: list[dict]
  answer_summary: str
  source_question_id: str | None
```

```text
SpecTreeUpdateResult
  spec_tree: list[dict]
  closed_node_ids: list[str]
  active_spec_node_id: str | None
  next_spec_node: dict
```

```text
TurnExecutionResult
  turn: dict
  state_patch: dict
  provider_logs: list[dict]
```

契约对象约束：

- 契约对象可以包含字典载荷，但字段名称必须稳定。
- 契约对象不能持有数据库 session。
- 契约对象不能自己调用模型。
- 契约对象不能直接修改会话 payload，只能作为轮次引擎的输入输出。

## 6. 单轮执行目标流程

J5 重构后，一次 `add_turn` 的目标流程应明确为以下顺序：

```text
1. SessionService 读取 RequirementAnalysisSession
2. SessionService 创建 turn_id，并调用 TurnEngine.run_turn(session, payload)
3. TurnContextBuilder.build 生成 TurnContext
4. TurnStrategyService.resolve 读取组织器包和阶段策略
5. TurnStageExecutor / ProviderCallService 产生 ProviderRunResult
6. TurnOutputService.normalize 校验和补齐模型候选输出
7. SpecProjectionService.project 选择本轮投影节点
8. SummaryArtifactService.apply 生成 facts / questions / patches 更新
9. SpecTreeService.apply 关闭节点并计算下一 open 节点
10. NextInteractionService.build 生成 next_interaction
11. TurnAuditService.build 生成 previous_interaction / spec_execution / post_update_review / closure_decision / decision_trace
12. ProviderCallLogService.build 生成 provider_logs
13. TurnEngine 返回 TurnExecutionResult
14. SessionService.apply_turn_execution_result 原子更新 payload 并保存
```

该流程必须满足：

- 用户输入是 Turn 起点。
- 上一轮交互对象只是上下文，不是强制问题。
- 模型提供方输出是候选，不能直接写会话。
- 投影节点必须有审计原因。
- 下一轮交互对象必须在规格补充和补充后回看之后生成。
- 调用日志必须记录模型输入、模型输出、归一化输出和服务端最终采纳输出。

## 7. 迁移顺序

迁移必须小步推进，每一步都保持外部 API 和现有测试通过。

| 顺序 | 重构动作 | 验收点 |
| --- | --- | --- |
| 1 | 新增 `TurnContextBuilder` 和 `TurnContext`，把轮次内的上下文拼装搬出 | 轮次测试仍通过，轮次引擎不再直接拼装上一轮交互和标准输入 |
| 2 | 新增 `ProviderCallLogService`，把调用日志组装从轮次引擎移出 | 调用日志页面字段不变，模型调用日志测试通过 |
| 3 | 新增 `SpecProjectionService`，把投影节点和 affected node 逻辑集中 | 投影节点、受影响节点与现有行为一致 |
| 4 | 新增 `NextInteractionService`，把下一轮问题、快捷选项和 next interaction 生成集中 | 会话管理页快捷选项和当前 Turn 审计不变 |
| 5 | 改造轮次引擎构造函数，显式注入依赖，移除反向回调 | 静态扫描不再出现轮次引擎反向调用上层服务的代码 |
| 6 | 收缩 `RequirementAnalysisSessionService`，只保留会话创建、读取、保存、序列化和少量装配 | 业务规则不再新增到会话服务 |
| 7 | 引入 `TurnStrategyService` 和 `TurnStageExecutor`，为 `write_then_review` 多阶段策略预留接口 | mock、DeepSeek、本地 runner 均仍可启动会话并发送 Turn |

迁移期间禁止：

- 改动 `/api/requirement-analysis/*` 外部接口路径。
- 改动前端依赖的 `messages`、`turns`、`spec_tree`、`next_interaction`、`provider_logs` 字段名。
- 把 Lab 过程产物直接写入正式需求规格文档。
- 为了迁移而保留两套平行业务路径。

## 8. 重构完成判据

J5 解耦重构完成后，应满足以下检查项：

| 检查项 | 判定标准 |
| --- | --- |
| 依赖方向 | 轮次引擎不再反向依赖会话服务内部方法 |
| 会话服务职责 | 会话服务不再暴露大量轮次委托方法，只负责会话生命周期和 DTO 投影 |
| 上下文契约 | `TurnContext` 可被单测构造，并可作为模型提供方、投影、审计服务共同输入 |
| 投影职责 | 规格节点投影逻辑集中在 `SpecProjectionService`，并有独立测试覆盖 active 节点、章节匹配和兜底情况 |
| 下一轮交互 | `NextInteractionService` 可独立测试开放问题、选择题和完成复核三种输出 |
| 调用日志 | `ProviderCallLogService` 可独立测试 mock、DeepSeek、本地 runner 三类日志结构 |
| API 稳定 | 现有 Lab 前端不需要改字段即可继续运行 |
| 回归测试 | P2 Lab API、模块单测、后端全量测试全部通过 |
