# P2 需求分析系统设计 - 260508 Lab 模板实例运行时消费补充

**文档日期：** 2026-05-08

**文档性质：** 设计补充稿。本文用于约束 Lab 模板实例从文件资产进入会话运行时的链路，先作为独立补充依据，验证后再回填 `P2-需求分析系统设计.md`。

**关联文档：**

- `P2-需求分析系统设计.md`
- `P2-需求分析系统设计-260506-0250-Write阶段章节配置与规划约束补充.md`
- `P2-需求分析系统设计-260507-1256-Write产物重定义与模板约束补充.md`

## 1. 问题背景

Lab 已经把需求规格说明模板拆分为基础模板和自定义模板实例：

```text
DOC/JB_DOC/02-软件工厂产物模板中心/01-需求与设计主链模板/01-需求规格模板/
  基础模板/
  自定义模板/
```

其中基础模板是只读依据，自定义模板实例是 Lab 可新建、编辑、保存和删除的 Markdown 文件。

当前已完成的是模板资产管理链路：前端可以列出模板实例、读取 Markdown 正文、保存实例正文、删除实例文件。尚未完成的是模板运行链路：会话创建和轮次执行仍主要根据 `template_id` 提取 `81433` 或 `82259`，再回退到内置 `default_template_payload()` 或数据库 `RequirementAuthoringTemplate`。这会导致用户创建的 Markdown 模板实例只在配置页可见，不能稳定驱动完成度树、章节配置上下文和模型 Prompt 上下文。

该状态不满足“前端模板配置可真正影响 Lab 运行”的设计目标。

## 2. 设计目标

本补充目标是让 Lab 自定义模板实例成为会话运行时的有效输入，而不是仅作为可编辑文件存在。

目标态包括：

1. 会话启动使用启动参数区显式选中的模板实例 id。
2. 后端根据该 `template_id` 读取自定义模板实例 Markdown 和 manifest 元数据。
3. Markdown 模板实例被解析为结构化模板运行时对象。
4. 完成度树根据解析后的模板章节和条款创建。
5. 临时正文和结构化状态投影携带模板实例元数据，方便用户确认本会话使用了哪个模板实例。
6. 阶段运行上下文和 Provider 请求上下文携带模板实例身份、Markdown 摘要和解析后的章节结构。
7. 如果模板实例不存在或 Markdown 无法解析出有效条款，应阻断会话创建，不应静默回退到内置 81433 / 82259。

## 3. 核心概念

| 序号 | 中文概念 | 英文标识 | 类型 | 定义 |
| --- | --- | --- | --- | --- |
| 1 | 基础模板依据 | `BaseTemplate` | 文件资产 | 标准模板来源，只读维护，用于初始化模板实例，不直接作为 Lab 会话编辑对象。 |
| 2 | 模板实例 | `TemplateInstance` | 文件资产 + manifest 元数据 | 基于基础模板派生出的可编辑 Markdown 模板，是 Lab 启动会话时选择的模板对象。 |
| 3 | 模板运行时对象 | `TemplateRuntimePayload` | 运行时结构化对象 | 由模板实例解析得到，包含模板身份、来源、Markdown 正文、章节条款结构和解析诊断。 |
| 4 | 模板条款节点 | `TemplateClause` | 运行时条款对象 | 从 Markdown 标题解析出的二级或更深层条款，用于生成完成度树叶子节点和章节配置上下文。 |
| 5 | 模板解析诊断 | `TemplateParseDiagnostic` | 校验结果 | 描述 Markdown 中无法识别、重复编号、缺少条款或层级异常等问题。阻断项必须阻止会话创建。 |

## 4. 运行链路

### 4.1 模板管理链路

```text
GET /template-bases
  -> RequirementAnalysisTemplateService.list_base_templates
  -> 读取 基础模板/

GET /templates
  -> RequirementAnalysisTemplateService.list_templates
  -> 读取 自定义模板/manifest.json

GET /templates/{template_id}
  -> RequirementAnalysisTemplateService.get_template
  -> 读取 自定义模板/{template_id}.md

POST /templates
  -> 从基础模板复制 Markdown
  -> 写入 自定义模板/{new_template_id}.md
  -> 更新 manifest
```

该链路只负责文件资产管理，不创建会话、不生成完成度树、不拼装模型 Prompt。

### 4.2 会话运行链路

```text
POST /sessions(template_id)
  -> RequirementAnalysisTemplateService.resolve_runtime_payload(template_id)
  -> MarkdownTemplateParser.parse(...)
  -> TemplateRuntimePayload
  -> RequirementSpecTreeService.new_spec_tree(template_runtime_payload, orchestrator_id)
  -> WorkingDocumentService.initialize(..., template_runtime_payload)
  -> DecisionStateService.initialize(..., template_runtime_payload 摘要)
  -> 保存到 session.payload.template_runtime
```

运行时不得只根据 `template_id` 中的数字选择内置结构。`template_id` 必须解析到一个模板实例；解析失败应返回 400。

### 4.3 轮次上下文链路

```text
TurnContextBuilder
  -> 从 session.payload.template_runtime 读取模板运行时对象
  -> 放入 TurnContext.template_runtime

StageRuntimeContextBuilder
  -> 读取 TurnContext.template_runtime
  -> 放入 prompt context
  -> ChapterConfigurationContextBuilder 基于 spec_tree + template_runtime 生成章节配置上下文
```

模型阶段看到的模板上下文必须来自已选模板实例，而不是硬编码 81433 默认章节。

## 5. 对象结构

### 5.1 `TemplateRuntimePayload`

```json
{
  "template_id": "xg-template-81433-default",
  "template_code": "81433",
  "base_template_id": "81433号",
  "base_template_name": "软件级需求规格说明模板",
  "name": "默认运算软件需求规格说明模板实例",
  "description": "基于 81433 扩充的 Lab 模板实例。",
  "format": "markdown",
  "content": "# 81433 软件级需求规格说明模板...",
  "sections": [
    {
      "section_id": "1",
      "title": "1 总则",
      "heading_level": 2,
      "clauses": [
        {
          "clause_id": "REQ-1.1",
          "title": "编写目的",
          "heading": "1.1 编写目的",
          "heading_level": 3,
          "source_heading": "### 1.1 编写目的"
        }
      ]
    }
  ],
  "parse_diagnostics": []
}
```

### 5.2 解析规则

1. Markdown 一级标题 `#` 视为模板标题，不进入完成度树。
2. `## 1 总则`、`## 2 项目概述` 这类二级标题解析为模板章节。
3. `### 1.1 编写目的`、`### 3.4 空间分析工具` 这类三级及更深标题解析为条款节点。
4. 条款 id 统一生成 `REQ-{编号}`，例如 `1.1` 生成 `REQ-1.1`。
5. 标题编号以 Markdown 文本为准，不由 Python 自行猜测或重排。
6. 若一个章节下没有任何条款，可将该章节自身生成一个条款节点，条款 id 为 `REQ-{section_id}`，但必须在诊断中标记为 `section_as_clause`。
7. 若 Markdown 中没有可解析章节或条款，返回阻断诊断，禁止创建会话。

解析服务只做标题结构识别，不判断业务语义，不决定章节应写什么内容。

## 6. 类与接口调整

### 6.1 `RequirementAnalysisTemplateService`

新增职责：

- `resolve_runtime_payload(template_id: str) -> dict | None`
- 读取 manifest 实例元数据和 Markdown 正文。
- 调用 Markdown 模板解析服务。
- 返回 `TemplateRuntimePayload`。

不新增职责：

- 不调用模型。
- 不生成完成度树状态。
- 不判断用户输入应写入哪个章节。

### 6.2 `MarkdownTemplateParser`

新增服务：

| 项 | 内容 |
| --- | --- |
| 文件 | `apps/api/app/requirement_analysis/template_parser.py` |
| 类型 | Markdown 模板解析服务 |
| 主要输入 | 模板实例元数据、Markdown 正文 |
| 主要输出 | `sections`、`parse_diagnostics` |
| 主要方法 | `parse` |
| 功能说明 | 将模板实例 Markdown 的标题层级解析为章节和条款结构。 |
| 边界说明 | 不做业务语义判断，不按固定 81433 章节重排，不生成 Prompt。 |

### 6.3 `RequirementSpecTreeService`

调整职责：

- `new_spec_tree` 支持接收 `template_runtime_payload`。
- `resolve_template_payload` 优先使用模板运行时对象。
- 只有在兼容旧测试或旧 API 且没有模板运行时对象时，才允许回退数据库模板或内置模板。

会话创建路径不得使用该兼容回退。

### 6.4 `WorkingDocumentService`

调整 `initialize`：

- 输入增加可选 `template_runtime_payload`。
- `working_document` 中保存 `template_id`、`template_name`、`template_code`、`base_template_id`。
- 标题优先使用模板实例名称，而不是只拼接 `template_id`。

### 6.5 `TurnContextBuilder` 与 `StageRuntimeContextBuilder`

调整职责：

- `TurnContext` 增加 `template_runtime` 字段。
- `StageRuntimeContext.to_prompt_context()` 增加 `template_runtime` 字段。
- `_turn_context` 增加模板实例摘要，便于调用日志查看当前 turn 到底使用了哪个模板。

## 7. 错误处理

| 场景 | 处理 |
| --- | --- |
| 启动会话选择的模板实例不存在 | `/sessions` 返回 400，提示模板实例不存在 |
| 模板实例 Markdown 文件缺失 | `/sessions` 返回 400，提示模板实例正文缺失 |
| Markdown 没有可解析章节或条款 | `/sessions` 返回 400，提示模板结构不可用 |
| Markdown 存在重复条款编号 | 返回 400 或阻断诊断；首版按阻断处理 |
| 模板管理页读取模板失败 | 模板详情接口返回 404，不影响其他实例 |

禁止静默回退到默认 81433。静默回退会使用户误以为自定义模板已经生效。

## 8. 验收标准

1. 在测试中创建一个自定义模板实例，Markdown 内包含独特条款，例如 `### 9.9 自定义验收观察点`。
2. 使用该模板实例启动 Lab 会话。
3. 新会话的 `spec_tree` 必须包含 `SPEC-REQ-9.9`。
4. 新会话的 `active_spec_node_id` 必须来自该模板实例解析结果。
5. `working_document.template_id`、`working_document.template_name` 必须与所选模板实例一致。
6. 执行一轮 turn 后，Provider 调用日志中的 `provider_request.prompt_bundle.context_json` 或等价上下文字段必须包含该模板实例身份和 `REQ-9.9` 章节结构。
7. 如果模板实例不存在，创建会话必须失败，不能继续生成默认完成度树。
