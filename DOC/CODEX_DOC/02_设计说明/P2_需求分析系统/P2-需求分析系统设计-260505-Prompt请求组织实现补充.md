# P2-需求分析系统设计-260505-Prompt请求组织实现补充

## 1. 目的

本文档不是 `P2-需求分析系统设计.md` 的替代版本，也不是主设计文档的直接改写稿。
它只回答一个具体问题：

> 在当前 `P2` 需求分析组织器 Lab 中，需求分析组织器应该如何把一轮 `turn` 的用户输入、会话状态、任务定义、文档结构和输出约束，组织成真正可执行、可审计、可替换的模型请求？

本轮补充的核心调整是：输入类型判断不能继续作为 `write` 阶段里的附属动作，而必须提升为独立的模型调用阶段；下一步交互规划也不能继续由规则树机械生成，而应成为独立的大模型阶段。
目标工作流从原先的两阶段升级为四阶段：

1. `intent_understanding`：意图理解阶段，判断用户这一轮到底想干什么，并产出后续阶段的任务定义候选。
2. `write`：正文补写阶段，基于意图理解结果和正式任务定义生成需求规格临时正文 patch。
3. `review_after_apply`：应用后回看阶段，基于已经写入临时正文的结果判断本轮是否真正补写到位。
4. `next_interaction_planning`：下一步交互规划阶段，综合 review 结果、临时正文和整体文档结构，决定下一轮应该问什么、是否给选择题或确认题。

本文档只描述上述四阶段 Prompt 组织的目标态、运行时对象、代码落点和审计展示要求。
评审通过后，稳定结论再归并到主设计文档的需求分析运算模块、轮次执行设计、模型调用边界、内部功能组成与前端审计展示章节。

## 2. 当前实现的根本问题

### 2.1 意图判断被错误地塞进了 `write`

当前实现把“用户想做什么”隐含在 `write` 阶段中，让模型同时承担：

- 判断用户输入类型；
- 理解和上一轮建议的关系；
- 生成正文 patch；
- 生成下一轮建议。

这会直接导致四类问题：

1. 输入类型判断不稳定，经常把用户真实输入解释成“回答当前 active 节点”。
2. `write` 阶段容易机械绑定 active 节点，而不是围绕真实输入构建文档内容。
3. 首轮产品构想无法稳定触发“先搭正文骨架”的策略。
4. 阶段任务定义没有正式来源，只能在 prompt 里临时暗示，导致后续阶段没有可靠上游。

因此，`write` 阶段不应再承担主要意图判断职责。意图理解必须成为 `write` 前的独立模型阶段。

### 2.2 模型请求组装入口分散

当前模型请求材料主要在以下位置被拼装：

- `apps/api/app/requirement_analysis/deepseek_client.py`
- `apps/api/app/orchestrators/stage_prompt_bundle_builder.py`
- `apps/api/app/orchestrators/runner_host.py`

这导致：

- 阶段任务定义没有独立对象；
- Prompt 的业务含义和 Provider 调用细节混在一起；
- `DeepSeekRequirementAnalysisClient` 直接决定了 `write` / `review` 两阶段的上下文形状和输出格式要求。

### 2.3 输出格式要求仍被写死在 Provider 适配器里

当前 `DeepSeekRequirementAnalysisClient._build_prompt_bundle()` 直接在代码里写了 `write` 和 `review_after_apply` 的 `output_schema`。

这会导致：

- 组织器包里的 `schemas/*.json` 退化为“可选资产”；
- 组织器无法真正通过包资产替换输出约束；
- Provider 适配器承担了本不该承担的业务职责。

### 2.4 当前 Prompt 更像说明性拼接，不是任务驱动型请求

当前 `StagePromptBundleBuilder` 主要把这些内容串起来：

- `base_contract_text`
- `ORCHESTRATOR.md`
- `policy.md`
- `stage_prompt_text`
- `context_json`
- `adoption_policy_json`
- `schema_json`

但缺少：

- 独立意图理解结果；
- 正式阶段任务定义；
- 目标文档结构；
- 当前阶段质量约束；
- 首轮建骨架策略；
- 基于 review 结果和整体文档结构的下一步交互规划。

结果是模型看到了组织器介绍和原则，却没有看到足够明确的本轮任务。

## 3. 四阶段模型调用总设计

### 3.1 四阶段工作流总览

四阶段工作流如下：

```text
TurnContextBuilder
  -> IntentStageContextBuilder
  -> 模型调用 1：intent_understanding
      -> IntentUnderstandingResult
  -> TargetDocumentStructureBuilder
  -> StageTaskDefinitionBuilder
  -> StageQualityConstraintBuilder
  -> StageRuntimeContextBuilder(stage=write)
  -> 模型调用 2：write
      -> document_patch / confirmed_facts_delta / open_questions_delta
  -> WorkingDocumentService.apply_patches
  -> StageRuntimeContextBuilder(stage=review_after_apply)
  -> 模型调用 3：review_after_apply
      -> target_review / global_review / review_annotations
  -> StageRuntimeContextBuilder(stage=next_interaction_planning)
  -> 模型调用 4：next_interaction_planning
      -> next_interaction_plan / quick_options / user_prompt
  -> TurnDecisionService
  -> TurnAuditService / ProviderCallLogService
```

### 3.2 四个模型阶段的职责边界

| 阶段 | 主要问题 | 输入重点 | 输出重点 | 不能做的事 |
| --- | --- | --- | --- | --- |
| `intent_understanding` | 用户这一轮到底想干什么？ | 用户原文、上一轮交互、快捷选项、当前正文摘要、规格树摘要、当前 active 节点 | 用户意图、输入类型、与上一轮关系、目标章节候选、阶段任务定义候选、质量档位建议 | 不生成正文 patch，不回看正文，不设计最终下一轮交互 |
| `write` | 根据意图和任务定义，应该写哪些需求规格正文？ | `IntentUnderstandingResult`、目标文档结构、质量约束、当前 turn 上下文、已有正文 | 正文 patch、确认事实、待确认问题、写入说明候选 | 不重新主导意图判断，不关闭节点，不做应用后 review，不设计最终下一轮交互 |
| `review_after_apply` | 应用后的临时正文是否满足本轮写作任务？ | `working_document_after_apply`、本轮修订片段、意图理解结果、任务定义、目标章节最低要求 | 目标范围回看、全局回看、剩余缺口、审计注记 | 不生成正文 patch，不把 review 建议直接写入正文，不设计最终下一轮交互 |
| `next_interaction_planning` | 下一轮最值得怎么推进？ | `ReviewAfterApplyResult`、临时正文、整体文档结构、规格树状态、用户沟通负担约束 | 下一步策略、用户说明、下一轮主问题、快捷选项、规划理由 | 不修改正文，不替代 review，不关闭节点 |

### 3.3 四阶段之间的控制关系

四阶段不是四个彼此独立的 prompt 串联，而是明确的数据控制链：

1. `intent_understanding` 是本轮任务来源。它输出的 `IntentUnderstandingResult` 是 `write` 和 `review_after_apply` 的上游依据。
2. `StageTaskDefinition` 不由 `write` 阶段临时猜测，而由服务端基于 `IntentUnderstandingResult`、组织器策略、模板结构和当前正文状态生成。
3. `write` 只消费 `StageTaskDefinition`，不得重新定义本轮目标。如果模型认为任务定义与用户输入冲突，只能输出风险或注记。
4. `review_after_apply` 只审查已经应用后的临时正文是否满足本轮任务定义和质量约束，不直接生成正文 patch。
5. `next_interaction_planning` 只在 review 之后运行，综合 review 结果和整体文档结构，生成下一步交互计划。
6. `TurnDecisionService` 只采用和校验 `next_interaction_planning` 的结果，不再用规则树机械生成最终下一题；但它仍负责状态写入、失败处理和审计落库。

因此，真实控制流应是：

```text
用户输入
  -> 意图理解
  -> 服务端任务定义
  -> 文档补写
  -> 临时正文应用
  -> 应用后回看
  -> 下一步交互规划
  -> 服务端轮次决策
```

这解决的是原先“模型一边猜用户意图、一边写二三十个字、一边匆忙抛下一题”的问题。

### 3.4 哪些步骤调用大模型，哪些步骤不调用

在目标态中，只有四个步骤调用大模型：

1. `intent_understanding`
2. `write`
3. `review_after_apply`
4. `next_interaction_planning`

其他步骤都是服务端确定性逻辑：

- `TurnContextBuilder`：整理会话上下文；
- `TargetDocumentStructureBuilder`：从模板、规格树和临时正文生成目标文档结构；
- `StageTaskDefinitionBuilder`：把意图理解结果映射成正式阶段任务定义；
- `StageQualityConstraintBuilder`：根据任务模式生成质量约束；
- `WorkingDocumentService.apply_patches`：把 patch 应用到临时正文；
- `TurnDecisionService`：校验下一步交互计划，写入下一轮交互和当前轮闭环状态。

这条边界必须固定，否则系统仍会退化为“模型在单轮里包打天下，服务端只做胶水”。

## 4. 阶段一：意图理解阶段设计

### 4.1 阶段定位

`intent_understanding` 是一轮 `turn` 的第一个模型调用。它负责把用户自然输入转化为可执行的需求分析任务。

该阶段必须实现两项功能：

1. 判断用户想要干什么。
2. 为后续 `write` 和 `review_after_apply` 生成任务定义候选。

这不是 `write` 阶段的“模型辅助判断”，而是独立阶段输出。后续阶段不得绕过它重新发明本轮任务。

### 4.2 输入数据来源

`intent_understanding` 的输入来自：

| 输入 | 来源 | 用途 |
| --- | --- | --- |
| 用户原文 | `RequirementAnalysisTurnCreate.user_input` | 判断本轮真实意图 |
| 归一化输入 | `InputNormalizer.normalize_input()` | 识别快捷选项、用户文本摘要 |
| 上一轮交互 | `TurnContext.previous_interaction` | 判断是回答、偏离、反驳还是自由补充 |
| 上轮快捷选项 | `TurnContext.last_quick_options` | 判断是否命中 A/B/C 选项 |
| 当前正文摘要 | `TurnContext.working_document` 摘要 | 判断是否首轮空白建文档 |
| 当前规格树摘要 | `TurnContext.spec_tree` 摘要 | 给出目标章节候选 |
| 当前 active 节点 | `TurnContext.active_spec_node` | 作为默认焦点，但不是强制解释框架 |
| 已确认事实 / 待确认问题 | `TurnContext.facts` / `questions` | 避免重复判断和重复追问 |

这些输入不是由 prompt 自己拼凑。目标实现中应由 `IntentStageContextBuilder` 生成 `IntentStageContext`，再由 `StagePromptBundleBuilder` 渲染成模型请求。

建议 `IntentStageContext` 至少包含：

- `turn_id`
- `user_input`
- `normalized_input`
- `server_precheck`
- `previous_interaction`
- `previous_quick_options`
- `previous_suggested_question`
- `working_document_snapshot`
- `spec_tree_snapshot`
- `active_spec_node`
- `known_facts_summary`
- `open_questions_summary`

其中 `server_precheck` 是服务端先行整理的硬事实，不是模型判断，至少包含：

- `exact_option_match`
- `option_prefix_match`
- `option_and_extra_text_present`
- `working_document_is_empty`
- `input_length_level`
- `contains_negation_or_correction`
- `contains_product_concept_signal`
- `contains_section_reference_signal`

### 4.3 意图理解输出对象

建议新增对象：

```python
IntentUnderstandingResult
```

建议字段：

- `user_goal_summary`
- `input_type`
  - `first_round_product_concept`
  - `answer_previous_question`
  - `section_supplement`
  - `option_answer`
  - `option_answer_with_supplement`
  - `ignore_options_new_topic`
  - `topic_shift`
  - `challenge_or_correction`
  - `free_supplement`
- `relation_to_previous_interaction`
- `option_handling`
- `matched_option`
- `supplemental_facts`
- `target_section_candidates`
- `document_strategy`
  - `bootstrap_document`
  - `write_targeted_sections`
  - `revise_existing_content`
  - `collect_clarification`
- `write_task_candidate`
- `review_focus_candidate`
- `ambiguities`
- `confidence`
- `reason`

其中 `write_task_candidate` 和 `review_focus_candidate` 不是最终任务定义，只是模型给出的候选。服务端必须通过 `StageTaskDefinitionBuilder` 将其映射为正式 `StageTaskDefinition`。

建议 `matched_option` 使用结构对象，而不是只保存 `"A"`：

- `option_id`
- `option_label`
- `option_content`
- `matched_by`
  - `exact_id`
  - `exact_label`
  - `semantic`
  - `none`

这样可以避免用户点击 `A` 后，系统误判为“未完全照搬建议”。

### 4.4 组合意图与忽略选项的判断

意图理解必须显式处理“用户输入和上一轮选项之间的关系”，不能只判断是否命中 A/B/C。

至少需要区分四种情况：

| 类型 | 判断含义 | 示例 | 后续处理 |
| --- | --- | --- | --- |
| `option_answer` | 用户只选择了上一轮选项，几乎没有新增事实 | “A” 或 “选择 A” | 采用该选项对应的任务定义 |
| `option_answer_with_supplement` | 用户同意或选择了某个选项，同时补充了关键事实、限制或例外 | “A。另外这个系统主要给指挥人员看，还要支持态势分析工具。” | 既采用选项方向，又把新增事实写入 `supplemental_facts`，并驱动 write 做插入或扩写 |
| `ignore_options_new_topic` | 用户没有承接上一轮选项，而是直接开始讲新的系统、章节、约束或纠错内容 | 上一轮给 A/B/C，用户直接说“我现在先说部署环境...” | 不强行解释为回答选项；以用户新输入为本轮主意图 |
| `challenge_or_correction` | 用户明确否定、纠正或质疑上一轮选项或系统判断 | “不是这个意思，你理解错了...” | 以纠错为主，必要时修订已有正文或任务方向 |

`option_answer_with_supplement` 是组合意图，不是普通 `option_answer`。它的关键要求是：

1. `matched_option` 记录用户承接了哪个选项。
2. `supplemental_facts` 记录用户额外补充了哪些事实。
3. `write_task_candidate` 必须同时包含“选项方向”和“补充事实写入任务”。
4. `StageTaskDefinitionBuilder` 不能只按选项模板生成任务，还要把 `supplemental_facts` 转成目标章节或正文插入要求。

`ignore_options_new_topic` 也不是失败场景。它表示用户合法地跳过了上一轮建议，系统必须尊重用户输入，把本轮主意图切换到新内容上。此时上一轮选项只能作为背景，不得强行进入 `write` 的主任务。

### 4.5 输入类型判断方式

输入类型判断必须是“模型阶段 + 服务端校验”，不是之前文档里写的轻量辅助判断。

建议规则如下：

1. 服务端先做硬事实证据整理：
   - 快捷选项精确命中；
   - 快捷选项前缀命中；
   - 用户是否在选项后追加了自由文本；
   - 正文是否为空；
   - 用户输入长度；
   - 是否包含明显否定或改题表达。
2. `intent_understanding` 模型基于这些证据输出完整意图判断。
3. 服务端校验模型输出是否合法：
   - `input_type` 必须在枚举内；
   - `option_answer_with_supplement` 必须同时有 `matched_option` 和 `supplemental_facts`；
   - `ignore_options_new_topic` 不得再强制绑定上一轮选项；
   - `target_section_candidates` 必须能映射到模板或规格树；
   - 若模型判断与硬事实冲突，写入审计并驳回该意图结果；允许重新调用一次意图理解，仍失败则本轮停止，不进入 `write`。
4. 最终写入 `IntentUnderstandingResult`，作为后续 `write` 和 `review` 的权威输入。

服务端在这里的职责是提供证据和做合法性校验，不是替代大模型理解用户真实意图。尤其是组合意图、忽略选项、新话题、纠错等语义判断，必须由 `intent_understanding` 模型阶段完成。

### 4.6 意图理解阶段 Prompt 资产

建议新增组织器资产：

```text
prompts/intent_understanding.system.md
prompts/intent_understanding.user.md
schemas/intent_understanding.output.schema.json
adoption/intent_understanding.adoption.json
```

`intent_understanding.system.md` 必须强调：

- 你只判断本轮用户意图和任务策略，不写正文；
- active 节点只是参考，不是强制解释框架；
- 若用户输入是首轮产品构想，应识别为 `first_round_product_concept`；
- 若用户选择了选项但追加了关键事实，应识别为 `option_answer_with_supplement`；
- 若用户没有承接上一轮选项而直接讲新内容，应识别为 `ignore_options_new_topic` 或更具体的新输入类型；
- 必须输出后续 `write` 阶段可用的任务候选；
- 不要生成面向用户的长回复。

`intent_understanding.user.md` 必须要求模型输出：

- 用户到底想建设、修改、补充、反驳还是选择；
- 本轮是否应进入首轮建骨架；
- 本轮是否承接、组合承接、忽略或反驳了上一轮选项；
- 如果是组合承接，新增事实是什么；
- 如果是忽略选项，新主线是什么；
- 本轮应优先影响哪些需求规格章节；
- 后续 write 应写什么、不该写什么；
- review 应重点审查什么。

### 4.7 意图理解 Prompt 的组成

`intent_understanding` 的模型请求应由以下部分组成：

| 组成 | 来源 | 作用 |
| --- | --- | --- |
| 基础输出契约 | `prompts/base_contract.md` | 要求只输出 JSON，不输出解释性正文 |
| 阶段系统 Prompt | `prompts/intent_understanding.system.md` | 定义本阶段只做意图和任务候选判断 |
| 阶段用户 Prompt | `prompts/intent_understanding.user.md` | 指示模型如何读取阶段上下文并填充输出对象 |
| 阶段上下文 JSON | `IntentStageContextBuilder` | 提供用户输入、上一轮交互、正文状态、规格树摘要 |
| 输出格式要求 | `schemas/intent_understanding.output.schema.json` | 限定模型返回结构 |
| 结果采用策略 | `adoption/intent_understanding.adoption.json` | 定义服务端如何采纳、校验或驳回结果 |

本阶段不应直接塞入完整 `ORCHESTRATOR.md`。组织器定位和维护说明对人工审阅有价值，但不是每次模型请求都需要的执行材料。模型请求应读取“本阶段需要的规则”，而不是把组织器说明全文拼进去。

### 4.8 意图理解结果采用策略

`IntentUnderstandingResult` 的采用必须分三层：

1. 结构校验：字段是否符合输出格式要求，枚举值是否合法，目标章节是否存在。
2. 硬事实校验：如果用户精确点击快捷选项，则 `matched_option` 不得为空；如果用户输入包含选项前缀和额外文本，则不得简单采纳为纯 `option_answer`；如果临时正文为空且用户输入是产品构想，不能降级成普通局部补充。
3. 策略映射：将 `input_type`、`document_strategy` 和任务候选映射到服务端可执行的 `task_mode`。

模型输出不应直接进入 `write`。正式进入 `write` 的是服务端采纳后的 `IntentUnderstandingResult`。

### 4.9 意图理解阶段失败处理

本系统的核心能力依赖大模型意图理解。如果 `intent_understanding` 阶段无法调用模型、模型服务不可用、认证失败、网络失败、响应超时或输出无法解析，本轮不应继续进入 `write`。

失败处理原则如下：

1. 不使用“输入较长就当作首轮产品构想”等规则替代模型理解。
2. 不回退到旧的 `write` 自行猜意图模式。
3. 不生成正文 patch。
4. 不更新临时正文、规格树、事实列表和待确认问题。
5. 向前端返回明确错误，并在调用日志中记录失败阶段、失败原因和原始错误摘要。

也就是说，模型不可用时，这一轮直接失败结束。服务端可以保存失败日志，但不能假装已经完成了需求理解。

## 5. 阶段二：文档 write 阶段设计

### 5.1 阶段定位

`write` 阶段只负责根据 `IntentUnderstandingResult` 和 `StageTaskDefinition` 生成可应用到临时正文的候选内容。

它不再负责主导意图判断。若发现意图结果明显不合理，可以输出 `annotations` 或 `risks`，但不能重新定义整轮任务。

### 5.2 write 阶段输入

`write` 阶段输入必须包含：

- `TurnContext`
- `IntentUnderstandingResult`
- `StageTaskDefinition`
- `TargetDocumentStructure`
- `StageQualityConstraints`
- 当前临时正文摘要
- 当前目标章节要求

目标实现中，`write` 阶段上下文由 `StageRuntimeContextBuilder(stage=write)` 生成，不由 `DeepSeekRequirementAnalysisClient` 或 prompt 文本临时拼装。

建议 `write` 阶段上下文包含：

- `turn_context_evidence`
- `intent_understanding_result`
- `stage_task_definition`
- `target_document_structure`
- `stage_quality_constraints`
- `working_document_before_write`
- `current_target_sections`
- `known_facts_summary`
- `open_questions_summary`
- `previous_revision_summary`

### 5.3 write 阶段输出

`write` 阶段输出仍以结构化结果为主：

- `organizer_interpretation`
- `assistant_message`
- `confirmed_facts_delta`
- `open_questions_delta`
- `document_patch`
- `annotations`
- `risks`
- `confidence`

但输出质量约束必须由 `StageQualityConstraints` 强化，不能只靠一句“不要匆忙跳题”。
注意：`write` 不再承担最终下一步问题和快捷选项设计职责。历史上由 `write` 输出的 `next_suggestion`、`quick_options` 不应继续作为目标态字段，应迁移到 `next_interaction_planning` 阶段。

### 5.4 首轮建骨架模式

当 `IntentUnderstandingResult.input_type = first_round_product_concept` 且临时正文为空或接近为空时，`StageTaskDefinitionBuilder` 必须生成：

- `task_mode = first_round_bootstrap`
- `min_patch_count >= 2`
- 目标章节至少覆盖：
  - 系统目标 / 建设目的；
  - 系统能力范围；
  - 待确认关键问题。

该模式下，`write` 阶段不得只生成一句摘要。它必须优先写正文，再说明本轮实际补写了什么。

对于用户测试输入：

```text
我希望创建一个态势分析系统。这个态势分析系统里面要有态势的展示，要有一些一系列的这种态势分析工具。你比如说地理信息的分析工具、同时量算、坡度，还有一些这个部署的这个分析系统。啊，这个，但是当前的用户啊、使用模式啊，我都没有想清楚，希望你来一块帮我想清楚
```

意图理解阶段应判断为：

- `input_type = first_round_product_concept`
- `document_strategy = bootstrap_document`
- 用户已给出系统类型、能力方向和不确定点；
- 用户希望系统帮助一起收束用户角色和使用模式。

因此 `write` 阶段的任务不应是追问“谁使用系统”，也不应只写一句“补充总则”。它应先形成一个初始需求规格正文骨架，例如覆盖建设目标、能力范围、待确认使用角色与使用模式，再把下一轮问题建立在这个正文基础上。

### 5.5 write Prompt 的组成

`write` 阶段的模型请求应由以下部分组成：

| 组成 | 来源 | 作用 |
| --- | --- | --- |
| 基础输出契约 | `prompts/base_contract.md` | 要求只返回 JSON |
| 阶段系统 Prompt | `prompts/write.system.md` | 定义只负责正文补写，不重新定义意图 |
| 阶段用户 Prompt | `prompts/write.user.md` | 指示模型根据任务定义生成 patch |
| 意图理解结果 | `IntentUnderstandingResult` | 作为本轮任务来源 |
| 阶段任务定义 | `StageTaskDefinition` | 规定本轮写什么、不写什么 |
| 目标文档结构 | `TargetDocumentStructure` | 告诉模型可写章节、锚点和最低要求 |
| 阶段质量约束 | `StageQualityConstraints` | 限定最小补写深度和助手回复顺序 |
| 当前临时正文 | `WorkingDocumentSnapshot` | 避免重复写、用于增量补充 |
| 输出格式要求 | `schemas/write.output.schema.json` | 限定返回结构 |
| 结果采用策略 | `adoption/write.adoption.json` | 规定 patch、事实、问题如何进入后处理 |

write Prompt 的核心不是“组织器定位”或“适用场景”，而是本轮可执行任务。它必须让模型明确看到：

- 本轮用户输入已被理解为什么；
- 服务端要求本轮写哪些章节或正文块；
- 最低输出深度是什么；
- 哪些内容应该写入正文；
- 哪些不确定项应该作为待确认问题保留。

### 5.6 write 结果采用策略

write 模型输出进入系统前必须经过服务端采用策略：

1. `document_patch` 必须有合法目标锚点；没有锚点时由 `TargetDocumentStructure` 兜底映射，而不是默认塞到 active 节点。
2. `assistant_message` 必须先说明本轮实际写入内容；如果模型只输出下一题，服务端应降级或追加实际写入摘要。
3. `confirmed_facts_delta` 和 `open_questions_delta` 只更新过程产物，不直接决定规格树关闭。
4. `write` 不得直接关闭节点；关闭判断只能发生在应用后 review、下一步交互规划和轮次决策之后。

## 6. 阶段三：应用后 review 阶段设计

### 6.1 阶段定位

`review_after_apply` 阶段只基于已经应用到临时正文后的内容进行审查。

它的审查对象不是：

- 用户原始输入；
- `write` 阶段输出；
- 模型自己对 patch 的评价。

它的审查对象必须是：

- `working_document_after_apply`
- 本轮修订片段；
- `IntentUnderstandingResult`
- `StageTaskDefinition`
- `TargetDocumentStructure`
- `StageQualityConstraints`

### 6.2 review 阶段输入

必须包含：

- 应用后的临时正文；
- 本轮命中的正文块；
- 本轮新增修订片段；
- 意图理解结果；
- 本轮任务定义；
- 目标章节最低成文要求。

目标实现中，review 阶段上下文由 `StageRuntimeContextBuilder(stage=review_after_apply)` 在 patch 已应用后生成。它必须读取应用后的临时正文，而不是读取 write 输出自评。

### 6.3 review 阶段输出

输出：

- `compliance_result`
- `blocking_findings`
- `blocking_reasons`
- `written_fact_summary`
- `target_review`
- `global_review`
- `rewrite_advice`
- `review_annotations`
- `planning_evidence`
- `confidence`

Review 的判断标准必须来自本轮任务定义和质量约束。
例如首轮建骨架时，如果正文没有形成系统目标、能力范围和关键待确认问题，就不能判定为充分。

这里要特别强调：`review_after_apply` 的职责只是评估“刚才写入的内容是否满足本轮写作任务”，不是决定“下一轮问什么”。
也就是说，review 可以指出：

- 本轮写得够不够；
- 本轮到底写入了哪些事实；
- 具体缺了什么；
- 卡在哪个要求、章节或信息缺口上；
- 为什么被卡住；
- 这些卡点是否会影响后续交互规划；
- 哪些地方与任务定义冲突；
- 如果继续改写，应该重点改哪里。

但 review 不应该直接负责选择题设计、下一轮主问题设计或用户沟通策略选择。

建议 `ReviewAfterApplyResult` 至少包含以下结构：

```json
{
  "compliance_result": {
    "status": "pass|partial|fail",
    "reason": "本轮应用后的正文是否满足 StageTaskDefinition 的简要判断",
    "confidence": "low|medium|high"
  },
  "written_fact_summary": [
    {
      "fact": "本轮已经实际写入临时正文的事实",
      "source": "user_input|write_patch|existing_document",
      "anchor_path": "写入位置"
    }
  ],
  "blocking_findings": [
    {
      "blocker_id": "B-001",
      "severity": "low|medium|high",
      "blocked_requirement": "被卡住的任务目标或质量要求",
      "evidence": "基于应用后正文看到的证据",
      "missing_or_problematic_content": "缺失、含混、冲突或写得不够的内容"
    }
  ],
  "blocking_reasons": [
    {
      "blocker_id": "B-001",
      "reason": "为什么这会卡住本轮任务",
      "needs_user_input": true,
      "can_be_fixed_by_rewrite": false
    }
  ],
  "planning_evidence": {
    "must_continue_current_gap": true,
    "safe_to_advance_next_topic": false,
    "recommended_planning_focus": "继续确认用户角色和使用模式",
    "facts_for_next_interaction": [
      "系统目标和能力范围已有初稿",
      "用户角色和使用模式仍缺关键事实"
    ]
  }
}
```

其中 `planning_evidence` 不是下一步规划结论，而是给 `next_interaction_planning` 使用的审查证据。
它只能说明“有哪些事实会影响后续规划”，不能直接决定下一轮具体问题和选项。

### 6.4 review Prompt 的组成

`review_after_apply` 阶段的模型请求应由以下部分组成：

| 组成 | 来源 | 作用 |
| --- | --- | --- |
| 基础输出契约 | `prompts/base_contract.md` | 要求只返回 JSON |
| 阶段系统 Prompt | `prompts/review_after_apply.system.md` | 定义只做应用后回看 |
| 阶段用户 Prompt | `prompts/review_after_apply.user.md` | 指示模型审查临时正文是否满足本轮任务 |
| 意图理解结果 | `IntentUnderstandingResult` | 说明本轮原始目标 |
| 阶段任务定义 | `StageTaskDefinition` | 提供回看标准 |
| 质量约束 | `StageQualityConstraints` | 判断充分性和下一步建议质量 |
| 应用后临时正文 | `WorkingDocumentAfterApply` | 作为唯一正文审查对象 |
| 本轮修订片段 | `RevisionFragmentList` | 标识本轮实际写入了什么 |
| 输出格式要求 | `schemas/review_after_apply.output.schema.json` | 限定返回结构 |
| 结果采用策略 | `adoption/review_after_apply.adoption.json` | 规定 review 如何进入轮次决策 |

### 6.5 review 结果采用策略

Review 输出只作为轮次决策输入，不直接修改正文。采用规则如下：

1. `compliance_result` 是本轮写入是否合格的主结论，必须被后续交互规划读取。
2. `written_fact_summary` 是本轮实际写入事实的结构化摘要，用于避免下一步规划误以为没有写入任何内容。
3. `blocking_findings` 和 `blocking_reasons` 是下一步规划判断“继续当前缺口还是推进下一主题”的关键证据。
4. `planning_evidence` 只提供影响后续规划的事实，不直接产出下一轮问题。
5. `target_review` 判断本轮任务覆盖范围是否充分。
6. `global_review` 判断整体需求规格当前的总体缺口，但不直接产出下一轮问题。
7. `rewrite_advice` 只作为后续改写建议，不自动应用到正文。
8. 如果 review 判定 write 输出不充分，系统可以选择：
   - 在当前 turn 内追加一次受限 rewrite；
   - 或把缺口交给 `next_interaction_planning` 阶段，生成继续补写当前主题的下一轮交互。

是否追加 rewrite 应由明确策略控制，不能无限循环。

## 7. 阶段四：下一步交互规划阶段设计

### 7.1 阶段定位

`next_interaction_planning` 是本轮的最后一个模型阶段。
它负责根据 review 结果、当前临时正文和整体文档结构，决定下一轮最值得推进什么，以及如何向用户发问。

它解决的问题不是“刚才写得好不好”，而是：

- 现在最值得继续补当前主题，还是推进下一主题？
- 如果继续补当前主题，应该怎么问才能最低成本拿到缺失信息？
- 如果推进下一主题，应该问哪个主题、为什么？
- 是适合给开放题、确认题，还是选择题？
- 如果 review 判定本轮写得不够，应该如何如实向用户说明？

### 7.2 阶段输入

`next_interaction_planning` 的输入必须包含：

- `IntentUnderstandingResult`
- `StageTaskDefinition`
- `ReviewAfterApplyResult`
  - `compliance_result`
  - `written_fact_summary`
  - `blocking_findings`
  - `blocking_reasons`
  - `planning_evidence`
- `WorkingDocumentAfterApply`
- `TargetDocumentStructure`
- 当前规格树状态
- 当前未确认问题和已确认事实摘要
- 用户沟通约束
  - 是否优先降低用户负担
  - 是否优先使用选择题
  - 是否适合继续围绕当前主题确认

### 7.3 阶段输出

建议输出对象：

```python
NextInteractionPlan
```

建议字段：

- `planning_strategy`
  - `continue_current_gap`
  - `advance_next_topic`
  - `request_clarification`
  - `present_confirmation`
- `user_message`
- `next_question`
- `quick_options`
- `plan_reason`
- `review_acknowledgement`
- `target_spec_nodes`
- `confidence`

这里的 `review_acknowledgement` 很关键。
如果 review 判断本轮补写不充分，下一步交互规划必须如实说明这一点，而不是假装已经顺利写完再跳题。

### 7.4 阶段 Prompt 的组成

`next_interaction_planning` 阶段的模型请求应由以下部分组成：

| 组成 | 来源 | 作用 |
| --- | --- | --- |
| 基础输出契约 | `prompts/base_contract.md` | 要求只返回 JSON |
| 阶段系统 Prompt | `prompts/next_interaction_planning.system.md` | 定义只做下一步交互规划 |
| 阶段用户 Prompt | `prompts/next_interaction_planning.user.md` | 指示模型根据 review 和文档状态设计下一步 |
| 意图理解结果 | `IntentUnderstandingResult` | 说明本轮用户原始目标 |
| 阶段任务定义 | `StageTaskDefinition` | 说明本轮原计划写什么 |
| review 结果 | `ReviewAfterApplyResult` | 告诉模型刚才写得够不够、实际写入了什么、卡在哪、为什么被卡住 |
| 应用后临时正文 | `WorkingDocumentAfterApply` | 提供当前文档全局状态 |
| 目标文档结构与规格树 | `TargetDocumentStructure`、`SpecTreeSnapshot` | 告诉模型整体还缺什么 |
| 输出格式要求 | `schemas/next_interaction_planning.output.schema.json` | 限定返回结构 |
| 结果采用策略 | `adoption/next_interaction_planning.adoption.json` | 规定下一步交互计划如何进入状态机 |

### 7.5 阶段结果采用策略

`next_interaction_planning` 的结果采用规则如下：

1. `next_question` 才是下一轮主问题的权威来源，不再由 `write` 或 `review` 直接给出最终版本。
2. `quick_options` 可以是空，也可以是选择题候选；是否显示由服务端基于规划结果和前端策略最终决定。
3. 如果 `ReviewAfterApplyResult.compliance_result.status = fail`，规划阶段必须优先解释卡点，并默认选择 `continue_current_gap` 或 `request_clarification`，除非有明确理由推进下一主题。
4. 如果 `ReviewAfterApplyResult.compliance_result.status = partial`，规划阶段必须比较“继续补当前缺口”和“推进下一主题”的收益，并在 `plan_reason` 中引用 review 的 `blocking_findings`。
5. 如果 `planning_strategy = continue_current_gap`，则下一轮必须优先围绕 review 指出的缺口继续确认。
6. 如果 `planning_strategy = advance_next_topic`，则必须给出从当前主题切换到下一主题的理由，并说明为什么 review 中的剩余缺口不会阻断推进。
7. 如果 `planning_strategy = request_clarification`，则说明当前系统不宜继续写入，而应先向用户澄清关键约束。

### 7.6 为什么不能把这一步放进 review

不能把下一步规划直接塞进 review，原因有三点：

1. `review_after_apply` 只对“刚才写入的内容是否满足本轮写作任务”负责。
2. 下一步规划还要读取整体文档结构、规格树优先级和用户沟通负担，这超出了 review 的局部审查职责。
3. 如果把两者混在一起，review 容易再次退化为“一边评估、一边写策略、一边出题”的混合阶段，边界会重新失控。

## 8. 阶段任务定义与相关运行时对象

### 8.1 `StageTaskDefinition` 的定位

`StageTaskDefinition` 不是单独凭空生成，也不是只读 `prompt.md`。

它必须绑定 `IntentUnderstandingResult`。只有先理解用户意图，才能决定本轮 `write` 到底是：

- 首轮建骨架；
- 局部章节补写；
- 修正已有正文；
- 回答上一轮问题；
- 改题或重定方向。

### 8.2 `StageTaskDefinitionBuilder`

建议新增：

```python
StageTaskDefinitionBuilder
```

输入：

- `IntentUnderstandingResult`
- `TurnContext`
- `TargetDocumentStructure`
- `spec_strategy.json.task_templates`
- `quality_profiles`

输出：

- `StageTaskDefinition`

建议字段：

- `stage_id`
- `task_mode`
- `task_statement`
- `task_goals`
- `task_non_goals`
- `target_sections`
- `required_outputs`
- `review_criteria`
- `quality_profile_id`

### 8.3 阶段任务定义与意图理解的绑定关系

`StageTaskDefinition` 必须由意图理解结果驱动，不能独立存在。绑定关系如下：

| `IntentUnderstandingResult` 字段 | 对 `StageTaskDefinition` 的影响 |
| --- | --- |
| `input_type` | 决定 `task_mode` 的基础类型 |
| `document_strategy` | 决定是建骨架、局部补写、修订还是澄清 |
| `target_section_candidates` | 决定 `target_sections` 候选 |
| `write_task_candidate` | 作为 `task_statement` 候选 |
| `review_focus_candidate` | 作为 `review_criteria` 候选 |
| `ambiguities` | 决定是否追加待确认问题 |
| `confidence` | 决定是否允许进入 write，或降级为澄清 |

服务端生成 `StageTaskDefinition` 时，不能只照搬模型候选。它必须用组织器包里的 `task_templates` 和 `quality_profiles` 进行映射。例如：

```text
first_round_product_concept + bootstrap_document
  -> task_mode = first_round_bootstrap
  -> quality_profile_id = bootstrap_document_minimum
  -> required_outputs = [document_patch, open_questions_delta, assistant_message]
```

### 8.4 `StageTaskDefinition` 示例

```json
{
  "stage_id": "write",
  "task_mode": "first_round_bootstrap",
  "task_statement": "基于用户给出的态势分析系统初始构想，形成需求规格说明的初始正文骨架。",
  "task_goals": [
    "写出系统建设目标或编写目的",

  "task_non_goals": [
    "不要假定已经明确最终用户角色",

    "不要只提出下一轮问题而不写正文"
  ],
  "target_sections": [
    "总则/编写目的",
    "项目概述/系统目标",
    "功能需求/能力范围",
    "待确认问题"
  ],
  "required_outputs": [
    "document_patch",
    "open_questions_delta",
    "assistant_message"
  ],
  "review_criteria": [
    "是否形成可阅读的初始正文",
    "是否覆盖用户已给出的态势展示和分析工具",

  ],
```

### 8.5 `TargetDocumentStructure`

建议新增：

```python
TargetDocumentStructure
```

字段：

- `template_id`
- `target_sections`
- `target_anchor_paths`
- `section_requirements`
- `current_primary_gap`
- `is_empty_working_document`

它应由服务端根据模板、规格树和临时正文生成，而不是让模型凭空猜“需求规格章节”。

### 8.6 `StageQualityConstraints`

建议新增：

```python
StageQualityConstraints
```

字段：

- `min_patch_count`
- `min_content_depth`
- `must_cover_dimensions`
- `must_not_do`
- `assistant_message_requirements`
- `question_generation_requirements`

质量约束用于解决“只输出二三十个字”的问题。
例如 `first_round_bootstrap` 模式下：

- 至少生成 2 个正文 patch；
- 每个 patch 是自然段或条款化正文；
- 必须覆盖系统目标、能力范围、待确认问题；
- `assistant_message` 先说明实际写入内容，再说下一步。

## 9. 运行时对象产出顺序与上下文组装

### 9.1 运行时对象产出顺序

目标实现中，每个运行时对象的产出顺序必须固定：

| 顺序 | 对象 | 产出者 | 是否调用模型 | 下游用途 |
| --- | --- | --- | --- | --- |
| 1 | `TurnContext` | `TurnContextBuilder` | 否 | 汇总用户输入、会话状态、上一轮交互 |
| 2 | `IntentStageContext` | `IntentStageContextBuilder` | 否 | 作为意图理解请求上下文 |
| 3 | `IntentUnderstandingResult` | `IntentUnderstandingService` | 是 | 作为本轮任务来源 |
| 4 | `TargetDocumentStructure` | `TargetDocumentStructureBuilder` | 否 | 提供可写章节和锚点 |
| 5 | `StageTaskDefinition` | `StageTaskDefinitionBuilder` | 否 | 定义 write/review 的具体任务 |
| 6 | `StageQualityConstraints` | `StageQualityConstraintBuilder` | 否 | 约束输出深度和质量 |
| 7 | `StageRuntimeContext(write)` | `StageRuntimeContextBuilder` | 否 | 作为 write 请求上下文 |
| 8 | `WriteStageResult` | `TurnStageExecutor` | 是 | 产生正文 patch |
| 9 | `WorkingDocumentAfterApply` | `WorkingDocumentService` | 否 | 形成 review 审查对象 |
| 10 | `StageRuntimeContext(review_after_apply)` | `StageRuntimeContextBuilder` | 否 | 作为 review 请求上下文 |
| 11 | `ReviewStageResult` | `TurnStageExecutor` | 是 | 产生回看结论 |
| 12 | `StageRuntimeContext(next_interaction_planning)` | `StageRuntimeContextBuilder` | 否 | 作为下一步交互规划请求上下文 |
| 13 | `NextInteractionPlan` | `TurnStageExecutor` | 是 | 生成下一轮交互计划 |
| 14 | `TurnDecision` | `TurnDecisionService` | 否 | 校验和写入下一轮交互与审计结论 |

这张表的关键约束是：只有 3、8、11、13 四步调用大模型，其他步骤是服务端确定性组织、校验和采用。

### 9.2 四个模型请求的输入差异

四个请求不能共用同一份上下文 JSON。它们的输入差异如下：

| 请求 | 必须包含 | 明确不包含 |
| --- | --- | --- |
| `intent_understanding` | 用户输入、上一轮交互、快捷选项、正文是否为空、规格树摘要、active 节点 | 正文 patch 任务定义、应用后正文、review 结论 |
| `write` | 意图理解结果、阶段任务定义、目标文档结构、质量约束、写入前正文 | 应用后 review 结论、下一步交互计划、最终轮次决策 |
| `review_after_apply` | 意图理解结果、阶段任务定义、质量约束、应用后正文、本轮修订片段 | 新的正文 patch 任务、下一轮问题和快捷选项设计、未应用的 write 自评 |
| `next_interaction_planning` | review 结果、应用后正文、整体文档结构、规格树状态、用户沟通约束 | 新的正文 patch、替代 review 的充分性判断、状态写入 |

### 9.3 Prompt Bundle 组装规则

`StagePromptBundleBuilder` 不应只是拼接 markdown。目标实现中，它要接收一个结构化的 `StageRuntimeContext`，并按固定顺序渲染：

1. 基础输出契约；
2. 当前阶段职责边界；
3. 当前阶段任务定义；
4. 当前阶段可见上下文；
5. 当前阶段质量约束；
6. 输出格式要求；
7. 结果采用提示。

`assembled_prompt` 是审计展示物，不是业务对象本体。业务对象本体应同时保存在：

- `context_json`
- `schema_json`
- `adoption_policy_json`
- `stage_task_definition_json`
- `quality_constraints_json`
- `next_interaction_plan_json`

便于前端分 tab 查看和后端测试断言。

### 10.2 `ORCHESTRATOR.md` 与 `policy.md` 的职责

`ORCHESTRATOR.md` 保留为人工说明文件，默认不进入每次模型请求。它用于：

- 人工审阅；
- 组织器选型；
- 维护说明。

`policy.md` 不再写口号式原则，而应改为阶段边界约束摘要，例如：

- `intent_understanding` 不写正文；
- `write` 不关闭节点；
- `review_after_apply` 不生成 patch；
- `next_interaction_planning` 不改正文；
- 下一轮建议必须由应用后回看之后的交互规划阶段产出。

这些内容也不应全文直接塞入 prompt，而应被阶段任务定义和阶段可见约束按需渲染。

### 10.3 `spec_strategy.json` 需要新增的策略内容

除了阶段顺序，`spec_strategy.json` 还应声明可被服务端读取的策略表：

- `input_type_rules`：输入类型枚举、硬事实优先级和冲突处理规则；
- `task_templates`：不同 `input_type + document_strategy` 对应的任务模板；
- `quality_profiles`：不同任务模式的最小 patch 数、正文深度、必须覆盖维度；
- `target_section_mapping`：意图候选章节如何映射到模板锚点；
- `review_profiles`：不同任务模式下 review 应检查的维度；
- `next_interaction_profiles`：不同 review 结果和文档缺口对应的下一步交互策略；
- `failure_blocking_policy`：模型不可用、低置信度、输出非法时的阻断方式；不得用服务端猜测替代意图理解。

这些策略表是组织器包真正可替换的核心，不应写死在 `turn_engine.py` 或 `deepseek_client.py`。

### 10.4 四类 Prompt 的具体职责

| Prompt | 主要任务 | 必须强调 | 不应强调 |
| --- | --- | --- | --- |
| `intent_understanding.system.md` | 判断用户意图和下游任务候选 | active 节点只是参考；首轮产品构想要识别为建骨架；不写正文 | 组织器适用场景、抽象理念 |
| `write.system.md` | 根据正式任务定义生成正文 patch | 先写正文；不得重新定义意图；不得直接关闭节点 | 再次判断用户想干什么；设计最终下一题 |
| `review_after_apply.system.md` | 审查应用后临时正文 | 只看应用后正文；按任务定义和质量约束判断充分性 | 生成新的正文 patch；设计最终下一题 |
| `next_interaction_planning.system.md` | 规划下一轮用户交互 | 如实使用 review 结果；结合整体文档缺口；决定题型和选项 | 修改正文；替代 review |

### 10.6 现有文件职责收缩要求

#### `deepseek_client.py`

应收缩为纯 Provider 适配器：

- 接收 `StagePromptBundle`
- 发送请求
- 返回原始响应
- 做最小 JSON 解析

它不应再定义：

- `write/review/next_interaction_planning` 的输出格式要求；
- `working_document_excerpt`；
- `review_goal`；
- 阶段上下文拼装逻辑。

#### `turn_engine.py`

需要从两段阶段执行改为四段阶段执行：

```text
intent -> write -> apply -> review -> next_interaction_planning -> decide
```

并把 `IntentUnderstandingResult` 放入后续阶段输入和当前 turn 审计链。

目标伪代码如下：

```python
context = turn_context_builder.build(...)
strategy = turn_strategy_service.load(...)

intent_context = intent_stage_context_builder.build(context=context, strategy=strategy)
intent_result = intent_understanding_service.run(
    orchestrator=orchestrator,
    session=session,
    context=intent_context,
)

target_document_structure = target_document_structure_builder.build(
    context=context,
    intent=intent_result,
    strategy=strategy,
)
stage_task_definition = stage_task_definition_builder.build(
    context=context,
    intent=intent_result,
    target_document_structure=target_document_structure,
    strategy=strategy,
)
quality_constraints = stage_quality_constraint_builder.build(
    task=stage_task_definition,
    strategy=strategy,
)

write_context = stage_runtime_context_builder.build_write(...)
write_result = turn_stage_executor.run(stage=write, context=write_context)
working_document_after_apply = working_document_service.apply_patches(...)

review_context = stage_runtime_context_builder.build_review(...)
review_result = turn_stage_executor.run(stage=review_after_apply, context=review_context)

next_interaction_context = stage_runtime_context_builder.build_next_interaction(...)
next_interaction_plan = turn_stage_executor.run(
    stage=next_interaction_planning,
    context=next_interaction_context,

```

这段伪代码的重点是：`StageTaskDefinition` 在 `write` 前已经产生，且它依赖 `IntentUnderstandingResult`。`write` 不再自己决定本轮到底是首轮建骨架、回答上一题还是局部补写。

- 阶段任务定义；
- 目标文档结构；

- 质量约束；

- 输出格式要求。

### 11.1 调用日志必须看到四类模型调用

调用日志中应能看到四类模型调用：

- 意图理解调用；
- 文档 write 调用；
- 应用后 review 调用；
- 下一步交互规划调用。

每条日志必须展示：

- `stage_id`
- `prompt_id`
- `context_json`
- `schema_json`
- `assembled_prompt`
- `provider_response`
- `provider_normalized_output`
- `service_output`

### 11.2 调用详情的子 tab 顺序建议

调用详情的子 tab 顺序建议调整为：

```text
概览 -> 当前 turn 上下文 -> 输出格式要求 -> 请求 -> 原始输出 -> 输出后处理
```

其中“当前 turn 上下文”在不同阶段展示不同对象：

- `intent_understanding`：展示 `IntentStageContext`；
- `write`：展示 `StageRuntimeContext(write)`；
- `review_after_apply`：展示 `StageRuntimeContext(review_after_apply)`；
- `next_interaction_planning`：展示 `StageRuntimeContext(next_interaction_planning)`。

这样用户能直接看到四次模型调用分别依据什么做判断，而不是只看到一段混合后的 `assembled_prompt`。

当前 turn 审计中也应新增意图理解摘要，至少包括：

- 用户意图；
- 输入类型；
- 目标章节候选；
- 本轮任务定义；
- 为什么进入首轮建骨架或局部补写；
- 应用后回看结论；
- 下一步交互规划理由。

## 12. 实施验收口径

本补充通过后，编码实现至少要满足以下验收条件：

1. `spec_strategy.json` 中能看到 `intent_understanding -> write -> review_after_apply -> next_interaction_planning` 四阶段顺序。
2. 组织器包中存在四类 Prompt、四类输出格式要求和四类采用策略。
3. 每个 turn 至少能记录四类模型调用日志；若 `intent_understanding` 阶段失败，日志中必须说明失败原因，并且本轮不得继续进入 `write`。
4. `write` 请求的上下文中必须包含采纳后的 `IntentUnderstandingResult` 和正式 `StageTaskDefinition`。
5. 首轮产品构想输入不能只生成二三十字摘要，必须形成可见的初始正文 patch。
6. `review_after_apply` 必须读取应用后的临时正文，不允许只审查 write 原始输出。
7. `next_interaction_planning` 必须读取 review 结果、应用后临时正文和整体文档结构，不允许由规则树直接机械生成最终下一题。
8. 前端调用日志能分阶段查看当前 turn 上下文、输出格式要求、请求、原始输出和输出后处理。
9. 当前 turn 审计能显示本轮意图理解、任务定义、正文写入、应用后回看、下一步交互规划和轮次决策的因果链。

## 13. 结论

输入类型判断必须升级为独立的 `intent_understanding` 模型阶段。
四阶段模型调用应是：

```text
intent_understanding -> write -> review_after_apply -> next_interaction_planning
```

其中：

- `intent_understanding` 解决“用户想要干什么”和“后续阶段任务如何定义”；
- `write` 只负责按任务定义生成正文 patch；
- `review_after_apply` 只负责基于应用后的临时正文审查是否足够；
- `next_interaction_planning` 只负责结合 review 和整体文档结构规划下一轮交互。

如果没有前置意图阶段，`write` 会继续混合意图判断和正文生成。
如果没有独立下一步交互规划阶段，系统又会退回到基于规则树机械出题，无法形成接近 brainstorming 的引导式闭环。
