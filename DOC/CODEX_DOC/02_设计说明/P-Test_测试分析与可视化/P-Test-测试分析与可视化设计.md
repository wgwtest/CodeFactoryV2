# P-Test 测试分析与可视化设计

## 1. 设计定位

P-Test 是跨阶段测试分析与可视化能力，用于承载 P2、P3、P4 等阶段后续反复执行的自测、对照测试、整改闭环测试和趋势复盘。

P-Test v1 的目标不是建设一个在线智能测试平台，而是建立一套稳定的测试分析产物组织方式：

1. 测试计划定义本次测试关心的指标、口径和展示要求。
2. 测试执行过程产生原始记录、证据附件、最终成果和整改说明。
3. Codex 或执行者读取指标定义和测试产物，完成分析、归一化和结构化统计。
4. 分析结果落为 `analysis.json`。
5. 固定 HTML/JS 报告模板只读取 `analysis.json`，以稳定形式展示趋势、对比和证据入口。

因此，P-Test v1 的“智能化”只发生在分析生成阶段，不发生在 HTML 页面运行阶段。HTML 页面不是决策器、评测器或在线测试平台。

`analysis.json` 的正式数据契约不在本设计说明中维护，而是由跨阶段数据规范统一约束：

```text
DOC/CODEX_DOC/03_规范与流程/01_数据规范/04-P-Test-analysis-json数据规范.md
```

本设计说明只解释 P-Test 的定位、使用模式、页面组成和边界；字段定义、枚举、必填项和版本维护以该数据规范为准。

## 2. 适用范围

P-Test 适用于以下场景：

1. 多轮整改闭环测试，例如 P2 组织器多轮自测整改。
2. 多对象对照测试，例如本地组织器、Dify workflow 组织器、真实 Codex `brainstorming` skill 的对照。
3. 长轮次交互质量分析，例如不超过 20 Turn 的需求探索会话。
4. 阶段性质量趋势复盘，例如连续 6 轮、10 轮或更多整改迭代的指标变化。
5. 测试证据索引展示，例如链接到每轮交互记录、最终成果和整改说明。

P-Test v1 不负责：

1. 直接启动被测系统。
2. 在线调用大模型或 Dify。
3. 在线读取数据库或后端 API。
4. 在线编辑测试计划、测试记录或指标定义。
5. 在浏览器中重新计算复杂智能判断。
6. 替代人工或 Codex 对测试现象的分析结论。

## 3. 总体使用模式

P-Test v1 的使用链路分为四个大块。前 3 个大块是用户要求“生成测试分析”时由 Codex 或执行者完成的分析生成工作，第 4 个大块才是 P-Test HTML 模板的展示工作。

### 3.1 读取指标定义

Codex 先读取对应测试计划中的测试对象、轮次、原始记录位置、指标定义、指标口径和展示要求。

指标定义由测试计划承载，而不是由 P-Test 页面临时发明。当前优先写在对应测试计划文档中，不单独抽取为全局 `metric_profile`。原因是当前不同测试计划的指标口径仍在形成过程中，过早抽取会造成概念空转。

当多个测试计划稳定复用同一组指标后，可以再抽取为独立指标配置。

### 3.2 读取测试执行产物

Codex 再读取测试执行阶段已经产生并归档的材料：

1. 每轮测试记录。
2. 每轮整改说明。
3. 交互证据附件。
4. 最终工作成果或最终草案。
5. 运行日志、调用日志、错误响应和必要截图。

这些材料仍按现有文档治理规则归档到 `06_测试文档`、`07_过程文档` 等目录。P-Test 不改变原始证据的归档位置。

### 3.3 生成 `analysis.json`

Codex 按测试计划中的指标口径和展示要求执行分析，生成结构化结果：

1. 按指标口径提取、计算或人工辅助判定数据。
2. 记录无法自动计算、需要人工判断或证据不足的指标。
3. 汇总证据链接、局限说明和结论。
4. 按 `04-P-Test-analysis-json数据规范.md` 生成 `analysis.json`。

该过程可以包含智能判断，例如内容丰富度、问题深度、决策推进质量等，但这些判断必须受测试计划中的指标定义约束，并在 `analysis.json` 中保留依据说明。

### 3.4 HTML 稳定展示

HTML/JS 报告模板只负责读取 `analysis.json` 并渲染。

固定模板的价值是：同一类测试的展示形式不会因为每次 Codex 分析措辞、数据漂移或运算漂移而变化。每轮需要重新生成的是数据，不是展示结构。

## 4. 核心对象

### 4.1 TestPlanMetric

`TestPlanMetric` 表示测试计划中定义的单个指标。

字段建议：

| 字段 | 含义 |
| --- | --- |
| `metric_id` | 指标稳定标识 |
| `name` | 指标中文名称 |
| `purpose` | 指标回答的问题 |
| `type` | `count`、`ratio`、`boolean`、`score`、`category`、`text` |
| `unit` | 字、个、次、百分比、分等 |
| `source` | 数据来源，例如 summary、交互附件、最终正文、人工判读 |
| `calculation` | 计算或判定口径 |
| `visualization` | 推荐展示方式，例如趋势折线、柱状、状态表 |
| `limitations` | 指标局限 |

### 4.2 TestObject

`TestObject` 表示被测对象。

示例：

```json
{
  "object_id": "brainstorm-v1",
  "display_name": "Brainstorm V1",
  "type": "p2_orchestrator"
}
```

### 4.3 TestIteration

`TestIteration` 表示第 N 轮测试或整改闭环。

字段建议：

| 字段 | 含义 |
| --- | --- |
| `iteration` | 轮次 |
| `started_at` | 起始时间 |
| `ended_at` | 结束时间 |
| `scope` | 本轮测试范围 |
| `changes_summary` | 本轮整改摘要 |
| `evidence_links` | 本轮证据入口 |

### 4.4 MetricSeries

`MetricSeries` 表示某个指标在多个轮次、多个被测对象上的取值。

P-Test 的展示应以指标为中心，而不是以组织器为中心。对于每个指标，横轴为轮次，同一张图上叠加多个被测对象的曲线或柱状数据。

### 4.5 AnalysisDataset

`AnalysisDataset` 是 `analysis.json` 的根对象。

字段语义、必填要求、枚举和版本维护以以下正式数据规范为准：

```text
DOC/CODEX_DOC/03_规范与流程/01_数据规范/04-P-Test-analysis-json数据规范.md
```

建议结构：

```json
{
  "schema_version": "ptest.analysis.v1",
  "title": "P2 组织器多轮整改 6 轮测试分析",
  "plan_ref": "",
  "generated_at": "",
  "analysis_method": {
    "executor": "codex",
    "mode": "plan_driven_manual_assisted",
    "notes": []
  },
  "test_objects": [],
  "iterations": [],
  "metrics": [],
  "series": [],
  "timeline": [],
  "evidence_index": [],
  "conclusions": []
}
```

## 5. 页面组成

P-Test v1 HTML 报告建议包含四个区域。

### 5.1 批次概览

批次概览只保留少量必要信息：

1. 测试主题。
2. 测试对象。
3. 轮次数量。
4. 测试计划入口。
5. 分析生成时间。
6. 总体结论摘要。

批次概览不是主要分析区，不应堆叠大量卡片。

### 5.2 指标趋势

指标趋势是核心区域。

展示规则：

1. 每个指标一张趋势图或状态图。
2. 横轴为测试轮次。
3. 不同被测对象作为同图中的不同序列。
4. 指标说明、计算口径和局限必须可见。
5. 数据缺失、不可比、人工判定必须显式标注。

例如，`final_working_document_text_chars` 一张图中同时展示 `brainstorm-v1` 与 `brainstorm-v1-dify-workflow` 的 6 轮变化，而不是单独设置一个“组织器对比”大章节。

### 5.3 整改时间线

整改时间线用于简述每轮发生了什么：

1. 本轮主要问题。
2. 本轮主要整改。
3. 本轮测试结论。
4. 证据链接。

时间线是辅助解释，不替代指标趋势。

### 5.4 证据下钻

证据下钻提供到原始文档的入口：

1. 每轮测试记录。
2. 每轮整改说明。
3. 每个被测对象的交互证据附件。
4. 最终成果文档。
5. 关键日志或错误响应。

P-Test 页面不复制完整证据内容，只做索引和摘要。

## 6. 指标定义原则

### 6.1 指标来自测试计划

P-Test 展示层不得自行发明指标。若页面需要展示某个指标，该指标必须能追溯到测试计划中的定义。

允许 Codex 在分析时建议新增指标，但新增指标必须先回写到测试计划或补充说明，再进入 `analysis.json`。

### 6.2 指标不是最终质量本身

指标用于辅助观察，不等同于最终质量结论。

例如，正文有效字数增加可能意味着草案更充分，也可能意味着冗余增加；开放问题数量减少可能意味着收束更好，也可能意味着问题被过早忽略。因此每个指标都应保留局限说明。

### 6.3 主观指标必须有证据口径

内容丰富度、话题深度、决策推进质量等主观指标可以存在，但必须满足：

1. 有明确评分区间或分类口径。
2. 有引用证据入口。
3. 有判定说明。
4. 可由后续执行者复核。

## 7. 文件与目录建议

P-Test 作为跨阶段能力，设计文档放在：

```text
DOC/CODEX_DOC/02_设计说明/P-Test_测试分析与可视化/
```

后续若进入实现，建议新增独立工具目录，而不是放入 P2 应用内部：

```text
tools/ptest/
```

建议结构：

```text
tools/ptest/
  README.md
  templates/
    report.html
    report.css
    report.js
  schemas/
    analysis.schema.json
  examples/
    p2-orchestrator-2026-05-10/
      analysis.json
      report.html
```

v1 可以先人工或 Codex 生成 `analysis.json`，暂不要求提供完整自动分析 CLI。

## 8. 与 P2 多轮整改测试的关系

P2 组织器 6 轮整改测试是 P-Test 的第一个样例，但不是 P-Test 的边界。

P2 计划应补充本次测试的指标定义与可视化要求。P-Test 只消费这些定义和测试产物：

```text
P2 测试计划
  -> P2 单轮测试记录与交互证据
  -> Codex 按计划生成 analysis.json
  -> P-Test HTML 模板展示
```

如果 P3 或 P4 后续也需要类似分析，只需要在对应测试计划中定义自己的指标与证据来源，再复用 P-Test 的 `analysis.json` 结构和 HTML 模板。

## 9. 后续演进

P-Test 可以按以下顺序演进：

1. v1：手工/Codex 辅助生成 `analysis.json`，固定 HTML 展示。
2. v2：提供本地 CLI，按测试计划和证据目录生成基础统计数据。
3. v3：支持指标配置复用，将稳定指标抽取为独立 `metric_profile`。
4. v4：接入平台后端，支持测试批次索引、报告列表和历史对比。
5. v5：支持在线重新分析，但仍保持指标定义由测试计划或指标配置驱动。

任何演进都不得改变一个核心原则：智能判断和指标口径必须可追溯，展示层不得隐藏业务决策。

## 10. 自检清单

后续实现或生成 P-Test 报告前，应检查：

1. 指标是否来自测试计划。
2. `analysis.json` 是否包含指标定义、数据、证据入口和局限说明。
3. HTML 是否只读 `analysis.json`。
4. 页面是否按指标组织趋势，而不是按组织器堆砌章节。
5. P2 专有概念是否没有写死进 P-Test 通用模板。
6. 主观判断是否有证据入口。
7. 数据缺失或不可比是否被显式标注。
