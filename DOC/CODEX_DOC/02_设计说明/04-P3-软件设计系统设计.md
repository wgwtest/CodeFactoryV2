## 1. 设计目标

`P3` 的目标不是约束软件工厂平台自身如何研发，而是为软件工厂即将生产的**软件级产物**提供正式的软件设计编制阶段。

`P3` 要把 `P2` 已冻结的 `需求规格说明` 继续加工为三类正式产物：

- `结构化设计基线`
- `软件设计说明`
- `批次模块工单包`

因此，`P3` 首版不是“文档写作器”，而是**订单驱动的软件设计编制与工单下发中台**。

## 2. 设计边界

### 2.1 首版负责

- 接收 `P2` 已准备好的正式需求规格说明
- 对输入虚规做快照化、结构解析和设计分析
- 创建 `P3` 订单并推进审批、生成、评审、冻结
- 生成软件设计说明草案并支持人工协作修订
- 生成面向 `P4` 的批次模块工单包
- 记录完整的 `P2 -> P3 -> P4` 追溯链

### 2.2 首版不负责

- `P2` 的需求建模与虚规编制
- `P4` 的工具资产持久化与执行编排
- 最终软件构建、装配与发布
- 系统级或子系统级产物的全量覆盖

### 2.3 首版对象约束

- 支持对象：`软件级`
- 暂不支持对象：`系统级 / 子系统级`
- 输入文档：`1` 份正式需求规格说明
- 输出文档：`1` 份正式软件设计说明
- 输出交付包：`1` 份批次模块工单包

一份需求规格说明对应一张 `P3` 主订单；一张订单内部允许多轮生成与修订，但只冻结一份正式软设和一份正式批次工单包。

## 3. 输入输出契约

### 3.1 输入侧

`P3` 只消费 `P2` 已冻结、状态明确、可追溯的需求规格说明。输入不应被当作黑盒文档直接喂给生成器，而应先完成：

- 接入登记
- 快照化留存
- 结构化解析
- 设计分析

`XX-P2-Sim` 在首版中作为 `P3.2` 下的上游联调入口存在，用于向现有 `requirements/specs` 池注入轻量样板，但它不是独立于 `P3` 主线之外的散点功能。

### 3.2 输出侧

`P3` 输出的不是单纯文档文件，而是三层语义一致的结果：

| 层次 | 正式对象 | 用途 |
| --- | --- | --- |
| 内部权威层 | `SoftwareDesignBaseline` | 作为结构化设计事实源 |
| 文档投影层 | `SoftwareDesignDescription` | 用于人工评审、冻结和留档 |
| 交接投影层 | `ModuleWorkorderBatchPackage` | 用于向 `P4` 下发模块级实现需求 |

`P4` 接收的是带包级前置说明的批次模块工单包，而不是一个没有上下文的裸列表。

### 3.3 `P5` 可行性反馈的唯一仲裁规则

`P3` 的“冻结”不是一旦冻结就永不再开，而是：

- 日常状态下保持冻结
- 只有在 `P5` 装配 / 导出可行性反馈进入正式仲裁后，才允许按规则重开

这里必须把三个概念分开：

- `P5` 的问题报告：只是事实输入
- `P3` 的仲裁结论：才是上游重开或下游下发的正式命令
- `P4` 的供给执行：只消费 `P3` 发起的新任务，不消费 `P5` 原始问题

`P3` 对 `P5` 反馈至少做三类判定：

- `design_gap`
- `supply_gap`
- `assembly_or_build_gap`

判定结果分别处理为：

- `design_gap`：在 `P3` 内部重开 `SoftwareDesignBaseline` 与其文档 / 工单投影
- `supply_gap`：由 `P3` 形成新的供给目标，并向 `P4` 下发新供给任务 / 派生任务 / 组件拆分任务
- `assembly_or_build_gap`：优先回到 `P5` 装配规则、导出规则或校验规则整改，不默认扰动 `P4`

这里还要保留一个批判性校正：

- 把所有 `P5` 不兼容都解释成 `P4` 需要修旧工具，是错误的
- 但把 `P4` 说成“完全不存在任何修订”，也过于绝对
- 更准确的边界是：`P4` 可以有平台内部质量修订，但不能直接承接来自 `P5` 的业务不匹配修订命令

## 4. 首版业务闭环

首版标准闭环为：

`P2 需求规格说明 -> P3 接入与分析 -> P3 订单创建 -> 审批 -> AI/模型生成软设草案 -> 结构完整性与规范符合性校核 -> 人机迭代修订 -> 人工评审 -> 冻结软件设计说明 -> 生成批次模块工单包 -> 人工推送到 P4`

关键约束如下：

- 模板与规范中心必须在没有订单时也可独立使用
- 软设草案生成默认允许交给模型或智能体，但不得直接视为终稿
- 生成后必须允许人工继续修订
- 未经过人工评审通过的结果不得进入 `P4`
- 推送到 `P4` 的动作必须由人工触发

## 5. 核心对象模型

### 5.1 `P3Order`

订单是 `P3` 的第一核心对象，用于承载受理、审批、生成、评审、冻结和交接状态。

最小语义应包括：

- 来源需求规格说明标识与版本
- 应用名称与领域
- 当前 `P3` 状态
- 审批信息
- 生成策略与运行记录
- 评审状态
- `P4` 推送状态

### 5.2 `SoftwareDesignBaseline`

结构化设计基线是 `P3` 内部权威设计表达，不直接面向人工阅读，但负责沉淀：

- 设计范围
- 架构建议
- 模块划分
- 输入输出
- 约束条件
- 推荐工具能力
- 评审线程
- 需求追溯关系

### 5.3 `SoftwareDesignDescription`

软件设计说明是 `SoftwareDesignBaseline` 的正式文档投影，用于：

- 专家审阅
- 正式冻结
- 留存设计结论
- 为工单包提供前置总体说明

### 5.4 `ModuleWorkorderBatchPackage`

批次模块工单包是面向 `P4` 的正式交接投影，至少要表达两层信息：

- 包级总体建议
  - 架构模式
  - 交互模式
  - 部署提示
  - 设计备注
- 条目级模块需求
  - 模块目标
  - 输入输出
  - 约束条件
  - 验收要点
  - 推荐工具能力

### 5.5 `DiscussionThread / ReviewDecision`

`P3` 首版必须显式承载人机协作与人工评审痕迹。评论线程和评审结论不是附属备注，而是结构化设计过程的一部分。

## 6. 工作台结构

`XX-P3` 作为首版验证与演示入口，采用独立驾驶舱页面 `/xx-p3`。其工作台结构应与阶段职责一一对应，而不是围绕单一文档视图展开。

建议保持以下主线：

- `P3.1` 模板与规范
- `P3.2` 需求规格说明接入与分析
- `P3.3` 设计编制与校核
- `P3.4` 评审协作与冻结
- `P3.5` 模块工单包生成
- `P3.6` 推送到 `P4`

其中：

- 模板与规范中心属于不依赖订单存在的基础能力
- 订单列表承担“当前处理对象选择”的作用
- 设计、评审、工单包都应围绕当前选中订单展开

## 7. WBS 收敛口径

当前正式采用以下 `P3` 结构：

- `P3.1` 设计依据与模板中心
- `P3.2` 需求规格说明接入与分析
  - `P3.2.3` `XX-P2-Sim` 轻量模拟输入台
- `P3.3` 软件设计说明生成与校核
- `P3.4` 人工评审与冻结
- `P3.5` 模块级工具化描述与批次工单包生成
- `P3.6` `P4` 兼容交接与推送

后续远端 issue 树、执行契约和本地计划若继续演进，均应遵循这套节点划分，不再回退到“接单、生成、导出”三段式的粗粒度表达。
