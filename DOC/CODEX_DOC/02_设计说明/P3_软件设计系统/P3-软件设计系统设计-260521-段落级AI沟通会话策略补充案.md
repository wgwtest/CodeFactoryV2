# P3 软件设计系统设计-段落级 AI 沟通会话策略补充案

**日期：** 2026-05-21

**归属主文档：** `P3-软件设计系统设计.md`

**设计状态：** 待评审补充案

## 1. 背景

当前 `P3` 已确认软件设计说明以 A4 文档形态进入统一软设工作区，并支持章节目录、正文块选中和 `Inspector` 联动。下一步需要支持用户围绕某个章节或段落直接与 AI 沟通，例如要求“这一段写得不好，拆成两段”“补充接口约束”“把本节按数据层、服务层、展示层重新组织”。

该能力不能被设计成简单的前端对话框。如果每选中一个章节或段落就创建一个独立聊天会话，会导致以下问题：

1. 同一份软件设计说明被拆成大量互不知情的局部会话。
2. 段落之间的上下文、设计基线和追溯关系难以保持一致。
3. Dify 或模型供应商的会话状态会变成事实源，后续审计、回放和替换模型都会失控。
4. 历史沟通不断增长后，前端无法可靠承担上下文压缩、补丁归并和冲突判断。

因此，段落级 AI 沟通应被定义为 `SoftwareDesignSession` 下的局部作用域 Turn，而不是段落私有聊天。

## 2. 设计目标

本补充案用于明确：

1. 软设段落和章节的 AI 沟通应驻留在哪里。
2. 前端选择的段落、章节、文本范围如何成为 AI Turn 的上下文锚点。
3. 后台如何组织全局会话、局部对象摘要、历史压缩和模型调用。
4. Dify 会话和 P3 权威会话之间的边界。
5. AI 对正文的修改应如何以补丁提案形式落地。
6. 该策略如何复用于功能树节点、分层架构模块、技术实现行、展示形态卡片和 `P4` 投影节点。

## 3. 核心结论

段落级 AI 沟通采用以下原则：

```text
一份软设一个主设计会话
  -> 每次沟通生成一个带作用域锚点的设计 Turn
    -> 后台基于锚点组装上下文
      -> AI 返回结构化补丁提案
        -> 用户确认后应用到正文和设计包
```

不采用：

```text
一个章节 / 一个段落 / 一个正文块 = 一个独立 AI 会话
```

也不采用：

```text
Dify conversation_id = P3 设计会话事实源
```

## 4. 会话归属

### 4.1 权威会话

权威会话必须是 `P3` 后台维护的 `SoftwareDesignSession`。该会话承载：

- 当前输入包。
- 当前软件设计包。
- 当前软件设计说明正文投影。
- 当前设计基线。
- 当前检查结果。
- 当前投影状态。
- 所有设计 Turn。
- 所有 AI 调用审计。
- 所有用户接受、拒绝或修改过的补丁。

段落级沟通只是在该会话下新增一个带 `scope_anchor` 的 Turn。

### 4.2 前端角色

前端不创建独立 AI 会话。前端只负责：

- 选择章节、正文块或文本范围。
- 展示当前选中对象。
- 收集用户自然语言修改意图。
- 提交带锚点的 Turn 请求。
- 展示 AI 返回的补丁提案、差异预览和执行反馈。
- 把接受、拒绝、继续追问等用户动作提交给后台。

前端可以保存 UI 展示状态，例如当前选中的正文块、滚动位置、目录宽度和 Inspector 页签，但不得保存会话事实、长期上下文摘要或模型记忆。

## 5. 作用域锚点模型

段落级沟通请求必须携带作用域锚点。建议对象名为 `DesignTurnScopeAnchor`。

```json
{
  "anchor_id": "scope-sdd-3-2-block-1",
  "anchor_type": "design_block",
  "document_id": "sdd-draft-001",
  "design_revision_id": "rev-0007",
  "section_id": "sdd-3-2",
  "block_id": "sdd-3-2-block-1",
  "text_range": {
    "start_offset": 0,
    "end_offset": 128
  },
  "source_refs": ["REQ-3.2", "REQ-5.1"],
  "selection_snapshot": {
    "title": "3.2 模块划分",
    "excerpt": "当前段落快照，用于防止后续文档漂移导致误改。"
  }
}
```

锚点类型包括：

| anchor_type | 含义 |
| --- | --- |
| `design_section` | 软件设计说明章节 |
| `design_block` | 软件设计说明正文块 |
| `text_range` | 正文块内部选区 |
| `function_node` | 功能树节点 |
| `architecture_node` | 分层架构节点 |
| `technical_mapping` | 技术实现映射行 |
| `presentation_shape` | 展示形态对象 |
| `p4_projection_node` | `P4` 投影节点 |
| `stage_relation` | 形态节点之间的转换关系 |

锚点必须引用稳定 ID，不得只依赖 DOM 位置、前端数组下标或屏幕坐标。

## 6. Turn 请求模型

建议新增或扩展 `POST /api/software-design-v2/sessions/{session_id}/turns`，使其支持作用域锚点。

```json
{
  "turn_type": "scoped_design_edit",
  "scope_anchor": {
    "anchor_type": "design_block",
    "section_id": "sdd-3-2",
    "block_id": "sdd-3-2-block-1",
    "design_revision_id": "rev-0007"
  },
  "user_instruction": "这一段写得太散，拆成两段，并补充接口边界。",
  "interaction_mode": "propose_patch",
  "expected_output": ["document_patch", "traceability_update", "quality_note"]
}
```

后台返回：

```json
{
  "turn_id": "turn-0042",
  "status": "patch_proposed",
  "scope_anchor": {},
  "assistant_summary": "已建议把本段拆为职责说明和接口边界两段。",
  "patch_proposal": {},
  "context_receipt": {},
  "provider_call_audit": {}
}
```

`interaction_mode` 首版建议包括：

| interaction_mode | 含义 |
| --- | --- |
| `propose_patch` | 生成补丁提案，等待用户确认 |
| `explain` | 解释当前段落或章节，不修改正文 |
| `review` | 检查当前对象质量，输出问题和建议 |
| `continue_discussion` | 在同一主会话下继续围绕当前对象追问 |

## 7. 后台上下文构建

后台收到带锚点的 Turn 后，由 `DesignTurnContextBuilder` 组装上下文。上下文应包括：

1. 当前输入包摘要。
2. 当前软件设计包摘要。
3. 当前章节或段落全文。
4. 当前章节的父章节、相邻段落和子章节摘要。
5. 当前段落关联的需求条款。
6. 当前段落关联的功能树节点、架构节点、技术实现和投影对象。
7. 当前设计基线中与该锚点相关的事实。
8. 当前对象历史讨论摘要。
9. 当前全局会话摘要。
10. 必要的最近 Turn 原文。
11. 适用的模板、写作规则和检查规则。

前端只传锚点和用户意图，不直接拼接长上下文。

## 8. 压缩机制

压缩必须由后台负责，前端不得承担长期上下文压缩。

### 8.1 三层记忆

后台维护三层记忆：

| 层级 | 对象 | 用途 |
| --- | --- | --- |
| 原始 Turn Ledger | `SoftwareDesignTurn[]` | 审计、回放、问题追责，不丢弃 |
| 全局会话摘要 | `SessionContextSummary` | 表达整份软设当前设计意图、关键决策、未决问题 |
| 局部对象摘要 | `ScopedObjectDiscussionSummary` | 表达某章节、正文块、功能节点或关系对象的局部讨论状态 |

原始 Turn Ledger 不应被覆盖。摘要是可重建的派生状态，可定期更新。

### 8.2 压缩触发

压缩可由以下条件触发：

- Turn 数量超过阈值。
- 某个对象的局部讨论超过阈值。
- 模型上下文预算不足。
- 用户接受补丁后，需要把旧讨论折叠为“已采纳决策”。
- 用户拒绝补丁后，需要把拒绝原因折叠为“后续生成禁止事项”。
- 会话保存或冻结前。

### 8.3 压缩归属

压缩逻辑归属 `软件设计会话与运算模块`，并通过 `DesignContextCompressionService` 或等价服务实现。该服务可以调用模型，也可以使用规则摘要，但其输出必须写回 P3 后台存储，而不是写入前端缓存或 Dify 私有会话。

## 9. Dify 边界

Dify 或其他模型编排器只能作为 `Turn Executor`，不能作为 P3 权威会话。

后台可以为执行器保存 `provider_binding`：

```json
{
  "provider": "dify",
  "workflow_id": "requirement-to-sdd-scoped-edit",
  "conversation_id": "dify-conv-xxx",
  "last_run_id": "run-yyy",
  "observability_level": "limited"
}
```

该绑定只用于：

- 供应商调用连续性。
- 调试和审计。
- 复用供应商侧短期上下文。

不得用于：

- 判断 P3 当前设计事实。
- 替代 `SoftwareDesignTurn`。
- 替代 `SessionContextSummary`。
- 替代局部对象摘要。
- 作为冻结或评审证据的唯一来源。

如果 Dify 会话丢失、过期或切换供应商，P3 必须能凭自己的 Turn Ledger、设计包、设计基线和摘要继续工作。

## 10. 补丁提案模型

AI 不直接改写正文。AI 返回 `DesignPatchProposal`，用户确认后才应用。

```json
{
  "proposal_id": "patch-0042",
  "base_revision_id": "rev-0007",
  "target_anchor": {
    "section_id": "sdd-3-2",
    "block_id": "sdd-3-2-block-1"
  },
  "operations": [
    {
      "op": "split_block",
      "target_block_id": "sdd-3-2-block-1",
      "new_blocks": [
        {
          "title": "职责边界",
          "content": "..."
        },
        {
          "title": "接口约束",
          "content": "..."
        }
      ]
    },
    {
      "op": "update_trace_refs",
      "target_block_id": "sdd-3-2-block-1",
      "source_refs": ["REQ-3.2", "REQ-5.1"]
    }
  ],
  "quality_notes": [
    "拆分后需要重新检查接口章节是否重复描述。"
  ]
}
```

补丁操作首版可包括：

| op | 含义 |
| --- | --- |
| `rewrite_block` | 重写正文块 |
| `split_block` | 拆分正文块 |
| `merge_blocks` | 合并正文块 |
| `insert_block_after` | 插入新正文块 |
| `add_subsection` | 新增子章节 |
| `update_trace_refs` | 更新追溯引用 |
| `add_quality_note` | 添加检查或评审提示 |

应用补丁前必须校验 `base_revision_id`。如果用户期间已经修改过正文，后台应返回冲突状态，要求重新生成或人工合并。

## 11. Inspector 交互形态

选中软设章节或正文块时，`Inspector` 的能力页应出现“局部 AI 沟通”区。

建议结构：

1. 当前对象摘要：章节名、正文块 ID、状态、来源需求。
2. 局部输入框：用户输入自然语言修改意图。
3. 上下文提示：显示本次会作用于哪个章节或段落。
4. 相关历史：只显示与当前锚点相关的 Turn 摘要，不显示全部全局聊天。
5. 输出区：补丁提案、差异预览、质量提示。
6. 操作区：接受补丁、放弃补丁、继续追问、查看上下文收据。

`当前 Turn` 视图仍然显示全局 Turn 列表。`Inspector` 中的局部历史只是全局 Turn Ledger 按锚点过滤后的视图，不是独立会话。

## 12. 可复用性

该机制不只服务软设正文段落。任何可选中对象都可以复用：

```text
选中对象
  -> 形成 scope_anchor
    -> 提交 scoped_design_turn
      -> 后台组装对象上下文
        -> AI 返回对象补丁或建议
```

复用对象包括：

- 功能树节点：补充子功能、调整层级、解释追溯缺口。
- 分层架构节点：调整层级归属、补充服务边界、补充数据依赖。
- 技术实现映射行：替换框架、解释插件覆盖关系、补充实现约束。
- 展示形态对象：调整展示位置、交互模式和可见状态。
- `P4` 投影节点：补充工单验收点、拆分工具包、解释投影来源。
- 阶段关系箭头：调整转换策略、解释生成依据、重跑局部转换。

因此，该能力应归入 `SelectedObjectInspector` 的通用对象能力，而不是写死在 A4 文档组件里。

## 13. 模块边界

| 模块 | 职责 | 禁止事项 |
| --- | --- | --- |
| 前端 `SelectedObjectInspector` | 展示选中对象、提交锚点 Turn、展示补丁和差异 | 不保存权威会话，不压缩上下文 |
| 前端文档渲染器 | 提供章节、正文块和文本范围选择 | 不直接调用 Dify，不拼接长期上下文 |
| 软件设计会话与运算模块 | 维护 Turn、上下文构建、模型调用审计和压缩摘要 | 不把 Dify 会话当权威事实源 |
| 软件设计说明编写模块 | 管理正文结构、正文块、补丁应用和修订版本 | 不绕过补丁确认直接改正文 |
| 软件设计基线模块 | 同步正文补丁对结构化设计事实的影响 | 不从前端 DOM 推断基线事实 |
| 模型 / Dify 执行器 | 执行单次或连续 Turn 调用 | 不拥有 P3 业务状态 |

## 15. 运行流程

```text
用户点击软设段落
  -> 前端生成 DesignMorphSelection
    -> Inspector 显示局部 AI 沟通入口
      -> 用户输入修改意图
        -> 前端提交 session_id + scope_anchor + user_instruction
          -> 后台构建上下文
            -> 后台必要时压缩或读取摘要
              -> 后台调用 Dify / 模型执行器
                -> 后台保存 Turn、调用审计和补丁提案
                  -> 前端展示差异预览
                    -> 用户接受补丁
                      -> 后台校验 base_revision_id
                        -> 应用正文补丁
                          -> 更新设计包 / 基线映射 / 检查状态
                            -> 更新局部对象摘要和全局会话摘要
```

## 16. 验收口径

该设计进入主文档和代码实现时，至少满足：

1. 选中软设章节或正文块后，`Inspector` 能显示局部 AI 沟通入口。
2. 前端提交请求必须携带 `scope_anchor`，不能只传自然语言。
3. 后台只创建主 `SoftwareDesignSession` 下的 Turn，不创建段落私有权威会话。
4. Dify `conversation_id` 只作为 `provider_binding`，不能成为 P3 权威状态。
5. AI 返回补丁提案，用户确认前不直接改正文。
6. 补丁应用必须校验 `base_revision_id`。
7. 历史上下文压缩在后台执行，前端不压缩长期会话。
8. 局部历史是全局 Turn Ledger 的锚点过滤视图，不是独立聊天记录。
9. 同一机制可复用于功能树、分层架构、技术实现、展示形态、`P4` 投影和阶段关系对象。

## 17. 待评审问题

1. 首版是否只支持 `design_section` 和 `design_block` 两类锚点，暂不支持正文内部 `text_range`。
2. 补丁提案是否先只支持 `rewrite_block`、`split_block`、`insert_block_after` 三类操作。
3. 局部对象摘要是否随每次补丁接受后立即更新，还是按 Turn 数量阈值批量压缩。
4. Dify 是否需要每个 `SoftwareDesignSession` 绑定一个长期 `conversation_id`，还是每个 Turn 独立调用并完全依赖 P3 后台摘要。
5. `Inspector` 中局部 AI 沟通入口是否默认展开，还是只在点击“沟通/修订”动作后展开。
