## 1. 补充目的

本补充文档用于把人工可读的 `81435-软件设计说明准模板-v1` 落为 P3 转换器可执行约定，并明确交给 Dify 工作流开发线程的输入输出要求。

当前问题不是 Dify 接不通，而是 Dify 收到的目标设计约束过弱。旧调用只提供了短章节名和少量必填字段校验，导致 workflow 即使成功运行，也容易生成只有 15 个短段落的软设摘要。后续必须让 Dify 按 CodeFactory 提供的 `target_design_profile_json` 和 `quality_rules_json` 生成长篇、可审查、可追溯的软件设计说明草稿。

## 2. 权威边界

CodeFactoryV2 负责维护：

- `81435` 准模板正文。
- 机器可读模板 profile。
- 字数阈值、章节覆盖、必备表格、追溯和缺口规则。
- Dify 调用 adapter、错误处理和结果归一化。
- P3 Design Lab 的会话状态、草稿展示、缺口展示、人工校核和冻结控制。

Dify 工作流负责：

- 按输入需求规格说明和模板 profile 生成软设草稿。
- 生成 `SoftwareDesignPackage` 初稿。
- 生成需求到设计追溯、缺口清单和人工校核项。
- 按 `quality_rules_json` 做自检并在 `process_output.quality_summary` 中返回统计结果。

Dify 工作流不负责：

- 冻结 P3 软件设计基线。
- 修改 CodeFactory 的模板权威文件。
- 持久化真实密钥。
- 绕过 CodeFactory 本地 adapter 的输出校验。

## 3. CodeFactory 已提供给 Dify 的输入

CodeFactory adapter 会继续调用：

```http
POST /v1/workflows/{workflow_id}/run
Authorization: Bearer ${CODEFACTORY_P3_DIFY_API_KEY}
Content-Type: application/json
```

请求体中的 `inputs` 至少包含：

| Dify Start 变量 | 含义 |
| --- | --- |
| `requirement_document_text` | P2 冻结需求规格说明正文 |
| `requirement_document_title` | P2 需求规格说明标题 |
| `standard_document_json` | P2 标准文档结构 JSON 字符串 |
| `structured_spec_json` | 结构化需求对象 JSON 字符串 |
| `annotations_json` | 批注和人工说明 JSON 字符串 |
| `knowledge_binding_json` | 知识绑定摘要 JSON 字符串 |
| `frozen_trace_json` | 冻结来源、版本、时间和包标识 JSON 字符串 |
| `target_design_profile_json` | 81435 准模板机器 profile JSON 字符串 |
| `conversion_options_json` | 转换策略、生成口径和期望输出 JSON 字符串 |
| `quality_rules_json` | 字数、章节、表格、追溯和质量规则 JSON 字符串 |
| `expected_output` | 固定为 `design_package_with_document` |

## 4. `target_design_profile_json` 必须消费的关键字段

Dify 工作流必须解析并使用 `target_design_profile_json`，不能只读取章节标题。

关键字段如下：

| 字段 | 期望值或结构 | Dify 使用要求 |
| --- | --- | --- |
| `template_id` | `81435-sdd-quasi-template-v1` | 写入输出 trace，证明使用了该模板 profile。 |
| `template_name` | `81435-软件设计说明准模板-v1` | 写入输出 trace 或质量摘要。 |
| `template_path` | 模板中心 markdown 相对路径 | 可作为人工追溯信息。 |
| `minimum_total_chars` | `12000` | 作为软设正文总长度下限。 |
| `section_coverage.level_1_required` | `1.0` | 15 个一级章节必须全部生成。 |
| `section_coverage.level_2_required` | `0.9` | 二级小节覆盖率不低于 90%。 |
| `required_sections` | 15 个章节对象 | 按 `number` 和 `title` 生成章节。 |
| `required_sections[].minimum_chars` | 每章最低中文字符数 | 核心章节必须扩写到阈值以上。 |
| `required_tables` | T1-T15 表格清单 | 在对应章节生成表格或等价结构。 |
| `generation_rules` | 生成规则列表 | 作为 Prompt 和自检规则。 |

核心章节最低字数：

| 章节 | 最低中文字符数 |
| --- | --- |
| 4 总体架构 | 1200 |
| 5 前端软件设计 | 1200 |
| 6 后端软件设计 | 1500 |
| 7 核心对象模型 | 1200 |
| 8 API 设计 | 1500 |
| 9 关键运行流程 | 1200 |
| 11 设计约束与质量门 | 1000 |

## 5. `quality_rules_json` 必须执行的质量规则

Dify 工作流应在生成后执行自检，并把结果写入 `process_output.quality_summary` 和 `gap_list`。

必须检查：

| 检查项 | 不通过处理 |
| --- | --- |
| 15 个一级章节是否全部存在 | 加入 `gap_list`，严重程度至少为 `blocking` 或 `warning`。 |
| 正文总长度是否不少于 12000 中文字符 | 若不足，优先扩写；仍不足则加入 `gap_list`。 |
| 核心章节是否达到最低字数 | 逐章扩写；仍不足则写入缺口。 |
| T1-T15 表格或等价结构是否存在 | 补表；无法补充时写明原因。 |
| P2 高优先级需求是否进入追溯表 | 未映射项写入 `gap_list`。 |
| Dify、模型、插件等外部能力是否有边界说明 | 未说明时写入 `review_findings`。 |
| 输出是否为 `draft` | 不允许输出冻结状态。 |

## 6. Dify 输出 JSON 要求

Dify 输出变量仍为：

```text
result_json
```

`result_json` 必须是合法 JSON 字符串，最小结构如下：

```json
{
  "protocol_version": "p3-design-converter-protocol@1",
  "converter": {
    "converter_id": "requirement-to-sdd-dify-workflow",
    "converter_type": "dify_workflow",
    "template_id": "81435-sdd-quasi-template-v1"
  },
  "design_document": {
    "title": "软件设计说明标题",
    "version_label": "v0.1",
    "status": "draft",
    "sections": []
  },
  "design_package": {
    "package_id": "sdp-...",
    "status": "draft",
    "document_projection": {},
    "functional_tree_projection": {},
    "layered_architecture_projection": {},
    "technical_implementation_projection": {},
    "api_projection": {},
    "workflow_projection": {},
    "quality_gate_projection": {},
    "p4_workorder_projection": {}
  },
  "traceability": [],
  "gap_list": [],
  "review_findings": [],
  "workorder_projection_candidate": {},
  "process_output": {
    "quality_summary": {
      "blocking_count": 0,
      "warning_count": 0,
      "passed_count": 0,
      "total_document_chars": 0,
      "template_id": "81435-sdd-quasi-template-v1"
    }
  },
  "raw_output": {
    "raw_workflow_trace": {}
  },
  "confidence": "medium",
  "annotations": [],
  "risks": []
}
```

`design_document.sections` 不允许只输出一级章节加纯文本 `content`。每个一级章节应包含 `children` 二级小节，核心章节还必须包含 `blocks`，用于承载段落、表格和图块。章节对象建议包含：

```json
{
  "section_id": "sdd-04",
  "title": "4. 总体架构",
  "content": "章节摘要正文。",
  "status": "generated",
  "source_refs": ["REQ-..."],
  "children": [
    {
      "section_id": "sdd-04-01",
      "title": "4.1 架构上下文",
      "content": "二级小节正文。",
      "status": "generated",
      "source_refs": ["REQ-..."]
    }
  ],
  "blocks": [
    {
      "block_id": "sdd-04-summary",
      "kind": "paragraph",
      "content": "段落正文。",
      "source_refs": ["REQ-..."]
    },
    {
      "block_id": "sdd-04-layer-table",
      "kind": "table",
      "title": "表 4-1 总体分层表",
      "columns": ["层次", "职责", "主要模块"],
      "rows": [["展示层", "承载用户交互", "Web 工作台"]]
    },
    {
      "block_id": "sdd-04-architecture-diagram",
      "kind": "diagram",
      "title": "图 4-1 总体架构图",
      "diagram_type": "mermaid",
      "content": "flowchart LR\n  UI[前端工作台] --> API[后端 API]\n  API --> Domain[领域服务]"
    }
  ],
  "quality": {
    "minimum_chars": 1200,
    "actual_chars": 1300,
    "required_tables": ["T4", "T5", "T6"],
    "required_diagrams": ["D1"]
  }
}
```

`blocks[].kind` 允许值包括 `paragraph`、`table`、`list`、`code`、`diagram`、`diagram_placeholder`。图块优先输出 Mermaid，其次可输出 PlantUML 或 graph JSON；当前不要求 Dify 生成图片文件。

必备图块至少包括：

| 编号 | 图块 | 推荐章节 |
| --- | --- | --- |
| D1 | 总体架构图 | 4 总体架构 |
| D2 | 后端模块/服务关系图 | 6 后端软件设计 |
| D3 | 核心对象关系图 | 7 核心对象模型 |
| D4 | 关键运行流程图 | 9 关键运行流程 |

## 7. 生成策略要求

Dify 工作流不应单步直接让一个 LLM 节点完成全部工作。建议至少拆成以下阶段：

1. 解析 P2 输入：提取角色、功能、对象、接口、非功能、验收和待确认事项。
2. 建立 P2 到 81435 章节的映射：先形成章节计划和追溯草表。
3. 分核心章节生成长文：总体架构、后端、对象、API、流程、质量门应分段生成。
4. 生成普通章节：系统定位、边界、目录、验收、结论等。
5. 合并设计包：生成 `design_document`、`design_package`、`traceability`、`gap_list` 和 `review_findings`。
6. 质量自检：检查字数、章节、二级小节、表格、图块、追溯、缺口和 draft 状态。
7. 输出守门：只输出合法 `result_json`，不得混入 Markdown 包裹、说明文字或 `<think>` 内容。

若模型上下文不足以一次生成 12000 字正文，Dify 应采用分章节生成和合并节点，而不是降低字数要求。

## 8. 验收样例

首个验收样例仍使用：

```text
P2 输入：DOC/JB_DOC/03-项目实例与样例/P2-P3主链样例-SX-DataStore/01-需求规格说明范本-SX-DataStore.md
目标参照：DOC/JB_DOC/03-项目实例与样例/P2-P3主链样例-SX-DataStore/02-软件设计说明范本-SX-DataStore.md
模板依据：DOC/JB_DOC/02-软件工厂产物模板中心/01-需求与设计主链模板/02-软件设计说明模板/基础模板/01-81435-软件设计说明准模板-v1.md
```

通过口径：

- `result_json` 能被 CodeFactory adapter 解析。
- `design_document.status == draft`。
- `design_document.sections` 包含 15 个一级章节。
- 至少 90% 一级章节包含 `children` 二级小节。
- 核心章节包含 `blocks`，表格用 `kind=table`，图用 `kind=diagram`，不得只写入普通 `content`。
- 至少包含 D1-D4 四类结构化图块；图块可用 Mermaid/PlantUML/graph JSON。
- 总正文不低于 12000 中文字符，或在 `gap_list` 明确说明因输入不足导致的未达标章节。
- 核心章节达到各自最低字数。
- T1-T15 表格存在或有等价结构。
- `traceability` 覆盖 P2 主要功能需求、接口需求、非功能需求和验收项。
- `gap_list` 和 `review_findings` 不为空时，必须能解释具体缺口，不得是泛泛提醒。

## 9. CodeFactory 本地实现状态

本分支已经新增机器可读 profile 构建器：

```text
apps/api/app/software_design_v2/sdd_template_profile.py
```

P3 转换请求已经把该 profile 注入：

```text
DesignConverterRunRequest.target_design_profile
DesignConverterRunRequest.quality_rules
```

```text

```

因此 Dify 线程不需要在 CodeFactory 仓库里查找模板正文才能开始改 workflow，但必须按上述两个 JSON 字段执行生成和自检。
