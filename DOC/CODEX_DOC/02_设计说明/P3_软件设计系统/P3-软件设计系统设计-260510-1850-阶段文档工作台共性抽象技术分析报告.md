## 1. 核心结论

本轮抽象的核心不是“把 `P2` 页面样式复制给 `P3`”，而是识别出 `CodeFactoryV2` 中一类更稳定的产品形态：

```text
阶段输入事实
  + 人机交互轮次
  -> 阶段结构化事实状态
    -> 标准文档主产物
      -> 质量检查
        -> 冻结包 / 下游投影
```

这个形态可以命名为：

```text
阶段文档工作台
```

`P2` 与 `P3` 的业务对象不同，但两者在工作台结构上高度同构：

| 层次 | P2 | P3 | 共性抽象 |
| --- | --- | --- | --- |
| 输入事实 | 专家自然语言、表单、P1 发布态知识 | P2 冻结需求规格说明 | 阶段输入事实 |
| 交互方式 | 问答模式、表单模式、短指令 | 需求规格只读查看、CLI 设计配置 | 人机交互轮次 |
| 后台事实 | 需求语义状态、需求规格聚合 | `SoftwareDesignBaseline v2` | 阶段结构化事实状态 |
| 正面产物 | 标准需求规格说明 | 软件设计说明 | 标准文档主产物 |
| 文档表现 | A4 正文、章节、条款、批注 | A4 正文、章节、模块、追溯 | 文档投影表面 |
| 质量控制 | 缺口检查、冻结门禁 | 设计完整性检查、冻结门禁 | 质量检查面 |
| 下游输出 | P3 可消费冻结包 | P4 工单投影、设计包 | 下游投影面 |

因此，本轮真正的抽象对象不是某个页面，而是一套围绕“标准文档主产物”的阶段工作台骨架。

## 2. 为什么这个抽象成立

### 2.1 `P2` 已经证明“文档是正面工作对象”

`P2` 当前成熟设计中，用户面对的是标准需求规格说明，而不是模型对话、内部字段或临时草稿状态。左侧问答和表单只是输入与校对方式，右侧标准正文才是专家持续审阅、修改和冻结的主产物。

这带来一个重要设计原则：

```text
用户工作对象应当是阶段标准文档；
结构化对象应当作为后台事实状态支撑生成、检查、追溯和下游交接。
```

`P2` 的右侧文档区已经承担了以下职责：

- 展示完整标准模板骨架。
- 展示章节、条款和待补齐状态。
- 支持轻量编辑和条款批注。
- 支持缺口定位。
- 支持冻结后只读预览。
- 支持把冻结包交给 `P3`。

这些能力不是 `P2` 独有。任何以阶段文档为主产物的子系统都需要类似能力。

### 2.2 `P3` 与 `P2` 的差异主要在输入输出语义，不在工作台骨架

`P3` 的输入不是自然语言起点，而是 `P2` 冻结需求规格说明。`P3` 的输出不是需求规格说明，而是软件设计说明、设计基线和工单投影。

但从工作台结构看，`P3` 仍然符合与 `P2` 相同的主链：

```text
P2 冻结需求规格说明
  + 自然语言设计配置
  -> SoftwareDesignBaseline v2
    -> 软件设计说明正文
      -> 设计完整性检查
        -> 设计冻结
          -> P4 工单投影
```

这说明 `P3` 不需要重造“新的页面场景”。它应当在 `P2` 成熟形态上更换输入事实、结构化状态、检查规则和下游投影。

### 2.3 `P2` 与 `P3` 的共同点比页面布局更深

两者真正相同的是五个稳定接口：

| 稳定接口 | 含义 | P2 示例 | P3 示例 |
| --- | --- | --- | --- |
| 输入事实接口 | 本阶段生成主产物所依赖的事实 | P1 知识、专家输入、模板字段 | P2 冻结包、需求正文、批注和追溯 |
| 交互轮次接口 | 人通过短指令、表单或配置影响阶段状态 | 问答消息、表单字段变更 | 设计 CLI、生成策略、修订指令 |
| 事实状态接口 | 后台可计算、可检查、可冻结的权威对象 | `RequirementSpec` / 需求语义状态 | `SoftwareDesignBaseline v2` |
| 文档投影接口 | 把事实状态投影为标准正文 | 标准需求规格说明 | 软件设计说明 |
| 质量和投影接口 | 检查、冻结和下游输出 | 缺口检查、P3 输入包 | 设计检查、P4 工单投影 |

这五个接口才是本轮抽象应当沉淀的核心，而不是固定的两栏或三栏比例。

## 3. 已经抽象出的结果

### 3.1 第一层：阶段工作台外壳

已形成组件：

```text
StageDocumentWorkbench
```

当前职责：

- 承载阶段标题、副标题、状态标签和动作区。
- 承载左侧输入区与右侧主产物区。
- 支持左侧拆成上区和下区。
- 不理解 `P2` 或 `P3` 的业务字段。
- 不直接调用 API。

这层抽象解决的是“阶段工作台整体骨架”问题。它把页面从“某个 P3 页面”提升为“某个阶段的文档工作台”。

当前成熟度判断：

```text
抽象设计成熟度：L2 已成立
代码实现成熟度：L1 已成立
```

它已经可以支撑 `P3`，并且具备回迁 `P2` 的结构条件；尚待验证的是 `P2` 迁移后是否需要补充更多左侧输入槽位。

### 3.2 第二层：主产物 Tab 表面

已形成组件：

```text
DocumentProductSurface
```

当前职责：

- 在右侧最大区域承载主产物。
- 通过 Tab 组织正文、目录、检查、投影等视图。
- 不持有业务生成逻辑。
- 由业务页面传入 Tab 配置。

这层抽象解决的是“标准文档主产物不只是一页正文”的问题。`P2` 和 `P3` 的主产物都应当包含正文、目录、检查和下游交接视图，只是每个 Tab 内部的业务内容不同。

当前成熟度判断：

```text
抽象设计成熟度：L2 已成立
代码实现成熟度：L1 已成立
```

它已经抽出了 Tab 容器。目录、检查、投影的通用模型在本文第 4 章补齐，代码层仍需把 `P3DesignLabPage` 内部的 Tab 内容下沉为可复用 Panel。

### 3.3 第三层：A4 标准文档纸面

已形成组件：

```text
A4DocumentSurface
```

当前职责：

- 提供接近正式文档的 A4 视觉形态。
- 支持标题、副标题、页眉、页脚和章节列表。
- 支持空状态。
- 不绑定文档类型。

这层抽象回应了用户对 `P3` 的关键要求：软件设计说明必须像正式 A4 文档，而不是静态布局卡片。它也对齐 `P2` 的设计原则：右侧主产物必须是标准正文，而不是聊天记录或数据面板。

当前成熟度判断：

```text
抽象设计成熟度：L2 已成立
代码实现成熟度：L1 已成立，文档渲染能力待增强
```

它能表达基础章节。条款编号、批注锚点、目录跳转、分页、多页页脚、修订标记和冻结版印记在本文第 4 章中被纳入标准文档模型，代码层后续分步实现。

### 3.4 第四层：业务适配层的抽象合同已明确

当前 `P3DesignLabPage` 内部已经做了轻量适配：

- 把 `P3DesignLabInputPackage` 映射为左侧需求规格说明输入区。
- 把 `P3DesignLabSession.design_document` 映射为 `A4DocumentSurface`。
- 把 `design_baseline` 映射为目录和模块摘要。
- 把 `check_result` 映射为检查 Tab。
- 把 `workorder_projection` 映射为投影 Tab。

这些适配逻辑在代码中仍写在页面文件内。第 4 章已经补齐独立 Adapter 合同，后续实现只需要按合同拆出独立文件。

当前成熟度判断：

```text
抽象设计成熟度：L2 已成立
代码实现成熟度：L0.5 到 L1 之间
```

Adapter 合同已经在本文第 4 章补齐；代码层还需要把当前页面内的轻量适配逻辑拆成独立 adapter 文件。

## 4. 共性抽象补全结果

本章把上一版报告中列为“尚未抽象完成”的内容补齐为可评审的抽象定义。这里的“补齐”指设计抽象和接口模型已明确；代码实现仍按后续计划分步落地。

### 4.1 阶段文档工作台内核

`阶段文档工作台` 的最小内核不是页面布局，而是七类稳定对象：

| 内核对象 | 职责 | P2 映射 | P3 映射 |
| --- | --- | --- | --- |
| `StageIdentity` | 标识当前阶段、入口、文档类型和上下游关系 | P2 需求分析系统、需求规格说明 | P3 软件设计系统、软件设计说明 |
| `StageInputFacts` | 承载本阶段生成主产物所依赖的事实 | P1 知识、专家输入、模板字段 | P2 冻结包、需求正文、批注、追溯 |
| `StageInteraction` | 承载用户如何影响阶段状态 | 问答、表单、短指令 | 设计 CLI、生成策略、修订指令 |
| `StageAuthoritativeState` | 后台权威结构化状态 | 需求语义状态 / `RequirementSpec` | `SoftwareDesignBaseline v2` |
| `StageDocumentProduct` | 阶段正面主产物 | 标准需求规格说明 | 软件设计说明 |
| `StageQualityGate` | 检查、门禁、冻结前条件 | 缺口检查 | 设计完整性检查 |
| `StageOutputProjection` | 冻结包和下游投影 | P3 可消费冻结包 | P4 工单投影 / 设计包 |

这七个对象共同构成平台级工作台骨架。任何阶段只要符合“输入事实 + 交互轮次 -> 结构化状态 -> 标准文档 -> 检查冻结 -> 下游投影”，就可以接入该骨架。

### 4.2 统一工作台视图模型

共性组件不应直接消费 `P2` 或 `P3` DTO，而应消费统一工作台视图模型：

```ts
type StageDocumentWorkbenchViewModel = {
  identity: StageIdentityViewModel;
  header: StageHeaderViewModel;
  layout: StageWorkbenchLayoutViewModel;
  inputFacts: StageInputFactsViewModel;
  interaction: StageInteractionViewModel;
  product: StageDocumentProductViewModel;
  quality: StageQualityGateViewModel;
  projection: StageOutputProjectionViewModel;
  actions: StageActionViewModel[];
};
```

其中：

| 字段 | 用途 |
| --- | --- |
| `identity` | 说明当前阶段、文档类型、上游来源、下游目标 |
| `header` | 提供标题、副标题、状态标签、运行提示 |
| `layout` | 提供左右比例、左侧上下比例、主产物默认 Tab |
| `inputFacts` | 提供左侧输入事实源的只读或可编辑视图 |
| `interaction` | 提供 CLI、问答、表单或其他交互视图 |
| `product` | 提供右侧标准文档主产物 |
| `quality` | 提供检查结果、门禁状态和冻结阻断说明 |
| `projection` | 提供下游投影和交接包摘要 |
| `actions` | 提供动作按钮和可用性状态 |

该模型不是后端低代码布局协议。后端仍提供业务 DTO 和业务规则；前端阶段 Adapter 负责把 DTO 转成该模型。

### 4.3 标准文档主产物模型

`P2` 和 `P3` 的右侧主产物应共用同一个标准文档模型：

```ts
type StandardDocumentViewModel = {
  documentId: string;
  documentType: "requirement_spec" | "software_design" | string;
  title: string;
  subtitle?: string;
  versionLabel?: string;
  status: "empty" | "draft" | "generated" | "checking" | "ready_to_freeze" | "frozen";
  page: StandardDocumentPageViewModel;
  sections: StandardDocumentSectionViewModel[];
  annotations: StandardDocumentAnnotationViewModel[];
  traceLinks: StageTraceLinkViewModel[];
};

type StandardDocumentSectionViewModel = {
  sectionId: string;
  title: string;
  ordinal?: string;
  summary?: string;
  blocks: StandardDocumentBlockViewModel[];
  status?: "empty" | "draft" | "generated" | "checked" | "blocked" | "frozen";
};

type StandardDocumentBlockViewModel = {
  blockId: string;
  kind: "paragraph" | "clause" | "table" | "list" | "code" | "diagram_placeholder";
  title?: string;
  content: string;
  anchorId?: string;
  sourceRefs?: string[];
  qualityRefs?: string[];
};
```

该模型把 `P2` 的条款和 `P3` 的设计段落统一为 `block`。`P2` 可以大量使用 `kind = "clause"`，`P3` 可以先使用 `paragraph`、`list` 和 `table`，后续再增加接口表、状态机表、模块表。

文档纸面不负责判断内容正确性，只负责表达：

- A4 纸面。
- 文档标题、版本和状态。
- 章节和正文块。
- 批注锚点。
- 检查定位。
- 来源追溯。
- 冻结版印记。

### 4.4 主产物 Tab 槽位模型

右侧主产物不应固定死为“正文一个视图”。它应由标准 Tab 槽位组成：

| Tab 槽位 | 共性名称 | P2 内容 | P3 内容 |
| --- | --- | --- | --- |
| 正文 | `document` | 需求规格说明 A4 正文 | 软件设计说明 A4 正文 |
| 目录 | `outline` | 章节、条款、缺口位置 | 章节、模块、接口、追溯位置 |
| 检查 | `quality` | 缺口检查结果 | 设计完整性检查结果 |
| 追溯 | `traceability` | P1 知识、用户输入、字段映射 | P2 条款到设计元素映射 |
| 投影 | `projection` | P3 可消费冻结包 | P4 工单投影 / P5 设计输入 |
| 冻结 | `freeze` | 冻结条件、冻结记录 | 设计冻结、工单投影锁定 |

`DocumentProductSurface` 应只负责 Tab 容器；每个槽位由专门 Panel 渲染。建议形成以下共性 Panel：

```text
DocumentBodyPanel
DocumentOutlinePanel
QualityCheckPanel
TraceabilityPanel
StageProjectionPanel
StageFreezePanel
```

这些 Panel 消费共性 view model，不消费业务 DTO。

### 4.5 质量检查和门禁模型

`P2` 的缺口检查与 `P3` 的设计完整性检查应统一为 `StageQualityGateViewModel`：

```ts
type StageQualityGateViewModel = {
  status: "not_run" | "running" | "passed" | "warning" | "blocked";
  summary: {
    blockingCount: number;
    warningCount: number;
    passedCount: number;
  };
  gates: StageQualityGateItemViewModel[];
};

type StageQualityGateItemViewModel = {
  itemId: string;
  severity: "blocking" | "warning" | "passed";
  title: string;
  description: string;
  scope: "input" | "document" | "state" | "projection" | "freeze";
  anchorId?: string;
  suggestedAction?: string;
};
```

该模型保留两层语义：

1. `status` 表达整个阶段是否具备冻结或投影条件。
2. `gates` 表达具体阻断项、提醒项和通过项。

共性层只显示检查结果和定位；检查规则仍属于各阶段业务层。

### 4.6 下游投影和交接包模型

`P2 -> P3` 与 `P3 -> P4` 都是阶段输出投影。统一模型如下：

```ts
type StageOutputProjectionViewModel = {
  targetStage: string;
  packageName: string;
  status: "not_ready" | "preview" | "ready" | "frozen" | "delivered";
  sourceDocumentId?: string;
  sourceStateId?: string;
  items: StageProjectionItemViewModel[];
};

type StageProjectionItemViewModel = {
  itemId: string;
  title: string;
  itemType: "document" | "module" | "workorder" | "interface" | "data_object" | "constraint";
  description?: string;
  traceRefs?: string[];
  readiness?: "missing" | "partial" | "ready";
};
```

`P2` 的投影项可以是需求规格文档、结构化需求包、条款映射；`P3` 的投影项可以是设计模块、接口、工单、约束和验收点。

### 4.7 交互轮次模型

`P2` 的问答模式、表单模式与 `P3` 的 CLI 不应被抽成同一个业务算法，但可以抽成同一个交互容器：

```ts
type StageInteractionViewModel = {
  mode: "cli" | "questionnaire" | "form" | "hybrid";
  title: string;
  description?: string;
  feed: StageInteractionMessageViewModel[];
  composer: StageInteractionComposerViewModel;
  lastTurn?: StageInteractionTurnViewModel;
};

type StageInteractionTurnViewModel = {
  turnId: string;
  userInput: string;
  interpretedIntent?: string;
  affectedScopes: Array<"input" | "state" | "document" | "quality" | "projection">;
  stateEffectSummary?: string;
  documentEffectSummary?: string;
  nextSuggestions: string[];
};
```

这个模型只定义“交互如何展示”和“一轮交互影响了哪些范围”。它不要求 `P2` 和 `P3` 共用组织器，也不要求共用 Prompt、状态机或生成规则。

### 4.8 冻结和发布模型

阶段冻结可以抽成统一动作，但冻结规则不抽：

```ts
type StageFreezeViewModel = {
  status: "not_ready" | "ready" | "freezing" | "frozen" | "reopened";
  gates: StageQualityGateItemViewModel[];
  candidateOutputs: StageFreezeOutputViewModel[];
  frozenRecord?: StageFreezeRecordViewModel;
};

type StageFreezeOutputViewModel = {
  outputId: string;
  outputType: "standard_document" | "structured_state" | "projection_package";
  title: string;
  targetStage?: string;
  readiness: "missing" | "partial" | "ready";
};
```

`P2` 冻结输出：

- 标准需求规格说明。
- 结构化 `RequirementSpec` 包。
- `P3` 可消费输入包。
- 条款批注和追溯信息。

`P3` 冻结输出：

- 软件设计说明。
- `SoftwareDesignBaseline v2`。
- `P4` 模块工单投影。
- 设计检查和追溯记录。

### 4.9 Adapter 合同

共性抽象能否成立，关键在 Adapter，而不是组件命名。每个阶段必须实现自己的 Adapter：

```text
P2RequirementAuthoringWorkbenchAdapter
P3DesignLabWorkbenchAdapter
```

Adapter 必须遵守以下规则：

1. 输入是阶段业务 DTO。
2. 输出是 `StageDocumentWorkbenchViewModel`。
3. 不访问 DOM。
4. 不调用 API。
5. 不写 CSS。
6. 不把业务 DTO 透传给共性组件。
7. 不吞掉业务字段，只把暂时无法展示的字段放入 `rawRefs` 或调试扩展区。

这样才能保证共性组件稳定，业务页面仍保留自身事实和规则。

### 4.10 抽象完成度结论

按“设计抽象”口径，本章已经把上一版缺口补齐为以下完整抽象：

- 工作台内核对象。
- 统一工作台视图模型。
- 标准文档模型。
- 主产物 Tab 槽位。
- 质量检查和门禁模型。
- 下游投影模型。
- 交互轮次模型。
- 冻结和发布模型。
- Adapter 合同。

按“代码实现”口径，当前仍只有外壳、主产物 Tab 和 A4 纸面的首版实现。下一轮开发应按本章模型把实现补齐，而不是再重新讨论抽象方向。

## 5. 抽象边界

### 5.1 应当抽象的部分

| 抽象对象 | 应抽象原因 | 设计抽象状态 | 代码实现状态 |
| --- | --- | --- |
| 阶段工作台外壳 | P2/P3/P4/P5 都可能需要阶段工作区 | 已定义 | 已有首版 `StageDocumentWorkbench` |
| 标准文档主产物表面 | P2 需求规格和 P3 软设都以文档为正面对象 | 已定义 | 已有首版 `DocumentProductSurface` |
| A4 文档纸面 | 正式文档体验应统一 | 已定义 | 已有首版 `A4DocumentSurface` |
| 主产物 Tab 槽位 | 正文、目录、检查、追溯、投影、冻结是共性视图槽 | 已定义 | 当前仅 `P3` 页面内实现部分 Tab |
| 标准文档模型 | 统一表达需求条款和设计章节 | 已定义 | 待从 A4 组件入手增强 |
| 质量检查和门禁模型 | 缺口检查和设计检查结构相似 | 已定义 | 实现待落地：`QualityCheckPanel` |
| 下游投影模型 | P2 到 P3、P3 到 P4 都是阶段输出投影 | 已定义 | 实现待落地：`StageProjectionPanel` |
| 交互轮次模型 | 问答、表单、CLI 都是人机状态修订入口 | 已定义 | 实现待落地：交互容器 |
| 冻结和发布模型 | 每阶段都需要冻结门禁和输出包锁定 | 已定义 | 实现待落地：`StageFreezePanel` |
| Adapter 合同 | 避免共性组件读取业务 DTO | 已定义 | 实现待落地：`P2` / `P3` adapter |

### 5.2 不应当抽象的部分

| 不抽象对象 | 原因 |
| --- | --- |
| `P2` 需求语义状态内部结构 | 它是需求分析业务事实，不是平台 UI 事实 |
| `P3` 的 `SoftwareDesignBaseline v2` 内部结构 | 它是软件设计业务事实，不应被 UI 共性层稀释 |
| `P2` 问答组织器运行算法 | 它服务需求收敛，不等于 P3 设计状态机 |
| `P3` 工单投影规则 | 它面向 P4 合同，不应放入通用工作台 |
| 旧 `/xx-p3` 审批流 | 当前不是 P3 新主线，保留但不参与本轮抽象 |
| 后端直接控制像素级布局 | 会把前端变成低代码页面系统，风险高且没有必要 |

抽象的边界原则是：

```text
共性层管工作台形态、文档投影、交互容器和检查展示；
业务层管阶段事实、生成算法、检查规则和输出包结构。
```

## 6. 分层目标架构

建议把阶段文档工作台分成五层。

```text
页面路由层
  -> 阶段页面编排层
    -> 阶段 Adapter 层
      -> 共性工作台组件层
        -> 基础 UI 组件和样式层
```

| 层 | 职责 | 不应承担 |
| --- | --- | --- |
| 页面路由层 | 绑定 `/requirement-authoring`、`/p3-design-lab` 等入口 | 不写业务默认值 |
| 阶段页面编排层 | 加载数据、提交动作、处理错误、控制弹窗 | 不拼接通用布局细节 |
| 阶段 Adapter 层 | 把业务 DTO 转成共性视图模型 | 不调用 DOM，不写 CSS |
| 共性工作台组件层 | 渲染工作台、文档表面、Tab、检查和投影 | 不直接调用 API，不理解业务 DTO |
| 基础 UI 组件和样式层 | 提供纸面、列表、徽标、空状态、响应式约束 | 不承载业务规则 |

当前实现大致处于：

```text
页面编排层 + 内联 Adapter + 共性工作台组件层首版
```

后续重点不是继续加页面，也不是重新讨论抽象，而是把第 4 章定义的模型落实到 Adapter 和 Panel 文件中。

## 8. 当前实现的价值和不足

### 8.1 当前实现价值

当前实现和本文抽象补全合在一起，已经完成了四件关键事：

1. 证明 `P3` 可以放弃旧流程页主线，转向以软件设计说明为正面对象的工作台。
2. 证明 `P2` 的“左侧交互、右侧标准正文”不是单阶段特例，可以迁移到 `P3`。
3. 形成了可被 `P2` 回迁验证的首批共性组件。
4. 把工作台内核、标准文档模型、质量门禁、下游投影、交互轮次、冻结发布和 Adapter 合同补齐为明确抽象。

这比单纯改出一个 `P3` 页面更重要，因为它为平台后续演进提供了共同结构。

### 8.2 当前代码实现不足

当前不足主要在代码落地，而不是抽象方向：

1. 共性层代码仍偏展示骨架，尚未实现完整 `StageDocumentWorkbenchViewModel`。
2. `P3DesignLabPage` 仍承担较多业务适配和 Tab 内容渲染。
3. `A4DocumentSurface` 只是基础纸面，还不是完整正式文档渲染器。
4. `DocumentProductSurface` 只是 Tab 容器，目录、检查、追溯、投影和冻结 Panel 尚未代码组件化。
5. `P2` 尚未迁移到共性组件，抽象尚未经过第二业务样本的运行验证。
6. `P3` CLI 提交、检查 API、冻结 API、持久化会话仍未完整接入。

因此，当前结论应表述为：

```text
阶段文档工作台抽象已经完成到可评审模型层，并完成 P3 首轮前端骨架验证；
但它尚未达到平台级实现稳定态，还需要按模型补齐代码、回迁 P2 并完成第二业务样本验证。
```

## 9. 风险分析

### 9.1 过早平台化风险

如果现在把共性工作台包装成完全通用平台框架，容易把尚未经过代码验证的业务差异强行抹平。尤其是 `P2` 的问答组织器和 `P3` 的设计状态机不同，不能用同一套后端流程抽象覆盖。

控制策略：

- 只把第 4 章定义为前端工作台和视图模型抽象。
- 暂不抽统一业务状态机、统一组织器或统一 Prompt。
- 等 `P2` 回迁后再评估是否抽更深层的阶段运行时。

### 9.2 静态原型化风险

用户已经指出当前界面容易像静态布局页。仅靠布局抽象不能解决这个问题。工作台必须体现运行状态、交互轮次、检查反馈和下游投影变化。

控制策略：

- 把 CLI 提交接入真实 `turns` API。
- 把检查 Tab 接入真实 `check` API。
- 把冻结和投影状态作为可变化状态显示。
- 保持右侧文档主产物随状态变化。

### 9.3 DTO 泄漏风险

如果共性组件直接读取 `RequirementAuthoringDocumentDetail` 或 `P3DesignLabSession`，抽象会失效，组件会变成跨业务 DTO 的混合层。

控制策略：

- 新增 `p2RequirementAuthoringWorkbenchAdapter`。
- 新增 `p3DesignLabWorkbenchAdapter`。
- 共性组件只接受共性 view model。

### 9.4 A4 文档组件过薄风险

当前 A4 组件只支持简单章节。若不继续增强，`P2` 回迁时会丢失条款、批注、缺口定位和冻结状态表达。

控制策略：

- 先扩展为章节加条款模型。
- 支持批注锚点和检查定位。
- 支持冻结版印记和只读态。
- 保持简单章节输入兼容 `P3` 当前形态。

## 11. 推荐验收口径

判断“抽象结果好不好”，不应只看 `P3` 页面是否好看，而应看以下条件：

1. `P3` 页面里是否已经不再围绕旧审批流展开。
2. `P3` 的正面工作对象是否明确变成软件设计说明。
3. 右侧主产物是否以 A4 标准文档为中心。
4. 左侧输入事实和 CLI 是否服务于右侧文档生成，而不是抢占主产物位置。
5. `P3` 页面是否复用了共性工作台外壳，而不是独立堆一套结构。
6. 报告是否定义了统一工作台模型、标准文档模型、质量门禁模型、投影模型、交互模型、冻结模型和 Adapter 合同。
7. 共性组件是否不读取 `P3` 专用 DTO。
8. `P2` 后续是否能在不破坏业务行为的前提下迁移到同一骨架。
9. 目录、检查、追溯、投影、冻结是否能成为共性 Tab，而不是每个阶段重复造。
10. 文档、检查、冻结、投影是否来自同一后台事实状态。
11. 旧 `/xx-p3` 是否被保留但不再主导新 P3 设计方向。

按设计抽象口径，当前报告满足第 1、2、3、4、5、6、11 项；第 7、8、9、10 项需要代码落地和 `P2` 回迁验证。

## 12. 最终判断

本轮抽象的价值在于：它把 `P3` 从“另一个独立业务页面”拉回到 `P2` 已经验证过的阶段文档工作台范式中。

更准确地说，当前抽象结果是：

```text
以标准文档为正面工作对象，
以结构化阶段事实为后台权威状态，
以左侧输入和交互轮次驱动右侧文档主产物，
以检查、冻结和下游投影完成阶段交接的工作台骨架。
```

这个抽象比 `P3` 当前页面本身更重要。页面只是第一个验证样本；真正应沉淀的是：

- 阶段文档工作台外壳。
- 标准文档主产物表面。
- A4 文档渲染能力。
- 目录、检查、追溯、投影、冻结等主产物附属面。
- 质量门禁、交互轮次、下游投影和冻结发布模型。
- 阶段 DTO 到共性 view model 的 adapter 规则。

按设计报告口径，这些抽象已经补齐；按工程落地口径，只有当这些能力通过 `P3` 代码验证并回迁 `P2` 后，`CodeFactoryV2` 才算真正拥有可复用的平台级阶段工作台，而不是多个看起来相似但实现割裂的页面。
