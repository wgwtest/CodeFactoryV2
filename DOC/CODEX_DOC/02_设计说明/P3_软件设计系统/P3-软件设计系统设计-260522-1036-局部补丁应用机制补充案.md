# P3 软件设计系统设计-局部补丁应用机制补充案

**日期：** 2026-05-22

**归属主文档：** `P3-软件设计系统设计.md`

**设计状态：** 待评审补充案

## 1. 背景

当前 `P3 Design Lab` 已支持在软设段落或章节上发起局部 AI 沟通，并由 Dify 或本地提案器返回 `patch_proposal`。该能力解决了“如何让 AI 针对当前对象提出修改建议”的问题，但还没有把“已经生成的补丁提案如何应用到软件设计说明和设计包”讲清楚。

如果缺少应用机制，用户会看到补丁提案，却无法判断下一步是复制粘贴、重新生成、继续追问，还是由系统自动写入正文。这会导致三个问题：

1. 补丁提案停留在展示层，无法成为设计闭环。
2. 用户可能误以为 AI 已经修改了软件设计说明，但实际上正文和设计基线没有变化。
3. 后续功能树、分层架构、技术实现和 `P4` 投影无法知道局部修改是否已经被采纳。
4. 前端缺少明确的刷新、定位和高亮规则，用户不知道应用后的正文变更落在文档哪里。
5. 局部快捷动作和补丁提案如果混在同一块区域中并列展示，会挤占真正需要确认的提案内容。

因此，局部 AI 沟通必须拆成两个阶段：

```text
生成补丁提案
  -> 人工确认应用补丁
```

其中，Dify 只负责第一阶段；第二阶段由 CodeFactory 的补丁应用服务负责。

## 2. 设计目标

本补充案用于明确：

1. 补丁提案和正式应用结果之间的边界。
2. 用户在 `Inspector` 中如何应用、放弃或继续追问一个提案。
3. 后端如何校验补丁、应用正文变更、同步设计基线和记录审计。
4. 哪些补丁可以首版自动应用，哪些只能作为人工建议展示。
5. 应用失败、版本冲突、不可执行提案和部分应用时如何处理。
6. 前端如何展示提案、应用结果、正文刷新、变更定位和轻量输入建议。

## 3. 核心结论

局部补丁应用采用以下模式：

```text
AI / Dify 生成 patch_proposal
  -> 后端保存为 scoped_design_edit Turn
    -> Inspector 展示提案、差异预览和质量提示
      -> 用户点击“应用到文档”
        -> 后端校验 base_revision_id 和 operations
          -> 正文补丁物化服务更新 design_document
            -> 设计基线归并服务同步 trace / baseline delta
              -> 追加 patch_application Turn / audit
                -> 前端刷新软设文档并高亮变更
```

不允许：

```text
Dify 直接改写 design_document
```

也不允许：

```text
前端把提案文本复制进正文后自行认为已应用
```

## 4. 用户使用流程

### 4.1 生成提案

1. 用户在软设工作区选中软设章节、软设段落、功能树节点、分层架构节点或其他可选对象。
2. `Inspector` 显示当前对象摘要和局部提案工作区。
3. 局部提案工作区默认包含一个修改意图输入框和少量轻量建议项，例如“扩写本段”“补充小节”“补充约束”。
4. 用户可以直接输入修改意图，也可以点击轻量建议项，把建议文本填入输入框。
5. 轻量建议项只负责组织输入意图，不直接等于已经生成补丁，也不应占用补丁提案展示区的主视觉空间。
6. 用户确认提交后，前端提交 `scoped_design_edit` Turn，请求携带 `scope_anchor`、`interaction_mode=propose_patch` 和 `expected_output`。
7. 后端调用 Dify 或本地提案器，保存 `patch_proposal`。
8. 前端展示补丁提案、差异预览、质量提示和上下文收据。

此阶段只说明“建议怎么改”，不修改权威软件设计说明。

### 4.2 判断是否可应用

前端收到 `patch_proposal` 后必须区分两类结果：

| 类型 | 条件 | 前端动作 |
| --- | --- | --- |
| 可执行补丁 | `operations` 非空，且每个 `op` 属于当前版本支持列表 | 显示“应用到文档”按钮 |
| 不可执行建议 | `operations` 为空、缺少目标锚点、只包含解释或质量提示 | 不显示应用按钮，显示“继续追问 / 重新生成可执行补丁” |

不可执行建议仍可保留在 Turn Ledger 中，但不得伪装成已经可应用的正文补丁。

### 4.3 应用提案

用户点击“应用到文档”后：

1. 前端提交 `proposal_id`、`turn_id`、`scope_anchor` 和当前前端看到的 `base_revision_id`。
2. 后端重新从当前会话中读取对应 `patch_proposal`，不信任前端回传的完整 operations。
3. 后端校验当前 `design_revision_id` 是否仍等于 `base_revision_id`。
4. 后端校验目标章节、正文块或对象仍存在。
5. 后端校验 operations 是否全部属于当前支持的操作类型。
6. 后端执行正文补丁物化。
7. 后端执行设计基线归并或追溯更新。
8. 后端把提案状态从 `proposed` 改为 `applied`。
9. 后端追加应用审计事件和应用结果 Turn。
10. 前端以服务端返回的权威结果刷新软设文档，并按 `updated_targets` 定位和高亮变更区域。

### 4.4 放弃和继续追问

用户可以选择：

- `放弃提案`：把提案状态改为 `rejected`，记录拒绝原因，不修改正文。
- `继续追问`：基于同一 `scope_anchor` 和上一轮 `patch_proposal` 继续生成新提案。
- `重新生成可执行补丁`：当当前结果只有说明、没有 operations 时，明确要求 Dify 输出可执行 operations。

这些动作都必须写入同一 `SoftwareDesignSession` 的 Turn Ledger，不能只停留在前端 UI 状态。

### 4.5 应用后的前端呈现

补丁应用成功后，前端不得依赖用户复制粘贴，也不得只在当前 DOM 上做临时文本替换。前端必须以服务端返回的 `updated_session`、`design_document`、`result_revision_id` 和 `updated_targets` 为准，重新渲染软件设计说明。

应用结果呈现规则如下：

| 操作 | 前端呈现 |
| --- | --- |
| `rewrite_block` | 原正文块替换为新正文块内容，保持章节位置不变，高亮该正文块 |
| `split_block` | 原正文块被多个新正文块替换，定位到第一个新块，并高亮整组新块 |
| `insert_block_after` | 在目标块之后插入新块，滚动到第一条新增内容 |
| `add_subsection` | 刷新章节目录，展开父章节，定位到新增小节标题 |
| `update_trace_refs` | 刷新当前块或章节的追溯信息，在 `Inspector` 中提示追溯已更新 |
| `add_quality_note` | 在提案区或质量提示区追加提示，不修改正文主体 |

前端应用成功后的状态反馈应包含：

1. 文档修订号从 `base_revision_id` 切换到 `result_revision_id`。
2. 软设文档窗口刷新为服务端返回的正文投影。
3. 章节目录同步更新，新增或拆分的小节可被选中。
4. 变更目标短时高亮，且 `Inspector` 保持选中最新目标。
5. 提案卡片状态改为“已应用”，应用按钮消失或禁用。
6. 如后端返回 `warnings`，在提案卡片下方显示，不覆盖正文。

如果应用失败，前端不得修改本地文档视图；只显示失败原因和建议动作。

## 5. 数据状态模型

### 5.1 `DesignPatchProposal`

`DesignPatchProposal` 至少包含：

```json
{
  "proposal_id": "patch-0042",
  "base_revision_id": "rev-0007",
  "target_anchor": {
    "anchor_type": "design_block",
    "section_id": "sdd-3-2",
    "block_id": "sdd-3-2-block-1"
  },
  "operations": [],
  "quality_notes": [],
  "status": "proposed",
  "applicability": {
    "can_apply": false,
    "reason": "operations_empty"
  }
}
```

`status` 取值：

| 状态 | 含义 |
| --- | --- |
| `proposed` | 已生成，等待用户确认 |
| `applied` | 已应用到正文或设计包 |
| `rejected` | 用户明确放弃 |
| `superseded` | 已被后续提案替代 |
| `conflicted` | 应用时发现版本或目标冲突 |
| `invalid` | 结构不满足应用条件 |

### 5.2 `PatchApplicability`

后端归一化补丁提案时，应计算 `applicability`：

```json
{
  "can_apply": true,
  "reason": "ready",
  "supported_ops": ["rewrite_block", "split_block", "insert_block_after", "add_subsection", "update_trace_refs"],
  "unsupported_ops": []
}
```

常见 `reason`：

| reason | 含义 |
| --- | --- |
| `ready` | 可应用 |
| `operations_empty` | 没有可执行操作 |
| `unsupported_operation` | 包含当前版本不支持的操作 |
| `missing_target_anchor` | 缺少目标锚点 |
| `missing_target_object` | 目标章节或正文块不存在 |
| `revision_conflict` | 当前文档版本与 `base_revision_id` 不一致 |
| `needs_manual_merge` | 只能人工合并 |

## 6. 首版支持的补丁操作

首版只支持直接作用于软件设计说明正文的少量操作，避免一次性把功能树、分层架构和 `P4` 投影都纳入自动写回。

| op | 首版行为 | 说明 |
| --- | --- | --- |
| `rewrite_block` | 支持 | 用新正文替换目标正文块内容 |
| `split_block` | 支持 | 用多个新正文块替换目标正文块 |
| `insert_block_after` | 支持 | 在目标正文块后插入正文块 |
| `add_subsection` | 支持 | 在目标章节下新增子章节或小节 |
| `update_trace_refs` | 有限支持 | 更新正文块或章节的来源引用，不直接改需求 |
| `add_quality_note` | 支持 | 追加到检查提示或当前对象质量提示 |
| `merge_blocks` | 暂缓 | 容易涉及相邻块冲突，首版作为人工建议 |

功能树、分层架构、技术实现、展示形态和 `P4` 投影对象的补丁，首版可以生成提案，但默认不自动应用；除非对应对象已有明确的物化服务和冲突校验。

## 7. 后端服务划分

### 7.1 应用入口

建议新增接口：

```text
POST /api/software-design-v2/sessions/{session_id}/patch-proposals/{proposal_id}/apply
```

请求体建议：

```json
{
  "turn_id": "p3turn-abc",
  "base_revision_id": "rev-0007",
  "apply_scope": "document_only",
  "user_note": "确认应用到 3.2 总体分层"
}
```

响应体建议返回更新后的会话、应用结果和被更新对象：

```json
{
  "application_id": "patch-app-001",
  "status": "applied",
  "updated_session": {},
  "updated_targets": [
    {
      "target_type": "design_block",
      "section_id": "sdd-3-2",
      "block_id": "sdd-3-2-block-1"
    }
  ],
  "warnings": []
}
```

### 7.2 正文补丁物化服务

`DesignDocumentPatchApplicationService` 负责：

- 定位目标章节和正文块。
- 执行 `rewrite_block`、`split_block`、`insert_block_after`、`add_subsection`。
- 生成新的正文块 ID。
- 保留旧正文块引用和变更来源。
- 更新文档修订号。
- 返回被更新的章节、正文块和差异摘要。

### 7.3 设计基线归并服务

`DesignBaselinePatchMergeService` 负责：

- 根据 `update_trace_refs` 更新追溯映射。
- 根据正文变更标记相关设计对象为 `needs_review` 或 `patched`。
- 对影响功能树、分层架构和投影的补丁只记录待应用调整，不越权直接改下游形态。
- 触发或标记后续设计完整性检查。

### 7.4 审计与摘要服务

补丁应用后，后台必须写入：

- 应用审计事件。
- 应用结果 Turn。
- 提案状态变化。
- 局部对象摘要。
- 全局会话摘要。

审计记录中必须包含原提案、执行时间、执行人、应用结果、冲突或警告。

## 8. 冲突与失败处理

### 8.1 版本冲突

如果当前文档修订号不等于 `base_revision_id`，后端不得直接应用补丁，应返回：

```json
{
  "status": "conflicted",
  "reason": "revision_conflict",
  "message": "当前软设正文已发生变化，请重新生成补丁或人工合并。"
}
```

前端显示“文档已变化，需重新生成或人工合并”，并提供“重新生成提案”动作。

### 8.2 不可执行提案

如果 `operations` 为空，后端应把提案标记为 `invalid` 或 `proposed` 但 `can_apply=false`。前端不得展示“应用到文档”按钮。

用户可继续追问：

```text
请把上面的建议转换为可执行补丁操作。
```

### 8.3 部分失败

首版不允许部分应用。只要一个 operation 不可执行，整个补丁应用失败，不修改正文。后续版本可以引入分组应用，但必须提供操作级差异预览和回滚记录。

### 8.4 重复应用

如果提案状态已经是 `applied`，再次应用应返回幂等结果或明确提示“已应用”。不得重复插入正文块。

## 9. 前端交互要求

`Inspector` 能力页中的局部区域应采用“局部提案工作区”，而不是把一组大按钮长期铺开。该工作区分为三个层级：

1. 对象摘要：只保留当前章节或段落的最小上下文，例如标题、来源和当前状态。
2. 输入区：包含修改意图输入框和轻量建议项。
3. 提案区：一旦生成 `patch_proposal`，提案区成为该工作区的主内容。

轻量建议项的设计要求：

- “扩写本段”“补充小节”“补充约束”等只能作为输入建议 chip、下拉项或小按钮存在。
- 点击轻量建议项默认只是把一段可编辑意图填入输入框，例如“请扩写当前段落，补充设计约束、处理流程和异常情况”。
- 是否自动提交应由明确的主按钮控制，不应让用户误以为点击建议项已经应用了正文变更。
- 轻量建议项不得和补丁提案卡片并列抢占空间；有提案后可以折叠到输入框上方或更多菜单。
- “应用补丁”不是默认常驻动作，只能作为某个可执行补丁提案卡片上的条件动作出现。

`Inspector` 中的补丁提案区应至少包含：

1. 提案状态：待应用、已应用、不可应用、冲突、已放弃。
2. 差异预览：展示将新增、替换或拆分的正文块。
3. 质量提示：展示 Dify 或检查器返回的警告和说明。
4. 主动作：
   - `应用到文档`
   - `放弃提案`
   - `继续追问`
   - `重新生成可执行补丁`
5. 应用中状态：按钮禁用、转圈、显示“正在应用补丁”。
6. 应用成功反馈：高亮被修改章节，并提示需要重新运行检查。
7. 应用失败反馈：显示后端 `reason` 和建议动作。

补丁提案卡片出现后，局部提案工作区的视觉优先级应调整为：

```text
当前对象摘要
  -> 补丁提案卡片 / 差异预览 / 质量提示
    -> 应用、放弃、继续追问
      -> 输入框和轻量建议项
```

没有补丁提案时，输入框和轻量建议项可以占主位；已有补丁提案时，提案卡片必须占主位。

如果补丁不可执行，前端应显示：

```text
当前提案只有说明或质量提示，没有可执行补丁操作。可继续追问，让 AI 生成可执行 operations。
```

## 10. 与 Dify 的边界

Dify 局部工作流只输出 `patch_proposal`，不负责：

- 修改 `design_document`。
- 修改 `design_baseline`。
- 决定补丁是否已经应用。
- 生成新的权威修订号。
- 处理版本冲突。

CodeFactory 负责：

- 归一化 Dify 输出。
- 判断补丁可应用性。
- 执行应用。
- 记录审计。
- 更新设计会话和文档投影。

如果 Dify 输出的是说明型提案，例如 `operations=[]` 但 `quality_notes` 有内容，则 CodeFactory 只能展示它，不能自动改写正文。

## 11. 与现有状态的关系

`patch_ready` 表示“有待确认补丁提案”，不表示“补丁已经应用”。

建议补充状态：

| 状态 | 含义 |
| --- | --- |
| `patch_ready` | 已有待确认提案 |
| `patch_applying` | 正在应用补丁 |
| `patched` | 至少一个补丁已应用，等待检查或保存 |
| `patch_conflicted` | 应用补丁时发生冲突 |

应用成功后，设计会话可以进入 `patched` 或保持 `patch_ready` 并通过提案状态区分。首版建议使用 `patched`，便于用户看到正文已发生变更。

## 12. 验收口径

本补充案进入代码实现时，至少满足：

1. 可执行提案和不可执行建议在 UI 上可区分。
2. `operations=[]` 时不显示“应用到文档”按钮。
3. 可执行提案能通过用户确认应用到 `design_document`。
4. 应用前校验 `base_revision_id`。
5. 应用后更新提案状态、会话状态、文档修订号和运行日志。
6. 应用后软设文档窗口刷新，并高亮更新章节或正文块。
7. 应用失败时不修改正文，并显示明确原因。
8. Dify 不直接写入权威正文或设计基线。
9. 应用动作写入 Turn Ledger 和审计事件，可回放、可追踪。
10. “扩写本段”“补充小节”等只是轻量输入建议，不作为和补丁提案并列的大动作按钮。
11. 补丁提案生成后，提案卡片在局部提案工作区占主位。
12. 应用后的正文展示必须来自服务端返回的权威文档结果，不能依赖手工复制粘贴或前端临时替换。

## 13. 首版建议

首版优先实现：

1. `rewrite_block`
2. `split_block`
3. `insert_block_after`
4. `add_subsection`
5. `update_trace_refs`

暂不实现：

- 跨章节合并。
- 多对象联动应用。
- 功能树自动改写。
- 分层架构自动改写。
- `P4` 投影自动改写。

这些能力可以继续生成补丁提案，但必须标记为“人工确认建议”或“待后续物化服务支持”。
