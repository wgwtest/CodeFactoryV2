# P3 软件设计系统设计-260516-0214-软设对象多形态设计补充案

> 本文件是 `P3-软件设计系统设计.md` 的补充案，记录对“软件设计说明 / 软设对象最终形态”的进一步设计判断。本文不替代主设计文档，待评审通过后再归并到主文档中。

## 1. 背景与问题

当前 `P3 Design Lab` 已经形成一个较简单的闭环：

```text
P2 需求规格说明冻结包
  -> 需规转软设基础转换
    -> 软件设计说明草稿
      -> 软设工作区
        -> 结构化数据
          -> P4 投影
```

这个闭环能证明 P3 的基本工作流成立，但还不足以支撑严肃的软件设计工作。原因是：如果只把软设理解成一份 A4 文档，系统虽然能生成“软件设计说明”，但无法充分表达软件设计中更重要的结构关系、技术承载关系和界面呈现关系。

用户提出的新问题可以概括为：

1. 软件设计说明文档是否足以表达软设对象。
2. 软设文档、软设工作区和 P4 投影是否应当完全数据联动。
3. 需规拆解后的功能树如何进入软设。
4. 功能树如何进一步转换为分层架构图。
5. 分层架构图如何映射到真实框架、插件和代码组织。
6. 真实软件模块如何继续表达展示形态或交互形态。

本补充案的结论是：**软设不应被定义为单一文档，而应被定义为一个结构化设计包。A4 软件设计说明只是该设计包的正式文档投影。**

## 2. 核心结论

P3 的主对象建议从“软件设计说明文档”扩展为：

```text
SoftwareDesignPackage
```

`SoftwareDesignPackage` 是一份软件设计的完整结构化表达，至少包含五种形态：

1. 文档形态。
2. 功能树形态。
3. 分层架构形态。
4. 真实技术实现形态。
5. 展示形态 / 交互形态。

它们不是五份互相独立的数据，而是同一份软设对象的不同投影。

```text
SoftwareDesignPackage
  -> DocumentProjection
  -> FunctionalTreeProjection
  -> LayeredArchitectureProjection
  -> TechnicalImplementationProjection
  -> PresentationShapeProjection
  -> P4WorkorderProjection
```

其中权威事实源不应是 A4 正文，也不应是 P4 投影，而应是结构化设计包本身。A4 正文、图形视图、P4 投影都从结构化设计包派生。

## 3. 软件设计包的五种形态

### 3.1 文档形态

文档形态是面向人审阅、评审、冻结和归档的软件设计说明。

它应保持 A4 文档形式，原因是：

- 软件设计说明需要被人阅读和正式评审。
- 设计结论需要进入冻结包。
- 设计过程需要能追溯到标准章节。
- P3 需要继承 P2 对“正式文档产物”的处理方式。

但文档形态不能成为唯一事实源。文档可以表达设计结论，但不擅长表达节点、边、层级、框架横跨关系和多种展示方案。

文档形态至少包含：

| 章节 | 内容 |
| --- | --- |
| 1 概述 | 设计目标、范围、输入需规、设计边界 |
| 2 设计输入与追溯 | 关联需规条款、输入冻结包、设计假设 |
| 3 功能设计 | 功能树主要节点及其设计说明 |
| 4 总体架构 | 分层架构、模块关系、主要技术路线 |
| 5 详细设计 | 模块、接口、数据、状态和异常处理 |
| 6 技术实现映射 | 框架、插件、服务包和代码组织 |
| 7 展示与交互设计 | 可见模块的展示形态、布局候选和交互规则 |
| 8 P4 投影说明 | 可下发工具包、模块工单和阻断项 |
| 9 约束与待确认项 | 非功能约束、技术风险、人工确认项 |

### 3.2 功能树形态

功能树形态负责表达“需规如何被软设承接”。

如果需规中有三个核心功能，软设应首先对应生成三个大功能节点，再继续拆解子功能。

```text
需求规格说明
  -> 功能 A
      -> 子功能 A1
      -> 子功能 A2
  -> 功能 B
      -> 子功能 B1
      -> 子功能 B2
  -> 功能 C
      -> 子功能 C1
```

功能树的优点是：

- 与需规条款天然可追溯。
- 与软件设计说明章节容易一一对应。
- 适合表达从业务功能到设计功能的拆解过程。

功能树的缺点是：

- 它不是软件架构。
- 它不能直接表达数据层、服务层、展示层的真实分工。
- 它不能表达框架或插件横跨多个理论层的情况。

因此功能树只能作为软设的第一层结构化表达，不能替代后续架构视图。

### 3.3 分层架构形态

分层架构形态负责把功能树转换为软件架构表达。

建议初始采用以下层次：

| 架构层 | 表达对象 |
| --- | --- |
| 展示层 | 页面、面板、地图视图、时间轴、图表、编辑器 |
| 交互层 | 用户操作、状态切换、命令入口、事件流 |
| 功能层 | 业务功能模块、工作台模块、设计动作模块 |
| 服务层 | 后端服务、领域服务、编排服务、模型调用服务 |
| 数据层 | 数据模型、存储对象、索引、缓存、文件对象 |
| 集成层 | 外部框架、插件、平台交换、P2/P4/P5/P6 接口 |

分层架构视图回答的问题是：

```text
一个功能树节点在软件架构中由哪些层共同承载？
```

例如：

```text
功能树：冲突识别
  -> 展示层：冲突列表、地图高亮、告警面板
  -> 功能层：冲突识别工作台模块
  -> 服务层：冲突规则计算服务
  -> 数据层：冲突记录、规划任务、空域对象
```

这一步的核心价值是把“业务功能拆解”转换成“软件架构组织”。

### 3.4 真实技术实现形态

真实技术实现形态负责表达理论架构与真实框架、插件、代码组织之间的差异。

用户指出的关键问题是：真实代码组织并不一定与理论架构层一一对应。例如：

- 若依框架可能同时覆盖数据权限、后端服务、管理界面和基础前端页面。
- Cesium 可能同时覆盖前端展示、空间交互、地图对象和部分空间分析能力。
- 一个时间轴模块可能既是展示组件，也是交互控制器，还可能牵动服务层查询接口。

因此 P3 不能简单地把分层架构节点直接变成代码模块。必须增加一个“真实技术实现映射”。

真实技术实现形态至少包含：

| 对象 | 说明 |
| --- | --- |
| 技术组件 | 如若依、Cesium、React、FastAPI、PostGIS、消息队列 |
| 框架承载范围 | 该技术组件覆盖哪些架构层和设计功能 |
| 代码组织候选 | 前端目录、后端服务、插件包、工具包、配置项 |
| 与功能树关系 | 承载哪些功能节点 |
| 与分层架构关系 | 横跨哪些理论层 |
| 与 P4 投影关系 | 是否生成独立工具包、插件包或模块工单 |

示例：

```text
技术组件：Cesium 地理信息球
  -> 承载功能：态势展示、空间查询、冲突区域查看
  -> 覆盖层次：展示层、交互层、部分功能层
  -> 代码组织：frontend/map/CesiumGlobe、frontend/map/layers、spatial-query adapter
  -> P4 投影：Cesium 地图工作台工具包
```

### 3.5 展示形态 / 交互形态

展示形态负责表达可见模块最终如何出现在界面上。

它不是普通 UI 美化，也不是原型图替代物，而是软件设计中的正式对象。原因是：对于交互式系统而言，很多软件模块的价值必须通过展示位置、展示方式和交互方式才能说清楚。

例如“时间轴模块”不能只写成：

```text
时间轴模块：展示事件流。
```

它至少需要表达：

```text
时间轴模块
  -> 展示候选 1：右下角浮层
  -> 展示候选 2：顶部横向时间轴
  -> 展示候选 3：画面中央主面板
  -> 触发方式：点击事件、自动播放、拖拽筛选
  -> 关联对象：地图、任务列表、事件详情
```

展示形态视图回答的问题是：

```text
这个设计模块在用户工作界面中如何被看见、操作和组合？
```

它应与 P3 原型设计衔接，但不等于最终视觉稿。它更像是“展示方案的设计事实源”，后续原型图、前端实现和 P4 工具包都从这里读取约束。

## 4. 五种形态之间的追溯关系

建议建立如下追溯链：

```text
RequirementClause
  -> FunctionalNode
    -> ArchitectureNode
      -> TechnicalModule
        -> PresentationShape
          -> P4WorkorderNode
```

对应说明：

| 起点 | 终点 | 含义 |
| --- | --- | --- |
| 需规条款 | 功能节点 | 需求被哪个设计功能承接 |
| 功能节点 | 架构节点 | 功能落在哪些架构层 |
| 架构节点 | 技术模块 | 理论设计由哪些真实技术承载 |
| 技术模块 | 展示形态 | 可见模块如何呈现和交互 |
| 技术模块 / 展示形态 | P4 工单节点 | 下游应实现什么工具包或模块 |

这条链路可以保证：

1. 文档正文不是孤立文本。
2. 功能树不是静态思维导图。
3. 架构图不是没有落地关系的抽象图。
4. 技术实现不是脱离需求的框架堆砌。
5. 展示形态不是临时 UI 想法。
6. P4 投影不是凭空生成工单。

## 5. 对现有软设工作区的调整建议

现有软设工作区已经区分：

```text
文档视图
结构化数据视图
P4 投影视图
```

下一阶段建议扩展为：

```text
软设工作区
  -> 文档视图
  -> 功能树视图
  -> 分层架构视图
  -> 技术实现视图
  -> 展示形态视图
  -> P4 投影视图
```

其中：

- 文档视图显示 A4 软件设计说明。
- 功能树视图显示从需规拆出的功能节点。
- 分层架构视图显示功能节点在展示层、功能层、服务层、数据层等位置的分布。
- 技术实现视图显示若依、Cesium、插件、服务、组件等真实承载关系。
- 展示形态视图显示可见模块的候选呈现方式。
- P4 投影视图显示从技术实现和展示形态继续派生的工具包 / 工单树。

这些视图可以放在软设工作区内部作为二级视图，也可以在 Lab 主导航中保留 P4 投影作为独立一级视图。若保留 P4 投影一级视图，仍应明确它读取的是同一份 `SoftwareDesignPackage`，不是独立数据源。

## 7. 生成流程调整

### 7.1 基础转换阶段

当前“需规转软设”基础转换不应只生成 A4 文档草稿，而应生成初始 `SoftwareDesignPackage`。

建议基础转换输出：

```text
基础转换输出
  -> A4 文档草稿
  -> 初始功能树
  -> 初始分层架构骨架
  -> 初始技术实现候选
  -> 初始追溯关系
```

展示形态和 P4 投影可以先生成空态或候选态，不要求一次生成完整。

### 7.2 软设微调阶段

软设微调不应只改正文，而应允许用户围绕不同视图微调同一份设计包：

| 用户动作 | 影响对象 |
| --- | --- |
| 补充章节 | 文档投影、追溯关系 |
| 拆分功能 | 功能树、文档章节 |
| 调整架构层 | 分层架构、技术实现候选 |
| 指定框架 | 技术实现、P4 投影候选 |
| 选择展示形态 | 展示形态、文档说明、P4 前端工单 |
| 生成投影候选 | P4 投影 |

### 7.3 P4 投影阶段

P4 投影不应直接从 A4 文档生成，而应从 `TechnicalModule` 和 `PresentationShape` 生成。

```text
TechnicalModule + PresentationShape
  -> P4WorkorderProjectionTree
```

这样可以避免“文档写得像设计，但下游不知道怎么做”的问题。

## 8. 与当前设计的关系

本补充案不否定当前设计，属于对当前设计的深化。

当前设计已经成立的部分：

- P3 正面产物是软件设计说明。
- A4 文档形态需要保留。
- 结构化设计基线是后台权威状态。
- P4 投影必须从设计基线派生。
- 软设工作区和 P4 投影应数据联动。

需要进一步升级的部分：

- `SoftwareDesignBaseline v2` 需要扩展为更完整的 `SoftwareDesignPackage` 或明确包含上述五种形态。
- 结构化数据视图不能只展示模块、接口和数据对象，还要能表达功能树、分层架构、技术实现和展示形态。
- A4 文档不再被视为软设唯一正式表达，而是 `SoftwareDesignPackage` 的文档投影。
- P4 投影的数据来源应进一步明确为技术实现形态和展示形态，而不是直接来自泛化模块列表。

## 9. 风险与设计约束

### 9.1 风险

1. 如果一次性实现五种视图，范围会过大。
2. 如果只做文档视图，P3 会停留在“生成说明书”的浅层能力。
3. 如果只做功能树，无法表达真实软件架构。
4. 如果只做分层架构，无法表达框架和插件横跨多层的问题。
5. 如果只做技术实现，容易变成代码目录规划，而丢失需求追溯。
6. 如果只做展示形态，容易退化为 UI 原型设计，而不是软件设计。

### 9.2 约束

1. 五种形态必须共享同一个软设对象。
2. 任一视图的修改都必须形成结构化增量。
3. 正式冻结必须冻结结构化设计包，而不是只冻结 A4 正文。
4. P4 投影必须可追溯到技术模块和展示形态。
5. 展示形态只能表达设计候选和决策，不替代最终 UI 原型评审。

## 11. 评审问题

本补充案需要用户重点确认：

1. 是否认可“软设 = 结构化设计包 + 多视图投影”，而不是“软设 = A4 文档”。
2. 是否认可五种形态：文档、功能树、分层架构、真实技术实现、展示形态。
3. 是否认可 P4 投影主要从技术实现形态和展示形态派生。
4. 是否需要把展示形态提升为软件设计正式对象，而不是只放在原型阶段。
5. 下一版原型是否按六个视图来画，而不是继续只改现有文档 / 结构化数据双视图。

## 12. 临时结论

P3 下一阶段的重点不应是继续细修页面，而应是重新定义软设对象。

临时结论如下：

```text
软件设计说明文档是正式投影；
SoftwareDesignPackage 才是软设事实源；
功能树负责承接需规；
分层架构负责表达软件组织；
真实技术实现负责表达框架、插件和代码承载；
展示形态负责表达可见模块如何进入界面；
P4 投影负责把技术实现和展示形态转化为可执行工单树。
```

该结论通过后，P3 才具备进入下一轮严肃代码研发的设计基础。
