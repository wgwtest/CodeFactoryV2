## 1. 本补充案目的

`P3 Design Lab` 已经具备从 P2 冻结需规包创建软设会话、执行基础转换、进入软设工作区、生成 P4 投影和冻结设计包的基本页面链路。但当前实现中的基础转换仍偏硬编码，无法稳定支撑真实项目中的多样化需求规格说明。

本文补充的核心目标是：

1. 把 `P3` 的“需规转软设”从固定策略函数升级为可替换的插件式转换器。
2. 明确首个转换器优先采用 Dify workflow，而不是直接自研完整推理引擎。
3. 保留后续自研转换器、远端服务转换器和混合转换器的扩展位置。
4. 固定 `SX-DataStore` 需求规格说明范本与软件设计说明范本作为首轮转换质量样例。
5. 明确转换器只生成可审阅草稿和结构化设计包初稿，不能绕过人工校核直接冻结。

## 2. 样例文档判断

### 2.1 P2 输出样例判断

`01-需求规格说明范本-SX-DataStore.md` 可以作为 P2 标准输出样例。原因如下：

- 它明确说明自己不是空白模板，也不是实现设计说明。
- 它覆盖软件定位、适用范围、术语、角色、场景、范围边界、功能需求、数据与接口需求、非功能需求和验收准则。
- 它刻意不规定前端框架、后端框架、目录结构、类设计和 API 字段实现，这些内容留给 P3 软设说明承接。
- 它包含 `6.3 待确认事项`，适合作为 P3 转换器生成设计缺口和人工校核项的依据。

该文档适合作为：

- P2 冻结需规包内容质量的对照样例。
- P3 转换器输入解析能力的测试样例。
- 需求到设计追溯映射的来源样例。

它不适合作为：

- 一次性投喂给 P2 多轮组织器的完整回答。
- P3 目标软设正文的直接复制来源。
- 软件架构、模块、接口和目录结构的权威来源。

### 2.2 P3 输出样例判断

`02-软件设计说明范本-SX-DataStore.md` 可以作为 P3 目标输出样例。原因如下：

- 它明确说明自己不是需求规格说明，不重新定义用户需求。
- 它把需求落实为系统定位、业务边界、总体架构、前端设计、后端设计、核心对象模型、API 分组、关键运行流程、智能检索、约束、目录结构和验收口径。
- 它能体现从需求事实到设计决策的转换，而不是把需求条目改标题重排。
- 它保留原型边界和后续扩展说明，不把模拟数据伪装成生产级设计。

该文档适合作为：

- P3 转换器目标章节结构的样例。
- 需求到架构、模块、对象、API、流程和质量门转换质量的人工验收参照。
- `SoftwareDesignPackage` 文档形态的初始目标样例。

它不适合作为：

- 唯一软设事实源。
- P4 工单投影的直接替代物。
- 对任意项目通用的固定正文模板。

## 3. 核心设计结论

### 3.1 转换器定位

P3 新增概念为：

```text
软件设计转换器（Software Design Converter）
```

转换器是 `P3` 运行时的一类可插拔能力，负责把 P2 冻结需求规格说明包转换为 `SoftwareDesignPackage` 初稿。

它的输入是：

```text
P2 冻结需求规格说明包
  + 目标软设结构规范
  + 转换策略
  + 样例和质量规则
```

它的输出是：

```text
SoftwareDesignPackage 初稿
  + 软件设计说明草稿
  + 结构化设计对象
  + 需求到设计追溯映射
  + 设计缺口清单
  + 人工校核项
  + P4 投影候选
```

转换器不是：

- P2 需求组织器。
- P4 工单生成器。
- 任意文档改写器。
- 自动冻结器。
- 完整替代人工软件架构师的工具。

### 3.2 与 P2 组织器机制的关系

P2 已经形成了一套有价值的插件化运行经验：

- 插件目录中声明 manifest。
- 宿主系统只通过统一输入输出协议调用插件。
- Dify 型插件由 adapter 调用真实 Dify Workflow API。
- 缺少 Dify 配置时明确失败，不伪造成功结果。
- Dify 输出必须经过本地 adapter 归一化后进入系统状态。

P3 应复用这些工程原则，但不直接复用 P2 语义对象。原因是：

| P2 组织器 | P3 转换器 |
| --- | --- |
| 多轮需求收敛 | 需求文档到设计包转换 |
| 产出需求规格正文 patch 和下一问 | 产出软设草稿、结构化设计包和缺口清单 |
| 面向专家交互 | 面向设计人员校核和冻结 |
| 关注需求是否补齐 | 关注设计是否可实现、可追溯、可投影 |

因此 P3 应建立自己的转换器协议和字段规范，但可以复用 P2 的插件发现、adapter 加载、Dify 调用、错误处理和测试方式。

### 3.3 Dify 优先策略

首版转换器建议优先采用 Dify workflow，理由是：

- 需求到软设的转换需要较强的长文本组织、结构推理和章节生成能力。
- Dify 已在 P2 `brainstorm-v1-dify-workflow` 中验证过 workflow 形态和 API 调用链路。
- 用 Dify 可以先把转换策略、Prompt、节点分支和输出 JSON 固定下来，减少本地自研引擎的早期复杂度。
- 本地工程可以专注于协议、adapter、校验、状态落库、UI 展示和验收，而不是在首轮就实现完整推理工作流。

但 Dify 不应成为唯一长期方案。P3 转换器体系应同时保留：

- `dify_workflow`：首版主路径。
- `local_package`：后续自研规则 / 小模型 / 本地脚本转换器。
- `remote_service`：后续独立转换服务。

### 3.4 Dify 工作台开发解耦

P3 分系统开发与 Dify 工作台开发必须解耦。

当前 CodeFactoryV2 工程负责：

- 定义 P3 转换器协议、字段规范、质量规则和样例验收口径。
- 提供转换器插件目录、adapter、mocked HTTP 测试和错误处理。
- 在 P3 Design Lab 中展示转换器选择、运行状态、结果、缺口和校核项。
- 编写可交给 Dify 工作台开发会话的执行文档。

当前 CodeFactoryV2 工程不负责：

- 直接登录或编辑 Dify 工作台。
- 在本分支保存真实 Dify API Key。
- 在本分支维护 Dify 内部节点状态。
- 把 Dify 内部 Prompt、节点调试过程当作 P3 分系统事实源。

Dify 工作台开发由另一个具备 Dify 接口、API 和密钥配置的 Codex 会话完成。该会话只需要按 P3 执行文档创建并发布 workflow，输出 workflow 标识、输入变量清单、输出 JSON 示例和联调结果。当前 P3 分系统后续只消费 Dify Workflow API 的运行结果。

### 3.5 转换器不得绕过人工校核

转换器输出只能让软设会话进入：

```text
draft_ready / check_pending / review_pending
```

不能直接进入：

```text
frozen
```

冻结仍必须满足：

- 阻断级设计检查通过。
- 设计缺口清单无阻断项，或已有人工处理结论。
- 主要设计章节能追溯到需规来源或明确标记为设计推导。
- 设计人员明确执行冻结动作。

## 4. 转换器输入输出协议

### 4.1 输入对象

建议新增 `DesignConverterRunRequest`，作为 P3 调用转换器的统一输入。

最小字段如下：

| 字段 | 含义 |
| --- | --- |
| `protocol_version` | 转换器协议版本，例如 `p3-design-converter-protocol@1` |
| `session` | P3 设计会话信息 |
| `input_package` | P2 冻结需求规格说明包快照 |
| `target_design_profile` | 目标软设章节结构、设计口径和样例引用 |
| `conversion_options` | 转换策略、粒度、输出风格、是否生成 P4 候选 |
| `quality_rules` | 质量门、缺口规则、追溯要求 |
| `execution_options` | 观测级别、超时、是否允许重试 |

### 4.2 输入包最低要求

转换器运行前，`input_package` 至少应包含：

- 需求规格说明正文。
- 结构化需求对象。
- 角色和职责。
- 核心业务流程。
- 功能项清单。
- 数据与接口需求。
- 非功能需求。
- 验收准则。
- 待确认事项。
- 来源追溯和冻结状态。

如果输入包缺少上述关键内容，转换器应输出设计缺口，而不是用通用话术补齐。

### 4.3 输出对象

建议新增 `DesignConverterRunResult`，作为转换器统一输出。

最小字段如下：

| 字段 | 含义 |
| --- | --- |
| `protocol_version` | 转换器协议版本 |
| `converter` | 实际运行的转换器身份和观测级别 |
| `design_document` | 软件设计说明草稿正文结构 |
| `design_package` | `SoftwareDesignPackage` 初稿 |
| `traceability` | 需求到设计章节、模块、对象、接口、流程的映射 |
| `gap_list` | 设计缺口清单 |
| `review_findings` | 人工校核建议和风险 |
| `workorder_projection_candidate` | P4 模块工单投影候选 |
| `process_output` | 转换过程、Dify trace、节点摘要和警告 |
| `raw_output` | 原始插件响应或远端 workflow 响应摘要 |

### 4.4 `SoftwareDesignPackage` 初稿结构

转换器首版生成的 `SoftwareDesignPackage` 至少包含：

| 子对象 | 说明 |
| --- | --- |
| `document_projection` | 软件设计说明 A4 正文草稿 |
| `functional_tree_projection` | 从需求功能项派生的功能树 |
| `layered_architecture_projection` | 展示层、交互层、功能层、服务层、数据层、集成层结构 |
| `technical_implementation_projection` | 技术栈、框架、服务包、目录候选 |
| `api_projection` | API 分组和关键接口候选 |
| `workflow_projection` | 关键运行流程 |
| `quality_gate_projection` | 非功能、异常、安全、测试和验收质量门 |
| `p4_workorder_projection` | P4 工单候选树 |

## 5. Dify workflow 设计口径

### 5.1 Dify 输入变量

P3 Dify 转换器建议使用以下变量：

| 变量 | 类型 | 含义 |
| --- | --- | --- |
| `requirement_document_text` | string | 需求规格说明正文 |
| `structured_spec_json` | string | 结构化需求对象 |
| `target_design_profile_json` | string | 目标软设结构规范 |
| `conversion_options_json` | string | 转换选项 |
| `quality_rules_json` | string | 质量规则 |
| `sx_datastore_requirement_sample` | string | SX-DataStore 需求样例摘要，不应整篇作为提示主输入 |
| `sx_datastore_design_sample_outline` | string | SX-DataStore 软设样例结构摘要 |

复杂对象统一以 JSON 字符串传入，沿用 P2 Dify 插件的低耦合做法。

### 5.2 Dify 输出 JSON

Dify workflow 必须返回可解析 JSON。推荐字段如下：

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `design_document` | 是 | 软件设计说明草稿 |
| `design_package` | 是 | 结构化设计包初稿 |
| `traceability` | 是 | 需求到设计映射 |
| `gap_list` | 是 | 缺口清单 |
| `review_findings` | 是 | 人工校核项 |
| `workorder_projection_candidate` | 否 | P4 工单候选 |
| `confidence` | 是 | 置信度 |
| `annotations` | 是 | 过程注释 |
| `risks` | 是 | 风险提示 |
| `raw_workflow_trace` | 否 | Dify 工作流 trace 摘要 |

adapter 必须校验必填字段。字段缺失、非 JSON、Dify 失败或超时，都应返回明确错误。

### 5.3 Dify 节点建议

首版 Dify workflow 可以按以下节点组织：

```text
normalize_input
  -> requirement_section_parse
  -> design_object_extraction
  -> target_outline_mapping
  -> design_package_compose
  -> gap_and_review_check
  -> normalize_output
```

各节点职责：

| 节点 | 职责 |
| --- | --- |
| `normalize_input` | 清洗输入包，抽取标题、章节、功能、数据、非功能、验收和待确认项 |
| `requirement_section_parse` | 识别 P2 章节和需求元素 |
| `design_object_extraction` | 抽取角色、对象、流程、模块候选、接口候选和质量约束 |
| `target_outline_mapping` | 将需求元素映射到目标软设章节 |
| `design_package_compose` | 生成软件设计说明草稿和结构化设计包 |
| `gap_and_review_check` | 生成设计缺口、风险和人工校核项 |
| `normalize_output` | 输出符合 P3 转换器协议的 JSON |

## 6. 后端落地设计

### 6.1 新增后端模块

建议新增：

```text
apps/api/app/design_converters/
  models.py
  converter_protocols.py
  plugin_discovery.py
  plugin_registry.py
  adapters/base.py
```

说明：

- `models.py` 定义 P3 转换器运行对象。
- `converter_protocols.py` 定义转换器输入输出协议。
- `plugin_discovery.py` 发现转换器插件目录。
- `plugin_registry.py` 提供转换器列表、默认转换器和 ID 解析。
- `adapters/base.py` 加载本地 adapter。

### 6.2 转换器插件目录

首个插件建议放在：

```text
converters/p3/requirement-to-sdd-dify-workflow/
  manifest.json
  adapter.py
  workflow.json
  CONVERTER.md
```

`manifest.json` 至少声明：

| 字段 | 含义 |
| --- | --- |
| `converter_id` | 转换器唯一标识 |
| `name` | 展示名称 |
| `converter_type` | `dify_workflow` / `local_package` / `remote_service` |
| `document_type` | `software_design_description` |
| `protocol` | `p3-design-converter-protocol@1` |
| `status` | `active` / `available` |
| `priority` | 默认排序 |
| `capabilities` | 能力声明 |
| `adapter_module` | adapter 模块 |
| `adapter_class` | adapter 类名 |

### 6.3 `software_design_v2` 接入方式

`SoftwareDesignV2Service.run_conversion` 应从当前硬编码实现升级为：

```text
读取 P3 设计会话
  -> 校验输入包
  -> 选择转换器
  -> 构造 DesignConverterRunRequest
  -> 调用转换器 adapter
  -> 校验 DesignConverterRunResult
  -> 写入 design_document / design_baseline / conversion / check seeds
  -> 记录 runtime_events
```

API 入参建议从单一 `strategy` 扩展为：

| 字段 | 含义 |
| --- | --- |
| `converter_id` | 可选，默认使用首选转换器 |
| `strategy` | 转换策略 |
| `options` | 粒度、输出形态、是否生成 P4 候选 |

保留 `strategy` 是为了兼容现有页面和测试，但它不再直接决定硬编码生成逻辑，而是作为转换器选项传入。

### 6.4 错误处理

P3 转换器错误语义应保持明确：

| 场景 | 处理 |
| --- | --- |
| 未配置 Dify API Key | 返回配置错误，不生成伪结果 |
| Dify 网络失败 | 返回远端调用错误，保留请求摘要 |
| Dify 返回非 JSON | 返回结构错误 |
| Dify 输出缺字段 | 返回输出校验错误 |
| 输入包缺关键内容 | 返回设计缺口或阻断项 |
| 转换器不存在 | 返回不支持的转换器 |

## 7. 前端落地设计

### 7.1 转换页新增能力

`P3RequirementToDesignConversionView` 应显示：

- 当前输入包摘要。
- 可选转换器。
- 转换策略。
- 执行基础转换按钮。
- 转换步骤进度。
- Dify / 本地 / 远端来源标识。
- 草稿预览。
- 追溯摘要。
- 缺口和人工校核项。

### 7.2 页面状态

转换页至少覆盖：

| 状态 | 说明 |
| --- | --- |
| `conversion_pending` | 已创建会话，未执行转换 |
| `conversion_running` | 转换执行中 |
| `draft_ready` | 草稿已生成 |
| `conversion_failed` | 转换失败 |
| `check_pending` | 等待检查 |
| `review_pending` | 等待人工校核 |

### 7.3 交互规则

- 未执行转换前，软设工作区不可作为主要编辑入口。
- 转换失败时，页面必须展示失败原因、转换器来源和重试入口。
- 草稿生成后，用户可以进入软设工作区微调。
- 缺口清单必须在检查评审区可见。
- 转换器输出的 Dify trace 只作为过程摘要展示，不应暴露密钥、完整 Prompt 或内部敏感信息。

## 8. 验收口径

### 8.1 文档样例验收

以 `SX-DataStore` 两份范本作为首轮样例时，P3 转换器至少应满足：

1. 能识别三类角色上下文：消费者、生产者、管理者。
2. 能识别核心对象：资源对象、资源申请、审批任务、交付订单、资源实例、页面配置。
3. 能识别核心流程：资源发现与申请、维护发布、审批交付、治理接管、页面配置发布。
4. 能从功能需求生成产品能力模块和后端服务模块候选。
5. 能从数据与接口需求生成 API 分组候选。
6. 能从非功能需求生成安全、可靠性、可维护性、部署和测试约束。
7. 能生成软件设计说明目标章节，而不是复述需求章节。
8. 能输出追溯映射和设计缺口。

### 8.2 工程验收

首轮工程落地至少应满足：

- 转换器插件可被发现并列出。
- 无 Dify 配置时返回明确配置错误。
- mocked HTTP 测试能验证 Dify 成功、失败、超时和结构错误。
- `software_design_v2` 能通过转换器结果生成 `design_document` 和 `design_baseline`。
- 现有 P3 Design Lab 页面测试不回退。
- 现有 P2/P3 交换层测试不回退。

### 8.3 人工验收

人工验收重点不是“是否生成了很多字”，而是：

- 软设是否真的包含架构、模块、对象、API、流程、质量门。
- 主要设计章节是否能追溯到需规来源。
- 设计推导是否标注为推导，而不是伪装成需求原文。
- 缺口清单是否指出需求不足以支持设计的地方。
- 冻结动作是否仍需要人工确认。

## 9. 分阶段落地建议

### 9.1 第一阶段：本地协议与插件框架

目标：

- 固定 P3 转换器协议。
- 新增转换器发现和注册。
- 新增 Dify 型转换器插件目录。
- 用 mocked HTTP 测试验证 adapter。

不要求：

- 真实 Dify workflow 已经创建。
- 前端完成全部展示。
- 转换质量达到最终目标。

### 9.2 第二阶段：Dify workflow 搭建规范

目标：

- 编写 P3 Dify workflow 搭建规范。
- 明确输入变量、输出 JSON 和节点职责。
- 在 Dify 工作台创建并发布 workflow。

交付物：

- workflow 创建说明。
- workflow 输入输出样例。
- 已发布 workflow 标识。
- 不含密钥的运行配置说明。

### 9.3 第三阶段：真实联调

目标：

- 通过真实 Dify API 跑通一次 `SX-DataStore` 样例转换。
- 记录运行结果、失败原因和人工评审意见。
- 根据结果调整 Prompt、节点和输出校验。

### 9.4 第四阶段：主设计归并

目标：

- 用户确认本文方向后，把稳定结论归入 `P3-软件设计系统设计.md`。
- 同步更新 P3 节点说明、验收入口和机测记录。
