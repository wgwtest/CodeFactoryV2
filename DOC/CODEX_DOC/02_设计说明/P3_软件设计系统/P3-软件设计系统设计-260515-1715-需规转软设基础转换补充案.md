## 1. 本补充案目的

v6 主设计归并案已经把 `P3 Design Lab` 收敛为“需规输入、软设工作区、P4 投影、当前 Turn、检查评审、运行日志”的组合入口。但 v6 仍存在一个关键链路缺口：从“新建软设”到“进入软设工作区微调”之间缺少显式的基础转换步骤。

真实工作流应拆成两段：

```text
需规输入 / 关联软设管理
  -> 需规转软设基础转换
    -> 软设工作区微调
```

本文用于回答：

1. 新增“需规转软设”页面在主设计中是什么性质。
2. 它与现有六个业务模块如何解耦。
3. 新建软设后为什么不能直接进入软设工作区。
4. 基础转换页的前端 ViewModel、后端用例、对象模型、API 和运行流程应如何设计。
5. 哪些内容后续应归入主文档第 5、6、7、8、9、10 章。

## 2. 核心设计结论

### 2.1 新增页面的系统定位

`需规转软设` 是 `P3 Design Lab` 中的一个主任务视图，用于承接“新建软设后、软设微调前”的基础转换过程。它不是新的业务模块，不是新的事实源，也不是独立服务。

正式定位如下：

```text
需规转软设基础转换视图
  = 软件设计输入模块 + 软件设计会话与运算模块 + 软件设计基线模块 + 软件设计说明编写模块的组合用例视图
```

它的唯一目标是把已选 `P2` 冻结需求规格说明转化为可进入软设工作区的初始软件设计草稿，包括：

- 输入侧：读取已选需规冻结包和输入快照。
- 策略侧：选择基础转换策略。
- 过程侧：展示基础转换进度。
- 输出侧：生成软件设计说明草稿、结构化设计事实初稿和追溯关系。

### 2.2 新导航链路

`P3 Design Lab` 左侧导航应从 v6 的六个主视图升级为七个主视图：

```text
需规输入
  -> 需规转软设
    -> 软设工作区
      -> P4 投影
        -> 当前 Turn
          -> 检查评审
            -> 运行日志
```

该顺序表达默认工作链路，不代表所有视图都必须线性执行。但在“新建软设”场景下，系统必须先进入 `需规转软设`，完成基础转换后，才能进入 `软设工作区` 做章节扩写、结构化修订和交互式微调。

### 2.3 与 v6 设计的关系

v7 不推翻 v6 的主体设计。v7 只修正 v6 的一个关键流程缺口：

| v6 口径 | v7 修正 |
| --- | --- |
| 需规输入页可以新建软设，随后进入软设工作区 | 新建软设后先进入需规转软设基础转换页 |
| 软设工作区默认看到已有软设草稿 | 软设草稿必须来自基础转换或既有历史版本 |
| 当前 Turn 可解释软设变化过程 | 基础转换本身也必须记录为系统触发的初始转换运行 |
| 软设工作区负责文档 / 结构化双视图微调 | 保持不变，但不承担初始基础转换页面职责 |

## 3. 设计原则

### 3.1 页面不是事实源

`需规转软设` 页面只展示和触发基础转换，不保存权威业务事实。权威事实仍归属：

- 需规来源与输入快照：软件设计输入模块。
- 转换运行与回合记录：软件设计会话与运算模块。
- 结构化设计事实：软件设计基线模块。
- 软件设计说明草稿：软件设计说明编写模块。
- 投影候选：设计投影与交换模块。

页面不得在前端通过解析需规正文自行生成正式模块、接口、数据对象或正文草稿。

### 3.2 生成草稿和微调草稿分离

基础转换页回答：

```text
这条需规如何被初始转换成一份软设草稿？
```

软设工作区回答：

```text
这份软设草稿如何继续扩写、修订、复核和提交？
```

因此：

- 基础转换页允许选择策略、执行转换、查看进度、预览初稿。
- 基础转换页不提供章节扩写、保存草稿、提交复核、冻结、发布、正式 P4 推送。
- 软设工作区不再显示“生成草稿”作为主动作；它只处理已转换后的微调。

### 3.3 转换过程是进度信息，不是按钮组

v7 原型确认的视觉原则需要进入主设计约束：

- 转换策略应表现为闭合下拉框，而不是展开菜单或多卡片选项。
- `执行基础转换` 应为普通主按钮，不应使用大箭头、大横幅或夸张容器。
- `1-4` 转换过程应表现为圆点加箭头的进度轨道。
- 每个步骤的文字是进度说明，不是可点击按钮，因此不应包裹成强边框卡片。

这些约束不属于像素级要求，但属于交互语义要求。后续实现可调整样式，但不能把进度信息重新做成一组按钮。

### 3.4 基础转换不等于发布和投影

基础转换完成后，系统最多生成：

- 软件设计说明草稿。
- `SoftwareDesignBaseline v2` 初稿。
- 需规条款到软设章节 / 设计对象的追溯关系。
- 可用于后续投影的候选信息。

基础转换不得直接：

- 发布软件设计说明。
- 冻结设计基线。
- 生成正式 P4 工单推送。
- 产生评审通过结论。

## 4. 前端软件设计补充

### 4.1 视图组件归属

建议新增前端视图组件：

```text
P3RequirementToDesignConversionView
```

它归属于 `P3DesignLabPage` 的任务视图之一，通过 `p3DesignLabWorkbenchAdapter` 读取后端 DTO 后组装展示模型。

组件结构建议：

```text
P3RequirementToDesignConversionView
  -> RequirementSpecA4Preview
  -> ConversionControlPanel
    -> ConversionStrategySelect
    -> RunConversionButton
    -> ConversionProgressTimeline
    -> EnterDesignWorkspaceAction
  -> SoftwareDesignDraftPreview
  -> ConversionTraceabilitySummary
```

其中：

- `RequirementSpecA4Preview` 展示当前需规冻结包正文摘要，不提供编辑。
- `ConversionStrategySelect` 展示闭合下拉框，当前选中一种转换策略。
- `RunConversionButton` 触发基础转换。
- `ConversionProgressTimeline` 展示四个进度节点。
- `SoftwareDesignDraftPreview` 展示转换后的 A4 软件设计说明草稿预览。
- `ConversionTraceabilitySummary` 展示追溯关系摘要，不提供完整映射编辑。

### 4.2 左侧导航补充

主文档 `5.5.4 左侧 Lab 导航` 应补充一项：

| 导航项 | 视图组件 | 说明 | 可用条件 |
| --- | --- | --- | --- |
| 需规转软设 | `P3RequirementToDesignConversionView` | 新建软设后执行基础转换，左侧需规、右侧软设草稿、中间策略和转换进度 | 已选中需规且存在待转换或转换中的软设对象 |

导航规则：

- 未选中需规时，该视图显示空态或禁用原因。
- 已选中需规但未新建软设时，该视图提示先在需规输入页新建软设。
- 新建软设后，该视图成为默认下一步。
- 已完成基础转换的软设再次打开时，可以直接进入软设工作区；如需查看转换记录，可从当前 Turn 或运行日志回溯。

### 4.3 转换页布局

转换页采用三栏结构：

```text
左侧：已选需规 A4 预览
中间：转换策略 + 执行按钮 + 转换进度
右侧：软设草稿 A4 预览 + 追溯摘要
```

左侧只读，用于确认输入来源。右侧只读或弱交互，用于预览基础转换结果。真正的正文微调必须进入软设工作区。

中间栏的对象语义如下：

| 区块 | 语义 | 允许动作 |
| --- | --- | --- |
| 转换策略下拉 | 选择基础转换策略 | 切换当前策略 |
| 执行基础转换按钮 | 启动或重新执行基础转换 | 执行、重试 |
| 转换进度轨道 | 展示转换运行状态 | 不作为按钮 |
| 进入软设工作区微调 | 转换完成后的下一步 | 打开软设工作区 |

### 4.4 转换策略

转换策略不是页面装饰字段，而是后端转换用例的输入参数。首版建议提供三类策略：

| 策略值 | 展示名 | 用途 |
| --- | --- | --- |
| `standard_sdd_draft` | 标准软设草稿生成 | 默认策略，按标准软设章节生成初稿 |
| `component_first` | 组件优先拆解 | 适合平台、前端、共性组件抽象优先的需求 |
| `p4_projection_first` | P4 投影优先 | 适合先明确下游工具包和模块工单的需求 |

静态原型只展示闭合下拉框，真实实现可以在用户点击后展开选项。未执行转换前允许切换策略；转换运行中应锁定策略；转换完成后如切换策略，应进入重新转换或另存设计分支流程。

### 4.5 转换进度节点

首版基础转换固定为四个可审计步骤：

| 序号 | 步骤 | 所属后端能力 | 主要输出 |
| --- | --- | --- | --- |
| 1 | 读取需规冻结包 | 软件设计输入模块 | 输入快照、正文、结构化条款、审批结论 |
| 2 | 抽取设计对象 | 软件设计会话与运算模块 | 模块候选、接口候选、数据对象候选、质量属性 |
| 3 | 生成软设草稿 | 软件设计说明编写模块、设计基线模块 | A4 正文草稿、`SoftwareDesignBaseline v2` 初稿 |
| 4 | 建立追溯映射 | 软件设计基线模块 | 需规条款到章节、模块、接口和 P4 候选的映射 |

每个节点至少有以下状态：

- `pending`：未开始。
- `running`：执行中。
- `succeeded`：完成。
- `failed`：失败。
- `skipped`：因策略或输入不适用而跳过。

流程节点展示进度，不承担直接编辑或执行动作。失败时可以在节点旁展示错误摘要，但重试动作仍应放在转换控制区，不放在每个节点卡片内。

### 4.6 页面动作收敛

转换页允许的动作：

- 选择转换策略。
- 执行基础转换。
- 重新执行基础转换。
- 查看输入需规。
- 查看软设草稿预览。
- 进入软设工作区微调。

转换页不允许的动作：

- 保存正文草稿。
- 扩写章节。
- 提交复核。
- 冻结。
- 发布。
- 推送 P4。
- 删除软设。
- 编辑需规正文。

## 5. 后端软件设计补充

### 5.1 模块协作关系

`需规转软设` 用例横跨多个模块，但不新增后端模块。建议后端按以下职责分摊：

| 模块 | 职责 |
| --- | --- |
| 软件设计输入模块 | 读取需规冻结包、建立输入快照、提供设计上下文 |
| 软件设计说明编写模块 | 创建软设壳对象、渲染 A4 正文草稿 |
| 软件设计会话与运算模块 | 管理转换运行、调用设计组织器、记录系统触发回合 |
| 软件设计基线模块 | 归并模块、接口、数据、质量属性和追溯矩阵 |
| 设计投影与交换模块 | 只生成投影候选摘要，不做正式推送 |
| 运行日志能力 | 记录 API、策略、步骤、模型调用和错误 |

### 5.2 新建软设后的状态

新建软设不应直接生成完整可微调草稿。建议将软设生命周期拆成以下早期状态：

| 状态 | 含义 | 默认页面 |
| --- | --- | --- |
| `conversion_pending` | 软设壳对象已创建，尚未执行基础转换 | 需规转软设 |
| `conversion_running` | 基础转换执行中 | 需规转软设 |
| `conversion_failed` | 基础转换失败，可查看错误并重试 | 需规转软设 |
| `draft_ready` | 基础转换完成，草稿可进入微调 | 软设工作区 |
| `drafting` | 正在进行章节微调或结构化修订 | 软设工作区 |

已冻结、已发布或历史软设仍按既有状态处理，不必重新进入转换页，除非用户明确发起“以当前需规重新转换生成新分支”。

### 5.3 基础转换运行

建议新增领域概念：

```text
RequirementToDesignConversionRun
```

它不是独立业务主对象，而是 `SoftwareDesignTurn` 或 `SoftwareDesignSession` 下的系统触发运行记录。它用于解释初始软设草稿如何出现。

运行记录至少包含：

- `conversion_run_id`
- `software_design_id`
- `requirement_spec_id`
- `input_snapshot_id`
- `strategy`
- `status`
- `steps[]`
- `started_at`
- `finished_at`
- `error_summary`
- `generated_baseline_id`
- `generated_document_id`
- `traceability_summary`
- `runtime_event_refs`

`steps[]` 至少包含：

- `step_key`
- `step_index`
- `title`
- `status`
- `started_at`
- `finished_at`
- `summary`
- `error_message`
- `output_refs`

### 5.4 与设计轮次的关系

基础转换应记录为系统触发的初始设计轮次，避免软设草稿来源不可追踪。建议规则：

```text
新建软设
  -> 创建 SoftwareDesignSession
    -> 创建 RequirementToDesignConversionRun
      -> 创建 SoftwareDesignTurn(trigger=initial_conversion)
        -> 写入 baseline/document/traceability
```

转换运行和设计轮次的关系：

- `RequirementToDesignConversionRun` 面向页面展示转换进度。
- `SoftwareDesignTurn` 面向设计审计、模型调用和后续回合列表。
- 二者可以共享同一个 `turn_id`，也可以通过 `conversion_run_id -> turn_id` 建立引用。
- 不能只记录运行日志而不记录设计轮次。

### 5.5 失败与重试

基础转换可能失败。失败不应创建半成品正式草稿，也不应直接进入软设工作区。

失败规则：

- 第 1 步失败：输入包不可用，软设状态回到 `conversion_failed`，提示重新刷新需规或重新建快照。
- 第 2 步失败：设计对象抽取失败，可更换策略后重试。
- 第 3 步失败：正文或基线初稿生成失败，不允许进入软设工作区。
- 第 4 步失败：允许展示草稿预览，但进入软设工作区前必须标记追溯不完整，不能提交复核。

重试规则：

- 重试必须生成新的 `conversion_run_id`。
- 上一次失败运行保留为历史审计。
- 如果切换策略后重试，应记录策略变化。
- 已进入 `drafting` 后重新转换，应创建新软设分支或明确覆盖策略，不能静默覆盖当前草稿。

## 7. API 设计补充

### 7.1 转换工作区 API

建议补充以下目标态 API，仍放在 `/api/software-design-v2` 前缀下：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/software-designs/{software_design_id}/conversion` | 读取需规转软设基础转换工作区 |
| `POST` | `/software-designs/{software_design_id}/conversion-runs` | 按选定策略执行基础转换 |
| `GET` | `/software-designs/{software_design_id}/conversion-runs/{conversion_run_id}` | 查询转换运行详情 |
| `GET` | `/software-designs/{software_design_id}/conversion-strategies` | 读取可选转换策略 |

### 7.2 既有 API 语义修正

既有 `POST /requirement-specs/{requirement_spec_id}/software-designs` 需要明确语义：

```text
为当前需规创建一份软件设计对象和设计会话，并进入 conversion_pending；
不直接返回可微调的完整软件设计说明。
```

返回值至少应包含：

- `software_design_id`
- `requirement_spec_id`
- `status=conversion_pending`
- `conversion_workspace_url` 或前端可识别的下一步视图标识。

既有 `GET /software-designs/{software_design_id}/workspace` 需要明确前置条件：

- 当 `conversion_status` 未完成时，不返回完整软设工作区；应返回阻断原因或引导前端进入转换页。
- 当 `conversion_status=draft_ready` 或后续状态时，返回文档视图和结构化数据视图所需聚合 DTO。

### 7.3 DTO 到 ViewModel 映射补充

`p3DesignLabWorkbenchAdapter` 应补充以下映射：

| 后端 DTO | 前端 ViewModel |
| --- | --- |
| `RequirementToDesignConversionWorkspaceDTO` | `RequirementToDesignConversionViewModel` |
| `ConversionStrategyDTO[]` | `strategyOptions[]` |
| `RequirementToDesignConversionRunDTO` | `conversionRun`、`steps[]` |

Adapter 只做字段映射和展示状态转换，不在前端本地执行需规到软设的业务推导。

## 8. 关键运行流程补充

### 8.1 从需规列表进入基础转换

主文档 `9.1 从需规列表进入软设工作区` 应调整为：

```text
用户进入 P3 Design Lab
  -> 前端读取可消费需规列表
    -> 用户选择一条需规
      -> 前端读取需规详情和关联软设列表
        -> 用户打开既有已转换软设
          -> 进入软设工作区
        -> 用户新建软设或打开待转换软设
          -> 进入需规转软设基础转换视图
```

规则：

- 选择需规不等于创建软设。
- 新建软设不等于生成完整软设草稿。
- 待转换、转换中、转换失败的软设默认进入转换页。
- 已完成基础转换的软设才默认进入软设工作区。

### 8.2 执行基础转换

```text
用户选择转换策略
  -> 点击执行基础转换
    -> 后端锁定当前策略和输入快照
      -> 步骤 1：读取需规冻结包
      -> 步骤 2：抽取设计对象
      -> 步骤 3：生成软设草稿
      -> 步骤 4：建立追溯映射
        -> 写入设计轮次、基线初稿、正文草稿和运行日志
          -> 返回草稿预览和转换状态
```

执行完成后：

- 状态变更为 `draft_ready`。
- 显示 `进入软设工作区微调`。
- 当前 Turn 列表中出现系统触发的初始转换回合。
- 运行日志记录策略、步骤、耗时、调用和错误摘要。

### 8.3 进入软设工作区微调

```text
基础转换完成
  -> 用户进入软设工作区
    -> 文档视图显示 A4 软件设计说明草稿
    -> 结构化数据视图显示 SoftwareDesignBaseline v2 初稿
      -> 用户通过章节交互或 CLI 微调
        -> 形成后续 SoftwareDesignTurn
```

软设工作区不重新执行基础转换。若用户认为初始转换策略不合适，应新建软设分支或执行明确的重新转换命令。

### 8.4 转换失败处理

```text
基础转换失败
  -> 页面停留在需规转软设视图
    -> 显示失败步骤、错误摘要和可重试策略
      -> 用户调整策略或重试
        -> 生成新的 conversion_run
```

失败状态下不允许提交复核、冻结或推送 P4。若已生成部分草稿，也只能作为错误排查预览，不能作为正式工作区草稿。

## 9. 设计组织器补充

### 9.1 初始转换组织器阶段

设计组织器需要增加或明确一组初始转换阶段：

| 阶段 | 输入 | 输出 |
| --- | --- | --- |
| `read_requirement_package` | 需规冻结包、输入快照 | 标准正文、结构化条款、来源追溯 |
| `extract_design_objects` | 标准正文、结构化条款、转换策略 | 模块候选、接口候选、数据对象、质量属性 |
| `draft_software_design` | 设计对象候选、软设模板 | 软件设计说明草稿、基线初稿 |
| `build_traceability` | 需规条款、设计章节、设计对象 | 追溯矩阵、覆盖摘要、缺失项 |

这些阶段可以在一次模型调用中完成，也可以分多次调用完成；设计上必须保留阶段边界，便于日志、重试和质量检查。

### 9.2 策略对提示词的影响

转换策略应影响组织器提示词和输出结构：

- `standard_sdd_draft`：优先完整生成标准软件设计说明章节。
- `component_first`：优先抽取可复用组件、前端/平台适配边界和共性工作台对象。
- `p4_projection_first`：优先抽取模块工单候选、工具包分支和投影所需字段。

策略不是 UI 文案，必须进入后端运行上下文和模型调用日志。

## 12. 设计结论

v7 原型补齐了 `P3` 主链路中最关键的中间阶段：

```text
需规输入
  -> 需规转软设基础转换
    -> 软设工作区微调
      -> P4 投影 / 当前 Turn / 检查评审 / 运行日志
```

这一阶段的正式设计结论是：

```text
新建软设不等于进入软设微调；
新建软设只建立软设壳、设计会话和转换上下文；
基础转换负责把 P2 冻结需规转成软件设计说明草稿、结构化设计事实初稿和追溯关系；
软设工作区只处理转换后的文档微调和结构化复核。
```

后续代码实现必须以该分段为前提，避免再次把“生成初稿”和“微调初稿”混在同一个页面或同一个按钮语义中。
