## 1. 背景与问题判断

当前 `P3 Design Lab` 已经把 `需规文档`、`软设文档`、`功能树`、`分层架构`、`技术实现`、`展示形态` 和 `P4 投影` 放入同一个 Canvas 软设工作区。`需规文档` 和 `软设文档` 已经升级为接近真实工作的 A4 文档对象，支持正文展示、内部滚动、结构化章节、块级选择和右侧 `Inspector` 联动。

但当前 `功能树` 仍停留在示意层：

1. `functionTree` 阶段只从 `SoftwareDesignBaseline.modules` 抽取模块名，数据形态是 `items: string[]`。
2. Canvas 的 `tree` 渲染器只画最多 5 行静态分支，没有节点 ID、父子关系、展开状态、选择事件或拖拽事件。
3. `功能树` 与 `需规文档`、`软设文档`、`分层架构` 之间缺少可点击、可追溯、可调整的中间设计对象。
4. 当前功能树无法承载后续“按节点生成子功能、拆分功能、合并功能、追溯来源、投影到架构层”的设计工作。

因此，本补充案判断：`功能树` 不应继续作为 Canvas 上的摘要画片，而应升级为与 A4 文档对象同级的可交互阶段对象。

## 2. 设计目标

本轮功能树深化的目标是：

1. 把 `功能树` 从静态字符串列表升级为具有节点 ID、层级、类型、状态和追溯信息的树形对象。
2. 在软设工作区中使用成熟树组件展示功能树，支持展开、收起、选择和必要搜索。
3. 首版支持前端拖拽重排事件，但默认以“待应用调整”记录，不直接改写冻结前设计基线。
4. 功能树节点选中后必须联动右侧 `Inspector`，展示节点详情、追溯来源、设计引用和可执行动作。
5. 功能树必须能与 `软设文档` 和 `分层架构` 建立连续关系：从软设章节抽取功能对象，再把功能对象投影到架构层。
6. 首版不强制等待 Dify 输出完整功能树；如果 Dify 尚未提供结构化功能树，前端可从现有设计基线和追溯关系派生基础树。
7. 后续 Dify 或自研转换器输出 `functional_tree_projection` 后，系统应优先消费真实结构化功能树，派生树只作为降级方案。

## 3. 非目标

本补充案不解决以下问题：

1. 不在首版实现完整功能建模编辑器。
2. 不在首版直接修改后端设计基线存储结构，除非后续实现阶段另行确认。
3. 不把功能树拖拽结果自动写入冻结产物。
4. 不把 `功能树` 做成独立于 `SoftwareDesignPackage` 的新事实源。
5. 不在首版引入复杂图布局引擎替代现有 Canvas 工作区。
6. 不要求 Dify 立即生成权威功能树；Dify 输出规范可作为第二阶段任务推进。

## 4. 组件选型结论

### 4.1 推荐首选：Ant Design Tree

首版建议使用 `antd` 的 `Tree` 作为功能树内部组件。

原因：

- 当前前端已经使用 `antd`，新增依赖成本最低。
- `P4DemandSheetTree` 已经使用 `antd Tree` 表达下游工单树，有本地先例。
- `Tree` 支持展开、收起、选中、拖拽、`onDrop`、`titleRender`、受控 `expandedKeys`、受控 `selectedKeys` 和虚拟滚动。
- 功能树属于“层级结构 + 节点元数据 + 操作入口”，不需要首版进入自由图布局。
- 它可以稳定嵌入现有 Canvas 的 HTML/React 对象覆盖层，不需要重写主 Canvas。

### 4.2 暂不首选：React Flow

`react-flow-renderer` 适合自由节点图、流程图和拓扑关系。它可用于后续 `分层架构` 或复杂依赖图，但不建议作为第一版功能树组件。

原因：

- 当前外层已经是 Canvas 工作区，内部再嵌一个可拖拽缩放的 React Flow，容易产生滚轮、拖拽、选中和缩放事件冲突。
- React Flow 的树自动布局需要额外布局算法，例如 dagre 或 d3-hierarchy。
- 第一版目标是把功能树做成可审阅、可展开、可追溯的层级对象，不是自由编排图。

### 4.3 暂不首选：Cytoscape.js

`cytoscape` 适合复杂网络图、图算法和关系分析。它不适合作为第一版功能树内部组件。

原因：

- 功能树首版主要是层级浏览和结构调整，不需要图数据库式网络分析。
- Cytoscape 的交互和样式成本高于 `antd Tree`。
- 若未来需要展示“需求-功能-模块-接口-P4 工单”的多源关系网，可在独立图谱视图中评估 Cytoscape，而不是替代功能树。

## 5. 目标信息架构

功能树在 `P3 Design Lab` 中承担中间形态职责：

```text
软设文档
  -> 功能树
    -> 分层架构
      -> 技术实现
        -> 展示形态
          -> P4 投影
```

功能树不是需求树的复制，也不是模块列表的平铺。它应该表达：

1. 软件系统的功能域。
2. 每个功能域下的能力项。
3. 能力项下的功能点、接口点、数据对象或质量约束。
4. 每个节点来自哪些需规条款和软设章节。
5. 每个节点后续落到哪些架构层、模块或 P4 工单。

首版建议树层级为：

```text
系统根节点
  -> 模块 / 功能域
    -> 能力组
      -> 功能项
        -> 接口 / 数据 / 状态 / 质量约束
```

如果当前数据不足，首版可退化为：

```text
系统根节点
  -> 设计模块
    -> 来源需规条款
    -> 关联软设章节
```

该退化结构必须在右侧 `Inspector` 中标识为“由当前设计基线派生”，不能伪装成转换器生成的完整功能树。功能树主体不显示该状态说明。

## 6. 数据模型设计

### 6.1 前端视图模型

建议在前端新增 `FunctionTreeViewModel`：

```ts
type FunctionTreeViewModel = {
  treeId: string;
  title: string;
  origin: "converter" | "derived" | "empty";
  summary: {
    nodeCount: number;
    tracedNodeCount: number;
    pendingNodeCount: number;
    maxDepth: number;
  };
  root: FunctionTreeNodeViewModel | null;
};

type FunctionTreeNodeViewModel = {
  nodeId: string;
  title: string;
  nodeType: FunctionTreeNodeType;
  status: "generated" | "derived" | "pending_confirmation" | "changed" | "untraced" | string;
  moduleId?: string;
  sourceRefs: string[];
  designRefs: string[];
  architectureRefs: string[];
  p4Refs: string[];
  description?: string;
  children: FunctionTreeNodeViewModel[];
};

type FunctionTreeNodeType =
  | "root"
  | "module"
  | "capability"
  | "function"
  | "interface"
  | "data"
  | "state"
  | "quality"
  | "trace";
```

该模型是 `P3 Design Lab` 的前端展示模型，不直接等同后端事实源。

### 6.2 数据来源优先级

功能树数据按以下优先级构建：

1. `design_baseline.function_tree` 或 `design_package.functional_tree_projection`：转换器输出的真实结构化功能树。
2. `design_baseline.modules + traceability + design_document.sections`：从现有设计基线派生的基础功能树。
3. `design_document.sections`：只有软设正文时，从章节标题派生临时功能树。
4. 空状态：没有软设文档或设计基线时显示待生成状态。

首版实现如果后端尚未暴露 `function_tree` 字段，应采用第 2 或第 3 条路径，不阻塞功能树交互框架。

### 6.3 与后端结构的后续对齐

后续建议在 `P3DesignLabDesignBaseline` 中补充：

```ts
type P3DesignLabDesignBaseline = {
  baseline_id: string;
  application_name?: string;
  architecture_mode: string;
  modules: Array<{ module_id: string; name: string; source_refs?: string[] }>;
  function_tree?: FunctionTreeSnapshot;
  traceability?: Array<Record<string, string>>;
  pending_confirmations?: string[];
};
```

其中 `FunctionTreeSnapshot` 由转换器或人工调整流程产生，并在设计冻结前纳入完整性检查。

## 7. 前端组件设计

### 7.1 `FunctionTreeStageObject`

新增 `FunctionTreeStageObject`，作为 Canvas 中 `functionTree` 阶段对象的真实 HTML/React 渲染器。

职责：

- 接收 `FunctionTreeViewModel`。
- 渲染搜索、展开控制和树主体。
- 管理 `expandedKeys`、`selectedKeys`、`searchKeyword` 等 UI 状态。
- 把节点选择、拖拽、操作按钮事件上抛给 `DesignMorphCanvasPlatform` 或 P3 页面容器。
- 不直接调用后端 API。
- 不直接修改 `SoftwareDesignBaseline`。

### 7.2 与 `DocumentStageObject` 的关系

`FunctionTreeStageObject` 与当前 `DocumentStageObject` 同级，都是 Canvas 对象覆盖层中的阶段对象渲染器。

建议演进为：

```text
DesignMorphCanvasPlatform
  -> StageObjectOverlayLayer
    -> DocumentStageObject
    -> FunctionTreeStageObject
    -> ProjectionTreeStageObject
    -> ...
```

短期可先在 `DesignMorphCanvasPlatform` 内按 `item.entityType === "software_function_tree"` 分支渲染，避免一次性抽象过大。后续再把阶段对象外壳提取为 `StageObjectFrame`。

### 7.3 树主体显示边界

功能树主体只承载核心树结构，原则是“越精简、越直观越好”。

功能树主体允许显示：

- 展开 / 收起控制。
- 节点标题。
- 当前选中状态。
- 必要的层级缩进和父子连线。
- 必要的搜索入口。

功能树主体不显示：

- 功能节点总数。
- 已追溯数量。
- 待确认数量。
- 最大层级。
- 派生 / 转换器来源说明。
- 节点追溯数。
- 节点状态标签。
- 节点待确认标签。
- 拖拽待应用摘要。
- 多个节点级操作按钮。

这些信息统一放入右侧 `Inspector`。原因是：功能树本体是轻交互结构视图，过多统计和状态会干扰树结构阅读，也会使拖拽、展开、节点编辑的交互命中区变复杂。

### 7.4 树节点标题渲染

每个节点标题建议包含：

```text
[展开控件] 节点标题
```

节点示例：

```text
▾ 规划任务管理
  ▾ 任务创建与草稿保存
    · 保存规划草案接口
    · 任务版本记录
  ▸ 任务发布校核
```

节点标题必须控制高度，避免长文本撑坏 Canvas 对象。长标题采用单行省略，完整说明、节点类型、来源、追溯数量和状态放入右侧 `Inspector`。

### 7.5 工具区

功能树对象内部顶部保留一行紧凑工具区：

- 搜索框：按标题、节点 ID、来源条款过滤。
- 展开全部。
- 收起全部。
- 重置视图。

筛选类入口，如“只看未追溯”“只看待确认”“只看当前子树”，首版放入右侧 `Inspector`，不放在树主体工具区。工具区不能变成大面积说明区。说明文字、规则解释、来源详情和副编辑入口放入右侧 `Inspector`。

## 8. 交互设计

### 8.1 展开与收起

展开状态由前端受控保存。用户离开功能树窗口再回来，应保留当前会话内的展开状态。

默认展开策略：

- 有转换器真实功能树时：展开到第 2 层。
- 派生功能树时：展开模块层。
- 节点数量少于 12 个时：默认展开全部。

### 8.2 节点选择

点击节点后：

1. 树中高亮该节点。
2. 右侧 `Inspector` 切换为 `function_node` 详情。
3. 显示节点标题、类型、状态、来源需规、关联软设章节、关联模块、统计信息和可执行动作。
4. 如果节点有 `designRefs`，允许定位到软设文档对应章节或块。
5. 如果节点有 `sourceRefs`，允许定位到需规文档对应条款。

### 8.3 拖拽调整

首版启用 `Tree` 的 `draggable`，但拖拽结果不直接写入后端。

拖拽后形成前端事件：

```ts
type FunctionTreeDropEvent = {
  treeId: string;
  dragNodeId: string;
  targetNodeId: string;
  position: "before" | "inside" | "after";
  previousParentId?: string;
  nextParentId?: string;
};
```

事件处理策略：

1. 树主体只保留被拖拽节点的轻量视觉提示。
2. 右侧 `Inspector` 显示“待应用调整”状态和调整摘要。
3. 用户确认后，后续可进入设计轮次或转换器补写流程。
4. 若未确认，刷新会话后不保留该调整。

这样既满足可拖拽试排，又避免前端直接改写设计事实源。

### 8.4 节点动作

每个节点可暴露动作清单：

| 动作 | 首版状态 | 说明 |
| --- | --- | --- |
| 查看来源需规 | 首版支持 | 定位或展示 `sourceRefs` |
| 查看软设章节 | 首版支持 | 定位或展示 `designRefs` |
| 只看子树 | 首版支持 | 放在 `Inspector` 中触发，过滤当前节点子树 |
| 只看未追溯 / 待确认 | 首版支持 | 放在 `Inspector` 中触发，不占用树主体工具区 |
| 标记待确认 | 首版可先记录 UI 状态 | 放在 `Inspector` 中触发，后续接设计轮次 |
| 生成子功能 | 后续支持 | 接 Dify 或自研转换器 |
| 拆分节点 | 后续支持 | 进入人工确认流程 |
| 合并节点 | 后续支持 | 需要多选能力 |
| 投影到架构层 | 后续支持 | 关联 `分层架构` 阶段对象 |

### 8.5 与 Canvas 拖拽的事件边界

功能树内部有滚动、展开、拖拽和点击事件。必须明确事件边界：

- 对象标题条拖拽：移动整个功能树对象。
- 对象右下角把手：缩放整个功能树对象。
- 树主体滚轮：滚动树内容。
- 树节点拖拽：调整树节点。
- 树主体空白处拖拽：不移动 Canvas。
- Canvas 空白区域拖拽：移动 Canvas 视口。

必要时在树主体事件中使用 `stopPropagation`，避免内部拖拽误触发 Canvas 拖拽。

## 9. 右侧 Inspector 设计

选中功能树节点时，`Inspector` 应显示：

1. 节点标题。
2. 节点类型。
3. 节点状态。
4. 节点说明。
5. 来源需规条款列表。
6. 关联软设章节或块。
7. 所属模块。
8. 子节点数量。
9. 待确认问题。
10. 功能节点总数、已追溯数、待确认数、最大层级等统计。
11. 可执行动作。

示例：

```text
对象：规划任务管理
类型：模块
状态：派生
来源：REQ-3.2、REQ-4.1
软设引用：4.2 模块划分、5.1 规划任务服务
统计：18 个功能节点 / 14 个已追溯 / 3 个待确认 / 最大 4 层
动作：查看来源需规 / 查看软设章节 / 只看子树 / 标记待确认
```

`Inspector` 不直接展示整棵树，避免与左侧对象内容重复。它负责解释当前选中节点和承接动作。

## 10. 与转换器和 Dify 的关系

### 10.1 首版不阻塞 Dify

当前 Dify 工作流已经负责生成软件设计说明、结构化章节、图块、模块和追溯信息。功能树深化首版不要求 Dify 立即输出完整 `functional_tree_projection`。

首版功能树可以从现有字段派生：

- `design_baseline.modules`
- `design_baseline.traceability`
- `design_document.sections`
- `workorder_projection.items`

这样可以先验证工作区交互模型。

### 10.2 后续 Dify 输出增强

第二阶段再要求 Dify 输出：

```json
{
  "functional_tree_projection": {
    "tree_id": "function-tree-main",
    "title": "软件功能树",
    "root": {
      "node_id": "root",
      "title": "系统功能",
      "node_type": "root",
      "children": []
    }
  }
}
```

每个节点至少包含：

- `node_id`
- `title`
- `node_type`
- `description`
- `source_refs`
- `design_refs`
- `module_id`
- `status`
- `children`

P3 后端 adapter 应把 Dify 输出归一化为 `FunctionTreeSnapshot`。前端不直接消费 Dify 原始 JSON。

### 10.3 质量约束

转换器输出功能树后，检查规则应补充：

1. 根节点必须存在。
2. 节点 ID 不允许重复。
3. 除根节点外，主要功能节点应至少有一个来源或设计引用。
4. 模块节点应能映射到 `design_baseline.modules`。
5. 待确认节点不能静默进入冻结状态。
6. 功能树与 P4 投影之间的断链需要进入检查结果。

## 11. 实施切片

### 11.1 第一切片：前端功能树对象化

目标：不改后端，不改 Dify，先把 `功能树` 框从示意图升级为可交互树对象。

范围：

- 新增 `FunctionTreeViewModel`。
- 新增 `buildP3FunctionTreeViewModel(workbench)`。
- 新增 `FunctionTreeStageObject`。
- `DesignMorphCanvasPlatform` 对 `software_function_tree` 使用真实 DOM 树对象渲染。
- 支持展开、收起、搜索、选择、右侧 `Inspector` 联动。
- 支持拖拽事件记录，但不持久化。
- 功能树主体不显示统计、追溯数、待确认数、派生状态和待应用摘要，这些信息放入 `Inspector`。

验收：

- 功能树对象中能看到至少两级树结构。
- 节点可展开、收起。
- 节点可选中，右侧显示详情。
- 节点拖拽不会移动整个 Canvas 对象。
- 标题条拖拽仍能移动整个对象。
- 功能树在 `软设文档 -> 功能树` 和 `功能树 -> 分层架构` 两个滑窗中都能正常展示。

### 11.2 第二切片：功能树与软设/需规定位联动

目标：让功能树节点真正成为追溯中间对象。

范围：

- 节点选择后支持查看来源需规。
- 节点选择后支持查看软设章节或块。
- `Inspector` 展示来源和设计引用。
- 支持“只看当前子树”。
- 支持“只看未追溯 / 待确认”。

验收：

- 选中模块节点能看到来源需规条款。
- 选中功能节点能看到关联软设章节。
- 未追溯节点在 `Inspector` 中有明显状态。
- 筛选不会破坏树层级上下文。

### 11.3 第三切片：后端结构化功能树

目标：把功能树从前端派生对象升级为设计基线的一部分。

范围：

- 后端 `P3DesignLabDesignBaseline` 增加 `function_tree`。
- 转换器 adapter 支持读取 `functional_tree_projection`。
- 检查规则覆盖功能树结构完整性。
- 保存草稿和冻结包包含功能树快照。

验收：

- Dify 返回功能树时优先使用 Dify 结构。
- Dify 未返回功能树时使用派生结构并明确标识。
- 冻结包中可找到功能树快照。

### 11.4 第四切片：功能树编辑闭环

目标：支持功能树调整进入设计轮次，而不是只做 UI 临时试排。

范围：

- 拖拽、拆分、合并、标记待确认形成设计调整命令。
- 命令进入设计轮次审计。
- 设计人员确认后更新 `function_tree`。
- 必要时触发软设章节补写或架构投影刷新。

验收：

- 用户调整树结构后能看到待应用摘要。
- 用户确认后生成可审计设计轮次。
- 调整结果能刷新功能树和相关追溯。

## 12. 测试与验收口径

### 12.1 单元测试

需要覆盖：

- 从 `modules + traceability + sections` 派生功能树。
- 空数据返回空状态。
- 节点 ID 稳定。
- 节点统计正确。
- Dify 结构化功能树优先级高于派生树。

### 12.2 前端组件测试

需要覆盖：

- 功能树渲染根节点和模块节点。
- 展开、收起按钮改变可见节点。
- 搜索过滤节点。
- 点击节点触发 `function_node` 选择。
- 拖拽节点触发 `onDropFunctionNode`。
- 树主体拖拽不触发 Canvas 对象移动。

### 12.3 回归测试

需要覆盖：

- `需规文档` 与 `软设文档` A4 对象继续正常渲染。
- Canvas 主视口拖拽、缩放、滑窗切换继续正常。
- 右侧 `Inspector` 对阶段关系、文档块、功能节点三类选择都能正常切换。
- P4 投影树不受功能树改造影响。

## 13. 风险与控制

| 风险 | 表现 | 控制策略 |
| --- | --- | --- |
| 事件冲突 | 树节点拖拽误移动 Canvas | 树主体事件隔离，标题条专门负责对象拖拽 |
| 数据不足 | 派生树层级太浅 | UI 明确标识“由当前设计基线派生”，后续接 Dify 结构化输出 |
| 组件膨胀 | `DesignMorphCanvasPlatform` 继续变大 | 首版可局部分支，第二轮抽 `StageObjectFrame` |
| 假持久化 | 用户误以为拖拽已保存 | 拖拽后标记“待应用调整”，确认前不写入事实源 |
| 与 P4 投影混淆 | 功能树被误认为工单树 | 节点类型、标题和说明明确区分“功能对象”与“工单投影” |

## 14. 设计结论

`功能树` 应升级为 `P3 Design Lab` 中与 A4 文档对象同级的可交互阶段对象。首版应优先采用 `antd Tree`，因为它符合当前技术栈、交互需求和落地成本约束。

落地策略应分两层推进：

1. 先在前端用派生功能树建立真实交互框架，解决展开、选择、搜索、拖拽事件和 `Inspector` 联动。
2. 再要求 Dify 或自研转换器输出标准 `functional_tree_projection`，并由后端归一化进入设计基线。

这样既能快速提升当前功能树框的可用性，也不会把临时 UI 派生数据误认成最终软件设计事实源。
