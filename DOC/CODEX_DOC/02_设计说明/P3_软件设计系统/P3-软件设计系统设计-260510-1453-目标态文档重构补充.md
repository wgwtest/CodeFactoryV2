## 1. 背景

`P2 需求分析系统` 经过多轮重构后，已经形成可作为后续阶段参照的设计范式。其主设计文档不是功能说明，也不是实现计划，而是目标态软件设计说明，稳定回答以下问题：

1. 系统正面工作对象是什么。
2. 后台权威状态是什么。
3. 页面如何围绕正面工作对象组织。
4. 后端如何按业务模块和技术层次分离。
5. 结构化状态、正文投影、冻结包和下游交换之间是什么关系。
6. 组织器、模型调用、日志、状态机和人工确认如何协同。

当前 `P3` 已有两类设计口径：

- `P3-软件设计系统设计.md`：早期订单、审批、评审、冻结和工单包流的概要设计。
- `docs/superpowers/specs/2026-05-01-p3-design-lab-v2-design.md`：新版 `P3 Design Lab` 的局部原理验证设计来源稿。

这两类文档都保留了有效判断，但还没有形成与 `P2` 主设计同等级别的 `P3` 目标态软件设计说明。尤其是 `P3` 的正面工作对象、后台权威状态、设计轮次状态机、软件设计说明正文投影、冻结口径和 `P4` 交接投影之间的关系，需要重新整理。

## 2. 本轮直接结论

本轮采用以下重构判断：

1. `P3` 主系统的正面工作对象是 `软件设计说明文档`，不是订单、审批单、工单列表或聊天记录。
2. `P3` 后台权威状态是 `SoftwareDesignBaseline v2`，软件设计说明和 `P4` 工单包都是它的投影。
3. `P3` 主输入只来自 `P2` 新版需求规格编写系统冻结包，不再兼容旧 `/requirements/specs` 规格池。
4. 自然语言交互是设计生成、策略补充、局部修订和校核通道，不替代需求规格说明本体。
5. 旧 `P3Order`、审批、评审、冻结和推送流程保留为历史流程能力和后续正式化侧线，不再作为新版 `P3` 的主架构起点。
6. 主文档必须按 `P2-需求分析系统设计.md` 的写法升级为完整目标态软件设计说明。

## 3. P2 范式对 P3 的映射

### 3.1 正面工作对象映射

| 阶段 | 正面工作对象 | 后台权威状态 | 下游消费包 |
| --- | --- | --- | --- |
| `P2` | 标准需求规格说明文档 | 需求语义状态 / `RequirementSpec` | `FrozenRequirementPackage` |
| `P3` | 软件设计说明文档 | `SoftwareDesignBaseline v2` | `SoftwareDesignPackage` / `ModuleWorkorderBatchPackage` |

`P2` 证明了一个关键设计原则：用户应面对标准文档，而不是内部状态或模型对话。`P3` 继承该原则。架构师、设计人员和评审人员正面审阅的是软件设计说明正文；结构化设计基线负责支撑生成、校核、追溯、冻结和投影。

### 3.2 主路径映射

`P2` 主路径：

```text
选择规格模板与领域知识
  -> 专家通过问答或表单输入需求
    -> 系统维护需求语义状态
      -> 生成并修补标准需求规格说明正文
        -> 缺口检查与条款批注
          -> 专家冻结
            -> 输出标准需求规格说明 + RequirementSpec 包给 P3
```

`P3` 目标主路径：

```text
读取 P2 冻结需求规格说明包
  -> 创建设计会话并建立设计上下文
    -> 系统维护结构化软件设计状态
      -> 生成并修补软件设计说明 A4 正文
        -> 设计完整性检查与人工校核
          -> 冻结 SoftwareDesignBaseline v2
            -> 输出软件设计说明 + P4 模块工单投影
```

两者的共同点是：文档投影可读，结构化状态可计算，冻结包可交接。

### 3.3 组织器与轮次机制映射

`P2` 已经把一次用户输入拆成可审计的多阶段轮次，典型阶段包括：

- 意图理解。
- 结构化状态增量。
- 下一步交互规划。
- 正文或结构化状态投影。
- 轮次审计与模型调用日志。

`P3` 继承该机制，但把阶段语义换成软件设计语义：

| P2 阶段 | P3 对应阶段 | P3 输出 |
| --- | --- | --- |
| 意图理解 | 设计意图理解 | 识别用户是在要求架构偏好、模块拆分、接口补充、状态机补充还是冻结检查 |
| 决策状态增量 | 设计状态增量 | 产生模块、接口、数据、状态、部署、约束和追溯增量 |
| 正文补丁 | 设计正文补丁 | 修改软件设计说明对应章节 |
| 下一步交互规划 | 设计交互规划 | 给出下一轮设计确认、局部补充或冻结建议 |
| 调用日志 | 设计调用日志 | 记录模型输入输出、合同校验、采用字段和失败原因 |

## 5. 旧 P3 内容的处理方式

旧 `P3` 中仍然有效的内容包括：

- 人工评审和冻结必须存在。
- 未冻结结果不得下发 `P4`。
- `P4` 接收的是带包级上下文的模块工单包，不是裸列表。
- `P5` 可行性反馈必须经 `P3` 仲裁，不能直接命令 `P4` 修旧工具。
- 面向 `P6` 的展示输出必须表达观察态，不替代业务流程。

这些内容回写到新主文档中，但表述位置调整：

| 旧内容 | 新位置 |
| --- | --- |
| `P3Order` | 作为评审 / 冻结 / 下发流程中的可选流程外壳，不再作为主权威对象 |
| 审批通过 / 驳回 | 后端评审与冻结模块、关键运行流程 |
| 批次工单包 | 工单投影与交换模块、对象模型、API、关键流程 |
| `P5` 回流仲裁 | 业务目标与边界、关键流程、质量门 |
| `/xx-p3` | 历史工作台 / 旧流程面，不再作为目标态主入口 |

## 8. 仍需后续确认的问题

以下问题本轮先给出目标态设计口径，但不在文档中写成已实现事实：

1. `P3` 是否需要像 `P2` 一样引入可替换设计组织器包。
2. 软件设计说明模板是否来自正式模板中心，还是先内置一版标准模板。
3. `SoftwareDesignBaseline v2` 是否需要持久化为独立表，还是短期继续通过 JSON 状态承载。
4. 旧 `P3Order` 是否迁移为新基线的评审流程外壳，还是后续新建 `DesignReviewCase`。
5. `P4` 工单投影是否先保持模块级，还是立即细化到子模块 / 接口 / 数据对象级。

主设计文档会把这些内容写成目标态边界和演进约束，不冒充已完成代码。

## 10. 本轮设计判断

`P3` 应当从“订单驱动的软件设计流程页面”升级为“以软件设计说明正文为正面工作对象、以结构化软件设计基线为后台事实源的软件设计系统”。

这不是否定旧 `P3` 的审批和工单流，而是把它们放回正确位置：评审、冻结和交接是设计基线成熟之后的治理环节，不应成为新版 `P3` 的主设计起点。
