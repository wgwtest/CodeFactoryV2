## 1. 背景

`P2` 与 `P3` 在业务语义上不同，但在产品结构上高度相似。

`P2` 的核心链路是：

```text
自然语言问答 / 表单输入
  -> 结构化需求状态
    -> 需求规格说明正文
      -> 缺口检查
        -> 冻结包
```

`P3` 的核心链路是：

```text
需求规格说明正文输入
  -> 自然语言设计配置 / CLI
    -> SoftwareDesignBaseline v2
      -> 软件设计说明正文
        -> 完整性检查
          -> P4 工具包 / 工单投影
```

两者共同点不是具体业务字段，而是“阶段工作台”形态：

- 左侧承载交互输入、配置、来源事实或阶段控制。
- 右侧承载标准文档主产物。
- 后台维护结构化状态。
- 主产物需要目录、正文、检查、批注、追溯和下游投影。
- 人工通过 CLI、表单或短指令持续修订阶段状态。

因此 `P3 Design Lab` 不应重新造一套独立页面结构。它应当以 `P2` 当前成熟形态为母版，抽象出跨阶段可复用的文档工作台组件，并作为第二个业务样本验证该抽象是否成立。

## 2. 本轮直接结论

1. `P3 Design Lab` 是新版 `P3` 的主深化入口。
2. 旧 `/xx-p3` 和 `/xx-p3-doc-sim` 暂时保留，但不作为后续深化主线。
3. `P3` 首轮重要成果是抽象平台共性工作台，而不是扩展旧订单流程。
4. 共性抽象必须从 `P2 RequirementAuthoringPage` 与 `P3 Design Lab` 的共同结构中提炼。
5. 首轮只在 `P3 Design Lab` 中验证共性组件，不立即改造 `P2`。
6. `P3` 验证通过后，再反向升级 `P2`，让 `P2` 也使用同一套阶段工作台骨架。

## 3. P2 与 P3 的工作台映射

| 维度 | P2 需求规格编写工作台 | P3 Design Lab | 共性抽象 |
| --- | --- | --- | --- |
| 输入主对象 | 自然语言问答 / 表单 | P2 冻结需求规格说明 | 阶段输入区 |
| 辅助交互 | 问答短指令、表单字段 | CLI 设计配置、局部修订指令 | `InteractionPane` |
| 后台状态 | 需求语义状态、文档聚合 | `SoftwareDesignBaseline v2` | 阶段结构化状态 |
| 主产物 | 需求规格说明 | 软件设计说明 | `DocumentProductSurface` |
| 主产物形态 | A4 标准正文 | A4 标准正文 | `A4DocumentSurface` |
| 目录 | 章节和条款 | 章节、设计模块、追溯 | `DocumentOutlinePanel` |
| 检查 | 缺口检查 | 设计完整性检查 | `QualityCheckPanel` |
| 下游输出 | P3 可消费冻结包 | P4 工具包 / 工单投影 | `ProjectionPanel` |
| 冻结 | 冻结需求规格说明 | 冻结设计基线和软设说明 | 阶段冻结动作 |

## 4. 共性组件边界

### 4.1 `StageDocumentWorkbench`

阶段文档工作台外壳。

职责：

- 承载标题、副标题、状态标签、动作区。
- 承载左右分栏布局。
- 支持左侧上区、左侧下区和右侧主产物区。
- 不理解 `P2` 或 `P3` 的业务字段。
- 不直接调用 API。

首轮比例：

- `P3`：左侧约 `36%`，右侧约 `64%`。
- 左侧内部：输入事实源约 `64%`，CLI 约 `36%`。

### 4.2 `DocumentProductSurface`

标准文档主产物表面。

职责：

- 作为右侧最大展示权重区域。
- 通过 Tab 组织正文、目录、检查、投影等视图。
- 默认打开正文页。
- 支持接入 A4 文档纸面组件。
- 不拥有正文生成逻辑。

首轮 P3 Tab：

| Tab | 内容 |
| --- | --- |
| 正文 | A4 软件设计说明正文 |
| 目录 | 软件设计说明章节、设计模块、追溯摘要 |
| 检查 | 设计完整性检查、阻断项、警告和通过项 |
| 投影 | 面向 `P4` 的模块工单投影 |

### 4.3 `A4DocumentSurface`

A4 标准文档纸面。

职责：

- 提供接近正式文档的视觉形态。
- 支持标题、页眉、页脚、章节列表。
- 支持空状态。
- 不限制文档类型。`P2` 可以渲染需求规格说明，`P3` 可以渲染软件设计说明。

### 4.4 `WorkbenchAdapter`

业务适配层。

职责：

- `P2` 把 `RequirementAuthoringDocumentDetail` 转换为共性工作台视图模型。
- `P3` 把 `P3DesignLabSession` 和 `P3DesignInputPackage` 转换为共性工作台视图模型。
- 共性组件只消费视图模型，不读取业务 DTO。

首轮可以先在 `P3DesignLabPage` 内部完成轻量适配；后续再抽独立 adapter 文件。

## 5. 首轮实现范围

本轮实现只做以下事项：

1. 新增共性前端组件目录。
2. 抽出阶段工作台外壳和主产物 Tab 表面。
3. 改造 `P3DesignLabPage` 使用共性工作台骨架。
4. 在 `P3` 右侧主产物区新增正文、目录、检查、投影 Tab。
5. 保持现有 `software-design-v2` API 不变。
6. 保持旧 `/xx-p3` 和 `/xx-p3-doc-sim` 不变。
7. 保持 `P2 RequirementAuthoringPage` 暂不改造。

本轮不做：

- 不迁移 `P2` 到共性组件。
- 不接回旧 `P3Order` 审批流。
- 不扩展真实模型调用。
- 不引入新的路由。
- 不兼容旧 `/requirements/specs`。

## 6. 验收口径

首轮完成后，至少满足：

1. `/p3-design-lab` 页面存在共性工作台骨架标识。
2. 左侧仍包含需求规格说明输入区和 CLI 区。
3. 右侧主产物区使用 Tab 展示。
4. 右侧至少包含正文、目录、检查、投影四个 Tab。
5. 正文 Tab 继续以 A4 软件设计说明形式展示。
6. 目录 Tab 能展示设计正文章节和设计基线模块。
7. 检查 Tab 能展示设计检查结果或未检查状态。
8. 投影 Tab 能展示 `P4` 模块工单投影。
9. 现有 P3 Design Lab 生成链路测试通过。
10. 旧 `/xx-p3` 不因本轮改造被修改。

## 7. 后续反向升级 P2 的条件

`P3` 验证成功后，`P2` 反向升级前应满足：

1. `StageDocumentWorkbench` 不含 `P3` 专用命名。
2. `DocumentProductSurface` 的 Tab 配置可以完全由业务页面传入。
3. A4 文档纸面能表达需求规格说明和软件设计说明两类文档。
4. `P3` 页面测试证明共性组件不会破坏原有生成链路。
5. `P2` 升级计划明确保留现有问答模式、表单模式、缺口检查和冻结行为。

## 8. 设计结论

`P3 Design Lab` 的深化目标不只是完成软件设计业务页面，而是证明 `CodeFactoryV2` 的阶段工作台可以形成平台级复用骨架。

`P2` 是第一业务样本，`P3` 是第二业务样本。只有把两者共同形态抽出来，后续 `P4`、`P5` 和 `P6` 才可能在统一平台体验下继续演进。
