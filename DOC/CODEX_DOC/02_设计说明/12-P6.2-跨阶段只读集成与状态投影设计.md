# P6.2 跨阶段只读集成与状态投影设计

## 1. 设计定位

`P6.2` 是 `P6` 稳定平台层的读侧集成底座，负责把 `P1 ~ P5` 的阶段状态、入口状态、核心指标和摘要信息，收敛为平台可消费的统一投影。

它本质上不是一个“页面功能”，而是一个平台级只读契约层。

## 2. 核心目标

- 为 `P6.1` 门户页提供统一读侧数据
- 为后续串行观察页提供阶段级状态投影
- 建立 `P1 ~ P5 -> P6` 的标准查询 / 订阅契约
- 明确 `P6` 的只读边界与降级策略

## 3. 只读边界

### 3.1 允许做的事

- 查询阶段概览
- 查询入口可用性
- 查询摘要指标、健康信息和告警摘要
- 订阅阶段状态变化
- 将阶段数据归一为平台投影对象

### 3.2 明确禁止的事

- 不写入 `P1 ~ P5` 内部事实对象
- 不触发阶段命令
- 不修改阶段语义
- 不直接读取阶段内部数据库
- 不直接抓取页面私有状态
- 不把临时脚本输出伪装成正式接口

这不是工程实现习惯问题，而是 `P6` 能否保持解耦的硬边界。

## 4. 输入契约

`P6.2` 面向每个阶段至少定义两类输入：

- 查询接口
- 订阅接口

首版允许“先查询、后订阅”，但查询接口是硬要求。

### 4.1 查询接口最小对象

每个阶段至少需要提供：

- `StageOverview`
- `StageEntryProjection`
- `StageMetricProjection`
- `StageHealthProjection`

推荐字段如下：

| 对象 | 最小字段 |
| --- | --- |
| `StageOverview` | `stageId`、`stageName`、`summary`、`status`、`updatedAt` |
| `StageEntryProjection` | `route`、`available`、`reason` |
| `StageMetricProjection` | `key`、`label`、`value`、`trend` |
| `StageHealthProjection` | `level`、`message`、`source`、`capturedAt` |

### 4.2 订阅接口最小对象

当阶段具备订阅能力时，推荐输出统一事件包络：

- `eventType`
- `stageId`
- `timestamp`
- `payload`
- `source`

事件类型首版建议固定为：

- `stage_status_changed`
- `metrics_changed`
- `health_changed`
- `entry_changed`
- `alert_created`

## 5. 归一化投影模型

`P6.2` 不应把各阶段的原始接口直接抛给页面，而应先归一化成平台级投影。

首版固定以下投影对象：

### 5.1 `StageSnapshot`

表示某阶段某一时刻的稳定快照，至少包含：

- 基本信息
- 入口状态
- 核心指标
- 健康摘要
- 数据来源
- 时间戳

### 5.2 `PortalProjection`

表示 `P6.1` 门户所需的聚合读模型，至少包含：

- 节点清单
- 关系清单
- 产物清单
- 门户摘要
- 当前知识库名

### 5.3 `ObservationProjection`

表示串行观察页所需的读模型，至少包含：

- 阶段卡片序列
- 关键指标序列
- 告警摘要
- 入口跳转信息

## 6. 数据来源与新鲜度规则

`P6.2` 必须对每份投影数据显式标注来源和时效。

### 6.1 来源字段

每份投影至少应标注：

- `sourceStage`
- `sourceInterface`
- `capturedAt`
- `projectionAt`

### 6.2 新鲜度字段

每份投影至少应标注：

- `freshness`
  - `fresh`
  - `stale`
  - `unknown`
- `staleAfterMs`
- `degradedReason`

### 6.3 降级规则

当某阶段读接口不可用时：

1. 不阻塞整个 `P6`
2. 该阶段显示为“数据暂不可用”而不是静默消失
3. 继续展示上次稳定快照时，必须显式标明“过期”

## 7. 阶段消费矩阵

首版建议 `P6.2` 优先消费如下数据：

- `P1`
  - 当前知识库
  - 已发布知识规模
  - 知识图谱入口状态
- `P2`
  - 建模任务数
  - 建模阶段状态
  - 需求规格入口状态
- `P3`
  - 设计任务数
  - 设计冻结状态
  - 评审状态
- `P4`
  - 工具供给数
  - 需求单状态
  - 巡检状态
- `P5`
  - 构建单数
  - 装配尝试状态
  - 缺口状态

这些数据的目标不是“全量搬运”，而是服务于平台观察。

## 8. 平台消费场景

`P6.2` 的首版消费方固定为：

- `P6.1` 首屏观察门户
- 串行观察页
- 平台级总览条与摘要卡

当前不允许：

- 把 `P6.2` 当成统一写接口
- 把阶段内部工作台当作 `P6.2` 的直接消费者

## 9. 实施顺序

首版按以下顺序推进：

1. 先收敛阶段查询接口
2. 再收敛统一投影对象
3. 先服务 `P6.1`
4. 订阅接口作为增强能力逐步补入

这能保证 `P6` 先稳定读通，而不是因为追求“全实时”把边界写乱。

## 10. 验收口径

1. `P6` 对 `P1 ~ P5` 的读写边界在正式文档中清晰固定。
2. 每个阶段至少具备最小查询投影要求。
3. 门户页消费的是归一化投影，而不是阶段私有结构。
4. 数据来源、新鲜度、降级原因有明确字段，不出现“看起来有数据但不知道来自哪”的情况。
5. 阶段接口不可用时，`P6` 能降级展示而不是整页失效。
