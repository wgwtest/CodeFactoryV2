# P2 需求分析系统设计

> 归档说明：本文件归档自 `docs/superpowers/specs/2026-04-13-application-requirement-modeler-design.md` 与 `docs/superpowers/specs/2026-04-17-xx-p2-sim-design.md`，作为 `P2` 阶段的正式详细设计基线。

**日期：** 2026-04-19

**对应节点：**
- `P2` 需求分析系统
- `P2.1` 应用需求建模器
- `P2.2` 需求规格对象输出与投影
- `P2.3` 模拟输入台与联调入口

## 1. 设计目标

`P2` 的目标是在 `P1` 已发布知识仓之上，为不懂技术的行业专家提供一个可交互、可解释、可导出的需求建模系统，把业务表达翻译为标准结构化 `RequirementSpec`。

`P2` 首版不是组件装配台，也不是低代码原型生成器，而是：

- 知识仓与软件设计系统之间的过渡层
- 用户意图到结构化需求对象之间的第一道翻译层
- 面向业务语言的交互式建模入口

## 2. 设计边界

### 2.1 首版负责

- 提供面向非技术用户的交互式建模器
- 支持在业务目标、对象、模块、动作、交接层面逐步建模
- 消费 `P1` 的发布态业务元素
- 允许当场新建临时元素并标记 `待入库`
- 输出结构化需求对象和 `MD` 可读投影

### 2.2 首版不负责

- 组件命中推荐和复用判断
- 软件设计说明生成
- 工具仓库资产管理
- 可运行原型生成
- BPMN / 泳道图编辑器
- 面向技术人员的专业低代码建模工具

## 3. 目标用户与交互原则

### 3.1 目标用户

首版唯一主用户画像：

- 不懂技术的行业专家
- 需求分析人员

### 3.2 设计原则

- 使用纯业务语言
- 采用强引导、低输入负担的交互方式
- 系统负责把业务表达翻译成结构化对象
- 先建需求，不混入组件与实现细节

### 3.3 对象优先于流程

`P2` 必须坚持“对象优先于流程”的建模逻辑。

原因：

- 对象建模要素比流程更完整
- 系统要支持探索新流程，而不只是复现既有流程
- 多对象跨流程应用是核心目标场景

## 4. 交互形态

### 4.1 双形态建模器

`P2` 正式支持两种互补交互形态：

- `表单式建模器 + 智能推荐`
- `选配式建模器`

二者是同一结构化模型的不同交互入口，不是两套割裂系统。

### 4.2 默认主路径

首版默认路径固定为：

`先向导收敛 -> 再进入按场景 / 模块组织的选配建模`

含义：

- 用户先收敛业务目标、受众和边界
- 再进入模块级建模
- 系统基于当前输入动态推荐动作、对象和交接点

### 4.3 页面骨架

首版沿用三栏工作台：

- 左侧：步骤导航
- 中间：当前步骤的提问、模块搭建、推荐项与手工补充
- 右侧：实时预览，包括模块骨架、动作链、模块交接和页面建议

## 5. 建模对象与步骤

### 5.1 建模核心单元

`P2` 的最小可解释单元不是裸流程节点，而是 `动作 / 任务`：

- `参与方`
- `业务对象`
- `行为`
- `结果 / 状态变化`

### 5.2 标准建模步骤

首版按以下 6 段推进：

1. 业务目标收敛
2. 使用对象与范围收敛
3. 自建模块
4. 模块内动作建模
5. 模块链路与交接动作
6. 自动页面建议与输出

### 5.3 模块与交接

模块由用户自行创建，至少填写：

- 模块名
- 一句用途

系统在读到模块名和用途后，再推荐：

- 动作候选
- 参与方
- 业务对象
- 候选交接点

多个模块之间通过 `交接动作` 连接，而不是只保留孤立模块列表。

## 6. 推荐体系

### 6.1 推荐来源

`P2` 的推荐来自三层：

- 通用应用知识
- `P1` 已发布领域知识
- 用户当前输入

### 6.2 推荐触发规则

至少支持以下触发：

- 写完 `模块名 + 用途` 后推荐动作候选
- 新建动作后推荐参与方、业务对象和结果状态
- 形成多个模块后推荐模块间交接动作
- 模块与动作骨架稳定后推导页面模板建议

### 6.3 来源标识

每个建模项都必须带来源：

- `recommended_common`
- `recommended_domain`
- `manual`
- `temporary_pending_intake`

### 6.4 推荐解释

系统至少要能解释：

- 为什么推荐某类通用模式
- 为什么某个知识项与当前模块或动作相关
- 为什么建议某个交接点或页面模板

## 7. 权威输出模型

`P2` 的权威输出不是说明文档，而是结构化对象。

首版对象名称采用：

- `ApplicationRequirementModel`

其内部至少应包含：

- `application_goal`
- `audiences`
- `roles`
- `modules`
- `actions`
- `business_objects`
- `module_handoffs`
- `page_suggestions`
- `knowledge_references`
- `temporary_elements`
- `draft_meta`

设计要求：

- 结构化对象是唯一权威输出
- `MD` 只是可读投影
- 每个核心项必须具备稳定 `id`
- 每个推荐/手工/临时项必须可追溯来源
- `page_suggestions` 只表达页面模板建议，不提前混入组件资产

## 8. `MD` 投影与草稿机制

### 8.1 `MD` 投影

首版 `MD` 投影至少包括：

- 应用名称与目标
- 受众与业务分工
- 模块清单与用途
- 每个模块的动作集合
- 模块间交接关系
- 自动页面建议
- 引用的领域知识
- 手工补充项和临时新增项

### 8.2 草稿状态

首版支持：

- `draft`
- `completed`
- `exported`

### 8.3 最小完成条件

至少满足以下条件，才能标记完成：

- 有业务目标
- 有至少一类使用对象
- 有至少一个模块
- 每个动作都包含 `参与方 + 业务对象 + 行为 + 结果`
- 已生成至少一项结构预览

## 9. `P2-Sim` 的正式定位

`P2-Sim` 不是替代真实 `P2` 的旁路功能，而是 `P2` 的轻量模拟输入台，用于：

- 从预置样板生成最小 `RequirementSpec`
- 一键写入现有 `requirements/specs` 池
- 为 `P3` 提供可重复、可操作的上游联调入口

首版约束：

- 不增加“推送到 P3”假动作
- 行为保持与真实上游一致，即提交需求规格说明即可
- 只提供轻量样板和预览，不做完整需求编辑器

## 10. 与上下游的边界

### 10.1 与 `P1` 的边界

`P2` 只消费 `P1` 的已发布知识结果，不允许读取：

- 候选知识
- 治理工作态
- 审核中间数据

首版正式输入包括：

- 发布态流程清单
- 发布态实体/事件清单
- 单项详情
- 关系邻域
- 知识引用元信息

### 10.2 与 `P3` 的边界

串行关系固定为：

`P1 -> P2 -> P3`

`P2` 向 `P3` 只输出：

- 结构化需求对象
- `JSON / YAML` 权威对象
- `MD` 可读投影
- 草稿/完成态元信息

`P3` 不应直接读取 `P2` 的交互式临时状态。

## 11. 模块划分与首版范围

首版建议拆为 5 个模块：

- 建模器前端
- 向导收敛服务
- 模块建模服务
- 推荐编排服务
- 结果投影服务

首版最小实现范围固定为：

- 独立“应用需求建模器”页面
- 默认主路径：`向导收敛 -> 模块建模 -> 自动页面建议`
- 左中右三栏布局
- 用户自建模块
- 模块内动作卡片建模
- 右侧实时链路与模块交接预览
- 临时元素标记
- 草稿保存 / 恢复 / 完成
- 导出 `JSON/YAML + MD`

首版场景范围固定为：

- `流程办理 / 协同审批`

## 12. 验收口径

首版验收只看以下问题是否成立：

1. 非技术行业专家能否用纯业务语言完成一次模块化建模
2. 用户能否自己创建模块，并用动作单元表达业务过程
3. 系统能否实时形成模块链路和模块间交接预览
4. 系统能否在骨架稳定后自动推导页面模板建议
5. 能否稳定导出结构化对象和 `MD`，并保留草稿继续编辑
