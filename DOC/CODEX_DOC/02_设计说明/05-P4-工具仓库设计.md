# P4 工具仓库设计

**对应节点：**

## 1. 设计目标

`P4` 的目标不是提供一个普通“工具列表管理页”，而是形成软件工厂中的工具资产运行中台，承接工具描述、资产登记、匹配、交付、自演进与验证工作台。

首版要形成以下最小闭环：

- 工具描述模型
- 工具仓库 CRUD
- 分类与标签体系
- 工具需求单与匹配规则 MVP
- 自演进巡检闭环
- 对 `P5` 可查询、可获取的结果出口

## 2. 设计边界

### 2.1 首版负责

- 工具、组件、执行器资产的结构化登记
- 工具需求单与叶子需求项的受理、匹配、审定与供给
- 工具池自演进巡检、发现项处置、内部任务推进与回退
- 统一数据快照与驾驶舱验证工作台

### 2.2 首版不负责

- 直接替代 `P3` 的软件设计对象生成
- 直接承担最终软件装配与运行
- 多工具依赖图调度平台
- 全厂统一通用调度中心

### 2.3 并行开发边界

`P4` 必须通过标准契约与上游耦合，不直接依赖：

- `P1` 治理工作态
- `P1 / P2 / P3` 的内部表结构
- 临时脚本输出
- 未发布中间 JSON

## 3. `P4` 的角色重定义

`P4` 同时承担两条业务闭环和一条公共运行骨架：

### 3.1 外部输入闭环

面向 `P3 / P3-sim`：

`工具需求单 -> 拆叶子工具项 -> 匹配 -> 审定 -> 直接交付或进入研制 -> 对 P5 提供查询与获取`

### 3.2 内部自演进闭环

面向 `P4` 工具池自身：

`工具仓快照 -> 巡检 -> 发现项 -> 采纳/忽略 -> 内部任务 -> 自动改写或人工跟进 -> 回退`

### 3.3 公共运行闭环

为两条业务链统一提供后台推进语义：

`命令接入 -> 事实写入 -> 任务投递 -> 调度 -> 分域执行 -> 查询投影刷新 -> 审计与回退`

### 3.4 外部回流边界与“非直接修订语义”

这里必须澄清一个容易混淆的点：`P4` 不直接接受 `P5` 的修订回流，并不等于 `P4` 完全不存在修订。

`P4` 内部仍存在两类合法演进：

- 面向平台内部质量的修订：缺陷修复、依赖升级、执行效率优化、可观测性增强
- 面向既有资产池治理的自演进：由 `P4.3` 巡检闭环触发的自动改写或人工跟进

但下列情况不应被称为 `P4` 修旧工具：

- 某次 `P5` 装配发现当前业务目标与既有资产不契合
- 某次 `P5` 交付场景需要新的业务组合语义

对这类问题，更合理的路径是：

- `P5` 上报问题
- `P3` 仲裁问题归属
- 若属于供给缺口，由 `P3` 向 `P4` 下发新供给任务 / 派生任务 / 组件拆分任务
- `P4` 再自主决定复用、派生、拆分或新建

这样才能保证：

- 平台级既有资产不会被某一次业务装配临时改写语义
- `P4` 的自循环可独立演进
- `P3` 始终保持对业务目标和设计语义的唯一解释权

## 4. 核心对象模型

### 4.1 `ToolDefinition`

首版核心资产对象为 `ToolDefinition`。

核心字段包括：

- `tool_id`
- `name / slug / summary`
- `status`
- `primary_domain_id`
- `tool_form_id`
- `runtime_platform_ids`
- `lifecycle_stage_ids`
- `input_types / output_types`
- `tags`
- `verification`

### 4.2 `ToolDemandSheet / ToolDemandItem`

`P4.2` 的主干协议流对象，用于承接 `P3 -> P4 -> P5` 的外部输入闭环。

### 4.3 `ToolMatchRun`

用于记录一次匹配请求、候选结果、命中维度、原因、缺口和验证状态。

### 4.4 `EvolutionRun / EvolutionFinding / EvolutionTask`

用于承接 `P4.3` 的巡检与自演进闭环。

### 4.5 统一快照投影

总览、输入工具链、自演进巡检、工具仓库应消费同一份 `P4` 事实源投影，而不是各自拼装隐式状态。

## 5. 分类、标签与匹配

### 5.1 稳定目录

首版目录至少包括：

- 业务域
- 生命周期环节
- 工具形态
- 运行平台

### 5.2 标签体系

标签使用命名空间前缀：

- `domain:*`
- `lifecycle:*`
- `form:*`
- `runtime:*`
- `input:*`
- `output:*`
- `risk:*`

### 5.3 匹配规则 MVP

首版只做可解释规则打分，不做黑盒智能排序。

主要维度包括：

- 业务域命中
- 生命周期命中
- 输入类型命中
- 输出类型命中
- 工具形态命中
- 运行平台命中
- 标签命中
- 场景关键词命中

## 6. 页面与工作台

首版 `P4` 工作台采用独立驾驶舱页承载，并按页内工作区切换：

- `总览`
- `输入工具链`
- `自演进巡检`
- `工具仓库`

工作台必须提供：

- 核心指标卡
- 覆盖热力矩阵
- 风险摘要
- 工具仓库管理与验证状态
- 输入链任务与巡检任务状态

### 6.1 工具仓库验证与测试治理

`P4.1` 不只是“能新增工具”，还必须承担验证期工具池治理职责。

首版正式约束：

- 支持单工具安全删除
- 支持当前阶段的临时“清空工具池”测试入口
- 删除失败时必须返回明确引用原因
- 验证关键按钮应保留稳定选择器，便于自动化回归

补充边界：

- 单工具删除是正式能力，但必须做引用检查
- 清空工具池只是验证期能力，不属于长期正式业务能力
- 清空操作只清理工具池与运行记录，不自动清理上游工单事实

### 6.2 `P3-sim` 典型工单发生器

`P3-sim` 在 `P4` 视角中不是独立产品，而是 `P4.2` 的标准联调输入台。

首版至少支持 3 类预置场景：

- `模拟蓝军`
- `导航规划`
- `数据治理`

设计要求：

- 各场景都必须投影为同一种 `ToolDemandSheetCreateRequest`
- 场景差异只体现在模板内容，不体现在协议结构
- 发生器页只负责发单，不承担 `P4` 内部处理逻辑

### 6.3 模拟研制执行器观察面

`P4.2` 的研制推进必须由后台执行器驱动，而不是由页面查询动作反向推进。

首版正式要求：

- 审定进入 `approve_manufacture` 后应形成独立制造计划
- 制造计划由后台模拟执行器自动推进
- `P5` 与 `P4` 页面上的查询动作只读，不改变推进状态
- 工具仓库工作台必须能看到模拟研制队列、当前进度与预计完成时间

## 7. 与上下游的契约边界

### 7.1 `P3 -> P4`

`P4` 只消费 `P3` 冻结后的模块级工具化描述和工单包，不消费 `P3` 的临时生成草稿。

### 7.2 `P4 -> P5`

`P5` 只通过标准查询与获取接口消费 `P4` 结果，不直接回写 `P4` 内部状态。

若 `P5` 报告供给不匹配，`P4` 也只接受经 `P3` 仲裁后重新签发的新供给目标，不接受 `P5` 直接修订命令。

### 7.3 `P1 -> P4`

`P4` 只允许消费 `P1` 的标准知识上下文：

- `archive_id`
- `entity_ids`
- `process_ids`
- `snapshot_version`

## 9. 验收口径

首版达到完成状态，至少满足：

1. 存在独立 `P4` 工作台和清晰的页内工作区切换
2. 工具仓库支持结构化 CRUD 与验证状态管理
3. 输入工具链支持受理、逐项审定、供给结果输出与完成判定
4. 自演进巡检支持配置、发现项处置、内部任务推进与回退
5. 驾驶舱页能展示覆盖热力矩阵与风险摘要
6. `P4` 与 `P1 / P3 / P5` 的契约边界清晰，不依赖内部实现
