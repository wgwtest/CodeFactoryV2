## 1. 设计定位

`P1` 的目标不是做一个“文档列表系统”或“只会展示节点数量的图谱页”，而是形成从业务资料到已发布知识仓的正式闭环，并向后续 `P2` 提供稳定、可解释、可追溯的业务元素出口。

`P1` 首版必须同时形成 5 类结果：

- 受控资料接入与结构化解析能力
- 正式知识抽取与候选知识持久化能力
- 人工治理、审核、发布与版本管理能力
- 发布态知识查询、图谱与流程浏览能力
- 面向 `P2` 的标准业务元素与证据回溯出口

## 2. 目标与边界

### 2.1 首版负责

- 接收 `PDF / DOC / DOCX` 等业务资料
- 生成保留章节、块、页码、锚点的结构化解析结果
- 按统一 schema 抽取实体、事件、流程、规则、指标与关系
- 记录抽取来源、置信度、执行元数据和版本信息
- 提供术语归并、关系修正、流程补链、审核发布与审计记录
- 存储与查询已发布知识，并支持图谱/流程双视图验证

### 2.2 首版不负责

- 需求建模本身
- 软件设计对象生成
- 工具/组件命中与复用判断
- 最终软件运行装配

### 2.3 设计原则

- `P1` 只向下游暴露标准成果物，不暴露内部脚本和中间态
- `P1.1 -> P1.5` 严格串行推进，但节点之间通过契约解耦
- 正式抽取/重建链必须与预览/调试链明确分离
- 已发布知识必须可回答“它是什么、与谁相关、证据在哪、由谁贡献”

## 3. 阶段节点与功能分解

### 3.1 `P1.1` 功能验证平台底座

`P1.1` 是阶段一的前置使能层，不替代业务子系统，而是负责：

- 承载文档、抽取、治理、图谱等验证页面
- 提供统一任务状态、日志、错误透传和证据查看能力
- 提供统一详情抽屉、调试入口和 API 客户端

首版技术口径：

- 前端壳：`React + Vite + TypeScript`
- 页面路由：`React Router`
- UI：`Ant Design`
- 数据访问：`TanStack Query + Axios`
- 图形能力预留：`Cytoscape.js / React Flow`
- 端到端验证：`Playwright`

### 3.2 `P1.2` 文档接入与结构化解析

`P1.2` 只回答“文档怎样被受控接入并解析”，不直接给出知识结论。

标准成果物包括：

- 资料元数据、归档信息与版本信息
- 解析任务状态与错误记录
- 结构化片段、块边界、章节、页码、锚点与表格结果
- 解析执行元数据

首版技术口径：

- 正式解析器：`Docling`
- 复杂版面增强：`Unstructured`
- `DOC -> DOCX`：`LibreOffice Headless`
- 调试期轻量回退：`python-docx / PyMuPDF`

### 3.3 `P1.3` 候选知识抽取

`P1.3` 负责从 `P1.2` 的结构化片段中生成候选知识，不直接写入发布态知识仓。

标准成果物包括：

- 统一 schema 约束下的候选实体、事件、流程、规则、指标、关系
- `sourceRefs / confidence / extraction_run_id`
- 文档级正式抽取产物仓
- 双语投影增强元数据

### 3.4 `P1.4` 知识治理与发布

`P1.4` 是 `P1` 的产品质量中枢，负责：

- 术语统一与别名归并
- 关系修正与流程补链
- 候选项审核、驳回、发布与审计
- 文档级正式并入/移出与全集重算

### 3.5 `P1.5` 已发布知识仓、查询与图谱展示

`P1.5` 只消费已发布知识，不直接持有未治理候选项。

标准成果物包括：

- 发布态知识主存储
- 版本化快照与导出结果
- 实体/事件/流程浏览
- 图谱视图、流程链路视图、实体详情和来源对照

## 4. 核心功能模块设计

`P1` 首版采用“模块化单体优先、按微服务边界设计”的形式落地，内部至少包含以下 6 个子系统：

### 4.1 资料接入子系统

职责：

- 接收、登记、归档、标记来源目录与版本
- 记录批次、标签、归属与审计信息

边界：

- 只解决“文档可控接入”
- 不直接产出知识结论

### 4.2 文档解析子系统

职责：

- 章节切分
- 页码与锚点定位
- 表格提取
- 图片/OCR 处理
- 形成可计算文档片段

边界：

- 输出的是结构化文档，不是已发布知识

### 4.3 知识抽取子系统

职责：

- 从结构化片段中抽取候选对象和关系
- 记录证据来源与置信度
- 生成文档级正式抽取产物

边界：

- 输出的是候选知识或文档级正式产物
- 不直接决定发布态

### 4.4 知识治理子系统

职责：

- 术语归并
- 关系修正
- 流程补链
- 审核发布
- 版本管理与审计

边界：

- 治理流程保证知识质量
- 不把模型结果直接等同于发布结果

### 4.5 知识仓与查询子系统

职责：

- 存储已发布知识
- 提供检索、关系查询、流程追踪与版本对比
- 提供图谱/流程双视图和证据回溯

边界：

- 只消费已发布知识
- 不直接持有未治理工作态

### 4.6 构建映射出口子系统

职责：

- 把发布态知识投影为 `P2` 可消费的业务元素
- 为后续建模提供对象、流程、事件和证据线索

边界：

- `P1` 只提供标准知识出口
- 不进入 `P2` 的需求建模内部

## 5. 核心知识对象模型

`P1` 的正式中心不是“文档片段”，而是可治理、可发布、可追溯的知识对象。

首版一等对象至少包括：

### 5.1 `Entity`

表示稳定领域对象，例如组织、角色、资源、事项、设备、单据、指标主体。

最小语义：

- `id`
- `name`
- `type`
- `aliases`
- `attributes`
- `sourceRefs`
- `version`

### 5.2 `Event`

表示可触发或已经发生的业务动作。

最小语义：

- `id`
- `name`
- `trigger`
- `actor`
- `targetEntity`
- `preconditions`
- `postconditions`
- `sourceRefs`

### 5.3 `Process`

表示有步骤、角色、输入输出和决策点的流程链路。

最小语义：

- `id`
- `name`
- `steps`
- `roles`
- `inputs`
- `outputs`
- `decisionPoints`
- `relatedRules`
- `relatedEvents`
- `sourceRefs`

### 5.4 `Rule`

表示制度、约束、阈值、判定条件和合规要求。

### 5.5 `Metric`

表示指标、统计口径、维度、周期和阈值。

### 5.6 `Relation`

表示对象之间的显式关系，例如：

- `entity-owns-entity`
- `event-changes-entity`
- `process-contains-step`
- `rule-constrains-process`
- `metric-measures-entity`

### 5.7 `Evidence`

每条已发布知识必须挂接证据，至少记录：

- 来源文档
- 页码 / 章节 / 块
- 原文片段
- 抽取方式
- 置信度
- 人工确认记录

### 5.8 `KnowledgeVersion`

首版必须支持至少以下状态：

- `draft`
- `pending_review`
- `published`
- `deprecated`

## 6. 正式知识抽取链与数据作用域

### 6.1 正式链与预览链分离

从设计上，`P1` 必须长期维持两类链路：

- 预览/调试链：允许容错，服务于排障与本地验证
- 正式抽取/重建链：必须执行严格约束，失败即失败

不能让预览结果冒充正式知识产物。

### 6.2 正式抽取硬约束

正式知识库抽取/重建必须满足以下规则：

- 正式解析必须使用 `Docling`
- 正式抽取必须使用结构化大模型
- 不允许静默降级到轻量解析器或规则-only 抽取
- 若 `Docling` 未生效、结构化大模型未生效或执行元数据缺失，整次任务必须失败
- 每次正式抽取必须生成执行报告，记录真实 `parser / provider / model / candidate_count / relation_count`

### 6.3 长文档正式抽取

长文档不能继续采用“少量采样片段代表全文”的方式。

正式策略固定为：

`结构化分块 -> 分块抽取 -> 全局归并 -> 治理 / 发布`

核心要求：

- 基于 `Docling` 章节、块、表格、列表构建语义块
- 多块分别执行规则抽取与结构化大模型抽取
- 文档级统一归并术语、别名、关系和证据
- 保留块级来源信息，至少能追溯到章节/块级证据

### 6.4 文档级正式产物仓

`P1.3.5` 的核心资产不是临时 JSON，而是文档级正式产物账本。

每篇文档至少应独立保存：

- 文档元数据
- 文档级候选知识
- 文档级关系贡献
- 抽取执行元数据
- `included_in_archive`

其意义是把“是否有正式产物”和“是否纳入当前正式全集”彻底解耦。

### 6.5 单文档正式并入 / 移出

`P1.4.5` 负责把文档级产物聚合为当前正式知识全集。

并入规则：

- 重新对目标文档执行正式抽取
- 替换旧正式产物
- 从文档级产物仓重算全集

移出规则：

- 保留文档级正式产物
- 只把 `included_in_archive` 置为 `false`
- 再由剩余纳入文档重算全集

### 6.5.1 库级同知识验证、合并与更新

同一知识库中的不同文档可能反复描述同一个业务概念、实体、规则、流程或指标。`P1` 不能把它们简单堆成多个节点，也不能只按名称去重。文档级候选进入知识库全集前，必须经过“库级知识归并与更新”机制。

核心目标：

- 识别不同文档中指向同一知识对象的候选项。
- 验证这些候选项是否真的语义一致，而不是同名异义。
- 合并多文档证据、别名、定义、关系和来源。
- 在新文档提供更强证据或更新信息时生成修订候选。
- 在不同文档存在冲突时保留冲突解释，进入治理或质量门禁。

识别依据不能只看 `name`，至少应组合以下信号：

- `object_type`：实体、事件、流程、规则、指标等类型必须兼容。
- `normalized_name`：标准化名称、别名、缩写和中英文投影。
- `definition_signature`：定义文本、摘要和语义嵌入相似度。
- `relation_neighborhood`：上下游关系、所属对象、约束对象和触发对象。
- `evidence_refs`：来源文档、章节、chunk、锚点和证据片段。
- `policy_snapshot_id` / `rule_id`：产生候选的策略版本和规则依据。

库级归并流程：

```text
DocumentKnowledgeCandidate
  -> KnowledgeIdentityKey
  -> CrossDocumentMatchCandidate
  -> KnowledgeMergeDecision
  -> CanonicalKnowledgeItem
  -> ArchiveKnowledgeResolutionSnapshot
  -> PublicationCandidateSnapshot
```

归并决策类型：

| 决策 | 含义 | 后续动作 |
| --- | --- | --- |
| `new` | 当前候选没有可匹配的库内知识 | 创建新的规范知识候选 |
| `same` | 与既有知识语义一致 | 合并证据、别名、来源和置信度 |
| `update` | 与既有知识同源同义，但内容更新或证据更强 | 生成修订候选，保留旧版本 |
| `conflict` | 与既有知识指向同一对象但定义、数值或关系冲突 | 进入冲突处理和治理确认 |
| `split` | 原本合并的对象被证明是多个不同对象 | 生成拆分候选和影响面 |
| `reject` | 当前候选证据不足或不满足策略 | 不进入发布候选 |

更新规则：

- 尚未治理确认的候选知识可以被新归并结果替换，但必须保留旧候选版本和差异。
- 已正式入库的知识不能被新文档静默覆盖；必须生成 `revision_candidate`，等待治理确认后成为新的正式版本。
- 如果新文档只增加证据或别名，不改变知识语义，可生成轻量 `evidence_append` 更新。
- 如果新文档改变定义、金额、阈值、关系方向、适用范围或发布边界，必须生成结构性更新候选。
- 移出文档时不得删除正式知识本体，只能重算该知识的支撑证据；若剩余文档无证据支撑，应标记为 `unsupported` 或生成撤回候选。

库级图谱表达：

- 发布态图谱中的主节点应是 `CanonicalKnowledgeItem`，不是单个文档的候选节点。
- 多文档证据通过证据边或来源面板挂在规范节点下。
- 同义、别名、旧版本和冲突候选不应默认铺满图谱，而应通过详情或质量报告展开。
- 跨文档合并、更新、拆分必须生成 `RuleExecutionRecord` 和可追溯差异说明。

### 6.6 双语知识投影

双语知识投影属于治理/展示增强层，不改变正式抽取主链。

首版增强字段包括：

- `中文主名`
- `英文原名`
- `缩写`
- `中文解释`
- `中文证据摘要`
- `中文化状态`

约束：

- 双语字段不能覆盖原始抽取原值
- 编号、工件号、缩写类对象保留原值，只补中文解释
- 不采用“全文先翻译再抽取”作为正式建库策略

### 6.7 结构化大模型适配层

`P1` 的正式抽取链允许切换主流大模型供应商，但不能把供应商名写死在抽取服务里。

因此正式设计要求存在独立的结构化 LLM 适配层，负责：

- Provider 配置
- 模型元数据显式声明
- OpenAI 兼容协议接入
- 统一结构化输出调用
- 错误标准化

这层是 `P1` 当前的抽取基础设施之一，也为后续 `P2 / P3 / P4` 的模型接入复用预留基础。

### 6.8 知识生成阶段解耦合同

`P1` 的知识生成链虽然在业务上按 13 个阶段顺序推进，但实现上必须按“阶段处理器”解耦。每个阶段只能依赖上游公开产物合同，不能读取其它阶段的内部临时变量、页面状态或未声明文件路径。

每个阶段处理器必须声明以下合同：

- `stage_id`：稳定阶段标识，必须与运行态 13 阶段定义一致。
- `input_artifacts`：本阶段允许读取的输入产物类型、版本、来源范围和必填字段。
- `output_artifacts`：本阶段输出的知识对象、关系、证据、规则命中、指标、观察窗载荷和运行态图谱节点。
- `rule_set_refs`：本阶段实际使用的规则集合、规则版本、规则哈希和启用范围。
- `dependency_selectors`：本阶段输出与上游文档块、证据、候选项、关系、策略规则之间的依赖选择器。
- `idempotency_key`：同一输入、同一规则版本、同一模型配置下的幂等执行键。
- `runtime_snapshot`：本阶段对前端暴露的快照格式，包括 `status / graph / observer / events / metrics`。

阶段之间只通过 `output_artifacts` 传递信息。后续如果某个阶段需要替换为新实现，必须保持上游输入合同和下游输出合同兼容；若不兼容，必须提升合同版本，并触发依赖阶段重算。

首版阶段边界如下：

| 阶段范围 | 输入合同 | 输出合同 |
| --- | --- | --- |
| 资料接入 / 解析路由 / 解析执行 / 统一文档 | 原始文件、解析器配置、结构化解析结果 | 统一文档对象、章节/块/表格/列表锚点、解析元数据 |
| 证据构造 / 证据图谱切块 / 证据包 | 统一文档对象、块级锚点、抽取策略 | 证据片段、证据图谱、证据包、证据覆盖指标 |
| 概念审查 / 关系家族 / 定义冲突 | 证据包、候选概念、候选关系、归并策略 | 规范化候选项、关系家族、定义/摘要/冲突处理结果 |
| 规范知识 / 质量门禁 / 发布 API | 已归并候选项、证据链、质量策略 | 规范知识候选、规则命中、门禁决策、发布候选快照、治理确认状态 |

### 6.9 规则输入输出合同

`P1` 的规则不是只指质量门禁规则，也包括分块规则、证据选择规则、候选筛选规则、关系归并规则、定义冲突规则、规范化规则和发布边界规则。所有规则都必须具备可追溯的输入输出合同，不能只作为代码中的隐式判断存在。

每条规则必须声明：

- `rule_id`：稳定规则标识，同一含义不得复用不同 id。
- `rule_version`：规则语义版本，任意阈值、字段、动作或适用范围变更都必须升级。
- `stage_id`：规则所属阶段。
- `scope_selector`：规则适用的文档、块、对象类型、关系类型或发布范围。
- `input_schema`：规则读取的对象字段、指标字段、证据字段和上游依赖。
- `output_schema`：规则产生的结果字段，如 `passed / outcome / action / reason / produced_objects / updated_objects / rejected_objects / deferred_objects`。
- `effect_kind`：规则对知识的影响类型，至少区分 `filter`、`score`、`normalize`、`merge`、`split`、`block`、`publish_candidate`。
- `trace_fields`：必须写入运行态和审计日志的解释字段，包括输入摘要、关键阈值、命中原因、输出对象和影响范围。

规则执行后必须生成 `RuleExecutionRecord`：

```text
RuleExecutionRecord
- execution_id
- archive_id
- document_id
- stage_id
- rule_id
- rule_version
- rule_hash
- input_artifact_refs
- input_hash
- output_artifact_refs
- output_hash
- affected_object_ids
- affected_relation_ids
- decision
- metrics
- executed_at
```

`RuleExecutionRecord` 是后续规则变更重算、页面解释、质量门禁溯源和治理确认的共同依据。没有执行记录的规则命中结果不得进入正式发布候选。

### 6.10 规则变更后的动态重算与知识调整

策略或规则调整后，系统不能只保存新配置，也不能简单要求用户手动重新全量抽取。必须根据规则输入输出合同动态计算影响面，并对受影响知识执行增量重算。

规则变更处理流程如下：

1. 生成新的 `policy_snapshot`，记录变更前后的规则版本、规则哈希和配置差异。
2. 根据 `RuleExecutionRecord`、`dependency_selectors` 和知识对象溯源，计算 `ImpactSet`。
3. 将受影响的阶段快照、候选知识、关系、规则命中和发布候选标记为 `stale`。
4. 从最早受影响阶段开始重跑，未受影响阶段可复用原快照，但必须更新依赖版本指针。
5. 生成新的候选知识版本、关系版本和发布候选快照。
6. 前端运行态展示“规则变更 -> 影响对象 -> 重算阶段 -> 新旧差异 -> 当前发布/治理状态”。

`ImpactSet` 至少包含：

- `changed_rule_ids`
- `affected_stage_ids`
- `affected_document_ids`
- `affected_chunk_ids`
- `affected_candidate_ids`
- `affected_relation_ids`
- `affected_publication_snapshot_ids`
- `minimum_rebuild_stage_id`
- `requires_governance_reconfirmation`

动态知识调整规则：

- 尚未发布的候选知识可以直接被新规则重算结果替换，但必须保留旧候选版本和差异。
- 已发布为机器候选、但尚未治理确认的知识，必须生成新的候选快照，并把旧候选快照标记为被规则变更替代。
- 已治理确认并正式入库的知识不能被规则变更静默覆盖；必须生成新修订候选和差异说明，等待治理确认后再成为正式版本。
- 如果规则变更只影响展示排序、评分或非发布字段，可以局部更新索引/API 暴露结果，但仍需记录规则版本。
- 如果规则变更影响 `block / publish_candidate / merge / split` 等结构性动作，必须重跑相关阶段并刷新单文档图谱。

单文档页面需要配套显示：

- 当前运行使用的策略快照版本。
- 当前阶段每条规则的输入对象和输出对象。
- 规则变更后哪些节点/边被标记为过期。
- 哪些知识对象由新规则重算产生，哪些对象被保留、替换、拆分或阻断。
- 若需要治理重新确认，发布/API 阶段必须明确显示“新候选已生成，等待治理确认”。

### 6.11 可复用策略资产库与抽取绑定

阶段策略不能只作为某个知识库页面上的临时配置存在。`P1` 必须把规则与阶段策略提升为可复用、可版本化、可选择的“策略资产”，以支持同一类知识内容采集复用既有规则，也支持面向新的文件类型或知识类型复制并创建新策略。

策略资产分为三层：

- `PolicyPackage`：可复用策略包，描述策略名称、适用业务域、适用文件类型、适用知识类型、13 阶段配置、规则合同集合、AI 适配配置、默认质量门禁与发布边界。
- `PolicyPackageVersion`：策略包版本，锁定每个阶段策略、规则版本、规则哈希、模型配置和输出合同版本。
- `PolicyRuntimeSnapshot`：抽取启动时冻结的运行快照，绑定具体知识库、文档集合、策略包版本和运行参数。单文档运行态只能展示本次快照，不能被当前最新配置静默覆盖。

`PolicyPackage` 至少包含：

```text
PolicyPackage
- package_id
- name
- description
- business_domain
- knowledge_content_types
- document_type_selectors
- default_stage_order
- stage_policy_refs
- rule_contract_refs
- ai_adaptation_profile
- quality_gate_profile
- publication_profile
- owner
- lifecycle_status
- created_at
- updated_at
```

`PolicyPackageVersion` 至少包含：

```text
PolicyPackageVersion
- package_version_id
- package_id
- version_label
- version_status
- parent_version_id
- stage_policy_versions
- rule_versions
- rule_hashes
- model_profile
- change_summary
- compatibility_notes
- created_at
```

抽取启动时必须显式完成策略绑定：

1. 选择当前知识库默认策略包。
2. 从策略库选择已有策略包版本。
3. 复制已有策略包并另存为新策略包或新版本。
4. 根据文件类型、知识类型和历史效果由系统推荐策略包，但仍需用户确认。
5. 冻结为 `PolicyRuntimeSnapshot` 后再启动抽取。

策略变更规则：

- 修改已发布策略包不能原地覆盖历史版本，必须生成新版本。
- 已启动或已完成抽取的文档继续绑定启动时的 `PolicyRuntimeSnapshot`。
- 若用户希望新策略作用于已有知识，必须进入影响面计算与增量重算流程。
- 一个知识库可以设置默认策略包，但单次抽取任务允许覆盖默认策略。
- 同一批文档允许按文件类型或知识类型分配不同策略包，但运行态必须清楚展示每份文档实际绑定的策略快照。

页面需要支持：

- 策略库/策略模板管理：查看、复制、新建、归档策略包。
- 抽取启动策略选择：已有策略、复制改造、新建策略、系统推荐。
- 阶段策略配置：在某个策略包版本下编辑 13 阶段配置。
- 单文档运行态：展示策略包名称、策略包版本、运行快照 ID。
- 规则变更重算：从策略包版本差异计算影响面，而不是只比较页面表单值。

## 7. 治理、发布与发布态浏览

### 7.1 治理工作台

`P1.4` 的工作台必须支持：

- 候选项筛选
- 术语归并
- 关系修正
- 流程补链
- 批量审核通过 / 驳回
- 审核留痕与状态回显

### 7.2 文档钻取

文档页不是只展示文档条目，而必须能：

- 搜索已建库文档
- 打开文档详情抽屉
- 查看本文档关联知识
- 查看正式并入/移出状态和运行状态

### 7.3 发布态知识浏览

`P1.5` 正式浏览口径采用：

- 类型筛选：`实体 / 事件 / 流程`
- 视图切换：`列表 / 图谱`
- 来源文档筛选：`全部 / 指定文档集合`

页面必须让用户直接判断：

- 这个对象是什么
- 它属于什么类型
- 它跟谁发生关系
- 它由哪些文档支撑

## 8. 与后续节点的关系

`P1` 对 `P2` 只暴露发布态知识结果。

首版消费面至少包括：

- 已发布实体、事件、流程、规则、指标
- 单项详情
- 关系邻域
- 搜索与筛选能力
- 来源文档与证据回溯

`P2` 不允许直接读取：

- 候选知识
- 治理中间态
- 审核工作数据
- 内部脚本或文件组织细节

## 9. 风险与约束

首版重点风险包括：

- 知识仓退化为“文档切片库”
- 过度依赖自动抽取，弱化治理责任
- 长文档抽取覆盖不足
- 实体详情无法解释业务含义

对应控制口径：

- 坚持知识对象中心而不是文档片段中心
- 坚持证据门、一致性门、审核门、版本门
- 长文档坚持分块抽取与全局归并
- 发布态页面必须围绕“解释性”而不是仅围绕数量统计

## 10. 面向 P6 的展示输出接口

`P1` 面向 `P6` 的展示输出必须遵循 `P6DisplayExportContract v2`。该接口只服务 `P6` 观察门户和详情卡渲染，不改变 `P1` 的知识治理、发布和供给业务闭环。

| 合同分组 | `P1` 输出口径 | 展示绑定 |
| --- | --- | --- |
| `stage_overview` | 阶段身份、业务知识库名称、发布态知识供给状态、入口可用性和新鲜度 | 详情卡标题与健康状态；标题使用“业务知识库”，不把 `P1` 编号作为主视觉 |
| `connected_users` | 正在接入查询、治理、发布态浏览或知识供给的用户与角色 | 详情卡顶部方形积木用户轨，不显示添加符号 |
| `system_overall_metrics` | 已发布知识库数、已发布知识条目数、领域目录数、贡献者数等总体资产规模 | 详情卡中段总体状态 |
| `live_counters` | 当前正在入库、正在抽取、正在治理发布、正在向 `P2` 供给的数量或速率 | 详情卡下段实时状态 |
| `flow_ports` | 不单独绘制外部知识输入端口；右侧仅为 `P1 -> P2` 发布态知识输出，外部知识入库由 `queue_projection` 表达 | 输出端口与当前流量 |
| `queue_projection` | 外部知识挂载队列、治理发布队列或供给队列；必须包含顺序、当前位和完成后前移规则 | 底部挂衣钩式知识队列 |
| `display_binding` | 绑定 `DOC/CODEX_DOC/08_原型与附图/2026-04-30-005207-CodeFactoryV2-P6语义画布流动与P3P5补充原型-v17/` 中的 `P1` 卡片与挂载队列表达 | `P1` 详情卡 / 语义画布区域 |
| `source_trace` | 追溯到本文件第 3 至第 8 章，以及配套知识抽取、长文档治理、增量重建和发布态专题设计 | 字段来源、计算口径和展示原因 |

禁止口径：

- 不得把候选知识、治理中间态或审核工作量伪装成发布态总体资产。
- 不得把当前文档、当前抽取任务或当前审核任务放入 `system_overall_metrics`。
- `P1` 的阶段输出端口只连接 `P2`；不得为了视觉对称编造 `P3`、`P4` 或 `P6` 输出端口。
- `connected_users` 只表达实时接入用户，不表达手动添加入口。
