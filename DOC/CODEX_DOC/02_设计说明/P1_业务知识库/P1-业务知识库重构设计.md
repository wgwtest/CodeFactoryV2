# P1 业务知识库重构设计

## 1. 文档定位

本文是 `P1` 业务知识库重构的正式设计入口，用于指导后续前端、后端、接口合同、运行态图谱和系统间输出的模块化重构。

本设计遵循：

- `DOC/CODEX_DOC/02_设计说明/P1_业务知识库/P1-业务知识库设计.md`
- `DOC/CODEX_DOC/02_设计说明/P1_业务知识库/P1-知识质量与图谱质量保障设计.md`
- `DOC/CODEX_DOC/02_设计说明/00_总纲/03-P1-P6数据互联互通与平台交换层设计.md`
- `DOC/CODEX_DOC/03_规范与流程/01_数据规范/01-P1-P5到P6状态输出接口规范.md`
- `DOC/CODEX_DOC/07_过程文档/04_历史分析/2026-05-08-P1重构边界与实施整理.md`

本文不是替代原 `P1` 设计，而是在原设计基础上给出可落地的重构边界、模块拆分和实施约束。

## 2. 重构目标

### 2.1 用户目标

- 终端用户能用更少入口完成知识库创建、文档接入、抽取启动、抽取观察和知识结果查看。
- 终端用户不需要理解规则字段合同、运行快照、增量重算等后台概念，也能知道当前知识库是否可用、文档是否完成抽取、知识是否已发布。
- 单文档抽取工作台能解释抽取过程，但默认展示应简洁，复杂规则细节通过观察窗或策略后台进入。

### 2.2 工程目标

- 前端按 feature 边界拆分，终端用户页面、策略后台页面、治理发布页面和发布态浏览页面互不侵入。
- 后端按领域模块拆分，策略、规则执行、运行态、图谱投影、发布候选、系统间输出各自有清晰服务接口。
- 所有跨模块调用通过合同对象或 service interface，不允许读取其它模块内部临时状态。
- 保留现有可运行抽取功能，通过 adapter 逐步迁移到合同驱动主链。

### 2.3 图谱目标

- 图谱成为运行合同的可视化投影，而不是前端临时拼接的节点堆叠。
- 默认图谱表达“输入对象 -> 规则/动作依据 -> 输出对象”。
- 明细节点、证据、候选项、关系和规则命中通过点击或视图切换展开。
- 发布态图谱只展示正式入库知识，不展示运行中临时节点。

### 2.4 系统目标

- `P1 -> P2` 只输出发布态知识标准出口。
- `P1 -> P6` 只输出只读展示合同，不作为业务输出主链。
- 内部候选态、治理态、运行态、策略态不得泄漏为系统间正式输出。

### 2.5 质量目标

- 每次正式抽取都生成可追溯的 `KnowledgeQualityReport` 和 `GraphQualityReport`，说明知识概念与图谱关系为什么可信、哪里存在风险。
- 质量不只依赖最终人工感受，而由结构覆盖率、证据覆盖率、规则命中、概念重复/冲突、关系合法性、图谱连通性和人工评测集回归共同衡量。
- 质量门禁只负责执行当次策略决策，质量评测层负责解释“质量如何、为什么、是否比上一版更好或更差”。
- 发布给下游系统的正式知识必须带质量摘要和来源追溯，低于发布阈值的候选不得进入 `P1 -> P2` 正式供给。

## 3. 当前结构问题

### 3.1 前端问题

当前 P1 相关能力集中在少数大页面中：

- `ArchiveManagementPage.tsx` 同时承担知识库总览、文档选择、抽取启动、单文档运行、图谱、观察窗、策略配置等职责。
- `P1PrototypeWorkflowPages.tsx` 同时承载策略库、阶段策略、规则合同、差异、影响面、质量门禁和发布候选原型。
- 路由层把终端用户入口、策略后台、运行解释、治理发布和发布态图谱并列展示，普通用户难以判断主路径。

### 3.2 后端问题

当前 `archive_knowledge` 模块已经具备大量能力，但边界偏扁平：

- `runtime_service.py` 负责运行态聚合、阶段快照、图谱载荷和多类适配。
- `policy_config.py` 同时包含策略默认值、版本、校验和配置响应。
- 各阶段 `runtime_*` 文件有业务语义，但缺少统一 `StageExecutionContract` 适配层。
- 系统间输出尚未从运行态/发布态内部服务中独立出来。

### 3.3 合同问题

- 规则合同、阶段合同、运行快照和系统间输出合同还没有形成完整分层。
- 13 阶段仍容易被实现成硬编码流程，而不是默认流程蓝图。
- 前端图谱仍有较多业务推断，后端未完全提供稳定 `RuntimeGraphProjection`。

## 4. 重构总架构

### 4.1 分层架构

```text
终端用户层
  知识库总览 / 文档清单 / 单文档实时抽取

策略运维层
  策略包 / 策略版本 / 阶段策略 / 规则字段合同 / 影响面重算

运行执行层
  PolicyRuntimeSnapshot / StageExecutionContract / RuleExecutionRecord / RuntimeEvent

图谱投影层
  RuntimeGraphProjection / PublishedGraphProjection

质量评测层
  KnowledgeQualityReport / GraphQualityReport / EvaluationRunReport

库级归并层
  KnowledgeIdentityKey / KnowledgeMergeDecision / ArchiveKnowledgeResolutionSnapshot

治理发布层
  PublicationCandidateSnapshot / GovernanceConfirmation / PublishedKnowledgeSnapshot

系统间输出层
  P1KnowledgeSupplyExport -> P2
  P6DisplayExportContract.v2 / StageSnapshot -> P6
```

### 4.2 核心主链

```text
PolicyPackage
  -> PolicyPackageVersion
  -> PolicyRuntimeSnapshot
  -> StageExecutionContract
  -> RuleContract
  -> RuleExecutionRecord
  -> RuntimeGraphProjection
  -> KnowledgeQualityReport / GraphQualityReport
  -> ArchiveKnowledgeResolutionSnapshot
  -> PublicationCandidateSnapshot
  -> GovernanceConfirmation
  -> PublishedKnowledgeSnapshot
  -> SystemInteropExport
```

### 4.3 13 阶段定位

13 阶段保留，但定位调整为：

- 默认策略包的流程蓝图。
- 单文档运行态的兼容进度视图。
- 后端阶段处理器的默认实现集合。

13 阶段不再作为所有设计的硬编码中心。真正的执行边界应由 `StageExecutionContract`、`RuleContract` 和 `PolicyRuntimeSnapshot` 决定。

### 6.2 模块职责

| 模块 | 职责 | 不允许做 |
| --- | --- | --- |
| `intake` | 文档接入、归档、导入 | 生成知识结论 |
| `parsing` | 解析器选择、统一文档对象、解析元数据 | 读取策略后台内部状态 |
| `policy` | 策略包、版本、阶段策略、规则合同持久化 | 执行抽取 |

| `quality` | 知识质量、图谱质量、评测集回归和质量报告生成 | 直接修改抽取候选或正式知识 |
| `knowledge_resolution` | 同库跨文档同知识验证、合并、冲突处理和修订候选生成 | 静默覆盖正式知识 |
| `rebuild` | 影响面计算、增量重算任务 | 覆盖正式入库知识 |
| `publication` | 发布候选快照、API 暴露范围 | 绕过治理确认写正式知识 |
| `governance` | 治理确认边界适配 | 参与抽取运行细节 |
| `external_exports` | `P1 -> P2`、`P1 -> P6` 输出适配 | 泄漏候选态或运行态 |

## 9. 迁移策略

### 9.1 第一阶段：接口外壳与兼容层

- 新增 feature 目录和 contracts 目录。
- 新增新路由，但旧路由仍可访问。
- 后端新增 contracts 和 service interface，不迁移旧逻辑。
- 旧 API 通过 adapter 返回新合同字段的子集。

### 9.2 第二阶段：运行态合同统一

- 旧 13 阶段输出包装为 `StageExecutionContract`。
- Runtime stream 和 polling 返回同一 payload。
- 图谱改为消费 `RuntimeGraphProjection`。
- 运行态同时产出最小质量指标，至少覆盖结构覆盖率、证据覆盖率、规则命中和图谱投影可追溯性。

### 9.3 第三阶段：策略合同主驱动

- 抽取启动冻结 `PolicyRuntimeSnapshot`。
- 规则执行生成 `RuleExecutionRecord`。
- 质量门禁、发布候选和增量重算依赖规则执行记录。
- 质量评测层基于 `RuleExecutionRecord`、候选对象、证据锚点和图谱投影生成 `KnowledgeQualityReport` / `GraphQualityReport`。
- 库级归并层基于文档级候选、证据、规则执行记录和既有发布态知识生成 `ArchiveKnowledgeResolutionSnapshot`。

### 9.4 第四阶段：系统间输出收口

- `P1 -> P2` 只从 `PublishedKnowledgeSnapshot` 输出。
- `P1 -> P6` 只从 system output adapter 输出。
- 正式输出必须携带质量摘要，且不得输出低于发布阈值的候选对象。
- 正式输出的知识对象必须是库级规范对象，而不是单文档候选对象。
- 增加合同测试，防止内部状态泄漏。

## 10. 并行开发约束

每条工作线必须声明：

- 输入合同。
- 输出合同。
- 可调用 API。
- 不负责范围。
- 自动化测试。
- 人工验收路径。

禁止：

- 前端页面之间互相 import 作为业务依赖。
- 后端模块读取其它模块的未声明文件。
- 为了页面展示绕过 service interface 读取临时 JSON。
- mock fallback 未标记就展示为真实能力。

## 11. 验收标准

### 11.1 结构验收

- 前端 P1 功能按 `user / intake / policy / runtime / graph / quality / knowledge-resolution / governance / published` 拆分。
- 后端 P1 功能按 `contracts / policy / rule_engine / runtime / stages / graph_projection / quality / knowledge_resolution / publication / external_exports` 拆分。
- 所有旧路由都有兼容策略。

### 11.2 功能验收

- 能创建知识库、导入文档、启动抽取。
- 单文档页能显示实时阶段、Stream / polling 状态、策略快照、图谱和观察窗。
- 策略后台能管理策略包、规则字段合同和影响面。
- 发布阶段能区分机器候选、治理确认和正式入库。
- 质量评测能说明当前抽取结果的概念质量、关系质量、证据覆盖和图谱可用性。
- 同一知识库内不同文档的相同知识能被验证、合并、冲突处理和版本更新。

### 11.3 接口验收

- `P1 -> P2` 只输出发布态知识。
- `P1 -> P6` 满足 `P6DisplayExportContract.v2`。
- Stream 和 polling 返回等价运行态。
- 规则变更能生成 `ImpactSet`，但不覆盖正式知识。
- `KnowledgeQualityReport` / `GraphQualityReport` 能被运行页、治理页和系统间输出摘要复用。
- `ArchiveKnowledgeResolutionSnapshot` 能说明每个规范知识由哪些文档候选合并而来，以及是否是新增、合并、修订、冲突或拆分。

## 12. 非目标

- 不在本轮重写底层 Docling / LLM 抽取算法。
- 不把模块化单体拆成真实微服务。
- 不主动重做 P2 / P6 页面。
- 不把规则-only 结果伪装为正式结构化大模型抽取结果。
- 不把候选态、治理态或运行态输出给下游系统。
