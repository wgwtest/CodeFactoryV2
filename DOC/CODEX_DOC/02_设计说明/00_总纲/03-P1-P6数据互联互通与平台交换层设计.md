## 1. 设计结论

`CodeFactoryV2` 不应在当前阶段直接做成六套完全独立的微服务，也不应做成一个没有边界的大后台。

推荐架构是：

```text
模块化单体后端 + 平台交换层 + 分域数据边界 + 可拆服务部署路线
```

核心含义：

1. 当前和近期仍以一套 `codefactory-api` 承载 `P1 ~ P6` 的 API。
2. 六个分系统在代码、数据模型、接口和测试上保持清晰边界。
3. 跨系统互通不通过直接读写彼此内部表实现，而通过“冻结成果物 + 交换登记 + 只读投影 + 事件/任务”实现。
4. 平台需要一个共性后台能力，但它的职责是“交换、登记、审计、投影、版本治理”，不是替六个分系统承担业务逻辑。
5. 后续是否拆成独立服务，应基于发布频率、负载、团队边界、队列和数据契约成熟度判断，而不是在对象模型尚未稳定时提前拆。

## 2. 背景问题

当前 `P1 ~ P6` 的设计和测试大量依赖模拟数据源。这一做法有两个正面价值：

- 每个分系统可以独立开发、独立演示、独立验证。
- 上下游未完成时，当前阶段不被阻塞。

但真实应用中不能长期停留在“各自模拟”的状态。否则会出现：

- `P2` 已生成需求规格，但 `P3` 不知道该消费哪一份、哪一个版本、是否已冻结。
- `P3` 已生成模块工单包，但 `P4` 只能靠模拟入口生成类似数据，无法追溯真实来源。
- `P4` 已供给工具或组件，但 `P5` 不知道该取哪个清单、哪个构建版本、是否可用。
- `P6` 能展示五阶段状态，但状态来源可能仍是模拟口径，无法说明新鲜度和降级原因。

因此，当前要解决的关键不是“启动几套服务”，而是先回答：

- 每个阶段的权威输出是什么？
- 输出在什么时候从草稿变成冻结事实？
- 下游如何引用、消费、留痕和回放？
- 模拟数据与真实数据如何共用同一套契约？
- 哪些能力属于共性平台后台，哪些仍属于分系统内部？

## 3. 架构原则

### 3.1 标准成果物优先

跨阶段只传递标准成果物，不传递上游内部实现。

例如：

- `P2 -> P3` 传递冻结的 `RequirementSpec`。
- `P3 -> P4` 传递冻结的 `ModuleWorkorderBatchPackage`。
- `P4 -> P5` 传递可消费的 `ToolDeliveryManifest` 或供给快照。
- `P1 ~ P5 -> P6` 传递只读 `StageSnapshot` 或 `P6DisplayExportContract`。

下游不应依赖上游页面状态、临时脚本、草稿目录或私有数据库表。

### 3.2 分系统拥有自己的写模型

每个分系统只写自己的事实对象。

允许：

- 下游保存上游成果物的输入快照。
- 下游记录对上游成果物的消费状态。
- 平台交换层登记成果物元数据、版本、依赖关系和事件。

禁止：

- `P3` 直接修改 `P2` 的需求草稿。
- `P4` 直接修改 `P3` 的设计对象。
- `P5` 直接把问题写成 `P4` 修订命令。
- `P6` 反写任一阶段业务事实。

### 3.3 模拟源和真实源共用合同

`mock` 和 `live` 只能是数据源模式差异，不应形成两套对象模型。

要求：

- 模拟源必须产生与真实源相同的 DTO / schema。
- 真实源未接通时，接口必须显式标记 `source_mode=mock` 或返回 `501/未实现`。
- 不允许把模拟数据伪装成真实数据。
- 合同测试必须同时覆盖模拟源和真实源适配器。

### 3.4 先模块化单体，后按证据拆分

当前应优先把边界设计正确，而不是优先拆服务。

拆服务的前提应至少包括：

- 对外合同和版本策略已经稳定。
- 单一服务发布频率明显阻塞某个分系统。
- 某个分系统的任务队列、资源消耗或安全边界明显不同。
- 团队组织已经按分系统稳定分工。
- 具备日志、审计、追踪、幂等、补偿和回放能力。

在这些条件未满足前，六套后台会增加复杂度，不会自动提高架构质量。

## 4. 总体架构

### 4.1 近期推荐运行形态

```text
apps/web
  -> codefactory-api
       -> P1 domain
       -> P2 domain
       -> P3 domain
       -> P4 domain
       -> P5 domain
       -> P6 projection domain
       -> platform exchange domain
       -> worker runtime
  -> PostgreSQL
  -> object storage
  -> optional graph store
```

最小部署单元：

- `codefactory-web`
- `codefactory-api`
- `codefactory-worker`
- `postgres`
- `object-store`
- 可选 `neo4j`

这里的一套 API 不代表一套混乱业务后台，而是一个模块化单体。

### 4.2 后端分域

后端内部至少分为以下 bounded context：

| 分域 | 责任 | 是否拥有业务写模型 |
| --- | --- | --- |
| `P1 Knowledge Domain` | 文档接入、解析、抽取、治理、发布态知识 | 是 |
| `P2 Requirement Domain` | 建模草稿、需求规格、规格冻结 | 是 |
| `P3 Software Design Domain` | 设计订单、设计基线、软件设计说明、工单包 | 是 |
| `P4 Tool Hub Domain` | 工具需求、匹配、制造、供给、manifest | 是 |
| `P5 Build Domain` | 交付主单、装配尝试、导出目录、缺口反馈 | 是 |
| `P6 Projection Domain` | 阶段快照、门户投影、观察投影 | 只读聚合为主 |
| `Platform Exchange Domain` | 成果物登记、schema 版本、事件、消费记录、审计 | 是，但只写平台交换元数据 |

### 4.3 平台交换层定位

平台交换层不是第七个业务分系统，也不是“万能后台”。

它只负责：

- 登记跨阶段成果物。
- 管理成果物版本、schema 版本和冻结状态。
- 记录生产者、消费者、消费时间和消费结果。
- 保存事件 outbox 和幂等键。
- 为 `P6` 或其他只读视图提供可追溯的投影来源。
- 为后续拆服务提供稳定交换协议。

它不负责：

- 生成需求规格。
- 生成软件设计。
- 匹配工具。
- 执行构建。
- 代替 P6 解释业务语义。

## 5. 标准成果物模型

### 5.1 成果物信封

跨阶段传递的每个成果物都应包在统一信封中。

建议对象名：

```text
ArtifactEnvelope
```

最小字段：

| 字段 | 含义 |
| --- | --- |
| `artifact_id` | 平台内全局唯一成果物 ID |
| `artifact_type` | 成果物类型，例如 `requirement_spec` |
| `artifact_version` | 同一成果物的业务版本 |
| `schema_version` | 该类型成果物的 schema 版本 |
| `producer_stage` | 生产阶段，例如 `P2` |
| `producer_ref_id` | 生产阶段内部对象 ID |
| `lifecycle_status` | `draft / frozen / published / consumed / superseded / revoked` |
| `payload_mode` | `inline / object_ref / file_ref` |
| `payload_ref` | 大对象或文件的存储位置 |
| `payload_hash` | 内容校验和 |
| `parent_artifact_ids` | 上游成果物链路 |
| `source_trace` | 来源说明和证据链 |
| `idempotency_key` | 防重复发布键 |
| `created_at` | 创建时间 |
| `frozen_at` | 冻结时间 |
| `published_at` | 发布到交换层时间 |

### 5.2 消费记录

每次下游消费成果物时，必须记录消费事实。

建议对象名：

```text
ArtifactConsumption
```

最小字段：

| 字段 | 含义 |
| --- | --- |
| `consumption_id` | 消费记录 ID |
| `artifact_id` | 被消费成果物 |
| `consumer_stage` | 消费阶段 |
| `consumer_ref_id` | 下游内部对象 ID |
| `consumption_mode` | `snapshot / reference / subscription` |
| `accepted_schema_version` | 下游实际接受的 schema 版本 |
| `result_status` | `accepted / rejected / degraded / failed` |
| `result_message` | 消费结果说明 |
| `consumed_at` | 消费时间 |

### 5.3 阶段成果物清单

| 流向 | 标准成果物 | 生产阶段 | 消费阶段 |
| --- | --- | --- | --- |
| `P1 -> P2` | `PublishedKnowledgeSnapshot` 或发布态知识查询结果 | `P1` | `P2` |
| `P2 -> P3` | 当前实现态：`RequirementAuthoringDocument.frozen_package` / `P3DesignInputPackage`；结构化交换对象：`RequirementSpec`；目标交换层态：`ArtifactEnvelope<RequirementSpecPackage>` | `P2` | `P3` |
| `P3 -> P4` | `ModuleWorkorderBatchPackage` | `P3` | `P4` |
| `P3 -> P5` | `SoftwareDesignBaseline` | `P3` | `P5` |
| `P4 -> P5` | `ToolDeliveryManifest` / `ToolSupplySnapshot` | `P4` | `P5` |
| `P5 -> 外部交付` | `DeliveryCatalog` / `build-manifest.json` | `P5` | 交付目录 |
| `P1 ~ P5 -> P6` | `StageSnapshot` / `P6DisplayExportContract` | `P1 ~ P5` | `P6` |
| `P5 -> P3` | `P5GapRecord` / `FeedbackTask` | `P5` | `P3` 仲裁 |

## 6. 主链数据流设计

### 6.1 `P1 -> P2`

`P1` 不直接把内部知识库表暴露给 `P2`。

正式输入方式：

1. `P2` 通过发布态知识查询接口选择实体、流程、事件、规则和指标。
2. `P2` 在需求规格中保存所选元素的引用和必要快照。
3. 当 `P2` 冻结规格时，当前实现通过 `archive_ids`、`knowledge_binding` 和冻结包保留知识来源；目标交换层态再收敛为 `RequirementSpec.source_trace`。

首版可以用查询接口优先，不必强制把每次知识选择都注册成独立成果物。

当需要形成可重复回放的建模输入批次时，再登记：

```text
PublishedKnowledgeSnapshot
```

### 6.2 `P2 -> P3`

`P2 -> P3` 是当前需要优先深化的真实互通边界。该边界不能再简化描述为 `RequirementSpec -> P3Order`。

当前系统已经形成三层对象：

| 层级 | 对象 | 当前事实 | 设计含义 |
| --- | --- | --- | --- |
| 事项治理层 | `RequirementSpecWorkItem` | `P2` 需规管理入口对象，记录标题、初始输入、模板、知识绑定、工作文档、分析会话、发布规格、发布包、版本和 `p3_consumable` | 管理一份需求规格说明从创建、配置、发布到修订的生命周期 |
| 冻结事实层 | `RequirementAuthoringDocument.frozen_package` | `P2` 正式工作文档冻结后生成，包含 `standard_document`、`structured_spec`、`annotations`、`frozen_at`、`p3_consumable` | 当前 `P3` 真实消费的上游冻结事实源 |
| 结构化交换层 | `RequirementSpec` / `P3DesignInputPackage` | `RequirementSpec` 保存结构化规格；`P3DesignInputPackage` 是 `P3` 侧从冻结包派生出的输入适配包 | `RequirementSpec` 面向后续平台交换层，`P3DesignInputPackage` 面向当前 `P3 Design Lab` |

当前实现态流程：

1. `P2` 通过 `RequirementSpecWorkItem` 创建需规对象，并关联或创建 `RequirementAuthoringDocument`。
2. 用户通过专家工作台、表单、组织器建议和人工修订形成正式需求规格说明。
3. 发布到 `P3` 时，`P2` 对 `RequirementAuthoringDocument` 执行缺口检查和冻结，生成 `frozen_package`。
4. `P2` 从 `frozen_package.structured_spec` 创建 `RequirementSpec`，并在 `RequirementSpecWorkItem` 上记录 `published_requirement_spec_id`、`published_package_id`、`published_to_p3` 和 `p3_consumable=true`。
5. `P3` 通过 `/api/software-design-v2/input-packages` 读取 `P2` 冻结包列表，只接收 `frozen_package.p3_consumable=true` 的对象。
6. `P3` 将冻结包适配为 `P3DesignInputPackage`，用户选择后创建 `P3DesignLabSession`。
7. `P3DesignLabSession` 保存输入快照，并在后续生成 `design_document`、`SoftwareDesignBaseline v2`、`workorder_projection` 和 `frozen_package`。

目标交换层态流程：

1. `P2` 发布 `RequirementSpecPackage` 到平台交换层，由 `ArtifactEnvelope` 记录 `artifact_id`、`schema_version`、生产阶段、生命周期状态、hash、payload 引用和父级来源。
2. `P3` 不直接扫描 `P2` 内部表，而是按可消费成果物列表选择输入。
3. `P3` 消费时登记 `ArtifactConsumption`，并把 payload 快照转换为 `P3DesignInputPackage`。
4. `P3DesignLabSession` 持有上游 `artifact_id` 和输入快照，后续 `P2` 草稿或修订不影响已创建的设计会话。

关键约束：

- `P3` 只消费冻结且 `p3_consumable=true` 的 `P2` 输出。
- `P3` 不消费 `P2` 临时草稿。
- `P3` 不消费 `P2` 组织器会话、临时正文投影、Provider 原始日志或未确认批注。
- `P3` 不反写 `P2` 的 `RequirementSpecWorkItem`、`RequirementAuthoringDocument` 或 `RequirementAnalysisSession`。
- `P2` 规格被修订时，应产生新版本或新冻结包，不应原地覆盖已被 `P3` 消费的版本。
- 当前 `P3DesignInputPackage` 是过渡期适配对象，不等同于长期平台交换层的 `ArtifactEnvelope`。
- `P3Order` 不再作为 `P2 -> P3` 主接口术语；历史旧流程可以保留兼容说明，但新设计以 `P3DesignLabSession` 为承载对象。

当前 `P3DesignInputPackage` 至少应包含：

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `input_package_id` | `P3` 适配层生成 | 当前实现为 `p2frozen-{source_document_id}` |
| `source_document_id` | `RequirementAuthoringDocument.id` | 上游冻结文档 ID |
| `source_title` | `RequirementAuthoringDocument.title` | 上游需求规格说明标题 |
| `standard_document` | `frozen_package.standard_document` | 人类可读正式需求规格说明 |
| `structured_spec` | `frozen_package.structured_spec` | 结构化需求规格 |
| `annotations` | `frozen_package.annotations` | 冻结时的批注和检查提示 |
| `knowledge_binding` | `semantic_state.knowledge_binding` | 需求规格绑定的知识来源摘要 |
| `frozen_at` | `frozen_package.frozen_at` | 冻结时间 |
| `p3_consumable` | `frozen_package.p3_consumable` | 是否允许进入 `P3` |
| `related_designs` | `P3DesignLabSession` 汇总 | 同一输入包下已创建的软件设计说明列表 |

后续补齐平台交换层时，`P3DesignInputPackage` 应从 `ArtifactEnvelope.payload` 派生，而不是直接扫描 `RequirementAuthoringDocument`。

### 6.3 `P3 -> P4`

`P3` 的正式输出不是单一设计文档，而是冻结设计对象的下游投影。

流程：

1. `P3` 从 `RequirementSpec` 生成 `SoftwareDesignBaseline`。
2. 评审通过后冻结设计基线。
3. `P3` 生成 `ModuleWorkorderBatchPackage`。
4. `P3` 将工单包发布到平台交换层。
5. `P4` 依据该成果物创建 `ToolDemandSheet`。

关键约束：

- `P4` 只接收冻结后的模块级或子模块级工具化描述。
- `P4` 不读取 `P3` 设计草稿。
- `P3` 的 `push_to_p4` 不应只是修改本地状态，最终应形成可追溯的成果物发布和消费记录。

### 6.4 `P4 -> P5`

`P4` 提供给 `P5` 的不只是工具名称，而是可消费的交付 manifest。

流程：

1. `P4` 接收工单包并拆分工具需求项。
2. `P4` 完成匹配、审定、制造或登记。
3. `P4` 输出 `ToolDeliveryManifest` 或 `ToolSupplySnapshot`。
4. `P5` 根据 `artifact_id` 或 manifest 查询接口绑定供给输入。
5. `P5` 在装配尝试中保存供给快照。

`ToolDeliveryManifest` 至少说明：

- 工具形态：前端元组件、后端模块、服务接口、模板包。
- 包装类型：源码包、包管理依赖、HTTP 服务、目录模板。
- 集成方式：`import_component / include_router / call_http_api / mount_page`。
- 运行依赖。
- artifact locator。
- 合同摘要。
- 验证状态。

### 6.5 `P3/P4 -> P5`

`P5` 的正式输入由两类组成：

1. `P3` 的设计基线或工单关联。
2. `P4` 的工具供给结果。

`P5` 创建交付主单时，应绑定输入成果物版本。

要求：

- 一张 `P5DeliveryOrder` 必须能追溯到明确的 `RequirementSpec` 和 `SoftwareDesignBaseline`。
- 一次 `P5AssemblyAttempt` 必须保存输入快照。
- 导出目录的 `build-manifest.json` 必须写入输入成果物 ID、schema 版本和 hash。

### 6.6 `P5 -> P3` 回流

`P5` 发现的问题不能直接改写 `P4` 或 `P3` 的事实。

流程：

1. `P5` 生成 `P5GapRecord`。
2. `P5` 发布反馈成果物或反馈事件。
3. `P3` 作为设计仲裁点判断：
   - 是否属于设计缺口；
   - 是否属于工具供给缺口；
   - 是否属于构建装配缺口；
   - 是否需要重新签发设计或工单。
4. 若需要 `P4` 修订，应由 `P3` 重新签发新的工具供给目标。

这可以避免 `P5` 绕过设计仲裁直接驱动 `P4` 修改。

### 6.7 `P1 ~ P5 -> P6`

`P6` 只消费只读投影。

流程：

1. 每个阶段提供最小状态查询对象。
2. `P6.2` 归一化为 `StageSnapshot`。
3. `P6.2` 聚合为 `PortalProjection` 和 `ObservationProjection`。
4. `P6.1` 和观察页只消费平台投影。

关键约束：

- `P6` 不直接读取阶段内部数据库。
- `P6` 不抓取阶段页面私有状态。
- `P6` 不反写阶段业务对象。
- `P6` 的 `mock` 源和 `live` 源必须输出同一投影合同。

## 7. 平台交换接口建议

### 7.1 成果物接口

建议新增平台交换接口族：

```text
POST   /api/exchange/artifacts
GET    /api/exchange/artifacts
GET    /api/exchange/artifacts/{artifact_id}
GET    /api/exchange/artifacts/{artifact_id}/payload
POST   /api/exchange/artifacts/{artifact_id}/freeze
POST   /api/exchange/artifacts/{artifact_id}/publish
POST   /api/exchange/artifacts/{artifact_id}/consume
GET    /api/exchange/artifacts/{artifact_id}/consumptions
```

阶段内部可以继续保留自己的业务接口，但跨阶段正式交接应能回溯到上述成果物接口。

### 7.2 事件接口

首版不必引入复杂消息中间件，但应先建立 outbox 语义。

建议接口：

```text
GET    /api/exchange/events
POST   /api/exchange/events/{event_id}/ack
POST   /api/exchange/events/{event_id}/retry
```

事件类型建议：

- `artifact.published`
- `artifact.consumed`
- `artifact.superseded`
- `stage.snapshot.updated`
- `delivery.gap.reported`

### 7.3 Schema 注册

建议维护轻量 schema 注册表。

最小对象：

```text
SchemaDefinition
```

最小字段：

- `schema_id`
- `artifact_type`
- `schema_version`
- `json_schema`
- `status`
- `created_at`

首版可以先用 Pydantic 模型和文档约束，后续再落数据库注册表。

## 8. 数据存储形态

### 8.1 近期推荐

近期推荐使用：

```text
一个 PostgreSQL 实例 + 分域表/分域 schema + 对象存储
```

原因：

- 便于本地开发和部署。
- 避免六套数据库迁移和连接配置。
- 仍然可以通过代码边界、表名前缀或 DB schema 保持分域。
- 后续拆服务时，可以按交换层记录迁移数据所有权。

建议逻辑分区：

| 分区 | 内容 |
| --- | --- |
| `p1_*` | 知识库业务事实 |
| `p2_*` | 需求建模和规格事实 |
| `p3_*` | 软件设计事实 |
| `p4_*` | 工具仓库事实 |
| `p5_*` | 构建与交付事实 |
| `p6_*` | 平台投影和展示配置 |
| `exchange_*` | 成果物、schema、事件、消费记录、审计 |

大文件和导出目录不应塞入关系数据库，应放入对象存储或受控文件目录，并由 `payload_ref` 引用。

### 8.2 后续独立服务存储

当某个分系统拆成独立服务后，推荐转为：

```text
分系统自有数据库 + exchange API / event outbox
```

但拆分后仍应保持：

- 交换层合同不变。
- 成果物 ID 不变。
- 下游仍通过成果物引用消费，不直接读上游数据库。

## 9. 部署演进路线

### 9.1 阶段 0：当前验证态

特征：

- 一套 API。
- 多数分系统可用模拟数据验证。
- 部分事实存储在 `.data/` 文件目录。
- P6 `live` 未接通。

目标：

- 保持分系统独立测试能力。
- 不把模拟数据伪装成真实互通。
- 开始补齐交换层设计和合同测试。

### 9.2 阶段 1：真实互通 MVP

推荐部署：

```text
codefactory-web
codefactory-api
codefactory-worker
postgres
object-store
```

目标：

- 建立 `exchange_*` 元数据表。
- 打通 `P2 -> P3` 的真实 `RequirementSpec` 发布和消费。
- 打通 `P3 -> P4` 的真实工单包发布和消费。
- 打通 `P4 -> P5` 的真实 manifest 消费。
- 为 `P6` 提供 `live` 阶段快照适配器。

### 9.3 阶段 2：分角色部署

优先拆出 worker，不优先拆 API。

候选 worker：

- `p1-extraction-worker`
- `p4-runtime-worker`
- `p5-build-worker`
- `exchange-event-worker`

此阶段重点是把耗时任务、队列和后台执行从 API 请求线程中剥离。

### 9.4 阶段 3：按证据拆服务

只有当拆分条件成熟时，才考虑独立服务。

优先拆分候选：

1. `P4 runtime / manufacture service`
2. `P5 build execution service`
3. `P1 extraction service`
4. `P6 projection service`

`P2` 和 `P3` 的对象模型与人工评审流程更依赖主链上下文，可保留在主 API 更久。

## 10. 测试与验收策略

### 10.1 合同测试

每类标准成果物必须有合同测试：

- schema 必填字段测试。
- 版本兼容测试。
- hash / payload_ref 测试。
- 冻结后不可变测试。
- 下游消费记录测试。

### 10.2 分系统独立测试

各分系统继续保留模拟数据测试。

要求：

- mock fixture 使用正式 DTO。
- mock 结果能通过同一套 schema 校验。
- 不允许为了测试方便创建与 live 不一致的字段。

### 10.3 跨阶段集成测试

建议逐步建立以下链路测试：

1. `P2 -> P3`
   - 当前实现态：`RequirementAuthoringDocument.frozen_package / P3DesignInputPackage -> P3DesignLabSession`
   - 目标交换层态：`ArtifactEnvelope<RequirementSpecPackage> -> P3 消费记录 -> P3DesignLabSession`
2. `P3 ModuleWorkorderBatchPackage -> P4 ToolDemandSheet`
3. `P4 ToolDeliveryManifest -> P5 DeliveryOrder`
4. `P5 GapRecord -> P3 ArbitrationInput`
5. `P1 ~ P5 StageSnapshot -> P6 PortalProjection`

每条链路至少验证：

- 上游只发布冻结成果物。
- 当前实现态下游至少保存输入快照；目标交换层态再按 `artifact_id` 消费。
- 下游保存输入快照。
- 交换层保存消费记录。
- 重复消费具备幂等行为。

### 10.4 边界测试

需要增加负面测试：

- 下游不能消费 `draft` 状态成果物。
- 下游不能消费不兼容 `schema_version`。
- `P6 live` 未实现时不能静默返回 mock。
- `P5` 反馈不能直接形成 `P4` 修订命令。

## 11. 风险与控制

### 11.1 模块化单体退化成大泥球

风险：

- 一套 API 可能诱导跨模块随意调用内部 service。

控制：

- 按分域目录组织代码。
- 跨阶段只允许通过 exchange DTO 或阶段公开 application service。
- 增加 import 边界检查。
- 代码评审时把“直接读写其他阶段内部仓储”视为架构违规。

### 11.2 平台交换层变成万能后台

风险：

- 所有业务都塞进 exchange，导致新的中心化泥球。

控制：

- exchange 只保存元数据、事件、schema、消费记录和审计。
- payload 的业务解释权仍归生产阶段。
- exchange 不实现需求生成、设计生成、工具匹配或构建执行。

### 11.3 Schema 频繁变化导致下游不稳定

风险：

- P2/P3/P4 对象还在演化，过早强约束可能影响迭代。

控制：

- 使用 `schema_version`。
- 冻结成果物不可原地覆盖。
- 允许新版本并行存在。
- 下游声明支持的版本范围。

### 11.4 真实源与模拟源混淆

风险：

- 用户看到 P6 门户，以为已经接通真实链路。

控制：

- 所有投影返回 `source_mode`。
- P6 页面展示数据来源和新鲜度。
- `live` 未实现时返回明确未实现。
- 机测记录必须说明使用 `mock` 还是 `live`。

## 12. 首批落地建议

建议按以下顺序推进：

1. 持续确认 P6.2 与 `P1-P5 到 P6` 接口规范没有冲突标记，避免正式文档事实源不干净。
2. 新增 `Platform Exchange Domain` 的最小模型：
   - `ArtifactEnvelope`
   - `ArtifactConsumption`
   - `ExchangeEvent`
   - `SchemaDefinition`
3. 先打通 `P2 -> P3`：
   - 先把当前实现态文档和代码口径统一为 `RequirementSpecWorkItem -> frozen_package -> P3DesignInputPackage -> P3DesignLabSession`；
   - 以现有 API 测试验证冻结包消费、输入快照、关联软设、冻结和删除约束；
   - 再引入 `ArtifactEnvelope` / `ArtifactConsumption`，把 `P3` 从“扫描 `P2` 冻结文档”演进到“按平台交换层成果物消费”；
   - 保留 `RequirementSpec` 作为结构化交换对象，但不再把 `P3Order` 作为主接口承载对象。
4. 再打通 `P3 -> P4`：
   - `ModuleWorkorderBatchPackage` 发布；
   - `P4` 从成果物创建 `ToolDemandSheet`。
5. 再打通 `P4 -> P5`：
   - `ToolDeliveryManifest` 或供给快照发布；
   - `P5` 绑定真实供给输入。
6. 最后补 `P6 live`：
   - 从各阶段真实状态接口或 exchange 投影生成 `StageSnapshot`；
   - 保留 `mock` 作为演示和降级源。
