# 长文档块级编辑共性能力设计

> 本文件是 `CodeFactoryV2` 的总纲级共性能力设计文档，用于定义跨阶段复用的长文档块级编辑能力。
>
> 本能力首先服务 `P2 需求分析系统` 的需求规格说明正文和 `P3 软件设计系统` 的软件设计说明正文，后续可扩展到其他具有长文档投影、局部 AI 修订、人工确认和版本追溯要求的阶段。
>
> 本文件不属于 `BasePlatform_基础平台`。基础平台负责跨阶段已发布资源的登记、存储、追溯、版本治理和消费分发；长文档块级编辑属于阶段运行态编辑能力，可在实现上复用共享模块，但不得把阶段内部草稿、补丁提案和编辑过程直接上收为基础平台权威事实。

**日期：** 2026-05-22

**适用范围：**

- `P2` 需求规格说明正文、需求分析 Lab 临时正文和专家工作台正文修订。
- `P3` 软件设计说明正文、设计说明局部沟通和设计文档深化修订。
- 后续其他阶段的人类可读长文档投影。

**关联正式文档：**

- `DOC/CODEX_DOC/02_设计说明/00_总纲/00-软件工厂平台总体设计.md`
- `DOC/CODEX_DOC/02_设计说明/BasePlatform_基础平台/BasePlatform-平台数据资源底座设计.md`
- `DOC/CODEX_DOC/02_设计说明/P2_需求分析系统/P2-需求分析系统设计.md`
- `DOC/CODEX_DOC/02_设计说明/P3_软件设计系统/P3-软件设计系统设计.md`

## 1. 文档目的与设计口径

### 1.1 文档目的

本文用于回答以下问题：

1. 为什么长文档局部修订不能只作为 `P3` 的局部补丁功能实现。
2. `P2` 需规正文和 `P3` 软设正文如何复用同一套块级编辑抽象。
3. 前端选中块、输入修改意图、生成提案、预览差异、确认应用和刷新定位应如何闭环。
4. 后台应如何构造面向 Dify 或自研模型插件的编辑任务包。
5. AI 返回的结果应如何区分说明型建议、可执行补丁、整节替换候选和整文替换候选。
6. 后端应如何校验版本、定位锚点、应用补丁、记录审计和处理冲突。

### 1.2 设计口径

本文采用平台总纲级设计口径：

- 只定义跨阶段共性模型、协议、流程和边界。
- 不替代 `P2`、`P3` 各自的业务状态、正文模板、冻结流程和发布流程。
- 不要求首版一次实现所有操作类型，但必须保证模型可以从块级替换扩展到整节、整篇候选。
- 不把 AI 输出直接写入权威正文，所有可写入正文的变更都必须经过系统校验和人工确认。

### 1.3 一句话定位

长文档块级编辑能力是面向阶段内长文档投影的共享编辑引擎，用统一的文档块模型、编辑任务包、补丁操作协议、差异预览、人工确认和应用状态机，支撑需规、软设等长文档的局部 AI 修订和可追溯落稿。

## 2. 边界关系

### 2.1 与 BasePlatform 的关系

基础平台（Base Platform）只承接已冻结、已发布、可下游消费的标准资源副本。

长文档块级编辑能力处理的是阶段内部运行态：

- 草稿正文。
- 临时正文。
- 局部编辑任务。
- AI 补丁提案。
- 差异预览。
- 应用前冲突。
- 应用审计。

这些对象默认不进入基础平台权威资源表。只有当 `P2` 或 `P3` 完成冻结 / 发布后，阶段系统才把正式产物组装为平台资源，由基础平台登记和分发。

### 2.2 与 P2 的关系

`P2` 已有 `working_document.blocks`、`revision_fragments`、`document_patch` 和 `applied_block_ids` 等临时正文机制。该机制应收敛为长文档块级编辑能力的一种领域适配：

- `RequirementAnalysisWorkingDocumentBlock` 映射为 `LongDocumentBlock`。
- `document_patch` 映射为 `LongDocumentPatchProposal.operations`。
- `revision_fragments` 映射为 `LongDocumentRevisionFragment`。
- `target_anchor_plan` 映射为稳定锚点与落位计划。

`P2` 仍然拥有需求语义状态、规格树、模板约束和发布流程；共享编辑能力只负责正文投影的可控修订。

### 2.3 与 P3 的关系

`P3` 的软件设计说明不应另建一套孤立的局部补丁协议。`SoftwareDesignDescription` 应投影为 `LongDocument`，软件设计段落、章节和块的局部沟通应使用统一编辑任务包与补丁应用状态机。

`P3` 仍然拥有软件设计基线、功能树、分层架构、技术实现、展示形态和 `P4` 投影。共享编辑能力只负责软设正文及其正文锚点相关的落稿动作；涉及设计基线、功能树或架构结构的变更，必须通过 `P3` 自己的领域命令归并。

## 3. 统一文档模型

### 3.1 LongDocument

`LongDocument` 是阶段长文档进入编辑能力后的统一投影，不要求替代阶段权威存储。

```json
{
  "document_id": "p3-design-doc-001",
  "document_type": "software_design",
  "owner_stage": "P3",
  "title": "软件设计说明",
  "revision_id": "rev-0007",
  "outline": [],
  "blocks": [],
  "anchors": [],
  "revision_fragments": []
}
```

关键字段：

| 字段 | 说明 |
| --- | --- |
| `document_id` | 阶段内文档标识 |
| `document_type` | 文档类型，例如 `requirement_spec`、`software_design` |
| `owner_stage` | 所属阶段，例如 `P2`、`P3` |
| `revision_id` | 当前正文修订号，用于应用前冲突校验 |
| `outline` | 章节目录投影 |
| `blocks` | 连续正文块，是局部编辑的主要载体 |
| `anchors` | 稳定锚点集合，用于绑定章节、条款、段落和来源对象 |
| `revision_fragments` | 已应用修订片段，用于高亮、审计和回放 |

### 3.2 LongDocumentBlock

正文块是长文档编辑的最小可写入单元。

```json
{
  "block_id": "blk-0007",
  "section_id": "3.2",
  "anchor_path": "3/3.2/总体分层",
  "block_type": "paragraph",
  "display_heading": "3.2 总体分层",
  "text": "当前正文内容",
  "order_index": 320,
  "source_refs": ["REQ-3.1"],
  "domain_refs": ["module:planning-task"],
  "last_revision_id": "rev-0007"
}
```

块必须具备稳定身份，不能依赖 DOM 位置、数组下标或屏幕坐标。前端点击段落时只提交锚点，后台必须根据锚点重新读取当前块快照。

### 3.3 LongDocumentAnchor

锚点用于表达“这个块在文档和领域对象中的位置”。

```json
{
  "anchor_id": "anchor-p3-3.2",
  "anchor_type": "section",
  "section_id": "3.2",
  "block_id": "blk-0007",
  "anchor_path": "3/3.2/总体分层",
  "title": "3.2 总体分层",
  "domain_refs": ["architecture:layered-overview"]
}
```

`P2` 可把模板条款、规格节点和目标锚点规划映射为 `LongDocumentAnchor`。`P3` 可把软设章节、正文块、功能节点或架构节点引用映射为 `LongDocumentAnchor`。

## 4. 编辑任务包

### 4.1 任务包定位

面向 Dify 或自研模型插件的请求不得只包含用户输入和完整文档大 JSON。后台必须构造 `LongDocumentEditTaskPackage`，明确告诉模型：

- 当前要改哪里。
- 当前块和章节原文是什么。
- 允许输出什么粒度的修改。
- 返回内容应如何被系统落位。
- 哪些内容只能作为建议，不能自动写入正文。

### 4.2 LongDocumentEditTaskPackage

```json
{
  "task_id": "edit-task-001",
  "document_ref": {
    "document_id": "p3-design-doc-001",
    "document_type": "software_design",
    "owner_stage": "P3",
    "revision_id": "rev-0007"
  },
  "user_instruction": "请深化 3.2 总体分层，补充分层架构图可依托的文字设计。",
  "edit_intent": "expand_section",
  "scope_anchor": {},
  "target_snapshot": {},
  "context_bundle": {},
  "allowed_operations": [],
  "forbidden_operations": [],
  "output_schema_ref": "LongDocumentPatchProposal.v1"
}
```

### 4.3 目标快照

`target_snapshot` 至少包含：

- 当前选中块全文。
- 所属章节全文。
- 父章节摘要。
- 子章节列表。
- 前一块和后一块摘要。
- 当前锚点对应的领域对象引用。
- 当前版本号。

如果用户选中的是章节，目标快照必须包含该章节下全部正文块；如果选中的是整文，必须包含文档摘要、目录、关键章节摘要和可替换范围，不应盲目传整篇超长正文。

### 4.4 上下文包

`context_bundle` 根据阶段适配：

| 阶段 | 必须包含 |
| --- | --- |
| `P2` | 需求规格模板、当前规格树节点、需求语义状态摘要、目标锚点规划、相关来源事实 |
| `P3` | 软件设计基线摘要、功能树相关节点、分层架构摘要、技术实现摘要、来源需规引用 |

上下文包必须区分“全局摘要”和“目标全文”。全局摘要用于理解整体方向，目标全文用于生成可落位的补丁。

## 5. 补丁提案协议

### 5.1 LongDocumentPatchProposal

```json
{
  "proposal_id": "patch-001",
  "task_id": "edit-task-001",
  "base_revision_id": "rev-0007",
  "proposal_type": "executable_patch",
  "target_anchor": {},
  "operations": [],
  "preview": {},
  "quality_notes": [],
  "applicability": {
    "can_apply": true,
    "reason": "ready"
  },
  "status": "proposed"
}
```

`proposal_type` 固定为以下值之一：

| 类型 | 含义 | 是否可直接应用 |
| --- | --- | --- |
| `advice_only` | 只有修改建议、解释或质量提示 | 否 |
| `executable_patch` | 含可执行 operations | 是，需人工确认 |
| `section_replacement_candidate` | 整节替换候选 | 是，需强预览和人工确认 |
| `document_replacement_candidate` | 整文替换候选 | 是，需强确认和版本保护 |
| `needs_manual_merge` | 需要人工合并 | 否 |

### 5.2 操作集合

首版建议支持以下操作：

| 操作 | 说明 | 首版优先级 |
| --- | --- | --- |
| `rewrite_block` | 替换一个正文块 | 必须 |
| `insert_block_after` | 在目标块后插入新块 | 必须 |
| `split_block` | 将目标块拆成多个块 | 必须 |
| `delete_block` | 删除目标块 | 建议 |
| `merge_blocks` | 合并多个相邻块 | 建议 |
| `replace_section_blocks` | 替换某章节下的块集合 | 必须 |
| `rewrite_section` | 替换整节正文和子块 | 必须 |
| `replace_document_draft` | 替换整篇草稿 | 后续，必须强确认 |
| `update_trace_refs` | 更新追溯引用 | 必须 |
| `add_quality_note` | 增加质量提示 | 必须 |

`P2` 和 `P3` 可以按阶段能力声明实际支持子集，但字段和语义必须一致。

### 5.3 不合格输出处理

如果模型返回自然语言建议但没有 operations，系统不得把它显示为“可应用补丁”。前端应标记为：

```text
修改建议，未形成可应用补丁
```

并显示原因：

```text
当前结果缺少可执行 operations，不能写入正文。
```

这种结果可以进入轮次审计，但不能出现“应用到文档”按钮。

## 6. 应用状态机

### 6.1 状态集合

长文档编辑请求至少包含以下状态：

| 状态 | 含义 |
| --- | --- |
| `idle` | 未发起编辑 |
| `task_building` | 后台正在构造编辑任务包 |
| `proposal_generating` | 正在调用模型或插件生成提案 |
| `proposal_ready` | 已生成可审阅提案 |
| `proposal_invalid` | 返回内容不符合可应用协议 |
| `preview_ready` | 已生成差异预览 |
| `applying` | 用户确认后正在应用 |
| `applied` | 已写入阶段权威正文或临时正文 |
| `conflicted` | 文档版本或目标锚点已变化 |
| `manual_merge_required` | 系统无法自动合并，需要人工处理 |

### 6.2 状态转移

```text
idle
  -> task_building
  -> proposal_generating
  -> proposal_ready
    -> preview_ready
      -> applying
        -> applied

proposal_generating
  -> proposal_invalid

preview_ready
  -> conflicted
  -> manual_merge_required
```

任何进入 `applying` 的动作都必须来自用户明确确认。AI 生成提案本身不得直接改正文。

### 6.3 应用前校验

应用前必须校验：

1. `base_revision_id` 与当前文档修订号一致。
2. 目标文档存在。
3. 目标章节、目标块或目标锚点仍存在。
4. 每个 operation 在当前文档类型下受支持。
5. 对整节或整文替换，用户已看到差异预览并完成强确认。
6. 阶段领域约束允许该正文变更，例如 `P3` 是否需要同步设计基线。

## 7. 前端交互闭环

### 7.1 标准流程

前端长文档编辑交互固定为：

```text
选中文档块或章节
  -> Inspector 展示对象摘要和编辑入口
  -> 用户输入修改意图
  -> 后台生成编辑任务包并调用模型
  -> 前端显示提案卡片
  -> 前端显示差异预览和影响范围
  -> 用户确认应用
  -> 后台应用并返回 updated_document
  -> 前端刷新文档、目录、修订标记和审计记录
  -> 定位并高亮变更区域
```

### 7.2 提案展示规则

提案卡片必须明确显示：

- 提案类型。
- 影响范围：本块、本节、跨节、整文。
- 可应用性。
- 目标锚点。
- 版本号。
- 主要差异。
- 风险提示。
- 应用按钮或不可应用原因。

按钮文案必须与状态一致：

| 状态 | 主按钮 |
| --- | --- |
| 无提案 | `生成编辑提案` |
| `advice_only` | 无应用按钮，可提供 `重新生成可应用补丁` |
| `executable_patch` | `应用到文档` |
| `section_replacement_candidate` | `确认替换本节` |
| `document_replacement_candidate` | `确认替换整篇草稿` |
| `conflicted` | `重新生成提案` 或 `进入人工合并` |

### 7.3 前端不得做的事

前端不得：

- 直接拼接长上下文绕过后台任务包服务。
- 只在 DOM 上临时替换文本。
- 把没有 operations 的建议显示成可应用补丁。
- 在用户没有确认时自动应用。
- 依赖数组下标定位块。
- 在 `P2` 和 `P3` 分别发明不兼容的补丁 UI。

## 8. 后端服务划分

### 8.1 共性服务

实现时建议形成共享后端模块，但不要求首版独立微服务：

```text
apps/api/app/long_document_edit/
  models.py
  task_package_builder.py
  patch_normalizer.py
  patch_applicator.py
  diff_preview_service.py
  revision_service.py
```

职责如下：

| 服务 | 职责 |
| --- | --- |
| `TaskPackageBuilder` | 根据阶段文档和锚点构造编辑任务包 |
| `PatchNormalizer` | 归一化 AI 输出并判断提案类型 |
| `DiffPreviewService` | 生成块级、节级或整文差异预览 |
| `PatchApplicator` | 校验并应用可执行 operations |
| `RevisionService` | 生成修订号、修订片段和审计记录 |

### 8.2 阶段适配器

共享服务不直接理解所有阶段业务对象，阶段系统必须提供适配器：

| 适配器 | 负责 |
| --- | --- |
| `P2LongDocumentAdapter` | 需规正文、临时正文、规格树和目标锚点规划映射 |
| `P3LongDocumentAdapter` | 软设正文、设计基线、功能树、架构引用和来源需规映射 |

适配器负责把阶段权威对象投影为 `LongDocument`，并把已确认的正文变更归并回阶段自己的权威状态或临时状态。

## 9. 首版落地边界

首版应优先完成以下能力：

1. 统一 `LongDocument`、`LongDocumentBlock`、`LongDocumentPatchProposal` 和 operations schema。
2. 将 `P3` 当前局部补丁能力迁移到共性协议，补齐 `rewrite_section` 和 `replace_section_blocks`。
3. 将 `P2` 现有 `working_document` 机制映射到共性协议，但不立即重写全部 P2 逻辑。
4. 前端提案卡片统一区分“修改建议”和“可应用补丁”。
5. 应用成功后统一刷新、定位和高亮变更块。
6. 对 `document_replacement_candidate` 只做协议预留，不在首版默认开放。

首版不做：

- 独立长文档编辑微服务。
- 多人协同编辑。
- 富文本逐字级编辑器。
- 跨阶段自动写入。
- 基础平台保存阶段运行态补丁。

## 10. 验收口径

共性能力首版验收至少包括：

1. `P2` 与 `P3` 均能把自己的长文档投影为统一块模型。
2. 选中块后，后台构造的编辑任务包包含目标块、所属章节、相邻块、全局摘要和允许操作集合。
3. AI 返回 `operations=[]` 时，前端显示“修改建议，未形成可应用补丁”，且不显示应用按钮。
4. AI 返回合法 `rewrite_block` 时，用户确认后只替换目标块。
5. AI 返回合法 `replace_section_blocks` 或 `rewrite_section` 时，用户确认后替换目标章节，并刷新目录和正文。
6. 文档修订号变化时，应用动作进入 `conflicted`，不得静默覆盖。
7. 应用成功后形成修订片段、应用审计和前端高亮定位。
8. BasePlatform 不保存未发布的编辑任务、提案或补丁应用过程。

## 11. 设计结论

长文档块级编辑是平台总纲级共性能力，而不是 `P3` 的局部按钮功能，也不是基础平台的数据资源存储职责。

它的核心目标是让 `P2` 需规和 `P3` 软设共用同一套“选中对象 -> 构造任务包 -> 生成提案 -> 预览差异 -> 人工确认 -> 应用正文 -> 审计追溯”的闭环。只有这样，AI 局部修订才知道改哪里、怎么改、返回后放在哪里，也才能避免说明型建议、可执行补丁和整节整文替换混在一起造成误解。
