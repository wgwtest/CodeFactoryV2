# 节点合同与验收文种体系设计

## 1. 文档目标

本文件用于定义 `CodeFactoryV2` 平台研发层的目标文种体系，重点回答以下问题：

- `WBS树`、`研制计划`、`节点合同`、`验收大纲`、`验收记录`、`验收结论` 之间到底是什么关系
- 为什么 `研制计划` 与 `节点合同` 不能合并成同一类文档
- `设计说明`、`数据规范`、`关键流程` 在文种体系中应处于什么位置
- 当前正式文档根应向什么目标结构演进，才能既适合本项目长期协作，又尽量符合标准软件研发流程

本文件不是：

- 某个单一阶段的设计说明
- 某个单一节点的执行合同
- 某一轮验收记录

本文件属于平台研发层的文种体系设计文档，用于约束后续 `P1 ~ P6` 的正式文档组织方式。

## 2. 适用范围与定位

本文件适用于：

- `DOC/CODEX_DOC/` 作为 `CodeFactoryV2` 平台研发正式文档根的组织设计
- 各阶段、各层级 `WBS` 节点的执行与验收文种定义
- 后续 `CODEX_DOC -> JB_DOC` 投影前的本地正式文种收敛

本文件当前不直接解决：

- `JB_DOC` 标准投影层的最终文种展开
- 某个具体 `P6.1.1` 节点的执行细节
- 某个阶段的代码实现细节

本文件的正式定位为：

- `CodeFactoryV2` 平台研发层的文种体系设计基线

## 3. 与标准研发规范的关系

### 3.1 本体系不是标准原版目录

本体系不是对 `ISO/IEC/IEEE` 或 `DoD DID` 文种名称的逐一照抄。

本项目当前采用的正确口径应为：

- `CODEX_DOC` 是平台研发层的本地正式文档根
- `JB_DOC` 是标准化投影层
- `CODEX_DOC` 负责平台自身如何被研发、设计、执行、验收和追溯
- `JB_DOC` 负责把可标准化的成熟内容投影成更接近正式交付文种的对象

因此，本体系的目标不是“把 `CODEX_DOC` 伪装成标准原版文种包”，而是：

- 让 `CODEX_DOC` 具备标准兼容的工程控制逻辑
- 让后续标准投影有稳定来源，不再依赖聊天或临时草案

### 3.2 本体系吸收的标准控制点

本体系主要吸收以下标准控制意图：

- `ISO/IEC/IEEE 12207`
  - 生命周期过程
- `ISO/IEC/IEEE 15289`
  - 生命周期信息项与文档类型
- `ISO/IEC/IEEE 16326`
  - 项目管理计划内容
- `ISO/IEC/IEEE 29148`
  - 需求工程过程与需求信息项
- `ISO/IEC/IEEE 29119`
  - 测试文档与测试证据组织
- `IEEE 1016`
  - 设计说明的内容组织思路

本体系与上述标准的关系应表述为：

- 它是标准兼容型本地研发文种体系
- 它不是标准原版文种目录
- 它允许存在本地扩展文种，例如“节点合同”

### 3.3 本地扩展文种的必要性

“节点合同”不是现成的国际标准原生命名，但在本项目中是必要的本地扩展文种。

原因在于：

- `WBS树` 解决的是结构分解问题，不解决执行约定问题
- `研制计划` 解决的是子树组织问题，不解决单节点交付约定问题
- `测试文档` 解决的是验收问题，不解决执行目标定义问题

因此，在 `WBS -> 执行 -> 验收` 之间，必须增加一个正式的“节点合同”层作为桥接对象。

## 4. 核心对象边界

### 4.1 `WBS树`

`WBS树` 是结构事实源。

它回答的是：

- 项目如何分解为阶段、子阶段和叶子节点
- 父子节点关系是什么
- 同级节点顺序是什么

它不回答：

- 当前节点这一轮到底交付什么
- 具体如何验收
- 当前变更由谁回写

### 4.2 `研制计划`

`研制计划` 是对子树的稳定说明。

它回答的是：

- 这个节点及其下级子树为什么这样拆
- 子树当前边界是什么
- 当前推进重点在哪
- 下级节点如何分层组织
- 该子树依赖哪些正式设计说明和共享规范

它不应承担：

- 详细接口字段定义
- 详细验收步骤定义
- 单节点执行约定
- 单节点代码落点和轮次证据

因此，`研制计划` 的正确定位是：

- 子树组织文档

### 4.3 `节点合同`

`节点合同` 是单节点执行约定文档。

它回答的是：

- 这个节点本身要交什么
- 这个节点依赖什么
- 这个节点的成果物是什么
- 这个节点如何判定已完成
- 这个节点当前状态是什么

它不应承担：

- 替整棵子树做长篇拆解说明
- 代替专项设计说明写模块设计细节
- 代替验收记录沉淀证据

因此，`节点合同` 的正确定位是：

- 单节点执行合同

### 4.4 `验收大纲`

`验收大纲` 是稳定的验收基线文档。

它回答的是：

- 一个节点验收时应检查哪些内容
- 每项检查的入口、判据和通过条件是什么
- 哪些属于必须通过项，哪些属于条件通过项

它不应承担：

- 轮次证据记录
- 临时讨论结论
- 当前具体一次验收的过程细节

### 4.5 `验收清单`

`验收清单` 是面向人工验收的操作单。

它回答的是：

- 本轮或当前活跃验收入口应该按什么顺序检查
- 用户可观察动作和可见判据是什么
- 当前哪些节点处于待验收、待重测或已移出活跃列表

它不应承担：

- 稳定的长期验收基线定义
- 开发者自测命令与技术验证日志
- 对事实过程的完整取证

因此，`验收清单` 的正确定位是：

- 面向人工验收的活跃操作单

### 4.6 `验收记录`

`验收记录` 是某一轮、某一次、某一批验收的过程证据文档。

它回答的是：

- 这次验收是什么时间、针对哪个节点
- 用了什么环境、入口和样例
- 实际观察到了什么结果
- 哪些项通过，哪些未通过

因此，`验收记录` 是时间戳滚动文档，不是稳定基线文档。

### 4.7 `验收结论`

`验收结论` 是对某次验收结果的正式归并判断。

它回答的是：

- 节点当前是否可判定为通过
- 当前是否仅达到“已自测 / 待人工验收 / 已验收”
- 如未通过，还差什么

它与验收记录的区别在于：

- 验收记录偏事实过程
- 验收结论偏状态判断

## 5. `研制计划` 与 `节点合同` 的边界

### 5.1 二者不应合并

若把 `研制计划` 和 `节点合同` 合并为一个文种，会出现三个问题：

1. 父节点文档会吞掉子节点独立性
2. 节点文档会变成“子树总说明书”，失去单节点执行边界
3. 子树组织逻辑与单节点执行逻辑混在一起，后续维护时会反复漂移

因此，两者必须保留为不同文种。

### 5.2 包节点合同与叶子节点合同

节点合同在不同层级都存在，但侧重点不同。

#### 包节点合同

例如：

- `P6`
- `P6.1`

包节点合同主要关注：

- 包级能力闭环
- 对下级节点交付的依赖门
- 集成后的整体效果
- 包级验收标准

它不负责替每个子节点重写设计。

#### 叶子节点合同

例如：

- `P6.1.1`
- `P6.1.2`

叶子节点合同主要关注：

- 直接实现对象
- 直接成果物
- 直接验收口径
- 本节点约束与边界

### 5.3 推荐的职责切分

| 文种 | 主要回答 | 不应承担 |
| --- | --- | --- |
| `WBS树` | 怎么分解 | 怎么执行 |
| `研制计划` | 子树怎么组织 | 单节点怎么交付 |
| `节点合同` | 单节点怎么交付 | 子树为什么这样拆 |
| `验收大纲` | 应如何验 | 本次验了什么 |
| `验收清单` | 本轮怎么验 | 长期标准是什么 |
| `验收记录` | 本次验了什么 | 长期标准是什么 |
| `验收结论` | 当前是否通过 | 详细过程事实 |

## 6. `设计说明`、`数据规范`、`关键流程` 的组织关系

### 6.1 为什么它们不能并入节点目录

这三类文档中，有些无法与单个节点一一对应。

例如：

- 跨阶段状态输出接口规范
- 跨阶段共享枚举
- 平台级关键降级流程

这些对象天然是跨节点、跨阶段的共享依据，因此不适合放入单一节点目录。

### 6.2 三类文档的正确顺序

建议顺序为：

1. `设计说明`
2. `规范与流程`
3. `研制计划`
4. `节点合同`
5. `测试文档`
6. `过程文档`

含义如下：

- `设计说明`
  - 定义系统职责、对象模型、模块边界和架构选择
- `规范与流程`
  - 定义共享字段、接口、状态机、关键流程和规则
- `研制计划`
  - 把设计与规范映射到某棵 `WBS` 子树
- `节点合同`
  - 把某个节点收敛为执行约定
- `测试文档`
  - 对节点合同形成验收基线和证据
- `过程文档`
  - 记录协作过程、交接和意见处理

### 6.3 当前目录结构结论

- `03_规范与流程/`

  - 需要时继续扩展其他稳定专题子目录

相对于旧结构，核心变化是：

- 原 `研制计划` 顺位后移为 `04_研制计划/`

## 8. 节点级文种要求

### 8.1 必备规则

每个正式 `WBS` 节点至少应具备：

1. 节点合同
2. 验收大纲

每个进入人工验收或正式交付回合的节点，应继续具备：

3. 验收清单

每个实际发生取证和归并判断的节点，应继续具备：

4. 验收记录
5. 验收结论

### 8.2 研制计划的适用层级

`研制计划` 不要求所有叶子节点都单独拥有一份。

建议规则是：

- 项目总根必须有总研制计划
- 具有下级子树拆分的包节点应有对应研制计划
- 纯叶子节点通常不再单独建立研制计划，除非其下还存在稳定的继续拆分或专题化执行路径

因此：

- `P6` 应有研制计划
- `P6.1` 若作为稳定子树承载多个子节点，也应有研制计划或被纳入更细一级子树计划
- `P6.1.1` 作为叶子节点，通常不再单独建研制计划，而以节点合同为主

### 8.3 文件命名规则

建议节点稳定文档按 `WBS编码 + 节点名 + 文种名` 命名，例如：

- `06-P6-门户与平台入口-节点合同.md`
- `06.01-P6.1-首屏观察门户-节点合同.md`
- `06.01.01-P6.1.1-节点定义-节点合同.md`
- `06.01.01-P6.1.1-节点定义-验收大纲.md`

轮次证据文档则按 `时间戳 + WBS编码 + 节点名 + 文种名` 命名，例如：

- `2026-04-21-100900-06.01.01-P6.1.1-节点定义-验收记录.md`
- `2026-04-21-100900-06.01.01-P6.1.1-节点定义-验收结论.md`

## 10. 落盘与维护原则

### 10.1 当前结构已正式落盘

当前目录重构已经完成，正式目录以当前实际文件系统为准，不再保留旧目录作为并行正式入口。

当前执行要求是：

1. 新文档按现目录直接落盘
2. 历史文档保留原时间语义，但引用路径应持续更新到现目录
3. 远端 Issue / Project / PR 中的正式路径引用与本地目录保持一致

### 10.2 当前维护顺序

后续维护按以下顺序推进：

1. 先补齐各阶段的 `节点合同`
2. 再补齐对应 `验收大纲`
3. 再补齐人工验收所需的 `验收清单`
4. 对已进入正式验收回合的节点补齐 `验收记录 / 验收结论`
5. 持续修正文档索引、策略和远端协作面中的正式路径

### 10.3 验收文种并行边界

当前 `06_测试文档/` 中各子类边界如下：

- `01_自测报告/`
  - 开发者自测与技术验证
- `02_验收大纲/`
  - 节点级稳定验收基线
- `03_验收记录/`
  - 某次验收过程事实
- `04_验收结论/`
  - 对某次验收结果的归并判断
- `05_验收清单/`
  - 当前活跃人工验收入口与操作单

上述文种并行存在不是双轨混乱，而是职责分层。

## 11. 本轮结论

本轮结论明确如下：

1. `CodeFactoryV2` 平台研发层应采用“标准兼容型、本地扩展可控”的正式文种体系。
2. `WBS树`、`研制计划`、`节点合同`、`验收文档` 必须分层，不应合并为单一文种。
3. `节点合同` 是本项目必要的本地扩展文种，用于承接 `WBS -> 执行 -> 验收` 之间的桥接。
4. `设计说明`、`数据规范`、`关键流程` 应保留为上位专题文档，不进入节点目录。
5. 当前正式目录已经固化为 `03_规范与流程 / 04_研制计划 / 05_节点合同 / 06_测试文档 / 07_过程文档`。
6. `P6` 不再是唯一进入节点合同 / 验收大纲体系的阶段；`P1 ~ P5` 顶层阶段也已按同构方式落盘。
