# P1 业务知识库设计

> 归档说明：本文件归档自 `docs/superpowers/specs/2026-04-11-software-factory-platform-design.md`，并吸收 `2026-04-11-archive-document-drilldown-design.md`、`2026-04-11-archive-knowledge-review-editing-design.md`、`2026-04-12-openai-compatible-llm-adapter-design.md`、`2026-04-14-formal-archive-extraction-hard-gate-design.md`、`2026-04-14-long-document-formal-extraction-design.md`、`2026-04-15-document-incremental-knowledge-rebuild-design.md`、`2026-04-16-bilingual-knowledge-projection-design.md` 的正式口径，作为 `P1` 阶段的正式详细设计基线。

**日期：** 2026-04-19

**对应节点：**
- `P1` 业务知识库
- `P1.1` 功能验证平台底座
- `P1.2` 文档接入与结构化解析
- `P1.3` 候选知识抽取
- `P1.4` 知识治理与发布
- `P1.5` 已发布知识仓、查询与图谱展示

## 1. 设计目标

`P1` 的目标不是做一个“文档列表系统”或“只会展示节点数量的图谱页”，而是形成从业务资料到已发布知识仓的正式闭环，并向后续 `P2` 提供稳定、可解释、可追溯的业务元素出口。

`P1` 首版必须同时形成 5 类结果：

- 受控资料接入与结构化解析能力
- 正式知识抽取与候选知识持久化能力
- 人工治理、审核、发布与版本管理能力
- 发布态知识查询、图谱与流程浏览能力
- 面向 `P2` 的标准业务元素与证据回溯出口

## 2. 设计边界

### 2.1 首版负责

- 接收 `PDF / DOC / DOCX` 等业务资料
- 生成保留章节、块、页码、锚点的结构化解析结果
- 按统一 schema 抽取实体、事件、流程、规则、指标与关系
- 记录抽取来源、置信度、执行元数据和版本信息
- 提供术语归并、关系修正、流程补链、审核发布与审计记录
- 存储与查询已发布知识，并支持图谱/流程双视图验证

### 2.2 首版不负责

- 需求建模本身
- 软件设计对象生成
- 工具/组件命中与复用判断
- 最终软件运行装配

### 2.3 设计原则

- `P1` 只向下游暴露标准成果物，不暴露内部脚本和中间态
- `P1.1 -> P1.5` 严格串行推进，但节点之间通过契约解耦
- 正式抽取/重建链必须与预览/调试链明确分离
- 已发布知识必须可回答“它是什么、与谁相关、证据在哪、由谁贡献”

## 3. 节点结构

### 3.1 `P1.1` 功能验证平台底座

`P1.1` 是阶段一的前置使能层，不替代业务子系统，而是负责：

- 承载文档、抽取、治理、图谱等验证页面
- 提供统一任务状态、日志、错误透传和证据查看能力
- 提供统一详情抽屉、调试入口和 API 客户端

首版技术口径：

- 前端壳：`React + Vite + TypeScript`
- 页面路由：`React Router`
- UI：`Ant Design`
- 数据访问：`TanStack Query + Axios`
- 图形能力预留：`Cytoscape.js / React Flow`
- 端到端验证：`Playwright`

### 3.2 `P1.2` 文档接入与结构化解析

`P1.2` 只回答“文档怎样被受控接入并解析”，不直接给出知识结论。

标准成果物包括：

- 资料元数据、归档信息与版本信息
- 解析任务状态与错误记录
- 结构化片段、块边界、章节、页码、锚点与表格结果
- 解析执行元数据

首版技术口径：

- 正式解析器：`Docling`
- 复杂版面增强：`Unstructured`
- `DOC -> DOCX`：`LibreOffice Headless`
- 调试期轻量回退：`python-docx / PyMuPDF`

### 3.3 `P1.3` 候选知识抽取

`P1.3` 负责从 `P1.2` 的结构化片段中生成候选知识，不直接写入发布态知识仓。

标准成果物包括：

- 统一 schema 约束下的候选实体、事件、流程、规则、指标、关系
- `sourceRefs / confidence / extraction_run_id`
- 文档级正式抽取产物仓
- 双语投影增强元数据

### 3.4 `P1.4` 知识治理与发布

`P1.4` 是 `P1` 的产品质量中枢，负责：

- 术语统一与别名归并
- 关系修正与流程补链
- 候选项审核、驳回、发布与审计
- 文档级正式并入/移出与全集重算

### 3.5 `P1.5` 已发布知识仓、查询与图谱展示

`P1.5` 只消费已发布知识，不直接持有未治理候选项。

标准成果物包括：

- 发布态知识主存储
- 版本化快照与导出结果
- 实体/事件/流程浏览
- 图谱视图、流程链路视图、实体详情和来源对照

## 4. 子系统架构

`P1` 首版采用“模块化单体优先、按微服务边界设计”的形式落地，内部至少包含以下 6 个子系统：

### 4.1 资料接入子系统

职责：

- 接收、登记、归档、标记来源目录与版本
- 记录批次、标签、归属与审计信息

边界：

- 只解决“文档可控接入”
- 不直接产出知识结论

### 4.2 文档解析子系统

职责：

- 章节切分
- 页码与锚点定位
- 表格提取
- 图片/OCR 处理
- 形成可计算文档片段

边界：

- 输出的是结构化文档，不是已发布知识

### 4.3 知识抽取子系统

职责：

- 从结构化片段中抽取候选对象和关系
- 记录证据来源与置信度
- 生成文档级正式抽取产物

边界：

- 输出的是候选知识或文档级正式产物
- 不直接决定发布态

### 4.4 知识治理子系统

职责：

- 术语归并
- 关系修正
- 流程补链
- 审核发布
- 版本管理与审计

边界：

- 治理流程保证知识质量
- 不把模型结果直接等同于发布结果

### 4.5 知识仓与查询子系统

职责：

- 存储已发布知识
- 提供检索、关系查询、流程追踪与版本对比
- 提供图谱/流程双视图和证据回溯

边界：

- 只消费已发布知识
- 不直接持有未治理工作态

### 4.6 构建映射出口子系统

职责：

- 把发布态知识投影为 `P2` 可消费的业务元素
- 为后续建模提供对象、流程、事件和证据线索

边界：

- `P1` 只提供标准知识出口
- 不进入 `P2` 的需求建模内部

## 5. 核心知识对象模型

`P1` 的正式中心不是“文档片段”，而是可治理、可发布、可追溯的知识对象。

首版一等对象至少包括：

### 5.1 `Entity`

表示稳定领域对象，例如组织、角色、资源、事项、设备、单据、指标主体。

最小语义：

- `id`
- `name`
- `type`
- `aliases`
- `attributes`
- `sourceRefs`
- `version`

### 5.2 `Event`

表示可触发或已经发生的业务动作。

最小语义：

- `id`
- `name`
- `trigger`
- `actor`
- `targetEntity`
- `preconditions`
- `postconditions`
- `sourceRefs`

### 5.3 `Process`

表示有步骤、角色、输入输出和决策点的流程链路。

最小语义：

- `id`
- `name`
- `steps`
- `roles`
- `inputs`
- `outputs`
- `decisionPoints`
- `relatedRules`
- `relatedEvents`
- `sourceRefs`

### 5.4 `Rule`

表示制度、约束、阈值、判定条件和合规要求。

### 5.5 `Metric`

表示指标、统计口径、维度、周期和阈值。

### 5.6 `Relation`

表示对象之间的显式关系，例如：

- `entity-owns-entity`
- `event-changes-entity`
- `process-contains-step`
- `rule-constrains-process`
- `metric-measures-entity`

### 5.7 `Evidence`

每条已发布知识必须挂接证据，至少记录：

- 来源文档
- 页码 / 章节 / 块
- 原文片段
- 抽取方式
- 置信度
- 人工确认记录

### 5.8 `KnowledgeVersion`

首版必须支持至少以下状态：

- `draft`
- `pending_review`
- `published`
- `deprecated`

## 6. 正式知识抽取链

### 6.1 正式链与预览链分离

从设计上，`P1` 必须长期维持两类链路：

- 预览/调试链：允许容错，服务于排障与本地验证
- 正式抽取/重建链：必须执行严格约束，失败即失败

不能让预览结果冒充正式知识产物。

### 6.2 正式抽取硬约束

正式知识库抽取/重建必须满足以下规则：

- 正式解析必须使用 `Docling`
- 正式抽取必须使用结构化大模型
- 不允许静默降级到轻量解析器或规则-only 抽取
- 若 `Docling` 未生效、结构化大模型未生效或执行元数据缺失，整次任务必须失败
- 每次正式抽取必须生成执行报告，记录真实 `parser / provider / model / candidate_count / relation_count`

### 6.3 长文档正式抽取

长文档不能继续采用“少量采样片段代表全文”的方式。

正式策略固定为：

`结构化分块 -> 分块抽取 -> 全局归并 -> 治理 / 发布`

核心要求：

- 基于 `Docling` 章节、块、表格、列表构建语义块
- 多块分别执行规则抽取与结构化大模型抽取
- 文档级统一归并术语、别名、关系和证据
- 保留块级来源信息，至少能追溯到章节/块级证据

### 6.4 文档级正式产物仓

`P1.3.5` 的核心资产不是临时 JSON，而是文档级正式产物账本。

每篇文档至少应独立保存：

- 文档元数据
- 文档级候选知识
- 文档级关系贡献
- 抽取执行元数据
- `included_in_archive`

其意义是把“是否有正式产物”和“是否纳入当前正式全集”彻底解耦。

### 6.5 单文档正式并入 / 移出

`P1.4.5` 负责把文档级产物聚合为当前正式知识全集。

并入规则：

- 重新对目标文档执行正式抽取
- 替换旧正式产物
- 从文档级产物仓重算全集

移出规则：

- 保留文档级正式产物
- 只把 `included_in_archive` 置为 `false`
- 再由剩余纳入文档重算全集

### 6.6 双语知识投影

双语知识投影属于治理/展示增强层，不改变正式抽取主链。

首版增强字段包括：

- `中文主名`
- `英文原名`
- `缩写`
- `中文解释`
- `中文证据摘要`
- `中文化状态`

约束：

- 双语字段不能覆盖原始抽取原值
- 编号、工件号、缩写类对象保留原值，只补中文解释
- 不采用“全文先翻译再抽取”作为正式建库策略

### 6.7 结构化大模型适配层

`P1` 的正式抽取链允许切换主流大模型供应商，但不能把供应商名写死在抽取服务里。

因此正式设计要求存在独立的结构化 LLM 适配层，负责：

- Provider 配置
- 模型元数据显式声明
- OpenAI 兼容协议接入
- 统一结构化输出调用
- 错误标准化

这层是 `P1` 当前的抽取基础设施之一，也为后续 `P2 / P3 / P4` 的模型接入复用预留基础。

## 7. 治理、发布与发布态浏览

### 7.1 治理工作台

`P1.4` 的工作台必须支持：

- 候选项筛选
- 术语归并
- 关系修正
- 流程补链
- 批量审核通过 / 驳回
- 审核留痕与状态回显

### 7.2 文档钻取

文档页不是只展示文档条目，而必须能：

- 搜索已建库文档
- 打开文档详情抽屉
- 查看本文档关联知识
- 查看正式并入/移出状态和运行状态

### 7.3 发布态知识浏览

`P1.5` 正式浏览口径采用：

- 类型筛选：`实体 / 事件 / 流程`
- 视图切换：`列表 / 图谱`
- 来源文档筛选：`全部 / 指定文档集合`

页面必须让用户直接判断：

- 这个对象是什么
- 它属于什么类型
- 它跟谁发生关系
- 它由哪些文档支撑

## 8. `P1 -> P2` 正式接口

`P1` 对 `P2` 只暴露发布态知识结果。

首版消费面至少包括：

- 已发布实体、事件、流程、规则、指标
- 单项详情
- 关系邻域
- 搜索与筛选能力
- 来源文档与证据回溯

`P2` 不允许直接读取：

- 候选知识
- 治理中间态
- 审核工作数据
- 内部脚本或文件组织细节

## 9. 风险与约束

首版重点风险包括：

- 知识仓退化为“文档切片库”
- 过度依赖自动抽取，弱化治理责任
- 长文档抽取覆盖不足
- 实体详情无法解释业务含义

对应控制口径：

- 坚持知识对象中心而不是文档片段中心
- 坚持证据门、一致性门、审核门、版本门
- 长文档坚持分块抽取与全局归并
- 发布态页面必须围绕“解释性”而不是仅围绕数量统计
