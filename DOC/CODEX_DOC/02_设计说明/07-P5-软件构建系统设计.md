## 1. 设计目标

`P5` 的目标不是重新做需求分析、软件设计或工具治理，而是在 `P3` 与 `P4` 已给出正式输入的前提下，形成一次可运行、可导出、可回看、可追踪的最终软件装配与交付闭环。

`P5` 首版要解决的核心问题只有一件：

- 把 `P3` 冻结下来的实现路线，与 `P4` 已供给的资产结果，在一个独立工作台中完成装配、尝试、导出、缺口留痕和回流准备。

因此，`P5` 首版不是单纯的“导出按钮页面”，而是订单驱动的交付装配与运行验证工作台。

## 2. 设计边界

### 2.1 首版负责

- 接收 `P3` 冻结软件设计订单与结构化设计基线
- 接收 `P4` 已审定 / 已供给资产结果或工具订单结果
- 创建 `P5DeliveryOrder` 主单与 `P5AssemblyAttempt` 尝试单
- 在独立 `P5` 工作台中展示当前对象、当前运行状态与当前导出结果
- 输出版本化交付目录
- 对缺口、占位和反馈任务进行结构化留痕

### 2.2 首版不负责

- 重新定义 `P3` 冻结后的模块语义
- 直接修订 `P4` 平台级资产
- 跳过 `P3 / P4` 直接从页面草稿装配系统
- 直接把 `P5` 发现的问题当作 `P4` 的修订命令

### 2.3 首版对象约束

- 软件形态：`Web` 前后端工程
- 首版交付载体：本地独立交付目录
- 标准目录形态：`frontend/ + backend/ + deploy/ + docs/`
- 首版完成度：结构完整、关键代码与说明文件已生成，但允许存在带缺口的占位结果

## 3. 上下游关系与输入输出契约

### 3.1 上游输入

`P5` 只消费两类正式输入：

1. `P3` 的冻结设计对象
2. `P4` 的已审定 / 已供给资产结果

其中：

- `P3` 输入是主输入，负责定义唯一实现路线与模块语义
- `P4` 输入是辅助输入，负责提供可复用、可绑定、可供给的资产结果

在正式全链路完全接上前，`P5.1` 允许使用两类最小模拟输入：

- `P3` 冻结设计模拟输出
- `P4` 已供给资产模拟输出

### 3.2 输出结果

`P5` 输出的不是单一文件，而是三层语义一致的结果：

| 层次 | 正式对象 | 用途 |
| --- | --- | --- |
| 运行事实层 | `P5AssemblyAttempt` | 记录本次尝试的输入快照、装配结果、运行状态和验证结论 |
| 工作台投影层 | `P5BuildOverview / P5DeliveryOrderDetail` | 面向页面展示主单队列、运行态和结果预览 |
| 交付目录层 | `frontend / backend / deploy / docs` + `build-manifest.json` | 面向最终导出、交接与追溯 |

### 3.3 输出文件约束

每次尝试至少生成以下正式说明文件：

- `build-manifest.json`
- `docs/delivery-report.md`
- `docs/gap-list.md`

它们分别承担：

- 交付元数据与目录快照
- 本次构建构成与验证结论
- 缺口、占位点和回流建议

## 4. 首版业务闭环

`P5.1` 的首版标准闭环为：

`P3 冻结设计 / 模拟设计输入 -> P4 供给结果 / 模拟供给输入 -> 创建 P5 主单 -> 生成装配尝试单 -> 装配投影 -> 运行监控 -> 导出目录 -> 缺口留痕 -> 形成反馈任务`

关键约束如下：

- 一份冻结后的 `P3` 设计，对应一张 `P5` 交付主单
- 一张主单下允许多次装配 / 导出尝试
- 每次尝试都生成独立版本目录
- 首版装配策略为“复用优先，缺口占位”
- 带缺口的尝试可以导出，但不能标记为正式完成

## 5. 核心对象模型

### 5.1 `P5DeliveryOrder`

主单是 `P5` 的第一核心对象，用于承载交付对象、来源关系与整体状态。

最小语义至少包括：

- `delivery_order_id`
- `p3_order_id`
- `requirement_spec_id`
- `application_name`
- `requested_by`
- `notes`
- `status`
- `current_attempt_count`
- `formal_result_ready`
- `created_at`
- `updated_at`

### 5.2 `P5AssemblyAttempt`

尝试单是 `P5` 的第二核心对象，用于承载每次装配、运行和导出的事实结果。

最小语义至少包括：

- `attempt_id`
- `delivery_order_id`
- `sequence`
- `export_config`
- `input_snapshot`
- `assembly_plan`
- `runtime_snapshot`
- `validation_report`
- `output_preview`
- `gaps`
- `feedback_tasks`
- `export_directory`

### 5.3 `P5AssemblyPlan / P5AssemblyModule`

装配计划是 `P5` 的内部权威装配表达，用于沉淀：

- 当前业务模块列表
- 模块目标与说明
- 每个模块对应的 `frontend / backend / deploy / docs` 投影
- 已命中资产模块
- 占位模块
- 当前装配链路顺序

其中 `P5AssemblyModule` 至少包括：

- `module_id`
- `name`
- `objective`
- `target_directories`
- `binding_status`
- `bound_tool_id`
- `bound_tool_name`
- `gap_reason`

### 5.4 `P5RuntimeSnapshot`

运行快照是工作台“构建运行与监控区”的权威对象，应至少包括：

- `executor_name`
- `executor_status`
- `attempt_status`
- `progress_percent`
- `stages`
- `recent_logs`
- `block_reason`

### 5.5 `P5OutputPreview`

输出预览是工作台“输出结果预览区”的权威对象，应至少包括：

- `root_directory`
- `directories`
- `key_files`

### 5.6 `P5GapRecord / P5FeedbackTask`

缺口和反馈不是附属备注，而是结构化交付事实的一部分。

最小语义至少包括：

- 缺口类型：`design_gap / supply_gap / assembly_or_build_gap`
- 关联模块
- 缺口摘要与详细说明
- 反馈任务标题与详情
- 反馈任务状态

## 6. 独立工作台与页面级交互设计

### 6.1 壳层规则

`P5` 首版前端必须采用独立工作台壳层，不复用当前通用知识库顶部导航壳。

正式口径固定为：

- 不在顶部展示“知识库管理 / 文档导入 / 知识审核发布 / 知识图谱 / 需求规格 / 建模引导”这类跨阶段导航
- 当前工作对象、当前构建运行状态和当前导出结果，必须在同一工作台内可回看、可切换、可追踪
- `/build` 必须作为独立驾驶舱入口存在

### 6.2 工作台视觉风格

`P5` 的阶段级工作台视觉风格必须放在本文件固定，而不是下沉到 `P5.1` 节点文档中完整重复。

`P5.1` 及其后续节点只记录“继承 + 节点例外”。

`P5` 首版默认继承 `P4` 已正式固定的工作台视觉基线，当前正式口径固定为：

- 轻灰画布背景
- 浅色、半透明、轻浮层页头容器
- 白色高密度卡片与子卡片
- 分段标签式工作区切换
- 活动态使用低饱和莫兰迪实色面，不使用强渐变
- 阴影与描边保持克制，优先强调结构秩序

`P5` 同时增加以下阶段级限制：

- 不采用门户式顶部导航壳
- 不采用“深色英雄区 + 浅色工作区”的强分裂视觉
- 不把平台级入口风格误写进 `P5.1` 节点设计

允许的节点级局部例外只包括：

- 运行监控日志区可以使用更低明度的中性子面板
- 缺口区可以使用低饱和暖色提示面
- 输出目录预览区可以使用等宽字与轻控制台气质

### 6.3 首版页面结构

`P5` 首版页面由“一个独立工作台壳层 + 五个核心区块 + 一个联调输入副区”组成。

五个核心区块固定为：

1. 交付主单队列区
2. 装配流程主视图区
3. 构建运行与监控区
4. 输出结果预览区
5. 缺口与反馈区

联调输入副区用于展示当前设计输入与供给输入快照，作为首版最小联调能力的页面承载区。

### 6.4 交付主单队列区

该区承担“当前处理对象选择”的作用，至少应展示：

- `P5DeliveryOrder` 列表
- 来源 `P3` 订单标识
- 来源 `P4` 供给快照 / 工具订单结果标识
- 当前状态
- 最近一次运行结果

关键交互：

- 点击主单卡片切换当前工作对象
- 切换后，右侧所有主视图、运行态、输出结果和缺口信息必须同步切换

### 6.5 联调输入快照副区

该区用于显式展示本次工作对象当前消费的输入上下文，至少应展示：

- 冻结设计输入来源
- 设计基线标识
- 模块数量与模块名摘要
- 供给快照来源
- 供给工具数
- 当前已命中供给数

关键交互：

- 首版以只读为主
- 该区必须与当前 `attempt` 同步变化，不允许显示“上一张主单”的旧快照

### 6.6 装配流程主视图区

这是 `P5` 首版的核心区域。

至少应展示：

- 当前业务模块装配图
- 模块到 `frontend / backend / deploy / docs` 的投影
- 已命中资产模块
- 占位模块
- 当前装配链路顺序

关键交互：

- 已命中模块和占位模块必须有明显视觉区分
- 首版允许资产装配调整，但只允许在 `P4` 已审定 / 已供给资产中切换
- 不允许在 `P5` 中重新定义模块语义

### 6.7 构建运行与监控区

`P5` 首版不是静态页面，必须呈现最小运行态。

至少应展示：

- 当前运行单 / 尝试单状态
- 模拟执行器状态
- 关键进度节点
- 最近日志
- 成功 / 失败 / 阻塞原因

关键交互：

- 点击“发起构建尝试”后，应创建新的 `attempt`
- 新尝试创建后，该区必须立即切换到最新尝试的运行态
- 日志、阶段和阻塞原因必须来自当前 `attempt`，不得混入其他尝试结果

### 6.8 输出结果预览区

至少应展示：

- 导出目录结构预览
- `build-manifest.json`
- `delivery-report.md`
- `gap-list.md`
- 最近一次输出目录位置

关键交互：

- 页面应能回看最近一次导出根目录
- 关键文件状态应明确区分 `generated / generated_with_gaps / placeholder`
- 首版允许复制导出目录位置，但不要求内嵌文件编辑

### 6.9 缺口与反馈区

至少应展示：

- 当前缺口清单
- 缺口分类
- 反馈任务
- 回流目标说明

关键交互：

- 缺口必须和当前 `attempt` 对齐
- 反馈任务默认进入 `pending_confirmation`
- 首版只允许留痕与显示，不在页面内直接驱动 `P4` 资产修订

### 6.10 首版状态要求

页面必须显式处理三类状态：

- 空态
  - 没有主单时，必须提供“装载演示闭环”入口
- 加载态
  - 主单、详情或尝试加载时，必须保留明确加载反馈
- 错误态
  - 接口失败或运行失败时，必须显式提示，而不是静默留空

## 7. 运行、导出与验证规则

### 7.1 版本目录规则

同一张主单下，每次尝试生成独立版本目录，例如：

- `delivery-order-001/attempt-001/`
- `delivery-order-001/attempt-002/`

### 7.2 完成状态规则

- 无缺口时，主单可以标记为 `completed`
- 有缺口但已完成导出时，主单标记为 `exported_with_gaps`
- 有缺口的结果只能视为“带缺口结果”，不能视为正式完成

### 7.3 校验规则

首版正式采用以下校验口径：

- 静态结构校验
- 导出目录校验
- 本地构建校验的正式闭合放到 `P5.2`

## 8. 回流与仲裁规则

### 8.1 问题分类

`P5` 首版发现问题时，至少分为三类：

- 设计缺口
- 供给缺口
- 装配 / 构建缺口

### 8.2 回流仲裁

当前正式采用以下口径：

- `P5` 只输出交付可行性问题报告与反馈任务
- `P3` 是唯一回流仲裁者
- `P4` 不直接接受来自 `P5` 的业务不匹配修订命令

### 8.3 对 `P4` 的正式语义

更准确的表达不是：

- `P4` 承接 `P5` 的修订回流

而是：

- `P4` 承接 `P3` 发起的新供给任务 / 派生任务 / 组件拆分任务

因此，本轮正式口径固定为：

- `P4` 对 `P5` 保持非直接修订语义
