# P4 真实工具落地验证设计

**日期：** 2026-04-19

**对应节点建议：**
- `P4.5`
- `P4.5.1` 工具定义与交付契约升级
- `P4.5.2` 产物存储、版本与比对机制
- `P4.5.3` AI 生成链与模板执行链
- `P4.5.4` 前端元组件样例实现与验证
- `P4.5.5` `P3 -> P4 -> P5` 真实交付闭环验证

## 1. 设计目标

在 `P4.2 ~ P4.4` 已经证明“工具中台闭环可以跑通”的前提下，把 `P4` 推进到下一层：

- 不再只验证模拟对象流转
- 开始验证一个真实工具能否被生产、登记、校验、交付和消费

本轮最重要的纠偏结论是：

- `P4` 中的“工具”默认不是完整页面
- 也不是完整应用
- 而是一个**可复用、可组合、可交付的最小原组件**

## 2. 工具定义纠偏

### 2.1 默认工具口径

`P4` 的默认工具，应满足以下条件：

- 能被其他系统或更高层资产复用
- 有清晰输入输出契约
- 有稳定交付物
- 有明确宿主接入方式
- 有可验证的运行边界

因此，第一优先级工具应是：

- 前端元组件
- 后端模块
- 服务接口
- 模板包

### 2.2 不应默认等同于页面

页面、页面模板、业务页脚手架并非无效资产，但它们属于更高层级的复合资产。

如果在 `P4.5` 的第一批真实验证中直接选择页面级产物，会出现两个问题：

- 无法区分工具本体与宿主页面职责
- 无法回答“别的系统究竟如何复用它”

因此，本轮默认不选“整页生成器”作为第一样例。

## 3. 本轮选定样例

### 3.1 样例名称

`React + Ant Design 查询表格元组件`

### 3.2 样例定位

它不是：

- 独立 HTML 页面
- 完整查询页
- 自带路由的小应用
- 自带后端的一体化系统

它是：

- 一个可被宿主前端项目 `import` 的前端元组件包
- 一个带显式 `props contract`、交付清单、验证报告和版本信息的真实工具

### 3.3 选择理由

选择这个样例，是因为它能同时验证 `P4` 的五个关键问题：

- 工具是否有明确形态
- 工具是否有明确宿主约束
- 工具是否有明确交付产物
- 工具是否有明确接入方式
- 工具是否有明确验证方式

相比“页面生成器”，它更能体现 `P4` 对最小可复用资产的治理能力。

## 4. 与 React / Ant Design 的关系

### 4.1 运行依赖

本样例工具运行时依赖：

- `react`
- `react-dom`
- `antd`

### 4.2 依赖策略

本轮推荐策略：

- `dependency_policy = peer`

含义是：

- 工具本体依赖 `React + Ant Design`
- 但不把这两个库打包进工具自身产物
- 由宿主项目自行提供这两个依赖

原因：

- 避免多份运行时副本
- 降低体积
- 降低版本冲突风险
- 更符合“元组件被宿主嵌入”的真实使用方式

### 4.3 对宿主的要求

宿主项目至少需要满足：

- 使用 `React`
- 使用与工具兼容版本范围内的 `Ant Design`
- 提供基础样式上下文
- 具备接入该组件所需的 API 调用能力或数据适配层

因此，这个工具不是“离开宿主也能独立跑的页面”，而是“由宿主项目承载的可嵌入组件”。

## 5. 工具消费方式

本样例的标准消费方式应为：

```tsx
import { QueryTableWidget } from "@p4-tools/query-table-widget";
```

宿主系统负责：

- 放到哪个页面
- 用什么布局承载
- 路由如何进入
- 权限如何控制
- 外层 API 如何适配

工具本体负责：

- 查询表格的通用呈现
- 筛选条件与列定义约束
- 组件级事件与最小交互契约

## 6. 交付物定义

本样例工具至少应交付：

- 组件源码包或构建产物
- `manifest.json`
- `props schema`
- 类型定义
- 版本号与 hash
- 示例宿主接入样例
- 验证报告

其中 `manifest.json` 至少应表达：

- `tool_form`
- `tool_granularity`
- `packaging_type`
- `integration_mode`
- `dependency_policy`
- `runtime_dependencies`
- `artifact locator`
- `contract version`

## 7. 数据与存储建议

### 7.1 权威事实存储

当 `P4` 进入真实工具交付阶段后，建议把权威事实逐步迁移到数据库，而不再长期停留在纯 JSON 演示模式。

当前推荐：

- 业务事实主存储：`PostgreSQL`
- 投影与缓存：可继续保留轻量只读投影
- 产物仓：文件系统或对象存储

### 7.2 产物仓建议

第一版可采用本地产物仓：

- `.data/tool_hub/artifacts/`

至少存放：

- 组件源码包
- 构建产物
- `manifest.json`
- 校验报告
- 比对快照

## 8. AI 生成链建议

### 8.1 基本原则

本轮不建议让大模型直接自由生成整份页面。

更合理的路径是：

- 大模型产出结构化 `ToolRecipe`
- 模板执行器依据 `ToolRecipe` 生成元组件骨架
- 本地验证器执行类型检查、构建和宿主接入 smoke test
- 通过后再登记为正式 `artifact version`

### 8.2 推荐方式

本轮建议采用：

- `LLM 负责结构化设计`
- `模板链负责稳定落码`
- `验证链负责准入`

这样可以避免第一版就进入“完全自由代码生成”的高漂移模式。

## 9. 建议节点拆分

建议新增一级节点：

- `P4.5` 真实工具落地验证

建议下挂子节点：

- `P4.5.1` 工具定义与交付契约升级
  - 固定“最小工具”的正式语义
  - 升级 `ToolDefinition / ToolFetchManifest`
- `P4.5.2` 产物存储、版本与比对机制
  - 固定产物仓、版本对象、diff 机制
- `P4.5.3` AI 生成链与模板执行链
  - 固定 `ToolRecipe -> Generator -> Validator`
- `P4.5.4` 前端元组件样例实现与验证
  - 实作 `QueryTableWidget`
- `P4.5.5` `P3 -> P4 -> P5` 真实交付闭环验证
  - 从 `P3-sim` 发出真实需求
  - `P4` 生成、登记、校验、交付
  - `P5` 查询并消费真实产物

## 10. 第一版验收口径

本轮如果要算“真实工具落地验证通过”，至少应满足：

1. `P3-sim` 能提交一个前端元组件需求
2. `P4` 能生成并登记该元组件的真实产物
3. 产物有显式 `manifest`、契约和版本信息
4. 工具明确声明自己依赖宿主提供 `React + Ant Design`
5. 宿主样例能够成功 `import` 并完成最小渲染
6. `P5` 能通过 `delivery manifest` 获取该工具并理解如何消费

## 11. 当前结论

`P4.5` 的第一批真实落地验证，推荐从“前端元组件”开始，而不是从“整页生成器”开始。

原因不是前端页面不重要，而是：

- 元组件更符合 `P4` 对“工具”的默认语义
- 更容易清楚界定宿主边界
- 更容易做版本、比对、接入和验证
- 更适合作为后续更高层页面资产的基础单元
