# P1-P5 到 P6 状态输出接口规范

## 1. 规范定位

本规范用于统一 `P1 ~ P5` 面向 `P6` 输出平台级状态事实时的最小接口契约。

本规范解决的问题不是“各阶段内部怎么实现”，而是：

- 各阶段至少要向 `P6` 暴露哪些正式状态字段
- 这些字段的语义、更新时间和来源应该如何表达
- `P6` 如何把这些字段收敛成统一的门户节点状态负载和观察投影

本规范是跨阶段共享规范，优先级高于 `P6` 页面实现细节。

若 `P1 ~ P5` 的任何阶段、任何分系统需要向 `P6` 暴露平台级状态输出，必须遵循本规范。

## 2. 适用范围

本规范适用于以下场景：

- `P6.1` 首屏观察门户的系统状态卡节点
- `P6.2` 跨阶段只读集成与状态投影
- 平台串行观察页
- `P6.4` 展示实验对阶段状态投影的消费

本规范当前不覆盖：

- 各阶段内部业务编辑接口
- 各阶段内部页面私有状态
- `P6` 对 `P1 ~ P5` 的写接口
- 登录与权限语义

## 3. 职责分工

### 3.1 阶段侧职责

`P1 ~ P5` 各阶段必须负责：

- 生产本阶段的正式状态事实
- 明确状态字段来源
- 提供可查询的正式只读接口
- 在具备条件时提供订阅接口

阶段侧不得把以下内容推给 `P6` 决定：

- 本阶段主状态的真实语义
- 核心指标的真实含义
- 更新时间和采集时间
- 入口是否可用的事实判断

### 3.2 平台侧职责

`P6` 必须负责：

- 固定平台最小消费字段
- 把各阶段事实映射成统一快照
- 形成门户节点状态负载
- 标注新鲜度、降级原因和告警摘要

平台侧不得：

- 伪造阶段事实
- 根据页面表现反推阶段状态
- 绕过正式读接口直接读取阶段内部数据库
- 直接抓页面私有状态作为正式事实源

## 4. 查询接口统一契约

每个阶段至少需要提供以下 4 类查询对象：

1. `StageOverview`
2. `StageEntryProjection`
3. `StageMetricProjection`
4. `StageHealthProjection`

### 4.1 `StageOverview`

最小字段固定为：

- `stage_id`
- `stage_name`
- `primary_status`
- `summary`
- `updated_at`

字段要求：

- `primary_status` 必须表达当前平台级主状态
- `summary` 必须是一行可供平台直接显示的摘要
- `updated_at` 必须是该阶段状态事实最近稳定更新时间

### 4.2 `StageEntryProjection`

最小字段固定为：

- `entry_route`
- `entry_available`
- `entry_reason`

字段要求：

- `entry_route` 是稳定入口路由，而不是临时调试 URL
- `entry_available` 是布尔型正式事实
- `entry_reason` 在入口不可用时必须可读

### 4.3 `StageMetricProjection`

最小字段固定为：

- `metric_key`
- `metric_label`
- `metric_value`
- `metric_trend`

字段要求：

- `metric_key` 应稳定可编程消费
- `metric_label` 应直接用于平台显示
- `metric_value` 必须已归一为平台可显示值
- `metric_trend` 首版允许为空

### 4.4 `StageHealthProjection`

最小字段固定为：

- `health_level`
- `health_message`
- `health_source`
- `captured_at`

字段要求：

- `health_level` 统一使用 `healthy / warning / blocked / unknown`
- `health_message` 应为平台用户可直接理解的句子
- `captured_at` 是健康事实采集时间，不等同于 `updated_at`

## 5. 平台统一骨架字段

所有阶段面向 `P6` 的状态输出，至少要能映射出以下统一骨架字段：

- `stage_id`
- `stage_name`
- `primary_status`
- `summary`
- `entry_route`
- `entry_available`
- `updated_at`
- `freshness`
- `health_level`

这些字段属于平台必需字段。

任何阶段若当前无法完整提供，必须明确标注缺失项和临时替代方案，不能静默省略。

## 6. 五阶段差异字段规范

统一骨架之外，各阶段必须补齐本阶段最关键的差异字段。

### 6.1 `P1` 业务知识库

必须额外提供：

- `knowledge_base_name`
- `latest_publish_status`
- `published_knowledge_count`
- `source_document_count`
- `graph_entry_available`
- `latest_publish_at`

### 6.2 `P2` 需求分析系统

必须额外提供：

- `active_requirement_batch_name`
- `requirement_spec_status`
- `active_requirement_count`
- `modeled_requirement_count`
- `requirements_entry_available`
- `latest_analysis_at`

### 6.3 `P3` 软件设计系统

必须额外提供：

- `active_design_order_name`
- `design_freeze_status`
- `design_review_status`
- `active_design_order_count`
- `review_pending_count`
- `software_design_entry_available`
- `latest_review_or_freeze_at`

### 6.4 `P4` 工具仓库

必须额外提供：

- `active_supply_snapshot_name`
- `tool_demand_status`
- `tool_evolution_status`
- `active_supply_snapshot_count`
- `tool_demand_open_count`
- `toolhub_entry_available`
- `latest_supply_or_scan_at`

### 6.5 `P5` 软件构建系统

必须额外提供：

- `active_delivery_order_name`
- `latest_attempt_status`
- `gap_status`
- `active_delivery_order_count`
- `review_pending_attempt_count`
- `build_entry_available`
- `latest_delivery_or_review_at`

## 7. 节点状态负载映射规范

`P6` 平台层面向门户节点和阶段观察卡，不直接消费阶段原始对象，而是消费统一的 `StageNodeStatusPayload`。

### 7.1 `StageNodeStatusPayload`

最小字段固定为：

- `stage_id`
- `headline_value`
- `summary_line`
- `metric_items`
- `entry_badge`
- `health_badge`
- `timestamp_label`
- `degraded_hint`

### 7.2 字段映射要求

- `headline_value`
  - 显示阶段当前最重要的主对象或主状态
  - 例如当前知识库、当前需求批次、当前设计单、当前供给快照、当前交付主单
- `summary_line`
  - 显示一行阶段摘要
- `metric_items`
  - 固定显示 2 到 4 个核心指标
- `entry_badge`
  - 用于表达入口可用性
- `health_badge`
  - 用于表达健康度或阻塞度
- `timestamp_label`
  - 用于表达“最近更新时间”或“最近稳定时间”
- `degraded_hint`
  - 在数据降级或回退时显示

### 7.3 五阶段映射建议

| 阶段 | `headline_value` | `metric_items` 推荐 |
| --- | --- | --- |
| `P1` | 当前知识库名称 / 最新发布状态 | 已发布知识规模、来源文档规模 |
| `P2` | 当前需求建模批次 / 规格状态 | 活跃需求数、已建模需求数 |
| `P3` | 当前设计单 / 冻结状态 / 评审状态 | 活跃设计单数、待评审数 |
| `P4` | 当前供给快照 / 需求单状态 / 演进状态 | 供给快照数、开放需求单数 |
| `P5` | 当前交付主单 / 最近尝试状态 / 缺口状态 | 活跃交付单数、待批阅尝试数 |

## 8. 订阅接口规范

当阶段具备订阅能力时，推荐统一输出事件包络：

- `event_type`
- `stage_id`
- `timestamp`
- `payload`
- `source`

首版推荐事件类型：

- `stage_status_changed`
- `metrics_changed`
- `health_changed`
- `entry_changed`
- `alert_created`

订阅接口是增强能力，不替代查询接口。

任何阶段不得只提供事件流而不提供可查询的当前稳定状态。

## 9. 新鲜度与降级规范

所有阶段输出都必须支持平台判断：

- 当前数据是否新鲜
- 当前数据是否过期
- 是否允许回退到上次稳定快照

### 9.1 新鲜度字段

至少需要可推导出以下字段：

- `captured_at`
- `updated_at`
- `freshness`
- `stale_after_ms`

其中：

- `captured_at` 用于表示事实采集时间
- `updated_at` 用于表示稳定状态最近更新时间
- `freshness` 统一使用 `fresh / stale / unknown`

### 9.2 降级字段

当阶段接口异常时，至少需要支持平台形成以下信息：

- `degraded_reason`
- `fallback_level`
- `last_stable_snapshot_ref`

平台消费方必须能区分：

- 无数据
- 数据暂不可用
- 过期快照

## 10. 响应结构建议

查询接口推荐统一采用如下包络：

```json
{
  "data": {
    "overview": {},
    "entry": {},
    "metrics": [],
    "health": {}
  },
  "meta": {
    "stage_id": "p3",
    "captured_at": "2026-04-20T14:20:00Z"
  }
}
```

其中：

- `data` 承载阶段事实
- `meta` 承载阶段身份和采集元数据

## 12. 验收要求

一个阶段要宣称“已具备面向 `P6` 的状态输出能力”，至少必须满足：

1. 能提供正式查询接口。
2. 查询接口可覆盖统一骨架字段。
3. 已补齐本阶段差异字段。
4. 平台能够据此映射出 `StageNodeStatusPayload`。
5. 能明确区分无数据、数据暂不可用和过期快照。
6. 所有字段都有稳定语义来源，而不是页面层临时拼装。
