# P1 业务知识库重构边界与实施整理

## 1. 整理目的

本文件用于把当前 `P1` 业务知识库的重构方向收束到正式设计文档口径下，避免继续围绕单个页面、单个图谱效果或某个阶段补丁零散推进。

本轮重构唯一目标：

- 让知识库功能更容易被终端使用者理解和操作。
- 让知识生成过程由可配置规则合同驱动，而不是被固定 13 阶段页面形态绑死。
- 让生成的知识图谱更能表达“输入对象 -> 规则/动作依据 -> 输出对象 -> 证据/状态”。
- 让知识概念质量和图谱质量可度量、可解释、可回归，而不是只靠人工主观观察。
- 让同一知识库内不同文档的相同知识能够被验证、合并、冲突处理和版本更新。
- 在不破坏现有抽取功能的前提下，逐步接入策略包、规则字段合同、运行快照和增量重算能力。

## 3. 当前主要偏差

### 3.1 产品入口偏差

当前页面更像后台运维和二次开发控制台，终端用户会被大量策略、规则、快照、运行合同、质量门禁细节干扰。

需要拆成两层：

- 终端用户层：知识库、文档、抽取进度、抽取结果、可理解图谱。
- 策略运维层：策略包、规则合同、字段合同、版本差异、影响面、增量重算。

### 3.2 前端模块偏差

当前 `ArchiveManagementPage.tsx` 和 `P1PrototypeWorkflowPages.tsx` 承载过多职责，导致：

- 路由含义不够清楚。
- 终端页面与策略后台页面混在一起。
- 图谱数据拼装、运行态展示、策略配置和抽取启动耦合过深。
- 后续继续改会让页面越来越难维护。

### 3.3 后端模块偏差

当前 `apps/api/app/archive_knowledge` 已经具备策略、运行态、质量门禁、发布候选、阶段快照等能力，但目录仍然过于扁平：

- 阶段处理器、策略配置、规则执行、运行态聚合和图谱投影混在同一层。
- 13 阶段仍然是强实现骨架，而不是可配置流程蓝图。
- 新规则合同已经开始出现，但还没有彻底成为抽取流程的主驱动。

### 3.4 图谱语义偏差

当前图谱已经比早期节点堆叠更好，但还没有完全做到“图谱是运行合同的投影”。

目标图谱不应该由前端临时猜测节点，而应该由后端基于以下数据统一投影：

- `input_artifacts`
- `output_artifacts`
- `rule_set_refs`
- `RuleExecutionRecord`
- `dependency_selectors`
- `runtime_snapshot`

### 3.5 质量保障偏差

当前实现已有质量门禁和规则命中，但仍不足以回答“提取的知识和图谱到底好不好”：

- 质量门禁偏执行决策，不能替代完整质量评测。
- 缺少统一的概念质量、关系质量、证据覆盖和图谱拓扑指标。
- 缺少固定评测集回归，无法比较策略、模型或规则变更后质量是否提升。
- 系统间输出缺少质量摘要，后续系统无法判断 P1 供给的可信度。

### 3.6 库级归并偏差

当前设计已有“文档级候选”和“全局归并”的方向，但还缺少一等合同来回答同一知识库中不同文档的相同知识如何处理。

必须补齐：

- 跨文档同知识识别，不只按名称去重。
- 多文档证据合并和可信度提升。
- 同名异义、定义冲突、关系冲突的明确决策。
- 正式知识更新不能静默覆盖，必须生成修订候选和治理确认。
- 发布态图谱节点应是库级规范知识，而不是单文档候选节点。

## 4. 重构后的产品分层

### 4.1 终端用户入口

面向普通业务用户，只回答三件事：

- 我有哪些知识库？
- 哪些文档正在抽取或已经形成知识？
- 这份文档当前抽取到哪里，生成了哪些可信知识？

建议页面：

- 知识库总览与抽取启动页。
- 知识库文档清单与文档选择页。
- 单文档实时抽取工作台。

这些页面应默认隐藏规则字段、合同校验、版本差异等工程细节，只保留必要状态提示。

### 4.2 策略运维入口

面向后台运维、策略管理员和二次开发者，负责维护可复用策略资产。

建议页面：

- 策略库与策略模板管理页。
- 阶段策略配置页。
- 规则字段配置与合同编辑页。
- 策略版本与规则差异页。
- 规则变更影响面与增量重算页。

这些页面可以展示策略包版本、规则字段合同、`RuleExecutionRecord`、`ImpactSet` 和增量重算任务。

### 4.3 治理与发布态入口

治理确认和发布态知识图谱属于 `P1.4 / P1.5` 边界。当前用户负责重点不是这部分，后续重构只保证接口和跳转边界清楚，不主动重做页面。

建议处理：

- 保留现有 `/governance` 和 `/graph` 作为独立入口。
- 单文档发布阶段只展示“机器已发布候选 / 等待治理确认 / 正式入库状态”。
- 不在抽取工作台里混入治理编辑能力。

## 6. 后端目标模块边界

当前不建议拆微服务，仍然采用“模块化单体”。但内部目录需要按设计边界重组。

建议后端领域模块：

```text
archive_knowledge/
├─ intake/                 # 文档接入、归档、导入
├─ parsing/                # 解析器、统一文档对象、解析元数据
├─ policy/                 # PolicyPackage、版本、规则合同、字段合同
├─ rule_engine/            # 规则执行、合同校验、RuleExecutionRecord
├─ runtime/                # 运行快照、stream、polling、事件流
├─ stages/                 # 阶段处理器适配层
├─ graph_projection/       # 运行态图谱和发布态图谱投影
├─ quality/                # 知识质量、图谱质量、评测集回归
├─ knowledge_resolution/   # 同库跨文档同知识验证、合并、冲突处理、修订候选
├─ rebuild/                # ImpactSet、增量重算任务
├─ publication/            # 发布候选快照、API 暴露范围
├─ governance/             # 治理确认边界适配
├─ external_exports/        # P1 -> P2 标准出口与 P1 -> P6 展示合同
└─ repositories/           # 文件仓储或未来数据库仓储
```

公共 API 可以先不大改，内部先通过适配层重组，降低一次性风险。

## 7. 核心合同主链

重构后的抽取主链应围绕以下合同运行：

```text
PolicyPackage
  -> PolicyPackageVersion
  -> PolicyRuntimeSnapshot
  -> StageExecutionContract
  -> RuleContract
  -> RuleExecutionRecord
  -> RuntimeGraphProjection
  -> KnowledgeQualityReport / GraphQualityReport
  -> ArchiveKnowledgeResolutionSnapshot
  -> PublicationCandidateSnapshot
  -> GovernanceConfirmation
  -> PublishedKnowledgeSnapshot
  -> SystemInteropExport
```

### 7.1 PolicyPackage

可复用策略包，描述适用业务域、文件类型、知识类型、阶段配置、规则合同集合、AI 适配配置、质量门禁和发布边界。

### 7.2 PolicyPackageVersion

锁定一个可运行版本。任何阈值、字段、动作、范围或规则语义变化都必须生成新版本，不能原地覆盖已发布版本。

### 7.3 PolicyRuntimeSnapshot

抽取启动时冻结的运行快照。单文档运行态只能展示本次快照，不能被当前最新策略配置静默覆盖。

### 7.4 StageExecutionContract

阶段处理器合同，至少包含：

- `stage_id`
- `input_artifacts`
- `output_artifacts`
- `rule_set_refs`
- `dependency_selectors`
- `idempotency_key`
- `runtime_snapshot`

### 7.5 RuleContract

规则合同，至少包含：

- `rule_id`
- `rule_version`
- `rule_hash`
- `stage_id`
- `scope_selector`
- `input_schema`
- `output_schema`
- `effect_kind`
- `trace_fields`
- `action_mapping`

### 7.6 RuleExecutionRecord

规则执行记录是解释、图谱、质量门禁、增量重算和治理确认的共同依据。没有执行记录的规则命中结果不得进入正式发布候选。

### 7.7 SystemInteropExport

系统间输出适配层。它不是新的业务事实源，只负责把 `P1` 内部已经确认的正式知识、系统状态和展示摘要转换为下游系统约定的接口合同。

## 8. 系统间输出接口硬边界

`P1` 不是孤立系统。重构后所有内部模块无论如何拆分，最终对外输出必须严格遵守系统间接口合同。

本章节是后续重构的硬约束：内部运行态、候选态、治理态、策略态可以演进，但对 `P2` 和 `P6` 的输出口径不能被页面实现或阶段实现随意改变。

### 8.1 权威接口事实源

系统间输出必须同时遵循：

- `DOC/CODEX_DOC/02_设计说明/P1_业务知识库/P1-业务知识库设计.md`
- `DOC/CODEX_DOC/02_设计说明/00_总纲/03-P1-P6数据互联互通与平台交换层设计.md`
- `DOC/CODEX_DOC/03_规范与流程/01_数据规范/01-P1-P5到P6状态输出接口规范.md`

其中 `P1` 正式设计定义业务边界，`P1-P6` 交换层设计定义跨系统数据原则，`P1-P5 到 P6` 状态输出接口规范定义平台观察合同。

### 8.2 P1 -> P2：正式业务输出

`P1 -> P2` 是业务主链输出，输出对象只能是发布态知识。建议命名为 `PublishedKnowledgeSnapshot` 或 `P1KnowledgeSupplyExport`。

首版消费面至少包括：

- 已发布实体、事件、流程、规则、指标。
- 单项详情。
- 关系邻域。
- 搜索与筛选能力。
- 来源文档与证据回溯。
- 版本号、新鲜度、来源快照和治理确认信息。

禁止对 `P2` 暴露：

- 候选知识。
- 治理中间态。
- 审核工作数据。
- 单文档运行态图谱。
- 规则后台内部配置。
- 内部脚本、缓存文件或阶段临时文件路径。

实现边界：

- `P2` 只能通过 `P1` 的发布态查询或标准出口消费知识。
- `P1` 不能让 `P2` 直接读取 archive 内部目录、runtime snapshot 或 publication candidate 临时文件。
- 已发布版本必须可追溯到治理确认记录和来源证据，但追溯信息也要通过标准字段输出。

### 8.3 P1 -> P6：只读展示输出

`P1 -> P6` 不是业务主链输出，而是平台观察输出。它必须遵循 `P6DisplayExportContract.v2`、`StageSnapshot` 和相关归一化对象。

至少要能输出：

- `StageOverview`
- `StageEntryProjection`
- `StageMetricProjection`
- `StageHealthProjection`
- `P6DisplayExportContract.v2`

`P1` 面向 `P6` 的差异字段必须强调：

- 知识资产规模。
- 发布状态。
- 外部知识入库队列。
- 对 `P2` 的知识供给。

`P1` 在 `P6DisplayExportContract.v2` 中的关键口径：

- `system_overall_metrics` 只能放已发布知识库数、已发布知识条目数、领域目录数、贡献者数等总体资产规模。
- `live_counters` 可以放当前正在入库、正在抽取、正在治理发布、正在向 `P2` 供给的数量或速率。
- `flow_ports` 右侧只能表达 `发布态知识 -> P2`，不得追加 `P3 / P4 / P6` 等牵强端口。
- `queue_projection` 用于表达外部知识挂载队列、治理发布队列或供给队列。
- `source_trace` 必须能说明字段来源、计算口径和设计依据。

禁止口径：

- 不得把候选知识、治理中间态或审核工作量伪装成发布态总体资产。
- 不得把当前文档、当前抽取任务或当前审核任务放入 `system_overall_metrics`。
- 不得把 `P6` 当成 `P1` 的业务输出端口。
- 不得为了视觉对称编造 `P1 -> P3`、`P1 -> P4` 或 `P1 -> P6` 业务流。

### 8.4 内部合同与系统间合同的关系

内部合同服务于可解释抽取和并行开发，系统间合同服务于后续系统消费。两者不能混同。

```text
内部运行合同：
PolicyRuntimeSnapshot / StageExecutionContract / RuleExecutionRecord / RuntimeGraphProjection

发布候选与治理合同：
PublicationCandidateSnapshot / GovernanceConfirmation / PublishedKnowledgeSnapshot

系统间输出合同：
P1KnowledgeSupplyExport -> P2
P6DisplayExportContract.v2 / StageSnapshot -> P6
```

因此，单文档实时抽取页展示得再完整，也不能把运行态图谱直接当成 `P2` 或 `P6` 的正式输入。只有通过治理确认并形成发布态知识后，才能进入系统间业务输出。

### 8.5 后端适配层要求

建议新增独立输出适配层：

```text
archive_knowledge/external_exports/
├─ p1_to_p2_export.py
├─ p6_display_export.py
├─ freshness.py
└─ validators.py
```

该层职责：

- 从发布态知识仓读取正式知识，生成 `P1 -> P2` 标准知识出口。
- 从系统状态、发布态摘要和队列状态生成 `P6DisplayExportContract.v2`。
- 做新鲜度、降级原因和健康状态映射。
- 阻止候选态、运行态和治理中间态越权进入系统间输出。

### 8.6 验收要求

系统间接口验收必须独立于页面验收：

- `P1 -> P2` 输出只包含正式发布知识。
- `P1 -> P2` 输出能提供实体、事件、流程、规则、指标、关系邻域、搜索和证据回溯。
- `P2` 无法通过接口读取候选知识、治理中间态或单文档运行态图谱。
- `P1 -> P6` 输出符合 `P6DisplayExportContract.v2`。
- `P1 -> P6` 的 `flow_ports` 只输出 `发布态知识 -> P2`。
- `P1 -> P6` 的 `system_overall_metrics` 不包含当前文档、当前抽取任务或审核工作量。
- 接口不可用或数据过期时，能输出明确的新鲜度与降级信息。

## 9. 13 阶段的处理方式

13 阶段不应被删除，但要从“硬编码流程主体”降级为“默认流程蓝图 + 兼容视图”。

建议规则：

- 默认策略包仍可使用 13 阶段顺序。
- 每个阶段必须声明输入输出合同。
- 页面可继续显示 13 阶段进度，但当前阶段来自运行态，不由用户点击决定。
- 后端阶段处理器只读取上游公开产物，不读取其它阶段内部临时变量。
- 后续允许策略包定义不同阶段组合，但需要提供兼容的运行态投影。

## 10. 图谱重构原则

### 10.1 图谱数据来源

运行态图谱应由后端基于合同和执行记录生成，不应由前端临时拼装。

图谱节点类型建议：

- 输入对象节点：文档块、锚点、证据、候选对象、候选关系。
- 规则节点：规则合同、阈值、策略动作。
- 动作节点：过滤、评分、归并、拆分、阻断、发布候选。
- 输出对象节点：候选知识、规范知识、发布候选、API 暴露对象。
- 状态节点：运行中、警告、阻断、stale、等待治理确认。

### 10.2 默认视图

默认使用语义聚合视图：

```text
输入对象集合 -> 规则/策略/动作依据 -> 输出对象集合
```

不要默认铺满全部明细节点。明细通过点击节点、切换视图或局部展开查看。

### 10.3 布局原则

- 主链节点按处理顺序横向排开。
- 非主链节点围绕相关主链节点形成局部簇。
- 边的起终点根据节点实际位置自动选择。
- 密集 fan-in 使用集合节点，不直接画满屏连线。
- 选中节点或边时，高亮相关输入、规则、输出和观察窗。

## 11. 兼容迁移策略

为了不影响现有抽取能力，建议采用三层迁移：

### 11.1 Legacy Adapter

保留当前可运行抽取逻辑，把旧阶段输出包装成 `output_artifacts`、`RuleExecutionRecord` 和 `RuntimeGraphProjection`。

目标是先让页面和合同主链稳定，不急着一次性重写抽取算法。

### 11.2 Contract Driven Shadow

在不改变旧抽取结果的前提下，让规则合同参与执行并生成解释记录。

此阶段验证：

- 策略包版本是否冻结正确。
- 规则输入输出是否能追溯。
- 运行态图谱是否能表达规则影响。
- 规则变更是否能算出影响面。

### 11.3 Contract Driven Primary

逐步把阶段处理器改成真正由规则合同驱动输入、执行和输出。

此阶段才开始弱化固定 13 阶段的实现依赖，但仍保留 13 阶段作为默认策略包。

## 12. 并行开发边界设计

后续 `P1` 重构必须支持多工作线并行推进。并行开发的前提不是简单按页面或文件分工，而是先约定领域边界、公共合同和验收方式。

### 12.1 并行拆分原则

- 每个工作线必须拥有清晰的领域职责，不跨边界直接读取其它工作线内部状态。
- 工作线之间只通过 TypeScript 类型、Python schema、HTTP API、事件 payload 或持久化成果物交换数据。
- 任一工作线可以先使用 stub / fixture / mock adapter 验证自己的页面或服务，但必须标记数据来源，不能伪装成真实能力。
- 公共合同先行，合同变更必须同步影响方，并补合同测试。
- 页面可以并行做视觉和交互，但业务判断必须最终收敛到后端合同。

### 12.2 推荐并行工作线

#### 工作线 A：终端用户知识库体验

职责：

- 知识库总览。
- 文档清单。
- 抽取启动。
- 单文档实时抽取入口。
- 终端用户版状态说明。

只依赖：

- `ArchiveSummary`
- `ArchiveDocumentList`
- `ExtractionStartRequest`
- `PolicyRuntimeSnapshotSummary`
- `RuntimeStatusSummary`

不负责：

- 规则字段合同编辑。
- 规则变更影响面计算。
- 治理审核细节。
- 发布态正式图谱算法。

可独立验收：

- 用户能创建/选择知识库。
- 用户能看到文档抽取状态。
- 用户能启动抽取并进入单文档运行页。
- 页面不暴露过多运维细节。

#### 工作线 B：策略包与规则合同后台

职责：

- 策略包管理。
- 策略包版本管理。
- 阶段策略配置。
- 规则字段合同编辑。
- 合同校验。

只依赖：

- `PolicyPackage`
- `PolicyPackageVersion`
- `RuleContract`
- `RuleFieldContract`
- `PolicyContractValidationResult`

不负责：

- 单文档运行态图谱展示。
- 文档接入解析。
- 治理确认页面。
- 发布态知识查询。

可独立验收：

- 能创建或复制策略包。
- 修改规则字段后生成新版本。
- 合同缺失字段会被明确标红和返回错误。
- 已发布策略包不能被原地覆盖。

#### 工作线 C：运行态与规则执行主链

职责：

- 抽取启动时冻结 `PolicyRuntimeSnapshot`。
- 阶段处理器适配 `StageExecutionContract`。
- 规则执行生成 `RuleExecutionRecord`。
- Stream / polling 返回等价 runtime payload。
- 运行事件流。

只依赖：

- `PolicyRuntimeSnapshot`
- `StageExecutionContract`
- `RuleExecutionRecord`
- `RuntimeEvent`
- `RuntimeSnapshot`

不负责：

- 前端图谱布局。
- 策略后台表单体验。
- 治理确认业务操作。

可独立验收：

- 抽取运行中能看到冻结策略快照。
- 每个阶段有输入、输出、规则引用和运行快照。
- 断开 stream 后 polling 能拿到同等字段。
- 任意规则命中都能追踪到规则版本和规则哈希。

#### 工作线 D：运行态语义图谱投影

职责：

- 从运行态合同生成 `RuntimeGraphProjection`。
- 聚合视图和明细视图数据结构。
- 节点/边语义分类。
- 选中节点/边时的观察窗载荷。

只依赖：

- `RuntimeSnapshot`
- `StageExecutionContract`
- `RuleExecutionRecord`
- `DependencySelector`
- `RuntimeGraphProjection`

不负责：

- 策略版本保存。
- 抽取算法本身。
- 前端页面导航。
- 正式治理审核。

可独立验收：

- 每个阶段都能投影出“输入对象 -> 规则/动作依据 -> 输出对象”。
- fan-in / fan-out 密集区域能用集合节点表达。
- 选中节点或边能返回解释载荷。
- 同一 runtime payload 在 stream 和 polling 下图谱一致。

#### 工作线 E：规则变更影响面与增量重算

职责：

- 比较新旧策略包版本。
- 基于 `RuleExecutionRecord` 和依赖选择器计算 `ImpactSet`。
- 生成增量重算任务。
- 标记 stale 对象、候选快照和发布候选。

只依赖：

- `PolicyPackageVersionDiff`
- `RuleExecutionRecord`
- `DependencySelector`
- `ImpactSet`
- `IncrementalRebuildTask`

不负责：

- 策略编辑 UI 的所有细节。
- 抽取工作台图谱交互。
- 治理确认页面重做。

可独立验收：

- 修改结构性规则后能得到最早重算阶段。
- 能列出受影响文档、候选、关系和发布候选快照。
- 不会直接覆盖正式入库知识。
- 可生成待确认的增量重算任务。

#### 工作线 F：治理发布与发布态边界适配

职责：

- 保持抽取候选、发布候选、治理确认、正式入库之间的边界。
- 确认 `/governance` 读取的是发布候选，不是抽取临时节点。
- 确认发布态图谱只展示正式入库知识。

只依赖：

- `PublicationCandidateSnapshot`
- `GovernanceConfirmation`
- `PublishedKnowledgeSnapshot`
- `PublishedGraphProjection`

不负责：

- 重新设计治理页面视觉。
- 单文档运行态策略配置。
- 文档接入解析。

可独立验收：

- 机器发布候选不会被误认为正式入库。
- 治理确认后才生成正式版本。
- 发布态知识图谱不展示运行中临时节点。

#### 工作线 G：系统间输出接口适配

职责：

- 生成 `P1 -> P2` 发布态知识标准出口。
- 生成 `P1 -> P6` 的 `P6DisplayExportContract.v2` 和 `StageSnapshot`。
- 校验系统间输出不泄漏候选态、运行态、治理中间态和策略后台内部字段。
- 提供系统间接口合同测试。

只依赖：

- `PublishedKnowledgeSnapshot`
- `PublishedGraphProjection`
- `P1KnowledgeSupplyExport`
- `P6DisplayExportContract.v2`
- `StageSnapshot`

不负责：

- 抽取算法实现。
- 单文档运行态展示。
- 策略后台编辑。
- 治理页面视觉。

可独立验收：

- `P1 -> P2` 只输出正式发布知识和证据回溯。
- `P1 -> P6` 满足统一骨架字段、P1 差异字段和端口规则。
- `flow_ports` 只表达 `发布态知识 -> P2`。
- 接口不可用或数据过期时返回明确新鲜度和降级原因。

#### 工作线 I：知识质量与图谱质量评测

职责：

- 生成 `KnowledgeQualityReport`，解释概念、候选、定义、证据和冲突质量。
- 生成 `GraphQualityReport`，解释图谱连通性、孤立节点、关系证据、动作依据覆盖和布局可读性。
- 生成 `EvaluationRunReport`，用固定评测集回归比较策略、规则、模型或解析变更后的质量变化。
- 把质量摘要提供给运行页、治理页、发布页和系统间输出层，但不泄漏规则后台内部合同。

只依赖：

- `RuleExecutionRecord`
- `RuntimeGraphProjection`
- `PublishedGraphProjection`
- `PublicationCandidateSnapshot`
- `EvaluationDataset`
- `PolicyRuntimeSnapshot`

不负责：

- 修改抽取候选对象。
- 修改正式入库知识。
- 决定治理审核结果。
- 重写图谱布局组件。

可独立验收：

- 能说明概念质量、关系质量、证据覆盖和图谱拓扑质量。
- 能指出无证据关系、孤立节点、缺少动作依据路径和低置信对象。
- 能输出固定评测集的概念 precision/recall/F1、关系 precision/recall/F1 和证据 recall。
- 任一进入发布候选的结果都有质量摘要。

#### 工作线 J：库级同知识归并与更新

职责：

- 识别同一知识库中来自不同文档的相同或相近知识候选。
- 生成 `KnowledgeIdentityKey`、`CrossDocumentMatchCandidate` 和 `KnowledgeMergeDecision`。
- 生成 `CanonicalKnowledgeItem` 和 `ArchiveKnowledgeResolutionSnapshot`。
- 处理新增、合并、修订、冲突、拆分、拒绝等归并决策。
- 为发布候选、治理确认和系统间输出提供库级规范知识对象。

只依赖：

- `DocumentKnowledgeCandidate`
- `KnowledgeQualityReport`
- `RuleExecutionRecord`
- `PublishedKnowledgeSnapshot`
- `PolicyRuntimeSnapshot`

不负责：

- 单文档抽取算法。
- 人工治理页面操作。
- 直接覆盖正式入库知识。
- P2 / P6 消费侧适配。

可独立验收：

- 多份文档中的同一知识能合并为一个规范知识对象。
- 同名异义不会被错误合并。
- 新文档补充证据可形成证据追加，改变语义时生成修订候选。
- 冲突定义或冲突关系能进入质量报告和治理确认。
- 移出文档后能重算支撑证据，不能直接删除正式知识本体。

### 12.3 公共合同目录建议

为了支持并行开发，建议逐步建立公共合同目录：

```text
apps/api/app/archive_knowledge/contracts/
├─ policy_contract.py
├─ rule_contract.py
├─ runtime_contract.py
├─ graph_projection_contract.py
├─ quality_contract.py
├─ knowledge_resolution_contract.py
├─ impact_contract.py
├─ publication_contract.py
└─ system_output_contract.py

apps/web/src/features/p1/contracts/
├─ policy.ts
├─ rule.ts
├─ runtime.ts
├─ graphProjection.ts
├─ quality.ts
├─ knowledgeResolution.ts
├─ impact.ts
├─ publication.ts
└─ systemOutput.ts
```

后端 schema 是事实源，前端类型可以由 OpenAPI 或手工镜像生成。短期允许手工维护，但必须有合同测试覆盖关键字段。

### 12.4 并行开发防串线规则

- 工作线不得直接 import 其它工作线的页面组件作为业务依赖。
- 工作线不得读取其它工作线的内部临时文件、缓存文件或未声明 JSON。
- 后端领域模块之间不能跨层读取实现细节，只能通过 service interface 或 contract object 调用。
- 新增 API 字段必须兼容旧字段，除非有明确迁移说明。
- 任何 mock fallback 必须在 UI 和代码命名上标记为 fallback。
- 每条工作线至少提供一条自动化测试和一条人工验收路径。

### 12.5 最小并行开发节奏

建议先并行启动 4 条线：

```text
A. 终端用户知识库体验
B. 策略包与规则合同后台
C. 运行态与规则执行主链
D. 运行态语义图谱投影
I. 质量评测指标与报告合同
J. 库级归并合同和最小同知识 fixture
```

系统间输出接口适配可以从一开始用 fixture 和合同测试并行建立防线，但真实数据接入建议在 `F` 稳定后合并。

随后再接：

```text
E. 规则变更影响面与增量重算
F. 治理发布与发布态边界适配
G. 系统间输出接口适配真实数据接入
I. 质量评测接入真实运行态、图谱和发布候选
J. 库级归并接入真实候选、质量报告和发布态知识
```

原因是 `E` 强依赖 `B / C / D` 的合同稳定，`F` 需要先明确发布候选与正式入库的接口边界，`G` 则必须以发布态事实为输入，不能直接消费运行中临时节点。`I` 可以先用 fixture 启动，但真实质量报告必须等 `C / D / F` 产物稳定后接入。`J` 可以先用同知识样本启动，但真实归并必须等文档级候选、质量报告和发布态知识引用稳定后接入。

## 13. 分阶段实施计划

### R0：文档与现状盘点

目标：

- 对照正式 `P1` 设计，列出现有页面、API、后端模块与目标设计的映射。
- 标记哪些属于终端用户页面，哪些属于策略后台页面，哪些属于治理发布边界。

验收：

- 有一份页面/接口/模块映射表。
- 能明确指出每个旧路由的新归属。

### R1：导航与页面边界重组

目标：

- 清理 P1 导航。
- 终端用户页与策略后台页分层。
- 保留旧路由兼容跳转。

验收：

- 用户进入 P1 后不会先看到复杂策略后台。
- 能从知识库总览顺畅进入文档清单和单文档实时抽取。
- 策略配置入口独立进入，不干扰普通抽取流程。

### R2：前端模块拆分

目标：

- 拆分 `ArchiveManagementPage.tsx` 的职责。
- 把图谱、观察窗、流程导航、抽取启动、知识库列表拆成独立模块。
- 把策略相关页面从原型页沉淀为正式 feature 模块。

验收：

- 单个页面文件不再继续膨胀。
- 图谱组件只消费后端投影数据，不直接承担业务推断。
- 策略页面只消费策略 API，不反向依赖单文档页面状态。

### R3：后端合同主干收口

目标：

- 固化 `PolicyPackage / PolicyPackageVersion / PolicyRuntimeSnapshot`。
- 固化 `RuleContract / RuleExecutionRecord`。
- 抽取启动必须冻结策略快照。
- Stream 和 polling 返回等价运行态。

验收：

- 任意单文档运行态都能看到本次使用的策略包版本和快照 ID。
- 任意规则命中都能追溯到 `rule_id / rule_version / rule_hash`。
- 修改策略不会影响已经启动的运行快照。

### R4：阶段处理器适配

目标：

- 给现有 13 阶段增加统一 `StageExecutionContract` 包装。
- 每个阶段输出标准化 `output_artifacts / runtime_snapshot / graph_projection`。
- 当前旧抽取逻辑仍然可运行。

验收：

- 13 阶段每一阶段都有输入合同和输出合同。
- 单文档页能展示每阶段输入对象、规则依据、输出对象。
- 慢速抽取源可以实时观察图谱变化。

### R5：图谱语义投影重构

目标：

- 后端输出 `RuntimeGraphProjection`。
- 前端默认展示语义聚合图。
- 明细节点通过点击或视图切换展开。

验收：

- 任意阶段都能看出“输入对象 -> 规则/动作依据 -> 输出对象”。
- 密集区域不再出现严重遮挡和满屏线海。
- 选中节点/边能联动观察窗解释来源、规则、输出和状态。

### R6：规则变更与增量重算闭环

目标：

- 规则变更生成新策略版本。
- 基于 `RuleExecutionRecord` 和依赖选择器计算 `ImpactSet`。
- 生成候选重算任务，不直接覆盖正式知识。

验收：

- 修改规则后能看到影响文档、影响候选、影响关系和最早重算阶段。
- 已正式入库知识不会被静默覆盖。
- 新候选需要治理确认后才进入正式版本。

### R7：知识质量与图谱质量评测闭环

目标：

- 建立 `KnowledgeQualityReport`，覆盖概念类型、定义完整性、证据覆盖、重复和冲突。
- 建立 `GraphQualityReport`，覆盖端点合法性、关系证据、连通性、动作依据覆盖和布局可读性。
- 建立固定评测集回归，比较策略、规则、模型或解析变更前后的质量差异。
- 在发布候选和系统间输出摘要中携带质量摘要。

验收：

- 任意发布候选都有可追溯质量报告。
- 任意质量风险都能定位到候选对象、关系、证据锚点或规则执行记录。
- 质量评测回归能输出概念、关系和证据指标。
- 低于发布阈值的候选不得进入 `P1 -> P2` 正式供给。

### R8：库级同知识归并与更新闭环

目标：

- 建立 `KnowledgeIdentityKey`，为文档级候选生成库级身份键。
- 建立 `KnowledgeMergeDecision`，区分新增、合并、修订、冲突、拆分和拒绝。
- 建立 `CanonicalKnowledgeItem`，让发布态图谱和系统间输出都消费库级规范知识。
- 建立 `ArchiveKnowledgeResolutionSnapshot`，记录每批归并结果和跨文档证据。

验收：

- 同一知识库内多份文档描述同一知识时只形成一个规范知识对象。
- 多文档支撑证据能被合并并提升可信度。
- 同名异义、定义冲突和关系冲突不会被静默合并。
- 正式知识更新必须生成修订候选，不允许新文档静默覆盖正式版本。
- 文档移出后能重算支撑证据，无证据支撑时标记为 `unsupported` 或生成撤回候选。

### R9：系统间输出接口收口

目标：

- 建立 `P1 -> P2` 发布态知识标准出口。
- 建立 `P1 -> P6` 只读展示输出适配。
- 补系统间接口合同测试，防止运行态、候选态和治理中间态越权输出。

验收：

- `P1 -> P2` 输出只包含正式发布知识。
- `P1 -> P2` 支持实体、事件、流程、规则、指标、关系邻域、搜索和证据回溯。
- `P1 -> P6` 输出符合 `P6DisplayExportContract.v2` 和 `StageSnapshot` 口径。
- `P1 -> P6` 不编造除 `发布态知识 -> P2` 以外的业务输出端口。

## 14. 测试与验收矩阵

### 14.1 后端测试

- 策略包版本生成测试。
- 策略快照冻结测试。
- 规则合同校验测试。
- `RuleExecutionRecord` 序列化测试。
- Stream / polling 等价测试。
- 规则变更 `ImpactSet` 测试。
- `KnowledgeQualityReport` 和 `GraphQualityReport` 指标计算测试。
- 固定评测集 `EvaluationRunReport` 回归测试。
- 跨文档同知识归并、冲突、修订和证据追加测试。
- 发布候选不覆盖正式知识测试。
- `P1 -> P2` 发布态知识出口合同测试。
- `P1 -> P6` 展示输出合同测试。
- 系统间输出不泄漏候选态、运行态和治理中间态测试。

### 14.2 前端测试

- 知识库总览入口测试。
- 文档清单选择测试。
- 单文档实时运行测试。
- Stream 断线回退轮询测试。
- 策略包版本展示测试。
- 图谱节点/边选择联动测试。
- 质量报告摘要展示测试。
- 策略配置保存和版本差异测试。
- 终端用户页跳转到下游供给状态时，不展示系统间接口之外的内部字段。

### 14.3 人工验收

使用慢速抽取源做完整验收：

- 不整页刷新。
- 当前阶段随运行态推进。
- 图谱节点动态进入和状态变化。
- 每阶段有规则/策略/动作依据。
- 观察窗能解释被选中的节点或边。
- 质量报告能解释概念质量、关系质量、证据覆盖和图谱质量风险。
- 多文档同知识能在发布态图谱中显示为一个规范节点，并能展开来源文档证据。
- 发布阶段能区分机器候选、治理确认和正式入库。
- `P1 -> P2` 供给口径能被解释为发布态知识，而不是抽取中临时结果。
- `P6` 观察口径只展示总体资产、实时流动、端口和队列，不展示当前单文档内部运行图谱。

## 15. 本轮非目标

以下内容不建议放入本轮重构：

- 不重写 Docling / LLM 解析抽取底层能力。
- 不把模块化单体拆成真实微服务。
- 不主动重做治理确认页和发布态知识图谱页。
- 不让前端用 mock 数据伪装已完成能力。
- 不用规则-only 抽取冒充正式结构化大模型抽取。

## 16. 立即建议动作

建议下一步按以下顺序推进：

1. 产出现有路由、页面、API、后端模块到目标设计的映射表，并单独标出 `P1 -> P2`、`P1 -> P6` 系统间输出接口。
2. 整理 P1 导航和页面层级，先解决“用户不知道该去哪”的问题。
3. 拆分单文档实时工作台，把图谱投影消费和页面展示解耦。
4. 后端补齐 `StageExecutionContract` 适配层，让旧抽取输出先能统一进入合同主链。
5. 建立质量评测合同和最小报告 fixture，先回答“知识和图谱为什么可信”。
6. 建立库级同知识归并与更新合同 fixture，先回答“多文档相同知识怎么合并和更新”。
7. 补系统间输出适配层的合同测试，确保内部运行态不会越权进入下游系统。
8. 再做图谱语义投影重构，避免前端继续照猫画虎。

## 17. 总结判断

当前系统不是没有能力，而是能力边界堆叠在一起了。

重构重点不是“再补几个页面”或“再画一版图谱”，而是把 `P1` 重新整理为：

```text
终端用户可理解的知识库闭环
+ 策略运维可配置的规则合同体系
+ 后端可追溯的运行快照与规则执行记录
+ 前端可解释的语义图谱投影
+ 可量化、可回归的知识质量与图谱质量报告
+ 可验证、可合并、可修订的库级规范知识对象
```

这样才能同时满足“更容易使用”和“知识图谱质量更好”两个目标。
