# 2026-05-10 P2 组织器多轮整改第 1 轮问题与整改说明

## 1. 背景

本文件配套第 1 轮受控动态多轮机测记录，用于说明本轮发现的问题、根因判断、整改边界、实际修改和复测结论。对应测试记录为：

```text
DOC/CODEX_DOC/06_测试文档/03_机测记录/2026-05-10-P2-组织器多轮整改第1轮测试记录.md
```

本轮执行原则是：第 1 轮发现的问题必须在本轮尽量全量修复、复测和归档后，才允许进入第 2 轮；不能把同一轮已经明确的问题拆到后续轮次慢慢处理。

## 2. 本轮问题与根因

### 2.1 `brainstorm-v1` 交付文案误把已确认事实统一标成模型推断

现象：

- 收束交付时，assistant 文案把草案中的内容整体描述为模型推断或待确认内容。
- 实际上，其中一部分是用户已确认事实，只有 `【待确认】`、`【暂定】` 或未闭合问题才应被标为推断或待确认。

根因：

`next_interaction_planning` 的交付提示没有明确区分“已确认事实”“暂定假设”“未闭合问题”和“模型推断”。

归属：

- `brainstorm-v1` Prompt。

### 2.2 Dify 章节锚点与当前 81433 模板不完全一致

现象：

- 早期输出曾出现 `REQ-3.UI`、`REQ-3.COLLAB`、`REQ-3.ERR` 等旧锚点。
- 这些锚点不属于当前 81433 模板实例的 canonical anchor。

根因：

Dify workflow 的 `document_projection` 仍保留旧章节映射，不完全跟随当前模板锚点。

归属：

- Dify workflow。
- 本地 `workflow.json` 和 Dify 搭建规范需要同步。

### 2.3 Dify 把“部署分析”错投到部署环境

现象：

- 输入“部署分析系统要支持覆盖、冲突、影响分析”时，事实进入 `5 非功能需求 / 部署与运行环境`。

根因：

分类规则把“部署”泛化为部署环境，未区分“部署分析/部署影响分析”这种功能行为与“内网部署/运行环境”这种非功能部署约束。

归属：

- Dify workflow `document_projection` 节点。

### 2.4 Dify 把边界排除项错投到协同共享

现象：

- 输入“不做自动决策推荐，不承诺高精度测绘级或工程级计算，也不做多单位在线协同指挥”时，因为同句包含“协同”，边界事实进入 `3 功能需求 / 结果输出与共享`。

根因：

协同/共享关键词优先级高于“不做、不承诺、排除、边界”等范围约束。

归属：

- Dify workflow `document_projection` 节点。

### 2.5 Dify 混合非功能枚举丢失部署与追溯维度

现象：

- 输入“非功能先按内网部署、角色权限、操作审计、结果可追溯考虑”时，只形成安全权限章节内容，部署环境和质量追溯没有独立沉淀。

根因：

`document_projection` 对同一句内的非功能枚举只做单章节分类，没有对跨部署、安全、质量的枚举做机械拆分。

归属：

- Dify workflow `document_projection` 节点。

### 2.6 Dify 收束草案重复堆叠

现象：

- 分类整改后的双组织器复测中，Dify 第 11 Turn 能进入 `draft_delivery`，但最终 A4 正文出现“旧正文 + 草案 bullet”重复堆叠。
- 例如 `REQ-2.1` 中“不做自动决策推荐”同时以旧正文和 bullet 形式出现。

根因：

Dify 草案分支继续使用 `append_or_update`。P2 `WorkingDocumentService` 对 `append_or_update` 的通用行为是追加并做整段去重，不会把已有章节内容替换为草案版本。

归属：

- Dify workflow 草案分支输出合同。
- P2 平台本体无需写业务规则；平台已有通用 `replace` 语义。

## 3. 整改边界

本轮没有把章节语义判断写入 P2 平台 Python 本体。实际处理边界如下：

| 类别 | 处理方式 |
| --- | --- |
| 用户输入意图、章节语义、事实投影 | 放在组织器 Prompt 或 Dify workflow 节点中 |
| `append_or_update`、`replace` 等 patch 机械应用 | 使用 P2 平台已有通用能力 |
| Dify 发布、备份、节点替换 | 新增脚本执行，但脚本不保存账号密码 |
| 测试统计和日志 | 放入 `.run-logs/`，不提交大体量原始日志 |

## 4. 实际修改

修改文件：


### 4.2 Dify 工作流发布脚本

新增文件：

```text

```

能力：

- 从环境变量读取 Dify 控制台账号和密码。
- 登录 Dify 控制台。
- 备份当前 draft 到 `.run-logs/`。
- 替换 `document_projection` 节点代码。
- 同步 draft。
- 可选发布 workflow。

## 6. 本轮结论

1. 本轮阻塞性问题已处理完：收束交付、Dify 当前模板锚点、部署分析分类、边界分类、混合非功能拆分、草案重复堆叠均复测通过。
2. 本轮没有把业务语义判断写入 P2 平台本体；业务判断仍由组织器 Prompt/Dify workflow 承担。
3. Dify 组织器产物仍偏轻，部分章节仍是“本章节待确认”；这属于下一轮质量提升方向，不属于本轮分类投影和草案堆叠阻塞问题。
4. 下一轮建议重点关注开放问题生命周期、验收准则信息保留、草案信息完整度和 Dify workflow 的阶段可观测性。
