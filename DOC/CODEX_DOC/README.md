# CodeFactoryV2 正式文档根

本目录是 `CodeFactoryV2` 的正式本地文档根，用于承接已经确认、需要长期追踪、需要在后续多轮开发中持续复用的工程文档。

## 1. 阅读顺序

1. `DOC/CODEX_DOC/README.md`
2. `DOC/CODEX_DOC/00-本地工程策略映射.md`
3. `DOC/CODEX_DOC/01_需求分析/00-工程总体分析.md`
4. `DOC/CODEX_DOC/02_设计说明/00-软件工厂平台总体设计.md`
5. `DOC/CODEX_DOC/02_设计说明/01-文档治理与superpowers协同设计.md`
6. `DOC/CODEX_DOC/03_研制计划/00-WBS-0-CodeFactoryV2-研发总纲-研制计划.md`

## 2. 文档三层模型

### 2.1 正式文档层

正式、权威、可长期追踪的文档统一放在 `DOC/CODEX_DOC/`。

适用对象：

- 平台总体设计
- WBS 研发总纲与阶段计划
- 本地工程策略映射
- 长期有效的数据规范、流程规范、验收文档、交接文档

### 2.2 superpowers 工作层

`docs/superpowers/` 是方案推演、实施计划、issue 镜像、阶段草案和执行工作台文档层，不是最终权威根。

适用对象：

- brainstorming 产物
- 设计草案与局部方案
- 执行计划
- issue tree mirror

规则：

- `superpowers` 文档可以先产生
- 一旦方案被采纳为正式基线，必须同步回 `DOC/CODEX_DOC/`
- 未同步进正式文档层的内容，不应当作长期稳定规范对外宣告

### 2.3 远端协作层

GitHub `Project / Issue / PR` 是排程、执行契约和评审协作层。

规则：

- 远端树结构以 GitHub parent/sub-issue 为准
- 路径引用默认使用仓库相对路径
- 正式路径优先引用 `DOC/CODEX_DOC/`

## 3. 当前工程主结构

当前项目按六个一级节点组织：

- `P1` 业务知识库
- `P2` 需求分析系统
- `P3` 软件设计系统
- `P4` 工具仓库
- `P5` 软件构建系统
- `P6` 门户与平台入口

其中：

- `P1 ~ P5` 是软件工厂业务主链
- `P6` 是平台入口、导航、权限与门户承载层

## 4. 目录职责

- `00-本地工程策略映射.md`：把全局工程策略映射到本仓库
- `01_需求分析/`：沉淀结构分析、模块边界、风险与缺口
- `02_设计说明/`：沉淀已经确认的正式设计
- `03_研制计划/`：沉淀 WBS 总纲与阶段节点计划
- `04_研发文档/`：沉淀研发过程中长期有效的规范、映射表和关键流程
- `05_测试文档/`：沉淀自测、验收、验收记录、验收结论
- `06_过程文档/`：沉淀交接、历史计划、验收意见处理

## 5. 当前执行约束

- 后续方案开发采用“`superpowers` 先产出工作文档，正式结论回写 `DOC/CODEX_DOC`”的双层协同方式
- 任何新的正式 WBS 节点、设计结论、验收口径，必须能在本目录中被追溯
- `docs/superpowers/` 可以继续使用，但不再承担单一权威文档根职责
