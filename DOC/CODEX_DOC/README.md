## 2. 文档三层模型

### 2.1 正式文档层

正式、权威、可长期追踪的文档统一放在 `DOC/CODEX_DOC/`。

适用对象：

- 平台总体设计
- WBS 研发总纲与阶段计划
- 本地工程策略映射
- 长期有效的数据规范、流程规范、验收文档、交接文档

### 2.2 superpowers 工作层

`docs/superpowers/` 是方案推演、实施计划、issue 镜像、阶段草案和执行工作台文档层，不是最终权威根。

适用对象：

- brainstorming 产物
- 设计草案与局部方案
- 执行计划
- issue tree mirror

规则：

- `superpowers` 文档可以先产生
- 一旦方案被采纳为正式基线，必须同步回 `DOC/CODEX_DOC/`
- 未同步进正式文档层的内容，不应当作长期稳定规范对外宣告

### 2.3 远端协作层

GitHub `Project / Issue / PR` 是排程、执行契约和评审协作层。

规则：

- 远端树结构以 GitHub parent/sub-issue 为准
- 路径引用默认使用仓库相对路径
- 正式路径优先引用 `DOC/CODEX_DOC/`

## 3. 当前工程主结构

当前项目按六个一级节点组织：

- `P1` 业务知识库
- `P2` 需求分析系统
- `P3` 软件设计系统
- `P4` 工具仓库
- `P5` 软件构建系统
- `P6` 平台门户、观察与前端展示实验层

其中：

- `P1 ~ P5` 是软件工厂业务主链
- `P6` 是平台级首屏观察、只读集成、设计语言统一与前端展示实验层

## 4. 目录职责

- `00-本地工程策略映射.md`：把全局工程策略映射到本仓库
- `01_需求分析/`：沉淀结构分析、模块边界、风险与缺口
- `02_设计说明/`：沉淀已经确认的正式设计
- `03_研制计划/`：沉淀 WBS 总纲与阶段节点计划
- `04_研发文档/`：沉淀研发过程中长期有效的规范、映射表和关键流程
- `05_测试文档/`：沉淀自测、验收、验收记录、验收结论
- `06_过程文档/`：沉淀交接、历史计划、验收意见处理

## 4.1 设计说明目录规则

`02_设计说明/` 不再使用全局 `01 / 02 / 03 ...` 编号承担阶段语义，而采用“`00_总纲 + P阶段目录`”结构。

编排规则如下：

- `00_总纲/`：只放跨阶段、跨模块的总纲和治理文档，继续使用普通顺序号，例如 `00-...`、`01-...`
- `P阶段_中文名/`：只放与某个阶段直接绑定的正式设计文档，例如 `P1_业务知识库/`、`P4_工具仓库/`
- 阶段主设计文档：使用 `P阶段-中文标题`，例如 `P3-软件设计系统设计.md`
- 阶段内专题文档：使用阶段内局部号，不再占用全局号位
- 已形成稳定子节点的专题：直接使用 WBS 语义编号，例如 `P5.1-最小构建闭环设计.md`、`P6.1-首屏观察门户设计.md`
- 仅为阶段内专题、但不单独作为一级 WBS 子节点的文档：使用局部槽位编号，例如 `P4-10`、`P4-20`、`P4-30`
- 新文档应插入所属阶段目录，不允许因为新增一个 `P4` 或 `P6` 文档而整体重排所有正式设计编号

当前目录按以下阅读顺序理解：

- `00_总纲/`：平台级总纲与文档治理
- `P1_业务知识库/`
- `P2_需求分析系统/`
- `P3_软件设计系统/`
- `P4_工具仓库/`
- `P5_软件构建系统/`
- `P6_门户与平台入口/`

补充说明：

- `05_测试文档/`、`06_过程文档/` 中的历史记录允许保留旧路径文本，作为时间证据层，不以其旧编号作为当前正式入口
- 当前正式入口以 `02_设计说明/` 实际目录结构和本文件阅读顺序为准

## 5. 当前执行约束

- 后续方案开发采用“`superpowers` 先产出工作文档，正式结论回写 `DOC/CODEX_DOC`”的双层协同方式
- 任何新的正式 WBS 节点、设计结论、验收口径，必须能在本目录中被追溯
- `docs/superpowers/` 可以继续使用，但不再承担单一权威文档根职责
