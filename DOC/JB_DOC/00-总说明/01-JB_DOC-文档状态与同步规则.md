# JB_DOC 文档状态与同步规则

## 1. 文档定位

**文档类别：** 标准化辅助文档  
**标准依据：** 吸收 `SDP / SEMP / 配置管理 / 质量保证 / 基线控制` 思路  
**当前状态：** 基线

本文件用于规定 `JB_DOC` 的状态分层、同步门槛、升级规则与维护责任。

## 2. 文档状态分层

### 2.1 骨架

含义：

- 已建立对象边界和章节框架
- 尚不足以承载稳定引用

适用对象：

- 后续待补文种
- 仅用于占位的矩阵或样例目录

### 2.2 候选

含义：

- 已根据现有 `CODEX_DOC` 正式文档完成首版标准化复写
- 具备较完整结构、关键控制点与来源声明
- 仍需继续补充更严格的编号、证据或实例

适用对象：

- 平台规格说明
- 平台设计说明
- `SEMP / SDP / CMP / QA / 验证发布` 等候选文档

### 2.3 基线

含义：

- 已完成稳定对象边界确认
- 已明确主要来源、标准依据和章节职责
- 可作为当前项目内部稳定引用对象

适用对象：

- 总说明
- 同步规则
- 已冻结的桥接与辅助文档

### 2.4 样例

含义：

- 面向某个真实项目实例的标准化输出文档
- 用于验证模板能否落地

适用对象：

- 未来项目实例 `SRS / SDD / RTVM / STP / STR / SVD` 等

## 3. `CODEX_DOC -> JB_DOC` 的同步原则

### 3.1 权责边界

- `CODEX_DOC`
  - 研发权威根
- `JB_DOC`
  - 标准化投影根

因此：

- `JB_DOC` 不能自发发明与 `CODEX_DOC` 冲突的正式边界
- `CODEX_DOC` 的正式结论一旦影响标准对象，应评估是否同步到 `JB_DOC`

### 3.2 必须同步的触发条件

出现以下任一情况时，必须评估并通常需要更新 `JB_DOC`：

- 平台总体边界、阶段主链或正式接口发生变化
- `P1 / P2 / P3 / P4 / P6` 的正式设计进入新基线
- `P4` 一类专题设计影响平台级设计说明表达
- 标准模板适用范围或分流规则发生变化
- 映射关系、缺口判断或路线图发生实质变化

### 3.3 可以延后批量同步的情况

以下情况允许不实时同步，但不得长期拖欠：

- 仅修正文案、不影响对象边界的小改动
- 纯过程记录更新
- 尚未被采纳为正式基线的 `superpowers` 草稿

## 4. 候选文档升级规则

### 4.1 从骨架到候选

至少满足：

- 有明确文档类别
- 有真实标准依据
- 有主要来源文档声明
- 有可读的章节主体，而不是只有目录

### 4.2 从候选到基线

至少满足：

- 关键章节不再明显空泛
- 主要来源映射已经在 `04-映射与追溯/` 中登记
- 与 `CODEX_DOC` 不存在明显矛盾
- 已经过一轮人工审阅或阶段性确认

### 4.3 样例文档的前提

只有当以下条件满足时，才适合创建样例文档：

- 对应模板已经稳定
- 对应平台对象已有真实输入
- 追溯关系可以落地

## 5. 每份关键文档的最小声明

`JB_DOC` 中的关键文档开头必须声明：

- 文档类别
- 标准依据
- 当前状态

建议同时声明：

- 主要来源文档
- 适用范围
- 当前限制

## 6. 来源追溯规则

### 6.1 追溯粒度

对于关键候选文档，不应只写“来自某目录”，而应尽量写到：

- 具体 `CODEX_DOC` 文件
- 关键阶段设计文档
- 关键计划文档
- 关键桥接文档

### 6.2 允许多来源合成

一份 `JB_DOC` 文档可以同时吸收：

- 平台总体设计
- 阶段详细设计
- WBS 计划
- 策略与映射文档

这不是缺陷，而是标准化重组的正常形态。

## 7. 维护责任规则

### 7.1 平台自身标准文档包

当 `CODEX_DOC/02_设计说明/` 和 `03_研制计划/` 有重大更新时，优先检查：

- `01-平台自身标准文档/`
- `04-映射与追溯/`

### 7.2 模板中心

当文种映射、参考库或 `P2 / P3` 产物对象发生变化时，检查：

- `02-软件工厂产物模板中心/`

### 7.3 样例层

当真实项目实例出现时，再正式推进：

- `03-项目实例与样例/`

## 8. 当前版本维护结论

本轮 `JB_DOC` 已进入“候选文档整体深化”阶段。

当前最重要的维护原则是：

- 不追求数量膨胀
- 优先保证来源真实、边界清楚、章节可用
- 后续继续按 `CODEX_DOC` 正式基线迭代，而不是脱离研发主根单独演化
