# JB_DOC 体系说明与使用边界

## 1. 文档定位

**文档类别：** 本地桥接文档  
**标准依据：** 无直接单一军标文种对应，吸收 `SRS / SDD / SDP / SEMP / RTVM` 体系化组织思路  
**当前状态：** 生效

本文件用于说明 `JB_DOC` 的定位、目标、边界和基本组织方式。

## 2. 为什么要建立 `JB_DOC`

当前项目已经有一套正式文档根：

- `DOC/CODEX_DOC/`

但这套文档根的核心职责是：

- 支撑平台研发协作
- 固化工程治理
- 归档阶段设计与过程证据

它不是按美军 / DoD 软件交付文种组织的目录。因此，若直接要求它整体转为军标体系，会带来两个问题：

- 治理文档与交付文种混写
- 本地研发协作效率下降

`JB_DOC` 的建立，就是为了解决这个矛盾：

- 让 `CODEX_DOC` 继续承担研发文档根职责
- 让 `JB_DOC` 承担标准化副本文档根职责

## 3. `JB_DOC` 解决什么问题

`JB_DOC` 主要解决四个问题：

### 3.1 标准化表达问题

把适合标准化表达的对象，从当前本地研发文档中抽取出来，按标准对象重新组织，而不是沿用当前本地目录树硬套。

### 3.2 模板中心组织问题

把软件工厂未来要生成的软件需求、设计、测试、发布、移交等标准模板族单独组织起来，形成稳定的模板中心目录。

### 3.3 样例验证问题

未来当软件工厂进入实例化交付时，可以在 `JB_DOC` 中承接某个具体项目的标准化文档样例，验证模板是否可落地。

### 3.4 追溯与审查问题

通过映射表、缺口清单和路线图，明确：

- 每份 `JB_DOC` 文档的来源
- 当前哪些标准对象已经覆盖
- 哪些对象仍缺失

## 4. `JB_DOC` 不解决什么问题

`JB_DOC` 不承担以下职责：

- 不替代 `CODEX_DOC` 的工程治理功能
- 不承载日常开发执行规程和阶段过程记录
- 不作为唯一权威文档根
- 不保证每一份文档都能直接对应某个标准编号

因此，`JB_DOC` 不是“标准文档万能根”，而是“标准化表达与投影根”。

## 5. `JB_DOC` 中的三类文档

### 5.1 标准文种候选文档

这类文档具有明确标准依据，例如：

- 平台规格说明候选
- 平台设计说明候选
- 需求规格模板组说明
- 设计说明模板组说明

要求：

- 必须写明标准依据
- 必须尽量按标准章节和控制点组织
- 不允许以标准名义大量自由发挥

### 5.2 标准化辅助文档

这类文档不直接等于某个军标文种，但为标准化体系服务，例如：

- 文档状态与同步规则
- 模板中心总说明
- 文种优先级路线图

要求：

- 必须明确标注为辅助性质
- 不得伪装成正式军标原件

### 5.3 本地桥接文档

这类文档用于连接 `CODEX_DOC` 与 `JB_DOC`，例如：

- 来源映射总表
- 覆盖缺口清单

要求：

- 明确来源和用途
- 强调桥接定位

## 6. 组织原则

### 6.1 面向标准对象组织，而不是面向当前本地目录组织

`JB_DOC` 的组织单位是：

- 标准对象
- 模板族
- 交付实例

而不是：

- 当前本地目录中的文件夹
- 当前研发阶段的工作分解

### 6.2 允许 `N : M` 映射

- 一份 `JB_DOC` 文档，可以综合多份 `CODEX_DOC` 文档内容
- 一份 `CODEX_DOC` 文档，也可以为多份 `JB_DOC` 文档提供来源

因此，不追求“文件对文件的一一复制”。

### 6.3 先白名单，后扩展

当前只把真正适合标准化表达的对象纳入 `JB_DOC` 首批目录，不把全部研发文档强行复制过来。

## 7. 当前目录边界

当前首批目录包括：

- `00-总说明`
- `01-平台自身标准文档`
- `02-软件工厂产物模板中心`
- `03-项目实例与样例`
- `04-映射与追溯`

后续可以扩展，但扩展原则不变：

- 先明确对象
- 再明确标准依据
- 最后再建文档

## 8. 当前结论

`JB_DOC` 当前应被理解为：

- `CodeFactoryV2` 的标准化副本文档根

而不是：

- 当前项目的唯一正式文档根
- 所有本地文档的军标复制仓
