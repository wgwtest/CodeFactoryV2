# JB_DOC 体系说明与使用边界

## 1. 文档定位

**文档类别：** 本地桥接文档  
**标准依据：** 无直接单一军标文种对应，综合吸收 `SRS / SDD / SDP / SEMP / RTVM / QA / CM` 体系化组织思路  
**当前状态：** 基线

本文件用于定义 `JB_DOC` 的角色、边界、对象层级与当前使用方法。

## 2. 为什么必须建立 `JB_DOC`

`CodeFactoryV2` 同时具有两种身份：

- 它本身是一个正在被研发的软件工厂平台
- 它又是一个将来要生成其他软件交付物的软件系统

这意味着项目天然存在两套不同但相关的文档需求：

- 平台自身研发与治理文档
- 平台未来生成的软件交付文档与模板文档

如果把这两类对象硬塞进一套目录，就会出现：

- 工程治理文档与交付文种混写
- 阶段设计文档与交付模板边界失真
- 平台自身的“元设计”与平台将来产出的“实例设计”难以区分

`JB_DOC` 的存在，就是为了解决这个结构性冲突。

## 3. `JB_DOC` 的核心职责

`JB_DOC` 主要承担四项职责：

### 3.1 标准化副本表达

把已经在 `CODEX_DOC` 中稳定下来的平台边界、阶段接口、工程控制点和模板逻辑，重组为更接近标准文种的表达。

### 3.2 平台自身标准文档包

把软件工厂平台自身的：

- 规格说明
- 设计说明
- 系统工程管理计划
- 软件开发计划
- 配置、质量、追溯、验证发布文档

组织成一套可读、可追溯、可持续深化的候选文档包。

### 3.3 平台产物模板中心

为未来由软件工厂生成的软件需求、设计、测试、发布、移交等文档提供模板中心。

### 3.4 映射与追溯台账

明确：

- 每份 `JB_DOC` 文档来自哪些 `CODEX_DOC`
- 当前哪些标准对象已覆盖
- 哪些对象仍缺失
- 后续该先补哪些文种

## 4. `JB_DOC` 不承担什么职责

`JB_DOC` 不承担以下职责：

- 不替代 `DOC/CODEX_DOC/` 的研发正式文档根地位
- 不承接日常开发执行规程、聊天决策、阶段性过程记录
- 不把所有本地研发文档都复制一份过来
- 不保证每份文档都能与某个标准编号做到一一严格对应

因此，`JB_DOC` 不是“万能军标根”，而是“标准化副本与桥接根”。

## 5. 三层对象模型

为避免长期混淆，本目录统一采用三层对象模型。

### 5.1 第一层：平台研发层

这一层回答：

- 平台自身如何被研发
- 阶段边界、WBS、设计、测试、过程记录如何组织

其权威根是：

- `DOC/CODEX_DOC/`

### 5.2 第二层：平台产物模板层

这一层回答：

- 软件工厂未来应生成什么样的标准化需求、设计、测试、发布、移交模板

其主要落点是：

- `DOC/JB_DOC/02-软件工厂产物模板中心/`

### 5.3 第三层：项目实例交付层

这一层回答：

- 当软件工厂接入真实项目时，应如何形成项目级正式交付文档样例

其当前落点是：

- `DOC/JB_DOC/03-项目实例与样例/`

## 6. 当前版本的实际吸收范围

本轮 `JB_DOC` 已吸收新版 `CODEX_DOC` 的以下正式结论：

- `P1` 业务知识库的正式抽取链、治理发布、文档钻取、发布态浏览与 `P1 -> P2` 接口
- `P2` 需求分析系统的对象优先建模、双形态建模器、权威输出模型与边界
- `P3` 软件设计系统的输入输出契约、设计基线、设计说明投影、批次工单包与评审冻结链
- `P4` 工具仓库的总体设计，以及核心业务循环、运行时、服务边界、数据与投影专题
- `P6` 门户与平台入口的蓝图画布、平台入口和观察层定位

当前仍只吸收到总纲与边界层的对象：

- `P5` 软件构建系统

这意味着本轮 `JB_DOC` 的详实化是建立在真实来源之上的，而不是人工填充不存在的方案。

## 7. 文档详细程度的控制原则

“详实”在 `JB_DOC` 中不是指无节制扩写，而是至少满足以下条件：

- 能说明对象边界，而不是只给一句定位
- 能说明与 `P1 ~ P6` 的关系，而不是只做抽象描述
- 能回溯到 `CODEX_DOC` 中的正式设计或计划来源
- 能明确当前已完成、待完成和不可假设的部分
- 能支撑后续模板中心和实例样例继续深化

## 8. 当前使用结论

当前 `JB_DOC` 应被理解为：

- `CodeFactoryV2` 的标准化副本文档根
- 平台研发层到标准表达层的桥接器
- 平台产物模板层和未来实例层的上位组织基线
