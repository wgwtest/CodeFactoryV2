# 文种优先级路线图

## 1. 文档定位

**文档类别：** 标准化辅助文档  
**标准依据：** 结合当前标准对象、平台阶段主链与现有设计成熟度  
**当前状态：** 基线

本文件用于定义：在新版 `CODEX_DOC` 与新版 `JB_DOC` 的基础上，后续标准化建设应该优先补哪些对象，避免无序扩张。

## 2. 排序原则

当前排序遵循以下原则：

- 优先服务当前平台主链
- 优先补齐闭环能力，而不是单纯增加文种数量
- 优先补齐已经有正式设计来源但尚未形成验证 / 样例的对象
- 对尚无正式设计来源的对象，先保留边界，不虚构正文

## 3. 当前阶段性判断

### 3.1 已进入候选深化阶段的对象

- 平台规格说明
- 平台设计说明
- 系统工程管理计划
- 软件开发计划
- 配置管理计划
- 质量保证计划
- 技术评审与阶段门控说明
- 验证与发布策略

### 3.2 已进入阶段投影深化阶段的对象

- `P1` 业务知识库
- `P2` 需求分析系统
- `P3` 软件设计系统
- `P4` 工具仓库总体
- `P4` 四类专题
- `P6.1 / P6.2 / P6.3 / P6.4`

补充说明：

- 这些对象当前只是完成了“独立投影稿形成”
- 尚未完成“按真实主文种归并收敛”

### 3.3 已进入骨架增强阶段的对象

- 平台级 `RTVM`

### 3.4 尚处边界定义阶段的对象

- `P5` 平台详细设计
- 平台测试链实例
- 平台发布链实例

## 4. 推荐优先级

### 第一优先级：完成主文种归并

优先对象：

- `P1 / P2 / P3 / P4 总体 / P6` 阶段投影稿向平台规格说明、平台设计说明回并
- `P4` 四类专题向平台设计说明及其补充件回并
- 主文种与投影稿之间的“已吸收 / 待吸收”标记

原因：

- 当前 `A` 类只是完成了“拆投影”，还没有完成“收主文种”
- 若长期停留在独立投影稿层，会偏离真实文种的最终交付形态

### 第二优先级：补齐 `B1` 契约级源文

优先对象：

- `P1` 接口契约与产物 schema
- `P2` 子结构 schema 与导出契约
- `P3` 状态机与数据契约包
- `P4` 协议级 API / 事件 / 错误码契约

原因：

- 主文种归并完成后，下一步最能提升正文质量的才是这些契约级正式源文

### 第三优先级：补齐平台闭环硬缺口

优先对象：

- `P5` 独立详细设计
- 平台级 `RTVM` 继续实化
- 平台测试链应用样例

原因：

- 这是当前平台文档包由“设计充分”走向“闭环充分”的关键

### 第四优先级：补齐测试与验证链

优先对象：

- `STP`
- `STD`
- `STR`

原因：

- 这是从“能描述平台”走向“能证明平台”的关键跃迁

### 第五优先级：补齐发布与移交链

优先对象：

- `SPS`
- `SVD`
- `STrP`

原因：

- 这是从“能验证”走向“能发布、能交接”的关键补齐

### 第六优先级：扩展接口与数据库链

优先对象：

- `IRS`
- `IDD`
- `DBDD`

原因：

- 重要，但应晚于主链闭环与验证发布链

### 第七优先级：项目实例样例层

优先对象：

- 真实项目级 `SRS / SDD / RTVM / STP / STR / SVD` 样例

原因：

- 只有当模板、追溯、测试和发布链都基本稳定后，实例层才不会变成一次性样板

## 5. 当前推荐推进法

当前推荐顺序为：

1. 保持平台自身标准文档包与 `CODEX_DOC` 同步
2. 保持 `99-标准来源库/` 中 current baseline revision 证据与旧主号页状态标记同步
3. 先按归并矩阵把阶段 / 专题投影稿吸收到主文种
4. 再补 `B1` 契约级源文
5. `B1` 补完后增强主文种和仍需保留的专题补卷
6. 为 `P5` 建立独立设计来源
7. 把 `RTVM` 从骨架增强版推进到证据增强版
8. 形成平台级测试链应用证据
9. 形成平台级发布与移交样例
10. 再进入项目实例层

## 6. 当前结论

`JB_DOC` 后续建设不应追求“文种越多越好”，而应坚持：

- 主文种收敛优先
- 主链优先
- 闭环优先
- 证据优先
- 样例晚于基线
