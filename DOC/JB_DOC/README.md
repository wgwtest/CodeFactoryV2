# CodeFactoryV2 标准化副本文档根

本目录用于承接 `CodeFactoryV2` 的标准化副本体系。

它的职责不是替代 `DOC/CODEX_DOC/`，而是把已经在研发文档根中形成稳定边界的内容，按更接近美军 / DoD 软件文种的方式重新组织，形成：

- 平台自身标准文档包
- 软件工厂产物模板中心
- 项目实例样例预留层
- 来源映射、覆盖缺口与建设路线图

## 1. 与 `CODEX_DOC` 的关系

### 1.1 双根关系

- `DOC/CODEX_DOC/`
  - 平台研发层正式文档根
  - 负责工程治理、WBS、阶段设计、测试与过程记录
- `DOC/JB_DOC/`
  - 标准化副本层
  - 负责把适合标准化表达的对象重组为候选标准文档、模板中心和追溯台账

因此：

- `CODEX_DOC` 是研发权威根
- `JB_DOC` 是标准化投影根
- 二者互相关联，但不互相替代

### 1.2 当前版本特征

本轮 `JB_DOC` 已按新版 `CODEX_DOC` 吸收以下深度：

- `P1 / P2 / P3 / P4 / P6` 正式设计已进入平台自身标准文档包的来源范围
- `P1 / P2 / P3 / P4` 及 `P6` 的 `A` 类阶段 / 专题设计，已从平台总包中拆出并归档到 `01-平台自身标准文档/90-阶段专题投影附件/`
- 上述独立投影稿当前仅作为来源投影与追溯层，不等同于真实军标终态下的平级主文种
- 后续将按“主文种归并 + 附件/补卷保留”的方式，把可归并内容吸收到平台规格说明、平台设计说明及其补充件中
- `P4` 的总体设计、核心业务循环、运行时、服务边界、数据投影专题已进入平台设计说明与追溯层
- `P1` 的正式抽取硬约束、长文档抽取、文档级正式产物仓、文档钻取、治理发布等内容已进入平台规格 / 设计文档的产品定义部分

- 平台自身标准文档包当前统一挂接的标准依据，已收敛到 `DI-IPSC-82259 / DI-IPSC-82284 / DI-SESS-81785 / DI-IPSC-81427B / DI-SESS-80858D / DI-QCIC-81794A` 这组 current baseline 组合

## 4. 当前最重要的使用原则

### 4.1 不伪装标准原件

没有直接标准对象对应的文档，必须明确声明：

- 本地桥接文档
- 或标准化辅助文档

不得把本地发挥型内容伪装成军标原件。

### 4.2 允许 `N : M` 映射

- 一份 `JB_DOC` 文档可以综合多份 `CODEX_DOC`
- 一份 `CODEX_DOC` 也可以同时支撑多份 `JB_DOC`

因此，本目录从一开始就不追求“逐文件复制”，而追求“按标准对象重组”。

### 4.3 先拆投影，再按文种归并

阶段 / 专题投影稿当前存在的目的，是先把 `CODEX_DOC` 中已成熟的细节从平台总包中拆出来，确保：

- 来源不丢
- 细节不被摘要吞没
- 评审时能逐阶段核对

但它们不是最终交付态的平级主文种。

后续必须按 `04-映射与追溯/03-阶段专题投影归并矩阵.md`，将可归并内容吸收到：

- `01-软件工厂平台规格说明-候选.md`
- `02-软件工厂平台设计说明-候选.md`
- 必要时保留为附录、补充件或专题补卷

为避免主目录干扰阅读效率，阶段 / 专题投影稿当前统一收纳在：

- `DOC/JB_DOC/01-平台自身标准文档/90-阶段专题投影附件/`

### 4.4 先保证真实，再追求完整

本目录力求详实，但详实不等于补写不存在的内容。

当前仍缺少独立正式设计的对象，例如 `P5`，在 `JB_DOC` 中应明确写成：

- 边界已知
- 细节待补

而不是虚构细设。

## 5. 当前结论

`JB_DOC` 当前应被理解为：

- `CodeFactoryV2` 的标准化副本文档根
- 已经吸收新版 `CODEX_DOC` 主要阶段设计的正式标准化表达层
- 已建立阶段 / 专题投影到主文种的归并规则
- 后续模板中心与项目实例层的稳定承接基础
