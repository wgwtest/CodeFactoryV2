# P4 Runtime 协调器与队列投影稿

## 1. 文档定位

**文档类别：** 标准化投影文档  
**标准依据：** 主要服务平台设计说明中的运行时专题补充，不直接对应单一军标原件  
**当前状态：** 候选  
**主要来源文档：**

- `DOC/CODEX_DOC/02_设计说明/P4_工具仓库/P4-30-Runtime协调器与队列设计.md`

## 2. 投影目标

本专题用于把当前 `P4` 中“单个后台线程推进多个流程”的验证实现，投影为未来可独立演进的运行时设计对象。

核心关注点包括：

- `Runtime Coordinator`
- 标准后台任务模型 `Queue / Job`
- 分域执行器 `Worker`
- 租约、重试、恢复与投影刷新

## 3. 运行时总图

推荐总图为：

`API 命令入口 -> Runtime Job Store -> Queue Dispatcher -> Worker Pool -> Aggregate Update -> Projection Refresh -> Query Store`

其含义是：

- `API` 负责命令登记
- `Runtime Coordinator` 负责调度
- `Worker` 执行具体业务
- `Projection Refresh` 负责查询投影

## 4. 核心组件投影

### 4.1 Runtime Coordinator

职责：

- 拉取可执行任务
- 触发定时任务
- 管理租约
- 处理超时和重试
- 回收僵尸任务
- 触发投影刷新

### 4.2 Job Queue

职责：

- 承载所有异步任务
- 提供标准状态流转
- 保证任务顺序、租约和幂等

### 4.3 Worker Pool

职责：

- 按任务类型执行对应逻辑
- 不关心页面表现
- 不直接暴露对外接口

### 4.4 Lease Manager

职责：

- 分配执行租约
- 避免重复执行
- 支持续租与过期回收

## 5. 任务模型投影

本专题已明确运行时任务至少具备：

- 任务类型
- 生命周期
- 租约语义
- 失败分类
- 重试策略
- 死信处理
- 触发模型
- 投影刷新机制

这使得 `P4` 可以从 MVP 级后台 tick 演进到更稳定的运行时抽象。

## 6. 与总体设计的关系

本专题不替代 `P4` 总体设计，而是专门回答：

- 业务逻辑如何被后台推进
- 运行推进如何与业务规则解耦
- 后续怎样从单体后台演进到独立运行时服务

## 7. 当前未纳入投影的缺口声明

本投影稿当前**不补写**以下内容：

- `RuntimeJob` 等对象的字段级 schema
- 任务事件 payload
- 具体中间件或消息队列产品选型

这些内容仍应等待 `B1` 契约补源与后续实现落版。

## 8. 当前结论

`P4 Runtime` 当前已形成足够成熟的专题级正式设计来源。

因此，它应被作为独立运行时专题投影进入 `JB_DOC`。
