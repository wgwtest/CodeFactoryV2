# P2 需求分析系统投影稿

## 1. 文档定位

**文档类别：** 标准化投影文档  
**标准依据：** 主要服务平台规格说明与平台设计说明的阶段级补充，不直接对应单一军标原件  
**当前状态：** 候选  
**主要来源文档：**

- `DOC/CODEX_DOC/02_设计说明/P2_需求分析系统/P2-需求分析系统设计.md`
- `DOC/CODEX_DOC/02_设计说明/00_总纲/00-软件工厂平台总体设计.md`

本文件用于把 `P2` 从平台总包中的摘要状态，提升为可单独阅读、可单独评估质量的阶段投影对象。

## 2. 投影目标

`P2` 在平台主链中的职责不是“低代码原型器”，而是：

- 面向非技术行业专家的需求建模层
- 知识仓与软件设计系统之间的过渡层
- 用户意图到结构化需求对象之间的翻译层

其首版权威输出不是说明文档，而是结构化需求对象。

## 3. 阶段职责重组

### 3.1 当前负责

- 提供交互式需求建模器
- 支持业务目标、对象、模块、动作、交接层面的逐步建模
- 消费 `P1` 已发布知识元素
- 允许当场新建临时元素并标记 `待入库`
- 输出结构化需求对象与 `MD` 可读投影

### 3.2 当前不负责

- 组件命中推荐与复用判断
- 软件设计说明生成
- 工具仓库资产管理
- 可运行原型生成
- 专业低代码建模平台

### 3.3 对象优先原则

`P2` 必须坚持“对象优先于流程”。

原因不是偏好问题，而是：

- 对象建模要素更完整
- 系统要支持探索新流程
- 多对象跨流程应用是核心场景

## 4. 交互形态与建模步骤

### 4.1 双形态建模器

`P2` 当前正式支持两种互补形态：

- `表单式建模器 + 智能推荐`
- `选配式建模器`

二者共享同一权威对象，不应被实现为两套割裂系统。

### 4.2 默认主路径

首版默认路径固定为：

`先向导收敛 -> 再进入按场景 / 模块组织的选配建模`

这保证用户先完成业务目标和边界收敛，再进入模块级建模。

### 4.3 标准建模步骤

首版按以下 6 段推进：

1. 业务目标收敛
2. 使用对象与范围收敛
3. 自建模块
4. 模块内动作建模
5. 模块链路与交接动作
6. 自动页面建议与输出

### 4.4 页面骨架

`P2` 首版沿用三栏工作台：

- 左侧：步骤导航
- 中间：当前步骤提问、模块搭建、推荐项与手工补充
- 右侧：实时预览，包括模块骨架、动作链、模块交接和页面建议

## 5. 推荐体系投影

### 5.1 推荐来源

`P2` 的推荐当前固定来自三层：

- 通用应用知识
- `P1` 已发布领域知识
- 用户当前输入

### 5.2 推荐触发规则

首版至少固定以下触发：

- 写完 `模块名 + 用途` 后推荐动作候选
- 新建动作后推荐参与方、业务对象和结果状态
- 形成多个模块后推荐模块间交接动作
- 模块与动作骨架稳定后推导页面模板建议

### 5.3 来源标识与解释

每个建模项都必须带来源标识：

- `recommended_common`
- `recommended_domain`
- `manual`
- `temporary_pending_intake`

系统至少要能解释：

- 为什么推荐某类通用模式
- 为什么某个知识项与当前模块或动作相关
- 为什么建议某个交接点或页面模板

## 6. 权威输出模型

### 6.1 权威对象

`P2` 当前固定的权威输出对象为：

- `ApplicationRequirementModel`

其当前稳定顶层结构包括：

- `application_goal`
- `audiences`
- `roles`
- `modules`
- `actions`
- `business_objects`
- `module_handoffs`
- `page_suggestions`
- `knowledge_references`
- `temporary_elements`
- `draft_meta`

### 6.2 结构化优先规则

当前投影必须固定以下规则：

- 结构化对象是唯一权威输出
- `MD` 只是可读投影
- 每个核心项应具备稳定 `id`
- 推荐项、手工项、临时项必须能追溯来源
- `page_suggestions` 只表达页面模板建议，不提前混入组件资产

## 7. 投影与状态

### 7.1 `MD` 投影

首版 `MD` 投影至少包含：

- 应用名称与目标
- 受众与业务分工
- 模块清单与用途
- 每个模块的动作集合
- 模块间交接关系
- 自动页面建议
- 引用的领域知识
- 手工补充项和临时新增项

### 7.2 草稿状态

当前已收敛的状态包括：

- `draft`
- `completed`
- `exported`

### 7.3 最小完成条件

至少满足以下条件，才能标记完成：

- 有业务目标
- 有至少一类使用对象
- 有至少一个模块
- 每个动作包含 `参与方 + 业务对象 + 行为 + 结果`
- 已生成至少一项结构预览

## 8. 与上下游的关系

### 8.1 上游关系

`P2` 只消费 `P1` 的发布态知识结果，不消费治理中间态。

### 8.2 下游关系

`P2` 对 `P3` 的正式输出，应理解为：

- 已冻结的需求规格说明
- 结构化需求对象及其文档投影
- 可追溯的业务目标、模块、动作与知识引用

### 8.3 `P2-Sim`

`P2-Sim` 在首版中是 `P2` 的轻量模拟输入台，用于：

- 从预置样板生成最小 `RequirementSpec`
- 向现有规格池写入上游联调入口

它不是独立于 `P2` 主线之外的旁路系统。

### 8.4 首版模块与实现范围

首版建议至少拆为以下 5 个模块：

- 建模器前端
- 向导收敛服务
- 模块建模服务
- 推荐编排服务
- 结果投影服务

首版最小实现范围固定为：

- 独立“应用需求建模器”页面
- 默认主路径：`向导收敛 -> 模块建模 -> 自动页面建议`
- 左中右三栏布局
- 用户自建模块
- 模块内动作卡片建模
- 右侧实时链路与模块交接预览
- 临时元素标记
- 草稿保存 / 恢复 / 完成
- 导出 `JSON / YAML + MD`

## 9. 当前未纳入投影的缺口声明

本投影稿当前**不补写**以下内容：

- `ApplicationRequirementModel` 的子结构 schema
- 正式导出契约
- 版本字段、兼容策略、导入回放规则和样例

这些内容已经被矩阵归入 `B1`，应先补到 `CODEX_DOC` 再继续投影。

## 10. 当前结论

`P2` 当前已经具备稳定的阶段目标、交互形态、权威输出模型与上下游边界。

因此：

- `P2` 不再应只以平台总包中的几段摘要存在
- 应作为独立阶段投影对象进入 `JB_DOC`

本文件承担这一投影职责。
