# P1 业务知识库投影稿

## 1. 文档定位

**文档类别：** 标准化投影文档  
**标准依据：** 主要服务平台规格说明与平台设计说明的阶段级补充，不直接对应单一军标原件  
**当前状态：** 候选  
**主要来源文档：**

- `DOC/CODEX_DOC/02_设计说明/02-P1-业务知识库设计.md`
- `DOC/CODEX_DOC/02_设计说明/00-软件工厂平台总体设计.md`

本文件用于把 `CODEX_DOC` 中已经成熟的 `P1` 阶段正式设计，按标准化副本层的阅读方式重组出来，避免 `P1` 只以摘要形式淹没在平台总包文档中。

## 2. 投影目标

`P1` 在平台主链中的职责不是“资料上传页”，而是从业务资料到已发布知识仓的正式前置阶段。

本投影稿固定以下认识：

- `P1` 是平台知识供给层
- `P1` 的正式结果是已发布知识，不是候选知识
- `P1` 必须向 `P2` 提供稳定、可解释、可追溯的业务元素出口

## 3. 阶段职责重组

### 3.1 当前负责

- 接收 `PDF / DOC / DOCX` 等业务资料
- 生成保留章节、块、页码、锚点的结构化解析结果
- 抽取实体、事件、流程、规则、指标与关系
- 提供人工治理、审核、发布与版本管理
- 提供发布态知识查询、图谱浏览、流程浏览与文档钻取

### 3.2 当前不负责

- 需求建模
- 软件设计对象生成
- 组件/工具命中与复用判断
- 最终软件装配与交付

### 3.3 阶段原则

- 只向下游暴露标准成果物
- 正式抽取链与调试链严格分离
- 节点串行推进，但通过稳定成果物解耦
- 已发布知识必须能解释“它是什么、与谁相关、证据在哪、由谁贡献”

## 4. 阶段内部链

`P1` 的正式闭环应被理解为：

`P1.1 功能验证平台底座 -> P1.2 文档接入与结构化解析 -> P1.3 候选知识抽取 -> P1.4 知识治理与发布 -> P1.5 已发布知识仓、查询与图谱展示`

各节点职责如下：

- `P1.1`
  - 承载验证页面、详情抽屉、状态透传与证据查看
- `P1.2`
  - 解决受控接入、归档、版本与结构化解析
- `P1.3`
  - 从结构化片段生成候选知识与文档级正式产物
- `P1.4`
  - 承担术语归并、关系修正、流程补链、审核发布
- `P1.5`
  - 只消费已发布知识，形成列表、图谱、流程与文档钻取

## 5. 核心对象与正式链

### 5.1 核心对象

`P1` 当前已经具备稳定投影基础的对象包括：

- `Entity`
- `Event`
- `Process`
- `Rule`
- `Metric`
- `Relation`
- `Evidence`
- `KnowledgeVersion`

这些对象共同回答：

- 知识对象本体是什么
- 它与哪些对象相关
- 它由哪些文档支撑
- 当前发布版本是什么

### 5.2 正式抽取链

`P1` 的正式抽取链当前已固定为：

`结构化分块 -> 分块抽取 -> 全局归并 -> 治理 / 发布`

关键约束包括：

- 正式解析以 `Docling` 为主
- 长文档按章节、块、表格、列表构建语义块
- 多块分别执行规则抽取与结构化大模型抽取
- 文档级统一归并术语、别名、关系和证据
- 至少保留章节/块级证据回溯

### 5.3 文档级正式产物账本

每篇文档的正式产物至少独立保存：

- 文档元数据
- 文档级候选知识
- 文档级关系贡献
- 抽取执行元数据
- `included_in_archive`

这意味着：

- “是否有正式产物”
- “是否并入当前正式全集”

两者被明确拆开，不再混为一个动作。

## 6. 治理、发布与浏览

### 6.1 治理工作台

当前投影应固定以下治理能力：

- 候选项筛选
- 术语归并
- 关系修正
- 流程补链
- 批量审核通过 / 驳回
- 审核留痕与状态回显

### 6.2 发布态浏览

已发布知识浏览当前采用：

- 类型筛选：`实体 / 事件 / 流程`
- 视图切换：`列表 / 图谱`
- 来源文档筛选：`全部 / 指定文档集合`

文档钻取必须能回答：

- 这篇文档关联了哪些知识
- 当前是否正式并入
- 运行状态与贡献范围是什么

## 7. 与上下游的关系

`P1 -> P2` 当前只暴露发布态知识结果，包括：

- 已发布实体、事件、流程、规则、指标
- 单项详情
- 关系邻域
- 搜索与筛选能力
- 来源文档与证据回溯

`P2` 不应直接读取：

- 候选知识
- 治理中间态
- 审核工作数据
- 内部脚本和文件组织细节

## 8. 当前未纳入投影的缺口声明

本投影稿当前**不补写**以下内容：

- `P1` 协议级接口契约包
- 文档级正式产物与执行报告的字段级 schema
- 请求/响应结构、错误码与样例

这些内容已经被矩阵归入 `B1`，应先在 `CODEX_DOC` 中补成正式契约，再投影到 `JB_DOC`。

## 9. 当前结论

`P1` 已经具备完整的阶段级正式设计来源，当前问题不再是“有没有 `P1` 设计”，而是：

- 不能再只把它埋在平台规格/平台设计总包里
- 应把其阶段职责、正式抽取链、治理发布和发布态出口独立投影出来

本文件即承担这一阶段级投影职责。
