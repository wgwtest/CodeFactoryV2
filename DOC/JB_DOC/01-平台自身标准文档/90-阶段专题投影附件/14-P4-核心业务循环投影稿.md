# P4 核心业务循环投影稿

## 1. 文档定位

**文档类别：** 标准化投影文档  
**标准依据：** 主要服务平台设计说明中的运行链专题补充，不直接对应单一军标原件  
**当前状态：** 候选  
**主要来源文档：**

- `DOC/CODEX_DOC/02_设计说明/06-P4-核心业务循环设计.md`

本文件用于把 `P4` 的统一业务循环从平台设计说明摘要中拆出，作为独立专题投影。

## 2. 投影目标

本专题固定的不是某个页面怎么画，而是 `P4` 的统一后台推进语义：

`接收命令 -> 写入业务事实 -> 投递后台任务 -> 统一调度 -> 分域执行 -> 刷新查询投影 -> 对外供给查询 -> 留痕与回退`

## 3. 核心循环投影

### 3.1 统一总图

`外部命令 / 定时触发 -> Command Intake -> Fact Persistence -> Job Dispatch -> Runtime Scheduling -> Domain Execution -> Projection Refresh -> 页面 / P5 查询 -> Audit and Recovery`

### 3.2 统一阶段

- `Command Intake`
  - 参数校验、幂等校验、边界校验
- `Fact Persistence`
  - 将业务事实写成稳定对象
- `Job Dispatch`
  - 把长耗时动作转成标准后台任务
- `Runtime Scheduling`
  - 处理调度、重试、超时、补偿、恢复
- `Domain Execution`
  - 由分域 Worker 执行具体逻辑
- `Projection Refresh`
  - 刷新只读投影
- `Audit and Recovery`
  - 留痕、回退与补偿

## 4. 两类业务闭环的统一承载

本统一循环必须同时承载：

- 外部输入闭环
- 内部自演进闭环

这意味着：

- 不能为 `P4.2` 和 `P4.3` 各自维护互不相干的后台推进方式
- 页面查询与 `P5` 查询都只读投影，不直接拼原始事实

## 5. 状态与完成判定

当前专题已固定：

- 存在显式状态流
- 存在完成判定
- 存在失败、重试、回退与审计口径

这一层的目标是让 `P4` 不再只是“若干后台函数在推进”，而是可被解释为稳定业务中台。

## 6. 与上下游的关系

### 6.1 与 `P3`

`P3` 负责输入供给目标与业务语义，不负责 `P4` 内部推进。

### 6.2 与 `P5`

`P5` 只负责消费结果。

`P5` 能做：

- 查询终态结论
- 获取交付结果
- 读取所需约束与说明

`P5` 不能做：

- 直接回写 `P4` 内部状态
- 直接向 `P4` 下发修旧工具命令

### 6.3 `P5` 问题进入路径

`P5` 装配失败、资产不匹配、构建阻塞等反馈，默认进入 `P3` 仲裁，而不是直接进入 `P4` 命令队列。

## 7. 当前未纳入投影的缺口声明

本投影稿当前**不补写**以下内容：

- 状态转换表的字段级定义
- API 协议说明
- 事件 payload 结构

这些内容应继续等待 `B1` 契约文档补源。

## 8. 当前结论

`P4` 的核心业务循环当前已经具备独立专题投影条件。

它不应继续只作为总体设计中的一节摘要存在。
