## 2. 适用范围

本规格说明覆盖平台自身的六个一级阶段对象：

- `P1` 业务知识库
- `P2` 需求分析系统
- `P3` 软件设计系统
- `P4` 工具仓库
- `P5` 软件构建系统
- `P6` 门户与平台入口

本文件不覆盖：

- 具体业务项目的实例交付文档
- 单个页面的视觉细节
- 某个阶段内部实现文件级设计
- `B1` 契约级 schema、错误码和字段级接口定义

## 3. 平台概述

### 3.1 平台目标

`CodeFactoryV2` 的目标是构建一条“知识驱动的软件工厂主链”，使行业专家、技术专家与平台本身形成可追溯的协同闭环：

`P1 业务知识库 -> P2 需求分析系统 -> P3 软件设计系统 -> P4 工具仓库 -> P5 软件构建系统`

`P6` 负责统一门户、导航、观察和平台级入口治理。

### 3.2 关键用户与使用方

平台当前主要面对以下对象：

| 对象 | 角色说明 | 主要关注点 |
| --- | --- | --- |
| 行业专家 | 不懂技术但懂业务 | 用知识元素和引导式建模表达需求 |
| 技术专家 | 参与设计判断、评审与冻结 | 把需求转为设计、审定工具化描述 |
| 平台研发者 | 维护平台自身 | 保证阶段边界、运行时、模板和标准副本稳定 |
| 平台操作者 | 运行治理、审核、验证 | 审核知识、观察门户、检查闭环状态 |

### 3.3 平台使用主线

平台应支持以下主线使用场景：

1. 接入业务资料，形成已发布知识仓。
2. 基于发布态知识进行交互式需求建模。
3. 将结构化需求转化为设计基线和设计说明投影。
4. 把设计中的模块级描述送入工具中台执行匹配、供给或研制。
5. 基于设计结果和工具资产形成目标软件或元数据应用。
6. 由门户统一承载入口、观察和导航。

## 4. 平台能力需求

### 4.1 `P1` 业务知识库能力需求

`P1` 是平台知识供给层，其正式结果是已发布知识，而不是候选知识列表。

平台应支持：

- 接收 `PDF / DOC / DOCX` 等业务资料。
- 生成保留章节、块、页码、锚点的结构化解析结果。
- 抽取实体、事件、流程、规则、指标与关系。
- 提供人工治理、审核、发布与版本管理。
- 提供发布态知识查询、图谱浏览、流程浏览与文档钻取。

`P1` 的正式内部链应固定为：

`P1.1 功能验证平台底座 -> P1.2 文档接入与结构化解析 -> P1.3 候选知识抽取 -> P1.4 知识治理与发布 -> P1.5 已发布知识仓、查询与图谱展示`

平台应至少围绕以下知识对象组织 `P1` 正式出口：

- `Entity`
- `Event`
- `Process`
- `Rule`
- `Metric`
- `Relation`
- `Evidence`
- `KnowledgeVersion`

平台应向 `P2` 暴露以下发布态能力：

- 已发布实体、事件、流程、规则、指标。
- 单项详情与关系邻域。
- 搜索与筛选能力。
- 来源文档与证据回溯。

关键约束：

- 正式抽取链必须与调试链严格分离。
- 正式抽取链不得静默降级到轻量规则链。
- 已发布知识必须可回答“它是什么、与谁相关、证据在哪、由谁贡献”。
- 每篇文档的正式产物至少要区分“已抽取正式产物”和“是否并入当前正式全集”。

### 4.2 `P2` 需求分析系统能力需求

`P2` 是知识仓与软件设计系统之间的过渡层，也是用户意图到结构化需求对象之间的翻译层。

平台应支持：

- 面向非技术行业专家的交互式需求建模。
- 业务目标、对象、模块、动作、交接层面的逐步建模。
- 消费 `P1` 已发布知识元素。
- 允许当场新建临时元素并标记 `待入库`。
- 输出结构化需求对象与 `MD` 可读投影。

`P2` 必须坚持“对象优先于流程”，因为：

- 对象建模要素更完整。
- 系统需要支持探索新流程。
- 多对象跨流程应用是核心场景。

`P2` 当前正式支持两种互补交互形态：

- `表单式建模器 + 智能推荐`
- `选配式建模器`

两种形态必须共享同一权威对象，不得被实现为两套割裂系统。

平台应按以下 6 段推进标准建模过程：

1. 业务目标收敛。
2. 使用对象与范围收敛。
3. 自建模块。
4. 模块内动作建模。
5. 模块链路与交接动作。
6. 自动页面建议与输出。

`P2` 当前固定的权威输出对象为：

- `ApplicationRequirementModel`

其稳定顶层结构至少应包括：

- `application_goal`
- `audiences`
- `roles`
- `modules`
- `actions`
- `business_objects`
- `module_handoffs`
- `page_suggestions`
- `knowledge_references`
- `temporary_elements`
- `draft_meta`

关键约束：

- 结构化对象是唯一权威输出。
- `MD` 只是可读投影，不是事实源。
- 推荐项、手工项、临时项必须保留来源标记。
- `page_suggestions` 只表达页面模板建议，不提前混入组件资产。

### 4.3 `P3` 软件设计系统能力需求

`P3` 的职责不是直接写几份设计文档，而是把冻结需求规格转化为结构化设计基线、设计说明投影和面向 `P4` 的工单包。

平台应支持：

- 接收已冻结、状态明确、可追溯的需求规格说明。
- 完成接入登记、快照留存、结构解析和设计分析。
- 创建并推进 `P3Order`。
- 生成软件设计说明草案并支持人工修订。
- 生成人工评审、冻结与批次工单包。
- 记录 `P2 -> P3 -> P4` 的追溯链。

`P3` 的正式输入不得被当作黑盒文档直接送入生成器，而必须先完成：

- 接入登记。
- 快照留存。
- 结构解析。
- 设计分析。

`P3` 的正式输出应是三层一致的结果：

| 层次 | 正式对象 | 用途 |
| --- | --- | --- |
| 内部权威层 | `SoftwareDesignBaseline` | 结构化设计事实源 |
| 文档投影层 | `SoftwareDesignDescription` | 人工评审、冻结和留档 |
| 交接投影层 | `ModuleWorkorderBatchPackage` | 向 `P4` 下发模块级实现需求 |

`ModuleWorkorderBatchPackage` 至少要表达：

- 包级总体建议。
- 条目级模块需求。
- 输入输出。
- 约束条件。
- 验收要点。
- 推荐工具能力。

关键约束：

- 设计说明与工具化描述不是并列终物。
- 正确顺序是：结构化设计对象 -> 设计说明投影 -> 人工校核 -> 工具化描述。
- `P3` 的冻结不是永不再开，但只能在 `P5` 可行性反馈进入正式仲裁后按规则重开。

### 4.4 `P4` 工具仓库能力需求

`P4` 是工具中台，不是工具列表页。它同时承担外部输入闭环、内部自演进闭环和公共运行骨架。

平台应支持：

- 工具、组件、执行器资产的结构化登记。
- 工具需求单与叶子需求项的受理、匹配、审定与供给。
- 工具池自演进巡检、发现项处置、内部任务推进与回退。
- 统一数据快照与驾驶舱验证工作台。
- 对 `P5` 可查询、可获取的结果出口。

`P4` 的三条基础运行链应固定为：

- 外部输入闭环：
  - `工具需求单 -> 拆叶子工具项 -> 匹配 -> 审定 -> 直接交付或进入研制 -> 对 P5 提供查询与获取`
- 内部自演进闭环：
  - `工具仓快照 -> 巡检 -> 发现项 -> 采纳/忽略 -> 内部任务 -> 自动改写或人工跟进 -> 回退`
- 公共运行骨架：
  - `命令接入 -> 事实写入 -> 任务投递 -> 调度 -> 分域执行 -> 查询投影刷新 -> 审计与回退`

平台应至少围绕以下对象组织 `P4` 资产与需求能力：

- `ToolDefinition`
- `ToolDemandSheet`
- `ToolDemandItem`
- `ToolSupplyResult`
- 工具仓快照
- 巡检发现项
- 内部任务

关键约束：

- 查询动作不得反向驱动内部推进。
- `P4` 只能通过标准契约与 `P1 / P3 / P5` 耦合。
- `P4` 不直接接受来自 `P5` 的业务不匹配修订命令。
- 若属于供给缺口，应由 `P3` 向 `P4` 下发新供给任务、派生任务或组件拆分任务。

### 4.5 `P5` 软件构建系统能力需求

平台应支持：

- 消费需求规格、设计对象与工具资产命中结果。
- 形成可运行的软件或元数据应用。
- 沉淀可复用的构建资产。

当前限制：

- `P5` 已知职责与接口边界已明确。
- `P5` 独立详细设计尚未形成，后续需在 `CODEX_DOC` 和 `JB_DOC` 中继续补齐。

### 4.6 `P6` 门户与平台入口能力需求

`P6` 是平台层，不改变 `P1 -> P5` 主链，但负责统一入口、统一观察、统一读侧集成、统一设计语言和前端展示实验。

平台应支持以下四类能力：

- `P6.1` 首屏观察门户：
  - 独立路由 `/portal`
  - 全屏、可拖拽、可缩放的蓝图画布
  - 阶段主节点与主链路表达
  - 单击高亮、双击进入模块
  - 门户级投影摘要与布局记忆
- `P6.2` 跨阶段只读集成与状态投影：
  - 查询阶段概览
  - 查询入口可用性
  - 查询摘要指标、健康信息和告警摘要
  - 订阅阶段状态变化
  - 将阶段数据归一为平台投影对象
- `P6.3` 设计语言与前端展示基线：
  - 统一阶段命名
  - 统一状态文案与状态色
  - 统一总览条、摘要卡、详情抽屉和双视图基础交互语义
  - 统一空态、加载态、错误态
- `P6.4` 前端展示工具化实验场：
  - 定义展示工具化的最小对象模型
  - 提供展示模板、数据绑定、布局组合和预设的实验框架
  - 记录实验结果并向 `P3 / P4 / P5` 反哺

关键约束：

- `P6` 默认只读，不得反写 `P1 ~ P5` 内部事实对象。
- 不得把临时脚本输出伪装成正式读侧接口。
- 门户首版不以弹窗为主交互，不承载遮挡主画布的大表头。
- `P6.R1` 登录接入与 `P6.R2` 权限控制当前仍是后置能力，不应被伪装为已冻结能力。

## 5. 接口与成果物需求

### 5.1 阶段接口语义

平台应固定以下阶段接口语义：

| 阶段接口 | 正式输入 | 正式输出 | 明确禁止 |
| --- | --- | --- | --- |
| `P1 -> P2` | 业务资料与治理后的发布动作 | 已发布知识对象、搜索筛选、关系邻域、来源回溯 | 暴露候选知识、治理中间态、内部脚本产物 |
| `P2 -> P3` | 已发布知识元素、用户建模输入 | 冻结需求规格、结构化需求对象及其文档投影 | 以页面状态或未冻结草稿替代正式需求对象 |
| `P3 -> P4` | 冻结需求规格 | 设计对象投影、批次工单包、工具化描述 | 直接把人工意见或聊天内容当成工单 |
| `P4 -> P5` | 设计供给目标、资产需求 | 资产命中结果、供给结果、运行约束、查询与获取出口 | 允许 `P5` 反写 `P4` 内部状态 |
| `P1~P5 -> P6` | 各阶段正式查询/订阅接口 | 阶段概览、入口投影、指标投影、健康投影 | 直接暴露内部数据库、私有页面状态或临时脚本结果 |

### 5.2 权威成果物

平台至少应围绕以下权威成果物组织：

| 成果物 | 所属阶段 | 最低语义 |
| --- | --- | --- |
| `PublishedKnowledge` | `P1` | 已发布知识集合及其来源、证据、版本语义 |
| `ApplicationRequirementModel` | `P2` | 业务目标、受众、角色、模块、动作、交接、知识引用、临时元素 |
| `SoftwareDesignBaseline` | `P3` | 结构化设计事实源 |
| `SoftwareDesignDescription` | `P3` | 面向人工评审与冻结的文档投影 |
| `ModuleWorkorderBatchPackage` | `P3` | 面向 `P4` 的模块级实现需求与包级总体建议 |
| `ToolDefinition` | `P4` | 工具身份、形态、输入输出、宿主约束、契约引用 |
| `ToolDemandSheet / ToolDemandItem` | `P4` | 工具供给需求整单与叶子项生命周期 |
| `ToolSupplyResult` | `P4` | 资产命中、供给、研制或驳回结论 |
| `StageSnapshot / PortalProjection / ObservationProjection` | `P6` | 面向门户和观察页的读侧投影对象 |

### 5.3 门户只读集成契约

每个阶段至少应向 `P6` 提供以下最小查询对象：

- `StageOverview`
- `StageEntryProjection`
- `StageMetricProjection`
- `StageHealthProjection`

当阶段具备订阅能力时，推荐统一事件包络：

- `eventType`
- `stageId`
- `timestamp`
- `payload`
- `source`

平台级读模型应至少包括：

- `StageSnapshot`
- `PortalProjection`
- `ObservationProjection`

每份读侧结果必须显式标注：

- 来源
- 时间戳
- 新鲜度
- 降级状态

## 6. 非功能需求

### 6.1 追溯性

平台应保证：

- 关键对象可回溯到上游来源文档或上游阶段对象。
- 关键发布结论可回溯到审定、评审或验证证据。
- 门户和观察页中的读侧结果可回溯到阶段接口来源。

### 6.2 可解释性

平台不应只给出黑盒结果，应能解释：

- 为什么推荐某业务元素。
- 为什么某设计项被拆成某批工单。
- 为什么某工具被命中、驳回或转研制。
- 为什么某门户状态是当前显示结果。

### 6.3 解耦性

平台各阶段只允许依赖标准成果物，不应依赖：

- 上游页面状态。
- 上游未发布 JSON。
- 未冻结草稿或临时脚本产物。
- 对方阶段的内部表结构。

### 6.4 审计与治理能力

平台应具备：

- 审核、发布、移出、回退等关键动作的记录能力。
- 关键运行任务的状态、失败、重试和进度留痕能力。
- 变更前后快照、回退记录和执行账本。

### 6.5 数据新鲜度与降级标注

平台级读侧展示必须显式表达：

- 数据何时生成。
- 数据来自哪个阶段。
- 当前是否发生降级。
- 当前展示是否属于最终一致快照。

### 6.6 门户可观察性

平台应提供门户级状态观察，至少可表达：

- 主链阶段。
- 当前知识库。
- 关键入口可用性。
- 主要流向和节点关系。
- 阶段指标、健康状态和告警摘要。

### 6.7 展示一致性

平台级页面应统一：

- 阶段命名。
- 状态文案与状态色。
- 总览条与摘要卡表达。
- 列表 / 图谱 / 抽屉 / 筛选条的基础交互语义。
- 页面空态、加载态、错误态。

## 7. 约束条件

平台当前必须遵守以下约束：

- 结构化对象优先于文档投影。
- 下游只消费上游标准成果物。
- 正式抽取链与调试链严格分离。
- 正式知识抽取不得静默降级。
- 读模型与写模型分离，查询与推进分离。
- 组件 / 工具闭环发生在应用生成过程中，而不是应用完成之后。
- `P5` 的装配失败、资产不匹配和构建阻塞默认先回到 `P3` 仲裁。
