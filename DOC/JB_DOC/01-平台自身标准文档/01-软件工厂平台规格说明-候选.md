## 2. 适用范围

本规格说明覆盖平台自身的六个一级阶段对象：

- `P1` 业务知识库
- `P2` 需求分析系统
- `P3` 软件设计系统
- `P4` 工具仓库
- `P5` 软件构建系统
- `P6` 门户与平台入口

本文件不覆盖：

- 具体业务项目的实例交付文档
- 单个页面的视觉细节
- 某个阶段内部实现文件级设计

## 3. 平台概述

### 3.1 平台目标

`CodeFactoryV2` 的目标是构建一条“知识驱动的软件工厂主链”，使行业专家、技术专家与平台本身形成可追溯的协同闭环：

`P1 业务知识库 -> P2 需求分析系统 -> P3 软件设计系统 -> P4 工具仓库 -> P5 软件构建系统`

`P6` 负责统一门户、导航、观察和平台级入口治理。

### 3.2 关键用户与使用方

平台当前主要面对以下对象：

| 对象 | 角色说明 | 主要关注点 |
| --- | --- | --- |
| 行业专家 | 不懂技术但懂业务 | 用知识元素和引导式建模表达需求 |
| 技术专家 | 参与设计判断、评审与冻结 | 把需求转为设计、审定工具化描述 |
| 平台研发者 | 维护平台自身 | 保证阶段边界、运行时、模板和标准副本稳定 |
| 平台操作者 | 运行治理、审核、验证 | 审核知识、观察门户、检查闭环状态 |

### 3.3 平台使用主线

平台应支持以下主线使用场景：

1. 接入业务资料，形成已发布知识仓
2. 基于发布态知识进行交互式需求建模
3. 将结构化需求转化为设计基线和设计说明投影
4. 把设计中的模块级描述送入工具中台执行匹配、供给或研制
5. 基于设计结果和工具资产形成目标软件或元数据应用
6. 由门户统一承载入口、观察和导航

## 4. 平台能力需求

### 4.1 `P1` 业务知识库能力需求

平台应支持：

- 接收 `PDF / DOC / DOCX` 等业务资料
- 进行结构化解析、知识抽取、治理发布和发布态浏览
- 形成实体、事件、流程、规则、指标和关系对象
- 提供来源文档、证据摘录和版本化回溯能力
- 向 `P2` 输出已发布业务元素和检索筛选能力

关键约束：

- 正式知识抽取链必须与调试/预览链分离
- 正式抽取不得静默降级到轻量规则链
- 已发布知识必须可回答“它是什么、与谁相关、证据在哪”

### 4.2 `P2` 需求分析系统能力需求

平台应支持：

- 面向非技术行业专家的交互式建模
- 以对象优先方式组织需求，而不是以现成组件驱动建模
- 双形态建模入口：`表单式建模器 + 智能推荐` 与 `选配式建模器`
- 引用 `P1` 已发布知识元素，并允许创建临时元素
- 输出结构化 `ApplicationRequirementModel / RequirementSpec`

关键约束：

- 权威输出必须是结构化对象，而不是说明文档
- 模型中的推荐项、手工项、临时项都必须有来源标记

### 4.3 `P3` 软件设计系统能力需求

平台应支持：

- 接收冻结后的需求规格说明
- 形成结构化设计基线
- 生成软件设计说明投影
- 支持人工评审、修订和冻结
- 生成面向 `P4` 的模块级 / 子模块级工具化描述和批次工单包

关键约束：

- 设计说明与工具化描述不是并列终物
- 正确顺序是：结构化设计对象 -> 设计说明投影 -> 人工校核 -> 工具化描述

### 4.4 `P4` 工具仓库能力需求

平台应支持：

- 工具、组件、执行器资产的结构化登记
- 工具需求单和叶子工具项的匹配、审定、供给或研制
- 工具池自演进巡检、发现项处置、内部任务推进与回退
- 运行时推进、查询投影和统一快照工作台

关键约束：

- 查询动作不得反向驱动内部推进
- `P4` 应通过标准契约与 `P1 / P3 / P5` 耦合，而不依赖其内部工作态

### 4.5 `P5` 软件构建系统能力需求

平台应支持：

- 消费需求规格、设计对象与工具资产命中结果
- 形成可运行的软件或元数据应用
- 沉淀可复用的构建资产

当前限制：

- `P5` 已知职责与接口边界已明确
- 但独立详细设计尚未形成，后续需在 `CODEX_DOC` 和 `JB_DOC` 中继续补齐

### 4.6 `P6` 门户与平台入口能力需求

平台应支持：

- 独立门户入口
- 全屏蓝图式画布
- 模块入口导航
- 状态观察与图例说明
- 登录、权限、平台入口治理的占位与后续扩展口

关键约束：

- `P6` 是平台层，不改变 `P1 -> P5` 主链
- 单击高亮、双击进入模块，不以弹窗为主交互

## 5. 接口与成果物需求

### 5.1 阶段接口

平台应固定以下正式接口语义：

- `P1 -> P2`
  - 已发布知识对象、检索筛选能力、来源回溯能力
- `P2 -> P3`
  - 冻结的结构化需求规格
- `P3 -> P4`
  - 模块级 / 子模块级工具化描述、冻结设计投影、批次工单包
- `P4 -> P5`
  - 工具/组件命中结果、可执行资产清单、校验与约束结果

### 5.2 核心成果物

平台至少应围绕以下核心对象组织：

- `PublishedKnowledge`
- `ApplicationRequirementModel`
- `SoftwareDesignBaseline`
- `SoftwareDesignDescription`
- `ModuleWorkorderBatchPackage`
- `ToolDefinition`
- `ToolDemandSheet / ToolDemandItem`
- `ToolSupplyResult`

## 6. 非功能需求

### 6.1 追溯性

平台应保证：

- 关键对象可回溯到上游来源文档或上游阶段对象
- 关键发布结论可回溯到审定、评审或验证证据

### 6.2 可解释性

平台不应只给出黑盒结果，应能解释：

- 为什么推荐某业务元素
- 为什么某设计项被拆成某批工单
- 为什么某工具被命中、驳回或转研制

### 6.3 解耦性

平台各阶段只允许依赖标准成果物，不应依赖：

- 上游页面状态
- 上游未发布 JSON
- 未冻结草稿或临时脚本产物

### 6.4 审计与治理能力

平台应具备：

- 审核、发布、移出、回退等关键动作的记录能力
- 关键运行任务的状态、失败、重试和进度留痕能力

### 6.5 门户可观察性

平台应提供门户级状态观察，至少可表达：

- 主链阶段
- 当前知识库
- 关键入口可用性
- 主要流向和节点关系

## 7. 约束条件

平台当前必须遵守以下约束：

- 结构化对象优先于文档投影
- 下游只消费上游标准成果物
- 组件 / 工具闭环发生在应用生成过程中
- 正式研发根与标准化副本根分层管理
- 平台默认以主工作区作为用户可见基线，不长期分裂成多套运行上下文

## 8. 验收考虑

平台级验收至少应覆盖：

- 主链阶段边界是否清晰
- 阶段输入输出是否为标准成果物
- `P1 / P2 / P3 / P4 / P6` 是否已有稳定设计表达
- `P5` 是否已被明确标注边界与待补项，而非被遗漏
- 标准化副本文档是否能追溯回 `CODEX_DOC`

## 9. 当前结论

本文件可作为 `CodeFactoryV2` 平台自身向系统 / 子系统规格说明方向演进的强化版候选稿。

本轮已经从“平台是什么”推进到“平台应具备哪些阶段能力、接口与约束”的层级；后续仍需补齐：

- 平台级需求编号体系
- 更细化的性能与资源指标
- 与未来项目实例交付链的更严格映射
