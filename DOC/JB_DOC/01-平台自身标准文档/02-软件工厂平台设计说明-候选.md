## 2. 设计范围

本设计说明覆盖：

- 平台总体架构。
- 六阶段模块分解。
- 核心对象与接口契约。
- 关键运行与协同原则。
- 门户读侧与展示实验设计。
- 文档根与平台层的关系。

本设计说明不覆盖：

- 单个前端页面的像素级方案。
- 单个后端文件或类的代码级细节。
- 项目实例级 `SRS / SDD / STP / STR` 文档。
- `B1` 契约级字段 schema 与 endpoint 级定义。

## 3. 设计驱动因素

### 3.1 平台属性特殊

`CodeFactoryV2` 是“生产软件的软件”，因此其设计不能只围绕一个业务域页面展开，而必须同时承接：

- 平台自身研发与治理。
- 平台生成标准化软件产物的能力。

### 3.2 结构化对象优先

平台所有关键阶段都优先输出结构化对象，再按需要投影为：

- 说明文档。
- 图谱 / 浏览器。
- 工单包。
- 门户投影视图。

### 3.3 标准成果物驱动

各阶段之间只能通过标准成果物协作，不允许通过：

- 内部工作态页面。
- 临时 JSON。
- 未冻结草稿。
- 手工补丁文件。

## 4. 总体架构

### 4.1 主链架构

平台正式主链为：

`P1 业务知识库 -> P2 需求分析系统 -> P3 软件设计系统 -> P4 工具仓库 -> P5 软件构建系统`

`P6` 独立承担门户、导航、观察与平台级入口治理。

### 4.2 三层视图

从设计上，平台可以理解为三层：

| 视图层 | 说明 | 主要文档根 |
| --- | --- | --- |
| 平台研发层 | 定义平台自身如何工作、如何被研发 | `DOC/CODEX_DOC/` |
| 标准化副本层 | 把平台与模板对象投影为标准化表达 | `DOC/JB_DOC/` |
| 项目实例层 | 承接未来实际项目的交付样例 | `DOC/JB_DOC/03-项目实例与样例/` |

### 4.3 模块职责分配

- `P1`
  - 文档接入、结构化解析、知识抽取、治理发布、发布态浏览。
- `P2`
  - 面向业务专家的需求建模与 `ApplicationRequirementModel` 输出。
- `P3`
  - 设计基线、设计说明投影、评审冻结与工单包生成。
- `P4`
  - 工具资产管理、输入工序链、运行时推进、自演进巡检与投影。
- `P5`
  - 装配与生成目标软件。
- `P6`
  - 门户蓝图画布、平台入口、只读观察、统一展示语言与前端展示实验。

## 5. 阶段级详细设计

### 5.1 `P1` 业务知识库设计

#### 5.1.1 阶段主链与设计原则

`P1` 采用“文档接入 -> 结构化解析 -> 候选知识抽取 -> 治理发布 -> 发布态浏览”的稳定链路。

`P1` 设计必须固定以下原则：

- `P1` 是平台知识供给层。
- `P1` 的正式结果是已发布知识，不是候选知识。
- 正式抽取链与调试链严格分离。
- 已发布知识必须可解释、可追溯、可回证。

`P1` 的内部节点链固定为：

`P1.1 功能验证平台底座 -> P1.2 文档接入与结构化解析 -> P1.3 候选知识抽取 -> P1.4 知识治理与发布 -> P1.5 已发布知识仓、查询与图谱展示`

#### 5.1.2 核心对象与正式产物账本

`P1` 当前围绕以下对象展开：

- `Entity`
- `Event`
- `Process`
- `Rule`
- `Metric`
- `Relation`
- `Evidence`
- `KnowledgeVersion`

文档级正式产物账本至少要独立保存：

- 文档元数据。
- 文档级候选知识。
- 文档级关系贡献。
- 抽取执行元数据。
- `included_in_archive`。

这意味着“是否已有正式产物”和“是否并入当前正式全集”必须被明确拆开。

#### 5.1.3 抽取、治理与发布态浏览

`P1` 正式抽取链固定为：

`结构化分块 -> 分块抽取 -> 全局归并 -> 治理 / 发布`

关键设计要求：

- 正式解析以 `Docling` 为主。
- 长文档按章节、块、表格、列表构建语义块。
- 多块分别执行规则抽取与结构化大模型抽取。
- 文档级统一归并术语、别名、关系和证据。
- 至少保留章节/块级证据回溯。

治理工作台至少承担：

- 候选项筛选。
- 术语归并。
- 关系修正。
- 流程补链。
- 批量审核通过 / 驳回。
- 审核留痕与状态回显。

发布态浏览至少承载：

- 类型筛选：`实体 / 事件 / 流程`。
- 视图切换：`列表 / 图谱`。
- 来源文档筛选：`全部 / 指定文档集合`。
- 文档钻取、详情抽屉、关系邻域与证据回溯。

### 5.2 `P2` 需求分析系统设计

#### 5.2.1 对象优先与双形态建模器

`P2` 的核心设计不是某种页面皮肤，而是对象优先的建模策略与统一权威对象。

`P2` 必须坚持“对象优先于流程”，因为：

- 对象建模要素更完整。
- 平台要支持探索新流程。
- 多对象跨流程应用是核心使用场景。

`P2` 当前正式支持两种互补交互形态：

- `表单式建模器 + 智能推荐`
- `选配式建模器`

二者共享同一权威对象，不能实现为两套语义不同的系统。

#### 5.2.2 标准建模步骤

首版默认路径固定为：

`先向导收敛 -> 再进入按场景 / 模块组织的选配建模`

标准建模过程按以下 6 段推进：

1. 业务目标收敛。
2. 使用对象与范围收敛。
3. 自建模块。
4. 模块内动作建模。
5. 模块链路与交接动作。
6. 自动页面建议与输出。

#### 5.2.3 权威输出模型与状态

`P2` 当前固定的权威输出对象为：

- `ApplicationRequirementModel`

其当前稳定顶层结构包括：

- `application_goal`
- `audiences`
- `roles`
- `modules`
- `actions`
- `business_objects`
- `module_handoffs`
- `page_suggestions`
- `knowledge_references`
- `temporary_elements`
- `draft_meta`

`P2` 的结构化优先规则如下：

- 结构化对象是唯一权威输出。
- `MD` 只是可读投影。
- 每个核心项应具备稳定 `id`。
- 推荐项、手工项、临时项必须可追溯来源。
- `page_suggestions` 只表达页面模板建议，不提前混入组件资产。

当前收敛的状态包括：

- `draft`
- `completed`
- `exported`

最小完成条件包括：

- 有业务目标。
- 有至少一类使用对象。
- 有至少一个模块。
- 每个动作包含 `参与方 + 业务对象 + 行为 + 结果`。
- 已生成至少一项结构预览。

### 5.3 `P3` 软件设计系统设计

#### 5.3.1 输入接入与分析链

`P3` 只消费已冻结、状态明确、可追溯的需求规格说明。

输入不应被当作黑盒文档直接喂给生成器，而应先完成：

- 接入登记。
- 快照留存。
- 结构解析。
- 设计分析。

`P3` 的第一核心对象是：

- `P3Order`

它用于承载：

- 受理。
- 审批。
- 生成。
- 评审。
- 冻结。
- 交接。

#### 5.3.2 三层输出模型

`P3` 输出的不是单纯文件，而是三层一致的结果：

| 层次 | 正式对象 | 用途 |
| --- | --- | --- |
| 内部权威层 | `SoftwareDesignBaseline` | 结构化设计事实源 |
| 文档投影层 | `SoftwareDesignDescription` | 人工评审、冻结和留档 |
| 交接投影层 | `ModuleWorkorderBatchPackage` | 向 `P4` 下发模块级实现需求 |

`SoftwareDesignBaseline` 用于沉淀：

- 设计范围。
- 架构建议。
- 模块划分。
- 输入输出。
- 约束条件。
- 推荐工具能力。
- 评审线程。
- 需求追溯关系。

`ModuleWorkorderBatchPackage` 至少表达两层信息：

- 包级总体建议。
- 条目级模块需求。

其中条目级需求至少包含：

- 模块目标。
- 输入输出。
- 约束条件。
- 验收要点。
- 推荐工具能力。

#### 5.3.3 评审、冻结与重新打开

`P3` 首版必须显式承载人工评审痕迹：

- `DiscussionThread`
- `ReviewDecision`

`P3` 的冻结不是永不再开，而是：

- 常态保持冻结。
- 只有在 `P5` 可行性反馈进入正式仲裁后，才允许按规则重开。

`P3` 对 `P5` 反馈至少做三类判定：

- `design_gap`
- `supply_gap`
- `assembly_or_build_gap`

处理方式分别是：

- `design_gap`
  - 在 `P3` 内部重开设计基线及其文档投影。
- `supply_gap`
  - 由 `P3` 向 `P4` 下发新供给任务、派生任务或组件拆分任务。
- `assembly_or_build_gap`
  - 优先回到 `P5` 装配规则、导出规则或校验规则整改。

### 5.4 `P4` 工具仓库设计

#### 5.4.1 总体角色与双闭环

`P4` 是工具中台，不是工具列表页，也不是跨全厂通用调度中心。

`P4` 同时承担两条业务闭环和一条公共运行骨架：

- 外部输入闭环。
- 内部自演进闭环。
- 公共运行骨架。

外部输入闭环面向 `P3 / P3-sim`：

`工具需求单 -> 拆叶子工具项 -> 匹配 -> 审定 -> 直接交付或进入研制 -> 对 P5 提供查询与获取`

内部自演进闭环面向工具池自身：

`工具仓快照 -> 巡检 -> 发现项 -> 采纳/忽略 -> 内部任务 -> 自动改写或人工跟进 -> 回退`

公共运行骨架统一提供：

`命令接入 -> 事实写入 -> 任务投递 -> 调度 -> 分域执行 -> 查询投影刷新 -> 审计与回退`

#### 5.4.2 核心业务循环

`P4` 的统一业务循环投影为：

`外部命令 / 定时触发 -> Command Intake -> Fact Persistence -> Job Dispatch -> Runtime Scheduling -> Domain Execution -> Projection Refresh -> 页面 / P5 查询 -> Audit and Recovery`

各阶段语义如下：

- `Command Intake`
  - 参数校验、幂等校验、边界校验。
- `Fact Persistence`
  - 将业务事实写成稳定对象。
- `Job Dispatch`
  - 把长耗时动作转成标准后台任务。
- `Runtime Scheduling`
  - 处理调度、重试、超时、补偿、恢复。
- `Domain Execution`
  - 由分域 Worker 执行具体逻辑。
- `Projection Refresh`
  - 刷新只读投影。
- `Audit and Recovery`
  - 留痕、回退与补偿。

该统一循环必须同时承载外部输入闭环与内部自演进闭环。

#### 5.4.3 Runtime 协调器与队列

`P4 Runtime` 的推荐总图为：

`API 命令入口 -> Runtime Job Store -> Queue Dispatcher -> Worker Pool -> Aggregate Update -> Projection Refresh -> Query Store`

核心组件包括：

- `Runtime Coordinator`
  - 拉取可执行任务、触发定时任务、管理租约、处理超时和重试、回收僵尸任务、触发投影刷新。
- `Job Queue`
  - 承载所有异步任务，提供标准状态流转，保证任务顺序、租约和幂等。
- `Worker Pool`
  - 按任务类型执行对应逻辑，不关心页面表现，不直接暴露对外接口。
- `Lease Manager`
  - 分配执行租约，避免重复执行，支持续租与过期回收。

运行时任务至少具备：

- 任务类型。
- 生命周期。
- 租约语义。
- 失败分类。
- 重试策略。
- 死信处理。
- 触发模型。
- 投影刷新机制。

#### 5.4.4 Backend 服务边界、分域与端口

未来独立的 `P4 backend service` 对外只承担与工具资产相关的职责：

- 接收外部工具需求。
- 管理工具资产。
- 推进未命中项研制。
- 执行工具池自演进巡检。
- 提供查询、供给和审计能力。

明确不承担：

- `P1` 的知识解析、治理与图谱存储。
- `P3` 的设计生成逻辑。
- `P5` 的构建执行逻辑。
- 跨全厂通用任务调度。

当前建议固定 6 个域：

- `Registry Domain`
- `Demand Domain`
- `Manufacture Domain`
- `Evolution Domain`
- `Projection Domain`
- `Runtime Domain`

当前外部视角端口包括：

- `P3 / P3-sim`
  - `P3 Input Port`
- `XX-P4 / Operator`
  - `Operator Port`
- `Worker / Runtime Coordinator`
  - `Internal Runtime Port`
- `P5 / P5-sim`
  - `P5 Query Port`

#### 5.4.5 数据与投影模型

`P4` 的数据模型当前明确分为四层：

- 业务事实层。
- 运行事实层。
- 查询投影层。
- 审计与快照层。

`ToolDefinition` 当前稳定字段语义至少包括：

- 工具身份。
- 业务技术形态。
- 交付包装方式。
- 宿主接入方式。
- 依赖策略。
- 运行依赖。
- 宿主约束。
- 暴露契约引用。
- 产物清单引用。

`Demand` 聚合围绕以下对象展开：

- `ToolDemandSheet`
- `ToolDemandItem`

查询投影层至少包括：

- `OverviewProjection`
- `Demand / Registry / Evolution` 投影。
- `ToolDeliveryProjection`

其中 `ToolDeliveryProjection` 直接服务于：

- `P5`
- `P5-sim`
- `XX-P4`

### 5.5 `P5` 软件构建系统设计

当前 `P5` 只形成以下平台级设计边界：

- 消费 `RequirementSpec`。
- 消费设计对象与资产命中结果。
- 负责装配、生成、交付与构建资产反哺。

当前未形成独立详设，因此在本文件中只保留边界、依赖约束和回流仲裁口径。

### 5.6 `P6` 门户与平台入口设计

#### 5.6.1 `P6.1` 首屏观察门户

`P6.1` 的首版关键对象是门户蓝图画布。

页面职责包括：

- 独立路由 `/portal`。
- 全屏、可拖拽、可缩放的蓝图画布。
- 阶段主节点与主链路表达。
- 单击高亮、双击进入模块。
- 门户级投影摘要与布局记忆。

页面采用四层结构：

1. 视口层。
2. 连线层。
3. 节点层。
4. 图例与摘要层。

首版固定主节点包括：

- `行业用户`
- `P1 业务知识库`
- `P2 需求分析系统`
- `P3 软件设计系统`
- `P4 工具仓库`
- `P5 软件构建系统`

`P6` 本身不作为并列业务节点出现，而以图例和平台说明存在。

#### 5.6.2 `P6.2` 跨阶段只读集成与状态投影

`P6.2` 只负责读侧集成，不负责跨阶段写入。

允许做的事包括：

- 查询阶段概览。
- 查询入口可用性。
- 查询摘要指标、健康信息和告警摘要。
- 订阅阶段状态变化。
- 将阶段数据归一为平台投影对象。

明确禁止的事包括：

- 写入 `P1 ~ P5` 内部事实对象。
- 触发阶段命令。
- 修改阶段语义。
- 直接读取阶段内部数据库。
- 直接抓取页面私有状态。

`P6.2` 应固定以下最小查询对象：

- `StageOverview`
- `StageEntryProjection`

#### 5.6.3 `P6.3` 设计语言与前端展示基线

`P6.3` 的目标是统一跨阶段观察与入口层的展示语义，而不是抹平各阶段业务个性。

必须统一的部分包括：

- 阶段命名。
- 状态文案与状态色。
- 总览条与摘要卡表达。
- 平台级入口按钮与跳转提示。
- 抽屉、详情页、列表、图谱视图的基础交互语义。
- 页面空态、加载态、错误态。

允许保留阶段个性的部分包括：

- 阶段特有业务字段。
- 专有工作台布局。
- 阶段内部图谱、建模、编排细节。
- 业务特有按钮和操作链。

平台级页面统一采用：

- 浅底工程蓝图方向。
- 高信息密度但低视觉噪声。
- 强结构感而非装饰型后台。

#### 5.6.4 `P6.4` 前端展示工具化实验场

`P6.4` 是探索验证层，不是正式生产页替代物。

当前负责：

- 定义展示工具化的最小对象模型。
- 提供展示模板、数据绑定、布局组合和预设的实验框架。
- 记录实验结果与反馈结论。
- 将可复用结论回传给 `P3 / P4 / P5`。

首版固定对象包括：

- `DisplayWidgetTemplate`
- `DisplayWidgetBinding`
- `DisplayWidgetLayout`
- `DisplayWidgetPreset`
- `DisplayExperimentRecord`

实验流程固定为：

1. 选择阶段数据源。
2. 选择或创建展示模板。
3. 建立字段绑定。
4. 组合布局。
5. 在平台观察页或实验页预览。
6. 记录实验结果。
7. 判断是否可进入正式复用链。

## 7. 运行与协同原则

### 7.1 命令、执行、查询分离

尤其在 `P4` 中，必须区分：

- 命令侧。
- 执行侧。
- 查询侧。

查询动作不应承担推进语义，页面查询与 `P5` 查询都只读投影，不直接拼装原始事实。

### 7.2 文档根与事实源协同

平台当前在文档层采用双根协同：

- `CODEX_DOC`
  - 研发正式根。
- `JB_DOC`
  - 标准化副本根。

设计上要求：

- 正式设计先在 `CODEX_DOC` 成为权威结论。
- 之后再由 `JB_DOC` 做标准化重组和主文种归并。

### 7.3 数据新鲜度与降级标注

`P6` 读侧展示必须显式标注：

- 来源。
- 时间戳。
- 新鲜度。
- 降级状态。

这保证门户与观察页展示的是“有来源、有时效”的读侧结果，而不是无法解释的数据拼接。

### 7.4 回流仲裁与非直接修订

`P5` 装配失败、资产不匹配、构建阻塞等反馈，默认进入 `P3` 仲裁，而不是直接进入 `P4` 命令队列。

这保证：

- 平台级资产语义不被单次装配临时改写。
- `P4` 自循环可以独立演进。
- `P3` 继续保持业务目标和设计语义的唯一解释权。

### 7.5 默认单工作区

平台当前默认单工作区开发与验收，不长期依赖多工作树分裂上下文。

## 8. 当前设计限制
