**文档类别：** 标准文种候选文档  
**标准依据：** 主要对齐 `DI-IPSC-82284 Software/Hardware Design Description`

本文件描述的是软件工厂平台自身的总体设计，不是由平台生成出来的业务系统设计说明。

## 2. 设计范围

本设计说明覆盖：

- 平台总体架构
- 六阶段模块分解
- 核心对象与接口契约
- 关键运行与协同原则
- 文档根与平台层的关系

本设计说明不覆盖：

- 单个前端页面的像素级方案
- 单个后端文件或类的代码级细节
- 实例项目级 `SRS / SDD / STP / STR` 文档

## 3. 设计驱动因素

### 3.1 平台属性特殊

`CodeFactoryV2` 是“生产软件的软件”，因此其设计不能只围绕一个业务域页面展开，而必须同时承接：

- 平台自身研发与治理
- 平台生成标准化软件产物的能力

### 3.2 结构化对象优先

平台所有关键阶段都优先输出结构化对象，再按需要投影为：

- 说明文档
- 图谱 / 浏览器
- 工单包
- 门户投影视图

### 3.3 标准成果物驱动

各阶段之间只能通过标准成果物协作，不允许通过：

- 内部工作态页面
- 临时 JSON
- 未冻结草稿
- 手工补丁文件

## 4. 总体架构

### 4.1 主链架构

平台正式主链为：

`P1 业务知识库 -> P2 需求分析系统 -> P3 软件设计系统 -> P4 工具仓库 -> P5 软件构建系统`

`P6` 独立承担门户、导航、观察与平台级入口治理。

### 4.2 三层视图

从设计上，平台可以理解为三层：

| 视图层 | 说明 | 主要文档根 |
| --- | --- | --- |
| 平台研发层 | 定义平台自身如何工作、如何被研发 | `DOC/CODEX_DOC/` |
| 标准化副本层 | 把平台与模板对象投影为标准化表达 | `DOC/JB_DOC/` |
| 项目实例层 | 承接未来实际项目的交付样例 | `DOC/JB_DOC/03-项目实例与样例/` |

### 4.3 模块职责分配

- `P1`
  - 文档接入、结构化解析、知识抽取、治理发布、发布态浏览
- `P2`
  - 面向业务专家的需求建模与 `RequirementSpec` 输出
- `P3`
  - 设计基线、设计说明投影、评审冻结与工单包生成
- `P4`
  - 工具资产管理、输入工序链、运行时推进、自演进巡检与投影
- `P5`
  - 装配与生成目标软件
- `P6`
  - 门户蓝图画布、平台入口、登录/权限占位与观察层

## 5. 阶段级设计摘要

### 5.1 `P1` 设计要点

`P1` 采用“文档接入 -> 结构化解析 -> 候选知识抽取 -> 治理发布 -> 发布态浏览”的链路。

关键设计点：

- 正式抽取链与调试链分离
- 正式链采用 `Docling + 结构化大模型` 硬约束
- 长文档采用分块抽取与全局归并
- 文档级正式产物账本支撑单文档并入 / 移出
- 文档详情抽屉、图谱视图、流程视图和来源文档筛选构成发布态浏览入口

### 5.2 `P2` 设计要点

`P2` 的关键不是页面样式，而是建模对象与权威输出模型。

设计关键点：

- 对象优先于流程
- 双形态建模器共享同一权威对象
- 推荐体系融合通用知识、领域知识和用户当前输入
- 权威输出是 `ApplicationRequirementModel`
- `MD` 只是可读投影

### 5.3 `P3` 设计要点

`P3` 的设计本质是把需求规格转化为设计基线和交接工单包。

核心设计对象：

- `P3Order`
- `SoftwareDesignBaseline`
- `SoftwareDesignDescription`
- `ModuleWorkorderBatchPackage`
- `DiscussionThread / ReviewDecision`

核心链路：

`冻结需求规格 -> 接入与分析 -> 生成设计基线 -> 投影设计说明 -> 人工评审与冻结 -> 生成批次工单包 -> 交接 P4`

### 5.4 `P4` 设计要点

`P4` 是工具中台，不是工具列表页。

其总体设计由四类文档共同支撑：

- 总体设计
- 核心业务循环
- Runtime 协调器与队列
- Backend 服务边界
- 数据与投影模型

`P4` 的核心结构包括：

- 外部输入闭环
- 内部自演进闭环
- 公共运行闭环
- 命令 / 执行 / 查询分离
- 事实层 / 运行层 / 投影层 / 审计层

### 5.5 `P5` 设计要点

当前 `P5` 只形成以下平台级设计边界：

- 消费 `RequirementSpec`
- 消费设计对象与资产命中结果
- 负责装配、生成、交付与构建资产反哺

当前未形成独立详设，因此在本文件中只保留边界和依赖约束。

### 5.6 `P6` 设计要点

`P6` 的首版关键对象是门户蓝图画布。

设计关键点：

- 独立路由 `/portal`
- 固定节点集合表示 `P1 ~ P5` 和行业用户
- `P6` 自身不作为并列主节点，而通过图例表达平台层身份
- 单击高亮、双击进入模块
- 采用世界坐标、节点卡片、连线层、特效层的混合画布结构

## 6. 核心对象与契约视图

### 6.1 跨阶段对象链

平台当前最重要的跨阶段对象链包括：

- `PublishedKnowledge`
- `ApplicationRequirementModel`
- `SoftwareDesignBaseline`
- `SoftwareDesignDescription`
- `ModuleWorkorderBatchPackage`
- `ToolDefinition`
- `ToolDemandSheet / ToolDemandItem`
- `ToolSupplyResult`

### 6.2 `P4` 关键运行对象

`P4` 当前已经明确的专题对象包括：

- `RuntimeJob`
- `RuntimeLease`
- `RuntimeExecutionRecord`
- `ToolManufacturePlan`
- `EvolutionRun`
- `EvolutionFinding`
- `EvolutionTask`
- `OverviewProjection`
- `RegistryProjection`
- `DemandItemProgressProjection`

### 6.3 阶段契约

当前固定契约如下：

- `P1 -> P2`
  - 发布态知识对象和证据回溯能力
- `P2 -> P3`
  - 冻结需求规格
- `P3 -> P4`
  - 冻结设计对象投影、批次工单包、工具化描述
- `P4 -> P5`
  - 资产命中结果、供给结果、运行约束

## 7. 运行与协同原则

### 7.1 命令、执行、查询分离

尤其在 `P4` 中，必须区分：

- 命令侧
- 执行侧
- 查询侧

查询动作不应承担推进语义。

### 7.2 文档根协同

平台当前在文档层采用双根协同：

- `CODEX_DOC`
  - 研发正式根
- `JB_DOC`
  - 标准化副本根

设计上要求：

- 正式设计先在 `CODEX_DOC` 成为权威结论
- 之后再由 `JB_DOC` 做标准化重组

### 7.3 默认单工作区

平台当前默认单工作区开发与验收，不长期依赖多工作树分裂上下文。

## 8. 当前设计限制

本文件当前仍存在以下有意保留的限制：

- `P5` 尚无独立详细设计
- 部分发布链与交付链对象仍停留在模板和策略层
- 运行部署形态仍以当前单服务 / 单工作区阶段为主，尚未全面转入正式多进程或分布式目标态

## 9. 当前结论

本文件可作为 `CodeFactoryV2` 平台自身向系统级设计说明方向演进的深化版候选稿。

与旧版相比，本轮已经把：

- `P1` 的正式抽取与治理链
- `P2` 的对象优先建模
- `P3` 的设计基线与评审冻结
- `P4` 的专题设计族
- `P6` 的门户画布设计

纳入了统一的平台设计视图中。
