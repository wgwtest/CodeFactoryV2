# 平台自身标准文档包总说明

## 1. 文档定位

**文档类别：** 标准化辅助文档  
**标准依据：** 组合参考 `SDP / SEMP / CMP / QAPP / RTVM` 与平台级规格设计文种  
**当前状态：** 基线

本文件用于说明 `01-平台自身标准文档/` 下各文档之间的关系，以及它们如何共同支撑平台自身研发。

## 2. 为什么不是靠一两份文档完成研发

平台自身研发不可能只靠一份规格说明和一份设计说明完成。完整的软件研发至少需要四类文档一起工作：

- 规格与设计类
- 计划与工程管理类
- 配置与质量控制类
- 追溯、验证与发布类

当前目录下的文档包，就是按这个思路组织的。

## 3. 文档包分层

### 3.1 产品定义层

- `01-软件工厂平台规格说明-候选.md`
- `02-软件工厂平台设计说明-候选.md`

回答：

- 平台要做什么
- 平台怎么设计

### 3.2 过程管理层

- `03-系统工程管理计划-候选.md`
- `04-软件开发计划-候选.md`
- `08-技术评审与阶段门控说明.md`

回答：

- 研发过程怎么推进
- 评审怎么过门
- 什么时候可以进入下一阶段

### 3.3 控制保障层

- `06-配置管理计划-候选.md`
- `07-质量保证计划-候选.md`

回答：

- 版本和基线怎么控
- 质量怎么控

### 3.4 闭环验证层

- `05-需求追溯验证矩阵-骨架.md`
- `09-验证与发布策略-候选.md`

回答：

- 需求到设计到验证怎么串起来
- 测试、发布、移交链后续如何补齐

## 4. 当前最小研发推进链

当前推荐把平台自身研发推进链理解为：

`规格说明 -> 设计说明 -> 系统工程管理计划 -> 软件开发计划 -> 技术评审与阶段门控 -> 配置管理 / 质量保证 -> 追溯矩阵 -> 验证与发布策略`

这条链并不意味着所有文档串行写完后才开发，而是意味着：

- 各类控制对象必须同时存在
- 不能只写产品定义文档，而缺失过程和验证控制文档

## 5. 当前结论

`01-平台自身标准文档/` 当前已经不再只是几份薄骨架，而是：

- 平台自身的首版标准文档包

它仍然需要继续扩写，但已经具备：

- 产品定义
- 过程管理
- 控制保障
- 闭环验证

四类基本组织能力。
