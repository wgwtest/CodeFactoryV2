# 受控动态考官手册-态势分析系统

## 1. 文档定位

本文档用于指导 Codex 或人工测试者以“受控动态考官”方式测试 P2 需求分析组织器。受控动态考官掌握 `需求规格说明样例-态势分析系统` 作为隐藏基准，但不把完整样例一次性输入给被测组织器。

本文档不是固定投喂脚本，不规定每一轮必须输入什么。测试者的默认职责是模拟真实用户回答组织器问题；只有在组织器明显偏离、连续空泛、遗漏已确认事实或过早收束时，才进行少量引导或纠偏。

## 2. 核心原则

- **不泄露完整答案：** 不把完整样例、完整功能清单或完整章节内容一次性提供给组织器。
- **不固定轮次：** 不使用“第几轮必须输入什么”的脚本化方式。
- **回答优先：** 组织器问什么，测试者优先回答什么；如果是选择题，应优先按选项回答，再补一句必要原因。
- **少量补充：** 每轮最多补充一个主题，通常不超过 3 条事实；不得在一轮内给出完整角色表、功能表、流程表或验收表。
- **顺着组织器交互：** 只要组织器问题方向合理，就不主动改写它的问题链，不抢先组织章节结构。
- **保留真实不确定性：** 当真实用户尚未想清楚角色、流程或边界时，应表达不确定，而不是直接给出完美答案。
- **轻量纠偏：** 当组织器把模板、样例、业务事实混淆，或擅自写入未确认结论时，用真实用户口吻指出边界，不直接重写答案。
- **评估最终产物：** 重点评估组织器最终是否形成可进入 P3 设计的需求规格，而不是是否命中固定输入顺序。
- **动作可追溯：** 每轮记录考官动作类型：答题、少量补充、轻量纠偏、收束请求或暂停观察。

## 3. 受控动态考官工作循环

### 3.1 观察

每轮先观察组织器输出：

- 它是否理解当前输入的真实问题。
- 它是否提出了必要的澄清问题。
- 它是否把事实、假设、决策和待确认事项区分开。
- 它是否把内容落到合适的需求规格章节。
- 它是否出现模板业务化、过度补全或虚构细节。

### 3.2 分类

将当前状态归为以下类型之一：

| 状态类型 | 判断标准 | 考官动作 |
| --- | --- | --- |
| 正常追问 | 组织器提出的问题聚焦角色、流程、功能、数据或边界 | 按题回答；选择题优先选项化回答，最多补充一句理由 |
| 合理选择题 | 组织器给出互斥选项，且选项覆盖主要方向 | 选择一个选项或说明倾向组合，不额外展开完整需求 |
| 轻微缺口 | 组织器问题合理，但遗漏了一个已确认事实 | 回答问题时顺带补一句事实，不要求它立刻成稿 |
| 过早成稿 | 组织器在关键缺口未闭合前直接生成完整正文 | 轻量提示“先别定稿”，要求继续澄清一个关键缺口 |
| 事实遗漏 | 组织器遗漏用户已明确提供的重要事实，并影响后续问题 | 简短重申该事实，要求后续按该事实继续 |
| 业务误判 | 组织器把辅助分析写成自动决策或正式指挥能力 | 用真实用户口吻纠正责任边界，不补充完整功能清单 |
| 模板污染 | 组织器把态势业务内容当作通用模板内容 | 要求区分模板和当前项目事实，不代替它重写模板 |
| 追问空泛 | 组织器连续两轮提出泛泛问题，无法推进规格说明 | 补充一个具体场景、角色或功能例子，观察其归纳能力 |

### 3.3 决策

根据分类决定下一步：

- 如果组织器问到了正确问题，按问题回答，不主动扩展到其他章节。
- 如果组织器给出选择题，优先选项化回答；只有选项都不合适时，才说明“不完全是这些选项”并给出一个简短修正。
- 如果组织器遗漏关键事实，优先在回答当前问题时顺带补充；只有遗漏会导致方向错误时，才单独纠偏。
- 如果组织器生成了未经确认的内容，要求标注为暂定假设或待确认事项，不直接提供完整替代正文。
- 如果组织器连续两轮卡在抽象层面，再给出一个具体业务场景、角色或功能例子。
- 如果组织器已经覆盖当前阶段重点，不继续强塞信息，转为要求它总结缺口和下一步问题。

### 3.4 信息释放限额

每轮考官输入应遵守以下限额：

| 输入类型 | 限额 | 说明 |
| --- | --- | --- |
| 回答选择题 | 1 个选项或 1 个组合倾向 + 1 句理由 | 不额外展开完整背景 |
| 回答开放问题 | 1 个主题，通常 2-3 条事实 | 只回答当前问题 |
| 少量补充 | 最多 1 个遗漏事实 | 应与当前问题直接相关 |
| 轻量纠偏 | 1 个边界错误 + 1 句正确口径 | 不重写需求规格正文 |
| 引导例子 | 1 个具体场景、角色或功能例子 | 仅在连续空泛或重复时使用 |

严禁以下行为：

- 一轮输入完整角色表、功能表、流程表、数据表或验收表。
- 主动要求组织器按指定章节号写作，例如直接要求写 `3.3`、`FR-01`。
- 在组织器尚未收束时，主动提供完整需求规格说明样例正文。
- 用考官掌握的隐藏基准替代组织器的追问和归纳过程。

### 3.5 响应

考官响应应保持真实用户口吻。推荐形式：

- “这个我还没完全想清楚，但目前倾向于……”
- “这里你理解错了，我不是要自动决策，只是辅助分析……”
- “可以先按科研人员日常分析来考虑，正式指挥协同先不做……”
- “这个功能先说输入和输出，算法细节后面再定……”
- “这个问题我选 A，但补充一点，结果最好能导出给别人看……”
- “先别急着完整定稿，我觉得用户角色和使用流程还没问清楚……”
- “你先按这个方向继续问，我暂时不补更多背景……”

## 4. 可动态释放的事实池

事实池不是脚本，只是考官可选素材。每次只释放与当前交互相关的少量事实。

### 4.1 初始意图事实

用户希望创建一个态势分析系统。系统需要有态势展示能力，也需要一系列地理信息分析工具，包括量算、坡度、通视分析、距离量算、面积量算、大气光照运算等。系统还需要创建态势、编辑态势、保存态势、导出态势等流程性工具。用户尚未想清楚具体谁用、怎么用、业务流程如何组织。

### 4.2 用户与角色事实

- 主要用户倾向于科研分析人员。
- 业务专家可能参与结果复核，但不是每天高频编辑系统的人。
- 数据管理员负责基础数据维护。
- 系统管理员负责账号、权限、日志和系统配置。
- 第一阶段不按多单位协同指挥系统设计。

### 4.3 业务价值事实

- 系统既像地理分析计算器，也像基础态势编辑管理平台。
- 它的价值是支撑日常地理信息分析、典型业务场景验证、基础数据分析和成果汇报。
- 它为其他工具软件提供态势承载、展示、分析和结果输出支撑。

### 4.4 核心流程事实

- 主流程一是态势创建与编辑：创建工程、加载图层、添加对象、编辑属性、保存工程。
- 主流程二是分析工具使用：选择工具、输入对象或参数、执行计算、查看结果、保存或导出结果。
- 主流程三是成果导出与复核：导出地图、结果、参数和说明，供业务专家查看。

### 4.5 功能事实

- 态势工程管理包括创建、打开、保存、另存、删除、导入和导出。
- 态势展示包括地图浏览、图层控制、对象查看、结果叠加显示。
- 态势编辑包括点线面对象、文字、符号、属性和样式编辑。
- 量算工具包括距离、面积、坐标和路径长度。
- 地形分析包括坡度、坡向和高程剖面。
- 通视分析需要观察点、目标点或目标区域、观察高度、目标高度和地形数据。
- 大气光照运算第一阶段只做辅助分析，不承诺物理级仿真。
- 分析结果需要保存、命名、查看、隐藏、删除和导出。

### 4.6 数据与接口事实

- 输入数据包括底图、地形数据、矢量数据、栅格数据、业务对象数据和分析参数。
- 输出数据包括态势工程文件、地图图片、分析结果图层、结果参数表和简要报告片段。
- 第一阶段以文件导入导出和内网数据加载为主，不做实时数据总线。

### 4.7 边界与约束事实

- 不做实时多源情报接入。
- 不做自动决策推荐。
- 不做高精度测绘级或工程级计算承诺。
- 不做多单位在线协同指挥。
- 分析结果是辅助判断，必须提示数据来源、参数和适用限制。

## 5. 纠偏规则

### 5.1 模板与样例混淆

如果组织器把态势展示、空间分析、通视等内容写成通用模板条款，应纠正为：

> 这些是态势分析系统这个样例项目的业务功能，不是通用需求规格模板的一部分。请把模板结构和当前项目事实分开处理。

### 5.2 自动决策过度扩展

如果组织器把系统描述为自动推荐、自动处置或正式指挥决策，应纠正为：

> 第一阶段只做科研分析和业务验证中的辅助分析，不做自动决策推荐，也不把结果表述为正式指挥结论。

### 5.3 忽略不确定性

如果组织器把用户尚未确认的内容写成确定需求，应纠正为：

> 这部分还没有确认，请先记录为暂定假设或待确认事项，并继续追问。

### 5.4 只列功能不写行为

如果组织器只列出功能名称，应要求：

> 请把核心功能拆成角色、触发条件、输入、处理、输出、异常和验收要点，而不是只列功能清单。

## 6. 终止条件

当组织器已经能够形成以下产物时，可以结束动态交互并进入评估：

- 已明确软件定位、使用范围和边界。
- 已识别主要用户角色和权限差异。
- 已形成至少两个核心业务流程。
- 已把核心功能写成可设计、可开发、可测试的行为级需求。
- 已覆盖数据、接口、非功能、异常和验收准则。
- 已把未确认事项独立列出。
