# 81435-软件设计说明准模板-v1

## 模板使用说明

**文档类别：** 软件设计说明准模板
**标准依据：** `DI-IPSC-81435 Software Design Description` 候选参照
**样例依据：** `P2-P3主链样例-SX-DataStore/02-软件设计说明范本-SX-DataStore.md`
**当前状态：** 准模板 v1，待评审
**适用对象：** 软件级应用、服务、工具或软件配置项
**不适用对象：** 平台级、系统级、软硬件一体化对象；此类对象应优先评估 `82284`。接口和数据库专项说明应分别评估 `81436`、`81437`。

本准模板用于把 P2 阶段形成的软件级需求规格说明转化为 P3 阶段的软件设计说明。它不是项目样例，不承载某个具体项目的业务事实；它把 `SX-DataStore` 软件设计说明范本中的稳定写法抽取为通用结构，用于约束后续人工编写、模型生成、转换器校验和 Dify 工作流交接。

本文不把 `81435` 解释为固定不可变的章节编号，而是将其核心要求转化为可执行的文档结构：说明软件范围、全局设计决策、总体架构、详细设计、对象模型、接口设计、运行流程、质量门和需求追溯。若项目已经存在更高优先级的行业模板或单位模板，应以更高优先级模板为准，并把本文作为补充检查依据。

### 使用原则

- 先确认软件级对象边界，再进入设计编写。若对象实质上是平台、系统或子系统，应停止套用本模板。
- 先承接 P2 需求规格说明中的角色、功能、数据、接口、非功能、验收和待确认事项，再生成设计结构。
- 设计说明应解释“如何实现需求”，不得重新发明需求，也不得把需求原文机械复制为设计结论。
- 前端、后端、对象、API、流程、质量门和验收口径必须互相追溯，不能各章独立成文。
- 对事实不足的内容，应标为“待项目确认”或“暂定设计假设”，不得写成已确认事实。
- 对已明确不做的范围，应写入边界或约束章节，防止后续设计和验收误判。

### 成稿长度与覆盖要求

正式软件设计说明不应生成短摘要。信息充足时，正文应满足以下最低展开要求：

| 检查项 | 最低要求 | 说明 |
| --- | --- | --- |
| 总正文长度 | 不少于 12000 个中文字符 | 不含目录、代码块装饰和空表格占位。 |
| 一级章节覆盖 | 100% | 本模板 15 个一级章节均应出现。 |
| 二级小节覆盖 | 不低于 90% | 允许按项目特性删减少量不适用小节，但必须说明原因。 |
| 结构化正文块 | 核心章节必须包含段落、表格和图块 | 转换器输出不得只提供一级章节和纯文本正文。 |
| 结构化图块 | 不少于 4 个关键图 | 图块可用 Mermaid、PlantUML 或 graph JSON 表达，当前不要求生成图片文件。 |
| 总体架构 | 不少于 1200 个中文字符 | 必须包含分层、能力模块、运行单元和关键设计决策。 |
| 前端软件设计 | 不少于 1200 个中文字符 | 若项目无前端，应改写为客户端、命令行、插件或交互端设计，并说明不适用原因。 |
| 后端软件设计 | 不少于 1500 个中文字符 | 必须展开模块边界、状态权威、调用规则和错误处理。 |
| 核心对象模型 | 不少于 1200 个中文字符 | 必须说明对象、状态、关系、模块归属和追溯来源。 |
| API 设计 | 不少于 1500 个中文字符 | 必须说明 API 分组、关键接口、请求响应、错误码和鉴权边界。 |
| 关键运行流程 | 不少于 1200 个中文字符 | 必须覆盖主业务闭环和异常/补偿路径。 |
| 设计约束与质量门 | 不少于 1000 个中文字符 | 必须形成可检查的工程约束、测试约束和验收门槛。 |
| 普通章节 | 每章不少于 400 个中文字符 | 适用于系统定位、业务目标、目录结构、验收口径等章节。 |
| 短章节 | 每章不少于 250 个中文字符 | 适用于文档目的、设计结论等天然较短章节，但不得只写套话。 |

当 P2 输入明显不足以支撑上述长度时，P3 输出仍应保留完整结构，并在对应章节写出缺口、假设、待确认问题和对下游实现的影响。不得用空泛段落凑长度。

## 1. 文档目的与设计口径

### 1.1 文档目的

**写作目标：** 说明本文档为什么编写、服务于哪个软件对象、承接哪些 P2 需求输入，以及将为哪些开发、测试、验收和移交活动提供依据。

**应确认信息：**

- 软件名称、版本或阶段名称。
- 上游 P2 需求规格说明名称、版本和范围。
- 本文档对应的软件级对象边界。
- 下游实现仓库、模块、服务、页面或交付物范围。
- 本文档对开发、测试、验收、平台展示和后续迭代的作用。

**正文建议：**

本文档用于说明 `{软件名称}` 在 `{阶段名称}` 的软件设计方案，承接 `{P2需求规格说明名称}` 中已经确认的角色、业务流程、功能需求、数据需求、接口需求、非功能需求和验收准则，形成可开发、可测试、可审查的软件结构说明。本文重点回答 `{软件名称}` 按什么设计口径组织、由哪些前端/后端/共享模块承接、核心对象如何建模、API 如何暴露、关键流程如何运行、质量门如何检查、需求如何追溯到设计与验证。

**生成约束：**

- 不得把本文写成需求规格说明的复述。
- 不得只写“用于指导开发测试”等套话，应列出具体设计回答对象。
- 若 P2 文档版本不明，应标注待项目确认。

**最低展开要求：** 至少形成 2 到 4 段正文，并列出本文重点回答的问题清单。

### 1.2 设计口径

**写作目标：** 说明本软件设计遵循的关键取舍、架构原则、边界原则和生成口径。

**应确认信息：**

- 第一阶段优先级最高的业务闭环。
- 架构风格，例如模块化单体、前后端分离、插件式架构、批处理工具、桌面客户端或微服务。
- 数据权威来源和状态权威来源。
- 页面、接口、服务、对象和流程之间的分工。
- 明确不做或延后做的技术能力。

**正文建议：**

本文采用以下设计口径：以 `{核心业务对象或业务闭环}` 为设计中心；以 `{架构风格}` 承接当前阶段实现；以 `{对象/状态/规则}` 作为跨模块一致性的权威来源；以 `{前端/客户端/交互端}` 消费后端或核心服务提供的视图模型，不在交互层重新制造业务事实；以 `{共享类型/协议/数据结构}` 固化跨端约定；对 `{暂不实现能力}` 仅保留扩展边界。

**生成约束：**

- 设计口径必须体现取舍，不能只写“高内聚低耦合”。
- 每条口径应能在后续章节找到对应设计落点。
- 对插件、模型调用、外部接口、数据持久化等容易扩张的能力，应明确当前阶段边界。

**最低展开要求：** 至少列出 5 条设计口径，每条应有一到两句解释。

### 1.3 术语与缩略语

**写作目标：** 统一 P2 与 P3 中的领域对象、设计对象、实现对象、状态名、接口名和缩略语，防止同名异义或异名同义。

**正文建议：**

| 术语 | 设计含义 | 来源 | 备注 |
| --- | --- | --- | --- |
| `{术语}` | `{在本软件设计中的精确定义}` | `{P2/用户输入/设计新增}` | `{限制或别名}` |

**生成约束：**

- 术语表应优先收纳核心业务对象、流程状态、角色、模块名、外部系统和共享对象。
- 若设计中新增技术术语，应说明它与 P2 需求术语的关系。
- 不得把普通动词或无审查价值的泛词放入术语表凑数。

**最低展开要求：** 信息充足时不少于 8 个术语；信息不足时至少列出已知核心术语和待确认术语。

### 1.4 系统主路径

**写作目标：** 用一条主路径说明软件从输入、处理、协作、输出到验收的核心业务闭环。

**正文建议：**

```text
{输入或触发} -> {核心处理一} -> {核心处理二} -> {状态确认或审批} -> {结果输出} -> {验收或后续使用}
```

辅助路径包括：

- `{辅助路径一}`。
- `{辅助路径二}`。
- `{辅助路径三}`。

**生成约束：**

- 主路径必须来自 P2 的核心业务流程或功能主线。
- 若软件存在多个并列主线，应说明首版主路径和次级路径。
- 主路径中的对象和状态应在后续对象模型、API 和流程章节继续出现。

## 2. 系统定位

### 2.1 一句话定位

**写作目标：** 用一句准确的话说明软件是什么、面向谁、解决什么核心问题、以什么方式交付价值。

**正文建议：**

`{软件名称}` 是一个面向 `{用户/组织/业务域}` 的 `{软件类型}`，以 `{核心对象/核心流程}` 为中心，提供 `{主要能力一}`、`{主要能力二}`、`{主要能力三}` 和 `{验证或输出能力}`。

**生成约束：**

- 一句话定位必须包含对象、用户、能力和价值，不应只有技术栈。
- 不得把软件定位写成平台愿景或市场宣传语。

### 2.2 正面工作对象

**写作目标：** 列出软件真正负责管理、处理、分析、展示或输出的业务对象和设计对象。

**应确认信息：**

- P2 功能需求涉及的核心对象。
- 数据输入、处理结果、配置对象、任务对象、流程对象和审计对象。
- 哪些对象只读、哪些对象由本软件创建或维护。

**正文建议：**

系统正面工作对象包括：

- `{对象一}`：`{设计含义、生命周期和责任边界}`。
- `{对象二}`：`{设计含义、生命周期和责任边界}`。
- `{对象三}`：`{设计含义、生命周期和责任边界}`。

**生成约束：**

- 工作对象不是功能清单，也不是页面清单。
- 每个对象应说明“本软件对它做什么”。
- 外部对象应标明只消费、只展示、同步缓存或本地维护。

### 2.3 用户角色与使用上下文

**写作目标：** 把 P2 中的用户角色转化为设计中的入口、权限、工作对象和交互上下文。

**正文建议：**

| 角色上下文 | 使用入口 | 主要工作对象 | 关键权限 | 设计说明 |
| --- | --- | --- | --- | --- |
| `{角色}` | `{页面/客户端/API/任务入口}` | `{对象}` | `{权限}` | `{设计含义}` |

**生成约束：**

- 角色上下文应与前端路由、API 鉴权、流程节点和验收场景保持一致。
- 若存在动态职责，例如审批人、复核人、任务责任人，应说明其不是固定用户类型，而是流程或对象上的职责。
- 若第一阶段不实现真实权限，应说明采用的替代机制和风险。

## 3. 业务目标与边界

### 3.1 首版负责

**写作目标：** 明确本阶段设计必须承接的功能、接口、数据、流程、质量和验收能力。

**正文建议：**

首版软件设计负责支持以下能力：

- `{能力一}`：承接 P2 `{需求编号或需求名称}`，由 `{模块/页面/API}` 实现。
- `{能力二}`：承接 P2 `{需求编号或需求名称}`，由 `{模块/页面/API}` 实现。
- `{能力三}`：承接 P2 `{需求编号或需求名称}`，由 `{模块/页面/API}` 实现。

**生成约束：**

- 必须能追溯到 P2 需求、约束或验收项。
- 不得在本节加入 P2 未出现且未说明来源的新范围。
- 能力描述应包含承接模块或后续设计位置。

### 3.2 首版不负责

**写作目标：** 明确当前阶段不设计、不实现、不验收的范围，并解释保留的扩展边界。

**正文建议：**

首版软件设计不负责：

- `{排除项一}`：原因是 `{原因}`，后续扩展位置为 `{扩展边界}`。
- `{排除项二}`：原因是 `{原因}`，当前替代方案为 `{替代方式}`。

**生成约束：**

- 排除项应来自 P2 边界、用户约束、技术阶段或当前实施条件。
- 不得把关键需求偷放进“不负责”以规避设计。
- 与接口、数据库、模型调用、生产级权限、复杂调度等有关的排除项必须写清替代方案。

### 3.3 上下游边界

**写作目标：** 说明本软件设计与上游需求、外部系统、下游开发、测试、部署和平台展示之间的边界。

**正文建议：**

| 上下游对象 | 边界说明 | 本软件责任 | 非本软件责任 |
| --- | --- | --- | --- |
| `{上游需求}` | `{输入范围和版本}` | `{承接方式}` | `{不负责内容}` |
| `{外部系统}` | `{接口或数据关系}` | `{消费/输出/同步}` | `{外部维护内容}` |
| `{下游实现}` | `{代码或模块范围}` | `{设计约束}` | `{实现外事项}` |
| `{下游测试}` | `{测试范围}` | `{可验证输出}` | `{测试外事项}` |

**生成约束：**

- 上下游边界必须能解释外部依赖失败、数据缺失、权限不足、接口未就绪时的设计处理。
- 若存在 Dify、模型服务、插件服务或其他外部能力，应写成清晰的执行边界和交接输入输出。

### 3.4 软件设计原则

**写作目标：** 将设计口径展开为可执行原则，指导后续模块划分、对象归属和接口设计。

**推荐原则类型：**

- 业务事实优先于页面表现。
- 服务边界优先于物理部署。
- 聚合接口优先于前端拼装。
- 共享对象优先于重复定义。
- 状态权威唯一，跨模块只通过约定接口变更状态。
- 当前阶段可验证优先，生产级增强保留扩展边界。

**生成约束：**

- 每条原则必须说明会影响哪些章节或模块。
- 不得堆砌通用软件工程口号。

### 3.5 完成条件

**写作目标：** 说明设计说明何时可以认为完成，可进入实现、测试或评审。
