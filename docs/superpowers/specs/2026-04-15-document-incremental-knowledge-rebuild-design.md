# 文档级正式抽取产物与增量重建设计

## 背景

当前 `P1` 已经具备：

- `Docling + 结构化大模型` 的正式知识库抽取硬门槛
- 长文档的结构化分块、分块抽取与全局归并
- 知识治理、发布与图谱查询能力

但正式知识库仍有一个关键断点：

1. 当前正式抽取入口本质上是“整库重建型快照”。
2. 单篇文档即使完成了更高质量的正式抽取，也只能作为独立预览结果存在。
3. 现有知识全集缺少“文档级正式产物账本”，无法安全判断某条关系、证据或节点到底由哪篇文档贡献。
4. 因此像 `FM_6-02` 这种单文档正式重抽结果，不能直接并入当前知识全集。

这不是因为技术上完全做不到，而是因为当前数据模型没有把“文档级正式贡献”作为标准资产保存下来。

## 目标

本轮目标是把“单文档正式抽取并入当前知识全集”补成正式能力，并满足以下要求：

1. 每篇文档的正式抽取结果必须独立持久化。
2. 单篇文档正式重抽后，系统必须能用它替换旧贡献，并重算当前知识全集。
3. 治理工作态不能因为重建而被整体抹掉。
4. 前端必须有明确的验证入口与反馈，用户能从文档页直接触发并查看结果。
5. 文档级正式产物与“是否纳入当前正式全集”必须解耦，支持在保留产物的前提下执行正式移出。

## 非目标

本轮不做以下工作：

1. 不引入图数据库级别的多版本差分引擎。
2. 不把治理状态改造成复杂审批流。
3. 不支持“没有任何正式抽取基线时，任意新文档零上下文直接并入旧全集”的弱一致方案。

## 节点归位

这项能力不应挂在 `P1.2`。

原因：

- `P1.2` 的标准成果物是“结构化解析结果”，只回答“文档被怎样解析”
- 文档级正式抽取产物属于 `P1.3`
- 单文档并入全集、治理态继承与全集重算属于 `P1.4`

因此本轮节点拆分如下：

- `P1.3.5` 文档级正式抽取产物持久化
- `P1.4.5` 文档级增量重建与全集合并

## 方案比较

### 方案 A：继续维持整库重建

做法：

- 每次单文档质量不满意时，重新全库正式抽取

优点：

- 最简单
- 数据一致性强

缺点：

- 成本高
- 用户无法把“单文档精修”沉淀为正式能力
- 与验证节奏不匹配

### 方案 B：基于文档级正式产物账本做增量重建

做法：

- 每篇文档独立生成正式抽取产物
- 全集由文档级产物聚合而来
- 单篇重抽时只替换该文档产物，再重算全集

优点：

- 符合主流知识抽取工程的增量化思路
- 能解释“这条知识由谁贡献”
- 后续可以继续演进为更强的差分治理

缺点：

- 需要补文档级产物仓与聚合器
- 需要定义治理态继承规则

### 方案 C：直接在现有全集上做就地补丁

做法：

- 从当前 `knowledge.json` 里删除目标文档相关节点，再拼入新结果

优点：

- 开发快

缺点：

- 现有关系层没有文档贡献账本
- 旧关系无法安全移除
- 容易留下脏数据

## 决策

采用方案 B。

原因：

1. 它不推翻当前 `Docling + 结构化大模型` 正式抽取链路。
2. 它能把单文档正式重抽从“临时预览能力”提升为“正式知识库增量能力”。
3. 它与 `P1` 现有串行、接口解耦约束一致。

## 架构设计

### 1. 文档级正式产物仓

新增“文档级正式产物仓”，每篇文档独立保存：

- 文档元数据
  - `document_id`
  - `path`
  - `title`
  - `file_type`
  - `source_archive`
  - `character_count`
  - `parser_name`
  - `segment_count`
- 文档级候选知识
  - `entities`
  - `events`
  - `processes`
- 文档级关系贡献
- 抽取执行元数据
  - `strategy`
  - `candidate_count`
  - `relation_count`
  - `llm_provider`
  - `llm_model`
  - `chunking_used`
  - 其他正式执行诊断

同时文档级正式产物清单必须补一个独立状态：

- `included_in_archive`

其含义不是“有没有正式产物”，而是“该文档正式产物当前是否参与正式知识全集聚合”。

这保证：

1. 正式产物可以长期保留，便于追溯与再次纳入。
2. “正式并入 / 正式移出”只改变全集纳入状态，不破坏文档级正式产物本身。

这些产物是 `P1.3` 对 `P1.4` 暴露的唯一正式输入。

### 2. 全集聚合器

全集不再只依赖“本轮运行时内存中的文档列表”，而是可以由文档级正式产物仓重算。

聚合规则：

1. 正式知识全集只聚合 `included_in_archive = true` 的文档级正式产物。
2. 节点按稳定 `id` 聚合，`document_ids / aliases / evidence` 做并集归并。
3. 关系先保留文档级命名引用，再在全集阶段统一解析为节点之间的边。
4. 仍保留 `document_mentions` 关系，保障前端详情页和来源筛选兼容。
5. 文档页的“已建库档案文档”清单和文档详情优先读取文档级正式产物仓，因此即使文档被正式移出，也仍然可查看该文档自身的正式抽取结果。

### 3. 单文档正式重抽与并入

当用户在文档页对某篇文档触发“正式并入”时：

1. 使用当前知识库的源目录定位该文档。
2. 按正式抽取硬门槛重新执行该文档：
   - 必须 `Docling`
   - 必须结构化大模型
   - 不允许静默降级
3. 将新结果写回该文档对应的正式产物文件。
4. 从文档级正式产物仓重算整个知识全集。
5. 重新生成：
   - `archive_id-knowledge.json`
   - `archive_id-knowledge-curated.json`
   - `archive_id-knowledge.md`
   - `archive_id-parsed-documents.json`
   - `archive_id-extraction-report.json`

### 3.1 单文档正式移出

当用户在文档页对某篇文档触发“正式移出”时：

1. 不删除该文档的正式产物文件。
2. 仅将该文档在正式产物清单中的 `included_in_archive` 置为 `false`。
3. 使用剩余 `included_in_archive = true` 的文档级正式产物重算当前知识全集。
4. 重新生成正式知识全集及其治理投影文件。

这意味着“正式并入 / 正式移出”是一组对称操作：

- `正式并入`：重抽目标文档正式产物，并纳入当前正式全集。
- `正式移出`：保留目标文档正式产物，但将其从当前正式全集中排除。

### 4. 首次初始化策略

如果某个知识库还没有“文档级正式产物仓”，则说明它来自旧版本整库快照。

这时单文档正式并入不能直接在旧快照上打补丁，而要先完成一次“正式产物仓初始化”：

1. 对当前知识库源目录执行一次完整正式抽取
2. 生成全部文档级正式产物
3. 再进入后续增量模式

这是一次性的迁移动作。完成后，同一知识库可以稳定使用单文档正式并入。

### 5. 治理态继承

治理态继承采用保守策略：

1. 优先按稳定 `id` 继承：
   - `name`
   - `category`
   - `aliases`
   - `review_status`
2. 若 `id` 不命中，则在同类型集合内按“名称/别名 slug 重合”尝试唯一匹配继承。
3. 若出现多义冲突或无法确定唯一映射，则回退为 `pending`，不做强行继承。

这样可以避免因为单篇文档重抽导致整库治理结果被清空，也能控制错误继承风险。

## 前端验证投影

本轮验证入口放在“已建库档案文档”页，而不是知识图谱页。

原因：

- 触发动作天然属于具体文档
- 用户最容易以“这篇文档抽得不对”为入口发起重抽
- 成功后可直接刷新文档详情、文档数量统计和后续图谱页结果

页面要求：

1. 每个已建库文档必须根据 `included_in_archive` 在“正式并入 / 正式移出”之间二选一显示。
2. 执行中必须显示状态标签，例如“正在并入 / 正在移出”。
3. 执行中必须在知识库级禁止重复提交，避免同一知识库并发重算。
4. “查看”操作继续可用。
5. 成功后给出明确反馈，说明本次属于：
   - 文档级增量并入
   - 文档级增量移出
   - 或首次正式产物仓初始化后再执行并入/移出

## 错误处理

1. 如果目标文档无法定位，直接失败。
2. 如果正式抽取失败，不能写入半成品产物。
3. 如果全集重算失败，保留旧的可读知识库文件，不覆盖成损坏状态。

## 验收标准

1. 全库正式抽取完成后，知识库目录中能看到文档级正式产物仓。
2. 对某篇已建库文档执行正式并入后，全集数量与文档详情能随之更新。
3. 已审核项在 `id` 稳定或别名唯一命中的情况下能够继承治理态。
4. 前端在执行期间禁止重复提交，并能显示成功/失败反馈。
5. 文档正式移出后，知识图谱与知识统计应剔除该文档贡献，但文档页仍可查看该文档正式产物内容。
