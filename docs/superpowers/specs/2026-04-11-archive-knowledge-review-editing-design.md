# 档案知识审核发布与在线修正设计

## 背景

当前“知识治理”页面只是在档案知识 JSON 的基础上生成一张候选项列表，用户只能看见机器抽取出的候选实体、事件、流程，却不能真正修正这些知识，也不能让修正后的结果立即反馈到文档页和图谱页。

这带来三个直接问题：

1. 名称不直观时，用户无法在系统中直接改名。
2. 类别不准确时，用户无法修正分类。
3. 明显重复的知识项无法合并，图谱和文档明细会持续出现重复项。

用户已经明确要求：

1. 将“知识治理”改为更直观的中文表述。
2. 支持实体、事件、流程三类知识的审核和在线修正。
3. 修正结果直接体现在当前知识库的文档页和图谱页上，而不是等到另一个离线发布阶段。
4. 合并时自动保留两边全部文档关联和证据。
5. 本轮不保留操作历史，也不做撤销。

## 目标

本轮目标是把当前只读的“知识治理”页升级为真正可用的“知识审核发布”页：

1. 将导航和页面文案统一改为“知识审核发布”。
2. 提供候选知识列表，并支持按类型、审核状态、关键字筛选。
3. 支持对单个知识项进行名称修改、类别修正、别名编辑。
4. 支持同类型知识项合并，自动合并文档关联、证据、别名和关系。
5. 支持单项通过、单项驳回、批量通过。
6. 所有修改在保存后立即作用于当前档案知识库，文档页和图谱页刷新后立刻可见。

## 非目标

本轮不包含以下内容：

1. 不做操作历史。
2. 不做撤销和版本回退。
3. 不引入数据库化知识编辑模型。
4. 不做人机协同冲突处理。
5. 不做跨档案库的知识合并。

## 核心方案

### 当前可编辑库

为避免直接破坏原始抽取结果，保留现有的原始档案知识文件：

- `20161116-nas-knowledge.json`

新增一份“当前可编辑库”：

- `20161116-nas-knowledge-curated.json`

读取规则：

1. 默认优先读取 `-knowledge-curated.json`。
2. 如果该文件不存在，则回退读取原始 `-knowledge.json`。

写入规则：

1. 第一次进行人工修改时，如果 `-knowledge-curated.json` 不存在，则先复制原始知识文件作为基线。
2. 所有审核、改名、改类、别名编辑、合并操作都只写入 `-knowledge-curated.json`。

对用户来说，这等同于“直接回写当前知识库”，因为当前页面读取的就是这份可编辑库；但底层仍保留原始抽取结果，便于未来重建和对照。

### 审核状态

为实体、事件、流程统一引入 `review_status` 字段：

1. `pending`
2. `approved`
3. `rejected`

规则：

1. 初始抽取项默认视为 `pending`。
2. `approved` 和 `pending` 的知识继续参与图谱、文档详情、检索和统计。
3. `rejected` 的知识从文档页、图谱页、公开检索结果中隐藏，但仍保留在审核页中可筛选查看。

这意味着：

1. “通过”主要作用于审核页状态流转。
2. “驳回”会立即从用户可见知识结果中移除该项。

## 用户体验设计

### 导航与页面命名

导航项名称从“知识治理”改为“知识审核发布”。

页面标题改为：

- `知识审核发布`

副标题聚焦两件事：

1. 审核机器抽取结果
2. 将修正直接应用到当前知识库

### 筛选区

在候选列表上方提供筛选工具：

1. 关键字搜索：匹配名称和别名
2. 类型筛选：全部、实体、事件、流程
3. 审核状态筛选：全部、待审核、已通过、已驳回
4. 快捷开关：默认勾选“只看待审核”

### 列表区

列表字段保留并增强：

1. 类型
2. 名称
3. 类别
4. 覆盖文档
5. 置信度
6. 证据
7. 审核状态
8. 操作

操作包括：

1. `查看 / 编辑`
2. `通过`
3. `驳回`

同时支持行选择和顶部批量操作：

1. `批量通过`

### 编辑抽屉

点击名称或“查看 / 编辑”后，右侧抽屉展开，展示：

1. 基础信息
2. 证据与关联文档
3. 关系项
4. 编辑表单
5. 合并面板

编辑表单支持：

1. 修改名称
2. 修改类别
3. 维护别名列表

底部按钮：

1. `应用修改`
2. `通过`
3. `驳回`

### 合并面板

抽屉内支持同类型候选项检索并选择目标项进行合并。

交互规则：

1. 当前打开的项为“主项”。
2. 选择另一个同类型候选项作为“副项”。
3. 点击“合并到当前项”后，副项被移除，所有可保留内容自动并入主项。

## 数据规则

### 编辑规则

1. 名称允许直接修改。
2. 类别允许直接修改为前端下拉中的预设分类值。
3. 别名编辑结果要去重、去空字符串，并排除与主名称完全相同的值。

### 合并规则

仅允许同类型知识项合并。

合并时自动处理：

1. `document_ids` 取并集并去重。
2. `evidence` 取并集并按 `document_id + excerpt` 去重。
3. `aliases` 取并集并去重，同时把副项名称纳入别名候选。
4. `relations` 中所有指向副项或从副项出发的关系统一改写为主项。
5. 如果关系改写后形成自环，则删除该关系。
6. 如果关系改写后产生重复关系，则去重。
7. 删除副项。

合并后：

1. 文档统计由现有统计逻辑自动重算。
2. 档案摘要中的实体数、事件数、流程数重新计算。

## 接口设计

在现有档案知识接口基础上新增以下能力：

- `GET /api/knowledge/archive/{archive_id}/review-candidates`
  - 新增支持返回 `review_status`
  - 支持 `query`、`item_type`、`review_status` 查询参数

- `PATCH /api/knowledge/archive/{archive_id}/items/{item_id}`
  - 更新名称、类别、别名

- `POST /api/knowledge/archive/{archive_id}/items/{item_id}/review`
  - 请求体包含 `review_status`
  - 允许值：`pending`、`approved`、`rejected`

- `POST /api/knowledge/archive/{archive_id}/reviews/batch-approve`
  - 请求体包含 `item_ids`

- `POST /api/knowledge/archive/{archive_id}/items/merge`
  - 请求体包含 `primary_item_id` 和 `secondary_item_id`

返回策略：

1. 修改类接口返回更新后的知识项详情，便于前端立即刷新抽屉内容。
2. 批量通过返回成功数量。

## 后端设计

### 服务层

在 `ArchiveKnowledgeService` 中补充“可编辑库”读写能力：

1. `_resolve_read_path`
2. `_resolve_edit_path`
3. `_load_for_edit`
4. `_save_payload`
5. `_rebuild_summary`
6. `_apply_visibility_filter`

新增编辑能力：

1. `update_item`
2. `set_review_status`
3. `batch_approve`
4. `merge_items`

所有公开读取接口先经过可见性过滤：

1. `rejected` 项不再出现在图谱、文档详情、搜索、实体列表、流程列表中。

### 路由层

继续复用 `knowledge.py` 中的档案知识路由，不再使用现有数据库版 `governance.py` 来处理档案审核。

原因：

1. 当前用户看的文档页和图谱页都基于档案 JSON。
2. 如果审核写进数据库而读取仍来自 JSON，就无法做到“当前页面立即生效”。

## 前端设计

### 页面

继续使用现有 `GovernancePage.tsx`，但角色改为真正的档案审核页。

需要新增的前端状态：

1. 查询关键字
2. 类型筛选
3. 审核状态筛选
4. 选中行 ID 列表
5. 当前编辑知识项 ID
6. 当前编辑知识项详情
7. 抽屉保存中状态

### 交互流

1. 页面初始化加载候选项列表。
2. 用户筛选后查看待处理项。
3. 点击名称打开抽屉，拉取知识详情。
4. 用户修改名称、类别、别名后点击“应用修改”。
5. 保存成功后刷新候选列表，同时让文档页和图谱页在下次请求时读取最新内容。
6. 如果执行“驳回”，该项从图谱和文档页立即消失。
7. 如果执行“合并”，副项在审核页和图谱页中消失，主项文档覆盖度和证据更新。

## 错误处理

1. 合并不同类型项时返回 `400`。
2. 编辑不存在的知识项时返回 `404`。
3. 批量通过时忽略已不存在的 ID，并返回实际更新数量。
4. 保存失败时，抽屉内展示错误提示，不关闭抽屉。

## 测试策略

### 后端

新增或扩展 API 测试，覆盖：

1. 当存在 `-knowledge-curated.json` 时，读取接口优先读该文件。
2. 更新名称、类别、别名后，实体详情和候选列表立即变化。
3. 将某项标记为 `rejected` 后，图谱、文档详情和搜索不再返回该项。
4. 批量通过可更新多个知识项的审核状态。
5. 合并后主项文档关联、别名、证据和关系被正确合并，副项消失。

### 前端

扩展 `GovernancePage` 测试，覆盖：

1. 页面标题和导航文案更新为中文新名称。
2. 可按审核状态和类型筛选候选项。
3. 点击“查看 / 编辑”可打开抽屉并展示证据、文档和关系。
4. 应用修改会调用更新接口并刷新列表。
5. 批量通过会调用批量接口。
6. 合并会调用合并接口并刷新页面数据。

## 验收标准

满足以下条件即可视为完成：

1. 导航和页面已从“知识治理”变为“知识审核发布”。
2. 用户可以对实体、事件、流程执行改名、改类、别名编辑。
3. 用户可以将同类型知识项合并，且保留两边全部文档和证据。
4. 用户可以单项通过、单项驳回、批量通过。
5. 驳回或合并后的结果，文档页与图谱页刷新后立即体现。
6. 前后端自动化测试通过。
