# P3 软件设计系统 `XX-P3` 设计

**日期：** 2026-04-17

**对应节点：**
- `P3` 软件设计系统 `[#9]`
- `P3.1` 场景驱动的功能模块划分 `[#10]`
- `P3.2` 软件设计说明生成与人工校核 `[#22]`
- `P3.3` 模块级工具化描述生成 `[#23]`
- `P3.4` 子模块级工具化描述下钻与拆分 `[#24]`

## 1. 设计目标

在 `P2` 已形成需求规格模型的前提下，为平台提供一个独立的 **软件设计系统**，把业务需求进一步转化为：

- 场景驱动的功能模块结构
- 可供技术专家审阅的 `软件设计说明`
- 可供 `P4` 工具中台消费的 `模块级工具化描述`

第一版产品名称采用：`XX-P3`

第一版页面定位采用：**独立驾驶舱页 + 页内工作区切换**

## 2. 产品定位与边界

### 2.1 产品定位

`XX-P3` 不是：

- `P2` 需求建模器的延伸步骤
- `P4` 工具中台的一个子模块
- 最终应用构建器
- 组件命中或装配决策台

`XX-P3` 是：

- `P2 -> P4` 之间的结构化软件设计中台
- 需求规格到软件设计对象之间的翻译层
- 技术专家介入审阅和冻结设计结果的承载面
- 模块级工具化描述的权威输出源

### 2.2 第一版边界

第一版只覆盖以下闭环：

`需求规格快照 -> 场景驱动模块结构 -> 软件设计说明投影 -> 人工校核/冻结 -> 模块级工具化描述导出`

第一版明确不做：

- 最终应用代码生成
- 组件命中与复用决策
- 多人协同评审流
- 自动子模块全量拆分
- 设计说明 Word/PDF 排版优化
- 与 `P4` 的在线双向联动编辑

### 2.3 并行开发边界

本设计遵守当前并行开发约束：

- `P3` 只通过 `P2` 的标准需求快照或标准 API 消费上游结果
- `P3` 对 `P4` 只输出冻结后的工具化描述包，不读取 `P4` 内部运行记录
- `P3` 的实现采用“模块化单体优先、按微服务边界设计”的方式，后续可以单独拆出服务
- `P3` 应提供独立页面壳层，不混入当前主导航

## 3. 权威对象与投影

### 3.1 权威对象

`P3` 的权威表达不是一份文档，而是结构化对象：`SoftwareDesignModel`

建议最小结构如下：

```yaml
design_id: sdm_xxx
requirement_snapshot_id: arm_snapshot_xxx
status: draft
context:
  application_name: 空域协同规划应用
  design_goal: 支撑多角色协同规划与状态跟踪
scenes:
  - scene_id: scene_1
    name: 规划发起
    summary: 由规划人员发起任务并录入基础信息
modules:
  - module_id: module_1
    name: 规划任务管理
    scene_ids: [scene_1]
    responsibilities:
      - 创建规划任务
      - 跟踪规划状态
    business_objects:
      - 国家空域体系
    related_flows:
      - 服务互操作流程
    interactions:
      - target_module_id: module_2
        interaction_type: submits_for_review
review:
  status: draft
  reviewer_notes: []
```

### 3.2 软件设计说明投影

`软件设计说明` 不是与结构化对象并列的另一套权威数据，而是 `SoftwareDesignModel` 的人类可读投影。

它至少应包含：

- 设计背景与目标
- 用户工作场景
- 功能模块清单
- 模块职责、边界与协作关系
- 关键对象、流程、规则与交互面
- 风险、待确认项与人工评审结论

### 3.3 工具化描述投影

`模块级工具化描述` 是冻结后的 `SoftwareDesignModel` 面向 `P4` 的标准输出投影。

建议第一版对象名采用：`ModuleToolDescriptorBundle`

最小结构如下：

```yaml
bundle_id: mtdb_xxx
design_id: sdm_xxx
status: frozen
descriptors:
  - descriptor_id: descriptor_1
    module_id: module_1
    name: 规划任务管理
    problem_statement: 管理规划任务的创建、状态跟踪与协同动作
    inputs:
      - planning_request
    outputs:
      - planning_task
    candidate_tools:
      - workflow_engine
      - form_builder
    source_refs:
      requirement_snapshot_id: arm_snapshot_xxx
      scene_ids: [scene_1]
```

### 3.4 顺序约束

`P3` 的设计说明与工具化描述不是平行关系，而是顺序关系：

`需求规格 -> 软件设计对象 -> 软件设计说明投影 -> 人工校核/冻结 -> 工具化描述导出`

允许直接在结构化对象层做修订，但不允许绕过结构化对象只修改说明书文本。

## 4. 第一版最小闭环

### 4.1 生命周期

第一版承载 4 个连续环节：

1. 选择 `P2` 输出的需求快照并初始化设计任务
2. 基于用户工作场景生成功能模块结构
3. 投影为软件设计说明并支持人工校核
4. 将冻结结果导出为模块级工具化描述

### 4.2 第一版首批骨架任务

为便于并行开发，第一版骨架拆为 8 个三级节点：

- `P3.1.1` 输入需求快照选择与设计任务初始化
- `P3.1.2` 场景驱动模块生成与关系图
- `P3.1.3` 模块追溯与来源投影
- `P3.2.1` 软件设计说明投影生成
- `P3.2.2` 人工校核、修订记录与冻结版本
- `P3.3.1` 模块级工具化描述协议
- `P3.3.2` `P4` 兼容导出与验证
- `P3.4.1` 子模块拆分规则与人工下钻

### 4.3 首版验收口径

第一版成功标志：

`选择一份需求规格快照 -> 自动得到模块结构 -> 技术专家可修订并冻结 -> 输出可被 P4 消费的工具化描述包`

## 5. 页面方案

### 5.1 路由与承载方式

第一版新增独立路由：

- `/xx-p3`

承载规则：

- 不并入当前顶部导航菜单
- 不替换当前首页
- 与现有知识仓页面同属于同一个前端应用，但使用独立页面壳层

### 5.2 页面结构

页面从上到下分为 4 层：

#### 5.2.1 顶部总览区

包含：

- 页面标题：`XX-P3`
- 页面副标题：`软件设计系统 / Software Design System`
- 当前输入上下文：需求快照、设计状态、冻结状态、最近导出状态

#### 5.2.2 核心指标区

第一版至少展示：

- 当前模块数
- 已识别场景数
- 待确认项数量
- 已冻结设计数
- 最近导出成功率

#### 5.2.3 结构与风险区

这一层是 `XX-P3` 的标志性信息区。

必须包含：

- 模块关系总览图
- 风险与待确认项摘要

#### 5.2.4 工作区切换区

首版不跳转子页，而是在页内切换 4 个工作区：

- `总览`
- `模块设计`
- `设计说明`
- `工具化描述`

### 5.3 工作区定义

#### 5.3.1 `总览`

目标：

- 展示当前设计任务的整体状态

必须包括：

- 输入需求快照摘要
- 模块统计
- 风险与待确认项
- 最近说明书冻结记录
- 最近导出结果

#### 5.3.2 `模块设计`

目标：

- 承载场景到模块结构的生成和调整

必须包括：

- 场景清单
- 模块卡片/关系图
- 关键对象、流程和规则的映射
- 模块追溯信息

#### 5.3.3 `设计说明`

目标：

- 承载软件设计说明投影与人工校核

必须包括：

- 说明书结构预览
- 模块级章节
- 待确认项与修订记录
- 冻结操作入口

#### 5.3.4 `工具化描述`

目标：

- 展示冻结后的模块级工具化描述及导出状态

必须包括：

- 描述包清单
- 字段预览
- 与 `P4` 的兼容性校验结果
- 导出状态与快照编号

## 6. 模块设计

在“模块化单体优先”的约束下，第一版建议拆为 4 个模块：

- `设计任务服务`
  - 需求快照选择、设计任务创建、状态流转
- `模块生成服务`
  - 场景识别、模块边界组织、关系追溯
- `设计评审服务`
  - 软件设计说明投影、人工修订、冻结
- `工具化导出服务`
  - 模块级工具化描述生成、兼容性校验、导出

模块之间只通过标准对象交互，不允许直接读取彼此内部状态。

## 7. 技术选型建议

建议技术选型：

- 后端子域：`FastAPI + Pydantic`
- 前端页面：`React + TypeScript + Ant Design`
- 前端图结构展示：优先复用当前图谱/拓扑组件风格
- 数据持久化：首版沿用文件型版本化快照，后续再评估数据库承载
- 契约约束：统一 `JSON Schema / Pydantic Model`

## 8. 与上下游的标准边界

### 8.1 与 P2 的边界

`P3` 只消费：

- `ApplicationRequirementModel` 冻结快照
- 对应的 `MD` 可读投影
- 需求快照元信息

`P3` 不消费：

- `P2` 草稿中间态
- `P2` 前端本地表单状态
- `P2` 内部推荐过程细节

### 8.2 与 P4 的边界

`P3` 只向 `P4` 提供：

- 冻结后的 `ModuleToolDescriptorBundle`
- 兼容性校验结果
- 需求/设计追溯元信息

`P4` 不应直接读取：

- `P3` 设计评审中间状态
- `P3` 草稿修订缓存
- `P3` 内部页面控件状态

## 9. 验收口径

第一版验收只看以下 5 条是否成立：

1. 给定一份需求规格快照，系统能否生成可解释的功能模块结构
2. 软件设计说明是否总能从结构化对象稳定投影出来
3. 技术专家是否能对说明书进行修订、记录并冻结
4. 冻结结果是否能稳定导出为模块级工具化描述
5. `P4` 是否可以把该描述包作为正式输入消费
