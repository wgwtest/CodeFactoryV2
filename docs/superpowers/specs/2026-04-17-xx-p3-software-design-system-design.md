# P3 软件设计编制与模块工单下发系统 `XX-P3` 设计

**日期：** 2026-04-17

**对应节点：**
- `P3` 软件设计系统 `[#9]`
- `P3.1` 设计依据与模板中心
- `P3.2` 需求规格说明接入与分析
- `P3.3` 软件设计说明生成与校核
- `P3.4` 人工评审与冻结
- `P3.5` 模块级工具化描述与批次工单包生成
- `P3.6` `P4` 兼容交接与推送

## 1. 阶段目标与应用对象

### 1.1 `P3` 的真实目标

`P3` 的目标不是规范或优化 `Code Factory` 平台自身的研发过程。

`P3` 的目标是为 **软件工厂将要生产的软件级产物** 提供一个正式的软件设计编制与下发阶段，使上游 `P2` 已完成的 `需求规格说明` 可以继续被加工为：

- 一份可供人工评审与冻结的 `软件设计说明`
- 一份带总体推荐信息的 `批次模块工单包`
- 一套可追溯、可讨论、可审批、可推送到 `P4` 的订单流转记录

因此，`P3` 首版不是“文档写作器”，而是 **订单驱动的软件设计编制与工单下发台**。

### 1.2 `P3` 服务的对象

`P3` 服务的对象是软件工厂的 **软件级生产任务**，不是软件工厂平台本身。

首版明确约束如下：

- 支持对象：`软件级` 产物
- 暂不支持对象：`系统级 / 子系统级` 产物
- 输入文档：一份正式的 `需求规格说明`
- 输出文档：一份正式的 `软件设计说明`
- 输出交付包：一份面向 `P4` 的 `批次模块工单包`

一份 `需求规格说明` 对应一张 `P3` 订单。

一张 `P3` 订单在完成后默认只冻结：

- `1` 份软件设计说明
- `1` 份批次模块工单包

批次模块工单包内部可以包含 `N` 条模块工单条目。

### 1.3 `P3` 不是什么

`XX-P3` 不是：

- `P2` 的需求规格说明写作页面
- `P4` 的工具匹配执行器
- 最终应用代码生成器
- 纯自动化的一键生成器
- 只负责“软设导出”的静态文档页

`XX-P3` 是：

- `P2 -> P4` 之间的软件设计编制中台
- 以订单流转驱动的软件设计生成、讨论、修订、评审、冻结与下发阶段
- 软件设计说明和模块工单包的统一权威来源

## 2. 首版业务闭环

### 2.1 闭环定义

首版承载的标准闭环为：

`P2 需求规格说明 -> P3 接入与分析 -> 创建 P3 订单并初始化设计任务 -> 接单审批 -> AI/模型生成软设草案 -> 生成结果校核 -> 人机迭代修订 -> 人工评审 -> 冻结软件设计说明 -> 生成批次模块工单包 -> 人工推送到 P4`

### 2.2 关键操作原则

- `P3` 必须有订单列表、状态流转、审批、驳回与历史记录
- `P3` 不能把输入需求规格说明当作黑盒文件直接丢给生成器，必须先完成接入、快照化和结构分析
- `需求规格说明 -> 软件设计说明` 的首轮生成默认交给模型或智能体完成
- 软设草案生成后，必须经过至少一轮结构完整性与规范符合性校核
- 生成后必须允许人工继续修改，不把 AI 结果当作直接终稿
- 人工修改方式首版至少应支持一种：
  - 结构化编辑器
  - 评论/留言板驱动的迭代修订
- 未经人工评审通过的设计结果，不得进入 `P4`
- 推送到 `P4` 的动作必须由人工触发，不做自动直推

### 2.3 一张订单的标准产物

每张 `P3` 订单应围绕同一份输入需规形成 3 类产物：

1. `结构化设计基线`
2. `软件设计说明`
3. `批次模块工单包`

其中：

- `结构化设计基线` 是内部权威对象
- `软件设计说明` 是面向专家审阅的正式文档投影
- `批次模块工单包` 是面向 `P4` 的生产交接投影

### 2.4 首版基础能力不依赖订单存在

`P3` 首版不能把全部基础能力都绑定在订单存在与否上。

即使当前没有任何 `P3` 订单，页面也应至少提供以下可直接使用的基础能力：

- `软件设计说明模板` 的目录展示
- `软件设计说明模板` 的正文阅读
- 相关 `军标 / 规范文档` 的查询与定位
- 模板章节和规范条款之间的映射查看

首版允许先采用较轻的实现方式：

- 模板展示先采用 `PDF` 阅读器
- 规范文档查询先支持文档级检索、章节定位和关键条款摘录

这些能力的目标不是替代后续订单流，而是为后续 `P3` 订单提供统一的设计依据工作台。

## 3. 核心对象模型

### 3.1 `P3Order`

`P3` 的第一核心对象是订单，而不是文档本身。

建议最小结构如下：

```yaml
order_id: p3_order_xxx
source_requirement_spec_id: srs_xxx
source_requirement_version: v1.0
application_name: 空域协同规划软件
status: pending_approval
submitter: 张三
submitted_at: 2026-04-17T10:00:00Z
approval:
  status: pending
  approver: null
  comments: []
generation:
  strategy: ai_first
  model_run_id: null
review:
  status: not_started
handoff:
  p4_push_status: not_ready
```

约束如下：

- `1` 份需求规格说明只能对应 `1` 张活跃的 `P3` 主订单
- 同一订单可以有多轮生成与修订
- 但只冻结 `1` 份正式软件设计说明和 `1` 份正式批次模块工单包

### 3.2 `SoftwareDesignBaseline`

`P3` 的第二核心对象是结构化设计基线。它不是最终给人看的文档，而是 `P3` 内部的权威设计表达。

建议最小结构如下：

```yaml
baseline_id: sdb_xxx
order_id: p3_order_xxx
status: draft
context:
  application_name: 空域协同规划软件
  design_scope: 软件级
  recommended_style:
    architecture_mode: unified_service
    interaction_mode: bs
    deployment_hint: intranet_first
modules:
  - module_id: module_1
    name: 规划任务管理
    responsibilities:
      - 创建规划任务
      - 跟踪任务状态
    inputs:
      - planning_request
    outputs:
      - planning_task
    constraints:
      - 审批状态需留痕
    recommended_tools:
      - workflow_engine
      - form_builder
review_threads:
  - thread_id: thread_1
    topic: 任务状态机是否拆分为独立模块
    status: open
traceability:
  source_requirement_spec_id: srs_xxx
  mapped_requirement_ids:
    - req_1
    - req_2
```

### 3.3 `SoftwareDesignDescription`

`软件设计说明` 不是第二套平行权威对象，而是 `SoftwareDesignBaseline` 的正式文档投影。

它用于：

- 人工专家审阅
- 正式冻结
- 留存设计结论
- 为下游模块工单包提供前置设计说明

### 3.4 `ModuleWorkorderBatchPackage`

`P3` 输出到 `P4` 的不是裸列表，而是一份带前置说明的批次模块工单包。

建议最小结构如下：

```yaml
package_id: mwbp_xxx
order_id: p3_order_xxx
design_description_id: sdd_xxx
status: ready_for_push
package_overview:
  architecture_recommendation: unified_service
  interaction_mode: bs
  deployment_hint: intranet_first
  tool_recommendations:
    - workflow_engine
    - form_builder
  design_notes:
    - 先实现统一服务版本，后续再评估微服务拆分
items:
  - item_id: workitem_1
    module_id: module_1
    title: 规划任务管理模块实现
    objective: 实现规划任务创建、状态流转与查询能力
    inputs:
      - planning_request
    outputs:
      - planning_task
    constraints:
      - 全链路操作留痕
    acceptance:
      - 可创建规划任务
      - 可查询状态历史
    recommended_tools:
      - workflow_engine
      - form_builder
traceability:
  source_requirement_ids:
    - req_1
    - req_2
```

这份包必须同时表达两层信息：

- 包级总体设计推荐
- 条目级模块实现需求

### 3.5 `DiscussionThread / ReviewDecision`

`P3` 首版需要显式承载人机协作与人工评审痕迹，因此应定义至少两类附属对象：

- `DiscussionThread`
  - 记录 AI 与人工围绕某个设计点的对话、留言、修订建议
- `ReviewDecision`
  - 记录人工评审通过、驳回、要求修改、冻结意见

这两类对象不替代正式文档，但必须成为订单历史的一部分。

## 4. 面向软件级产物的文档体系

### 4.1 设计原则

本节讨论的文档体系是 **软件工厂产物的工程文档体系**，不是 `Code Factory` 平台自身的研发文档体系。

首版采用以下原则：

- 先支持 `软件级` 文档，不强行覆盖系统级文档
- 先锁定主文档链，再扩展可选派生文档
- 正式文档必须和订单、结构化基线、工单包形成追溯关系
- 文档不是孤立文件，而是生产流程中的阶段性交付物

### 4.2 首版主文档链

首版正式纳入 `P3` 设计的主文档链如下：

1. `需求规格说明`
   - 上游 `P2` 输出
   - `P3` 的正式输入
2. `软件设计说明`
   - `P3` 的正式输出
   - `P3` 评审与冻结的核心对象
3. `批次模块工单包`
   - `P3` 面向 `P4` 的正式交付包
   - 内含多个模块工单条目

### 4.3 模板选型原则

由于首版只支持软件级产物，主模板族应优先对齐软件级军标文种，而不是系统级文种。

推荐采用：

- `需求规格说明`
  - 参考 `DI-IPSC-81433` `Software Requirements Specification (SRS)`
- `软件设计说明`
  - 参考 `DI-IPSC-81435` `Software Design Description (SDD)`

不采用 `SHRS/SHDD` 作为首版主模板的原因是：

- `SHRS/SHDD` 更适合系统级或子系统级对象
- 当前 `P3` 首版只服务软件级产物
- 直接引入系统级模板会让首版对象层级失焦

### 4.4 基础文档能力

`P3` 首版必须把“模板展示”和“规范查询”定义为平台基础能力，而不是订单附属功能。

首版最小闭环应包括：

- `模板目录`
  - 展示当前支持的软件设计说明模板族、版本号、适用对象和来源依据
- `模板阅读器`
  - 允许直接阅读模板原文，首版可以采用 `PDF` 阅读器
- `规范文档库`
  - 展示当前纳入 `P3` 的设计规范、军标和补充参考材料
- `规范查询`
  - 支持标题检索、章节检索、条款定位和关键段落查看
- `模板-规范映射`
  - 支持查看“某一模板章节依据了哪些规范条款”

这组能力应在无订单状态下可见、可用。

### 4.5 `需求规格说明` 在体系中的角色

`需求规格说明` 的模板编制与正式生成属于 `P2` 的职责，不是 `P3` 首版直接生成的对象。

但 `P3` 必须提前把这份文档在整体体系中的位置定义清楚，因为它是 `P3` 的唯一正式输入。

`P3` 对 `需求规格说明` 的要求至少包括：

- 文档必须已经过上游正式确认
- 文档应具有稳定的章节结构和编号
- 关键需求条目应有唯一标识
- 需求条目应可被设计章节和模块工单项引用

### 4.6 `软件设计说明` 的职责

`软件设计说明` 是 `P3` 阶段的正式主文档。

它至少应承载：

- 设计目标与范围
- 总体架构与技术路线建议
- 架构模式说明，例如统一服务或微服务
- 交互形态说明，例如 `BS / CS`
- 模块划分与职责
- 模块间接口、数据流、控制流
- 关键约束、风险、待确认项
- 需求到设计的追溯关系
- 评审结论与冻结信息

### 4.7 `批次模块工单包` 的职责

`批次模块工单包` 不是传统军标文种，但它是软件工厂内部生产链必须存在的正式交付物。

它应位于 `软件设计说明` 之后，承担“设计冻结后向 `P4` 下发可执行模块请求”的作用。

它至少应承载：

- 包级前置说明
- 推荐工具/能力类型
- 推荐架构模式
- 推荐交互形态
- 模块工单条目列表
- 每条工单的输入、输出、约束、验收和追溯来源
- 推送状态与目标批次信息

### 4.8 可选派生文档

首版不把这些文档做成主链强制项，但应预留扩展位：

- `接口需求说明`
- `接口设计说明`
- `部署与运行建议附录`
- `数据项/消息项附录`

当后续某类软件产物的接口复杂度显著提高时，再决定是否把它们升级为主文档。

### 4.9 文档追溯链

`P3` 首版必须建立以下追溯链：

`需求规格说明条目 -> 软件设计说明章节/模块 -> 批次模块工单包条目 -> P4 工具订单`

禁止出现以下做法：

- 只改 `软件设计说明` 文本，不回写结构化设计基线
- 只编工单包，不保留与软设的对应关系
- `P4` 直接绕过工单包读取 `P3` 内部草稿状态

## 5. 订单流转与评审机制

### 5.1 订单生命周期

建议首版状态如下：

1. `pending_approval`
   - 已接收到上游需规订单，待审批
2. `rejected`
   - 审批拒绝，不进入软设生成
3. `approved_for_generation`
   - 审批通过，允许启动生成
4. `generating`
   - AI/模型生成软设草案中
5. `draft_ready`
   - 首轮草案已生成
6. `in_revision`
   - 人工与 AI 持续讨论、修改
7. `pending_review`
   - 提交人工正式评审
8. `changes_requested`
   - 评审要求修改
9. `frozen`
   - 软件设计说明冻结
10. `package_ready`
    - 批次模块工单包已生成
11. `pushed_to_p4`
    - 已人工推送至 `P4`

### 5.2 审批与驳回

`P3` 首版必须有明确的接单审批入口。

审批阶段至少回答 3 个问题：

- 这份需规是否已经达到 `P3` 可消费状态
- 这份需规是否属于 `软件级` 对象
- 这份需规是否可以进入当前批次设计资源队列

若任何一项不满足，应允许驳回并给出原因。

### 5.3 人机协作修订

首版不要求同时做重型编辑器和重型协同系统，但必须有一个稳定的人机协作修订面。

推荐首版采用“文档投影 + 评论线程/留言板”的轻量方式：

- 软设正文按章节投影展示
- 每章或每模块都可挂评论线程
- AI 可根据评论生成修订建议
- 人工选择接受、拒绝或继续追问

如果后续编辑诉求增强，再升级为结构化编辑器。

### 5.4 人工评审与冻结

`P3` 的正式出口门是人工评审，不是模型输出。

冻结前必须完成：

- 关键章节完整性检查
- 关键需求条目追溯检查
- 总体技术路线确认
- 模块划分与边界确认
- 批次模块工单包生成准备确认

只有 `frozen` 状态的设计结果才能生成正式批次模块工单包。

## 6. 页面与工作区方案

### 6.1 路由与定位

第一版新增独立路由：

- `/xx-p3`

该页面是一个独立壳层的订单驱动设计工作台，不并入当前顶部主导航。

### 6.2 页面结构

首版页面从上到下分为 5 层：

#### 6.2.1 顶部总览区

包含：

- 页面标题：`XX-P3`
- 页面副标题：`软件设计编制与模块工单下发系统`
- 当前队列概览：待审批订单数、评审中订单数、待推送包数

#### 6.2.2 模板与规范入口区

这是首版必须补齐的一层，并且不依赖订单存在。

至少包括：

- 软件设计说明模板列表
- 模板版本信息
- 模板阅读器入口
- 规范文档库入口
- 规范查询入口

#### 6.2.3 订单队列区

这是首版必须突出的一层。

至少包括：

- 需规订单列表
- 状态筛选
- 审批/驳回入口
- 最近更新时间

#### 6.2.4 当前订单上下文区

至少包括：

- 输入需求规格说明摘要
- 当前软设状态
- 当前评审状态
- 当前批次模块工单包状态

#### 6.2.5 工作区切换区

首版采用页内切换，不拆成多个独立子页。

建议工作区为：

- `模板与规范`
- `总览`
- `设计编制`
- `评审协作`
- `模块工单包`

### 6.3 工作区定义

#### 6.3.1 `模板与规范`

目标：

- 在无订单状态下也能提供设计依据浏览和查询能力

必须包括：

- 模板目录与版本信息
- 模板 `PDF` 阅读器
- 规范文档检索框
- 规范文档定位结果
- 模板章节与规范条款映射

#### 6.3.2 `总览`

目标：

- 展示当前订单整体健康度和关键风险

必须包括：

- 输入需求规格说明摘要
- 当前阶段状态
- 风险与待确认项
- 历史操作时间线

#### 6.3.3 `设计编制`

目标：

- 展示和修订软件设计说明草案

必须包括：

- 说明书章节导航
- 总体技术路线说明
- 模块划分与关系
- 章节级修订入口

#### 6.3.4 `评审协作`

目标：

- 承载 AI 留言、人工评论、评审结论和冻结入口

必须包括：

- 评论线程列表
- 章节/模块挂点
- AI 修订建议
- 评审结论与冻结操作

#### 6.3.5 `模块工单包`

目标：

- 管理面向 `P4` 的批次工单包

必须包括：

- 包级前置说明
- 工单条目列表
- 每条工单的输入/输出/约束/验收
- 推荐工具与实现模式
- 手动推送到 `P4` 的入口

## 7. 内部模块划分

在“模块化单体优先”的约束下，首版建议拆为 7 个内部模块：

- `设计依据与模板中心服务`
  - 管理模板目录、模板版本、模板阅读投影、规范文档索引与查询
- `需求规格说明接入与分析服务`
  - 接收正式需求规格说明、生成输入快照、完成对象/流程/约束分析，并承载 `XX-P2-Sim` 上游联调入口
- `订单受理与审批服务`
  - 根据已完成分析的需求规格说明创建 `P3` 订单，并负责列表展示、审批、驳回、状态流转
- `设计生成与校核编排服务`
  - 调用模型/智能体完成 `需规 -> 软设草案`，并执行结构/规范校核
- `设计基线与文档投影服务`
  - 维护结构化设计基线，投影生成软件设计说明
- `评审协作服务`
  - 承载评论线程、修订建议、评审决定、冻结
- `模块工单包装配与下发服务`
  - 根据冻结软设生成批次模块工单包，并人工推送到 `P4`

模块之间只通过标准对象交互，不允许直接读取彼此内部运行态。

## 8. 与上下游的边界

### 8.1 与 `P2` 的边界

`P3` 只消费：

- 已正式确认的 `需求规格说明`
- 需求条目唯一标识
- 需求版本信息和提交元信息

`P3` 不消费：

- `P2` 草稿表单
- `P2` 内部推荐链路细节
- 未经正式确认的临时需求文本

### 8.2 与 `P4` 的边界

`P3` 只向 `P4` 提供：

- 冻结后的 `批次模块工单包`
- 包级总体推荐信息
- 模块条目级输入、输出、约束、验收和追溯信息

`P4` 不应直接读取：

- `P3` 评论草稿
- `P3` 软设未冻结版本
- `P3` 内部编辑器状态

## 9. 技术选型建议

建议技术选型：

- 后端子域：`FastAPI + Pydantic`
- 前端页面：`React + TypeScript + Ant Design`
- 数据持久化：首版沿用文件型版本化快照
- 评论与修订对象：统一结构化存储，避免纯文本散落
- 契约表达：统一 `JSON Schema / Pydantic Model`

## 10. 首版验收口径

第一版验收只看以下 8 条是否成立：

1. 在无订单状态下，用户能否查看 `软件设计说明模板` 目录和版本信息
2. 在无订单状态下，用户能否通过 `PDF` 阅读器查看模板正文，并查询规范文档
3. 能否基于一份正式 `需求规格说明` 创建一张 `P3` 订单并完成审批/驳回
4. 审批通过后，系统能否生成一份可读的软件设计说明草案
5. 人工是否可以围绕软设进行评论、修订、评审与冻结
6. 冻结后，系统能否生成一份带包级前置说明的批次模块工单包
7. 这份工单包是否能同时表达总体推荐信息和条目级模块工单信息
8. `P4` 是否可以把该工单包作为正式输入进行后续工具订单处理
