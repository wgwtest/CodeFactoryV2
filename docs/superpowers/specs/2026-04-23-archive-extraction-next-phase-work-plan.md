# 知识仓库抽取系统下一阶段工作计划

## 文档目的

本文档用于承接当前知识仓库抽取系统的原型成果，并明确下一阶段的工作重点。

当前系统已经具备：

- 13 阶段 runtime 合同
- 单知识库 / 单文档运行态页面
- runtime stream + fallback
- 按阶段组织的策略与配置页面
- 单文档图谱、流程导航、对象观察窗

但这些能力目前仍主要处于“可演示、可观察”的原型阶段，距离“抽取过程真实、策略真正驱动、图谱具备解释价值、抽取效果可验证”的目标还有明显差距。

因此，下一阶段的重点不应继续优先打磨页面外观，而应优先补齐运行真相、策略执行、图谱语义和效果评测这四个基础层。

## 当前判断

### 当前版本的价值

当前版本最大的价值是：已经把知识仓库抽取系统从一个近似黑盒的过程，初步改造成了一个可观察、可配置、可继续演化的基础框架。

### 当前版本的局限

当前版本仍然更接近“运行态原型”，而不是“可信的抽取系统”。

主要问题在于：

1. 页面上虽然能看到 13 阶段，但很多阶段快照仍偏向“阶段结果重建”，不是“真实执行痕迹”。
2. 策略与配置虽然已经可以编辑、保存、冻结到快照，但还没有充分参与真正的抽取决策。
3. 图谱虽然已经开始按阶段做语义化布局，但很多阶段还没有形成“输入对象 -> 判定动作 -> 输出对象”的阶段转换图。
4. 当前缺少抽取质量评测基线，因此很难稳定判断某次优化是否真的提升了抽取效果。

## 下一阶段总目标

下一阶段的总目标是：

**把当前“可演示的运行态原型”推进成“运行过程真实、策略可执行、图谱可解释、效果可评测”的抽取系统基础版本。**

对应四个一级目标：

1. 让 runtime 更真实
2. 让策略真正驱动抽取
3. 让图谱真正表达阶段转换
4. 让抽取质量能够被量化验证

## 核心差距拆解

### 1. runtime 还不够“真”

当前很多阶段图谱和观察信息，虽然已经比最早完整很多，但依然存在“从已有产物反推阶段状态”的情况。

这会导致：

- 页面能展示阶段，但不一定能真实说明阶段内部到底做了什么
- 用户看到的是“结果投影”，不是“执行轨迹”
- 很难解释“为什么当前对象会进入下一步”

下一阶段需要把 runtime 从“阶段快照重建”继续推进为“真实阶段事件留痕”。

### 2. 策略配置已经接上，但还没有真正成为抽取引擎的一部分

当前已经有：

- 策略配置页面
- 阶段策略合同
- 策略保存接口
- 抽取启动时的策略快照冻结

但还缺少关键的一步：

**这些策略要真正参与 parser 路由、证据保留、候选筛选、关系归一、质量门禁等阶段决策。**

否则策略页仍然偏向“配置可见”，而不是“配置驱动”。

### 3. 图谱已经开始变清楚，但还没有成为“阶段转换图”

单文档图谱现在已经具备基础交互和部分阶段的语义化布局，但整体仍存在两个问题：

- 很多阶段里，节点仍偏向“对象堆叠”，而不是“处理转换”
- 节点之间的动作依据、规则命中、AI 判断、对象 lineage 还不够强

下一阶段要让图谱真正回答下面的问题：

- 哪些具体上游对象进入了本阶段
- 本阶段通过哪些规则 / AI / 判定动作处理这些对象
- 本阶段最终产出了哪些下游对象

### 4. 抽取质量还没有被系统化度量

当前大量工作集中在运行态、页面和图谱展示上，但抽取系统最终是否“好用”，仍要回到抽取效果本身。

下一阶段必须补齐评测基线，否则容易出现下面的问题：

- 页面越来越复杂，但抽取质量没有稳定提升
- 优化方向主要依赖主观观察，缺少客观指标
- 很难区分“展示变好了”和“抽取真的变好了”

## 下一阶段优先级

## P0：先把 runtime 做真

这是下一阶段的最高优先级。

### 目标

不再主要依赖“阶段结束后重建阶段图”，而是在真实抽取链路里留下阶段事件、对象、规则命中和输出关系。

### 第一批重点阶段

优先做这 4 个阶段：

1. `unified_document_object`
2. `evidence_constructor`
3. `evidence_graph_chunk_layer`
4. `quality_policy_evaluation_governance_gate`

### 原因

这 4 个阶段最能体现“上游具体对象 -> 本阶段处理 -> 下游结果”的转换关系，也是单文档页图谱最有解释价值的部分。

### 落地要求

在真实运行链里，为每个阶段至少记录：

- 输入对象
- 判定动作
- 命中规则
- AI 决策摘要
- 输出对象
- 关键事件流

### 主要修改位置

- `apps/api/app/archive_knowledge/extraction.py`
- `apps/api/app/archive_knowledge/builder.py`
- `apps/api/app/archive_knowledge/runtime_service.py`
- 对应阶段的 `runtime_*.py`

### 验收标准

- 单文档页在这 4 个阶段看到的是执行轨迹，不是单纯结果映射
- 当前阶段推进时，图谱和观察窗能跟随真实阶段事件更新
- 用户能从页面上看出“为什么从这个对象走到了下一个对象”

## P1：把策略从“可配置”变成“可执行”

### 目标

让策略配置不只是被保存和展示，而是真正参与阶段内的自动决策。

### 第一批要接入的策略执行点

1. parser 路由条件
2. 证据保留 / 过滤阈值
3. 概念候选置信度阈值
4. 关系归一优先级
5. 质量门禁阻断 / 告警条件

### 要求

每个策略项都要能回答：

- 它在什么阶段生效
- 它影响哪一类对象
- 它改变了什么决策
- 它如何被记录到 runtime 里

### 验收标准

- 调整策略后，抽取行为会真实变化
- 单文档页能看到当前阶段正在使用的策略摘要
- 图谱边或观察窗里能看到关键规则命中信息

## P2：把 4 个重点阶段做成真正的阶段转换图

### 目标

让图谱从“对象堆叠”升级成“阶段转换图”。

### 重点阶段要求

#### Unified Document

- 完整体现章节、段落、表格、锚点等统一后对象
- 能看出归一决策和统一结果之间的关系

#### Evidence Constructor

- 明确体现：源段落 -> 证据单元 -> span / anchor
- 证据单元必须带来源 lineage

#### Evidence Graph / Chunk Layer

- 明确体现：evidence unit -> chunk planning -> chunk -> graph layer
- 显示切块和边界修正的依据

#### Quality Gate

- 明确体现：候选对象 -> 规则命中 -> 门禁决策 -> 阻断 / 人工复核 / 发布目标
- 规则命中和默认动作必须可见

### 布局原则

重点阶段优先采用三栏或三带结构：

- 左侧：输入对象
- 中部：策略 / AI / 判定动作
- 右侧：输出结果

### 验收标准

- 用户能通过图谱理解本阶段到底“处理了什么”
- 边标签不再只是关系名，而要体现动作依据
- 重点阶段图谱具备参考价值，而不是只作为视觉装饰

## P3：补一套抽取效果评测基线

### 目标

建立一套最基本的样本文档评测体系，用于判断抽取优化是否真的有效。

### 第一批建议指标

1. 结构覆盖率
2. 证据召回率
3. 候选概念准确率
4. 关系归一稳定性
5. 门禁误判率

### 第一批样本建议

- 长文档
- 结构复杂文档
- 中英混合文档
- 证据稀疏文档
- 存在冲突定义文档

### 验收标准

- 至少有一批固定样本可以重复跑
- 每次优化后都能看到指标变化
- 能区分“页面看起来更好”和“抽取效果真的更好”

## 下一阶段实施顺序

建议严格按下面顺序推进：

1. 先做 P0：4 个重点阶段的真实事件流与对象留痕
2. 再做 P1：把策略执行点真正接入抽取逻辑
3. 再做 P2：让 4 个重点阶段图谱消费真实阶段事件与策略命中
4. 最后做 P3：建立抽取效果基线与验证集

## 明确不优先做的事项

下一阶段不建议优先投入以下工作：

- 继续做纯页面外观微调
- 继续做更多通用图谱布局优化
- 继续扩展新的展示页
- 过早追求全部 13 阶段都做成高度定制图谱

原因是：

如果 runtime 不真、策略不执行、评测不完整，再好的页面也只能提升“看起来像”的程度，不能真正提升抽取系统质量。

## 阶段性完成定义

下一阶段完成时，至少应达到下面的状态：

1. 4 个重点阶段具备真实事件流和对象留痕
2. 策略配置中的关键阈值与动作已接入真实运行逻辑
3. 单文档图谱能清楚体现 4 个重点阶段的输入、判定和输出
4. 至少有一批样本文档与基础评测指标可以重复执行

只有达到以上状态，当前知识仓库抽取系统才算从“运行态原型”真正进入“可持续优化的抽取引擎阶段”。
