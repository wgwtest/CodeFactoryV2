# P2.1 应用需求建模器设计

**日期：** 2026-04-13  
**修订：** 2026-04-17

**对应节点：**
- `P2` 构建描述模型与组件资产底座
- `P2.1` 定义构建描述模型最小闭环

## 1. 设计目标

在 `P1` 已发布知识仓的基础上，提供一个面向非技术行业专家/需求分析人员的交互式建模器，让用户用纯业务语言逐步回答“这个应用想解决什么问题、谁来用、由哪些场景/模块构成、每个模块里要做哪些动作、这些动作之间如何交接”，系统再把这些输入翻译为可持续消费的结构化需求模型。

第一版聚焦：

- 目标场景：`流程办理 / 协同审批`
- 默认交互路径：`先向导收敛 -> 再进入按场景/模块组织的选配建模`
- 建模核心单元：`动作/任务 = 参与方 + 业务对象 + 行为 + 结果/状态变化`
- 页面建议方式：在模块和动作骨架稳定后，由系统自动推导页面模板建议
- 产出形态：`结构化对象 + MD 可读投影`

## 2. 产品定位与边界

### 2.1 产品定位

产品名称暂定为：`应用需求建模器`

它不是：

- 低代码拖拽画布
- 组件装配台
- 可运行原型生成器
- 面向技术人员的专业建模工具

它是：

- 知识仓与软件设计系统之间的过渡层
- 用户意图到结构化构建描述之间的第一道翻译层
- 面向业务表达的建模入口

### 2.2 目标用户

唯一主用户画像：

- 不懂技术的行业专家
- 需求分析人员

设计原则：

- 必须使用纯业务语言
- 必须强引导
- 必须降低输入负担
- 系统负责把业务表达翻译成结构化对象
- 第一版默认不要求用户先懂流程建模或页面设计

### 2.3 第一版非目标

第一版明确不做：

- 组件命中推荐
- 组件复用判断
- 低代码拖拽画布
- 可运行原型生成
- BPMN/泳道图设计器
- 多人协同编辑
- 复杂版本对比
- 面向全行业的通用建模器
- 页面分区级别的 UI 设计

## 3. 交互方案

### 3.1 页面骨架

第一版沿用已确认的三栏结构：

- 左侧：步骤导航
- 中间：当前步骤的业务提问、模块搭建、推荐项与手工补充
- 右侧：实时预览，包括模块骨架、动作链、模块交接和页面建议

### 3.2 默认入口路径

第一版不采用“直接进入空白选配画布”的默认入口，而采用以下主路径：

`先向导收敛 -> 再进入按场景/模块组织的选配建模`

原因：

- 非技术用户在进入模块建模前，需要先通过少量问题收敛应用目标和使用对象
- 模块边界由用户自己决定，但推荐范围应先被向导阶段适度收缩
- 这样既保留用户主导的模块划分，又避免一上来面对完全空白画布

### 3.3 向导阶段

向导阶段只负责收敛，不负责替用户自动生成模块草案。

当前默认收敛内容包括：

- 业务目标
- 目标结果
- 成功标准
- 使用对象 / 参与方类型
- 应用边界与优先范围

### 3.4 选配阶段的组织轴

选配阶段按 `场景 / 模块` 组织，不按对象表或页面表直接组织。

具体规则：

- 模块由用户自己从空白创建
- 用户至少填写 `模块名 + 一句用途`
- 系统在读到模块名和用途后，立刻推荐相关动作、对象、参与方和候选交接点

### 3.5 模块内部的建模核心

模块内部默认先建 `动作/任务`，再由动作集合形成链路。

每个动作在第一版都必须绑定以下 4 类信息：

- `参与方`
- `业务对象`
- `行为`
- `结果 / 状态变化`

也就是说，动作不是“一个裸名字”，而是最小可解释业务单元。

### 3.6 链路形成方式

第一版中：

- 模块内部先形成动作集合
- 右侧实时根据当前动作集合生成链路草图
- 用户不是进入一个独立“串链步骤”后才看到流程，而是在建动作的同时看到结构在右侧持续成形

### 3.7 多模块关系

多个模块之间通过 `交接动作` 连接，而不是只保留孤立模块列表。

典型表达方式：

- 模块 A 提交协同请求
- 模块 B 接收并处理
- 模块 B 回传处理结果

这样最终得到的是应用级业务骨架，而不是彼此脱节的模块卡片。

### 3.8 页面建议的进入时机

页面/承载面不在第一轮由用户手工先建，而是在模块和动作骨架相对稳定后，由系统自动推导。

当前默认的页面建议颗粒度为 `页面模板层`，例如：

- 工作台
- 列表页
- 发起表单
- 审批页
- 详情页
- 跟踪页

这一层级先作为第一版默认假设，后续可根据实际体验再调整。

### 3.9 操作原则

- 推荐项为主，但允许手工补充
- 用户不采纳推荐项也能继续
- 每次输入都要即时反馈到右侧预览
- 第一版不要求用户先建立完整流程，再回头看结果
- 建模器只做建模，不提前混入组件资产和实现细节
- 允许当场新建临时元素，并标记为 `待入库`

## 4. 建模步骤

第一版建议按 6 个阶段推进：

### 4.1 业务目标收敛

输入：

- 业务问题
- 目标结果
- 成功标准

输出：

- `application_goal`
- `business_context`
- `success_criteria`

### 4.2 使用对象与范围收敛

输入：

- 谁会使用这个应用
- 有几类参与方
- 当前优先覆盖哪些工作范围

输出：

- `audiences`
- `roles`
- `responsibility_summary`
- `scope_constraints`

### 4.3 自建模块

输入：

- 模块名
- 模块用途 / 目标

输出：

- `modules`
- `module_intent`

要求：

- 模块不由系统预生成
- 用户新建模块后，系统再进行推荐

### 4.4 模块内动作建模

输入：

- 参与方
- 业务对象
- 行为
- 结果 / 状态变化

输出：

- `actions`
- `action_sources`
- `temporary_elements`

### 4.5 模块链路与交接动作

输入：

- 动作集合
- 模块间交接点

输出：

- `action_links`
- `module_handoffs`
- `module_graph`

特点：

- 右侧实时生成链路草图
- 不要求用户先完成全部动作后再看链路

### 4.6 自动页面建议与输出

输入：

- 模块结构
- 动作链
- 模块间交接

输出：

- `workspace_suggestions`
- `page_suggestions`
- `interaction_surface_suggestions`
- `ApplicationRequirementModel`
- `MD` 投影

## 5. 推荐体系

`P2.1` 的推荐来源分为 3 层：

### 5.1 通用应用知识

平台内置，不依赖领域知识仓，主要覆盖：

- 常见参与方类型
- 常见动作模式
- 常见页面模板
- 常见协作与权限模式

作用：

- 帮助非技术用户更容易表达需求
- 补足领域知识仓中不存在的通用构建常识

### 5.2 领域知识推荐

来自 `P1` 的已发布知识仓，主要提供：

- 已发布流程
- 已发布业务对象
- 已发布事件
- 对象与流程之间的关系线索
- 解释与证据来源

要求：

- 不能直接把“实体/事件/流程”术语硬抛给用户
- 需要翻译成业务问题、动作候选或模块候选要素

### 5.3 用户当前输入

用户已经确认的目标、参与方、模块名、模块用途、动作和交接关系会反过来收缩后续推荐。

推荐必须是动态收敛的，而不是一次性列出全部候选。

### 5.4 推荐触发规则

第一版默认支持以下触发：

- 用户写完 `模块名 + 用途` 后，推荐动作候选
- 用户新建动作后，推荐参与方、业务对象和结果状态
- 用户形成多个模块后，推荐模块间交接动作
- 模块和动作骨架稳定后，推导页面模板建议

### 5.5 来源标识

每个建模项必须具备来源标识：

- `recommended_common`
- `recommended_domain`
- `manual`
- `temporary_pending_intake`

### 5.6 推荐解释

第一版至少支持这 4 种解释：

- 因为你选择了某类业务目标，所以推荐某类通用模式
- 因为知识仓中这些对象/事件/流程经常关联出现，所以推荐某个动作或交接点
- 因为你刚创建了某个模块，所以推荐该模块的候选动作
- 因为当前模块链路已经形成，所以推导出某些页面模板建议

## 6. 权威输出模型

第一版权威输出对象名称继续采用：`ApplicationRequirementModel`

但其内部结构从“流程 + 页面建议”升级为“模块 + 动作 + 交接 + 页面建议”。

建议结构：

```yaml
model_id: arm_xxx
version: 2
status: draft
application_name: xxx
application_goal:
  problem_statement: xxx
  target_outcome: xxx
  success_criteria:
    - xxx
audiences:
  - id: audience_xxx
    name: 一线办理人员
    description: xxx
roles:
  - id: role_xxx
    name: 发起方
    audience_id: audience_xxx
    responsibility_summary: xxx
modules:
  - id: module_xxx
    name: 任务发起与协同
    purpose: 建立任务并发起协同
    source_kind: manual
    actions:
      - id: action_xxx
        name: 发起任务
        actor_refs:
          - role_xxx
        object_refs:
          - object_xxx
        verb: create_and_submit
        result_state: pending_collaboration
        source_kind: recommended_domain
business_objects:
  - id: object_xxx
    name: 任务说明
    description: xxx
module_handoffs:
  - id: handoff_xxx
    from_module_id: module_xxx
    to_module_id: module_yyy
    action_ref: action_xxx
    handoff_type: submit_for_review
page_suggestions:
  - id: page_xxx
    page_type: task_form
    name: 任务发起表单
    based_on_modules:
      - module_xxx
    based_on_actions:
      - action_xxx
knowledge_references:
  - source_type: domain
    source_id: item_xxx
    source_name: xxx流程
temporary_elements:
  - id: temp_xxx
    name: 临时协调方
    element_type: role
    intake_status: pending
draft_meta:
  created_at: xxx
  updated_at: xxx
  created_by: xxx
```

设计要求：

- 结构化对象作为权威输出
- `MD` 只是可读投影
- 每个核心项必须具备稳定 `id`
- 每个推荐/手工/临时项必须可追溯来源
- `page_suggestions` 只能表达页面模板建议，不能提前混入组件信息
- 临时元素允许进入模型，但必须明确标记为 `待入库`

## 7. MD 投影

第一版自动生成的 `MD` 结构建议固定为：

- 应用名称与目标
- 受众与业务分工
- 模块清单与用途
- 每个模块的动作集合
- 模块间交接关系
- 自动推导的页面建议
- 引用了哪些领域知识
- 哪些内容由用户手工补充
- 哪些元素属于临时新增且待入库

作用：

- 便于行业专家阅读与复核
- 作为交付沟通材料
- 作为结构化对象的可读投影

## 8. 草稿机制

### 8.1 草稿状态

第一版支持：

- `draft`
- `completed`
- `exported`

### 8.2 能力范围

- 用户可随时保存草稿
- 草稿可恢复继续编辑
- 可从已完成模型复制出新草稿
- 只有达到最小完成条件时，才能标记 `completed`
- 导出后可进入 `exported`

### 8.3 最小校验

至少满足以下条件才能标记完成：

- 有业务目标
- 有至少一类使用对象
- 有至少一个模块
- 每个已保存动作都包含 `参与方 + 业务对象 + 行为 + 结果`
- 系统已成功生成至少一项结构预览，例如模块链路或页面建议

## 9. 系统边界

### 9.1 与 P1 的边界

`P2.1` 只消费 `P1` 的已发布知识结果，不允许读取：

- 候选知识
- 治理中间状态
- 审核工作数据

`P1 -> P2.1` 的输入只包括：

- 发布态流程清单
- 发布态实体/事件清单
- 单个知识项详情
- 知识项关系邻域
- 知识引用元信息

用户在 `P2.1` 中手工新增的内容不反写 `P1`。

### 9.2 与 P2.2 的边界

`P2.1` 只负责需求建模，不负责：

- 组件推荐
- 组件命中
- 组件适配
- 未命中开发清单

`P2.1 -> P2.2` 的标准输出：

- `ApplicationRequirementModel`
- `JSON/YAML` 权威对象
- `MD` 可读投影
- 草稿/完成态元信息

### 9.3 与 P3 的边界

串行关系固定为：

- `P1` 提供知识底座
- `P2.1` 形成应用需求模型
- `P2.2` 形成组件复用映射结果
- `P3` 进行软件设计说明与工具化描述生成

## 10. 模块划分

在“模块化单体优先”的约束下，`P2.1` 建议拆为 5 个模块：

- `建模器前端`
  - 左侧步骤导航、中间建模区、右侧实时预览
- `向导收敛服务`
  - 业务目标、参与方、范围收敛
- `模块建模服务`
  - 模块创建、动作建模、交接关系维护
- `推荐编排服务`
  - 融合通用知识、领域知识和用户当前输入
- `结果投影服务`
  - 结构化对象 -> 右侧预览 / MD / 页面建议

模块之间只通过标准对象交互，不允许直接读取彼此内部状态。

## 11. 第一版最小实现范围

第一版只做：

- 一个独立“应用需求建模器”页面
- 默认主路径：`向导收敛 -> 模块建模 -> 自动页面建议`
- 左中右三栏布局
- 用户自建模块
- 模块内动作卡片建模
- 右侧实时链路与模块交接预览
- 临时元素标记
- 草稿保存 / 恢复 / 完成
- 导出 `JSON/YAML + MD`

场景范围固定为：

- `流程办理 / 协同审批`

## 12. 验收口径

第一版验收只看以下 5 条是否成立：

1. 非技术行业专家能否用纯业务语言完成一次模块化建模
2. 用户能否自己创建模块，并用动作单元表达业务过程
3. 系统能否实时形成模块链路和模块间交接预览
4. 系统能否在骨架稳定后自动推导页面模板建议
5. 能否稳定导出结构化对象和 MD，并保留草稿继续编辑

第一版成功标志：

`业务人员先收敛目标 -> 自己创建模块 -> 用动作表达业务 -> 右侧实时成形应用骨架 -> 系统自动补出页面建议 -> 导出为 JSON/YAML + MD`
