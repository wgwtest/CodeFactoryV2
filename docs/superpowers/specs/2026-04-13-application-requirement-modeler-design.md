# P2.1 应用需求建模器设计

**日期：** 2026-04-13

**对应节点：**
- `P2` 构建描述模型与组件资产底座
- `P2.1` 定义构建描述模型最小闭环

## 1. 设计目标

在 `P1` 已发布知识仓的基础上，提供一个面向非技术行业专家/需求分析人员的交互式建模器，让用户用纯业务语言逐步回答“这个应用想解决什么问题、谁来用、覆盖哪些流程、处理哪些业务信息、需要哪些应用承载方式”，系统再把这些输入翻译为可持续消费的结构化需求模型。

第一版聚焦：

- 目标场景：`流程办理 / 协同审批`
- 交互形态：`左侧分步引导 + 中间业务问答/点选 + 右侧实时预览`
- 产出形态：`结构化对象 + MD 可读投影`

## 2. 产品定位与边界

### 2.1 产品定位

产品名称暂定为：`应用需求建模器`

它不是：

- 低代码拖拽画布
- 组件装配台
- 可运行原型生成器
- 面向技术人员的专业建模工具

它是：

- 知识仓与应用生成之间的过渡层
- 用户意图到结构化构建描述之间的第一道翻译层
- 面向业务表达的建模入口

### 2.2 目标用户

唯一主用户画像：

- 不懂技术的行业专家
- 需求分析人员

设计原则：

- 必须使用纯业务语言
- 必须强引导
- 必须降低输入负担
- 系统负责把业务表达翻译成结构化对象

### 2.3 第一版非目标

第一版明确不做：

- 组件命中推荐
- 组件复用判断
- 低代码拖拽画布
- 可运行原型生成
- BPMN/泳道图设计器
- 多人协同编辑
- 复杂版本对比
- 面向全行业的通用建模器

## 3. 交互方案

### 3.1 页面骨架

第一版采用已确认的 `A` 方案：

- 左侧：步骤导航
- 中间：当前步骤的业务提问、推荐项与手工补充
- 右侧：业务模型预览、应用结构建议、结构化输出预览

### 3.2 起步方式

第一屏从业务问题开始，而不是从技术结构开始。

第一步核心问题：

- 你想解决什么业务问题？
- 希望这个应用服务什么场景？
- 最希望先改善哪一部分工作？

第一版起步策略：

- 用户先选择应用目标
- 系统基于通用应用知识和领域知识给出推荐
- 用户再逐步补充、裁剪、确认

### 3.3 操作原则

- 推荐项为主，但允许手工补充
- 用户不选推荐项也能继续
- 每次选择都要即时反馈到右侧预览
- 建模器只做建模，不提前混入组件资产和实现细节

## 4. 建模步骤

第一版固定为 5 步：

### 4.1 业务目标

输入：

- 业务问题
- 目标结果
- 成功标准

输出：

- `application_goal`
- `business_context`
- `success_criteria`

### 4.2 使用对象

输入：

- 谁会使用这个应用
- 有几类使用方
- 各类使用方大致承担什么职责

输出：

- `audiences`
- `roles`
- `responsibility_summary`

界面文案不直接使用“角色”术语，可用：

- 使用方类型
- 参与方
- 业务分工

### 4.3 核心流程

输入：

- 应用要覆盖哪些流程
- 哪些流程最重要
- 哪些流程必须先做

输出：

- `business_flows`
- `flow_priority`
- `flow_scope`

### 4.4 关键信息与动作

输入：

- 需要处理哪些业务资料/业务对象
- 会发生哪些关键动作或状态变化
- 需要记录哪些信息

输出：

- `business_objects`
- `key_events`
- `data_capture_intent`

### 4.5 应用承载方式

输入：

- 需要哪些入口和页面
- 不同使用方看到的内容是否相同
- 哪些环节需要填报、审核、查询、提醒

输出：

- `workspace_suggestions`
- `page_suggestions`
- `form_intents`
- `permission_intents`

## 5. 推荐体系

`P2.1` 的推荐来源分为 3 层：

### 5.1 通用应用知识

平台内置，不依赖领域知识仓，主要覆盖：

- 常见参与方类型
- 常见流程模式
- 常见页面类型
- 常见协作与权限模式

作用：

- 帮助非技术用户更容易表达需求
- 补足领域知识仓中不存在的通用构建常识

### 5.2 领域知识推荐

来自 `P1` 的已发布知识仓，主要提供：

- 已发布流程
- 已发布业务对象
- 已发布事件
- 对象与流程之间的关系线索
- 解释与证据来源

要求：

- 不能直接把“实体/事件/流程”术语硬抛给用户
- 需要翻译成业务问题和推荐项

### 5.3 用户当前输入

用户已经确认的目标、参与方、流程、对象会反过来收缩后续推荐。

推荐必须是动态收敛的，而不是一次性列出全部候选。

### 5.4 来源标识

每个建模项必须具备来源标识：

- `recommended_common`
- `recommended_domain`
- `manual`

### 5.5 推荐解释

第一版至少支持这 3 种解释：

- 因为你选择了某类业务目标，所以推荐某类通用模式
- 因为知识仓中这些流程/对象/事件经常关联出现，所以推荐纳入
- 因为你前面已经选择了某类参与方或流程，所以推荐对应页面/处理入口

## 6. 权威输出模型

第一版权威输出对象名称建议为：`ApplicationRequirementModel`

建议结构：

```yaml
model_id: arm_xxx
version: 1
status: draft
application_name: xxx
application_goal:
  problem_statement: xxx
  target_outcome: xxx
  success_criteria:
    - xxx
audiences:
  - id: audience_xxx
    name: 一线办理人员
    description: xxx
roles:
  - id: role_xxx
    name: 发起方
    audience_id: audience_xxx
    responsibility_summary: xxx
business_flows:
  - id: flow_xxx
    name: 申请与审批
    scope: core
    priority: high
    participants:
      - role_xxx
business_objects:
  - id: object_xxx
    name: 申请单
    description: xxx
key_events:
  - id: event_xxx
    name: 提交申请
    description: xxx
application_structure:
  workspaces:
    - id: ws_xxx
      name: 办理工作台
  pages:
    - id: page_xxx
      name: 审批处理页
      page_type: task_form
  permission_intents:
    - role_id: role_xxx
      access_scope: own_and_pending
knowledge_references:
  - source_type: domain
    source_id: item_xxx
    source_name: xxx流程
manual_additions:
  - target_type: role
    name: 临时协调人
draft_meta:
  created_at: xxx
  updated_at: xxx
  created_by: xxx
```

设计要求：

- 结构化对象作为权威输出
- `MD` 只是可读投影
- 每个核心项必须具备稳定 `id`
- 每个推荐/手工项必须可追溯来源
- `application_structure` 只能表达“建议”，不能提前混入组件信息

## 7. MD 投影

第一版自动生成的 `MD` 结构建议固定为：

- 应用名称与目标
- 受众与业务分工
- 核心流程范围
- 关键业务对象与动作
- 建议的应用结构
- 引用了哪些领域知识
- 哪些内容由用户手工补充

作用：

- 便于行业专家阅读与复核
- 作为交付沟通材料
- 作为结构化对象的可读投影

## 8. 草稿机制

### 8.1 草稿状态

第一版支持：

- `draft`
- `completed`
- `exported`

### 8.2 能力范围

- 用户可随时保存草稿
- 草稿可恢复继续编辑
- 可从已完成模型复制出新草稿
- 只有达到最小完成条件时，才能标记 `completed`
- 导出后可进入 `exported`

### 8.3 最小校验

至少满足以下条件才能标记完成：

- 有业务目标
- 有至少一类使用对象
- 有至少一条核心流程
- 有至少一种应用承载建议

## 9. 系统边界

### 9.1 与 P1 的边界

`P2.1` 只消费 `P1` 的已发布知识结果，不允许读取：

- 候选知识
- 治理中间状态
- 审核工作数据

`P1 -> P2.1` 的输入只包括：

- 发布态流程清单
- 发布态实体/事件清单
- 单个知识项详情
- 知识项关系邻域
- 知识引用元信息

用户在 `P2.1` 中手工新增的内容不反写 `P1`。

### 9.2 与 P2.2 的边界

`P2.1` 只负责需求建模，不负责：

- 组件推荐
- 组件命中
- 组件适配
- 未命中开发清单

`P2.1 -> P2.2` 的标准输出：

- `ApplicationRequirementModel`
- `JSON/YAML` 权威对象
- `MD` 可读投影
- 草稿/完成态元信息

### 9.3 与 P3 的边界

串行关系固定为：

- `P1` 提供知识底座
- `P2.1` 形成应用需求模型
- `P2.2` 形成组件复用映射结果
- `P3` 进行正式应用装配与生成

## 10. 模块划分

在“模块化单体优先”的约束下，`P2.1` 建议拆为 4 个模块：

- `建模器前端`
  - 步骤导航、业务提问、实时预览
- `建模草稿服务`
  - 草稿保存、恢复、完成态校验、导出
- `推荐编排服务`
  - 融合通用知识、领域知识和用户当前输入
- `结果投影服务`
  - 结构化对象 -> 右侧预览 / MD

模块之间只通过标准对象交互，不允许直接读取彼此内部状态。

## 11. 第一版最小实现范围

第一版只做：

- 一个独立“应用需求建模器”页面
- 固定 5 步向导
- 左中右三栏布局
- 推荐项选择 + 手工补充
- 草稿保存 / 恢复 / 完成
- 导出 `JSON/YAML + MD`

场景范围固定为：

- `流程办理 / 协同审批`

## 12. 验收口径

第一版验收只看以下 5 条是否成立：

1. 非技术行业专家能否用纯业务语言完成一次建模
2. 建模过程中能否同时使用推荐项和手工补充
3. 系统能否实时形成业务模型和应用结构建议
4. 能否稳定导出结构化对象和 MD
5. 草稿能否保存并继续编辑

第一版成功标志：

`业务人员描述目标 -> 逐步点选/补充 -> 系统实时翻译 -> 得到结构化应用需求模型 -> 导出为 JSON/YAML + MD`
