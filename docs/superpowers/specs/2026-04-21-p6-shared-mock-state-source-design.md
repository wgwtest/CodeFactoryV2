# P6 公共模拟状态源与门户读侧切换设计

## 1. 设计目标

当前 `P6` 已有 `/portal` 页面、蓝图画布组件和基础交互，但页面数据仍然来自前端静态常量，尚未形成可复用的公共读侧来源。

现阶段不适合直接接入 `P1 ~ P5` 真实数据端口，原因如下：

- `P1 ~ P5` 仍有大量功能未完成
- 对应状态输出接口尚未全部绑定并锁死
- 若 `P6` 过早依赖真实源，会把门户实现和上游未稳定接口耦合在一起

因此，本设计固定采用以下策略：

- 在 `P6.2` 下新增独立叶子节点 `P6.2.5 模拟状态源`
- 首版由 `P6` 自己提供公共模拟读源
- 公共模拟读源统一产出 `StageSnapshot / StageNodeStatusPayload / PortalProjection / ObservationProjection`
- `/portal` 只负责消费读侧投影，不再直接持有业务假数据
- 首版通过一个很小的按钮在门户页内切换模拟场景，不新增单独页面

## 2. 设计结论

本轮不采用“前端本地静态 mock 继续扩写”的做法，也不采用“前后端各维护一份 mock”的做法。

最终结论如下：

- 采用 `P6` 公共模拟读源方案
- 模拟读源由后端统一提供
- 前端 `/portal` 通过 API 请求公共投影对象
- 数据源模式统一预留 `mock | live`
- 首版仅实现 `mock`
- 首版提供 3 套预置场景模板，而不是只做单一静态演示状态

该方案的核心价值是：

- `P6.1`、未来串行观察页、`P6.4` 可复用同一套读源
- `P6` 可以先完成页面闭环，不被 `P1 ~ P5` 的真实接口进度阻塞
- 后续真实源接入时，只替换 `P6.2` 读源实现，不推翻门户页结构

## 3. WBS 落点

`P6` 当前实现推进应在既有树下继续细化，不另起平行树。

建议在 `P6.2` 下新增叶子节点：

- `P6.2.5 模拟状态源`

新增后 `P6.2` 的叶子结构为：

- `P6.2.1 阶段查询接口`
- `P6.2.2 状态快照模型`
- `P6.2.3 缓存与降级`
- `P6.2.4 页面接口`
- `P6.2.5 模拟状态源`

职责边界固定如下：

- `P6.2.5` 负责模拟场景模板、快照生成、投影输出
- `P6.1` 负责门户渲染、交互、布局和跳转
- 未来串行观察页和 `P6.4` 必须复用 `P6.2.5` 的公共读源，而不是再各自生成 mock

## 4. 作用域与非作用域

### 4.1 当前负责

- 新建 `P6` 专用读侧 API
- 新建公共模拟场景模板
- 基于正式对象骨架生成 5 阶段统一快照
- 为 `/portal` 提供门户投影
- 为未来串行观察页预留观察投影
- 在 `/portal` 页面提供极小的场景切换控件

### 4.2 当前不负责

- 接入 `P1 ~ P5` 真实数据端口
- 新增独立模拟源页面
- 自动推进的动态时间模拟
- 多人协同切换场景
- 在门户页内直接编辑业务事实

## 5. 后端设计

### 5.1 模块边界

首版新增独立 `p6` 模块，不把逻辑塞进任一现有 `P1 ~ P5` 服务。

建议文件边界如下：

- `apps/api/app/p6/models.py`
  - 定义 `MockScenarioSummary`
  - 定义 `StageSnapshot`
  - 定义 `StageNodeStatusPayload`
  - 定义 `PortalProjection`
  - 定义 `ObservationProjection`
- `apps/api/app/p6/mock_scenarios.py`
  - 定义 3 套预置场景模板
- `apps/api/app/p6/service.py`
  - 负责 `source=mock|live` 分发
  - 负责场景装载
  - 负责快照归一化
  - 负责门户投影和观察投影生成
- `apps/api/app/api/routes/p6.py`
  - 对外暴露 `P6` 专用读侧路由
- `apps/api/app/main.py`
  - 挂载 `p6` router

### 5.2 路由设计

首版固定新增以下 API：

- `GET /api/p6/mock-scenarios`
- `GET /api/p6/stage-snapshots?source=mock&scenario=<id>`
- `GET /api/p6/portal-projection?source=mock&scenario=<id>`
- `GET /api/p6/observation-projection?source=mock&scenario=<id>`

其中：

- `source` 统一预留为 `mock | live`
- 首版只实现 `mock`
- 若调用 `source=live`，后端必须明确返回 `501 not implemented`

### 5.3 场景模板

首版提供以下 3 套固定场景：

- `baseline`
  - 主链通畅
  - 5 阶段入口可用
  - 适合演示基础蓝图结构
- `review-pressure`
  - `P3` 评审积压
  - `P4` 供给跟进中
  - 适合演示中游压力传导
- `delivery-gap`
  - `P5` 存在交付缺口
  - `P4 / P5` 状态更重
  - 适合演示告警和降级表达

场景模板只允许变更字段值，不允许破坏统一对象骨架。

### 5.4 对象模型要求

3 套场景必须共用以下对象链：

- `StageSnapshot`
- `StageNodeStatusPayload`
- `PortalProjection`
- `ObservationProjection`

禁止为某个场景单独发明页面私有字段。

门户页最关心的对象要求如下：

- `StageSnapshot`
  - 表达阶段原始统一快照
- `StageNodeStatusPayload`
  - 表达门户系统状态卡节点显示负载
- `PortalProjection`
  - 直接供 `/portal` 消费
- `ObservationProjection`
  - 首版先定义并可返回，为未来观察页复用留接口位

### 5.5 推荐布局责任

推荐布局属于平台投影的一部分，不属于页面私有常量。

因此首版约束如下：

- 推荐布局坐标进入 `PortalProjection`
- 门户摘要、新鲜度、降级原因也进入 `PortalProjection`
- 前端只保留个人布局覆盖和视口状态
- 前端不再保存业务节点和业务文案常量

## 6. 前端设计

### 6.1 页面职责

`/portal` 继续保持独立路由，不进入 `MainShell`。

首版前端职责边界如下：

- `P6PortalPage`
  - 负责加载场景列表
  - 负责加载门户投影
  - 负责维护 `source / scenario / loading / error`
  - 负责展示小型切换控件
- `P6BlueprintCanvas`
  - 收敛为纯渲染与交互组件
  - 消费 API 投影数据
  - 不再直接依赖前端业务 mock 常量
- `p6PortalData`
  - 只保留世界尺寸、默认布局、`localStorage key` 等 UI 常量
  - 不再保存业务节点、业务流和产物假数据

### 6.2 控件设计

首版不新增独立页面，只在门户主画布上提供一个很小的控制区。

控件位置建议固定在右上角工具带，视觉权重必须弱于蓝图主体。

控件内容固定如下：

- 一个极小的源标记：`模拟源`
- 一个场景切换下拉：
  - `基线`
  - `评审压力`
  - `交付缺口`

切换行为固定如下：

- 切换场景后重新请求 `P6` 读侧接口
- 当前场景名、新鲜度、降级原因仍在门户摘要区展示
- 控件区不堆叠大段解释文案

### 6.3 布局记忆边界

个人布局继续按 `node_id` 保存。

因此首版显式允许：

- 用户先拖动节点形成个人布局
- 再切换场景
- 同一 `node_id` 的位置覆盖继续生效

这属于预期行为，而不是串数据。

## 7. 错误与降级边界

首版禁止在读取失败时静默回退到旧的前端静态常量。

错误与降级规则固定如下：

- `scenario` 不存在
  - 后端返回 `404`
- `source=live`
  - 后端返回 `501`
- 首次加载失败
  - 页面显示错误提示
  - 不伪造成功数据
- 已成功加载后再切场景失败
  - 保留上一份成功投影
  - 显示错误提示
- 场景内存在降级状态
  - 通过 `PortalProjection` 的新鲜度和降级原因表达
  - 不隐藏节点

## 8. 测试设计

### 8.1 后端测试

新增：

- `apps/api/tests/test_p6_api.py`

至少覆盖以下行为：

- 场景列表可读
- `baseline` 能返回 5 阶段 `StageSnapshot`
- `portal-projection` 返回正确场景和摘要
- `observation-projection` 可返回同构读模型
- `source=live` 明确返回未实现错误
- 未知 `scenario` 明确返回错误

### 8.2 前端测试

继续复用并扩展：

- `apps/web/src/test/P6PortalPage.test.tsx`

至少覆盖以下行为：

- `/portal` 仍然独立于 `MainShell`
- 页面通过 `P6` 读侧接口加载数据
- 页面可以切换 3 套场景
- 切换后节点文案或门户摘要发生变化
- 加载失败时显示错误，不展示伪数据
- 个人布局在场景切换后仍保留

## 9. 未来真实源接入策略

本设计不是为了永久停留在 mock，而是为了把真实源接入位置提前固定。

后续当 `P1 ~ P5` 状态输出接口完成锁定后，接入策略固定如下：

- 保持 `/api/p6/*` 路由不变
- 保持前端对象结构不变
- 在 `P6` 服务层新增 `live` 源实现
- 用 `live` 源替换当前 `mock` 源
- 不反向让 `/portal` 直接连接各阶段私有接口

## 10. 实施建议

本设计的首个可交付目标不是“真实跨阶段联通”，而是：

- 让 `P6` 先拥有一套正式、统一、可复用、可切换场景的公共读源
- 让 `/portal` 从静态常量升级为真实消费平台读侧投影的页面

完成这一目标后，再继续推进：

- `P6.1` 门户渲染增强
- 串行观察页
- `P6.4` 展示实验复用
- `P1 ~ P5` 真实源逐步替换
