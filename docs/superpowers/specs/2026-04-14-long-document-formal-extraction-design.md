# 长文档正式抽取升级设计

## 背景

当前正式知识库抽取链路已经满足两项硬门槛：

- 解析必须使用 `Docling`
- 抽取必须使用结构化大模型

但长文档场景仍存在明显不足：

1. 当前大模型增强仍采用“少量分段采样 + 单次抽取”的方式。
2. 当前规则抽取存在大量前部窗口限制，例如只扫描前若干百行。
3. 对于手册、条例、作战条令、架构总册等长文档，后半部分知识覆盖率不足。
4. 页面展示又默认读取治理/发布可见态，容易让用户误以为“可见数量 = 原始抽取数量”。

以 `FM_6-02_Signal_Support_to_Operations_CitizenMilitem.pdf` 为例：

- `Docling` 解析成功
- 文本量约 `190,994` 字符
- 分段量约 `385`
- 当前原始候选约 `69`

这说明问题不在解析失败，而在长文档抽取策略偏保守。

## 目标

本轮升级只解决“正式知识库抽取/重建”阶段的长文档覆盖率与来源可追溯问题。

目标如下：

1. 正式抽取不再用“少量采样片段”代表整篇长文档。
2. 长文档必须采用“结构化分块 -> 分块抽取 -> 全局归并”策略。
3. 抽取结果必须保留块级来源信息，为后续治理与解释提供依据。
4. 现有知识构建、治理、发布与前端消费接口尽量保持兼容。

## 非目标

本轮不做以下工作：

1. 不引入 `GraphRAG`、社区发现、图索引重建等重型能力。
2. 不改造前端图谱页的数据协议。
3. 不重写治理工作台逻辑。
4. 不在本轮自动补全跨块隐式关系，只做显式证据可支持的关系抽取。

## 方案比较

### 方案 A：扩大当前采样窗口

做法：

- 提高 `segment_limit`
- 提高 `char_limit`
- 继续做单次抽取

优点：

- 改动最小

缺点：

- 本质仍是采样
- 长文档覆盖率不稳定
- 不能作为正式长期方案

### 方案 B：结构化分块 -> 分块抽取 -> 全局归并

做法：

- 基于 `Docling` 分段构建语义块
- 每个块单独执行规则抽取与结构化大模型抽取
- 文档级汇总所有块的候选与关系，再做统一归并

优点：

- 接近当前主流长文档抽取工程实践
- 能显著提升覆盖率
- 可保留块级来源
- 与现有代码兼容度较高

缺点：

- 实现量高于方案 A
- 调用次数增加，成本上升

### 方案 C：GraphRAG / 图索引式多轮抽取

优点：

- 能力上限更高

缺点：

- 超出当前阶段范围
- 引入复杂度与新依赖过高

## 决策

采用方案 B。

原因：

1. 它满足“正式方案至少不低于主流”的目标。
2. 它不要求推翻现有 `Docling + schema 约束 + 结构化大模型` 链路。
3. 它能在当前工程内渐进落地，并保留后续升级到更重图抽取架构的空间。

## 架构设计

### 1. 长文档判定

仅在“正式知识库抽取/重建”路径中启用长文档增强模式。

建议触发条件：

- `segment_count` 超过阈值，或
- 文本字符数超过阈值

触发后切换到 `chunked_formal_extraction` 模式；未触发则保留现有标准抽取模式。

### 2. 语义块构建器

新增独立的长文档块化组件，输入为 `ParsedSegment[]`，输出为 `DocumentChunk[]`。

每个 `DocumentChunk` 至少包含：

- `chunk_id`
- `heading`
- `segments`
- `segment_ids`
- `char_count`
- `block_types`
- `anchors`

分块规则：

1. 按 `heading` 聚合同一语义区域内的相邻段落。
2. 表格类分段优先单独成块，避免被普通段落稀释。
3. 超长块按字符或 token 上限继续切分。
4. 块必须保持顺序稳定，便于后续解释和排障。
5. 对 `Docling PDF` 场景，需要先识别“语义标题”与“正文首句标题”，避免把正文首句误当成独立标题导致“一段一块”。
6. 分块边界采用“软边界”策略：遇到新的小标题时，如果当前块仍过短，则允许继续合并，优先形成更完整的语义块。

当前工程默认参数：

- `formal_chunk_char_limit = 32000`
- `formal_chunk_segment_threshold = 120`
- `formal_chunk_char_threshold = 50000`

在 `FM_6-02_Signal_Support_to_Operations_CitizenMilitem.pdf` 上，当前默认规则已从 `385` 个段落收敛到约 `16` 个正式抽取块。

### 3. 块级抽取编排器

新增块级编排器，负责对每个块执行抽取。

每个块按如下顺序处理：

1. 块级规则抽取
2. 块级结构化大模型抽取
3. 块内结果归并

块级抽取仍复用现有 `ExtractionBatch` 抽象，但 `metadata` 需要额外记录：

- `chunk_id`
- `chunk_heading`
- `chunk_index`
- `chunk_char_count`
- `chunk_segment_count`

### 4. 文档级全局归并

所有块级结果在文档级做统一归并，输出一个最终 `ExtractionBatch` 给现有知识构建链路。

归并规则：

1. 候选按 `(item_type, canonical_name)` 归并。
2. 关系按 `(relation_type, source_name, target_name)` 归并。
3. `aliases` 去重合并。
4. `evidence` 保留多条，不再只保留单条。
5. 新增 `source_refs`，保存候选或关系来自哪些块。

### 5. 来源信息

候选与关系的 `payload` 需要新增来源信息：

- `source_refs`
  - `chunk_id`
  - `chunk_heading`
  - `segment_ids`
  - `anchors`

这样后续治理和解释时，至少能回答：

- 它来自哪一章
- 它来自哪几个块
- 证据落在文档哪个范围

### 6. 抽取报告扩展

正式抽取报告需新增长文档统计：

- `chunking_used`
- `chunk_count`
- `chunk_char_limit`
- `chunk_candidate_count_total`
- `chunk_relation_count_total`
- `merged_candidate_count`
- `merged_relation_count`

对长文档，最终报告必须能区分：

- 块级候选总量
- 文档级归并后候选量
- 最终进入知识仓的结果量

## 与现有代码的兼容策略

本轮尽量保持以下兼容：

1. `build_archive_knowledge()` 不改调用入口。
2. `build_knowledge_index()` 继续消费单个文档级 `ExtractionBatch`。
3. 前端文档页、治理页、图谱页接口保持现状。

允许变更的范围：

1. `ExtractionService`
2. `ExtractionBatch.metadata`
3. `candidate.payload`
4. `relation.payload`
5. 正式抽取报告结构

## 错误处理

正式抽取模式下：

1. 任一块级结构化抽取失败，需要按统一策略处理。
2. 推荐默认策略是“整篇文档失败”，而不是静默跳过失败块。

原因：

- 正式知识库抽取不能把残缺结果冒充完整结果。

调试/预览模式下可允许更宽松策略，但不属于本轮范围。

## 测试策略

### 单元测试

新增测试覆盖：

1. 长文档会进入分块模式
2. 块构建规则正确保留表格块与标题块
3. 多块结果能正确归并
4. `source_refs` 能写入候选与关系
5. 短文档仍走旧路径

### 集成测试

增加正式抽取链路测试：

1. 验证执行报告包含 `chunk_count` 等新字段
2. 验证 `FM_6-02...pdf` 这类长文档候选数相较旧策略提升
3. 验证结果中存在块级来源信息

## 风险与控制

### 1. 成本上升

分块抽取会增加大模型调用次数。

控制方式：

- 仅在正式抽取与长文档场景启用
- 对块大小做合理上限控制

### 2. 归并过度或不足

块级抽取后，同义项和变体会增加。

控制方式：

- 第一轮仍采用保守归并
- 让治理工作台继续承担最终人工校正

### 3. 结果解释复杂化

多块来源会让数据结构变复杂。

控制方式：

- 先把来源信息存入 `payload.source_refs`
- 页面展示放到下一轮做，不阻塞引擎升级

## 验收标准

满足以下条件，视为本轮设计落地：

1. 正式长文档抽取不再使用单次采样式全文抽取。
2. 正式长文档抽取能按结构分块执行多次结构化抽取。
3. 文档级结果能对块级结果做统一归并。
4. 候选与关系结果保留块级来源信息。
5. 执行报告能解释分块模式是否生效，以及块级/归并后统计。
