# 软件工厂平台总蓝图设计

**日期：** 2026-04-11

**设计目标：** 构建一个私有化部署的软件工厂平台，以领域知识为起点，逐步形成业务知识库、需求分析系统、软件设计系统、工具仓库/中台与软件构建系统的完整闭环。

## 1. 平台定位

该项目不定义为单纯的知识库平台，也不定义为传统低代码平台，而定义为一个**知识驱动的软件工厂**。

平台长期闭环如下：

`领域资料 -> 业务知识库 -> 需求分析系统 -> 软件设计系统 -> 工具仓库/中台 -> 软件构建系统 -> 新知识/新工具沉淀 -> 反哺后续构建`

本轮设计已确认的边界如下：

- 产品形态：通用底座 + 行业扩展包
- 首期聚焦：流程/事件驱动系统 + 数据分析类应用
- 主要驱动人群：业务专家主导需求建模，技术专家主导设计转译与工具化
- 部署方式：企业私有化 / 本地化部署
- 第一阶段主验收物：高质量知识仓
- 第一阶段知识主模型：实体/事件图谱 + 流程链路双核心
- 第一阶段不绑定具体行业，先做行业无关底座
- 后续应用生成目标：以平台内可运行的元数据应用为主

## 2. 分阶段目标

### 阶段一：知识仓底座

目标是把 PDF/DOC/DOCX 等领域资料转化为高质量、可治理、可发布、可展示的知识资产。

这一阶段不以完整应用生成为主交付，而以如下能力为验收核心：

- 资料接入与版本管理
- 文档结构化解析
- 候选知识抽取
- 知识治理与发布
- 双核心知识展示
- 面向后续需求分析系统的正式知识元素出口

当前验证基线（2026-04-12）：

- 已完成前后端功能验证平台，当前可直接验证 `文档接入/解析`、`知识治理/发布`、`知识图谱/流程链路视图`
- 已完成对 `20161116体系结构文献翻译汇总` 资料的全量重建，当前基线为 `75` 份文档、`1305` 个实体、`24` 个事件、`143` 条流程、`3180` 条关系
- 已完成“文档详情 -> 关联知识 -> 实体详情 -> 关系邻域/全局图谱”的前端可视化联通
- 已完成“候选知识审核 -> 批量通过/全部通过 -> 发布版本 -> 发布态查询”的主链路闭环

为避免出现“每个节点都要求前端验证，但验证平台何时建设、如何承载验证却未定义”的执行断点，阶段一内部执行顺序明确拆为 `P1.1` 到 `P1.5` 五个二级节点，并要求每个节点都具备对应的验证投影。

#### P1.1 功能验证平台底座

这是阶段一的前置使能层，不替代业务子系统本身，而是为后续各节点提供统一的可见、可测、可解释承载面。

- `P1.1.1` 前后端工程壳与运行环境
- `P1.1.2` 路由、导航与页面骨架
- `P1.1.3` 通用 API 契约、状态回显与任务日志
- `P1.1.4` 通用验证组件、证据查看与错误透传

建议技术选型：

- 前端壳：`React + Vite + TypeScript`
- UI 与验证工作台：`Ant Design`
- 页面路由：`React Router`
- 服务数据访问：`TanStack Query + Axios`
- 基础验证图形能力预留：`Cytoscape.js`、`React Flow`
- 端到端冒烟验证：`Playwright`

节点成果物：

- 可运行的前后端验证平台骨架
- 统一导航、通用详情抽屉、状态提示和错误透传机制
- 统一 API 客户端、环境配置和调试入口
- 支撑后续 `P1.2` 到 `P1.5` 的页面承载框架与验证基座

当前实现回写（2026-04-13）：

- 已落地 `FastAPI + React + Vite + TypeScript` 的单仓前后端工程壳
- 前端已提供 `上传源文档`、`知识治理`、`知识图谱`、`流程链路` 四个验证入口
- 已形成可复用的 `ValidationWorkspace`、`ValidationDrawer`、`EvidenceList` 等验证组件
- 当前 API 统一挂载在 `/api` 前缀下，前后端本地联调链路已稳定

#### P1.2 文档接入与结构化解析

- `P1.2.1` 资料导入、归档与版本管理
- `P1.2.2` 解析任务调度与执行跟踪
- `P1.2.3` 结构化解析管线
- `P1.2.4` 文档接入/解析验证页细化

建议技术选型：

- 文档主解析器：`Docling`（当前主用于 `DOCX`）
- 复杂版面与元素切分增强：`Unstructured`
- `DOC` 转 `DOCX`：`LibreOffice Headless`
- `DOCX` 轻量回退：`python-docx`
- `PDF` 轻量回退：`PyMuPDF`
- 表格类资料解析：`openpyxl`
- 解析任务编排：优先沿用现有 `Python API + Job Runner` 结构，不单独引入重型调度平台

节点成果物：

- 文档上传、归档、版本管理与解析任务流转
- 保留章节、表格、页码、锚点、块边界的结构化文档结果
- 可回溯的解析批次记录、错误记录与解析状态
- 文档解析验证页，可直接查看原文、结构化片段和解析质量

当前实现回写（2026-04-13）：

- 接入端已支持 `pdf / docx / doc / xlsx / xls`
- `DOCX` 当前解析链路为 `Docling -> Unstructured -> python-docx`
- `PDF` 当前默认解析链路为 `Unstructured -> PyMuPDF`，`Docling PDF` 已预埋但默认关闭，避免首次部署拉取重依赖影响稳定性
- `DOC` 当前通过 `LibreOffice Headless` 先转 `DOCX` 再进入统一解析链路
- 已持久化 `文档版本`、`解析批次`、`结构化片段`、`锚点`、`解析器名称/版本`
- 文档页已支持“已接入文档检索 + 解析详情抽屉 + 已建库文档检索 + 文档关联知识抽屉”

#### P1.3 候选知识抽取

- `P1.3.1` 领域 schema 与抽取对象定义
- `P1.3.2` 实体、关系、流程、规则、指标抽取
- `P1.3.3` 证据锚点、置信度与抽取批次记录
- `P1.3.4` 抽取结果验证页细化

建议技术选型：

- 抽取策略：`领域 schema 约束 + 规则抽取 + LLM 结构化抽取` 的混合方案
- 结构化输出格式：以统一 `JSON Schema / Pydantic Model` 约束实体、关系、流程、规则、指标
- LLM 编排增强：当前使用 `LlamaIndex Structured LLM + Pydantic Schema`，通过 `OpenAI-compatible` 适配层接入不同模型提供方
- 实体消歧与别名归一：先用规则与词典归并，后续再引入向量或 embedding 辅助
- 抽取质量管理：必须保留 `sourceRefs`、`confidence`、`extraction_run_id`

节点成果物：

- 面向 NAS 领域的抽取 schema 与对象字典
- 候选实体、关系、流程、规则、指标抽取管线
- 可追溯到文档片段的证据锚点和置信度记录
- 抽取结果验证页，可直接审查候选对象、证据和关系邻域

当前实现回写（2026-04-12）：

- 已形成 `规则抽取 + LLM 结构化增强` 的双通路抽取服务，最终在批次层合并去重
- 已定义 `StructuredExtractionResponse`、`ExtractedCandidate`、`ExtractedRelation` 等强约束 schema
- 已完成 `OpenAI-compatible` 适配模块，支持 `OpenAI / DeepSeek / 兼容 OpenAI 协议的模型服务`
- 当前为保证真实文档抽取完整度，兼容模型走 `PydanticProgramMode.LLM`，避免函数调用模式导致的结构化字段缺失
- 全量资料重建已验证可生成实体、事件、流程与关系，并输出到 `.data/knowledge_output`

#### P1.4 知识治理与发布

- `P1.4.1` 术语统一与别名归并

- `P1.4.3` 审核、驳回、发布与版本管理

- 关系修正方式：人工治理为主，保留规则辅助与后续模型辅助入口

节点成果物：

- 候选知识治理工作台
- 术语归并、关系修正、流程补链、冲突处理能力
- 审核、驳回、发布、版本追踪与审计记录
- 治理验证页，可解释每次修订、发布与状态变化来源

当前实现回写（2026-04-12）：

#### P1.5 已发布知识仓、查询与图谱展示

- `P1.5.2` 检索、关系查询、流程追踪与版本对比

阶段一执行原则补充如下：

- `P1.1` 必须先落地，然后才能进入 `P1.2` 到 `P1.5`
- `P1.1` 到 `P1.5` 的执行顺序是串行的，每个节点只以前一节点的标准成果物作为输入，不依赖其内部实现方式
- `P1.2` 到 `P1.5` 每个节点都必须同时交付业务能力与验证投影
- 下游节点只能依赖上游节点对外发布的接口、数据契约、版本化产物和验证页面，不允许直接依赖上游节点的内部表结构、脚本细节、文件组织或具体技术选型
- 上游节点若发生技术替换，只要其对外契约与版本化成果物保持兼容，下游节点不得因此被迫重做
- 若上游节点必须调整契约，则必须通过显式版本升级、兼容期和回归验证来控制影响，禁止隐式传导到后续节点
- 验证平台不是一次性搭完后静止不动，而是随各节点推进逐步细化
- 任何节点若无法在验证平台中被直观看到、解释和回溯，就不能视为达到阶段验收标准

### 阶段二：需求分析系统

目标是让行业专家基于 `P1` 已发布知识与通用应用常识，构建一份面向单个应用的结构化 `需求规格说明`。

这一阶段的核心原则如下：

- 一份应用对应一份需求规格模型
- 主合同是结构化表达，说明书只是派生产物
- 默认从“核心业务对象”开始建模，而不是从既有流程开始
- 主编辑方式是“选配式建模器”，同时保留“表单式建模器 + 智能推荐”
- 允许现场创建临时元素，并标记为“待入库”
- 临时元素可继续进入后续设计与构建主链，不以是否已入知识库作为阻塞条件

建议阶段拆分如下：

- `P2.1` 需求规格结构化模型
- `P2.2` 选配式建模器
- `P2.3` 表单式建模器与智能推荐
- `P2.4` 需求说明书投影与导出
- `P2.5` 临时元素回流与待入库治理接口

`P2` 的标准输出应至少包含：

- 应用基本信息
- 业务对象
- 支撑对象
- 对象参与关系
- 角色汇总
- 对象生命周期
- 流程
- 规则
- 指标
- 非功能约束
- 元素来源状态

其中需特别明确：

- 角色优先从对象参与关系中汇总，不先做全局角色表
- 流程同时支持“对象生命周期流”和“跨对象协同流”
- 表单/台账是对象与流程模型的派生视图，而不是主建模对象

当前实现回写（2026-04-13）：

- 后端已新增独立 `application_modeling` 模块，负责草稿创建、保存、完成、导出
- 草稿当前落盘在 `.data/application_modeling`
- 已提供 `/api/modeling/requirement-drafts`、`/complete`、`/export` 等接口
- 前端已新增 `/modeling` 页面，提供三栏式“应用需求建模器”
- 当前已支持保存草稿、完成建模、导出 `JSON / YAML / Markdown`
- 当前实现可视为 `P2.1` 的起步版本，后续需按“对象优先、双编辑视图、临时元素回流”的新合同继续收敛

### 阶段三：软件设计系统

目标是把 `P2` 的业务语义模型转化为软件功能结构模型，先形成 `软件设计说明`，再转化为 `工具化描述`。

这一阶段的关键原则如下：

- `P2` 以对象为主轴，`P3` 以用户工作场景为主轴
- 软件设计说明应按功能模块展开，而不是直接按对象或流程平铺
- 功能模块主要由用户工作场景聚合形成
- `工具化描述` 不是与设计说明并列的独立起点，而是设计说明经人工判断、评估和校正后的执行化表达
- 允许在部分简单场景中直接从需求规格说明进入工具化描述，但这不是默认主路径

建议阶段拆分如下：

- `P3.1` 场景驱动的功能模块划分
- `P3.2` 软件设计说明生成与人工校核
- `P3.3` 模块级工具化描述生成
- `P3.4` 子模块级工具化描述下钻与拆分

### 阶段四：工具仓库 / 工具中台

目标是建立可匹配、可管理、可组合、可持续沉淀的工具资产体系。

这一阶段不再讨论“是否需要工具资产”，而是明确工具仓库实际承担中台职责：

- 工具资产登记与分类
- 工具匹配分析
- 工具组合规则管理
- 工具创建、优化与退役管理
- 复用度量与适用场景管理

建议阶段拆分如下：

- `P4.1` 工具目录与能力分类
- `P4.2` 工具匹配分析与命中规则
- `P4.3` 工具组合规则与装配约束
- `P4.4` 工具管理、优化与复用度量

### 阶段五：软件构建系统

目标是基于 `工具化描述` 和 `工具匹配结果` 完成工具结合、组装集成和应用产出。

这一阶段的主链定义为：

`需求分析 -> 软件设计说明 -> 工具化描述 -> 工具匹配 -> 命中复用 / 未命中补建 -> 工具结合与组装集成 -> 形成应用`

其中需要强调：

- 工具/组件闭环发生在应用生成过程中，而不是在应用完成之后
- 未命中的能力应在构建过程中形成新工具资产，并回流到 `P4`
- 需求分析、设计和构建过程中新增的领域元素，应以“待入库”方式回流到 `P1`

## 3. 总体架构

平台采用“五大业务系统 + 功能验证平台底座”的总体结构：

- **业务知识库**：负责领域资料到正式知识元素的全过程
- **需求分析系统**：负责生成结构化 `需求规格说明`
- **软件设计系统**：负责生成 `软件设计说明` 与 `工具化描述`
- **工具仓库 / 工具中台**：负责工具资产、匹配分析、组合规则与管理优化
- **软件构建系统**：负责工具结合、组装集成与应用产出
- **功能验证平台底座**：负责承载阶段性功能验证、状态观察、证据回溯与演示验收

需要强调的是，功能验证平台底座是实施与验收承载层，不替代上述五个业务系统本身。当前已落地的能力重点仍集中在 `P1 业务知识库`，`P2` 已有起步实现，`P3-P5` 仍以设计和后续实现为主。

具体实现形态上，第一阶段采用“**模块化单体优先、按微服务边界设计**”的方式推进：

- 默认实现形态优先选择标准模块化单体，而不是一开始拆成多个独立部署的分布式微服务
- 但所有业务模块必须按微服务思路划分边界，即职责单一、契约清晰、存储边界明确、内部实现可替换
- 模块之间只允许通过显式接口、消息、版本化数据契约或受控应用服务交互
- 后续若某个模块需要独立扩容、独立部署或独立技术演进，应能够在不重写上下游业务逻辑的前提下拆出为独立服务
- 任何模块若无法被单独替换、单独测试、单独演进，就说明当前边界划分失败，需要在设计阶段回收重构

### 3.1 功能验证平台底座

职责：

- 承载阶段一各节点的前端验证页面与调试入口
- 提供统一的任务状态回显、日志观察、错误透传和证据查看
- 为文档、抽取、治理、图谱等节点提供统一的演示与验收界面
- 为后续阶段保留可复用的验证型页面框架

边界：

- 它是实施与验收承载层，不直接生产领域知识
- 它不替代资料接入、解析、抽取、治理、知识仓等业务子系统

### 3.2 资料接入子系统

职责：

- 接收 PDF/DOC/DOCX 等资料
- 记录来源、归属、批次、标签与版本
- 管理导入任务状态
- 提供权限控制与审计归属

边界：

- 只解决资料可控接入和可追踪问题
- 不在本子系统内做知识抽取结论

### 3.3 文档解析子系统

职责：

- 版面解析
- 章节切分
- 页码与锚点定位
- 表格提取
- 图片/OCR 处理
- 形成标准化文档片段

边界：

- 输出的是“可计算文档”
- 不是知识发布层

### 3.4 知识抽取子系统

职责：

- 从标准化文档片段中抽取候选实体
- 抽取候选事件、流程、规则、指标及关系
- 记录来源证据、抽取方式和置信度

边界：

- 输出的是“候选知识”
- 不允许直接写入发布态知识仓

### 3.5 知识治理子系统

职责：

- 术语统一
- 别名归并
- 关系修正
- 流程补链
- 冲突裁决
- 审核发布
- 版本管理

边界：

- 第一阶段最关键的产品中枢
- 知识质量由治理流程保证，而不是由抽取模型单独保证

### 3.6 知识仓与查询子系统

职责：

- 存储已发布知识
- 提供检索、关系查询、流程追踪、版本对比
- 提供图谱视图与流程链路视图
- 向其他系统输出权威知识结果

边界：

- 只消费已发布知识
- 不直接持有未治理候选知识

### 3.7 需求分析系统初始子系统

职责：

- 消费 `P1` 已发布知识与通用应用知识
- 生成结构化 `需求规格说明`
- 提供需求说明书投影与导出
- 允许在建模现场创建临时元素并标记“待入库”

边界：

- 当前只做需求建模，不做工具匹配判断
- 当前不直接承担软件设计说明生成、工具化描述编排或软件组装集成
- 当前只通过标准化结构对象向 `P3` 输出，不直接依赖 `P4/P5` 内部状态

当前实现回写（2026-04-13）：

- 该子系统当前首先落地 `P2.1 应用需求建模器`
- 当前对外标准输出为 `ApplicationRequirementModel`
- 当前输出同时提供结构化对象与 `Markdown` 投影
- 当前推荐编排严格区分 `recommended_common / recommended_domain / manual` 三类来源，避免后续阶段边界混乱

### 3.8 当前阶段运行态存储分层

为保证当前阶段可落地、可验证、可替换，现阶段采用分层存储而不是单一技术栈一把梭：

- 文档接入与解析层：关系型模型 + 文件存储
- 候选知识治理层：`curated JSON` 作为当前主运行编辑面
- 发布态知识层：版本化 `published JSON snapshot` 作为当前权威发布源
- 需求建模层：`application modeling draft` 作为 `P2` 当前草稿存储面
- 图数据库层：仅保留 `Neo4j` 扩展位，等发布态查询、路径分析、跨版本图查询需求进一步提升后再切入

当前这样设计的原因不是回避图数据库，而是为了保证：

- `P1` 阶段先把“资料 -> 候选知识 -> 审核发布 -> 图谱验证”主链路跑通
- 当前所有页面、接口与发布机制都可以在本地稳定重建和检查
- 后续若引入 `Neo4j`，只替换发布态仓储后端，不推翻前端工作台与治理流程

## 4. 统一知识元模型

第一阶段的知识仓不能以“文档片段”作为中心，而应以可治理、可发布的知识对象为中心。

建议定义以下 8 类一等对象：

### 4.1 Entity

表示领域中的稳定对象，例如组织、角色、资源、事项、单据、设备、指标对象等。

建议核心属性：

- `id`
- `name`
- `type`
- `aliases`
- `attributes`
- `status`
- `sourceRefs`
- `version`

### 4.2 Event

表示发生的业务事件或可触发的动作，例如受理、派单、审批、归档、告警、异常上报等。

建议核心属性：

- `id`
- `name`
- `trigger`
- `actor`
- `targetEntity`
- `preconditions`
- `postconditions`
- `sourceRefs`
- `version`

### 4.3 Process

表示具有顺序、角色和状态流转的流程链路。

建议核心属性：

- `id`
- `name`
- `steps`
- `roles`
- `inputs`
- `outputs`
- `decisionPoints`
- `relatedRules`
- `relatedEvents`
- `sourceRefs`
- `version`

### 4.4 Rule

表示制度约束、判断条件、阈值规则、合规要求等。

建议核心属性：

- `id`
- `name`
- `ruleType`
- `expression`
- `scope`
- `relatedEntities`
- `relatedProcesses`
- `relatedMetrics`
- `sourceRefs`
- `version`

### 4.5 Metric

表示指标、统计口径、维度、周期、阈值和分析定义。

建议核心属性：

- `id`
- `name`
- `metricType`
- `subject`
- `formula`
- `dimensions`
- `period`
- `thresholds`
- `sourceRefs`
- `version`

### 4.6 Relation

表示对象之间的显式关系，例如：

- `entity-owns-entity`
- `event-changes-entity`
- `process-contains-step`
- `rule-constrains-process`
- `metric-measures-entity`

### 4.7 Evidence

每条知识都必须挂接证据，禁止无证据知识发布。

建议至少记录：

- 来源文档
- 页码/章节
- 原文片段
- 抽取方式
- 置信度
- 人工确认记录

### 4.8 KnowledgeVersion

知识必须支持版本化，至少有以下主状态：

- 草稿
- 待审核
- 已发布
- 已废弃

## 5. 双核心知识视图

知识仓采用两个一等核心视图：

### 5.1 实体/事件图谱视图

用于表达：

- 术语体系
- 领域对象
- 事件因果
- 职责与角色
- 对象之间的显式关系

适合支持：

- 关系追踪
- 术语治理
- 知识网络浏览
- 规则挂接

### 5.2 流程链路视图

用于表达：

- 步骤顺序
- 角色参与
- 输入输出
- 状态流转
- 决策节点
- 规则约束

适合支持：

- 流程理解
- 链路分析
- 流程补链
- 构建描述映射

当前实现边界（2026-04-13）：

- 第一版流程链路视图以“已发布流程清单 + 流程详情抽屉 + 关系邻域图”为主
- 当前已能解释“该流程是什么、由哪些文档支撑、关联哪些实体/事件/约束、处于怎样的一度关系邻域”
- 当前尚未进入步骤级 BPMN、泳道图或时序编排视图，因为发布态数据尚未形成稳定的步骤级结构化对象
- 后续若要升级为真正的步骤级流程图，必须先在抽取与发布链路中补充 `步骤 / 角色 / 输入输出 / 时序` 的结构化契约，而不是仅改前端展示

这两个视图共享同一套底层知识对象，只是观察方式不同，不能设计成两套完全割裂的数据体系。

除此之外，所有知识视图都必须能从验证平台进入，并支持至少以下验证动作：

- 查看来源文档与证据摘录
- 查看当前对象的关系邻域
- 看到当前对象处于候选态、治理态还是发布态
- 能从页面反向定位到对应的任务、版本或处理记录

## 6. 核心流程与质量闭环

平台第一阶段的端到端流程建议固定为 5 段：

### 6.1 资料入库

- 上传资料
- 记录资料元数据
- 建立版本与归属
- 创建解析任务

产物：受控资料资产

### 6.2 结构化解析

- 切分章节与段落
- 提取表格、图片与 OCR 内容
- 保留页码、章节锚点和原文定位

产物：可计算文档片段

### 6.3 候选知识抽取

- 使用规则抽取和模型抽取生成候选对象
- 标注置信度
- 挂接来源证据
- 允许冲突、重复和不完整

产物：候选知识集

### 6.4 治理与发布

- 术语归并
- 冲突处理
- 关系修正
- 流程补链
- 审核确认
- 版本发布

产物：发布态知识

### 6.5 查询与消费

- 检索发布态知识
- 图谱展示
- 流程链路展示
- 版本对比
- 向需求分析系统输出正式领域元素与查询结果

产物：权威知识出口

### 6.6 验证投影闭环

除上述 5 段业务流外，第一阶段执行过程中必须存在一条持续伴随的验证投影闭环：

- 将每个阶段节点的输入、处理中状态和输出结果投影到验证平台
- 允许从页面进入文档、证据、关系、流程、审核、发布等关键对象详情
- 允许定位失败任务、异常抽取、错误关系和缺失证据
- 使阶段验收不依赖命令行或数据库手工核查

产物：可观察、可解释、可验收的阶段实现结果

为确保第一阶段成果可用，建议设置 4 个质量门：

### 6.7 证据门

没有来源证据的知识不得发布。

### 6.8 一致性门

必须检测术语冲突、关系断裂、流程孤点、规则悬空等问题。

### 6.9 审核门

候选知识必须经过角色化审核后才能进入发布态。

### 6.10 版本门

每次发布必须可回溯到原始资料、抽取方式、审核记录与责任人。

## 7. P2-P5 关键合同与转换关系

第一阶段虽然以知识仓为主交付，但系统从一开始就必须为 `P2-P5` 预留稳定合同。

### 7.1 需求规格说明定位

`需求规格说明` 是 `P2` 的主合同，不是普通自然语言文档。

它应满足以下约束：

- 一份应用对应一份结构化需求模型
- 默认从“核心业务对象”开始建模
- 对象区分“业务对象”和“支撑对象”
- 角色由对象参与关系归并得到
- 流程同时包含“对象生命周期流”和“跨对象协同流”
- 表单/台账只是对象与流程模型的派生视图
- 需求说明书只是结构化模型的可读投影
- 临时元素允许进入模型并标记为“待入库”

### 7.2 软件设计说明定位

`软件设计说明` 是 `P3` 的主合同。

它不是把 `P2` 结构原样平移，而是要把业务语义模型重组成软件功能结构模型。其核心原则如下：

- 按用户工作场景组织功能模块
- 每个功能模块需要明确职责、涉及对象、关联流程、关键规则和交互面
- 功能模块是后续工具化描述和工具匹配的上游输入

### 7.3 工具化描述定位

`工具化描述` 是从 `软件设计说明` 进一步转译得到的执行化表达。

其关键约束如下：

- 默认经人工判断、评估、校正后生成
- 在简单场景下允许从 `需求规格说明` 直接生成，但不是默认主路径
- 同时支持“模块级”和“子模块级”两层粒度
- 默认先输出模块级，再按需要继续下钻拆分

### 7.4 工具仓库 / 工具中台定位

工具仓库不是单纯的前端组件库，也不是静态素材目录，而是承担中台职责的工具资产体系。

其关键职责如下：

- 管理工具资产与能力分类
- 承载工具匹配分析
- 维护工具组合规则
- 提供工具创建、优化、退役与复用度量能力

## 8. 软件工厂运行主链

平台的运行主链应定义为：

1. 用户进入需求分析系统
2. 从业务知识库选择正式领域元素，并允许补充临时元素
3. 生成结构化 `需求规格说明`
4. 由软件设计系统按用户工作场景形成 `软件设计说明`
5. 由技术专家评估并转译为 `工具化描述`
6. 工具仓库 / 工具中台执行工具匹配分析
7. 对命中能力直接复用，对未命中能力进入补建
8. 软件构建系统完成工具结合、组装集成和应用产出
9. 新形成的领域元素回流 `P1` 进入待治理知识闭环
10. 新形成的工具能力回流 `P4` 进入工具资产闭环

这意味着“软件工厂”的正循环应表达为：

`业务知识库供给领域元素 -> 需求分析形成结构化规格 -> 软件设计形成场景化模块 -> 工具匹配参与构建 -> 未命中能力补建并沉淀 -> 反哺下一轮分析与构建`

## 9. 角色与权限

第一阶段至少设计以下角色：

- **资料上传者**：上传与维护原始资料
- **知识治理者**：处理候选知识、做术语归并和关系修正
- **审核发布者**：审核并发布正式知识版本
- **普通查询者**：查询已发布知识
- **平台管理员**：负责模型接入、权限配置、审计与平台维护

关键要求：

- 角色职责分离
- 发布动作可审计
- 关键修改保留操作日志

## 10. 非功能要求

### 10.1 私有化可部署

- 文档、知识、索引、审计、权限应在内网闭环运行
- 模型能力需要支持本地模型或私有模型接入

### 10.2 可追溯

- 已发布知识必须回溯到原始资料、原文位置、抽取方式、审核记录与版本

### 10.3 可治理

- 系统重点不是一次抽对，而是支持持续校正与稳定发布

### 10.4 可扩展

- 支持未来增加行业扩展包、规则模板、流程模板、工具模板与词汇包

### 10.5 权限与审计

- 保留关键操作审计记录
- 支持按组织、角色、资料来源等维度控制访问范围

### 10.6 节点解耦与契约稳定性

- `P1` 到 `P5` 必须遵循“顺序推进、接口解耦”的工程约束
- 每个阶段的下游依赖对象只能是上游阶段的标准输入输出契约、版本化成果物和验证投影，不得绑定其具体实现技术
- 阶段内部实现可更换，例如解析器、抽取器、存储引擎、设计生成器、匹配引擎、装配引擎均可演进，但必须保证阶段对外契约稳定或可版本化迁移
- 禁止跨阶段直接读取上游阶段内部数据库表、临时文件、内存结构或未发布中间状态作为正式依赖
- 任一阶段发生技术替换时，默认只允许在本阶段内消化；若会影响下游，必须先升级契约版本并完成兼容验证

### 10.7 模块化与微服务式边界

- 第一阶段默认采用模块化单体实现，但模块边界必须按微服务标准设计
- 每个模块应具备单一职责、清晰接口、独立测试能力和可替换实现
- 模块之间禁止通过共享内部类、跨目录直接调用、隐式数据库耦合或私有脚本耦合来建立依赖
- 若未来需要拆为独立微服务，应以当前模块接口与契约为基础平滑迁移，而不是回头重做业务边界
- 技术选型服务于模块边界，而不是反过来让技术框架决定业务边界

## 11. 主要风险

### 11.1 知识仓退化为文档切片库

如果最终只得到全文检索和向量问答，而没有稳定的知识对象、关系和流程结构，则无法支撑后续软件生成。

### 11.2 过度依赖自动抽取

如果没有强治理流程，知识仓很快会失去可信度，后续团队不会使用其结果。

### 11.3 元模型抽象过重

如果第一阶段过度引入复杂的软件建模抽象，会拖慢知识仓底座建设，应坚持第一阶段以知识质量为中心。

### 11.4 行业无关底座过空

虽然平台首期不绑定具体行业，但规格设计中必须预留“参考场景验证集”，用于校验知识模型、流程模型和指标模型是否足够可用。

## 12. 第一阶段验收指标

第一阶段建议至少满足以下验收项：

1. 提供统一的功能验证平台底座，可承载阶段一各节点的验证与演示
2. 支持 PDF/DOC/DOCX 的资料接入、版本记录和解析任务管理
3. 能从原始文档中形成结构化片段，并保留页码、章节与原文证据
4. 能抽取候选实体、事件、流程、规则、指标及关系
5. 提供知识治理工作台，支持术语归并、关系修正、流程补链、冲突处理、审核发布
6. 提供实体/事件图谱视图
7. 提供流程链路视图
8. 发布态知识支持检索、追踪和版本对比
9. 对外提供标准知识出口，为后续需求分析系统提供正式领域元素输入

## 13. 后续实施建议

后续实施不建议直接按“大而全平台”推进，而应拆成连续可验证的子项目：

1. 第一子项目：知识仓底座
2. 第二子项目：需求分析系统
3. 第三子项目：软件设计系统
4. 第四子项目：工具仓库 / 工具中台
5. 第五子项目：软件构建系统

其中当前最适合进入实施计划的，是**第二子项目：需求分析系统**；第一子项目仍以问题修复、质量补强和知识持续治理为主。

本次修订后，第一子项目内部执行顺序明确为：

1. `P1.1` 功能验证平台底座
2. `P1.2` 文档接入与结构化解析
3. `P1.3` 候选知识抽取
4. `P1.4` 知识治理与发布
5. `P1.5` 已发布知识仓、查询与图谱展示

在进入 `P2` 时，应以前述 `P1` 正式知识元素作为标准输入，同时允许 `P2` 现场新增临时元素并回流治理，不得反向要求 `P1` 先行完备所有领域细节。
