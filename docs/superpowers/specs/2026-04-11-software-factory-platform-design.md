# 软件工厂平台总蓝图设计

**日期：** 2026-04-11

**设计目标：** 构建一个私有化部署的软件工厂平台，以领域知识为起点，逐步形成知识仓、构建描述模型、交互式应用生成与组件资产复用闭环。

## 1. 平台定位

该项目不定义为单纯的知识库平台，也不定义为传统低代码平台，而定义为一个**知识驱动的软件工厂**。

平台长期闭环如下：

`领域资料 -> 知识仓 -> 构建描述模型 -> 应用生成 -> 组件复用/新组件沉淀 -> 反哺后续生成`

本轮设计已确认的边界如下：

- 产品形态：通用底座 + 行业扩展包
- 首期聚焦：流程/事件驱动系统 + 数据分析类应用
- 主要驱动人群：开发团队为主，兼顾业务专家参与
- 部署方式：企业私有化 / 本地化部署
- 第一阶段主验收物：高质量知识仓
- 第一阶段知识主模型：实体/事件图谱 + 流程链路双核心
- 第一阶段不绑定具体行业，先做行业无关底座
- 后续应用生成目标：以平台内可运行的元数据应用为主

## 2. 分阶段目标

### 阶段一：知识仓底座

目标是把 PDF/DOC/DOCX 等领域资料转化为高质量、可治理、可发布、可展示的知识资产。

这一阶段不以完整应用生成为主交付，而以如下能力为验收核心：

- 资料接入与版本管理
- 文档结构化解析
- 候选知识抽取
- 知识治理与发布
- 双核心知识展示
- 面向后续构建描述模型的知识出口

为避免出现“每个节点都要求前端验证，但验证平台何时建设、如何承载验证却未定义”的执行断点，阶段一内部执行顺序明确拆为 `P1.1` 到 `P1.5` 五个二级节点，并要求每个节点都具备对应的验证投影。

#### P1.1 功能验证平台底座

这是阶段一的前置使能层，不替代业务子系统本身，而是为后续各节点提供统一的可见、可测、可解释承载面。

- `P1.1.1` 前后端工程壳与运行环境
- `P1.1.2` 路由、导航与页面骨架
- `P1.1.3` 通用 API 契约、状态回显与任务日志
- `P1.1.4` 通用验证组件、证据查看与错误透传

建议技术选型：

- 前端壳：`React + Vite + TypeScript`
- UI 与验证工作台：`Ant Design`
- 页面路由：`React Router`
- 服务数据访问：`TanStack Query + Axios`
- 基础验证图形能力预留：`Cytoscape.js`、`React Flow`
- 端到端冒烟验证：`Playwright`

节点成果物：

- 可运行的前后端验证平台骨架
- 统一导航、通用详情抽屉、状态提示和错误透传机制
- 统一 API 客户端、环境配置和调试入口
- 支撑后续 `P1.2` 到 `P1.5` 的页面承载框架与验证基座

#### P1.2 文档接入与结构化解析

- `P1.2.1` 资料导入、归档与版本管理
- `P1.2.2` 解析任务调度与执行跟踪
- `P1.2.3` 结构化解析管线
- `P1.2.4` 文档接入/解析验证页细化

建议技术选型：

- 文档主解析器：`Docling`
- 复杂版面与元素切分增强：`Unstructured`
- `DOC` 转 `DOCX`：`LibreOffice Headless`
- `DOCX` 轻量回退：`python-docx`
- `PDF` 轻量回退：`PyMuPDF`
- 解析任务编排：优先沿用现有 `Python API + Job Runner` 结构，不单独引入重型调度平台

正式知识库抽取约束：

- “正式知识库抽取/重建”必须以 `Docling` 作为正式解析器
- 预览、调试链路可以保留轻量 fallback，但正式抽取链路不允许静默降级到 `python-docx`、`PyMuPDF` 或其他非 `Docling` 解析器
- 任一正式抽取文档未通过 `Docling` 成功解析时，整次正式抽取必须直接失败

节点成果物：

- 文档上传、归档、版本管理与解析任务流转
- 保留章节、表格、页码、锚点、块边界的结构化文档结果
- 可回溯的解析批次记录、错误记录与解析状态
- 文档解析验证页，可直接查看原文、结构化片段和解析质量

#### P1.3 候选知识抽取

- `P1.3.1` 领域 schema 与抽取对象定义
- `P1.3.2` 实体、关系、流程、规则、指标抽取
- `P1.3.3` 证据锚点、置信度与抽取批次记录
- `P1.3.4` 抽取结果验证页细化

建议技术选型：

- 抽取策略：`领域 schema 约束 + 规则抽取 + LLM 结构化抽取` 的混合方案
- 结构化输出格式：以统一 `JSON Schema / Pydantic Model` 约束实体、关系、流程、规则、指标
- LLM 编排增强：可选接入 `LlamaIndex Property Graph` 能力，但不作为首版硬依赖
- 实体消歧与别名归一：先用规则与词典归并，后续再引入向量或 embedding 辅助
- 抽取质量管理：必须保留 `sourceRefs`、`confidence`、`extraction_run_id`

正式知识库抽取约束：

- “正式知识库抽取/重建”必须使用结构化大模型抽取，不允许静默退回为规则-only 抽取
- 具体模型供应商可配置为主流大模型提供方，但必须在执行报告中记录实际 `provider / model`
- 任一正式抽取文档未使用结构化大模型成功完成抽取时，整次正式抽取必须直接失败
- 正式抽取必须生成执行报告，记录实际解析器、实际模型、候选数、关系数和失败原因

节点成果物：

- 面向 NAS 领域的抽取 schema 与对象字典
- 候选实体、关系、流程、规则、指标抽取管线
- 可追溯到文档片段的证据锚点和置信度记录
- 抽取结果验证页，可直接审查候选对象、证据和关系邻域

#### P1.4 知识治理与发布

- `P1.4.1` 术语统一与别名归并
- `P1.4.2` 关系修正与流程补链
- `P1.4.3` 审核、驳回、发布与版本管理
- `P1.4.4` 治理工作台验证页细化

建议技术选型：

- 治理工作流存储：沿用 `PostgreSQL` 承载候选项、审核记录、归并记录、发布版本和审计日志
- 审核交互：前端工作台 + 抽屉详情 + 批量审核操作
- 版本发布机制：发布态快照 + 审计记录 + 可回放发布批次
- 关系修正方式：人工治理为主，保留规则辅助与后续模型辅助入口

节点成果物：

- 候选知识治理工作台
- 术语归并、关系修正、流程补链、冲突处理能力
- 审核、驳回、发布、版本追踪与审计记录
- 治理验证页，可解释每次修订、发布与状态变化来源

#### P1.5 已发布知识仓、查询与图谱展示

- `P1.5.1` 发布态知识存储模型
- `P1.5.2` 检索、关系查询、流程追踪与版本对比
- `P1.5.3` 图谱视图、流程链路视图与实体详情
- `P1.5.4` 发布态知识验证页细化

建议技术选型：

- 发布态知识主存储：`Neo4j` 属性图
- 发布快照与调试导出：保留版本化 `JSON` 导出，作为审计与离线检查副产物
- 关系浏览与业务探索：`Neo4j Bloom`
- 平台内查询与展示：保留自研 `Web` 页面，作为日常验证与业务工作入口
- 查询 API：从“文件读取”升级为“图查询 + 证据回溯”的服务模式

节点成果物：

- 支持发布态知识对象、关系、证据、版本的权威知识仓
- 支持实体检索、关系追踪、流程追踪、版本对比和证据回溯的查询接口
- 图谱视图、流程链路视图、实体详情与关系邻域展示
- 发布态知识验证页，可直接解释“它是什么、与谁相关、由谁产生、证据在哪”

阶段一执行原则补充如下：

- `P1.1` 必须先落地，然后才能进入 `P1.2` 到 `P1.5`
- `P1.1` 到 `P1.5` 的执行顺序是串行的，每个节点只以前一节点的标准成果物作为输入，不依赖其内部实现方式
- `P1.2` 到 `P1.5` 每个节点都必须同时交付业务能力与验证投影
- 下游节点只能依赖上游节点对外发布的接口、数据契约、版本化产物和验证页面，不允许直接依赖上游节点的内部表结构、脚本细节、文件组织或具体技术选型
- 上游节点若发生技术替换，只要其对外契约与版本化成果物保持兼容，下游节点不得因此被迫重做
- 若上游节点必须调整契约，则必须通过显式版本升级、兼容期和回归验证来控制影响，禁止隐式传导到后续节点
- 验证平台不是一次性搭完后静止不动，而是随各节点推进逐步细化
- 任何节点若无法在验证平台中被直观看到、解释和回溯，就不能视为达到阶段验收标准

### 阶段二：构建描述模型与组件资产底座

目标是把已发布知识映射为后续应用可消费的构建描述，并建立组件资产中心的基础治理能力。

这一阶段重点回答两个问题：

- 领域知识可以被转换成哪些软件构建抽象
- 当前应用目标中哪些能力可以通过已有组件复用

### 阶段三：交互式应用生成闭环

组件闭环在这个阶段内生发生，而不是在应用完成后才发生。

应用开发主流程定义为：

`分析需求 -> 形成设计方案/构建描述 -> 功能解耦 -> 检索组件库 -> 命中复用 / 未命中开发 -> 形成应用`

在该阶段中，组件资产中心在生成过程中实时参与：

- 对目标能力做组件级解耦
- 检索已有组件
- 判断组件命中与适配方式
- 对未命中部分进入新组件开发/装配
- 将新组件纳入组件资产中心

### 阶段四：复用飞轮强化

在阶段三已形成生成内闭环的前提下，阶段四重点做规模化治理和强化：

- 组件标准化与版本治理
- 行业扩展包沉淀
- 规则模板、流程模板、分析模板积累
- 跨项目复用率提升

## 3. 总体架构

平台采用“双中台 + 验证底座 + 多子系统”的总体结构：

- **知识中台**：负责领域资料到知识资产的全过程
- **构建中台**：负责知识到软件构建描述的映射，并支撑组件复用与应用生成
- **功能验证平台底座**：负责承载阶段性功能验证、状态观察、证据回溯与演示验收

需要强调的是，功能验证平台底座是阶段一的实施前置层，不替代业务子系统本身。第一阶段业务架构仍按 6 个一级业务子系统划分，同时由验证底座统一承载它们的验证投影。

具体实现形态上，第一阶段采用“**模块化单体优先、按微服务边界设计**”的方式推进：

- 默认实现形态优先选择标准模块化单体，而不是一开始拆成多个独立部署的分布式微服务
- 但所有业务模块必须按微服务思路划分边界，即职责单一、契约清晰、存储边界明确、内部实现可替换
- 模块之间只允许通过显式接口、消息、版本化数据契约或受控应用服务交互
- 后续若某个模块需要独立扩容、独立部署或独立技术演进，应能够在不重写上下游业务逻辑的前提下拆出为独立服务
- 任何模块若无法被单独替换、单独测试、单独演进，就说明当前边界划分失败，需要在设计阶段回收重构

### 3.1 功能验证平台底座

职责：

- 承载阶段一各节点的前端验证页面与调试入口
- 提供统一的任务状态回显、日志观察、错误透传和证据查看
- 为文档、抽取、治理、图谱等节点提供统一的演示与验收界面
- 为后续阶段保留可复用的验证型页面框架

边界：

- 它是实施与验收承载层，不直接生产领域知识
- 它不替代资料接入、解析、抽取、治理、知识仓等业务子系统

### 3.2 资料接入子系统

职责：

- 接收 PDF/DOC/DOCX 等资料
- 记录来源、归属、批次、标签与版本
- 管理导入任务状态
- 提供权限控制与审计归属

边界：

- 只解决资料可控接入和可追踪问题
- 不在本子系统内做知识抽取结论

### 3.3 文档解析子系统

职责：

- 版面解析
- 章节切分
- 页码与锚点定位
- 表格提取
- 图片/OCR 处理
- 形成标准化文档片段

边界：

- 输出的是“可计算文档”
- 不是知识发布层

### 3.4 知识抽取子系统

职责：

- 从标准化文档片段中抽取候选实体
- 抽取候选事件、流程、规则、指标及关系
- 记录来源证据、抽取方式和置信度

边界：

- 输出的是“候选知识”
- 不允许直接写入发布态知识仓

### 3.5 知识治理子系统

职责：

- 术语统一
- 别名归并
- 关系修正
- 流程补链
- 冲突裁决
- 审核发布
- 版本管理

边界：

- 第一阶段最关键的产品中枢
- 知识质量由治理流程保证，而不是由抽取模型单独保证

### 3.6 知识仓与查询子系统

职责：

- 存储已发布知识
- 提供检索、关系查询、流程追踪、版本对比
- 提供图谱视图与流程链路视图
- 向其他系统输出权威知识结果

边界：

- 只消费已发布知识
- 不直接持有未治理候选知识

### 3.7 构建映射与扩展子系统

职责：

- 把知识对象映射为后续软件构建描述
- 为流程系统和分析系统提供统一元模型出口
- 为组件检索和应用生成提供领域语义输入

边界：

- 第一阶段只要求可映射、可验证、可扩展
- 不要求完成完整应用生成闭环

## 4. 统一知识元模型

第一阶段的知识仓不能以“文档片段”作为中心，而应以可治理、可发布的知识对象为中心。

建议定义以下 8 类一等对象：

### 4.1 Entity

表示领域中的稳定对象，例如组织、角色、资源、事项、单据、设备、指标对象等。

建议核心属性：

- `id`
- `name`
- `type`
- `aliases`
- `attributes`
- `status`
- `sourceRefs`
- `version`

### 4.2 Event

表示发生的业务事件或可触发的动作，例如受理、派单、审批、归档、告警、异常上报等。

建议核心属性：

- `id`
- `name`
- `trigger`
- `actor`
- `targetEntity`
- `preconditions`
- `postconditions`
- `sourceRefs`
- `version`

### 4.3 Process

表示具有顺序、角色和状态流转的流程链路。

建议核心属性：

- `id`
- `name`
- `steps`
- `roles`
- `inputs`
- `outputs`
- `decisionPoints`
- `relatedRules`
- `relatedEvents`
- `sourceRefs`
- `version`

### 4.4 Rule

表示制度约束、判断条件、阈值规则、合规要求等。

建议核心属性：

- `id`
- `name`
- `ruleType`
- `expression`
- `scope`
- `relatedEntities`
- `relatedProcesses`
- `relatedMetrics`
- `sourceRefs`
- `version`

### 4.5 Metric

表示指标、统计口径、维度、周期、阈值和分析定义。

建议核心属性：

- `id`
- `name`
- `metricType`
- `subject`
- `formula`
- `dimensions`
- `period`
- `thresholds`
- `sourceRefs`
- `version`

### 4.6 Relation

表示对象之间的显式关系，例如：

- `entity-owns-entity`
- `event-changes-entity`
- `process-contains-step`
- `rule-constrains-process`
- `metric-measures-entity`

### 4.7 Evidence

每条知识都必须挂接证据，禁止无证据知识发布。

建议至少记录：

- 来源文档
- 页码/章节
- 原文片段
- 抽取方式
- 置信度
- 人工确认记录

### 4.8 KnowledgeVersion

知识必须支持版本化，至少有以下主状态：

- 草稿
- 待审核
- 已发布
- 已废弃

## 5. 双核心知识视图

知识仓采用两个一等核心视图：

### 5.1 实体/事件图谱视图

用于表达：

- 术语体系
- 领域对象
- 事件因果
- 职责与角色
- 对象之间的显式关系

适合支持：

- 关系追踪
- 术语治理
- 知识网络浏览
- 规则挂接

### 5.2 流程链路视图

用于表达：

- 步骤顺序
- 角色参与
- 输入输出
- 状态流转
- 决策节点
- 规则约束

适合支持：

- 流程理解
- 链路分析
- 流程补链
- 构建描述映射

这两个视图共享同一套底层知识对象，只是观察方式不同，不能设计成两套完全割裂的数据体系。

除此之外，所有知识视图都必须能从验证平台进入，并支持至少以下验证动作：

- 查看来源文档与证据摘录
- 查看当前对象的关系邻域
- 看到当前对象处于候选态、治理态还是发布态
- 能从页面反向定位到对应的任务、版本或处理记录

## 6. 核心流程与质量闭环

平台第一阶段的端到端流程建议固定为 5 段：

### 6.1 资料入库

- 上传资料
- 记录资料元数据
- 建立版本与归属
- 创建解析任务

产物：受控资料资产

### 6.2 结构化解析

- 切分章节与段落
- 提取表格、图片与 OCR 内容
- 保留页码、章节锚点和原文定位

产物：可计算文档片段

### 6.3 候选知识抽取

- 使用规则抽取和模型抽取生成候选对象
- 标注置信度
- 挂接来源证据
- 允许冲突、重复和不完整

产物：候选知识集

### 6.4 治理与发布

- 术语归并
- 冲突处理
- 关系修正
- 流程补链
- 审核确认
- 版本发布

产物：发布态知识

### 6.5 查询与消费

- 检索发布态知识
- 图谱展示
- 流程链路展示
- 版本对比
- 向构建映射层输出知识结果

产物：权威知识出口

### 6.6 验证投影闭环

除上述 5 段业务流外，第一阶段执行过程中必须存在一条持续伴随的验证投影闭环：

- 将每个阶段节点的输入、处理中状态和输出结果投影到验证平台
- 允许从页面进入文档、证据、关系、流程、审核、发布等关键对象详情
- 允许定位失败任务、异常抽取、错误关系和缺失证据
- 使阶段验收不依赖命令行或数据库手工核查

产物：可观察、可解释、可验收的阶段实现结果

为确保第一阶段成果可用，建议设置 4 个质量门：

### 6.7 证据门

没有来源证据的知识不得发布。

### 6.8 一致性门

必须检测术语冲突、关系断裂、流程孤点、规则悬空等问题。

### 6.9 审核门

候选知识必须经过角色化审核后才能进入发布态。

### 6.10 版本门

每次发布必须可回溯到原始资料、抽取方式、审核记录与责任人。

## 7. 构建描述模型与组件资产中心

第一阶段虽然不要求完整应用生成，但必须从一开始为第二阶段和第三阶段预留接口。

### 7.1 构建描述模型定位

构建描述模型用于回答：

- 这个领域问题应由哪些软件能力组成
- 这些能力如何映射到对象、事件、流程、规则、指标与界面结构

建议后续逐步定义如下映射：

- `Entity -> 业务对象模型`
- `Event -> 动作/状态变更/触发器`
- `Process -> 流程定义候选`
- `Rule -> 校验规则/约束规则/告警规则`
- `Metric -> 分析主题/指标口径/报表定义候选`

### 7.2 组件资产中心定位

组件中心不是单纯的前端控件库，而是同时承担两类职责：

#### 生成期职责

- 在应用设计和生成过程中做组件级功能解耦
- 检索已有组件
- 判定命中与适配方式
- 支持复用决策

#### 资产期职责

- 新组件入库
- 版本管理
- 依赖管理
- 可视化管理
- 适用场景管理
- 支持后续项目再次检索与复用

### 7.3 组件分层

建议组件中心至少区分两层：

- **技术组件层**：表单控件、布局容器、图表容器、流程节点渲染器等
- **业务组件层**：案件受理卡片、事件处置流、审批链模板、指标分析面板、异常闭环模板等

## 8. 应用生成闭环

平台中的组件闭环发生在应用生成过程中，而不是在应用完成后才开始。

建议将应用开发流程定义为：

1. 分析需求
2. 形成设计方案
3. 生成构建描述
4. 对目标能力进行组件级解耦
5. 检索组件库
6. 对命中组件直接复用
7. 对未命中部分进入新组件开发/装配
8. 形成应用
9. 将新增组件纳入组件资产中心

这意味着“软件工厂”的正循环应表达为：

`知识仓提供领域语义 -> 构建描述形成应用方案 -> 组件检索与复用参与生成 -> 未命中组件被开发并入库 -> 反哺下一轮应用生成`

## 9. 角色与权限

第一阶段至少设计以下角色：

- **资料上传者**：上传与维护原始资料
- **知识治理者**：处理候选知识、做术语归并和关系修正
- **审核发布者**：审核并发布正式知识版本
- **普通查询者**：查询已发布知识
- **平台管理员**：负责模型接入、权限配置、审计与平台维护

关键要求：

- 角色职责分离
- 发布动作可审计
- 关键修改保留操作日志

## 10. 非功能要求

### 10.1 私有化可部署

- 文档、知识、索引、审计、权限应在内网闭环运行
- 模型能力需要支持本地模型或私有模型接入

### 10.2 可追溯

- 已发布知识必须回溯到原始资料、原文位置、抽取方式、审核记录与版本

### 10.3 可治理

- 系统重点不是一次抽对，而是支持持续校正与稳定发布

### 10.4 可扩展

- 支持未来增加行业扩展包、规则模板、流程模板、组件模板与词汇包

### 10.5 权限与审计

- 保留关键操作审计记录
- 支持按组织、角色、资料来源等维度控制访问范围

### 10.6 节点解耦与契约稳定性

- `P1.1` 到 `P1.5` 必须遵循“串行推进、接口解耦”的工程约束
- 每个节点的下游依赖对象只能是上游节点的标准输入输出契约、版本化成果物和验证投影，不得绑定其具体实现技术
- 节点内部实现可更换，例如解析器、抽取器、存储引擎、图谱引擎均可演进，但必须保证节点对外契约稳定或可版本化迁移
- 但“正式知识库抽取/重建”属于例外硬约束路径：该路径当前明确锁定为 `Docling + 结构化大模型抽取`，在未完成新一轮工程决策前不得自行降级或替换
- 禁止跨节点直接读取上游节点内部数据库表、临时文件、内存结构或未发布中间状态作为正式依赖
- 任一节点发生技术替换时，默认只允许在本节点内消化；若会影响下游，必须先升级契约版本并完成兼容验证

### 10.7 模块化与微服务式边界

- 第一阶段默认采用模块化单体实现，但模块边界必须按微服务标准设计
- 每个模块应具备单一职责、清晰接口、独立测试能力和可替换实现
- 模块之间禁止通过共享内部类、跨目录直接调用、隐式数据库耦合或私有脚本耦合来建立依赖
- 若未来需要拆为独立微服务，应以当前模块接口与契约为基础平滑迁移，而不是回头重做业务边界
- 技术选型服务于模块边界，而不是反过来让技术框架决定业务边界

## 11. 主要风险

### 11.1 知识仓退化为文档切片库

如果最终只得到全文检索和向量问答，而没有稳定的知识对象、关系和流程结构，则无法支撑后续软件生成。

### 11.2 过度依赖自动抽取

如果没有强治理流程，知识仓很快会失去可信度，后续团队不会使用其结果。

### 11.3 元模型抽象过重

如果第一阶段过度引入复杂的软件建模抽象，会拖慢知识仓底座建设，应坚持第一阶段以知识质量为中心。

### 11.4 行业无关底座过空

虽然平台首期不绑定具体行业，但规格设计中必须预留“参考场景验证集”，用于校验知识模型、流程模型和指标模型是否足够可用。

## 12. 第一阶段验收指标

第一阶段建议至少满足以下验收项：

1. 提供统一的功能验证平台底座，可承载阶段一各节点的验证与演示
2. 支持 PDF/DOC/DOCX 的资料接入、版本记录和解析任务管理
3. 能从原始文档中形成结构化片段，并保留页码、章节与原文证据
4. 能抽取候选实体、事件、流程、规则、指标及关系
5. 提供知识治理工作台，支持术语归并、关系修正、流程补链、冲突处理、审核发布
6. 提供实体/事件图谱视图
7. 提供流程链路视图
8. 发布态知识支持检索、追踪和版本对比
9. 对外提供标准知识出口，为后续构建描述模型提供输入

## 13. 后续实施建议

后续实施不建议直接按“大而全平台”推进，而应拆成连续可验证的子项目：

1. 第一子项目：知识仓底座
2. 第二子项目：构建描述模型与组件资产底座
3. 第三子项目：交互式应用生成闭环
4. 第四子项目：行业扩展包与复用飞轮强化

其中当前最适合进入实施计划的，是**第一子项目：知识仓底座**。

本次修订后，第一子项目内部执行顺序明确为：

1. `P1.1` 功能验证平台底座
2. `P1.2` 文档接入与结构化解析
3. `P1.3` 候选知识抽取
4. `P1.4` 知识治理与发布
5. `P1.5` 已发布知识仓、查询与图谱展示
