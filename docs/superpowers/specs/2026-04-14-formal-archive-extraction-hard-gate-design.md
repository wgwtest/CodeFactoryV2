# 正式知识库抽取硬门槛设计

## 背景

当前项目里同时存在两类链路：

1. 文档预览、调试、单文件排查
2. 知识库正式抽取/重建

这两类链路的目标不同，容错策略也不能相同。

此前正式抽取链路虽然接入了 `Docling`、结构化大模型适配与 OpenAI 兼容 provider，但运行时仍可能静默降级到：

- `PyMuPDF`
- `python-docx`
- `Unstructured`
- 规则-only 抽取

这会导致“看起来完成了正式建库”，但实际产物并未真正经过目标链路处理。

## 本轮决策

从本轮开始，`知识库正式抽取/重建` 明确采用以下硬约束：

- 正式解析必须使用 `Docling`
- 正式抽取必须使用结构化大模型
- 不允许在正式链路中静默降级到轻量解析器或规则-only 抽取
- 若 `Docling` 未生效、结构化大模型未生效、执行元数据缺失，整次正式抽取必须直接失败
- 每次正式抽取必须生成执行报告，记录真实执行情况

补充说明：

- 大模型供应商不强制限定为某一家
- 只要求是当前工程接入的主流大模型 provider，并能提供结构化输出
- 报告中必须记录实际 `provider` 与 `model`

## 作用范围

本设计只作用于：

- 知识库正式抽取
- 知识库重建
- 通过档案管理入口触发的正式建库任务

本设计不直接作用于：

- 文档页预览
- 本地调试脚本中的临时解析
- 开发期故障排查

也就是说，预览/调试链路可以继续保留容错能力，但正式链路不允许用这些容错结果冒充正式产物。

## 实施方式

### 1. 解析阶段硬校验

- `PDF / DOC / DOCX` 在正式抽取时必须实际由 `Docling` 成功解析
- 若解析器最终不是 `docling_pdf` 或 `docling_docx`，直接失败
- 若 `Docling` 未产出有效文本，直接失败

### 2. 抽取阶段硬校验

- 正式抽取时必须强制尝试结构化大模型抽取
- 若大模型调用失败、schema 校验失败、或没有记录实际 `provider / model`，直接失败
- 不允许静默退回为规则-only 抽取结果

### 3. 执行报告

每次正式抽取必须输出 `archive_id-extraction-report.json`，至少包含：

- `strict_mode`
- 每个文档的 `parser_name`
- 每个文档的 `llm_provider`
- 每个文档的 `llm_model`
- 每个文档的 `candidate_count`
- 每个文档的 `relation_count`
- 总体 `summary`

## 验收标准

满足以下条件，可认为该设计已落实：

1. 正式抽取入口默认启用硬门槛模式
2. 任一正式文档若未实际使用 `Docling`，任务会失败
3. 任一正式文档若未实际使用结构化大模型，任务会失败
4. 成功任务会生成执行报告，而不是只生成知识 JSON
5. 预览/调试链路不因该门槛被误伤
