## 1. 阶段定位

### 1.1 `P5` 的真实目标

`P5` 不是继续做需求分析，也不是继续做软件设计。

`P5` 的目标是把软件工厂内部已经冻结的正式成果物，真正落地为一个**脱离工厂内部运行态的独立交付目录**。

因此，`P5` 是软件工厂主链中的“最终交付实现阶段”，而不是：

- 知识抽取阶段
- 需求建模阶段
- 软件设计阶段
- 工具资产治理阶段

`P5` 首版要回答的问题是：

- 最终交付物落在哪
- 以什么目录形态存在
- 如何从 `P3` 冻结设计和 `P4` 供给资产组装成真实工程
- 如何判断这次组装是否可行
- 如何把组装中暴露的问题回流给上游

### 1.2 `P5` 首版服务对象

`P5` 首版只支持以下对象：

- 软件形态：`Web 前后端工程`
- 第一交付载体：本地独立交付目录
- 交付完成度：结构完整、关键代码已生成，但允许部分占位待继续开发

### 1.3 `P5` 首版非目标

首版明确不做：

- 直接部署到服务器
- 直接输出安装包 / 可执行包
- 多软件形态并行支持
- 在 `P5` 中重新做设计
- 让 `P5` 反向接管 `P4` 资产治理职责

## 2. 首版边界

### 2.1 交付目录形态

`P5` 首版的交付根目录采用标准分区：

- `frontend/`
- `backend/`
- `deploy/`
- `docs/`

说明：

- `frontend/` 承载前端工程
- `backend/` 承载后端工程
- `deploy/` 承载环境样例、构建脚本、部署占位文件
- `docs/` 承载交付说明、缺口说明、构建与导出记录

### 2.2 导出路径规则

首版导出规则固定为：

- 默认导出到工厂固定根目录
- 允许用户改成自定义路径

因此，`P5` 不只是生成工程，还必须显式承载一次“导出落地动作”。

### 2.3 校验深度

首版强制执行两类校验：

- 静态结构校验
- 本地构建校验

首版不强制执行：

- 完整运行时启动校验

### 2.4 输入主次关系

`P5` 首版输入优先级固定为：

1. 主输入：`P3` 冻结设计对象
2. 辅输入：`P4` 已审定 / 已供给资产结果

这意味着：

- `P5` 不重新决定实现路线
- `P5` 不以 `P4` 资产为唯一主导
- `P5` 只负责把已经冻结的蓝图和已经供给的资产组装成最终交付

## 3. 与 `P3 / P4` 的关系

### 3.1 `P3` 必须冻结唯一实现路线

`P5` 首版不能自己决定技术路线。

唯一实现路线必须由 `P3` 作为正式设计结果之一冻结下来。它至少应包括：

- 软件形态
- 前端实现路线
- 后端实现路线
- 数据存储方式
- 目录结构约定
- 构建 / 启动方式
- 部署占位方式

当前结论：

- `P3` 现有正式设计中还缺这一层
- 后续必须把“实现路线冻结（Implementation Profile Freeze）”补入 `P3`

### 3.2 `P4` 的角色

`P4` 的职责不是替 `P5` 做最终装配，而是：

- 提供已审定 / 已供给资产
- 提供可查询、可获取的供给结果
- 维持平台级工具资产仓

`P5` 在首版中只允许：

- 查询 `P4` 结果
- 获取 `P4` 已审定资产
- 在已审定资产中做装配切换

`P5` 不允许：

- 越过 `P4` 审定绑定未审定资产
- 直接修改 `P4` 内部状态
- 直接把 `P5` 的问题回流给 `P4`

### 3.3 `P4` 的非修订语义

`P5` 发现“装不起来”时，不能默认解释成：

- `P4` 现有工具错误
- `P4` 现有工具必须被修订

更合理的解释是：

- 可能是 `P3` 的蓝图不匹配
- 可能是 `P3` 的目标契约不完整
- 可能是 `P5` 装配规则有问题
- 也可能只是“当前业务场景与既有资产不契合”

因此，`P4` 在这条链里不应承接“来自 `P5` 的修订命令”。

更准确的规则是：

- `P5` 只输出问题报告
- `P3` 是唯一回流仲裁者
- `P3` 判断问题是否需要形成新的供给目标
- `P4` 只接受 `P3` 发起的**新供给任务 / 派生任务 / 组件拆分任务**

这意味着：

- `P4` 的平台级既有资产不能因某一次 `P5` 装配不契合而被默认改写语义
- `P4` 可以内部继续做 bug 修复、依赖升级、质量优化等内部修订
- 但“面向某次业务装配的不契合”，原则上先按新供给目标处理，而不是按旧资产修订处理

### 3.4 对“P4 完全无修订”的校正

如果把上述结论再简化成“`P4` 完全没有修订”，这个说法仍然过度绝对。

更准确的正式口径应当是：

- `P4` 不直接承接来自 `P5` 的业务不匹配修订命令
- `P4` 仍保留平台内部质量修订、自演进、缺陷修复和依赖治理能力

也就是说：

- `P5` 发现业务不匹配时，不能直接要求 `P4` 改写既有资产语义
- 但 `P4` 内部仍可依据自身质量闭环持续优化资产池

## 4. 核心对象模型

### 4.1 `P5DeliveryOrder`

`P5` 的第一核心对象是交付主单。

一份冻结后的 `P3` 设计，对应一张 `P5DeliveryOrder`。

它至少记录：

- 来源 `P3` 设计标识与版本
- 来源 `P4` 供给结果快照标识
- 当前交付状态
- 当前尝试次数
- 是否已形成正式完成结果

### 4.2 `P5AssemblyAttempt`

同一张交付主单下允许多次装配 / 导出尝试。

每次尝试必须独立记录：

- 尝试编号
- 使用的导出配置
- 使用的资产选择结果
- 校验结果
- 缺口记录
- 回流任务记录
- 导出目录位置

首版目录输出规则固定为：

- 每次尝试输出到独立版本目录
- 不覆盖旧尝试结果

### 4.3 `P5AssemblyPlan`

`P5AssemblyPlan` 是当前这次尝试的权威装配事实对象。

它至少应表达：

- 业务模块清单
- 每个模块的目标职责
- 每个模块落到前端 / 后端 / 部署 / 文档中的位置
- 每个模块当前绑定的 `P4` 已审定资产
- 哪些模块仍是占位节点
- 模块间依赖关系

### 4.4 `P5ExportConfig`

用于记录：

- 导出根目录
- 自定义路径
- 目录命名规则
- 构建 profile
- 尝试备注

### 4.5 `P5ValidationReport`

用于记录两类验证：

- 模块装配是否闭合
- 目录与构建是否闭合

验证优先级固定为：

1. 先验证模块装配闭合
2. 再验证目录与构建闭合

### 4.6 `P5GapRecord`

用于记录：

- 模块缺口
- 资产不匹配
- 装配冲突
- 构建阻塞点

首版要求：

- 缺口既要在工厂内部留痕
- 也要在导出目录中形成显式说明

### 4.7 `P5FeedbackTask`

`P5` 发现问题后，必须自动创建反馈任务。

但反馈任务默认只进入“待人工确认”状态，不自动重开上游流程。

## 5. 主流程

首版标准主流程固定为：

`接收冻结设计 -> 拉取 P4 已审定资产 -> 生成装配计划 -> 在画布中完成资产装配选择 -> 验证模块装配闭合 -> 生成交付目录 -> 执行静态结构与构建校验 -> 生成交付说明与缺口清单 -> 自动创建反馈任务 -> 标记尝试结果`

关键约束如下：

- 复用优先，缺口允许占位
- 装配时只能在 `P4` 已审定 / 已供给资产中切换
- 若无已审定资产，允许占位继续装配，但必须自动创建反馈任务
- 可导出“带缺口标记”的结果，但不能标记为正式完成

## 6. 装配画布主视图

### 6.1 角色定位

`P5` 首版主入口不是表格页，而是：

- 装配画布主视图

这张画布的作用不是自由绘图，而是把 `P5AssemblyPlan` 作为结构化对象投影出来，让用户直观看到：

- 蓝图如何被装配
- 哪些模块命中了现有资产
- 哪些模块仍然占位
- 哪些位置存在缺口

### 6.2 层级规则

画布采用双层结构：

- 主层级：业务模块粒度
- 次层级：工程目录投影粒度

用户首先看到的是业务模块装配关系，再下钻看到它们分别落入：

- `frontend/`
- `backend/`
- `deploy/`
- `docs/`

### 6.3 节点规则

首版至少应区分：

- 已命中资产模块
- 占位模块
- 前端宿主
- 后端宿主
- 部署单元
- 文档单元

硬约束：

- 缺口模块必须作为明显不同的占位节点
- 在视觉上必须与已命中资产模块严格区分

### 6.4 首版可编辑性

首版允许局部调整，但不能改 `P3` 冻结下来的设计语义。

首版优先支持的可编辑项是：

- 资产装配调整

具体规则：

- 只允许在 `P4` 已审定 / 已供给资产中切换
- 不允许直接绑定未审定资产
- 不允许在 `P5` 中重新定义模块语义

### 6.5 首版工作台壳层

`P5` 首版前端不应复用当前通用知识库顶部导航壳。

正式口径应固定为：

- `P5` 使用独立工作台壳层
- 不在顶部展示“知识库管理 / 文档导入 / 知识审核发布 / 知识图谱 / 需求规格 / 建模引导”这类跨阶段导航
- 当前工作对象、当前构建运行状态和当前导出结果，必须在同一工作台中可回看、可切换、可追踪

因此，`P5` 页面入口应该更接近 `P3 / P4` 的独立驾驶舱，而不是门户中的普通内容页。

### 6.6 阶段工作台视觉风格

`P5` 的视觉风格不应只停留在节点级说明中，而应作为阶段级工作台规则单独固定。

正式口径固定为：

- `P5` 继承 `P6.3` 的平台级设计语言
- `P5` 阶段工作台继续继承当前 `P4` 已验收的驾驶舱气质
- 阶段级风格基线应以轻灰或浅灰工程画布、浅色头部、白色高密度工作卡、克制阴影为主
- 阶段级风格保留浅色、半透明、轻浮层页头容器与白色高密度子卡片
- 若存在页内工作区切换，应优先采用 `P4` 的分段式实色导航或分段标签式工作区切换，不使用重渐变激活态
- 活动态使用低饱和莫兰迪实色面，不使用强渐变

阶段个性固定为：

- 使用偏钢蓝、天青、冷灰蓝的构建语义色
- 运行日志区允许保留局部深色容器
- 已命中、占位、阻塞状态需有清晰但克制的色彩区分
- 缺口区允许使用低饱和暖色提示面
- 输出目录预览区允许使用等宽字与轻控制台气质

应避免：

- 不采用门户式顶部导航壳
- 大面积深色英雄区
- 径向渐变和装饰性背景主导页面
- 普通后台表单页式平铺
- 节点设计重复定义整套阶段风格而不是记录继承与局部例外

### 6.7 首版工作台分区

`P5` 首版工作台至少应包含以下五个区块：

#### 6.7.1 交付主单队列区

用于展示和选择当前处理对象，至少包括：

- `P5DeliveryOrder` 列表
- 来源 `P3` 订单标识
- 来源 `P4` 供给快照 / 工具订单结果标识
- 当前状态
- 最近一次运行结果

#### 6.7.2 装配流程主视图区

这是 `P5` 首版的核心区域。

至少需要看到：

- 当前业务模块装配图
- 模块到 `frontend / backend / deploy / docs` 的投影
- 已命中资产模块
- 占位模块
- 当前装配链路顺序

#### 6.7.3 构建运行与监控区

`P5` 首版不是静态页面，必须呈现最小运行态。

至少应展示：

- 当前运行单 / 尝试单状态
- 模拟执行器状态
- 关键进度节点
- 最近日志
- 成功 / 失败 / 阻塞原因

#### 6.7.4 输出结果预览区

至少应展示：

- 导出目录结构预览
- `build-manifest.json`
- `delivery-report.md`
- `gap-list.md`
- 最近一次输出目录位置

#### 6.7.5 缺口与反馈区

至少应展示：

- 当前缺口清单
- 缺口分类
- 反馈任务
- 回流目标说明

## 6.8 首版最小联调输入

在正式 `P3 / P4` 全链路完全接上前，`P5` 首版必须先具备最小模拟输入能力。

至少需要：

- `P3` 冻结设计模拟输出
- `P4` 已供给资产模拟输出
- `P5` 基于两者生成装配运行单

没有这层模拟输入，`P5` 无法形成真正的最小闭环。

## 7. 导出目录与交付元数据

### 7.1 每次尝试的目录规则

同一张主单下，每次尝试生成独立版本目录，例如：

- `delivery-order-001/attempt-001/`
- `delivery-order-001/attempt-002/`

### 7.2 导出目录中的说明文件

导出目录首版至少应附带：

- `docs/delivery-report.md`
- `docs/gap-list.md`
- `build-manifest.json`

说明：

- `delivery-report.md` 说明本次交付的构成、资产命中情况、验证结果
- `gap-list.md` 说明当前缺口、占位点和回流建议
- `build-manifest.json` 说明本次尝试的元数据、目录结构、版本和构建结果

## 8. 验证与回流闭环

### 8.1 闭合判断依据

`P5` 对“模块装配是否闭合”的判断，不应主要靠现场试出来，而应优先基于两类正式输入共同判断：

1. `P3` 的冻结设计对象
2. `P4` 的已审定 / 已供给资产结果

### 8.2 问题分类

`P5` 首版发现问题时，至少分为三类：

- 设计缺口
- 供给缺口
- 装配 / 构建缺口

### 8.3 回流规则

回流规则固定为：

- `P5` 自动创建反馈任务
- 默认进入待人工确认状态
- 不自动重开 `P3 / P4`

结构性约束：

- `P5` 只上报问题，不直接驱动 `P4`
- `P3` 是唯一回流仲裁者
- `P4` 只接受 `P3` 发起的新供给目标，而不是 `P5` 的直接修订请求

## 9. 首版实施顺序

当前 `P5` 首版的正确实施顺序应固定为：

1. `P5.1` 最小构建闭环
   - 主单
   - 装配运行
   - 独立工作台
   - 运行监控
   - 模拟输入
   - 模拟输出
2. `P5.2` 运行生成与监控深化
   - 更完整执行器
   - 校验闭合
   - 重试与多次尝试
3. `P5.3` 缺口回流与追溯
   - 反馈任务
   - 回流仲裁
   - 追溯链

也就是说：

- `P5.3` 不能早于 `P5.1`
- 先有可运行闭环，后有正式回流闭环
